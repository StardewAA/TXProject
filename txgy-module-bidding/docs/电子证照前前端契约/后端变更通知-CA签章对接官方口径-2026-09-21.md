
## 四、接入避坑（本轮实修，前端自测时必看）

### 坑 1：公开/回调端点为什么曾 401（已修，但要知道原因）
框架 `TxgyWebSecurityConfigurerAdapter` **扫描 `@PermitAll` 生成免登录 URL 列表**。
**缺 `@PermitAll` → Security 在过滤器层直接 401**，此时连 `@TenantIgnore` 都没机会生效。
而未登录请求又**没有租户上下文** → 前端补 `tenant-id` 头后仍需登录态 → **两头都进不去**。

**已修端点**（现均 200）：
| 端点 | 修复 |
| --- | --- |
| `GET /bidding/notice/public/list` | + `@TenantIgnore` |
| `GET /bidding/notice/public/detail` | + `@TenantIgnore` |
| `POST /bidding/ca/share/seal/callback` | + `@PermitAll` + `@TenantIgnore` |
| `POST /bidding/ca/share/seal/client-callback` | + `@PermitAll` + `@TenantIgnore` |

> **前端记住**：大厅公开接口（公告列表/详情/外部公告）**不要带 token、不要带 tenant-id**，直接请求即可。

### 坑 2：回调落库的租户归属（后端已修，前端需知）
官方回调**不带租户**，而后端**按"待签文件 Hash"匹配台账**。
相同内容的文件在不同租户下**哈希相同** → 曾存在"误改他租户台账"隐患。
**已修**：跨租户找候选 → 按 `tenant_id` 分组 → 在各租户上下文内分别回写。

**对前端的含义**：**签章前必须先登记台账**（`/bidding/ca/seal/document` 或对应登记接口），
否则回调回来**匹配不到**（后端会记 warning 并跳过，不报错）。

#### ② 一处必须知道的口径差异：两个验签口径、两把密钥

- 文件盖章（`seal/document`）由**服务端本地密钥**（`LocalCryptoUtils` 统一测试账号私钥，证书 SN `SN-LOCAL-CA-TEST-0001`）对文件 SM3 签名；

### 8.9 ⛔ 后端请求：文件级摘要缺国密来源（"扫码签名"链路只能拿 SHA-256 占位）（2026-09-21）

**问题**：文件摘要分两条链路，目前只有一条是国密口径 ——

| 链路 | 文件摘要从哪来 | 是否国密 |
| --- | --- | --- |
| **盖章** `POST /bidding/ca/seal/document` | 后端对**文件字节**自行算 SM3（`LocalCryptoUtils.sm3Hex(content)`）→ SM2 对摘要签名 → 台账存 `sm3_hash` / `signature` | ✅ SM3（GB/T 32905） |
| **扫码签名** `POST /bidding/ca/sign/qrcode` 等 | 入参 digestHex 由前端提供；上传响应只有 sha256，后端只有「文本 → SM3」（`GET /bidding/ca/sm3?text=`），**没有「按 fileId 取文件 SM3」的接口** | ❌ 只能拿 **SHA-256** 占位（国际算法） |

**算法分层的依据**（便于统一口径，避免"文件走 SM2、什么走 SM3"这类混淆）：

- 国密组合 = **SM3 摘要 + SM2 签名**：`docs/接口互认/01-移动数字证书CA互认技术规范.md`「使用国密算法的数字证书宜采用 SM3 杂凑算法和 SM2 加密算法」（国际算法对应 SHA256 + RSA）；
- 项目配置：`CaSdkProperties.digestAlgorithm = "SM3"`（待签名原文摘要算法）、`publicKeyAlgorithm = "SM2"`（签名证书公钥算法）；
- 代码：`CaSealServiceImpl#signAndPersist()` → `sm3 = sm3Hex(content)`（对文件字节）→ `signature = sm2SignDigestHex(sm3)`（SM2 对**摘要**签名）；台账验签 = 重算 SM3 + 公钥验 SM2；
- 文件加密/解密另有 **SM4**（GB/T 32907）：官方 08/09 号指南 = 投标文件 SM4 加密 + 密钥数字信封 + 开标解密；
- 该缺口 30 号文档 §七早有登记（「上传响应暂为 sha256，真实 SM3 由文件服务扩展后带回」），至今未落地。

**请后端加一个接口**（二选一即可）：

```
GET /admin-api/bidding/file/sm3?id=<fileId>      → {"code":0,"data":"<64 位小写 hex>"}
GET /admin-api/bidding/ca/sm3/file?id=<fileId>   → 同上
```

- 语义：按 fileId 取其**存储坐标**的文件字节，计算 **SM3（GB/T 32905）**；
- 权限：`isAuthenticated()` 即可（与现有 `/bidding/ca/sm3` 一致）；
- 病毒口径复用现成规则（INFECTED 拒发），且**只回摘要不回字节**，避免变成绕过病毒检查的取文件旁路；
- 有了它，扫码签名链路的文件摘要才是国密口径，也才能与盖章台账的 `sm3_hash` 对上。

**前端现状（已如实标注，不冒充）**：`CaSignEntry` 一旦检测到"摘要来自文件 sha256"，会在摘要上方显示橙色标签 **SHA-256 占位** 并说明原因与替代路径；文件类签名在**测试态**可用，但不作为国密口径交付。
