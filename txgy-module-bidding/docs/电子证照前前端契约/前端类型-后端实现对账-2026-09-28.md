## 一、必须修的不一致（7 处）

### 1. Q3 `GET /bidding/certificate/stats` —— 出参字段名整套不一致（影响看板 5 张卡片）　✅ **已修复**

| | 内容 |
| --- | --- |
| 前端期望 | `api/bidding/certificate/index.ts:461-476` 的 `CertificateStats`：`total` / `active` / `expiring` / `abnormal` / `cancelled` / `unverified` / `byStatus` |
| 后端实现 | `CertificateStatsRespVO`：`total` / `statusCounts` / `verificationCounts` / `typeCounts` |
| 影响 | 前端读 `active/expiring/abnormal/cancelled/unverified` 全是 `undefined` → 卡片显示空；`byStatus` 不存在（后端叫 `statusCounts`） |
| 建议 | **后端补齐**（纯增量）：① `byStatus` = 现有 `statusCounts`（两者都发，兼容）；② 五个扁平桶按**字典 `color_type` 动态分桶**（不硬编码状态名）：`active`=success 桶、`expiring`=warning 桶、`abnormal`=error 桶、`cancelled`=info 桶、`unverified`=`verificationCounts.UNVERIFIED` |

### 2. Q5 `GET /bidding/qualification/stats` —— 缺 `byStatus`　⏳ **待补**（服务文件在并发改动中）

- 前端 `api/bidding/qualification/index.ts:683-692`：`total/valid/expiring/expired/unlinkedStaff/**byStatus**`；
- 后端 `QualificationStatsRespVO`：前五项都有，**无 `byStatus`**；
- 建议：后端补 `byStatus`（按 `qualStatus` 逐码计数，与 Q3 同口径，动态取字典不硬编码）。

### 3. Q1/Q6 导入入参形态：前端发 `{fileId}`，后端要 multipart `file`

- 前端：`certificate/index.ts:732` `importCertificates(data: {fileId:number})`、`qualification/index.ts:668` 同形；
- 后端：`CertificateController#importCertificates(@RequestParam("file") MultipartFile)`、`QualificationController#importQualification(...)`；
- **为什么后端这样做（2026-09-28 澄清）**：**infra 未提供"按 fileId 取文件内容"的方法**，后端拿到 `fileId` 也无法读到 Excel 字节流，
  故只能 multipart 直传；同源限制也解释了 Q16 的 `evidenceFileIds` 无法回填文件名；
- 建议：**前端改为 multipart 上传**（`FormData` 附加 `file`），模板取 `GET /bidding/{certificate,qualification}/import-template`；
  后端已按此实现并在《后端变更通知-给前端.md》条目 17/18 说明，本条再次确认为"因 infra 能力所限的唯一可行形态"。

### 4. Q1/Q6 导入回执字段名：`failCount` / `totalRows`　✅ **已修复（证照侧）**；⏳ 资质侧待补（同文件阻塞）

- 前端 `ImportResp`（`certificate/index.ts:499-506`、`qualification/index.ts:695-700`）：`totalRows` / `successCount` / `failCount` / `failures[{message,rowNum}]`；
- 后端：`successCount` / **`failureCount`** / `failures[{rowNum,message}]`；
- 影响：前端读 `failCount`、`totalRows` 为 `undefined`（失败条数、总行数显示为空）；
- 建议：后端补 `failCount`（= `failureCount` 别名，两个都发）与 `totalRows`（= 数据行数）。

### 5. Q6 导出路径：前端 `/export-excel`，后端 `/export`　✅ **已修复**（后端双路径映射）

- 前端 `qualification/index.ts:673`：`requestClient.download('/bidding/qualification/export-excel', ...)`；
- 后端 `QualificationController`：`@GetMapping("/export")`；
- 影响：404；
- 建议：**后端加一条 `/export-excel` 映射**（旧 `/export` 保留），一行改动、零前端改动；
  若坚持契约只留一个，则需前端改（契约 Q6 原文写的是 `GET /bidding/qualification/export`）。

### 6. Q2 `POST /bidding/certificate-verify/verify-batch` —— 容器名与元素字段名不一致　✅ **已修复**

- 前端 `certificate/index.ts:478-494`：`VerifyBatchRespVO.items[]`，元素 `{certId, certName, accepted, verifyResult, verifyChannel, message}`；
- 后端：`CertVerifyBatchRespVO{results[], successCount, failureCount}`，元素 `{certId, success, message}`；
- 影响：前端逐条结果表读 `items` 为 `undefined`；`accepted/verifyResult/verifyChannel/certName` 均为空；
- 建议：后端补 `items`（= `results` 的别名字段，元素含 `certName/accepted/verifyResult/verifyChannel/message`；
  `accepted` 对应现有 `success`），或前端改用后端形态（二选一，推荐前者零前端改动）。

### 7. Q11 `POST /bidding/personnel-certificate/batch-renew` —— 出参形状 + 入参模式　✅ **已修复**

- 前端 `personnel/index.ts:604-610` 期望 `BatchResult` **对象**：`{total, successCount, failCount, failures:[{id,name,message}]}`；
  后端返回**裸数组** `PersonnelCertBatchRenewItemRespVO[]{id, success, message}` → 前端读 `successCount` 为 `undefined`；
- 入参：前端 `BatchRenewReq`（`personnel/index.ts:594-602`）支持两种模式：`items[]`（逐条）**或** `certIds[] + newValidTo`（统一设同一有效期）；
  后端只实现了 `items[]` → "统一批量设期"模式点了没反应；
- 建议：后端返回包装对象（或两个都发）+ 支持 `certIds+newValidTo` 模式（后者属增量能力，建议一并补）。
