# 后端变更请求：主体档案合并为「一租户一档」（角色不再拆档）——2026-09-20

> 提出方：前端（招投标模块）。依据：《招标投标法》第 25/26 条（投标人=法人/其他组织）、GB 32100-2015（统一社会信用代码唯一键）、
> 07-主体域前端交付-业务口径说明 §5（"主体类型 BIDDER/TENDERER 是企业扮演的角色，同一家企业可同时是投标人和招标人，
> **别在界面上固化成二选一档案**"）。
> 用户裁定（2026-09-20）：① 主体档案入口搬到「资质与证书管理」目录；② 招投标人用的是同一主体档案，**不需要分开**。

---

## 一、现状与问题

| 项 | 现状 | 问题 |
|---|---|---|
| 表唯一键 | `bidding_subject_profile`：`uk_subject_profile_type (tenant_id, subject_type, deleted)` | **同一租户（同一家企业）强制按 BIDDER/TENDERER 各存一份档案** |
| 前端页面 | `subjectProfile/index.vue` 提供「投标人/招标人」双档切换 | 同企业名称/uscc/法人/执照要填两遍，改甲忘乙、两套数据可能不一致 |
| 业务口径 | 07 文档 §5 明确"别固化成二选一档案" | 表结构与接口（按 subjectType 分存分查）恰好固化了二选一 |
| 法规 | 投标人是法人/其他组织，uscc 是企业唯一身份 | 角色是企业的业务身份（授权维度），不是档案主键 |

**结论：档案应是一份（企业主体，uscc/租户唯一）；投标人/招标人只是该企业被平台授权的角色，角色信息留在授权表，不拆档案。**

---

## 二、后端变更请求（4 项）

### 2.1 档案唯一键：一租户一档（核心）

`bidding_subject_profile` 唯一键由 `(tenant_id, subject_type, deleted)` 改为 **`(tenant_id, deleted)`**
（租户内一份档案；同 uscc 重复建档仅体现在 tenant 维度，跨租户仍可同 uscc——平台多租户各自维护自己档案，符合 T 轨隔离）。

- `subject_type` 列**保留**，语义降级为「角色标记」（记录最先建档的角色或最近一次保存携带的角色，**不参与唯一键/不参与 upsert 判定**）。
- 存量数据迁移建议（由后端定执行时机，前端不执行 SQL）：若某租户已有 BIDDER/TENDERER 两行，保留 `deleted=0` 中较新/信息更全的一行，
  另一行置 `deleted=1`（保留留痕，不物理删除）；`complete_flag` 按保留行核算。

### 2.2 接口：档案读写不再按类型分档

- **GET /bidding/subject/profile/get**：`subjectType` 参数改为**可选**（前端可传可不传）；后端一律返回**本租户唯一档案**（不存在返回 null，语义不变）。
- **POST /bidding/subject/profile/save**：请求体 `subjectType` 改为可选；后端按 `tenant_id` 做 **upsert（一租户一档）**，
  不再存在"同一租户两条档案"分支；返回主键 id 不变。若请求携带 subjectType，仅回写角色标记列，不作为新档案分键。

### 2.3 资格门：保持按角色授权，档案完善度取唯一档案（后端行为不变或微调）

投标资格（后续投标递交预留）看 BIDDER 授权；招标人发布资格（notice/filing 前置断言）看 TENDERER 授权——
**授权仍按角色**（`bidding_subject_auth` 不动，`uk_subject_auth_tenant_type` 保留）。变化仅在：断言时读取的
档案完善度（`complete_flag`）来自**唯一档案**，不再因类型取不到。`GET /bidding/subject/profile/eligibility` 的
`subjectType` 参数保留（用于判定"该角色是否已授权"），但档案完善度读取同一份档案。

### 2.4 经办人绑定：建议同步去类型（可选，本期不阻塞）

`bidding_subject_user` 的 `uk_subject_user_bind (tenant_id, subject_type, user_id, deleted)` 建议改为
`(tenant_id, user_id, deleted)`——经办人是"企业的操作人"，绑定到企业而非角色（同人同企业无需绑定两次）。
**若本期不做也可接受**：前端 subjectAuth 页面暂不展示经办人角色差异，接口字段保持不变。

## 三、前端行为（本轮已落地）

1. **菜单归位**：主体档案页面（`bidding/subjectProfile/index`）菜单从「主体信息与授权管理」（6759）迁至
   「资质与证书管理」（60005000）目录下（6760 sort=0 排第一位）；前端组件/路由路径不变，
   菜单 SQL 见 `sql/history/2026-09-20-subject-profile-relocate.sql`；6759 目录保留（其下为平台侧授权管理 6762/6763）。
2. **页面单档化**：`subjectProfile/index.vue` 移除 BIDDER/TENDERER 双档切换，改为"企业主体档案 ×1 + 角色只读标签"；
   加载与保存仅调一次档案接口（不传/传任选角色）。
3. **调用点统一**：`certificate/modules/cert-form.vue`（取本企业名）、`material-check.vue`、`safety-risk.vue`、
   `safety-risk/index.vue`（取本企业主体）由「BIDDER 失败再试 TENDERER」改为**单次无类型调用**
   `fetchSubjectProfile()`（签名 `subjectType?: string`，不传即不发送该参数）。
4. **不回归**：平台侧 `subjectAuth`（授权管理）保持现状（授权按角色展示不变）。

## 四、验收（达成即算落地）

- [ ] 同一租户在主体档案页保存一次，投标/招标两个业务入口读取的是**同一份**档案内容（uscc/名称/法人一致）；
- [ ] GET /profile/get 不传 subjectType 返回本租户档案；传 BIDDER/TENDERER 均返回同一份；
- [ ] 招标人发布公告前资格门仍按 TENDERER 授权校验；投标资格（预留）仍按 BIDDER 授权校验——仅档案完善度共用一份；
- [ ] 前端页面无「投标人/招标人」档案切换；证照/资质/材料自查/安许取本企业主体均单次调用成功。
