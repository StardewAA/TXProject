# 后端变更请求：管理端项目主档出参放开政务公开字段 —— 2026-09-18

> 依据：《VO 数据对象规范（国家V2.0模版·陕西适配全量版）》ProjectVO 的「公开范围」列；
> `txgy-module-bidding/README.md` §1.1 第 2 条 / §9.3；
> 现有文档：`docs/电子证照前前端契约/后端变更请求-编号体系归位-2026-09-20.md`（同格式先例）。
> 请求方：前端（管理端项目主档）。**这是口径变更请求，不是缺陷报告**——现行为是后端有意设计的，见 §二。

---

## 一、现象

管理后台「项目台账」→ 行内「详情」进入项目主档后，**一部分已填字段显示为空**，看起来像"没保存"。

实测记录（`bidding_project` 最新一行，项目编号 `I3301002026000001`）：

```json
"BIDDING_SITUATION": "1", "ORGANIZE_FORM": "2", "PROJECT_TRADE_TYPE": "B",
"INVEST_RECKON": "8500.00", "OTHER_OWNED_FUND": "8500.00", "PRIVATE_FUND": "0",
"BUIDING_AREA": "12500.50", "REPORT_DUTY": "李四", "CONTACT_INFORMATION": "13800138000",
"OTHER_INSTRUCTIONS": "本项目需严格按照政府投资项目管理办法执行，确保工程质量与安全。"
```

**值全部在库**（`bidding_project.fields_json`），是读取时被裁掉的。

## 二、根因定位（现有行为，非缺陷）

| 出处 | 原文 |
| --- | --- |
| `ProjectServiceImpl` 类注释第 7 行 | 「出参统一按 `@PublicLevel(SOCIAL)` 裁剪，避免各接口自行拼装导致口径漂移」 |
| `ProjectRespVO.fields` 字段注释 | 「数据集**公开字段子集**（`@PublicLevel=SOCIAL`；键=规范英文名）」 |
| README §9.3 数据格式约定 | 「公开范围：**对外出参**过 `PublicLevelFilter`：**政务公开字段到不了大厅 / ES**，前端『字段缺失』先查这一层」 |

裁剪发生在 `ProjectServiceImpl.toProjectResp(...)`——**列表、`get`、`get-by-code`、追溯聚合共用的唯一出参组装点**
（`pageProject` / `getProject` / `getProjectByCode` 三处均调用它，`ProjectTraceRespVO.project` 复用的也是 `ProjectRespVO`）。

## 三、受影响字段（ProjectVO 中 `政务公开` 且主档可编辑，共 16 个）

| 规范码 | 字段名称 |
| --- | --- |
| `PROJECT_TRADE_TYPE` | 项目交易分类 |
| `ORGANIZE_FORM` | 招标组织形式 |
| `BIDDING_SITUATION` | 招标情形 |
| `INVEST_RECKON` | 项目投资总额 |

| `PRIVATE_FUND` | 私有资金 |
| `PRIVATE_FUND_RATIO` | 私有资金比例 |

| `FOREIGN_PRIVATE_FUND` | 境外私人投资 |

后果不只是"显示不好看"：这 16 个字段在管理端**既看不到也改不了**，填报方无法维护自己录入的政务字段。

## 四、为什么请求放开管理端（论证）

1. **管理端是填报方，不属于「对外」。** §9.3 的口径原文是"**对外**出参"——即大厅 / ES / 公共服务大厅等对外出口。
   而 `get-by-code` / `get` 属管理端台账接口，权限码 `bidding:project:query`，服务对象是录数据的人。
2. **规范里「政务公开」是披露范围，不是可见范围。** 其含义是"仅向政务平台报送、不对外公开"。
   前端 `views/bidding/vo/voFieldControl.ts` 已按此理解写明：「VO 的『公开范围』是**披露范围**……
   **不是『谁填报』**。因此**不能按 pub 隐藏字段**」。出参裁剪与之相冲。
3. **同一份 VO/同一条路径同时服务两类受众**，导致"对外该裁"与"管理端必须看"无法兼得——这正是本请求要拆开的地方。

## 五、影响面（决定改法不能用「直接删裁剪」）

**门户前台页面复用同一套接口**：`views/portal/bidding/project/index.vue` 直接
`import { deleteProject, getProjectPage, saveProject } from '#/api/bidding/project'`，
与管理端命中同一批 URL。若无条件去掉裁剪，等于把政务公开字段给了对外页面，与 §9.3 正好相反。

## 六、改法建议（二选一，推荐 A）

**方案 A（推荐，改动最小）：加"是否含政务字段"入参**

- `ProjectController.get` / `get-by-code`（必要时含 `trace`）增加可选入参，如 `includeGovernment`（默认 `false`，保持现有对外行为）；
- `ProjectServiceImpl.toProjectResp(entity, includeGovernment)`：为 `true` 时按 ProjectVO 全量字段返回 `fields`，不再按 `SOCIAL` 裁剪；
- 管理端项目主档详情以 `includeGovernment=true` 调用；门户侧不动，行为与现在完全一致。

**方案 B：管理端单独出参 VO**

- 新增管理端专用 RespVO（如 `ProjectAdminRespVO`），`fields` 不裁剪；对外仍走 `ProjectRespVO`。
- 好处是受众彻底分离；代价是多一个 VO + 转换，且 `ProjectTraceRespVO.project` 也要一并处理。

## 七、前端行为（本次无需改动）

前端 `MainCardTable` 的 `recordToFields()` 本就是**遍历 `record.fields` 的全部键**铺平字段，
只要这些键随响应返回，详情页立刻正常显示，**不需要前端配合发版**。

> 附带确认（不丢数据）：编辑态仅提交「发生变更」的字段，显示为空但实际有值的字段不会被当作清空提交，
> 因此该现象期间不会造成数据损坏。

## 八、验收口径

1. 管理端项目主档详情：§三 的 16 个字段能回显库中值（以 `I3301002026000001` 为例，招标情形=1、项目交易分类=B、项目投资总额=8500.00）；
2. 门户前台页面：政务公开字段**仍然不可见**（对外口径不回归）；
3. 项目台账**列表**行为不变（列表只出主列，本就不含这批字段）。
