# 后端变更请求：投标文件与资格预审材料多文件化（2026-10-02）

> 状态：**已确认方向**（用户 2026-10-02 拍板：投标文件/资格预审材料"不只一个文件"，绑定"投标单元"而非公告/公共标段；**投标文件多附件优先**，资格预审次之）。
> 违反任何一条请先回本文档核对，勿擅自改绑定口径。

---

## 一、业务口径（为什么）

投标人在一个标段下递交的材料是**文件集**而不是单个文件：
- **投标文件集**：投标函 / 报价表 / 技术标 / 商务标 / 资质证明 / 其他（招标投标法第 31 条、电子招标投标办法第 26 条要求提交完整投标文件）；
- **资格预审材料集**（仅"资格审查方式=资格预审（前审）"的项目）：资质证书 / 业绩证明 / 财务报表 / 其他。

两类都是**投标人 → 招标方**的递交物，按标段组织；**招标方 → 投标人**的发布物（招标文件/资审文件/图纸）走既有公告/标段附件能力（`ANNOUNCEMENT`/`BID_SECTION`），不在本次范围。

## 二、现状实锤（缺口）

| 对象 | 现字段 | 问题 |
|---|---|---|
| `bidding_process_track`（投标流程跟踪） | `document_file_id` + name/size/hash/signature（**单文件主件**） | 投标文件集只能传一个 |
| `bidding_prequal_apply`（资格预审申请） | `file_id`（**单文件**） | 预审材料只能传一个 |
| 通用附件域 `bidding_attachment` | `save/delete/list` + 病毒扫描 + 35 类类型字典 | **bizType 仅 PROJECT/TENDER_PROJECT/BID_SECTION/ANNOUNCEMENT 四种，没有"投标/资格预审申请"** |

## 三、请求

### R1. 附件归属实体扩展两种 bizType（核心）
`AttachmentBizTypeEnum（或 FlowBizTypeEnum）` 增加：
- `BID_TRACK` —— **投标流程跟踪**（bizCode = `bidding_process_track.id`）；鉴权限 `bidding:process-track:query`；
- `PREQUAL_APPLY` —— **资格预审申请**（bizCode = `bidding_prequal_apply.id`）；鉴权限 `bidding:prequal:query`。

`/bidding/attachment/save|delete|list` 三个接口本身**复用**，仅枚举扩展。前端 `AttachmentSaveReq.bizType` 类型已同步声明。

### R2. 投标流程返回体带附件清单
`/bidding/process-track/page`、`/bidding/process-track/my`、`/bidding/process-track/detail` 的返回行/详情增加：
`attachments?: AttachmentRespVO[]`（= `attachment/list?bizType=BID_TRACK&bizCode=trackId` 的结果，按 seq 排序；可为空数组）。

### R3. 资格预审申请返回体带附件清单
`/bidding/prequal/apply/page`、`/bidding/prequal/apply/get` 增加：
`attachments?: AttachmentRespVO[]`（= `attachment/list?bizType=PREQUAL_APPLY&bizCode=applyId`）。

### R5. 标段聚合查询：投标记录按标段过滤 + 开标查询接口（联动）
标段详情页要按标段聚合"投标记录 / 保证金 / 开标 / 合同"，现有两个缺口一并请求：
- `/bidding/process-track/page` 增加可选入参 `bidSectionCode`（现状只有 keyword/state/tenantId，无法按标段拉投标人记录）；
- 新增 `/bidding/bid-opening/page?bidSectionCode=`（表 `bidding_bid_opening` 已带 `bid_section_code`，缺前端查询接口；鉴权 `bidding:bid-opening:query`，无权限码可挂既有子域）。

保证金（`/bidding/deposit/page?bidSectionCode`）与合同（`/bidding/contract/page?bidSectionCode`）已支持标段过滤，前端直接聚合。

### R6. 资格预审申请按标段聚合（联动标段详情）
`/bidding/prequal/apply-page` 增加可选入参 `bidSectionCode`（表 `bidding_prequal_apply` 已带 `bid_section_code`，缺过滤）；标段详情「投标与材料」据此聚合该标段所有预审申请（提交人 / 材料 / 审查结论），与 R2/R3 的多文件返回体配合。

### R4. 主件保留（CA 签章链路不回归）
`process_track.document_file_id`（CA 签章主件，SM3/SM2 证据链）与 `prequal_apply.file_id` **保留不改**；多文件是"主件 + 附件清单"叠加，不是替换。递交时允许附件**逐份**病毒扫描（attachment 域既有 `virusStatus`），主件仍走 CA 签章。

## 四、绑定口径（红线）

- ✅ 投标文件 → 绑 `BID_TRACK` + bizCode=track.id（**标段由 track.bid_section_code 本身带出**，不额外传）；
- ✅ 预审材料 → 绑 `PREQUAL_APPLY` + bizCode=apply.id（同样自带标段）；
- ❌ **不绑公告**（`ANNOUNCEMENT` 是招标方发布物）；
- ❌ **不绑公共标段**（`BID_SECTION` 会把招标方文件与所有投标人文件混在一起，分不清谁交的、哪一步）。

## 五、优先级

1. **投标文件多附件**（R2+R1-BID_TRACK）：每个项目都发生，不依赖前审/后审；
2. **资格预审材料多附件**（R3+R1-PREQUAL_APPLY）：仅前审项目，随后做；
3. 两者可同一版本实现（成本低：都是枚举 + 返回体透传），但前端先接投标。

## 六、前端消费（对齐声明，等待后端）

- `api/bidding/attachment/index.ts`：`AttachmentBizType` 已加 `BID_TRACK`/`PREQUAL_APPLY`；`ATTACHMENT_TYPE_OPTIONS` 补「投标文件 / 资格预审材料 / 资质文件 / 业绩证明」等类型；
- 门户 `process.vue`（投标流程管理）：递交区多文件选择 → 逐文件 `uploadBiddingFile` → `saveAttachment({bizType:'BID_TRACK', bizCode: trackId})`；行详情展示 `attachments[]`（文件名/类型/大小/病毒状态，INFECTED 不下发 URL）；
- 资格预审申请提交（`PrequalPanel` Tab②）多文件绑定 `PREQUAL_APPLY`；
- 后端未落地前（save 返回 bizType 非法 400）：前端捕获并提示「多文件附加上传待后端契约支持」，不崩溃。
- 页面编号/绑定回显：`/bidding/process-track/my` 未补 `attachments` 前，行卡片附*认清单为空、只显示主件。

## 七、验证口径

- 前端对一个标段传 3 份投标文件 → `attachment/list?bizType=BID_TRACK&bizCode=trackId` 返回 3 行（seq 有序、病毒状态逐份）；
- `process-track/detail` 返回 `attachments[3]`；主件 document_file_id 仍 CA 签章（SM3/SM2 不回归）；
- 预审申请同样 3 份材料 → 管理端审查任务按文件集逐份可见；
- 契约 B（公告标段复数回写）与本契约独立，互不阻塞。
