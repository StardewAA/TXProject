# 后端变更请求 · 资质与证书管理 五页改造缺接口（2026-09-18）

> 提出方：前端（电子证照管理模块 · 资质与证书管理 5 页）。
> 背景：组长下发《企业资质与证书管理系统》5 页原型，前端负责落地。**页面一（证照台账）已完成改造**（看板全库计数、
> 状态圆点、查看抽屉、每页 20 条），但其中「批量导入 / 批量验真」两项**后端没有接口**，按钮暂以置灰占位；
> 页面二~五（企业资质 / 员工资质 / 证件全生命周期 / 安许风险联动）另有部分能力后端没有接口。一并列此清单请后端评估。
> 依据：《电子证照模块-前端接口契约-v1.0》（下称 v1.0）、《电子证照模块-前端接口契约-v1.1-安许风险联动》（下称 v1.1）、
> 《_契约精读摘要-2026-09-20》。

## 0. 前置口径（不改）

- 前端只改现有页面文件，**不新建页面、不新增菜单号段**（菜单仍是 60005000 段）。
- 枚举 / 阈值一律取 `GET /bidding/meta/dicts`、`GET /bidding/meta/configs`，**不硬编码**（v1.0 §0.5）。
- 写接口一律按钮 loading + 回传乐观锁 `version`，失败不自动重试（v1.0 §0.7）。
- 新增能力请**同时注册权限点**（本模块惯例：`bidding:<域>:<动作>`），否则前端按钮不可见。
- 优先级：**P0** = 阻塞该页原型功能实现；**P1** = 影响体验但不阻塞；**P2** = 优化项（有替代实现）。

## 2. 页面一 · 证照台账（菜单 60005100）

**现状**：已完成原型改造（看板全库计数 + 点击联动、状态/验真彩色圆点、"查看"抽屉、每页 20 条）。
接口 `GET /bidding/certificate/{page,get}`、`POST /create|update|file/register|change-status`、
`POST /bidding/certificate-verify/{verify,verify-file}`、`GET /bidding/certificate-verify/history/page`、
`GET /bidding/cert-alert/{page}`、`POST /bidding/cert-alert/{scan,dispatch}`、`cert-lifecycle/*`。
**原型顶部操作区**：`新建证照 / 批量导入 / 批量验真 / 派发通知 / 配置字典 / 管理员`。
其中新建、派发通知、配置字典（跳系统字典页）、管理员（显示当前登录人）均已实现，**只有下面两项缺接口**。

### Q1（P1）批量导入
- 现状：`bidding` 侧**没有任何证照导入接口**（API 层逐一核对，无 import/batch/excel 相关方法）。
- 请求：`POST /bidding/certificate/import`——入参 = 文件（Excel），出参 = **行级结果回执**（成功 N 行 / 失败行号 + 原因）；
  另需模板下载入口。校验口径建议与 `create` 一致（`certNo` 租户内唯一、`certStatus` 初值、`holderType` 默认 ORG）。
- 前端已按"**置灰保留位置 + 注明待接口**"处理（不隐藏），接口就绪后只需把按钮 enable 并接上传。
- 权限点建议：`bidding:certificate:import`。

### Q2（P1）批量验真
- 现状：验真只有单条 `POST /bidding/certificate-verify/verify`（入参 `certId` + 可选 `verifyChannel`）。**无批量版**。
- 明确**不做**的方案：前端循环调单条——会真实触发 N 次验真调用，无事务、无进度、部分失败难回滚，且可能触发上游验真渠道的频控。故不采用。
- 请求二选一：
  - Q2a（推荐）`POST /bidding/certificate-verify/verify-batch`，入参 `certIds[]` + 可选 `verifyChannel`；
    出参**逐条结果**（`certId, verifyResult, message`），并保留既有验真历史留痕（`verify/history/page` 应能查到本批）。
  - Q2b 若上游渠道不支持批量，请明确"批量"在后端仍为串行 + 限流，前端只需一个统一入口、统一返回结构。
- 权限点建议：复用 `bidding:certificate:verify`。

### Q3（P2，优化项）看板统计聚合接口（**非阻塞，如实说明**）
- 现状：**已用前端方案实现，无需后端也能跑**——用 `certificate/page` 的 `pageSize=1` 并发计数取 `total`（共 5 次请求）得到全库总数/正常/临期/异常/未验真。
- 已知限制：该接口的 `certStatus` / `verificationStatus` **只接受单个 code**（不能 `in(多个)`），
  故看板按"每个 tagType 取 sort 最小的一个代表码"实现（正常=ACTIVE / 临期=EXPIRING_SOON / 异常=EXPIRED / 未验真=UNVERIFIED），
  暂扣(SUSPENDED)、吊销(REVOKED)、注销(CANCELLED) 不计入卡片。
- 请求（可选）：`GET /bidding/certificate/stats`，出参按状态全量计数（含暂扣/吊销/注销），并支持 `certStatus in (...)` 多选筛选。
  收益：页面加载少 4 次请求；卡片可覆盖全部状态。**不做也不影响页面一交付。**

## 3. 页面二 · 企业资质（菜单 60005200）

**现状**：5 个页签（① 资质台账 ② 延续申报台账 ③ 标准与要素 ④ 安许证与预警 ⑤ 完备性明细），
接口 `GET /bidding/qualification/page|get`、`POST /create|renew|approve|reject`、`standard/*`、`element/*`、`review/*`、`permit/*`、`alert/*`。
**原型要求**：企业维度单表（资质名称 / 所属企业 / 资质等级 / 发证机关 / 有效期至 / 状态 / 关联人员）+ 建档 / 批量导入 / 批量导出 + 数据看板。

### Q4（P0）资质主档编辑
- 现状：`POST /bidding/qualification/create` 只走 insert，**无更新接口**（页面注释已明确记录该缺口）。
- 请求：`PUT /bidding/qualification/update`，入参 = `SaveReq` + `id` + `version`（乐观锁），返回 id 或 void。
- 权限点建议：`bidding:qualification:update`（可与 create 合并，但请明确）。

### Q5（P0）看板统计
- 原型卡片：资质总数 / 正常 / 临期预警 / 异常过期 / **未关联人员**。
- 前端可退化方案：前 4 项可由前端**并发计数**（按 `qual_status` 逐码 `pageSize=1` 取 `total`）算出，无需后端；
  但第 5 项"**未关联人员**"没有现成数据——"资质 ↔ 人员"的关联目前只落在要素台账 `qualification_staff`，台账行上没有关联度。
- 请求二选一：
  - Q5a（推荐）`GET /bidding/qualification/stats?entId=`，出参 `{ total, valid, expiring, expired, unlinkedStaff }`；
  - Q5b 若"未关联人员"另有业务定义，请给出口径（是"无绑定员工的资质数"还是"未关联任何资质的人员数"？），前端按口径实现。

### Q6（P1）批量导入 / 批量导出
- 请求：`POST /bidding/qualification/import`（模板下载 + 行级校验 + 错误行回执）、`GET /bidding/qualification/export-excel`（参照系统既有导出风格）。
- 权限点建议：`bidding:qualification:import` / `bidding:qualification:export`。

### Q7（P0，口径）"所属企业"下拉
- 现有页面**刻意不做企业选择器**：普通租户只看本企业（主体档案自动带出），跨租户查看走「平台审查中心」。
- 原型要"所属企业"下拉 ⇒ 等于打开**跨租户数据面**。请先定：
  - Q7a 不做（维持单租户，前端不加该下拉）；或
  - Q7b 做平台级视图：需后端支持按 `entId` 跨租户查询（`@TenantIgnore`）+ 明确"哪些角色可见哪些租户"，前端用 `userStore.userRoles.includes('super_admin')` 判超管。
- **在口径确定前，前端不实现该项。**

### Q8（P1）"关联人员"列
- 请求：`page` 出参补 `staffCount`（或 `staffNames[]`），取自要素台账人员配置。

## 4. 页面三 · 员工资质（菜单 60005300）

**现状**：员工档案页签 + 履历（培训/社保/劳动合同）+ 员工证书平铺表 + 到期看板 + 安许配备自查 + 多岗兼任。
接口 `personnel-profile/*`、`personnel-certificate/{page,list-by-person,list-expiring,count-by-sub-type,create,update,change-status,delete}`、`personnel-record/*`。
**原型要求**：**员工维度可展开树表**（员工行：姓名/工号/部门/持有证书数/最近到期时间 → 展开为证书行）+ 批量续期 + 批量到期提醒 + 看板。

### Q9（P0）员工维度分页
- 现有 `page` 是按**证书**分页；前端若先取一批再按人分组，**分页会把人切断**（同一人可能跨页）。
- 请求：`GET /bidding/personnel-certificate/page-by-person`，入参 `deptName` / `certType` / `certStatus` / `expiringDays` / 分页；
  出参（人维度）：`personId, personName, personNo, deptName, certCount, nearestValidTo, certs[]`（`certs` = 该人在同筛选下的证书，字段同现有 Cert 出参）。
- 若后端不便新增，请说明"按人分页"是否可由现有接口参数组合达成（前端目前找不到可行组合）。

### Q10（P0）看板统计
- 原型卡片：持证员工数 / 证书总数 / 临期预警 / 异常过期 / 未验真。
- 部分可拼：`count-by-sub-type` 给不了"总数"，`list-expiring` 给窗口内清单。
- 请求：`GET /bidding/personnel-certificate/stats?entId=&deptName=`，出参 `{ holderCount, certTotal, expiring, expired, unverified }`。

### Q11（P1）批量续期
- 请求：`POST /bidding/personnel-certificate/batch-renew`，入参 `items[{id, version, newValidTo, renewalType}]` 或 `ids[] + 统一新有效期`；
  返回**逐条结果**（成功/失败原因），单个失败不影响其余（前端据此展示部分成功）。
- 权限点建议：`bidding:personnel:cert:renew`。

### Q12（P1）批量到期提醒
- 现状：只有 `POST /bidding/personnel-certificate/alert/scan`（全量扫描，生成预警）。
- 原型"批量到期提醒"是**对所选人/证书发提醒**。请求：`POST /bidding/personnel-certificate/alert/notify`，
  入参 `personIds[]` 或 `certIds[]`，产出通知（幂等，避免重复推送）。

### Q13（P1）证书级"验真"
- 现状：`platformVerified` 只是标记位，无验真动作接口。
- 请求：明确员工证书是否走验真。若走，建议 `POST /bidding/personnel-certificate/verify`（可复用证照域验真渠道）；若不走，前端**去掉该按钮**。

## 5. 页面四 · 证件全生命周期（菜单 60005400）

**现状**：**只有列表视图**。接口 `cert-lifecycle/{apply,audit,effect,get,page,list-by-biz}`，状态机 PENDING→REVIEWING→APPROVED→EFFECTIVE（可 REJECTED）。
**原型要求**：看板 / 时间轴 / 列表三视图切换；时间轴节点带"查看附件 / 查看报告 / 查看审批详情 / 催办"。

### Q14（P1，口径）看板视图分列口径
- 原型分列：待验真 / 正常 / 临期 / **续期中** / 已注销。

  其中"待验真/正常/临期/已注销"属**证照状态**（`cert_status`：UNVERIFIED/ACTIVE/EXPIRING_SOON/…/CANCELLED），
  "续期中"属**流程状态**（`lifecycle_status`）。两套枚举混在同一组看板列里，请与产品统一口径。
- 前端说明：若改为按 `lifecycle_status` 分列（待办/审核中/已通过/已生效/已驳回），**用现有 page 接口 + 多状态并发计数即可实现，无需后端新增**。

### Q15（P0）催办
- 请求：`POST /bidding/cert-lifecycle/urge`，入参 `id`（生命周期记录）；产出通知/待办；幂等（同日重复催办不叠加，或明确可叠加）。
- 权限点建议：`bidding:certificate:lifecycle:urge`。

### Q16（P1）节点"查看报告 / 查看附件"
- 附件：现有 `evidenceFileIds` 已有；"**报告**"指代不明——是审批单 PDF？达标核查报告？请明确要什么。
- 若指审批留痕：现有 `get` 出参已含 `appliedBy/handledBy/effectiveAt/remark`，前端可直接展示，**无需新增**。
- 若指文件清单：请在 `get` 出参补 `files[]`（`fileId/文件名/类别/上传时间`）。

### Q17（无需后端）时间轴按证照切换
- 现有 `GET /bidding/cert-lifecycle/list-by-biz?bizDomain&bizId` 已可支撑；前端加"证照切换下拉"+ 复用现有 `cert-timeline.vue` 组件即可。

## 6. 页面五 · 安许风险联动（菜单 60005500）

**现状**：A/B/C 配备风险卡片 + 多岗兼任校验 + 人员风险 + 项目关键岗位变更 + **规则配置（阈值键值）**。
接口 `safety-permit/*`（v1.1 §12）、`rule-config/{get,save,rollback,history,audit/page}`。
**原型要求**：**风险条目清单**（风险等级/风险描述/关联证照/影响主体/责任人/状态/指派）+ 风险大盘（高/中/低/已处理/总数）+ 规则配置（规则名称/触发条件/影响范围/启用禁用）+ 重新扫描 + 导出报告 + 一键预警。

### Q18（P0）风险条目数据模型
- 现状**没有"风险条目"实体**：现有的是①安许 A/B/C 配备结论、②人员风险标签、③项目关键岗位变更超限统计，都不是"可指派、有责任人、有处理状态"的风险工单。
- 原型要的是一套**风险工单**。请求（形态可议）：
  - `GET /bidding/safety-permit/risk/page`（入参 `riskLevel`/`status`/`assigneeId`/`keyword`/分页；出参 `riskLevel, riskDesc, certRef, entName, assigneeId, assigneeName, status, foundAt` 等）；
  - `GET /bidding/safety-permit/risk/get?id=`；
  - `POST /bidding/safety-permit/risk/assign`（入参 `id, assigneeId, remark`）；
  - `POST /bidding/safety-permit/risk/handle`（入参 `id, status, remark`，乐观锁 version）。
- 权限点建议：`bidding:safety-risk:query` / `bidding:safety-risk:assign` / `bidding:safety-risk:handle`。

### Q19（P0）风险大盘统计
- 随 Q18 给出 `GET /bidding/safety-permit/risk/stats`，出参 `{ high, medium, low, handled, total }`。

### Q20（P1）重新扫描风险
- 现有 `POST /bidding/safety-permit/risk/recheck` 针对安许 A/B/C。请明确"重新扫描风险"是**复用**它，还是新增扫描产出"风险条目"（与 Q18 配套）。

### Q21（P1）导出风险报告
- 请求：`GET /bidding/safety-permit/risk/export`（范围 = 当前筛选，格式 xlsx/pdf 由后端定）。

### Q22（P1）一键预警
- 请求：`POST /bidding/safety-permit/risk/alert/batch`（对所选风险条目批量发预警，幂等）。

### Q23（P1，口径）风险规则配置
- 现有 `RuleConfig` 是**阈值键值**（`ruleKey`/`value`/`legalFloor` + 版本历史 + 读取审计），**不是**"规则"实体。
- 原型要"规则名称 / 触发条件 / 影响范围 / 启用禁用"。请二选一：
  - Q23a 维持现状：前端用现有 `RuleConfigPanel` 呈现，并在页面注明"规则=阈值配置"的口径差异；
  - Q23b 新增规则实体：需给出 `ruleName / condition / scope / enabled` 的数据模型与增删改查接口。
