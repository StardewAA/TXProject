# 后端变更请求：投标文件 CA 签章 → 递交衔接契约（2026-09-20）

> 说明：本文件是**前端 → 后端的变更请求 / 契约**，用于把「投标文件 CA 签章」与「投标流程跟踪递交」两条已各自就绪的链路**接起来**。
> 关联文档：`30-CA互认H5签章组件-前端接入说明-2026-09-28.md`、`后端变更通知-CA签章台账-2026-09-28.md`、`29-外部CA与身份认证对接清单-2026-09-18.md`、`28-招标全流程状态流转接口-2026-09-21.md`。
> 结论先说：**两条链路各自都能跑，但接口之间没有契约**——签章接口产出的三件套（SM3 指纹 / SM2 签名 / 证书号）恰好是递交接口的必填入参，
> 而递交接口又要求客户端自行提供，形成"产物在服务端、入参要客户端给"的错位。本文件列出 10 个缺口与一条收敛建议。

## 1. 目标流程（业务口径）

投标人在门户对某标段完成「意向投标 → 报名 → 资质审核通过（待投标）」后，递交投标文件：

```
选文件 → 上传（拿 fileId/sha256） → CA 认证检测 → 未认证则扫码签章（SM3 指纹 + SM2 签名）
      → 递交（PENDING_BID → BIDDED）→ 留痕（document_hash / document_signature / ca_cert_no）
```

法规依据：《电子招标投标办法》第 20/30 条、《电子签名法》第 13/14 条 —— 投标文件须经**电子签名并加密**，签章与递交是同一份文件的同一份证据链。

> ⚠️ 口径澄清（用户裁定）：**不要把「CA 签章链路」与前端自制哈希混为一谈**。
> 前端**不引入** `sm-crypto` 之类本地国密实现去自算摘要——文件级指纹必须由服务端产出，前端只搬运。

## 3. 字段映射（前端按现状能填 / 不能填）

递交接口 `POST /bidding/process-track/upload`（`ProcessTrackUploadReqVO`）入参 ← 签章接口（`SealDocumentRespVO`）产物：

| upload 入参 | 必填 | 现状来源 | 能否填 |
|---|---|---|---|
| `id` | ✅ | 投标流程 id | ✅ |
| `userId` | ✅ | 登录人 | ✅ |
| `documentFileId` | ✅ | 候选：原文件 fileId 或 `sealFileId` | ⚠️ 语义未定（A3） |
| `documentName` | 否 | `sealFileName` | ✅ |
| `documentSize` | ✅ | **签章响应没有该字段** | ❌ **无法填（A1，硬阻塞）** |
| `documentHash` | ✅ | `hash`（SM3） | ✅ |
| `documentSignature` | ✅ | `signature`（SM2 base64） | ✅ |
| `caCertNo` | ✅ | `certSn` | ✅ |
| `documentHashAlgo` | 否 | 无（语义固定 SM3） | ⚠️ 需后端兜底（A9） |
| `caPublicKey` | 否 | `SealDocumentRespVO` 无 | — |

**A1 的严重度取决于 A3**：`documentSize` 为 `@NotNull`，而 `SealDocumentRespVO` / `CaSealRespVO` / 前端 `SealDocument` **均无**"签章后文件字节数"（已实测逐个核对）。
- 若 `document_file_id` 取 `sealFileId`（法律证据应以已签章文件为准）→ 大小与前端已知的原文件大小**不是同一个值**，前端无法在不说谎的前提下填出 → **硬阻塞**；
- 若 `document_file_id` 取原文件 `fileId` → 大小用上传返回的原文件大小即可，链路可立即跑通，但证据链指向的是**未签章原文件**。

## 4. 缺口清单

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| **A1** | `SealDocumentRespVO` 缺 `sealFileSize`（签章后文件字节数；`CaSealRespVO` 同样没有，已实测） | 若 `document_file_id` 取 `sealFileId`，前端无法填 `documentSize`(@NotNull) → **硬阻塞**；取原文件则可绕过但证据链指向原文件 | 签章/批量签章响应补 `sealFileSize`（Long，字节）；或按 §5 建议改由后端回填 |
| **A2** | **双重写库责任不清**：`/ca/seal/document?businessCode=<trackId>` 会写 `bidding_process_track`（signature/cert_no/hash），`/process-track/upload` 也写同样字段 | 两处口径不同（前者服务端签章产物、后者客户端回传）→ 数据可能被后者覆盖或互相矛盾 | 明确**唯一权威写入方**；建议由签章接口写证据链、递交接口只做**状态流转**（见 §5） |
| **A3** | `document_file_id` 语义未定：原文件 or 已签章文件(`sealFileId`)? | 证据链指向不明；出证/开标解密时取错文件 | 契约写明。法律证据应以**已签章文件**为准，则 `document_file_id ← sealFileId` |
| **A4** | **台账与流程表数据不一致**（实测）：`bidding_ca_seal` **0 行**，而 `bidding_process_track` **7 行**已带 `document_signature`/`ca_cert_no` | `GET /seal/check` 只查台账 → 这 7 条历史签章被判 `caAuthed=false`，前端会重复提示"未认证"并**重复签章** | 提供一次性回填迁移（process_track 签章字段 → `bidding_ca_seal`），或 `check` 同时回查 process_track 兜底 |
| **A5** | `/seal/check` 按**原文件 fileId**匹配，签章产物却是 `sealFileId` | 对已签章文件再走"检测"匹配不到；重传场景只能靠 `sha256` 兜底 | 明确匹配键优先级（fileId → sha256 → sealFileId）并写入契约 |
| **A6** | **权限模型不一致**：`/ca/seal/*` 多为 `isAuthenticated()`，`/process-track/upload` 要 `bidding:process-track:upload` | 用户可能"能签章、交不了"，或反之；签章是递交的前置步骤却不受业务权限约束 | 二选一并写明：①签章同样校验业务权限；②明确"签章通用、递交受控"口径 |
| **A7** | multipart 体积/超时**无口径**（`/seal/document`、`/seal/batch`） | 前端只能猜预校验阈值（门户现按 16 MB）；超限表现为长时间无响应而非明确报错 | 给出单文件/批量总大小上限、超时与超限错误码 |
| **A8** | 幂等/重试语义未定义：`@Idempotent` 的幂等键是什么 | 签章成功但递交失败后，重试是否安全不明 | 写明幂等键（建议 `trackId + sealId`）与可重试窗口 |
| **A9** | `documentHashAlgo` 未被强制为 SM3，签章响应也不回该字段 | 客户端可写入非法算法值，证据链算法标识不可信 | 递交接口校验/落库默认 `SM3`，响应回带该字段 |
| **A10** | 测试配置（`bidding.ca.sdk.enabled=false`，本地测试账号 `SN-LOCAL-CA-TEST-0001`）与生产 CA 互认共享组件的行为差异未声明 | 前端无法判断哪些字段在生产下语义不变 | 声明字段稳定性：`signature/certSn/hash` 语义不变；`orgName/sealTime/documentId` 生产由 CA 平台给出 |

## 5. 收敛建议（首选方案，一次解决 A1/A2/A3/A9）

**把 `POST /bidding/process-track/upload` 的入参从「客户端回传签章三件套」改为「引用签章台账」**：

```diff
 POST /bidding/process-track/upload
-{ id, userId, documentFileId, documentSize, documentHash, documentSignature, caCertNo }
+{ id, userId, sealId }          // sealId = bidding_ca_seal.id（签章接口落库产物）
```

后端据此从 `bidding_ca_seal` 台账回填 `document_hash / document_signature / ca_cert_no / document_file_id(sealFileId) / document_size(sealFileSize)`，并执行 PENDING_BID → BIDDED。

**收益**：
1. 解决 A1（大小由后端从台账/文件服务取，前端无需知道）；
2. 解决 A2（签章接口是证据链唯一写入方，递交只做状态流转）；
3. 解决 A3（文件指向由后端统一决定）；
4. 解决 A9（算法由后端固定 SM3）；
5. **安全**：消除"客户端回传签名值"这一可伪造面——当前形态下客户端理论上可提交任意 `documentSignature`，后端仅校验非空。

**兼容**：保留旧入参三字段为可选（缺 `sealId` 时走旧逻辑），避免破坏既有调用方。

## 7. 前端现状与接线计划

**现状**：门户「确认上传」**已停止本地伪造状态**（原实现点一下就把流程置为"已投标"却不产生任何服务端记录，属假成功）。
当前 `composables/useBiddingProcess.ts` 的 `advance(t,'UPLOAD_DOCUMENT')` 在三件套缺失时**明确拒绝并说明原因**，不调接口、不伪造。

**本契约确认后的接线计划**（前端已具备全部封装，改动量小）：
1. 选文件 → `POST /bidding/file/upload`（fileId + sha256）；
2. `GET /bidding/ca/seal/check?fileId=&sha256=` → `caAuthed=false` 提示「该文件未 CA 认证」并询问；
3. 确认后 → `POST /bidding/ca/seal/document`（multipart，`businessCode=<trackId>`）→ 拿签章产物；
4. 按 §5 新契约 → `POST /bidding/process-track/upload { id, userId, sealId }`；未采纳 §5 时退化为按 §3 映射回填（**需先补 A1 的 `sealFileSize`**）。

> 相关既有约定：门户标书上传前端预校验 16 MB 与 `spring.servlet.multipart.max-file-size` 对齐；A7 明确口径后同步该阈值。

1. **每次签章直接落库台账 `bidding_ca_seal`**（不再依赖 `businessCode`）；`businessCode` 可解析为投标流程 id 时**同时**回写 `bidding_process_track`。
