# 后端变更请求 · 本站公告（内部公告）的「三级编号」跟踪扇出

- 日期：2026-09-23
- 提出方：前端（门户招投标 / 公告发布工作台）
- 影响接口：`POST /admin-api/bidding/notice/publish`（发布即扇出）、`POST /admin-api/bidding/notice/update`（已发布改正文即扇出）
- 影响页面：门户「投标流程管理」`/portal/bidding/process`、「我的关注」`/portal/bidding/subscriptions`
- 前置结论：**本站公告的发布扇出只认「项目编号」一级**，招标项目级 / 标段级关注者在结构上不可能收到动态；
  且前端两个发布入口此前把**招标项目编号**写进了项目编号槽位（本轮已修）。两者叠加 = 「发布成功、没有任何人被通知」。

## 0. 一句话结论

门户关注（`notice-follow`）支持三级编号：**项目编号 / 招标项目编号 / 标段（包）编号**
（`targetType = PROJECT / TENDER_PROJECT / SECTION`，前端「我的关注」筛选器就是这三档）。
但本站公告发布时，扇出方法 `FollowServiceImpl#handleInternalNoticeChanged` 只查 `ANNOUNCEMENT`（前端入口已下线）与
`PROJECT` 两类订阅，且 `PROJECT` 只用 `notice.projectCode` 一个键 ——
**用户按招标项目编号或标段编号建的关注，永远不会被本站公告命中。**

对照：**外部采集公告**的同一套门户关注是**三维可追**的（`NoticeExternalDO` 有
`project_code` / `tender_project_code` / `bid_section_codes` 三列，匹配谓词三键 OR）。
同一套 UI、两种能力，用户看不出区别，所以"发布了但没人收到"会直接被当成 Bug。

### 2.2 现场复现：同一标段发两条内部公告，**只有项目级关注者收到**（2026-09-23 实测）

做法（全部走真实 API，不是造数脚本、不是模拟查询）：

1. 以 tenant 1 的 admin 建三个 **FOLLOWING** 关注（同一批内部编号）：
   `PROJECT = I610100202600000h`、`TENDER_PROJECT = I610100202600000h001`、`SECTION = I610100202600000h001001`
   （`POST /bidding/notice-follow/follow`，三次都 `code=0` —— 关注域不做编号存在性校验，任意编号都能建关注）；
2. 用 `POST /bidding/notice/create` + `POST /bidding/notice/publish` 发**两条同一标段**的内部公告
   （标题 `探针-同标段双公告-A / -B`；根 `project_code=I610100202600000h`、
   `payload.TENDER_PROJECT_CODE=I610100202600000h001`、`payload.BID_SECTION_CODES=I610100202600000h001001`；
   发布门要求 pdfFileId，先 `PUT /bidding/notice/update` 补上）。

结果（`GET /bidding/notice-follow/item/{itemId}/timeline` 实测，用户可见口径）：

| 关注级别 | 关注键 | 时间线 total | 动态内容 |
| --- | --- | --- | --- |
| ① 项目 PROJECT | `I610100202600000h` | **2** | `NOTICE_PUBLISHED` ×2（标题快照 A、B 各一条；unread=2，latest=2026-09-23 02:27:09） |
| ② 招标项目 TENDER_PROJECT | `I610100202600000h001` | **0** | 无（unread=0、latest=NULL） |
| ③ 标段 SECTION | `I610100202600000h001001` | **0** | 无（unread=0、latest=NULL） |

事件表（`bidding_follow_item_event`，`source='INTERNAL'`）只落了 **2 行**，`item_id` 都是**项目级**关注行；
`event_key = 1-<itemId>-INTERNAL-<noticeId>-NOTICE_PUBLISHED-1` 含 `noticeId`
⇒ **两条公告产生两条独立动态，不会互相去重**（同一条公告重复发布同版本才会 `created=0`）。

→ 结论：
1. **同一标段下发两条，项目级关注者能收到两条**，不丢、不合并（"能不能收到"这一问，项目级答案=能）；
2. 招标项目级 / 标段级**收不到**，不是编号写错、也不是索引没建，而是 1.2 的代码事实：
   扇出只查 `PROJECT` 一级，另两级**根本没有查询分支**。

（探针数据已全部回滚：两条公告撤下 + 逻辑删除、三个关注与两条动态已清；库内计数回到探针前
`有效公告 7 / 订阅 13 / 关注行 3 / INTERNAL 事件 0`。）

### 2.3 前端侧的编号错位（本轮已修，仅作记录）

两个发布入口都把**招标项目编号**写进了根字段 `projectCode`：

| 入口 | 原代码 | 后果 |
| --- | --- | --- |
| 后台/门户「发布工作台」`NoticeWorkbench.vue#applyTenderProject` | `form.projectCode = code`（`code` = 招标项目编号） | 根字段被招标项目编号占用，真实项目编号丢失 |
| 前台标段页「创建公告」`NoticeCreateModal.vue#submit` | `projectCode: props.tenderProjectCode` | 同上（传入的 `props.projectCode` 被忽略） |

后果叠加：即使后端只匹配 `PROJECT` 一级，键也是错的（除非用户恰好按**招标项目编号**建了 `PROJECT` 关注）。
§2.1 表里 #1 就是这种错位形态，其余 6 条是正确形态（根=父项目编号、数据集=招标项目编号）。

**口径澄清（使用方 2026-09-23 裁定，勿再当成缺陷）**：外部采集公告用外部平台的编号、
本站公告用本平台内部编号（`I610100202600000h` 这类），**两套编号本来就不同、也不应互相匹配**
（公告来自两个不同平台，跨平台查不到是正常的）。所以"外部关注键与本站公告编号交集为 0"
**不是问题**，不需要任何"跨平台联动"；本文件只处理**本站公告内部**的三级跟踪闭环。

**前端修复（本轮提交）**：根字段只放真实项目编号（取自项目主档台账 / 招标项目自带的父项目编号），
招标项目编号留在 `TENDER_PROJECT_CODE`、标段编号留在 `BID_SECTION_CODES`；
发布工作台新增「跟踪档位」条（缺哪一级就提示该级关注者收不到，**只提示不阻断发布**）。

### B1【必须·唯一硬缺口】发布扇出改为三级匹配

**改计入参**（`NoticeServiceImpl` 已有 `readPayload(notice.getFieldsJson())`，时间轴注册在用，直接复用）：

```java
Map<String, Object> payload = readPayload(notice.getFieldsJson());
String tenderProjectCode = text(payload.get("TENDER_PROJECT_CODE"));
List<String> sectionCodes  = splitCodes(payload.get("BID_SECTION_CODES")); // 半角分号；兼容中文分号「；」/顿号「、」/逗号（与既有 SECTION 分隔符口径一致）
fanoutInternalVersionChange("PUBLISHED", id, notice.getTitle(), notice.getPublisherName(),
        notice.getProjectName(), notice.getProjectCode(), tenderProjectCode, sectionCodes, version);
```

**匹配谓词扩为三级**（与外部公告 1.3 完全同构）：

| 级别 | 订阅 `target_type` | 命中条件 |
| --- | --- | --- |
| ① 项目 | `PROJECT` | `target_key = notice.project_code`（现状不变） |
| ② 招标项目 | `TENDER_PROJECT` | `target_key = payload.TENDER_PROJECT_CODE` |
| ③ 标段（包） | `SECTION` | `target_key ∈ payload.BID_SECTION_CODES` |

**幂等/去重**：现有事件键 `userId-itemId-INTERNAL-noticeId-eventType-version` 不受影响；
`seen` 去重（`:543-544`，按订阅行 id）可直接复用 —— 同一用户同时关注了项目与其标段时，
两行订阅各自产生一条动态（各自 `itemId`），**不做跨行合并**（现状语义，如需合并请另定口径）。

**建议同时加一个核对入口**（外部公告已有 refanout，本站没有）：
`POST /admin-api/bidding/notice/{id}/refanout?dryRun=true` → 返回 `matched / created / skipped`，
便于"到底该命中几条"先 dryRun 再真放，出问题时不用改库查。

### B2【建议】本站公告也支持「维度关注回填」

外部公告有关注即回填历史（`seedDimensionInitial`），本站公告没有对应逻辑 →
用户关注一个项目后，「投标流程管理」里看不到该项目**此前**发布过的本站公告。
建议：`seedDimensionInitial` 增加本站公告来源（按上面同一套三级键查 `bidding_notice` 的 PUBLISHED 行），
或在发布时对已存在的关注补写历史动态。B1 解决"新发布能被追"，B2 解决"历史看不见"。

### B3【可选·口径统一】根字段语义写进契约注释

`NoticeSaveReqVO.projectCode` 的 `@Schema` 目前写的是「关联招标项目编号（可为空）」，
但列名、前端、扇出都按**项目编号**使用，种子数据也两种口径混存（§2.1）。
建议统一为「关联项目编号（项目主档 `project_code`，三级跟踪第①级）」，
并明确"招标项目编号 = 数据集 `TENDER_PROJECT_CODE`"，避免下一个人再写错槽位。

### B4【必须·「存进去就能查」】本站公告分页查询补 招标项目编号 / 标段编号 入参

**现状**：`NoticePageReqVO` 只有 `projectCode`（+ keyword/noticeType/status/internalFlag/publicLevel/发布时间区间），
所以按**招标项目编号 / 标段编号查不到任何本站公告**（对照：`NoticeExternalPageReqVO` 三个编号入参齐全）。
前端「投标流程管理 → 关联公告」弹窗因此只能查外部公告表。

**诉求（使用方口径）**：本站公告的三级编号既然已经落在公告上（根字段 + `fields_json`），
就应该和外部公告一样能用**精确查询**查出来 —— 存进去 → 建列/索引 → 能查。建议二选一：

- **A（推荐，零 DDL）**：`projectCode` 继续匹配根字段列；`tenderProjectCode` / `bidSectionCode` 走 JSON 提取：
  ```sql
  JSON_UNQUOTE(JSON_EXTRACT(fields_json, '$.TENDER_PROJECT_CODE')) = #{tenderProjectCode}
  FIND_IN_SET(#{bidSectionCode}, REPLACE(JSON_UNQUOTE(JSON_EXTRACT(fields_json, '$.BID_SECTION_CODES')), ';', ',')) > 0
  ```
- **B（性能/索引友好）**：加两列 `tender_project_code varchar(64)` + `bid_section_codes varchar(600)`，
  创建/更新时与 payload 同步写入，查询走列（可建索引）。

配套：`/bidding/notice/page`（管理端）与 `/bidding/notice/public/list`（大厅公开）**共用同一个 VO**，
一处改动两边生效；前端即可用同一套编号参数同时覆盖外部公告与本站公告。

**验收**：
```bash
GET /admin-api/bidding/notice/page?tenderProjectCode=I610100202600000h001   # 命中 B6100002026000002
GET /admin-api/bidding/notice/page?bidSectionCode=I610100202600000h001001    # 命中 B6100002026000002
```

## 7. 验收口径

> 第 1-6 条为 B1 落地后的验收；第 0 条是**当前实测基线**（B1 未落地时的真实表现，2026-09-23 复现）。

0. **当前基线（B1 未落地）**：同一标段发两条本站公告 →
   项目级关注者时间线 **2 条** `NOTICE_PUBLISHED`；招标项目级 / 标段级时间线 **0 条**（见 §2.2 实测表）。
1. 造数：一条 PUBLISHED 本站公告，根 `project_code = P`、`payload.TENDER_PROJECT_CODE = T`、
   `payload.BID_SECTION_CODES = S1;S2`；三个用户分别 FOLLOWING `P` / `T` / `S1`；
2. 撤下再发布该公告 → 三个用户**各自产生 1 条** `source=INTERNAL / event_type=NOTICE_PUBLISHED` 动态；
   同标段发**两条**公告 → 三级关注者**各自 2 条**（不合并、不丢）；
3. 关注 `S9`（不在 `S1;S2` 内）的用户 → **0 条**（不能误伤）；
4. 关注 `S2` 的用户 → 1 条（多标段公告按"命中任一标段"匹配）；
5. 同一用户同时关注 `P` 与 `S1`（两行订阅）→ 两行各自 1 条动态（现状按订阅行去重，不跨行合并）；
6. 同版本重复发布 → `created = 0`（事件键幂等）；
7. `dryRun=true` 的 `matched` 数 = 真实发布后 `created` 数（无重复订阅时）。
