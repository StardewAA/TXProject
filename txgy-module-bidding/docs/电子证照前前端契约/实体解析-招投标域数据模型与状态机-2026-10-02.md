# 实体解析：招投标域数据模型与状态机（2026-10-02，按实体管）

> 按实体而非功能组织。每个实体 = 一张表 + 归属链 + 生命周期状态机 + 页面归属。
> 表结构来自 ruoyi-vue-pro 库（docker txgy-mysql，MySQL 8.4）实锤。

## 一、实体清单与归属链

```
招标项目(bidding_tender_project, 根·tender_project_code)
 ├─ 标段(bidding_bid_section, N·bid_section_code=项目码+2位序号)
 │   ├─ 资格预审(bidding_prequal, 1:标段·bid_section_code 可空=项目级)
 │   │   └─ 资格预审申请(bidding_prequal_apply, N·prequal_id)
 │   ├─ 投标保证金(bidding_bid_deposit, N·bid_section_code+subject_id)
 │   ├─ 合同(bidding_contract, N·bid_section_code)
 │   ├─ 开标(bidding_bid_opening, 1:标段·bid_section_code 可空=覆盖全标段)
 │   └─ 投标流程(bidding_process_track, N·投标人档案 follow_key=标段编号)
 ├─ 公告(bidding_notice, N·project_code, 本站发布含公示)
 └─ 附件(bidding_attachment, 通用一对N·biz_type+biz_code, 挂任意业务实体)
```

## 三、生命周期状态机（实锤枚举）

1. **资格预审** status：`DRAFT → PUBLISHED → APPLYING → REVIEWING → RESULTED → CLOSED`
2. **资格预审申请** status（字典 prequal_apply_status）+ 审查：提交 → review_result(APPROVED/REJECTED) + review_reason/review_time
3. **投标流程** current_state：`INTENTION → REGISTER → QUALIFICATION_REVIEW → APPROVE → PENDING_BID → UPLOAD_DOCUMENT → BIDDED`；REJECT/CANCEL → `TERMINATED`；时间戳链逐节点推进（intention_time→register_time→review_time→pending_bid_time→bidded_time/terminated_time）
4. **开标双轨**：opening_status(PENDING→DECRYPTING→DONE) + room_status(WAITING→DECRYPTING→OPENING→DONE)
5. **合同**：SIGNED(登记即生效) → ARCHIVED(归档只读, retention_until=归档+15年)
6. **招标项目** state：域字典（当前库 19 条多为 COMPLETED）

## 五、数据驱动结论（解析「为什么入口亮/不亮」）

- 入口显隐 = 对应实体行存在（如流程行 deleted=0、资格预审 PUBLISHED、审查方式=1）——**前端零硬编码**
- 当前库内活数据：招标项目 19（含炼化=前审）、标段含炼化 1001001、预审 P20261002001(PUBLISHED)、流程行活 3（炼化标段）、开标 4（含 NULL 覆盖）、外部公告 2322 + 本站 2
- 公告详情·标段行入口：需公告含该标段（外部公告无覆盖 / 内部公告依赖契约 B 未实现）——功能就绪，数据未覆盖

## 六、审计要点（凭此可复核）

- 资格预审表有唯一键 uk_prequal_code；标段编号=项目码+2 位序号（可推导归属）
- 流程行 CA 字段完整（SM3 指纹/SM2 签名/证书号）——主件证据链不回归（契约 R4）
- 附件 bizType 仅新增 BID_TRACK/PREQUAL_APPLY 两类私有绑定（红线：不绑 ANNOUNCEMENT/BID_SECTION）
- 开标 open_list 为 JSON（bidderName/bidSectionCode/price/decryptStatus），两端页面均展开展示
