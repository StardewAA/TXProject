# 后端变更请求 · 平台企业资质审查 + 录入方式扩展（2026-09-20）

> 提出方：前端（电子证照管理模块）。本文只描述**前端已按契约实现之外、需要后端新增/确认**的点。
> 依据：用户 2026-09-20 口径 + 《电子证照模块-前端接口契约-v1.0》（下称 v1.0）/《企业资质页-页面级契约-v1.0》（下称 QUAL）。

## 0. 用户口径（原文要点）
1. 需要「电子证照管理」模块，**分别管理企业资质与个人资质**；目前只是**手工录入**信息。
2. **后续可能有其他录入方式**，需要**把位置空出来**。
3. **企业资质审查**：目前**没有机器和接口审查**，只能**人工审查**；**只生成企业证照**，**员工证照由租户企业自己录入和审查**。
4. 审查时**由平台**执行，需要知道**是哪个企业**，然后它的**录入信息和文件都要查看**。
5. **审查通过后才能被其他接口调用，不然只能在审查接口**（访问）。
6. 录入时**主要是上传文件、填表**；**不要让用户输入他不可能知道的、或可以拿接口调用的静态信息**。

- 字典/配置：`/bidding/meta/dicts`、`/bidding/meta/configs`。

## 2. 缺口 A（阻塞）：企业资质「平台人工审查」缺少接口与门禁
### 2.1 现状为何不够
- 现有 `POST /bidding/qualification/approve|reject`（`bidding:qualification:approve|reject`）语义是**延续申报单的审批**（QUAL §3.3/§3.4，作用于 `qual_apply_status`），**不是**"首次录入的资质能否被平台认可"。
- 现有 `POST /bidding/qualification/review/run`（`bidding:qualification:review`）是**达标核查（规则复算）**，用户明确"目前没有机器和接口审查，只能人工审查"——该能力本期不作为审查依据。
- 因此 v1.0/QUAL 全文中**不存在**"审查通过前不得被其他接口调用"的门禁（已逐条核对 v1.0 §2–§9、QUAL §3–§5）。
### 2.2 请后端确认/新增
| # | 需要 | 建议形态 | 说明 |
| --- | --- | --- | --- |
| A1 | 资质状态增加「待平台审查」 | `qual_status` 新增值 `PENDING_REVIEW`（字典 `qual_status` 同步增加，含 label/tagType/sort；是否终态=false） | 企业录入后初始为 `PENDING_REVIEW`；平台通过后 → `VALID`；驳回 → `REJECTED`（如复用现有 `REJECTED` 语义需后端确认） |
| A2 | 审查队列（分页） | `GET /bidding/qualification/platform-review/page`，入参 `entId`/`qualStatus`/`keyword`/`submittedFrom`/`submittedTo`/分页；出参含 **entId、企业名称、统一社会信用代码、资质三联动、certNo、submitTime、qualStatus、version** | 平台视角必须能看出**是哪个企业**（用户口径 4） |
| A3 | 审查详情（企业 + 录入信息 + 文件） | 复用 `GET /bidding/qualification/get` 补出参：`entName`、`entUscc`、`files[]`（`fileId/文件名/类别/sha256/上传时间`） | 用户口径 4「他的录入信息和文件都要查看」；若不便扩展现有出参，请新增 `GET /bidding/qualification/platform-review/get` |
| A4 | 审查动作：通过 / 驳回 | `POST /bidding/qualification/platform-review/approve`、`.../reject`；入参 `qualId`、`version`（乐观锁，必传）、`remark`（驳回必填）；幂等；权限点建议独立 `bidding:qualification:platform-review` | 不建议复用 `:approve`（那是申报单审批，混权限会让租户企业自己也能"通过"自己的资质） |
| A5 | **门禁**：未通过的资质只能被审查接口访问 | 在配证、申报、安许风险联动、要素引用等写接口中校验：资质 `qualStatus != VALID` 时拒绝，错误码复用 v1.0 §9 的 `1060107008`（证书已失效/不能用于配证或申报）或新增专用码 | 用户口径 5。请明确**只读查询是否也拦**（前端建议：列表/详情可读，**写与引用一律拒**） |
| A6 | 审查留痕 | 记录 `reviewedBy/reviewedAt/reviewResult/remark`，并允许 `GET /bidding/cert-lifecycle/page?bizDomain=ENTERPRISE_QUAL&bizId=<qualId>` 或新增审查历史查询 | 追溯"谁在什么时候通过/驳回" |
### 2.3 边界（避免与既有能力冲突）
- **只对企业资质**启用该门禁；**员工证照不设平台审查**，由**租户企业自审**（现有 `PUT /bidding/personnel-certificate/change-status` 已可流转，符合口径 3）。
- 修复/换证等后续动作是否重新进入 `PENDING_REVIEW`，请后端给出口径（前端建议：仅**首次录入**与**关键字段变更**需重新审查）。

## 3. 缺口 B：录入「企业主体」不应让用户手填 id
- 现状：`views/bidding/personnel/index.vue` 第 876 行让用户手填 `entId`（`a-input-number placeholder="企业主体 id"`），企业资质页同样需要 entId。
- 用户口径 6 明确"不要让用户输入他不可能知道的"。
- 请后端二选一：
  - B1（推荐）`GET /bidding/subject/profile/list`（本租户企业主体选项：`id`、`subjectName`、`uscc`、`subjectType`），前端下拉选择；
  - B2 确认可直接用 `GET /bidding/subject/profile/get?subjectType=BIDDER|TENDERER` 取当前登录企业主体（单主体场景即可自动带出，无需用户选）。
- 若同时存在多主体，请说明**如何区分**（前端不得自造键，见 v1.0/doc10 §24 口径）。

## 4. 缺口 C：为「其他录入方式」留出扩展位
- 用户口径 2：后续可能有其他录入方式（如官方通道同步、批量导入、API 推送），**先把位置空出来**。
- 现状：`certificate_info` / `qualification_info` 均有 `sourceChannel`（字典 `source_channel`）。
- 请后端确认：
  - C1 字典 `source_channel` 补齐**预留值**（前端建议：`MANUAL` 手工录入（本期唯一可用）、`API` 接口推送、`IMPORT` 批量导入、`OFFICIAL_SYNC` 官方通道同步），并标注哪些**本期不可用**（前端将渲染为"暂未开放"占位，不隐藏）；
  - C2 是否需要在录入接口显式传 `sourceChannel`（前端建议：本期由后端固定 `MANUAL`，前端不传，避免用户误选）；
  - C3 若未来"其他录入方式"会**跳过审查**，请在门禁（A5）中一并给出规则。

## 5. 前端将如何配合（不依赖后端新增即可先做的部分）
- 录入表单：以**文件上传 + 填表**为主；企业名称、统一社会信用代码等**由主体档案接口带出**（`cert-form.vue` 已有 `takeOrgName()` 先例），不提供手填入口；平台注入字段保持只读折叠（`vo/voFieldControl.ts` 的 `PLATFORM_MAINTAINED_CODES`）。
- 枚举/阈值：一律取 `GET /bidding/meta/dicts`、`GET /bidding/meta/configs`，**不硬编码**（v1.0 §0.5）。
- 写接口一律按钮 loading + 禁用，`version` 原样回传（v1.0 §0.7）。
- 审查界面（待 A2–A4 就绪后接）：列表→详情（企业信息 + 录入信息 + 文件预览）→ 通过/驳回（**驳回必填理由**）；无权限按钮**隐藏**，无 query 权限整页 403 占位（QUAL §1.1）。

## 6. 验收标准（后端交付后前端据此验收）
1. 平台账号能在审查队列看到**企业名称 + uscc + 资质信息 + 文件**；
2. 通过后该资质 `qualStatus=VALID`，且可被配证/申报类接口引用；
3. 未通过（PENDING_REVIEW/REJECTED）的资质在该类接口被拒（错误码明确）；
4. 员工证照**不出现**平台审查入口，租户企业可自行录入并流转状态；
5. 字典 `source_channel` 含预留值，前端可渲染"暂未开放"占位。

## 附二：前端已实现（2026-09-20 第 3 轮）——UI 已消费的**确切**字段

> 平台审查页签**已实现**：`views/bidding/qualification/index.vue` 的「⑥ 平台审查」（队列 + 详情 + 通过/驳回）。
> 后端按下列**确切字段名**返回即可直接生效；字段缺失不白屏（按空值降级），但功能会不全。

### 接口与权限

| 用途 | 方法 路径 | 前端使用的权限点 |
| --- | --- | --- |
| 队列分页 | `GET /bidding/qualification/platform-review/page` | `bidding:qualification:platform-review` |
| 详情 | `GET /bidding/qualification/platform-review/get?id=` | 同上 |
| 通过 | `POST /bidding/qualification/platform-review/approve` | 同上 |
| 驳回 | `POST /bidding/qualification/platform-review/reject` | 同上 |

- 该权限点**未注册时**前端隐藏「通过/驳回」并显示"无审查权限"提示（不报错）。**请务必注册并授予平台审查角色**，否则按钮不可见。
- 前端**不硬编码**企业主体：审查队列**跨企业**（不跟随"页首主体"选择），企业身份由后端在每一行返回（`entName`/`entUscc`）。

### 队列分页入参（前端已发送）

`pageNo`、`pageSize`、`keyword`（企业名称/统一社会信用代码模糊）、`qualStatus`。

### 响应字段（前端已读取，务必同名）

- 队列行：`id`（资质 id，详情与动作都用它）、`version`（**通过/驳回必须回传的乐观锁**）、`entId`、`entName`、`entUscc`、
  `qualSerial`、`qualCategory`、`qualGrade`、`certNo`、`submitTime`（时间戳或可被解析的日期串）、`qualStatus`。
- 详情：队列行全部字段 + `issuingAuthority`、`issueDate`、`validTo`（空视为"长期"）、`remark`、`files[]`。
- `files[]` 每项：`fileId`、`fileName`、`fileSize`（**字节**，前端 ÷1024 显示 KB）、`fileCategory`（走 `file_category` 字典）、`uploadTime`。

### 动作入参（前端已发送）

```json
{ "qualId": 123, "version": 7, "remark": "驳回理由（驳回必填，通过可空）" }
```

- `version` 缺失时前端**拒绝提交**并提示重新打开详情（乐观锁口径 §0.7）；后端乐观锁失败请返回明确错误码。
- 前端按 **404** 判定"后端未实现"并显示空状态；**业务错误**（无权限、乐观锁冲突等）按原始 `msg` 提示。

### 员工侧口径（已确认，无需后端改动）

员工证照**不出现**平台审查入口；租户企业自审走既有 `PUT /bidding/personnel-certificate/change-status`（员工资质页已具备）。
