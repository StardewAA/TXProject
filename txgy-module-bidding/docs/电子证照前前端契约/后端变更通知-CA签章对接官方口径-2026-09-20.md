## 一、先理清：为什么有两套签章接口

| 接口族 | 口径 | 用途 |
| --- | --- | --- |
| `/bidding/ca/seal/**`（现有） | **本模块自定义** | 本地测试签章、演示数据、单纯盖章 |
| **`/bidding/ca/share/**`（本次新增） | **官方固定格式** | **对接官方 CA 互认签章工具/组件** |

**关键**：官方组件按**固定 JSON 结构**回调，字段名/嵌套/类型任一不符就反序列化失败 → 回调丢失 → 签章结果不入账。
所以官方口径必须**逐字对齐**，不能"合理简化"。

## 二、官方调起参数（前端构造后交给官方工具）

官方《指南》§5.3.1 原文结构（**字段名照抄，注意大小写**）：

```json
{
  "CAShareUseScene": "00",
  "keyParameter": {
    "document": [{
      "awaitingSignatureFilePath": "待签章文件地址（本地路径或网络路径）",
      "awaitingSignatureFileName": "待签章文件名称",
      "signatureFileSavePath": "签章后文件保存路径",
      "signatureFileName": "签章后文件名称",
      "awaitingSignatureFileType": "pdf"
    }],
    "seal": { "dpi": 96, "transparency": 0.8, "sealImgMaxValue": 150 }
  },
  "caShareComponentConfig": {
    "tradingSystemCode": "交易系统编码",
    "serviceUrl": "CA互认共享组件服务地址",
    "clientId": "客户端ID",
    "clientSecret": "客户端密钥",
    "accessKeySecret": "签名密钥"
  },
  "tradingSystemConfig": { "callBackUrl": "回调地址" }
}
```

### ⚠️ 三个易错点（官方原文如此，**不要"纠正"**）
1. `CAShareUseScene` —— **大驼峰**，不是 `caShareUseScene`
2. `callBackUrl` —— **大写 B**，不是 `callbackUrl`
3. 客户端密钥字段名：官方**文档表格写 `ClientSercet`**（拼写瑕疵），**JSON 示例写 `clientSecret`**。
   后端 VO **两个字段都收**（填其一即可）；前端建议按 **JSON 示例的 `clientSecret`**（示例是可直接运行的代码）。

### 调起前的硬性要求（官方明示）
- **当前待签章文件必须处于关闭状态**才能调起检测安装工具；
- 用户机器需**退出 360/腾讯管家**等（否则注册表写入被拦），这属客户端环境问题，前端只需提示。

## 三、官方回调（**后端已实现，前端了解即可**）

### 3.1 H5 组件回调 —— `POST /admin-api/bidding/ca/share/seal/callback`

官方格式（`action` + `data` 包裹）：
```json
{
  "action": "allDone",
  "data": {
    "awaitingSignatureFileId": "...", "sourceFileKey": "...", "sourceFileStorage": "s3",
    "status": "20", "targetFileKey": "sign/202411/24/final_xxx.pdf", "targetFileStorage": "s3",
    "time": "20241124154901", "tradingSystemCode": "C1100005553",
    "transactionId": "...", "userId": "userId",
    "signatureInfo": {
      "callbackRequestType": "完成签章",
      "completedSignatureTime": "2024-11-24 15:49:01",
      "tradingSystemCode": "C1100005553",
      "document": [{
        "awaitingSignatureFileHash": "...", "awaitingSignatureFileName": "...",
        "fileCurrentSealCount": 2, "fileSignatureStatus": "已签章已验章",
        "fileTotalPages": 98, "fileTotalSealCount": 135,
        "signatureFileHash": "...", "signatureFileName": "sign/..."
      }]
    }
  }
}
```
- `action`：`sign` 单词签章 / `allDone` 本批全部完成
- `data.status`：`10` 进行中 / `20` 已完成 / `30` 失败（**仅 20 落库**）

### 3.2 客户端工具回调 —— `POST /admin-api/bidding/ca/share/seal/client-callback`

官方格式（**扁平结构**，与 H5 不同）：
```json
{
  "tradingSystemCode": "C1100005553",
  "callbackRequestType": "signedAndVerified",
  "completedSignatureTime": "2024-11-24 15:49:01",
  "document": [{ "awaitingSignatureFileName": "...", "signatureFileName": "...",
                 "awaitingSignatureFileHash": "...", "signatureFileHash": "...",
                 "fileTotalPages": 98, "fileTotalSealCount": 135,
                 "fileCurrentSealCount": 2, "fileSignatureStatus": "1" }],
  "ipAddress": "...", "macAddress": "...", "cpuSn": "...", "hardDiskSn": "..."
}
```
- `callbackRequestType`：`exitSignature` 退出程序 / `signedAndVerified` 完成签章与验
  （**退出程序也带 document，但不视为完成签章**——后端已按官方语义区分）

### 3.3 回调响应（后端**必须这么回**，官方按此解析）
```json
{ "code": 200, "success": true, "data": null, "msg": "成功接收签章组件回调", "errorCode": null }
```
> 所以这两个端点**不用** `CommonResult` 结构——用了官方会判为失败。

### 3.4 回调如何落到台账（后端映射，前端无需关心）
| 官方字段 | 落到 |
| --- | --- |
| `awaitingSignatureFileHash` | 匹配键（对 `bidding_ca_seal.file_sha256`） |
| `signatureFileName` | `seal_file_name` |
| `fileSignatureStatus`=已签章已验章 | `verify_status`=PASS（其余保持 UNVERIFIED，不臆断通过） |
| `completedSignatureTime` | `seal_time` |
| `fileCurrentSealCount` | `remark`（本模块无"签章数量"列，记入备注留痕） |

## 六、前端实测核对结论（2026-09-20）—— ⛔ **两个回调端点当前不可用，需后端修**

> 本节为前端按本文档 §三 逐字构造官方报文后的**实测结果**（活服务，网关 48080）。

### 6.1 实测结果：两个端点都返回 401，拿不到官方响应结构

```
POST /admin-api/bidding/ca/share/seal/callback          （官方 H5 报文，status=10 / status=20 均试）
POST /admin-api/bidding/ca/share/seal/client-callback   （官方客户端报文，signedAndVerified / exitSignature 均试）
→ 全部返回： {"code":401,"data":null,"msg":"账号未登录"}
```

**期望**（本文档 §3.3 / 官方 §4.2.2）：`{code:200, success:true, data:null, msg:"成功接收签章组件回调", errorCode:null}`

**后果**：官方 H5 组件 / 客户端工具按自己的结构解析响应，收到 401 会判为**回调失败**，可能反复重试或直接报错
——即"签章做完了但结果入不了账"。这正是本文档开头强调的"逐字对齐"要防的情况，只不过这次卡在**鉴权层**而非字段层。

### 6.2 根因：注释里写了 `@PermitAll`，但**注解没加**

`CaShareCallbackController` 类注释：

> 两个端点均为 `{@code @PermitAll}` 语义（**不加 @PreAuthorize**）

**这个假设不成立**：本框架下 `/admin-api/**` 默认要求登录，"不写 `@PreAuthorize`" ≠ "放行"。
需显式加注解。同模块的既有免登端点都是这么写的：

| 文件 | 写法 |
| --- | --- |
| `NoticeController.publicList / publicDetail` | `@PermitAll`（`jakarta.annotation.security.PermitAll`） |
| `NoticeExternalController.page / go` | `@PermitAll` + **`@TenantIgnore`**（注释原文："大厅公开：G 轨全局数据，无租户概念（**免租户头直接可访**）"） |

### 6.3 需要后端做的修复：**两个注解都要加**（不是"评估"，是必需）

官方组件/客户端 POST 回调时**既不带登录态、也不带 `tenant-id` 头**，因此要穿过两道关卡：

| 关卡 | 缺什么 | 现状 | 修法 |
| --- | --- | --- | --- |
| ① Security 登录态 | `@PermitAll` | **实测 401**（带/不带 `tenant-id` 都是 401，说明 Security 先拦） | 两个方法各加 `@PermitAll` |
| ② 租户拦截器 | `@TenantIgnore` | 现在被①挡住、还看不到；①修好后会暴露 | 两个方法各加 `@TenantIgnore` |

**② 的依据是代码里自己的注释，不是推测** —— `NoticeController.java` 的两个大厅公开端点：

```java
@PermitAll
@TenantIgnore // 大厅公开：未登录请求无租户上下文，不加此注解会被租户拦截器拦为「请求的租户标识未传递」
public CommonResult<PageResult<NoticeRespVO>> publicList(...)
```

`publicDetail` 同款注释：`// 同 publicList：大厅公开端点须忽略租户上下文（与 notice-external 同口径）`。
框架侧对应 `TenantContextHolder.getRequiredTenantId()`：无租户上下文时直接抛「不存在租户编号」。

**只加 `@PermitAll` 是不够的**：过了 Security 仍会撞上租户拦截器，官方工具会拿到「请求的租户标识未传递」，
一样是"章盖完了结果入不了账"。

### 6.3.1 口径已定：**回调不带租户，就是该忽略租户**（不需要"二选一"）

**业务事实（需求方 2026-09-20 明确）**：CA 签章用的是**签章人自己在外部 CA 平台的个人账号**
——**该账号根本不在我们系统里，与我们任何一个租户都没有关系**。整条链路是"调人家的外部接口"，
因此回调报文里**没有、也不应该有租户标识**；我们带 `tenant-id` 对它毫无意义。

**结论**：两个方法**直接加 `@TenantIgnore`**，不做"回调带租户标识"的方案。
台账匹配就按**文件指纹 `file_sha256` 全库匹配**（这正是 `CaShareCallbackServiceImpl` 现在的做法）。

**由此给后端的一条口径确认（唯一需要写明的点）**：`@TenantIgnore` 下匹配是**跨租户**的，
若同一个文件（同 SHA-256）在多个租户下各有一条 `bidding_ca_seal` 记录，回调该回写哪一条会**有歧义**。
建议后端二选一写明并落到代码：
- a) 只回写**最近一条未完成**（`verify_status != 'PASS'` 或 `seal_file_name is null`）的记录；
- b) 或对 `file_sha256` + 未完成态加唯一约束，从数据层杜绝歧义。
（实务上投标/证照文件不会跨租户重复，风险低，但口径应写明，避免以后出问题查不出来。）

### 6.4 修复后的验收方式（前端可复跑）

```bash
curl -s -X POST "$API/bidding/ca/share/seal/callback" -H 'Content-Type: application/json' \
  -d '{"action":"allDone","data":{"status":"20","transactionId":"T","signatureInfo":{"completedSignatureTime":"2026-09-20 15:49:01","document":[{"awaitingSignatureFileHash":"<台账里真实存在的 file_sha256>","signatureFileName":"sign/x.pdf","fileSignatureStatus":"已签章已验章","fileCurrentSealCount":2}]}}}'
# 期望：{"code":200,"success":true,"data":null,"msg":"成功接收签章组件回调","errorCode":null}
# 并核验：bidding_ca_seal 对应行 verify_status=PASS、seal_file_name/seal_time 已回写
```

> 附：本次实测用**不存在的 hash**做负向验证，确认"匹配不到就跳过、不误写台账"——该行为正确（台账仍 0 行）。
> 另：两个端点 **HTTP 状态码是 200**（业务码在 body 的 `code` 字段），所以"HTTP 200"不能当作端点可用。
