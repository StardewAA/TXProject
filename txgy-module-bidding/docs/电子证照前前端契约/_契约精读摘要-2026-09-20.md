出处缩写：**[v1.0]**=电子证照模块-前端接口契约-v1.0.md（1735 行，契约自称唯一事实来源）；**[v1.1]**=电子证照模块-前端接口契约-v1.1-安许风险联动.md（336 行）；**[QUAL]**=企业资质页-页面级契约-v1.0.md（470 行，含升到 v1.4 的变更记录）；**[NOTIFY]**=后端变更通知-给前端.md（209 行，编号越大越新）；**[BL]**=营业执照纳入证照台账-前端接入契约.md（120 行）。

## 3. 状态机与流转

**3.1 证照台账 cert_status**（[v1.0] §1.1）：ACTIVE 正常(success) / EXPIRING_SOON 即将到期(warning) / EXPIRED 已过期(error) / SUSPENDED 暂扣(warning) / REVOKED 吊销(error, **terminal=true**) / CANCELLED 注销(info, **terminal=true**)。流转入口唯一：`POST /bidding/certificate/change-status`（targetStatus 取字典；reason 建议必填）。非法流转→1090109003；契约要求"目标状态选项 = 字典中**非终态**项 ∪ 允许恢复项"，但**不自行推断合法跃迁**，以 terminal 禁用按钮、以后端返回为准（[v1.0] §2.5）。状态字段**不在 update 接口改**，避免绕过留痕（[v1.0] §2.4）。
**3.2 验真 verification_status**：UNVERIFIED / VERIFYING / VERIFIED / INVALID（[v1.0] §1.1）。三段式：发起验真返回历史主键 → **前端不轮询验真接口**，短延时 3~5 秒后重拉详情读 verificationStatus/lastVerifiedAt（[v1.0] §4.1）；INVALID 需红色告警。v1.1.5 补充：幂等改为按配置窗口的滑动窗口、键前缀隔离 INFO:/FILE:；窗口内重复点"验真"返回的是**既有那条历史**（其 verifiedAt 可能早于本次请求），前端若展示"本次验真时间"应读该记录的 verifiedAt（[v1.0] §11 v1.1.5）。
**3.3 文件类别 file_category**：ORIGINAL 原件 / COPY 加注件 / CHANGE_PAGE 变更页 / RENEWAL_PAGE 延续页 / E_CERT 电子证照；版本只追加不覆盖，isCurrent 标当前（[v1.0] §1.1/§3.1）。
**3.4 生命周期 lifecycle_status**：PENDING 待办 → REVIEWING 审核中 → APPROVED 已通过 → EFFECTIVE 已生效，另有 REJECTED 已驳回（[v1.0] §1.1）。audit 只允许 targetStatus=REVIEWING/APPROVED/REJECTED；**effect 仅 APPROVED 可调**；非法→1060107016"生命周期流程状态流转非法（待办→审核中→通过→生效）"（[v1.0] §6.2/§6.3）。契约明确"**生效才回写台账**：审核通过 ≠ 已生效"，前端必须分两个时点展示（[v1.0] §6 引言、§6.3）。
**3.5 资质 qual_status**（[QUAL] §5 状态机，后端 isTransitionAllowed 裁决）：VALID ──到期窗口──▶ EXPIRING_SOON ──过有效期──▶ EXPIRED；VALID/EXPIRING_SOON ──发起延续──▶ PENDING_RENEW ──批复通过──▶ VALID（回写新有效期）；PENDING_RENEW ──退回──▶ VALID（还原）；VALID/EXPIRING_SOON/EXPIRED ──限制/吊销──▶ LIMITED / REVOKED（**终态，不可回退**）。
**3.6 资质申报 qual_apply_status（8 态）**：DRAFT 草稿 → SUBMITTED 已提交 → ACCEPTED 已受理 → REVIEWING 审核中 → APPROVED 已批准 → PUBLISHED 公示中 → ISSUED 已办结；任一环节退回 → REJECTED 已退回（可重新发起新申报）。泳道：待受理(SUBMITTED)/审核中(ACCEPTED+REVIEWING)/待领证(APPROVED+PUBLISHED)/已办结(ISSUED)/已退回(REJECTED)。**"在途申报"口径=状态不属于 DRAFT/ISSUED/REJECTED**（决定"延续申报"按钮是否置灰）（[QUAL] §5）。
**3.7 安许 safety_permit_status**：VALID ⇄ EXPIRING_SOON → EXPIRED；VALID → SUSPENDED（暂扣）→ VALID（恢复）或 REVOKED（终态）（[QUAL] §5）；字典值 VALID/EXPIRING_SOON/EXPIRED/SUSPENDED/REVOKED（[v1.0] §1.1）。
**3.8 员工证书 person_cert_status**：VALID / EXPIRING_SOON / EXPIRED / SUSPENDED / REVOKED / CANCELLED；类型 person_cert_type：ID_CARD / EDUCATION_CERT / DEGREE_CERT / TITLE_CERT / REG_PRACTICE_CERT / SAFETY_ASSESS_CERT / SKILL_CERT / TRAINING_CERT / OTHER（[v1.0] §1.1）。
**3.9 注销吊销方式 revoke_type → 目标状态**：REVOKE 吊销→REVOKED / CANCEL 注销→CANCELLED / SUSPEND 暂扣→SUSPENDED / RESTORE 恢复→VALID（[v1.0] §1.1）。
**3.10 材料 material_result**：PASS 齐备 / RISK 部分缺失或临近到期 / FAIL 必备材料缺失；material_status：READY 齐备 / EXPIRING 临近到期 / MISSING 缺失 / EXPIRED 已过期（[v1.0] §1.1；注意 [v1.0] §7.1 items.status 只写 READY/EXPIRING/MISSING，[QUAL] §3.10 写含 EXPIRED）。
**3.11 风险标签**：safety_risk_flag：NORMAL 正常 / YELLOW 黄色预警 / RED 红色预警 / INVALID 失效 / FREQUENT 频繁预警（企业级）；person_risk_flag：NORMAL 正常 / ABNORMAL 一年异常 / FREQUENT 频繁异常（人员级）；risk_level：LOW / MEDIUM / HIGH / MAJOR（[v1.1] §12.0）。企业级与人员级**严格分离**（[v1.1] §12.6）。业务口径（[v1.1] §12 背景）：A/B/C 任一不达标→黄；任一为 0→红；全为 0→失效；一年预警≥4 次→频繁；法定代表人变更致仅剩 1 名 A 证给 180 天宽限；劳务分包企业 B 证为 0 不触发红。
**3.12 "审查通过后才可被其他接口调用、否则只能在审查接口访问"在契约中的具体体现**：契约全文**没有**这句通用门禁的表述，也没有"审查接口独占"的机制定义。可对应的具体落点只有：
① 生命周期三段式——只有 `/cert-lifecycle/effect` 在 APPROVED 后执行才回写台账主档，未生效前主档不变（[v1.0] §6/§6.3）；
② 业务资格门禁——错误码 **1060107008"证书已失效（过期/吊销/注销），不能用于配证或申报"**（[v1.0] §9），即失效证书不能被配证/申报类接口使用；另有 1060107009"该证书类型必须登记有效期"；
③ 安许风险阻断——§12.1 的 blocked（服务端按配置判定）用于禁用招投标提交 / 施工许可申报 / 现场监督检查三入口的提交（[v1.1] §12.1；阻断档位默认配置 safety.abc.block.flags=["INVALID","RED"]，**最终以接口 blocked 字段为准**，[v1.1] §12.0）；
④ 资质行级禁用——状态 EXPIRED/REVOKED 的行只保留"查看"，延续申报按钮置灰（[QUAL] §2）；
⑤ 写入互斥——hasPendingApply=true 时"延续申报"按钮置灰（[QUAL] §3.11；在途口径见 3.6）。
以上均为"业务动作被禁用/被拒"，**不存在**"非审查角色连查询都访问不到"的字段或校验描述。

## 4. 规则（契约明文）

**4.1 审查主体（平台 vs 租户）**：**这 5 份契约中没有任何"企业证照由平台审查、员工证照由租户企业自审"的表述**——在本目录检索"平台审查 / 由平台 / 平台侧 / 租户企业 / 由租户 / 企业自审"均 0 命中。契约中与"谁审"相关的可用事实只有：① 资质延续审批的按钮权限码是租户侧 `bidding:qualification:approve` / `:reject`（[QUAL] §1.1）；② 生命周期审核权限码 `bidding:certificate:lifecycle:audit`（[v1.0] §6.2）；③ 安许风险接口权限码 `bidding:qualification:permit:query|update`（[v1.1] §12.1/§12.4）；④ [QUAL] §3.22 明确"处理人由服务端从登录态取"（防代人签字）。**结论：该规则在本契约集内无出处，属留白（见 §5）。** 唯一与"审查"字面相关的表述是 [v1.0] §2.5"投标资格审查的硬门槛数据来源"与 [QUAL] §3.7"作为投标资格审核的依据"，均指**结果被用于**投标审核，未规定审查主体归属。
**4.2 录入方式**：契约文档化的唯一录入路径是"**文件上传 + 填表**"——先走通用文件服务上传拿到 `fileId`，再 `POST /bidding/certificate/file/register` 登记元数据（[v1.0] §3.1④；[BL] 第2步）。数据来源字典 source_channel 含 MANUAL 手工录入 / IMPORT 批量导入 / **OCR 识别录入**（[v1.0] §1.1），即另外两种录入方式**只在字典里预留，契约未定义任何批量导入/OCR 接口**（见 §5-27）。
**4.3 不得用户手填 / 必须自动带出 / 不可改的字段（逐条）**
