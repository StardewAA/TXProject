## §1【后端缺陷 · 必修】follow() 幂等分支不重建被软删的关注列表行

### 现象（用户报障）
门户「投标流程管理」看不到**已关注**的外部公告；重新点「关注」也无济于事（接口返回成功）。

### 实锤证据（本地库 2026-10-02 实测）
| 表 | 目标 PROJECT `0866-26D2SXQY0628`（user 1） |
|---|---|
| `bidding_notice_subscription`（关注状态） | 有行，`follow_status=FOLLOWING` |
| `bidding_follow_item`（**门户关注列表 `GET /notice-follow/item/page` 的数据源**） | 行存在但 `deleted=1`（软删） |

即：**订阅有效、关注列表行被软删** → `pageMyFollow()` 过滤 `follow_status=FOLLOWING` 且 MyBatis 逻辑删除过滤 `deleted=0` → 查询为空 → 门户看不到。

### 根因（源码）
`FollowServiceImpl.follow()`：

```java
NoticeSubscriptionDO exists = findSubscription(userId, targetType, targetKey);
if (exists != null) {
    if (!STATUS_FOLLOWING.equals(exists.getFollowStatus())) {
        exists.setFollowStatus(STATUS_FOLLOWING);
        ...
        restoreFollowItem(exists);      // ← 只有"退订后再关注"才恢复行
    }
    return;                             // ← 订阅仍 FOLLOWING 时直接返回：
}                                       //    不检查 follow_item 是否存在/是否被软删
```

→ 一旦 `follow_item` 行被软删而订阅仍是 FOLLOWING，**用户永远无法通过"重新关注"恢复**（接口永远返回成功，列表永远为空）。

### 修复要求
`exists != null && STATUS_FOLLOWING` 分支在 `return` 之前，必须检查关注列表行并自愈：

1. 查询必须**包含已软删行**（`findItem` 当前受逻辑删除过滤，查不到被删行 → 需用忽略逻辑删除的查询，或按 `(tenant_id,user_id,follow_type,follow_key)` 直查）；
2. 行不存在 → 按现有建行逻辑补齐（`display_name` 快照、`stage_code=UNKNOWN`、`unread_count=0`）；
3. 行存在但 `deleted=1` → 恢复：`deleted=0`、`follow_status=FOLLOWING`、`unfollow_time=NULL`，并刷新快照（`display_name`/`issuer_name`）；
4. 顺带：`pageMyFollow()` 可按订阅表兜底（发现 FOLLOWING 订阅缺列表行时补建），作为二次保险。

### 影响面
所有经历过"关注行被清理/软删"的用户（本库 1 个 user、3 条外部关注已中招），以及未来任何数据修复/清理场景。

## §2【数据一致性要求】软删 follow_item 必须同步订阅表

- 事实：2026-09-25 12:42:47 一次 `updater='cleanup'` 的批量操作把 `bidding_follow_item` 的 **8 行**软删（含 3 行 FOLLOWING 的外部项目关注），**未同步** `bidding_notice_subscription` → 两表状态分叉，直接触发 §1 的死锁。
- 要求：任何对 `bidding_follow_item` 的软删/清理，必须**同一事务内**处理对应订阅行（同时软删，或都不动）；取关动作（`unfollow()`）当前实现是正确的（两表同改），请保持。
- 建议：加一条对账（定时或在 `pageMyFollow` 兜底）——订阅 FOLLOWING 而列表行缺失/被删时自动补齐。
