# 后端变更请求：公告公开检索需覆盖本站公告（2026-10-02）

## 一、现象（用户验收反馈）

门户公告大厅按**编号**查询，查不到本平台自己发布的公告。

例：本站公告 `B6100002026000005`（炼化公司…装置大修/消缺公开招标招标公告，bidding_notice 表，PUBLISHED）

## 二、实锤（网关 48080 实测，2026-10-02）

```
GET /admin-api/bidding/notice/public/list?keyword=B6100002026000005&pageNo=1&pageSize=3
→ {"code":0,"data":{"list":[],"total":0}}          ← 编号精确查询：空

GET /admin-api/bidding/notice/public/list?keyword=炼化&pageNo=1&pageSize=3
→ {"code":0,"data":{"list":[],"total":0}}          ← 标题关键词：空

GET /admin-api/bidding/notice/public/list?pageNo=1&pageSize=2
→ {"code":0,"data":{"list":[{...B6100002026000005...}]}}   ← 不带 keyword：正常有数据
```

结论：`public/list` 的 keyword 走检索组件，**索引只覆盖外部公告域（bidding_notice_external）**，
本站公告（bidding_notice）未进索引 → 关键词/编号查询恒为空。

## 三、影响

- 门户大厅：用户按公告编号（如 B6100002026000005）或标题关键词检索，**永远查不到本平台发布的公告**
  （含中标候选人公示、中标结果公示等本站公示）；
- 门户「本站」来源筛选 + 关键词组合同样为空；
- 该缺陷在验收中由用户直接报出（"编号查询查不到内部公告"）。

## 四、请求（二选一，后端定）

**方案 A（推荐，与外部域一致）**：为 `bidding_notice` 建检索索引（索引字段建议：
notice_code / title / project_name / project_code / notice_type），
`public/list` 的 keyword 同时命中外部索引与本站索引。

**方案 B（轻量）**：`public/list` 的 keyword 对本站公告退化为
「notice_code 精确/前缀匹配 + title LIKE」结构化查询
（编号查询是**主键类查询**，不是全文检索，规范 4.6「业务表不做全文 LIKE」不构成障碍；
若规范上仍不允许，请给出口径）。

## 五、前端现状（兜底，不阻塞用户）

前端已实现**本地匹配兜底**（commit `770b728e2`）：
门户大厅关键词/编号查询时，本站侧改为拉取（上限 200 行，MAX 截断如实告知）后
本地按 编号/标题/项目编号/项目名 匹配（大小写不敏感），命中则与外部结果合并展示。

**局限**：本站公告超过 200 条后可能漏命中；后端方案 A/B 落地后前端应删除该兜底（回归服务端检索）。

## 六、验证方式（后端落地后）

```
GET /admin-api/bidding/notice/public/list?keyword=B6100002026000005   → total ≥ 1（命中该公告）
GET /admin-api/bidding/notice/public/list?keyword=炼化                 → total ≥ 1
```
