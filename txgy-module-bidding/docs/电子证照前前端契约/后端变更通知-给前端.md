### 37. 🟡 错误码分流：**401 才跳登录页，403 不要跳**（新增契约文档，2026-09-21）

**影响范围**：全部页面（web-antd 全模块）。用户反馈「不管是缺权限还是没登录都直接跳登录页」，
无权限用户会陷入**登录 → 跳回 → 再登录 → 再跳回**的死循环（权限不会因为重新登录而出现）。

**契约文档（请前端精读）**：《33-前端错误码分流契约-401与403不再一律跳登录-2026-09-21.md》
（`docs/前端规范-全域接口说明/`），含实测基线表 + 验收自测清单。

**核心事实（活服务实测，非推断）**：
- 本框架**鉴权失败不是 HTTP 401，是 HTTP 200 + `body.code`**——`res.ok`/`res.status`/`error.response.status` 全都判不出来；
- **未登录/token 失效 → `code=401`**；**已登录但无权限 → `code=403`**（两者后端已正确区分，可直接依赖）；
- 因此：**只有 401 清登录态 + 跳登录页；403 留在当前页提示"无操作权限，请联系管理员开通"**。

| 探测（`/admin-api/bidding/certificate/page`） | HTTP | body.code |
| --- | --- | --- |
| 无 token / 无效 token | 200 | **401** |
| 无权限账号 | 200 | **403** |
| 正常 | 200 | 0 |

**另外两条容易踩的**：
1. `GET /system/auth/get-permission-info` 在 **system 服务**，直连 bidding 端口会 404（走网关即可）；
   无角色账号返回 `roles/permissions/menus` 全为 `[]`，**code 仍是 0，不是未登录**。
2. 招投标域有**两种鉴权范式**：关注域/附件域/文件域/**标书审查门户**是**仅登录**（不需权限码），
   对这些入口做"按权限码置灰"会**误灰**；只有权限码范式的按钮才该置灰。

**前端需要做什么**：改统一 `requestClient` 拦截器一处，把 401/403 分流收敛；
清掉全仓基于 HTTP 状态的鉴权判定（§33 已登记过 6 处同类修复）。

#### ① 实测（不是推断）

用租户 1 的普通角色（`common`）账号实测，同一个域读写结果**不对称**：

| 调用 | 修复前 | 修复后 |
| --- | --- | --- |
| `POST /bidding/notice-follow/follow`（关注） | **code=0**（成功） | code=0 |
| `GET /bidding/notice-follow/status`（详情页关注按钮初始态） | **403 没有该操作权限** | **code=0** |
| `GET /bidding/notice-follow/item/page`（我的关注） | **403 没有该操作权限** | **code=0** |

前端把 403 渲染成「无操作权限（需要 bidding:notice-external:query/update），请联系管理员开通」，
并把关注按钮回落成「需登录」——所以看到的现象是"明明登录了却说需登录"。

#### ② 根因（两条，缺一不可）

1. **`bidding:notice-external:query` 在整个 `system_menu` 里没有承载菜单**（只有 `:update` 有 6736「外部公告审核管理」）。

2. **这个"查不到承载菜单"的结果也被缓存了**：Redis 里
   `permission_menu_ids:bidding:notice-external:query = ["java.util.ArrayList",[]]` ⇒
   **只补菜单不清缓存，仍然 403**。

| 动作 | 明细 |

| 脚本 | `txgy-module-bidding/sql/history/2026-09-21-门户关注权限承载修复.sql`（幂等 + 自带校验段），已登记进 `sql/README-完整执行清单.md` |

### 33. 🔴 判成败/判登录态**只看 `body.code`，不看 HTTP 状态** —— 全仓排查 + 6 处修复（2026-09-21）

**影响范围**：全部前端页面（web-antd 全模块，不限电子证照域）；重点是**取文件流 / 下载 / 预览 / 盖章取材**这几条链路。
**背景**：后端提醒「鉴权失败是 HTTP 200 + body `code:401`，不是 HTTP 401」。这条成立 —— 本轮已实测，并把全仓同类写法逐一改掉。

#### ① 实测（`admin-api`，无 token 裸请求，2026-09-21 复验）

| 端点 | HTTP | content-type | body |
| --- | --- | --- | --- |

| `POST /bidding/ca/share/launch-param`（R3 新端点） | **200** | `application/json` | 同上 |

⇒ `res.ok`、`res.status === 401`、`error.response.status` 在本框架里**判不出问题**。
带 token 且文件存在时：`HTTP 200 / application/pdf / Content-Disposition: inline`（内联预览口径正确，实测响应体以 `%PDF-` 开头）。

#### ② 全仓扫描结果（模式：`res.ok` / `response.status` / `status===401|403` / `http_code`）

**真问题 6 处（已改）**：

#### ③ 前端统一取件入口（新增，请复用）

`apps/web-antd/src/utils/fetchFile.ts` → **`fetchFileBlob(url, { allowJson?, auth? })`**

- 0 字节同样抛错。

2. 判登录态用 `body.code === 401`（或直接交给 requestClient 拦截器）；
3. review 时看到 `if (res.ok)` / `if (response.status === 401)` / `error.response.status` 就按本节改；
4. 本框架**成功**是 `code=0`，**不是** `code=200`（`code=200` 是官方 CA 回调那套结构，两套别串）。

#### ① Q15 催办：接口已可用（契约《后端变更请求-资质证书五页改造缺接口-2026-09-18》§Q15 落地）

| 项 | 实现（以代码为准） |
| --- | --- |
| 端点 | `POST /admin-api/bidding/cert-lifecycle/urge` |
| 入参 | **JSON body**：`{ "id": <生命周期记录主键> }`（VO `CertLifecycleUrgeReqVO`） |

**⚠️ 契约口径更正（3 点，前端按本节接线）**：

1. **入参必须走 JSON body，不是 query 参数**。契约 §Q15 只写了"入参 `id`"，未写传递方式。
   实测：`POST .../urge?id=999999` → `code=400 请求参数类型错误: request body 缺失`；
   `POST .../urge` + body `{"id":999999}` → `code=1060107015 证件生命周期记录不存在`（即端点与参数均正确）。
2. **`operatorId` 不要传**：后端由 `SecurityFrameworkUtils.getLoginUserId()` 取当前登录人（符合本文件 §12「id 类字段前端不传」口径）。
3. **前端需做什么**：时间轴「催办」按钮 → `POST` JSON body `{id}`；`code=0` 提示"已催办"；
   已催办过同日再次点击也返回 `code=0`（幂等，不报错），如需区分可前端自行按日记忆；
   终态记录建议前端**不渲染**催办按钮（后端会拒）。
