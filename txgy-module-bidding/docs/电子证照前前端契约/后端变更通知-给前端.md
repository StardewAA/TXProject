# 后端 → 前端 变更通知（电子资质域）

> **用法**：这是后端给前端的**单向通知文件**。只增不改历史条目；**编号越大越新**（新条目追加在末尾，避免与历史条目重排冲突）。
> 每条包含：影响范围 → 实际行为（以实现为准）→ 前端需要做什么（若有）。前端按需读取，不必逐条回复。
> 后端不再通过口头/群消息同步契约变更——**以本文件 + 契约文档为准**。
> 最后更新：2026-09-13（本轮）

## 本轮（2026-09-13）变更

### 1. ⚠️ 重要：预警清单现在会回传 `version`，`POST /bidding/qualification/alert/handle` 已可正常接入

- **接口**：`GET /bidding/qualification/alert/page` 的出参行新增字段 **`version`**（number）。
- **为什么**：`POST /bidding/qualification/alert/handle` 用版本号做并发控制（CAS，防止"我看到的备注"被覆盖或我覆盖别人），
  其请求体 `version` 为必填。此前清单**不回传 version**，前端拿不到真实版本号 —— 接了也只能发假值
  （要么恒冲突、要么等于绕过并发控制）。现已补上，属后端缺陷修复。
- **接入方式**：从清单行取 `version` 原样回传即可；若返回"记录已被他人处理/版本不一致"类业务错误，
  按契约 §3.22 的处理流程重新拉取清单再试。
- **权限码**：该端点用 `bidding:qualification:alert-run`（与"手动扫描"同一码，未新增码）。

### 2. 员工证书接口新增 `isCurrent` 字段（契约 §8.1、§8.2 同步受益）

- **接口**：`GET /bidding/personnel/certificate/page`（§8.1）、到期清单（§8.2）、按人查询证书列表。
- **字段**：`isCurrent` (boolean)，false = **已被换证替换的历史旧证**。
- **注意口径差异**：分页/到期清单两条接口的查询**只返回当前有效证**（故那里恒为 true）；
  **按人查全部证书**的接口会返回 false 的行 —— 需要区分"现行证/历史证"的界面请用后者。

### 3. 材料完备性自查的窗口键改名（不影响调用方式）

- 规则键由 `enterprise.material.expiring.window.days` 改为 **`qual.material.expiring.window.days`**（默认值仍 60）。
- **为什么**：分组校验按**键前缀**判组（QUAL 组要求 `qual.` 前缀），原名会让按分组拉配置时漏掉该项。
- **对前端**：该窗口由**后端**读取并决定 PASS/RISK/FAIL，前端不需要传、也不应写死；
  若页面要展示"当前生效的窗口天数"，走 `GET /bidding/meta/configs` 按分组 `QUAL` 拉取即可。

### 4. 后端已确认的契约缺口（前端无需改动，仅告知）

- 契约 §6.1「生命周期记录出参」里的 **`applyContentJson`（申请原文）本期未实现**：后端既无该列也无该字段，
  属"契约先写了、后端没做"。**不要按该字段开发**。若审批页确需对照申请原文，请回写需要哪些字段（本文件追加一条即可），
  后端按最小字段集补；在补齐前，审批对照请以申报单自身的数据为准。
- 契约 §6.1 与 §6.5 对同一字段的命名自相矛盾（`lifecycleStatus` vs `status`）：**以 `status` 为准**（后端实际返回 `status`），
  契约已按此更正。

### 3.2 ⚠️ §1.2「预警设置页的下限拦截」**当前算不出来**（后端不拦，也不会自动拦）

- **事实**：`cert.alert.thresholds`（设置页编辑、扫描真正读取的档位）是**一个全局数组** `[90,60,30,7]`；
  而 `cert.alert.legal.floor.days`（法定下限）是**按证照类别**的。**全局档位 vs 按类别下限，无法比较**。
- **后果**：① 设置页把档位调到低于法定下限，**后端不会拒绝**（契约 §1.2 写的"后端才是最终裁判"目前不成立）；
  ② `GET /bidding/personnel-alert-run/legal-floor-days` 返回的下限**只能当提示**，且其 key 与 §8.4 Mock 不一致（见本文件 §5）。
- **可以确定的**：`cert.alert.thresholds` 的修改**确实会改变预警结果**（扫描按它判档位与候选窗口）——所以"改了不生效"的担心不成立，
  但"改到低于法定窗口"也**不会被拦**。
- **后端后续**：这一处要不要做成"按类别档位 + 按类别下限拦截"，是**产品口径决定**（涉及数据迁移与扫描改造）；
  在决定之前，**后端行为保持不变**，本文件会在决定后追加一条。
- **给前端的确定性结论（不用等）**：请把页面上"不得低于法定下限"当作**提示**而非**保证**；不要依赖"提交一定被拒"。

### 3.1 ⚠️⚠️ §0.2 / §0.4 承诺的「表单字段级报错」与「traceId」**目前后端没有实现**（影响所有页面）

核对结果（在后端框架与 server 模块里全文检索）：

| 契约承诺 | 后端实际情况 |
| --- | --- |
| 校验失败时返回 `data.fieldErrors[]`（含 `field` / `message` / `rejectedValue`，供前端**高亮表单项**） | **未实现**：`fieldErrors` / `rejectedValue` 在后端代码中 **0 命中** ⇒ 只会有一个整串 `msg` |
| 响应头 `X-Trace-Id` + `data.traceId`（用户报障时必须带上） | **未实现**：`X-Trace-Id` 在后端代码中 **0 命中** ⇒ 拿不到 traceId |

**这直接影响两件事**：① "哪个表单项错了"的表单高亮/逐项提示；② 报障时贴 traceId。
**建议的临时口径（在前端不改逻辑的前提下）**：把 `msg` 整串展示在表单顶部/字段就近位置；报障时带上**接口路径 + 时间 + 请求体**代替 traceId。
若确实需要逐字段错误与 traceId，这是**平台/框架层**的改造（全局异常处理器 + 链路追踪），需要单独立项，不在本模块范围内。

### 4.1 ⚠️ §3.2「证照文件版本列表」的指纹字段实际叫 `fileHash`（契约写的是 `sha256`）

- **接口**：`GET /bidding/certificate/file/list?certId=…`（权限 `bidding:certificate:query`）。
- **实际返回**：`fileHash`（内容是 SHA-256 十六进制串）；契约 §3.2 写的 `sha256` **不存在** ⇒ 取 `sha256` 得到 `undefined`，
  §4.2「文件验真（指纹核验）」会对不上。
- **口径（后端已定）**：**以实际返回的 `fileHash` 为准**，后端**不会**把它改名成 `sha256`——已发布字段改名只会让前端返工、没有收益；
  契约 §3.2 那处按"实现为准"更正。
- **另**：该接口当前**直接返回数据对象**，除契约 13 个字段外还带 `tenantId`/`deleted`/`creator`/`updater` 等**未文档化字段**。
  后端已补响应对象收敛字段集（`CertFileVersionRespVO`）；请**只使用契约 §3.2 列出的字段**，不要依赖 `deleted`/`tenantId` 这类内部列。

#### 4.2 ⚠️《企业资质页-页面级契约》§3.5 资质标准登记：**Mock 的字段名与真实请求体不一致**

- **接口**：`POST /bidding/qualification/standard/create`。
- **契约 §3.5 写的**：入参见 `QualificationStandardSaveReqVO`（**这个类名在后端不存在**）；Mock 用的是
  `{ "serial": …, "category": …, "grade": …, "versionNo": …, "requirement": … }`。
- **真实请求体**（`StandardCreateReqVO`，以代码为准）：

| 契约 Mock 的 key | 真实 key | 说明 |
| --- | --- | --- |
| `serial` | `qualSerial` | 资质序列 |
| `category` | `qualCategory` | 资质类别 |
| `grade` | `qualGrade` | 资质等级 |
| `versionNo` | `stdVersion` | 标准版本号（必填） |
| `requirement`（单个） | `reqStaff` / `reqAssets` / `reqPerformance` / `reqEquipment` | **拆成 4 个 JSON 字符串字段**（人员/资产/业绩/设备），其中 `reqStaff` 必填 |

- **影响**：照 Mock 拼请求体会 400（`stdVersion` 等必填缺失），或字段被静默忽略。**请按上表右侧的 key 发送**。
- 其余 21 个小节（§3.1–§3.22 含 §3.10）已与实现逐项对齐，未发现第二个不一致。

### 5. ⚠️ §8.4「法定预警下限查询」返回的 key 与契约 Mock **不一致**（前端即时对比会静默失效）

- **接口**：`GET /bidding/personnel-alert-run/legal-floor-days`（权限 `bidding:personnel:cert:query`）。
- **实际返回的 key**（以运行期口径为准）：`REG_PRACTICE_CERT`、`SAFETY_ASSESS_CERT`、`SPECIAL_EQUIPMENT`、`SKILL_CERT`、`POLLUTION_PERMIT`、`ID_CARD`。
- **契约 §8.4 的 Mock 写的是另一套名**：`SAFETY_PERMIT`、`SEWAGE_PERMIT`、`SPECIAL_EQUIPMENT`、`REG_PRACTICE_CERT`、`ID_CARD`。
  两者有三处对不上：`SAFETY_PERMIT↔SAFETY_ASSESS_CERT`、`SEWAGE_PERMIT↔POLLUTION_PERMIT`、`BOILER_REVIEW↔SKILL_CERT`。
- **影响**：按契约 Mock 的 key 去取值时，**这三类会拿到 undefined → 输入框不标红、不提示**，等于法定下限提示对安许/排污/司炉**静默失效**（保存接口那边也未必拦得住，见下）。
- **临时口径（在词表统一之前）**：**以本接口实际返回的 key 为准**做对比；对返回里没有的类别，按"无下限"处理但**保留提示位**。
- **后端后续**（不需要前端做任何事）：法定下限的"权威词表"正在定（决策 ①）；统一后本文件会追加一条，届时 key 集合才可能变化。
- **另**：契约 §1.2 的 `legalFloor` 用的是配置侧词表（与 §8.4 Mock 同源）。**保存校验当前并不能保证拦住低于下限的值**，所以页面上"低于下限标红"这条提示请按"辅助提示"对待，不要作为唯一防线。

### 7. 🟢 营业执照改为「纳入证照台账」（新增契约文件，后端**零代码改动**）

- **背景**：一租户一家公司的口径已确认；营业执照此前只以主体档案的 `license_file_id`（单个字段）存在，
  **没有版本历史、指纹、到期日、验真**，并且——
- **⚠️ 现在就在发生的后果**：材料完备性自查里"营业执照"**必然报缺失**。
  依据：`EnterpriseMaterialTypeEnum.BUSINESS_LICENSE` 是 `mandatory=true`（必备）、来源 `MaterialSource.CERT`、
  `certType=ADMIN_LICENSE`；完备性检查遍历全部枚举项，`fillByCertificate` **只查证照台账**
  ⇒ 前端只填主体档案时，台账里没有这条记录，用户明明上传过却显示"缺失"。
- **怎么改**：**不需要新接口、后端也不需要改代码**——`cert_type` 字典里本来就有 `ADMIN_LICENSE = 营业执照`。
  前端把营业执照作为一条证照登记进台账即可（字段映射、影像版本、展示、验收清单见新契约）。
- **📄 新契约**：`电子证照前前端契约/营业执照纳入证照台账-前端接入契约.md`（含 7 条验收清单，其中第 5 条就是"完备性不再报缺失"）。
- **主体档案不动**：那张影像继续承担实名核验职责；两边可用 `certNo = 统一社会信用代码` 对账。
- **可选增强**（需要就说）：后端提供"从主体档案一键生成营业执照证照"的接口，免去前端双写。
