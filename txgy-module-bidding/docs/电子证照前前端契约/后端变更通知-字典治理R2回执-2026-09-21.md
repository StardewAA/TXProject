### 1.2 实现方式（方案 a）

```
GET /bidding/certificate/page?certCategory=IDENTITY
  → 后端按字典 cert_type_category 展开为大类下的类型集合
  → certType in ('ADMIN_LICENSE','LEGAL_PERSON_ID','AUTH_LETTER')
```

- **新增入参**：`certCategory`（page 与 stats **都支持**，保持"同过滤口径"的既有约定）
- **与 `certType` 同传**：形成交集（= 该大类下的指定类型）
- **查字典而非硬编码映射**：类型归属由运营在 `cert_type_category` 维护，调整归属**不用改代码发版**
- **大类下无类型时**：返回空集（而非忽略条件全量返回——否则用户会以为"筛选没生效"，正是你担心的现象）

**前端接线只差一行**：把 `query.certCategory` 一并提交即可（你说已预留该字段）。

**所以 §五「废弃：不要再依赖枚举」的表述请按下面理解（结论不变，理由变了）**：

> **枚举不是"废弃"，而是"不对外"**——它是**后端代码内部的事实来源**（状态机校验、分支判断）；
> **字典是对外的取值来源**（前端读它做下拉，运营可配）。
> **对前端的结论完全不变：仍然只读字典、用出参中文名，不要自己映射枚举。**

**保留（这才是"让前端不依赖枚举"的正解）**：
- 出参中文名：`certTypeName`/`certCategory`/`certCategoryName`/`certStatusName`/`verificationStatusName`/`fileCategoryName`
- 四类归口字典：`cert_category`（大类）+ `cert_type_category`（归属映射）

## 四、⚠️ 追加发现：另一个"筛选静默失效"的坑（已修复）

首次自测 R2 时我发现：`certCategory=IDENTITY` **恒返回 0 条**，且传不存在的大类结果完全一样——
**看起来就像"筛选没生效"**（正是 §1.2 里我担心、并专门规避的那种体感）。追下去是一个更底层的租户问题：

| 项 | 说明 |
| --- | --- |
| 现象 | 大类筛选无效果；统计接口 `active/expiring/abnormal/cancelled` **恒为 0**（但 `byStatus` 有数，两者自相矛盾） |
| 根因 | 证照域字典（`cert_type`/`cert_status`/`cert_category`/`cert_type_category`）**统一注册在平台租户 0**；而代码按**当前租户 1** 查字典 → 查不到 → 大类展开为空 |
| 修复 | 改为**平台租户 0 打底 + 当前租户覆盖**（与既有 `MetaDictServiceImpl` 的合并口径对齐） |
| 影响面 | 大类筛选 **+ 统计分桶**（后者是**此前就存在的隐藏 bug**，不是 R2 引入的） |

**已实测验证**（真实请求、租户 1，播种其他大类数据后）：

| 请求 | 结果 | 符合预期 |
| --- | --- | --- |
| 不传 `certCategory` | 18 | ✅ 基线 |
| `certCategory=IDENTITY` | 16 | ✅ |
| `certCategory=QUALIFICATION` | 1 | ✅ |
| `certCategory=CREDIT` | 1 | ✅ |
| `certCategory=PERFORMANCE` | 0 | ✅ 无数据 |
| `certCategory=NOPE_XXX` | 0 | ✅ 非法值 |
| `QUALIFICATION` + `certType=SYSTEM_CERT` | 1 | ✅ 交集 |
| `CREDIT` + `certType=SYSTEM_CERT` | 0 | ✅ 交集为空 |

统计分桶也已恢复：`active=16`（取 `cert_status` 字典的 `color_type=success`），修复前恒为 0。

> **对前端的意义**：如果你之前看到"大类筛选点了没反应"或"看板四个桶全是 0"，
> 那**不是你的接线问题**，是后端字典租户口径的 bug，现在已修。
> 建议你重连后再复核一遍这两个点。
