## 三、根因：两层拦截叠加（应用日志原文）

`C:/Users/离不开牛奶/logs/bidding-server.log`（采样窗口 2026-09-23 10:53:47 ~ 11:11:38，`[pdfContent]` 46 行）：

```text
      https://gx.e-bidding.org/bidprocurement/datacenter-cebpubserver/cebpubserver/dataCeboubServerCommonController/openFileById?fileType=2&id=…
```

| 日志信号 | 次数 |
| --- | --- |
| `[平台归档] 获取失败: SSRF 拦截：目标解析到受限地址` | 22（目标地址分布 `{"127.0.0.1":22}`） |
| `未到合规下载间隔，本次不访问外站` | 25 |
| `已回退外站直链预览`（兜底成功） | **0** |
| `[平台归档]` 其它失败 / 空体 | 0 / 0 |

代码位置（三层，链路完整）：

1. `NoticeExternalServiceImpl#fetchPdfBytes`（行 839）—— 平台归档分支统一走 `httpFetchClient.getBytes(url)`；
2. `HttpFetchClient#fetchBytes`（行 197-200）—— 所有 GET 都汇到这里做 `SsrfGuard.checkOutbound(url, cfg().getSsrfAllowHosts())`；
3. `SsrfGuard` —— 环回/私有网段/链路本地一律拒；`bidding.crawl.http.ssrf-allow-hosts` 未配置时"默认空=全拦"。

而 **infra 存储配置的 domain 就是宿主回环**（`http://127.0.0.1:48080/admin-api/infra/file/4/get/…`，GX 全部 344 条 `pdf_download_url` 都是这个形状），于是归档分支必然被拒。

链路后果：① 归档读不出 → ② 兜底外站直链 → ③ 外站下载受**全局单闸**（`CrawlDownloadGate`：`SCOPE_GLOBAL`，间隔 = `max(consumer-delay-ms, 120s)`，默认 300s）限制，`tryAcquire` 非阻塞 → 几乎恒 false → `return null` → 404。这正好解释用户看到的两种表现：「没定位到」= 404 空体；「定位到了但 PDF.js 里没有」= iframe 拿到空体/JSON，白屏无提示。

**同一类缺陷已在采集侧修过一次**：`CrawlNoticeProcessor` 行 124-131（2026-09-22）因"112 条采集任务在 ARCHIVE_HTML 回读环节全部失败进死信（704 次审计）"，改为 `UrlHostGuard.isInternalFileUrl(rawFileUrl) ? fetchTextInternal(rawFileUrl) : fetchText(rawFileUrl)`，并在 `HttpFetchClient#fetchTextInternal` 的 javadoc 里写明「调用前应已据此分流」。**预览路径当时漏改**，本契约即补这一处。

## 四、变更请求（二选一，建议 A）

### A. 代码修（推荐；补丁已生成、`git apply --check` 已通过）

`补丁-外部公告PDF预览平台归档免检通道-2026-09-23.patch`：`NoticeExternalServiceImpl.java` 单文件 **+9 −1**，只改 `fetchPdfBytes` 的一行取值：

```java
byte[] bytes = UrlHostGuard.isInternalFileUrl(url)
        ? httpFetchClient.fetchTextInternal(url).getBytes()   // 系统自产文件端点：免检（同采集侧 2026-09-22 修法）
        : httpFetchClient.getBytes(url);                      // 外站 URL：保留 SSRF 校验，防护面不扩大
```

- 复用现成能力：`UrlHostGuard.isInternalFileUrl` 与 `HttpFetchClient#fetchTextInternal` 均已存在（后者返回的 `FetchOutcome#getBytes()` 就是字节）；
- 行为契约不变：失败/空体仍返回 null → 404；接口签名、错误码、前端均无需适配；
- 单测建议：给 `fetchPdfBytes` 的平台 URL 分支打桩，断言走免检通道（可参考现有 `NoticeExternalDetailSecurityTest` 风格）。

### B. 只改配置（零代码，但削弱防护面）

`bidding.crawl.http.ssrf-allow-hosts` 加入平台文件主机（如 `127.0.0.1`）。**不推荐**：该白名单是采集链路共用的，放行后所有走 `getBytes/fetchText` 的出站都能打回环，等于把 B1 的防护拆开一个口子（`SsrfGuard` javadoc 明确反对）。若必须临时止血，建议限定为"平台文件主机 + 端口"并在代码修好后立刻撤回。

## 五、连带发现（需后端/运维决策，本契约不含补丁）

1. **`pdf_file_id` 从未回填（双登记不一致）**：345 条有归档的行里 330 条 `pdf_file_id IS NULL`（`pdf_size` 却是非 0）；而 16 条有 fileId 的行，其 fileId **都不在 `bidding_file` 登记表**（该表 164 行全是 `source=UPLOAD`）→ `/bidding/file/download?id=` 对采集归档一律不可用（与本批次《后端回执-自营公告PDF预览代理-2026-09-23》§2.1 同因）。建议：采集归档成功后同时登记 `bidding_file`（file_id/config_id/path/size/virus_status/source=CRAWL）并回填 `pdf_file_id`。
2. **预览会占用全局下载闸**：`pdfContent` 的外站兜底与采集共用 `CrawlDownloadGate` 的 5 分钟单闸 —— 用户点一次预览若命中外站兜底，就消耗一次"下载原文"额度（合规口径上"预览≠采集"但代价相同）。归档分支修好后影响大减，但建议明确该口径。
3. **审计表与现状不符，需一次对账**：`bidding_crawl_download_audit` 中 GX 侧 `PDF/FAILED` 377 行（下载 53,767,168 字节、`file_id` 全空），失败原因集中在 `归档校验异常: 请求地址不存在:rpc-api/infra/file/metadata-by-url`（335 次）与 `Connect timed out … http://infra-server/rpc-api/infra/file/create`（41 次）—— 但同批文件在 infra 里**是存在的**（345/347 URL 可取到字节）。即"审计判失败、文件其实在、登记没回填"，三者不一致，建议后端核一次归档成功判定口径。
4. **归档地址写死回环**：`pdf_download_url` 全量存的是 `http://127.0.0.1:48080/…`，远端浏览器根本不可达；且 `/admin-api/infra/file/4/get/**` 实测**无鉴权可读**并带 `Access-Control-Allow-Origin: *`（我用裸 curl 取到了 6MB 的 PDF）。外部公告是公开数据，风险有限，但"存储坐标泄漏 + 世界可读"应单独评估。
5. **2 条真缺归档**（`pdf_download_url` 为空）：`pdf_file_id` 也为空，但 `meta_json.pdfDownloadUrl` 有外站直链 —— 现有 `POST /bidding/notice-external/backfill-pdf-urls` 正好覆盖这 2 条（它的 WHERE 只选 url 为空的行，因此**不需要**用它去补那 328 条"URL 非空"的行；那些行的字节本来就是好的）。注意该接口逐条受全局闸限制（约 5 分钟/条）。
