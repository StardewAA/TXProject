# 后端变更请求 · 门户公告「关键词检索」质量与截断

- 日期：2026-09-22
- 提出方：前端/门户侧（本组）
- 影响接口：`GET /admin-api/bidding/notice-external/page`（`keyword` 参数）
- 影响页面：门户「公告大厅」`/portal/bidding`（搜索框）
- 涉及后端类：`txgy-module-bidding-server/.../service/noticeexternal/search/EsExternalNoticeSearchEngine#matchNoticeIds`
  （同源常量：`NoticeExternalServiceImpl.KEYWORD_MATCH_LIMIT = 200`；索引 `bidding-notice-external`）

---

## 0. 一句话结论

门户关键词检索目前 **「能返回、但返回的不对」**：命中判定是**单字 OR**（宽泛），结果集是**按发布时间取最新 200 条**（把最相关的旧公告挤出去），且 `total` 恒等于 200（截断值）。
用户反馈原文：**「ES 返回的那个东西好像有点宽泛，很多时候搜不到我想要的。」** —— 实测证实，非主观感受。

---

## 1. 现状（当前实现）

`EsExternalNoticeSearchEngine#matchNoticeIds` 实际发出的 DSL：

```json
{
  "size": 200,
  "query": { "bool": { "must": [ { "multi_match": {
      "query": "<keyword>",
      "fields": ["title^3","projectName^2","projectCode","tenderProjectCode","issuerName","contentText"]
  } } ] } },
  "sort": [ { "publishTime": { "order": "desc" } } ]
}
```

命中后回主表 `id IN (...)` 过滤 ACTIVE/SOCIAL 并分页（该设计本身没问题）。

问题集中在 DSL 的三处：**没写 `operator`**、**排序用时间而非相关性**、**`size` 上限直接当 `total` 用**。

---

## 2. 实测证据（可复现）

### 2.1 精确率：搜「炼化」→ 100 条里 0 条真的含「炼化」

方法：调接口取 pageSize=100 的结果 id，再回库用 `HEX(title)` / `HEX(content_html)` 精确比对（规避中文编码问题）。

| 关键词 | 返回 | 标题含**完整词** | 正文含完整词 | 标题**只含其中一个字** |
| --- | --- | --- | --- | --- |
| **炼化** | 100 | **0** | **0** | **80** |
| 采购 | 100 | 79 | 98 | 8 |

搜「炼化」时返回的前 5 条标题：

```
陕西煤业化工集团有限责任公司2027年度集中采购项目（矿用液压移动列车组）准入公告
陕西煤业化工集团有限责任公司2027年度集中采购项目（矿用气动注浆泵）准入公告
陕西煤业化工集团有限责任公司2027年度集中采购项目（煤矿用耐磨多级离心泵）准入公告
陕西煤业化工集团有限责任公司2027年度集中采购项目（往复泥浆泵）准入公告
陕西煤业化工集团有限责任公司2027年度集中采购项目（潜水泵）准入公告
```

→ 命中的是「**化**」这一个字。**根因：`multi_match` 未指定 `operator`，默认 OR；中文被按单字切分，于是"任意一个字命中"即算命中。**

### 2.2 截断 + 时间排序：最相关（且较早）的公告永远进不来

| 项 | 实测值 |
| --- | --- |
| 库里标题含「公告」的 ACTIVE 公告 | **1114 条** |
| ES 命中后实际取用 | **前 200 条**，且 `publishTime desc` |
| 最早那条（2026-05-17）是否出现在结果中 | **否**（翻两页共 200 条都没有） |
| 接口返回的 `total` | **恒为 200**（截断值，不是真实命中数） |

→ 用户看到的现象：**永远是 200 条、翻页翻不出新东西、真正想要的那条（往往不是最新的）根本进不来。**

## 3. 变更请求（逐项，按优先级）

### B1（最关键，1 行）`multi_match` 增加 `"operator":"and"`

- **现状**：默认 OR，单字命中即算命中。
- **建议**：
  ```json
  { "multi_match": { "query": "<keyword>",
      "fields": ["title^3","projectName^2","projectCode","tenderProjectCode","issuerName","contentText"],
      "operator": "and" } }
  ```
- **预期**：搜「炼化」不再返回只含「化」的公告；宽泛查询的结果数会显著下降（这是**预期行为**，不是回归）。
- **验收**：搜「炼化」，返回集合中「标题或正文含完整词『炼化』」的比例应显著 > 0（现状 0/100）。

### B2（1 行）排序改为「相关性优先，时间兜底」

- **现状**：`"sort":[{"publishTime":{"order":"desc"}}]` —— 200 条上限里留下的是**最新**的，不是**最相关**的。
- **建议**：
  ```json
  "sort": [ { "_score": { "order": "desc" } }, { "publishTime": { "order": "desc" } } ]
  ```
- **预期**：上限截断时保留最相关命中，相关但较早的公告不再被挤掉。

### B3 编号字段改用精确匹配（不要走分词全文）

- **现状**：`projectCode` / `tenderProjectCode` 参与 `multi_match` 分词匹配，编号会被切碎。
- **建议**：编号类字段单独走 `term`（或 `match_phrase`）子查询；标题/正文才走全文。
- **理由**：编号是**标识**不是**文本**；用户按编号检索时期望精确命中。
- **备注**：前端已新增「编号精确搜索」走结构化参数（`projectCode`/`tenderProjectCode`/`bidSectionCode`，**不经 ES**），可作为该问题的旁路；但 ES 侧仍应按标识语义处理。

### B4 `contentText` 降权 / 提高命中门槛

- **现状**：正文与标题同权重（标题 3×），正文里偶然出现的字也会命中。
- **建议**：降低 `contentText` 权重（如 `contentText^0.5`），或对正文单独要求 `minimum_should_match`。

### B5 `total` 口径：返回真实命中数，或明示截断

- **现状**：`KEYWORD_MATCH_LIMIT = 200` 被当作 `total` 下发 → 前端永远显示「共 200 条」，分页器也按 200 算。
- **建议（二选一）**：
  1. 返回 ES 的 `hits.total.value`（真实命中数），并在超过 200 时把截断事实单独下发（如 `truncated=true`）；
  2. 若不便改响应结构，至少在契约里写明「关键词检索 total 上限 200」，由前端在 UI 上标注「仅显示前 200 条」。
- **前端现状**：已在合并视图路径支持 `truncated` 字段（可选），普通关键词路径目前拿不到该信息。

### B6（治本，可选排期）中文分词器

- 现状按单字切分是"宽泛"的根源；引入中文分词（IK 等）或对短词改用 `match_phrase`，可从根上提升精确率。
- 若引入新分词器，注意**索引需重建**（`bidding-notice-external`），且索引写入方 `EsExternalNoticeIndexNotifier` 的 mapping 需同步。

---

## 4. 最小止血（若 B1/B2 暂不能排期）

只做 **B2 + B5** 两处即可显著改善"想找的搜不到 / 永远 200 条"的体验；**B1 是精确率的关键**，建议优先。

---

## 5. 对前端的影响

**无破坏性变更**：接口签名、参数、分页结构均不变，前端无需改动即可受益。
唯一可选的配合项：若后端下发 `truncated`（B5-1），前端可在列表页脚提示「仅显示前 N 条」。
