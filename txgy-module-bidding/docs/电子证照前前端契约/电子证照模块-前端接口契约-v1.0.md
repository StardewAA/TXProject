# 电子证照模块 · 前端接口契约

> **契约版本**：v1.0　**生效日期**：2026-09-13　**后端模块**：txgy-module-bidding（电子资质子模块）
> **契约地位**：本文件是电子证照模块前后端交互的**唯一事实来源（Single Source of Truth）**。
> 前端（含 AI 生成的前端代码）必须按本契约开发；后端实现任何影响报文的变更，必须先改本文件再改代码。
> **本文件不含任何前端视图/逻辑代码**：所有交互、状态、数据流转均以"业务目标 + 交互约束"的方式界定。

## 0. 契约总则

### 0.1 如何用这份契约

| 你是 | 请这样用 |
| --- | --- |
| 前端开发者 / AI | §1 先拉字典与配置（**枚举和阈值都不要写死**）→ 再按 §2~§8 实现页面 → 报错文案与状态处理见每节「前端交互与状态约束」 |
| 后端开发者 | 每个接口的字段/错误码/幂等语义以本文件为准；改字段必须同步升版本并在 §11 记录 |
| 测试 | 用每节 Mock 示例直接造用例；异常契约给出可断言 code |

### 0.2 统一响应信封（所有接口一致）

```json
{ "code": 0, "msg": "", "data": { } }
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | number | **0 = 成功**；非 0 = 业务错误码（见 §9）。前端判成功**只认 code===0**，不要用 HTTP 状态码判断 |
| `msg` | string | 用户可读提示（后端已本地化，可直接 toast） |
| `data` | object \| array \| null | 业务数据；失败时为 `null`（参数校验失败时见 §0.4） |

**HTTP 状态约定**：业务错误仍返回 **HTTP 200**（信封内 `code` 表意）；仅鉴权/网关层失败返回 401/403/404/500。

**分页信封**（`/page` 类接口的 `data`）：

```json
{ "list": [], "total": 0 }
```

### 0.3 统一请求头

| Header | 必填 | 说明 |
| --- | --- | --- |
| `Authorization` | 是 | `Bearer {accessToken}` |
| `tenant-id` | 是 | 当前企业租户编号；**决定数据可见范围**（多租户隔离由后端拦截器自动加条件，前端只管传对） |
| `Content-Type` | POST/PUT 必填 | `application/json;charset=UTF-8` |
| `Accept-Language` | 否 | 如 `zh-CN`，影响 `msg` 语言 |
| `X-Trace-Id`（**响应头**） | — | 后端返回的链路追踪 ID；报错时请一并展示/上报 §0.4 |

**Base URL**：经网关 `/admin-api`（本地 `http://127.0.0.1:48080/admin-api`）。下文路径均**不含** `/admin-api` 前缀。

### 0.4 异常契约

```json
// A. 业务异常（HTTP 200）
{ "code": 1090109001, "msg": "证照编号已存在", "data": null }

// B. 参数校验失败（HTTP 200，data 内带字段级错误 —— 本模块增强契约）
{
  "code": 400,
  "msg": "请求参数不正确:证照名称不能为空",
  "data": {
    "traceId": "8f1c2d3e4a5b6c7d",
    "fieldErrors": [
      { "field": "certName", "message": "证照名称不能为空", "rejectedValue": null }
    ]
  }
}

// C. 鉴权失败（HTTP 401/403，由框架返回）
{ "code": 401, "msg": "账号未登录", "data": null }
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.traceId` | string | 链路追踪 ID（同响应头 `X-Trace-Id`）；**用户报障时必须带上** |
| `data.fieldErrors[].field` | string | 出错的**表单字段名**（与请求体字段名一致，前端据此高亮表单项） |
| `data.fieldErrors[].message` | string | 该字段的用户可读提示（直接显示在表单项下方） |
| `data.fieldErrors[].rejectedValue` | any | 被拒绝的原值（可能为 null，仅用于调试，勿直接回显） |

**前端处理规范（强制）**：
1. 有 `fieldErrors` → **逐项定位到表单字段**显示，不要只弹全局 toast；
2. 无 `fieldErrors` 但有 `code !== 0` → 全局 toast `msg`；
3. `code === 401` → 走统一登录跳转，**不弹业务提示**；
4. 任何异常都建议在控制台/埋点记录 `traceId`。

### 0.5 动态配置与字典（**严禁前端硬编码枚举与阈值**）

本模块所有状态码、类型码、阈值、天数、比例都可由后台动态调整。前端**必须**：

1. 应用启动 / 进入电子证照模块时调用 **§1.1 字典接口**与 **§1.2 配置接口**，把结果放入全局 store；
2. 所有下拉框、状态标签、角标颜色按字典的 `label` / `tagType` 渲染，**不要把 code→中文的映射写死在组件里**；
3. 阈值（如"即将到期 ≤ N 天"）取自 §1.2；后台把 90 天改成 120 天后，**前端不重新发版也应生效**；
4. 字典缺失时降级为展示原始 code，**不得报错、不得隐藏该条数据**。

### 0.6 通用分页与排序

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `pageNo` | number | 否 | `1` | 页码，从 1 开始 |
| `pageSize` | number | 否 | `10` | 每页条数，建议 ≤ 100 |

- 排序由后端按业务固定（如到期日升序），**契约不暴露排序字段**，避免前端与服务端口径分叉；
- 翻页越界返回空 `list` + 真实 `total`（前端据此回退到最后一页）。

### 0.7 幂等与乐观锁（写接口必读）

| 机制 | 何时用 | 前端义务 |
| --- | --- | --- |
| **幂等保护**（`@Idempotent`） | 所有 POST 写接口 | **提交按钮必须置 loading 并禁用**；后端对 1 秒内同参重复请求直接返回 `重复请求，请稍后重试`（code 见 §9），前端不得自动重试写接口 |
| **乐观锁**（`version`） | 所有 update / change-status / 审核 / 生效 | 详情接口返回的 `version` 必须**原样回传**；收到 `数据已被他人修改`（code 见 §9）时提示"数据已被他人修改，请刷新后重试"并**自动重新拉取详情** |

### 0.8 通用交互与状态约束（适用于全部接口）

| 状态 | 规范 |
| --- | --- |
| Loading | 首屏用骨架屏/表格 loading；写操作用按钮 loading（**不要全屏遮罩**，避免用户以为卡死） |
| 防重复提交 | 写接口：请求期间禁用按钮；成功后关闭弹窗并刷新列表 |
| 空状态 | 列表 `total=0` 显示业务化空态（如"暂无证照，去登记第一张证照"），不要显示裸表格 |
| 错误提示 | 见 §0.4；**同一错误不要 toast + 弹窗重复提示** |
| 缓存 | 字典/配置：本地缓存（建议 TTL 10 分钟）或每次进入模块刷新一次；业务列表：**不缓存**（证照状态会因定时任务变化） |
| 轮询 | 仅**扫描类/派发类**接口（§5）在触发后需要短轮询或延时刷新；其余接口**禁止轮询** |
| 时间格式 | 日期 `yyyy-MM-dd`；时间 `yyyy-MM-dd HH:mm:ss`；后端统一按平台序列化返回，前端按此格式化即可 |
| 长文本 | `certScope`（许可范围）等长文本列表内截断 + 悬浮完整展示 |

## 1. 元数据与动态配置（契约基石，**必须先接**）

### 1.1 获取字典（枚举值对照表）

**① 接口业务目标**
前端**不要**把"证照状态有哪些、文件类别有哪些"写死在代码里。本接口一次性返回电子证照模块用到的全部枚举（含中文名、标签色、是否终态），
使运营在后台调整字典后**前端无需发版**即可生效；同时解决"下拉框与后端 code 不一致导致筛选查不到数据"的高频问题，形成"配置—展示—筛选"闭环。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `GET /bidding/meta/dicts` |
| 权限 | 登录即可（不额外校验业务权限） |

请求参数：

| 字段 | 类型 | 必填 | 默认 | 业务含义 |
| --- | --- | --- | --- | --- |
| `types` | string | 否 | 空=全部 | 需要的字典类型，逗号分隔，如 `cert_status,file_category`；**建议按页面按需拉取**以减小报文 |

响应 `data`（`Record<string, DictItem[]>`，key = 字典类型）：

| 字段 | 类型 | 业务含义 |
| --- | --- | --- |
| `value` | string | 枚举 code（提交给后端的值） |
| `label` | string | 中文名（直接展示） |
| `tagType` | string | 标签色：`success`/`warning`/`error`/`info`/`default`（状态标签直接用它） |
| `terminal` | boolean | 是否终态（终态禁止再做状态流转按钮，前端据此禁用按钮） |
| `sort` | number | 展示顺序 |

**字典类型清单（类型名固定，取值以接口返回为准）**

| 字典类型 | 用于 | 默认取值（**参考值，运行时以接口为准**） |
| --- | --- | --- |
| `cert_status` | 证照台账状态、列表筛选、状态标签 | ACTIVE 正常 / EXPIRING_SOON 即将到期 / EXPIRED 已过期 / SUSPENDED 暂扣 / REVOKED 吊销 / CANCELLED 注销 |
| `verification_status` | 验真状态角标 | UNVERIFIED 未验真 / VERIFYING 验真中 / VERIFIED 已验真 / INVALID 验真不通过 |
| `file_category` | 文件版本类别 | ORIGINAL 原件 / COPY 加注件 / CHANGE_PAGE 变更页 / RENEWAL_PAGE 延续页 / E_CERT 电子证照 |
| `verify_channel` | 验真渠道选择 | FOUR_PLATFORM 四库一平台 / MINISTRY 部级平台 / PROVINCE 省级平台 |
| `source_channel` | 数据来源标签 | MANUAL 手工录入 / IMPORT 批量导入 / OCR 识别录入 |
| `notify_channel` | 预警通知渠道（配置用） | EMAIL / SMS / IN_APP / DINGTALK / WEBHOOK |
| `lifecycle_type` | 生命周期流程类型 | CHANGE 变更 / RENEW 续期 / REVOKE 注销吊销 / ANNUAL 年检 |
| `lifecycle_status` | 流程状态（含审批流） | PENDING 待办 / REVIEWING 审核中 / APPROVED 已通过 / REJECTED 已驳回 / EFFECTIVE 已生效 |
| `biz_domain` | 流程作用对象 | CERT 证照台账 / PERSON_CERT 员工证书 / ENTERPRISE_QUAL 企业资质 / SAFETY_PERMIT 安许证 |
| `person_cert_status` | 员工证书状态 | VALID / EXPIRING_SOON / EXPIRED / SUSPENDED / REVOKED / CANCELLED |
| `person_cert_type` | 员工证书类型 | ID_CARD / EDUCATION_CERT / DEGREE_CERT / TITLE_CERT / REG_PRACTICE_CERT / SAFETY_ASSESS_CERT / SKILL_CERT / TRAINING_CERT / OTHER |
| `revoke_type` | 注销吊销方式（决定目标状态） | REVOKE 吊销→REVOKED / CANCEL 注销→CANCELLED / SUSPEND 暂扣→SUSPENDED / RESTORE 恢复→VALID |
| `renewal_type` | 续期方式 | RENEW 延续 / REISSUE 补换证 |
| `material_category` | 材料大类（完备性自查） | IDENTITY 身份类 / QUALIFICATION 资质类 / STRENGTH 实力类 / OTHER 其他 |
| `material_result` | 材料完备性**总体结论** | PASS 齐备 / RISK 部分缺失或临近到期 / FAIL 必备材料缺失 |
| `material_status` | 材料完备性**逐项状态** | READY 齐备 / EXPIRING 临近到期 / MISSING 缺失 / EXPIRED 已过期 |

**③ 异常契约**

| code | msg | 触发场景 | 前端处理 |
| --- | --- | --- | --- |
| 401 | 账号未登录 | token 失效 | 跳登录 |
| 500 | 系统异常 | 字典查询内部错误 | toast + 记录 traceId；**枚举降级为展示原始 code，页面不可白屏** |

**④ 前端交互与状态约束**
- 时机：**进入电子证照任意页面时**调用（或应用启动预热），结果放全局 store；
- 缓存：建议缓存 10 分钟；写操作成功后**不需要**刷新字典（字典变更低频）；
- 空/异常：接口失败时用"仅显示 code"的兜底渲染，**禁止**因为字典失败而阻塞页面。

### 1.2 获取业务阈值与规则配置

**① 接口业务目标**
把"多久算即将到期""验真幂等窗口多长""预警提前多少天"这类**会变动的数值**交给后台。
页面上的红黄角标、到期倒计时、预警说明文案都由本接口驱动，业务调整阈值后前端**不重新发版即生效**；
同时让前端能在保存预警设置前**先做预校验**（§1.2 的 `legalFloorDays`），避免"填完才报错"。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `GET /bidding/meta/configs` |
| 权限 | 登录即可 |

请求参数：

| 字段 | 类型 | 必填 | 默认 | 业务含义 |
| --- | --- | --- | --- | --- |
| `group` | string | 否 | 空=全部 | 配置分组：`CERT`（证照）/`ALERT`（预警）/`PERSONNEL`（员工） |
| `keys` | string | 否 | 空=分组全部 | 精确取某些键，逗号分隔 |

响应 `data`：

| 字段 | 类型 | 业务含义 |
| --- | --- | --- |
| `items[].ruleKey` | string | 配置键（稳定标识） |
| `items[].value` | any | 配置值（number/string/boolean/object，按 `valueType` 解释） |
| `items[].valueType` | string | `INT`/`DECIMAL`/`BOOL`/`STRING`/`JSON` |
| `items[].description` | string | 人话说明（**可直接作为页面提示文案**） |
| `items[].regulationRef` | string | 法规出处（如"《排污许可管理条例》第十四条"），设置页需展示 |
| `items[].legalFloor` | object | 允许边界 `{min,max}`，用于前端输入校验 |
| `items[].versionNo` | number | 配置版本号（**建议随写请求回传，便于后端识别并发改配置**） |

**本期电子证照相关关键键（默认值仅为参考，运行时以接口为准）**

| ruleKey | 默认 | 业务含义 | 前端用途 |
| --- | --- | --- | --- |
| `cert.expiring.window.days` | 60 | 距到期 ≤ N 天视为"即将到期" | 列表角标、筛选"即将到期" |
| `cert.alert.thresholds` | [90,60,30,7] | 多级预警提前天数 | 预警设置页多档输入 + 展示 |
| `cert.alert.legal.floor.days` | 见证照类别 | 法定预警下限（按类别） | 设置页**下限提示**（仅提示、不拦截，3-C 口径） |
| `cert.verify.idempotent.window.seconds` | 60 | 同证同分钟重复验真的幂等窗口 | 验真按钮防抖时长说明 |
| `cert.file.max.size.mb` | 50 | 单文件大小上限 | 上传前校验 |
| `cert.file.allow.formats` | ["PDF","JPG","PNG","OFD"] | 允许的文件格式 | 上传组件 accept |
| `cert.annotation.max.days` | 90 | 加注件最长有效期 | 加注件表单最大可选日期 |
| `cert.annotation.warn.days` | [30,7,1] | 加注件到期预警档位 | 加注件列表角标 |

**③ 异常契约**：同 §1.1。

**④ 前端交互与状态约束**
- 缓存：同 §1.1；
- **写配置前用 `legalFloor` 做前端提示**（低于下限标红并显示法规出处）；**后端不拦截**——保存不因低于下限被拒绝（3-C 口径，2026-09-21 更正：此前「后端才是最终裁判、保存会被拒绝」的表述与实现不符，该拦截路径不存在）。
- 阈值变化不需要通知用户，但页面上若已有"即将到期"角标，建议在阈值刷新后**重算一次展示**。

## 2. 证照台账（模块首页核心）

### 2.1 证照分页列表

**① 接口业务目标**
电子证照大厅首页的主数据源：让企业在一张表里看到**自己名下全部证照**及其"是否有效、是否即将到期、是否验真"，
支持按状态/类型/持证人筛选，帮助经办人**优先处理快过期的证照**（痛点：证照散落在文件夹与个人手里，过期才发现，导致投标被否决）。
业务闭环：列表 → 详情 → 续期/变更（§6）→ 状态更新回列表。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `GET /bidding/certificate/page` |
| 权限码 | `bidding:certificate:query` |
| 请求 | Query String（见下表） |

请求参数：

| 字段 | 类型 | 必填 | 默认 | 业务含义 |
| --- | --- | --- | --- | --- |
| `pageNo` / `pageSize` | number | 否 | 1 / 10 | 分页 |

## 3. 证照文件版本

### 3.1 登记证照文件版本

**① 接口业务目标**
证照的**影像/电子件**按版本管理：换发、变更、延续都会产生新版文件，但**旧版必须保留**（投标追溯、监管核查要看到历史件）。
本接口在文件经平台 FileApi 上传成功后**只登记元数据**（不重复传文件体），并以"同证同哈希"判重防止同一份文件被反复登记。
**F1（2026-09-26 已落地）**：同证同哈希命中时**幂等返回已有版本主键**，不再抛错——撤销作废后重新登记同一份原件，或网络重试重复提交，都只会拿到同一个版本，前端无需特判。
业务闭环：上传 → 登记版本 → 详情页按版本切换预览 → 生命周期流程引用指定版本。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `POST /bidding/certificate/file/register` |
| 权限码 | `bidding:certificate:file` |
| 前置 | 已通过平台文件上传接口拿到 `fileId`（见 §0.3 Base URL 的通用文件接口） |
| 幂等 | 是 |

请求体：

| 字段 | 类型 | 必填 | 业务含义 |
| --- | --- | --- | --- |
| `certId` | number | **是** | 所属证照主键 |
| `fileCategory` | string | **是** | 文件类别 code（取自 `file_category`）：ORIGINAL 原件 / COPY 加注件 / CHANGE_PAGE 变更页 / RENEWAL_PAGE 延续页 / E_CERT 电子证照 |
| `fileName` | string | **是** | 原始文件名（展示用） |
| `fileId` | number | **是** | 平台文件 ID（FileApi 返回） |
| `fileHash` | string | 否 | SHA-256；**建议传**，用于同证同哈希判重与防篡改 |
| `fileFormat`$ | string | 否 | PDF/JPG/PNG/OFD（OFD 为陕西住建电子证书格式） |
| `fileSize` | number | 否 | 字节数 |

**③ 异常契约**

| 500 | 系统异常 | toast + traceId |

**④ 前端交互与状态约束**
- 上传流程：先上传文件拿 `fileId` → 再调本接口登记；两步都要 loading 与失败重试提示；
- 文件类别选 `COPY` 时**必须展开加注件 4 字段**（制作时间/制作人/事由/失效时间），这是加注件的法定元数据；

### 3.3 作废证照文件版本（F2）

**① 接口业务目标**
版本"只追加"导致无法撤销登记错误的文件（改文件名无效——判重按内容指纹）。本接口提供**作废=软删留痕**：
行保留（监管追溯仍可见历史），但标记已作废；若作废的是**当前版本**，同时清除 `isCurrent`，该类别暂时失去当前版本，
用户重新登记新版本（F1 幂等保证同一份原件可以再次登记）。
业务闭环：登记错误 → 作废 → 重新登记 → 新版本成为当前版本。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `POST /bidding/certificate/file/void` |
| 权限码 | `bidding:certificate:file` |
| 幂等 | 是 |

请求体：

| 字段 | 类型 | 必填 | 业务含义 |
| --- | --- | --- | --- |
| `fileVersionId` | number | **是** | 待作废的文件版本主键 |
| `reason` | string | **是** | 作废原因（留痕展示给监管核查，必填） |

**③ 异常契约**

| code | msg | 前端处理 |

## 4. 验真（对接官方查验渠道）

### 4.1 发起证照验真

**① 接口业务目标**
证照"登记了"不等于"是真的"。本接口向**官方白名单查验渠道**发起核验，把结果与请求快照留档，
解决三类痛点：① 收到 PS 过的证件扫描件；② 官方已吊销但企业台账仍显示有效；③ 事后被质疑"当时怎么没核验"。
业务闭环：验真 → 更新台账 `verificationStatus` → 列表角标变化 → 不通过的证照在投标引用环节被拦截。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `POST /bidding/certificate-verify/verify` |
| 权限码 | `bidding:certificate:verify` |
| 幂等 | **是，且带时间窗**：同证同渠道在窗口期内重复请求返回同一条验真记录（窗口取自 §1.2 `cert.verify.idempotent.window.seconds`） |

请求体：

| 字段 | 类型 | 必填 | 业务含义 |
| --- | --- | --- | --- |
| `certId` | number | **是** | 待验真证照主键 |
| `verifyChannel` | string | 否 | 查验渠道 code（取自 `verify_channel`）：FOUR_PLATFORM 四库一平台 / MINISTRY 部级 / PROVINCE 省级；不传默认 FOUR_PLATFORM（当前实现未按类别区分渠道） |

响应 `data`：验真历史记录主键（number）。**注意：本接口返回的是"已受理并留档"**，
若为同步验真，结果字段见 §4.1 的补充说明；前端统一按"轮询/重新拉取详情看状态"处理。

**③ 异常契约**

| code | msg | 前端处理 |
| --- | --- | --- |
| 1090109000 | 证照不存在 | 返回列表刷新 |
| 1090109012 | 验真进行中，请稍后刷新 | 按钮 loading 中，勿重复提交（VERIFYING 状态本身有角标） |
| 1090109013 | 核验通道未就绪，请联系管理员开通 | 提示联系管理员（未对接真实网关时后端抛出） |
| 1090109014 | 验真渠道不合法 | 字段级提示（前端应只用 §1.2 字典值，正常不会走到） |
| 403 | 没有该操作权限 | 隐藏验真按钮 |
| 500 | 系统异常（渠道超时等） | toast + traceId；**允许用户稍后重试（验真是幂等窗口内安全操作）** |

**④ 前端交互与状态约束**
- 触发后按钮 loading 并禁用；建议提示"验真结果可能需要几十秒"；
- **不要在前端轮询验真接口**：应短延时（如 3~5 秒）后重新拉取 §2.2 详情，读 `verificationStatus` 与 `lastVerifiedAt`；
- 状态为 `VERIFYING` 时列表角标为"验真中"（用字典的 `tagType`），完成后变 `VERIFIED`/`INVALID`；
- `INVALID`（验真不通过）需**显著红色告警**并提示"请核对证件真伪，必要时联系发证机关"。

## 5. 预警运行（运维手动补跑）

### 5.1 手动触发到期扫描

**① 接口业务目标**
到期预警平时由定时任务执行；但存在三类需要**人工补跑**的场景：① 定时任务窗口错过；② 刚批量导入证照希望立刻看到预警；
③ 改了预警阈值后想立即重算角标。本接口即为此提供入口，**同日重跑幂等**（不会重复推送、不会消息轰炸），
业务闭环：调整配置/导入数据 → 手动扫描 → 预警列表与角标立即反映最新口径。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `POST /bidding/certificate-alert-run/scan` |
| 权限码 | `bidding:certificate:alert-run` |
| 幂等 | 是（幂等键含触发日期：同一天重复触发不会产生重复预警） |

请求体：无（以服务器当天为基准日）。

响应 `data`：本次**新生成**的预警条数（number）。返回 0 表示"今日已扫过或暂无命中"，都属正常。

**③ 异常契约**

| code | msg | 前端处理 |
| --- | --- | --- |
| 403 | 没有该操作权限 | 隐藏入口 |
| 500 | 系统异常 | toast + traceId |

> **未启用/未配置阈值不返回错误码**：扫描被关闭或阈值未配置时接口直接返回 `data = 0`
> （与"今日已扫过/暂无命中"同值），前端按 0 分支提示即可；契约旧稿的 `1090109012`（到期预警未启用）
> 属**误写**——该码真实含义为**验真进行中**（§9 总表已按真实语义收录），"未配置阈值"场景不返回任何错误码。

**④ 前端交互与状态约束**
- 做成运维按钮 + 二次确认（属于后台动作，误点影响面小但会改数据）；
- 触发后**不要轮询本接口**；可提示"已生成 N 条预警"，并让用户手动刷新预警列表；
- 若返回 0，提示"今日无新增预警（可能已扫描过）"，避免用户以为失败而反复点击。

```json
{ "code": 0, "msg": "", "data": 0 }
```

## 6. 证件全生命周期（变更 / 续期 / 注销吊销 / 年检）

> 本节四个流程共用一套"**申请 → 审核 → 生效**"状态机（`PENDING → REVIEWING → APPROVED → EFFECTIVE`，可 `REJECTED`）。
> **生效才回写台账**：审核通过 ≠ 已生效（续期要拿到新证、注销要等决定书），因此是两个时点，前端要区分展示。

### 6.1 发起生命周期流程

**① 接口业务目标**
把"改台账"变成"走流程"：企业名称变更、证书续期、被吊销注销、年检换证，都必须**先申请、后审核、再生效**，
解决"谁把有效期改了、依据是什么"无法追溯的痛点，并让台账与真实证件始终一致。
业务闭环：申请（带新旧值/新有效期）→ 审批 → 生效回写台账 → 台账驱动预警与投标资格。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `POST /bidding/cert-lifecycle/apply` |
| 权限码 | `bidding:certificate:lifecycle:apply` |
| 幂等 | **是，按业务单号**：同对象 + 同类型 + 同 `applyNo` 重复发起被拒 |

请求体：

| 字段 | 类型 | 必填 | 业务含义 |
| --- | --- | --- | --- |
| `bizDomain` | string | **是** | 作用对象域：CERT 证照 / PERSON_CERT 员工证书 / ENTERPRISE_QUAL 企业资质 / SAFETY_PERMIT 安许证 |
| `bizId` | number | **是** | 对象主键 |
| `lifecycleType` | string | **是** | 类型：CHANGE 变更 / RENEW 续期 / REVOKE 注销吊销 / ANNUAL 年检 |
| `applyNo` | string | **是** | 申请单号（业务自拟，唯一，用于幂等与对账） |
| `changes` | array | CHANGE 必填 | 变更字段清单，元素 `{fieldName, oldValue, newValue}`；**一行一字段**，后端自动归组 |
| `changeSummary` | string | 否 | 变更摘要（审批人看） |
| `renewalType` | string | RENEW 必填 | RENEW 延续 / REISSUE 补换证 |
| `newValidFrom` / `newValidTo`` | string(date) | RENEW 必填（`newValidTo`） | 续期后的新有效期（生效时回写台账，并驱动下一轮预警） |
| `newNextReviewDate` | string(date) | 否 | 新下次年检日 |

### 6.2 审核流转

**① 接口业务目标**

痛点：线下审批无记录，出事后无法界定责任；驳回意见无法沉淀。

**② 契约定义**

| 项 | 值 |

| Method / URL | `POST /bidding/cert-lifecycle/audit` |

### 6.3 流程生效（回写台账）

**① 接口业务目标**
审批通过后，在**真正拿到新证/决定书**时执行生效：把新有效期、变更字段、注销状态、下次年检日**一次性回写台账**，
使台账成为"事实"而非"申请意图"，并让下一轮预警基于新有效期重新计算。
痛点：审批通过就改台账会造出"证还没到手但系统显示有效"的假数据。

**② 契约定义**

| 项 | 值 |

请求体：

**③ 异常契约**

| code | msg | 前端处理 |
| --- | --- | --- |
| 1060107016 | 生命周期流程状态流转非法 | 提示"仅审核通过的申请可生效"，刷新详情 |

**④ 前端交互与状态约束**

## 7. 企业材料完备性自查

### 7.1 材料完备性检查

**① 接口业务目标**
投标/资质申报前**一次自查**：按"身份类（营业执照、法人身份证明、授权委托书）/ 资质类（资质证书、安全生产许可证）/
实力类（审计报告、业绩、社保证明）"三档输出结论 + 缺失清单 + 临近到期清单，
解决"材料缺一件就被否决、却没人能提前发现"的痛点。业务闭环：自查 → 补材料/续期（§6）→ 再自查通过 → 提交投标。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `GET /bidding/enterprise-material/completeness` |
| 权限码 | `bidding:qualification:material:query` |

请求参数：

| 字段 | 类型 | 必填 | 默认 | 业务含义 |
| --- | --- | --- | --- | --- |
| `entId` | number | **是** | — | 企业主体 ID |
| `asOf` | string(date) | 否 | 今天 | **核验基准日**；可用于"以投标截止日为基准"预演（如填 `2026-10-01` 看那时是否仍有效） |

响应 `data`：

| 字段 | 类型 | 业务含义 |
| --- | --- | --- |
| `entId` / `asOf` | number / date | 回显入参（前端可校验一致性） |
| `result` | string | 总结论：**PASS 齐备 / RISK 有临近到期 / FAIL 有缺失或已过期** |
| `requiredCount` / `readyCount` | number | 必备材料数 / 已齐备数（用于进度展示） |
| `items[]` | array | 逐项明细（见下） |
| `missingItems[]` | array | 缺失/过期项（结论 FAIL 时的行动清单） |
| `expiringItems[]` | array | 临近到期项（结论 RISK 时的提醒清单） |

`items[]` 元素：

| 字段 | 类型 | 业务含义 |
| --- | --- | --- |
| `materialType` | string | 材料类型 code |
| `materialName` | string | 材料名称（直接展示） |
| `category` | string | 大类 code：IDENTITY / QUALIFICATION / STRENGTH / OTHER |
| `mandatory` | boolean | 是否必备（非必备缺失不影响 PASS/FAIL） |
| `status` | string | **READY 齐备 / EXPIRING 临近到期 / MISSING 缺失或已过期** |
| `sourceRef` | string | 取数来源（证照/资质/安许/业绩），便于点击跳转 |
| `expireDate` | string(date) | 到期日（长期为 null → 显示"长期"） |
| `message` | string | 说明（如"台账内该材料均已过期"） |

**③ 异常契约**

| code | msg | 前端处理 |
| --- | --- | --- |
| 1060107013 | 企业材料不完备，缺少：{清单} | **这不一定是错误**（部分场景作为阻断返回）；前端优先用 `data` 渲染，仅当无 data 时用 msg |
| 1060107014 | 必备材料清单为空，无法执行完备性检查 | 提示"尚未配置必备材料清单"，提供管理入口 |
| 403 | 没有该操作权限 | 隐藏入口 |

**④ 前端交互与状态约束**
- 结论三档用**醒目色块 + 图标**：PASS 绿 / RISK 黄 / FAIL 红；
- FAIL 时把 `missingItems` 渲染成**待办清单**，每项提供"去登记/去续期"跳转；
- `asOf` 建议提供日期选择器（默认今天），标签写明"以投标截止日预演"；
- 结果**不缓存**（材料状态会变）；每次进入页面重新请求。

## 8. 员工证书（证照域延伸：人证合一）

### 8.1 员工证书分页列表

**① 接口业务目标**
把"人"和"证"关联起来：按员工、证书类型、状态、**到期窗口**检索，供安许证三类人员（A/B/C）配备自查、
投标配证与到期预警使用。痛点：人员证书散落在个人手里，投标时才发现关键岗位人员证书已过期。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `GET /bidding/personnel-certificate/page` |
| 权限码 | `bidding:personnel:cert:query` |

请求参数：

| 字段 | 类型 | 必填 | 业务含义 |
| --- | --- | --- | --- |
| `pageNo` / `pageSize` | number | 否 | 分页 |
| `personId` | number | 否 | 持证员工 |
| `entId` | number | 否 | 归属企业 |
| `certType` | string | 否 | 证书类型 code（字典 `person_cert_type`） |
| `certNo` | string | 否 | 证书编号（精确） |
| `certStatus` | string | 否 | 状态 code（`person_cert_status`） |
| `major` | string | 否 | 专业（模糊） |
| `expiringDays` | number | 否 | **到期窗口**：仅返回 `validTo ∈ [今天, 今天+N]` 的证书（预警列表用） |

响应 `data.list[]`：字段与 §2.1 同构（`personId`、`certSubType` 细分 A/B/C、`nextReviewDate` 复审日、`validTo`、`certStatus` 等），
**员工证书特有字段**：

| 字段 | 类型 | 业务含义 |
| --- | --- | --- |
| `personId` | number | 持证员工主键 |
| `certSubType` | string | 证书细分：安许 A/B/C、特种设备 G1/G2/G3、C1/C2/C3（**安许配备统计依赖它**） |
| `nextReviewDate` | date | **下次复审日**（与到期日独立的维度；司炉/ISO 等"到期前就已失效"） |
| `registerUnit` / `registerNo` | string | 注册单位/注册编号（人证合一核查） |
| `isCurrent` | boolean | 是否当前有效版本 |

**③ 异常契约**：403 无权限；500 系统异常。

**④ 前端交互与状态约束**
- 类型/状态用字典；`expiringDays` 建议做成快捷筛选（30/60/90 天，**默认值取自 §1.2**）；
- `nextReviewDate` 临近需**单独角标**（复审逾期比到期更早失效）；
- 列表需展示员工姓名（若接口未直接返回，用 `personId` 在员工字典/接口中补全，**不要在列表里逐个请求**）。

**⑤ Mock 数据示例**

```json
      "certType": "SAFETY_ASSESS_CERT", "certSubType": "B", "certNo": "陕建安B(2023)000123",
      "major": "建筑工程", "validFrom": "2023-06-01", "validTo": "2026-10-05",
      "nextReviewDate": "2026-09-20", "certStatus": "EXPIRING_SOON",
```

### 8.2 到期清单（预警看板）

**① 接口业务目标**
为"到期预警看板"提供**不分页的紧凑清单**（按到期日升序），让经办人一眼看完未来 N 天内要处理的证照，
直接支撑"今天该干什么"的日清场景。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `GET /bidding/personnel-certificate/list-expiring` |
| 权限码 | `bidding:personnel:cert:query` |

请求参数：

| 字段 | 类型 | 必填 | 默认 | 业务含义 |
| --- | --- | --- | --- | --- |
| `entId` | number | 否 | 全部 | 归属企业 |
| `days`$ | number | 否 | 30 | 到期窗口天数（**建议前端默认取 §1.2 配置值**） |

响应 `data`：数组，字段同 §8.1。

**③ 异常契约**：403 无权限；500 系统异常。

**④ 前端交互与状态约束**
- 看板**不做分页**，但应限制 `days` 上限（如 365）避免一次拉回全量；超量时提示用户缩小窗口；
- 按剩余天数分档着色（剩余 ≤7 红、≤30 黄），**分档阈值同样取 §1.2**；
- 每行提供"去续期"入口（跳 §6.1 续期表单并预填 `bizDomain=PERSON_CERT`、`bizId`）。

**⑤ Mock 数据示例**

### 8.3 按细分统计可用持证人数

**① 接口业务目标**
安许证**三类人员（A/B/C）配备自查**的核心接口：按 `cert_sub_type` 统计"可用状态的持证人数"，
让企业随时知道"我现在够不够 A 类 1 人、B 类若干人"，避免动态核查被判不达标甚至失效。
痛点：人员流动后无人统计，被监管抽查时才发现不达标。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `GET /bidding/personnel-certificate/count-by-sub-type` |
| 权限码 | `bidding:personnel:cert:query` |

请求参数：

| 字段 | 类型 | 必填 | 业务含义 |
| --- | --- | --- | --- |
| `entId` | number | **是** | 归属企业 |
| `certType` | string | **是** | 证书类型 code，如 `SAFETY_ASSESS_CERT` |

响应 `data`：`Record<string, number>`，key = `certSubType`（如 `A`/`B`/`C` 或未细分时 `UNSPECIFIED`），value = 可用人数。

**③ 异常契约**：403 无权限；500 系统异常。

**④ 前端交互与状态约束**
- 渲染为"配备看板"：每类显示"当前人数 / 要求人数（§1.2 配置）"，不足标黄、为 0 标红；
- **要求人数必须来自 §1.2 配置**，不得前端写死；
- 人数变化后看板需手动刷新（不轮询）；建议提供"查看明细"跳 §8.1 并带 `certType + certSubType` 筛选。

**⑤ Mock 数据示例**

```json
{ "code": 0, "msg": "", "data": { "A": 1, "B": 2, "C": 3 } }
```

### 8.4 法定预警下限查询

**① 接口业务目标**
在"预警设置"页告诉管理员**法律规定的办理提前期**（如安许证延期需提前 3 个月、排污许可 60 日），
让预警天数设置时有**法定窗口参考**（低于下限即时提示法规出处）；**仅提示、不拦截**——保存不因低于下限被拒绝（3-C 口径，2026-09-21 更正，与 §1.2 一致）。

**② 契约定义**

| 项 | 值 |
| --- | --- |
| Method / URL | `GET /bidding/personnel-alert-run/legal-floor-days` |
| 权限码 | `bidding:personnel:cert:query` |

响应 `data`：`Record<string, number>`，key = 证照类别 code，value = 法定下限天数。

**③ 异常契约**：403 无权限；500 系统异常。

**④ 前端交互与状态约束**
- 设置页在用户输入预警天数时**即时对比**本接口结果：低于下限时输入框标红并显示"不得低于 N 天（依据：{法规}）"；
- 该提示是**辅助**（仅提示、不拦截）；保存接口不因低于下限拒绝（3-C 口径，2026-09-21 更正：后端不设拦截，以返回结果为准）。

**⑤ Mock 数据示例**

```json
{ "code": 0, "msg": "",
```

## 9. 错误码总表（电子证照域）

> 前端只需按段位做**兜底文案**，具体文案直接展示后端 `msg`（后端已本地化）。
> 段位规则：`1_060_{段}_{序号}`；本模块涉及段位 **109（证书与资质台账：证照/文件版本/验真/预警/企业资质/资质标准/安许）**、
> **107（员工资质与证件生命周期：员工档案/证书/履历/材料完备性/变更续期注销年检流程）**、
> **108（规则配置中心与业务字典：配置发布与字典下发）**。
> ⚠️ **2026-09-13 段位变更**：证书与资质台账原用 106 段，但 106 段已登记给"外部公告/采集/关注提醒"域，
> 两域 `000~026` 整段重叠（同一错误码两义，如 `1060106000` 既可能是"证照不存在"也可能是"PDF 抽取结果为空"），
> 故证照块整体迁至新登记的 **109** 段。**前端若已按旧号硬编码，请同步改为 `1090109xxx`。**

**兼容性承诺与迁移窗口**

1. **新增字段**：向后兼容，前端可忽略；
2. **新增枚举值**：向后兼容（前端必须按字典渲染，不得用 `switch` 穷举，否则新值会渲染异常）；
3. **删除/改名/改语义字段**：视为**破坏性变更**，需升主版本号，并保留**至少一个迭代**的双字段并存期（旧字段继续返回、标注 deprecated）；
4. **错误码**：只增不改语义；前端不得依赖具体数字做业务分支（除 400/401/403/500 这些平台级码）；
5. 契约变更流程：**先改本文件 → 记 §11 → 再改后端**；前端按版本号对齐。

### 编写原因
用户要求：在编写电子证照后端代码的同时，同步输出前端接口契约，且**严禁修改前端业务代码**，前后端只能通过契约协作。
因此需要一份既可人工审阅（含业务目标与交互约束）、又可被机器/AI 读取（含 Schema 与 TS 类型）的契约文件。

### 编写依据
1) 用户 2026-09-13 契约输出要求（5 维度：业务目标 / 契约定义 / 异常契约 / 交互与状态约束 / Mock 与版本）；
2) 实际后端代码：`certificate`、`certificate-verify`、`certificate-alert-run`、`cert-lifecycle`、
`enterprise-material`、`personnel-certificate`、`personnel-alert-run` 各 Controller 与 VO 字段逐一核对；
3) 框架约定：`CommonResult{code,msg,data}`（成功码 0）、`PageResult{list,total}`、请求头
`Authorization` / `tenant-id` / `Accept-Language`（取自框架租户与安全 starter、前端既有请求客户端约定）；
4) 《招投标模块开发规范》§4.4/§4.5/§4.7/§4.8（RESTful、幂等、错误码段位、数据分级与脱敏）；
5) 《电子资质七大模块技术方案.md》§8.1（规则配置中心——动态阈值与字典的数据来源）；
6) 用户硬约束："所有阈值、状态码、枚举值必须支持动态配置，严禁硬编码"。
