# 后端变更请求 · 门户投标的"用户类型识别"与投标资格门接线

> 提出方：前端（门户招投标）　日期：2026-09-29　状态：待后端处理
> 关联：`docs/电子证照前前端契约/后端变更通知-给前端.md`；`前端规范-全域接口说明/07-主体域前端交付-业务口径说明.md`

---

## 一、现象（用户原话）

> "个人用户由于没有企业档案，不能进行投标，但是点击建档之后依然是要求登录，明明已经登录。
>  这里需要两个提示：个人用户——本功能未对个人用户开放；租户员工用户——请联系贵公司对企业档案进行完善。"

即：**登录态是有效的，但用户被引导去登录**——提示语与真实原因不匹配。

---

## 二、根因（已定位到代码，三处，前端两处后端一处）

### 2.1 【后端】投标资格门从未接线

`SubjectEligibilityService.assertBidderEligible(tenantId)` 的 Javadoc 写着
"供后续'投标/报名递交'流程调用；不具备则抛 106_031/106_034"，
但**全仓检索没有任何调用点**（唯一出现处是接口声明与服务实现自身）。

后果：
- "没有企业档案不能投标"这条规则**实际上没有在后端生效**；
- 企业员工即使档案未完善、未授权，也能直接 `POST /bidding/process-track/create` 建出投标流程；
- 用户看到的"不能投标"其实来自**另一条路径**（见 2.2），规则与现象不是一回事。

### 2.2 【后端】门户端点用的是"管理端权限码"，个人用户注定 403

```java
// BiddingProcessTrackController
@PostMapping("/create")
@PreAuthorize("@ss.hasPermission('bidding:process-track:create')")
// GET /my 同理：@PreAuthorize("@ss.hasPermission('bidding:process-track:query')")
```

个人用户注册在保留租户 `tenant_id=0`（`TenantSecurityWebFilter.PERSONAL_TENANT_ID = 0L`），
**不可能持有任何企业角色的权限码** ⇒ 请求必然 403。
但 403 的语义是"没有该操作权限（权限未开通）"，与"本功能未对个人用户开放"是两件事。

### 2.3 【前端·本次已修，但需后端配合才彻底】租户越权 403 会清空会话

`TenantSecurityWebFilter` 在**请求头租户 ≠ 令牌租户**时返回：

```java
CommonResult.error(FORBIDDEN.getCode(), "您无权访问该租户的数据")
```

前端 `api/request.ts` 对这条特定 403 的处理是 `doTenantReAuthenticate()`——
**清 token + logout**（原意是"用户切换了租户，旧会话失效"）。

对**个人用户**来说这个处理是错的：他只是访问了门户的企业级接口，
不是"会话过期"，却因此在**下一次点击时变成未登录**——
这就是"明明已经登录，点建档却要求登录"的直接成因。

---

## 三、请求后端做的四件事

### 3.1 【必须】给出"当前登录用户类型"，供前端分流提示

个人用户与企业员工被拒的原因不同，前端必须能分辨。推荐二选一：

**方案 A（推荐，最小改动）**：在登录/用户信息出参里加一个字段。

```
GET /system/auth/get-permission-info  →  resp.user.userType: 'PERSONAL' | 'ENTERPRISE'
或
GET /system/user/get                  →  resp.userType: 'PERSONAL' | 'ENTERPRISE'
```

判据建议与 `PERSONAL_TENANT_ID` 同源：`tenantId == 0 → PERSONAL`，否则 `ENTERPRISE`。
（前端目前只能靠 `accessStore.tenantId === 0` 自行推断；这是**可实现但脆弱**的耦合，
后端显式下发后前端即可去掉该推断。）

**方案 B**：不加字段，由后端在两个业务错误码里把"开放范围"说清楚（见 3.2），
前端按错误码而非用户类型分流。二选一即可，**A + B 同时做最稳**。

### 3.2 【必须】门户投标入口按"原因"返回两个不同错误码（替代裸 403）

个人用户与"企业档案未完善"必须可区分，建议：

| 场景 | 建议错误码 | 建议 msg（前端可直接展示） |
| --- | --- | --- |
| 个人用户调用企业级投标入口 | **新增** `1_060_106_042 BID_PORTAL_PERSONAL_NOT_OPEN`（106 段 041 之后顺延，需先在规范 §4.7 登记） | `本功能未对个人用户开放` |
| 企业员工，但本租户未建档 | 复用现有 `1_060_109_037 SUBJECT_PROFILE_NOT_BUILT`（**建议改 msg**） | `请联系贵公司对企业档案进行完善` |
| 企业员工，档案存在但未完善 | 复用现有 `1_060_106_034 SUBJECT_PROFILE_INCOMPLETE`（**建议改 msg**） | `请联系贵公司对企业档案进行完善：{缺失项}` |
| 企业员工，未授权/授权停用 | 复用现有 `1_060_106_031 SUBJECT_NOT_AUTHORIZED` | 保持现状（平台侧动作，非企业可自助） |

> msg 改动说明：现有 037/034 的文案是"请先在「企业主体档案」完善信息后再操作"，
> 对**企业员工**不准确——员工个人无权维护企业档案，正确的下一步是**告知公司**。
> 建议统一为"请联系贵公司对企业档案进行完善"。

**关键**：这些码必须以 `code != 403` 的**业务错误**返回（`CommonResult.error(1_060_xxx, msg)`），
不能走 `@PreAuthorize` 的 403 通道——否则前端无法与"真的没权限"区分，
且会命中 2.3 的会话清理逻辑。

### 3.3 【必须】把投标资格门真正接到投标链路上

在下列入口调用 `assertBidderEligible(getTenantId())`（个人用户则先抛 3.2 的个人用户码）：

| 端点 | 说明 |
| --- | --- |
| `POST /bidding/process-track/create` | 意向投标建档 —— **最先该拦的一步** |
| `POST /bidding/process-track/register` | 报名投标 |
| `POST /bidding/process-track/upload` | 递交加密投标文件（最终门，务必拦） |

**顺序建议**：先判用户类型（个人 → 042）→ 再判租户资格（037/034/031）→ 才进业务。
这样"个人用户"不会被误报成"档案没完善"。

### 3.4 【必须】个人用户不应被租户门拦成"您无权访问该租户的数据"

`TenantSecurityWebFilter` 已对 `tenant_id = 0` 跳过租户状态校验，
但**"请求头租户 ≠ 令牌租户"的判等仍会把个人用户打回 403**。请确认：

- 个人用户（令牌租户 = 0）访问门户（`/portal/**` 对应的 `/bidding/**` 读接口）时，
  请求头带任何非 0 租户**都不应**产生"您无权访问该租户的数据"；
- 建议对 `PERSONAL_TENANT_ID` 的会话**忽略请求头租户、一律以令牌租户为准**，
  或仅对该 403 场景返回业务码而非全局 403（避免前端清会话）。

## 四、前端本轮已做的配合改动

| 改动 | 文件 | 说明 |
| --- | --- | --- |
| **个人账号不再因租户越权被登出** | `api/request.ts` | `doTenantReAuthenticate()` 增加例外：`tenantId===0` 时**不清 token、不 logout**。理由：个人用户没有企业租户可切，"无权访问该租户的数据"不是会话问题而是功能边界；原实现直接清会话，这正是"点一下变成要求登录"的直接成因 |
| 个人账号的租户越权给出业务提示 | 同上 | 该 403 原被静默吞掉（等清会话跳转）；个人账号下改为提示 **"本功能未对个人用户开放"**，不再出现"操作没反应" |
| 按用户类型分流两条提示 | `views/portal/bidding/detail.vue` | 新增 `isPersonalAccount`（`tenantId===0`）与 `subjectGateHint()`：个人 → "本功能未对个人用户开放"；企业员工 → "请联系贵公司对企业档案进行完善"。**优先按后端业务码判定**（042/037/034），码未落地时才回退到用户类型推断 |
| 新增 `blocked` 按钮态 | 同上 | 被业务规则拦下时按钮显示原因摘要（"未对个人开放" / "需完善企业档案"），点击给完整提示 + 下一步找谁，**不跳登录页** |
| 提示行写清"该找谁" | 同上 | 个人：说明需用企业账号；企业员工：说明企业档案由公司管理员在「设置 · 主体档案」维护，员工个人无权限 |

> 仍未改的部分（有意保留）：企业账号的租户错配仍按原逻辑清会话重登——
> 那是"切换租户后旧会话失效"的正解，与本条个人用户场景不同，不应一并改动。

---

## 五、验收口径

1. 个人用户在小程序/门户点「意向投标」→ 提示 **"本功能未对个人用户开放"**，**不跳登录页**；
2. 未建档/档案未完善的企业员工点同一按钮 → 提示 **"请联系贵公司对企业档案进行完善"**，**不跳登录页**；
3. 已建档且已授权的企业员工 → 建档成功，进入"投标流程管理"可见；
4. 上述三种情况下，**登录态均不被清除**（浏览器刷新后仍是登录态）；
5. `sql/tools/check-permission-coverage.js` 仍 `[OK]`（新增码需同步登记菜单权限点）。

```
       │      期望：业务码 1_060_106_042「本功能未对个人用户开放」

```
