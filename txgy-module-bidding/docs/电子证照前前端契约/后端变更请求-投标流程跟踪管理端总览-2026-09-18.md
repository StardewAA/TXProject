## 0. 一句话结论

页面要的是「**按租户/公司盘点的投标意向跟进台账**」：一次读到 `公司 → 意向项目 → 投标方动作阶段 → 负责人`，超管跨租户、租户只看本公司。

后端当前**没有任何**跨租户聚合端点；`bidding_process_track` / `bidding_process_event` 两表也未落地（仅在 `投标流程跟踪功能设计方案.md` §3 有 DDL 设计）。本文请求补齐 **3 个读接口 + 1 组候选/字典**，并做 **1 处菜单权限归位**。

## 1. 先裁定三件事（不确认这三条，接口会做歪）

### 1.1 `21-主流程通读问题清单` §3 的 (c)/(d) 冲突 → 裁定 **(d)**

21 号文档原文提出两个互斥读法并明确「只报告不动手，需你裁定」：

- (c) 维持 A 方案：后台保留「我的关注」个人跟踪视图；
- (d) 后台改为**企业维度跟踪**（需后端补企业级出参）。

**用户 2026-09-17 口径 = (d)**，且进一步明确为：**超管（平台）可看全部租户的投标流程，各租户/公司只看得见本公司**。
因此：后台**不再保留**「个人视角」的投标跟踪，个人视角只留门户（`portal/bidding`）。后台此页的语义随之从「我的关注」
变为「**企业跟进台账**」——可见性归企业，但每行仍标注该意向的**经办人（负责人）**。

### 1.2 与 `26/28` 号的「招标全流程状态机」不是同一件事（必须分清，勿合并）

| 维度 | 26/28 号：招标全流程 | **本契约：投标流程跟踪** |
|---|---|---|
| 视角 | 招标方（发布方） | 投标方（跟进方） |
| 跟踪对象 | 项目 / 招标项目 / 标段 / 公告 四个实体的生命周期 | **某公司对某个招标机会的跟进记录** |
| 阶段口径 | 项目 5 态 + 招标项目 12 态 + 标段 6 态 + 公告 5 态 | 意向投标 → 资质审核 → 待投标 → 已投标 / 流程结束（5 态） |
| 已有实现 | ✅ `POST /bidding/flow/transition`、`GET /flow/next-actions`、`/flow/logs` | ❌ 未落地 |
| 与另一者的关系 | 描述「这场招标走到哪了」 | 描述「**我们公司**在这场上做到哪了」 |

两者是**正交的两个状态机**：同一场招标可以「招标侧已到评标中」而「我方还在资质审核」。本页**只展示后者**，
不得用 `TenderStatusEnum` / `ProjectStatusEnum` 顶替。

### 1.3 ⚠️ 现表 `bidding_follow_item.stage_code` 是**第三种口径**，不能当本页阶段用

`FollowItemDO.stageCode` 注释原文取值：`PENDING/TENDER/OPEN_BID/EVAL/RESULT/CONTRACT/DONE/UNKNOWN`——
那是**招标侧进展的快照**（与 §1.2 左列同源），不是投标方的动作态。两个维度**必须分开存、分开展**，
否则会出现「公司还没报名，页面却显示已到 RESULT」这类自相矛盾的行。

## 2. 页面需要的数据形状（这就是出参要对齐的目标）

前端 `views/bidding/processTrack/demoData.ts` 已把形状固定下来，后端出参按此对齐即可：

```
公司（租户）
├── tenantId / tenantName / 统一社会信用代码 / 企业联系人
├── 项目数 + 阶段分布（用于卡头标签）
└── 意向项目[]
    ├── 项目名 / 项目编号 / 招标人 / 地区 / 预算金额 / 投标截止
    ├── 阶段 state（5 态之一）
    ├── 负责人 owner：姓名 / 职务 / 联系方式
    ├── 各阶段时间：意向 / 报名 / 审核完成 / 已投标 / 结束
    ├── 审核结果与原因（APPROVED / REJECTED + reason）
    ├── 标书名（documentName）
    ├── 备注
    └── 事件史 events[]（只读展示：事件类型 / 时间 / 操作人 / 说明）
```

页面另有：顶部 6 个 KPI（公司数 / 项目总数 / 进行中 / 已投标 / 已结束 / 负责人数），
与四维筛选（关键词=公司·项目名·编号·招标人·负责人 / 阶段 / 公司 / 负责人）。

## 3. 数据模型建议（请后端选型，二选一）

### 方案 A：复用 `bidding_follow_item`，只补动作态字段

现表（`TenantBaseDO`，含 `tenant_id`）已有 `user_id / followType / followKey / displayName / issuerName /
followTime / followStatus`——「公司 + 意向项目 + 负责人」三要素其实已经齐了。缺的只是**投标方动作态**与各阶段时间戳。

- 优点：不新增表，意向天然来自关注，不会出现「两份意向」。
- 风险：该表已被门户「我的关注」消费（`GET /bidding/notice-follow/item/page`），加字段会同时影响那个页面；
  且 `stage_code` 已被 §1.3 的招标侧口径占用，动作态只能另起字段名（如 `act_state`），容易混淆。

### 方案 B（推荐）：按 `投标流程跟踪功能设计方案.md` §3 落两表

`bidding_process_track`（主档）+ `bidding_process_event`（事件留痕），以 `follow_item_id` 关联关注行——
**意向来源仍指向关注，不复制第二份意向**（这一点与 `09` §5「现役意向已由关注闭环覆盖，无需再造一份意向表」一致）。

设计文档的表已覆盖页面所需（`tenant_id` / `user_id` / `current_state` / `previous_state` /
`intention_time` / `register_time` / `review_time` / `pending_bid_time` / `bidded_time` / `terminated_time` /
`review_result` / `review_reason` / `document_id` / `document_name` / `document_size` / `remark`）。**建议在此基础上补 4 处**：

| 建议补充 | 理由 |
|---|---|
| `tenant_name` 快照 | 页面要按公司分组并显示公司名。`TenantCommonApi` 目前**只有** `getTenantIdList()` / `validTenant(id)`，**没有取租户名的能力**（已核对 `system/api/tenant/TenantApiImpl`），bidding 的 `RpcConfiguration` 也只注册了 `AdminUserApi/DeptApi/FileApi`。落快照可免去新增 RPC |
| `owner_user_id` + `owner_name` 快照 | 负责人姓名。**现成做法可抄**：`SubjectUserDO` 就是「`AdminUserApi.getUser(id).nickname` 授权时点取值」存昵称快照——同样避免逐行 RPC、也避免用户改名导致台账历史漂移 |
| `region` / `amount` / `deadline` 快照 | 页面要展示地区/预算/投标截止。若每次都从 `bidding_project` / `bidding_tender_project` 联查，列表页 N 行就是 N 次关联；快照更稳（对齐本模块既有的 displayName/issuerName 快照习惯） |
| `uk` 唯一键语义确认 | 设计文档写的是 `uk_user_follow(user_id, follow_item_id, deleted)`。按 §1.1 的 (d) 口径，**可见性归企业**，请确认同一家公司多个业务员跟进同一个项目时，是「一人一行」还是「一公司一项一行」——页面按公司分组，若一人一行会出现同项目重复行，建议唯一键收敛到 `(tenant_id, follow_item_id, deleted)` |

### 4.1 阶段 / 事件字典需注册

前端当前把阶段与事件中文写成页面内具名常量（`STATE_TEXT` / `EVENT_TEXT`），这是本仓库

|---|---|

## 5. 接口清单（3 个读接口 + 1 组候选/字典）

一律 `GET`，前缀 `/admin-api/bidding/process-track/**`；返回 `CommonResult`，分页 `PageResult`。

### 接口 1｜总览分页（**项目粒度**，出参自带公司信息）

| 项 | 内容 |
|---|---|
| 路径 | `GET /bidding/process-track/page` |
| 权限 | `bidding:process-track:query`（租户+超管）/ 超管跨租户见 §6 |
| 入参 | `pageNo` `pageSize` / `keyword`（公司名·项目名·项目编号·招标人·负责人姓名，包含匹配）/ `state` / `tenantId`（**仅超管有效**，租户视角后端强制忽略）/ `ownerUserId` |
| 出参 | `PageResult<ProcessTrackItemVO>` |

`ProcessTrackItemVO`：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | 跟踪行主键（**雪花 ID 一律 String，禁止 Number()**，见 doc 24 §2.1） |
| tenantId / tenantName | String | 公司维度（**tenantId 必须 String**） |
| followItemId / followKey / followType | String | 关联的关注行（意向来源，可追溯） |
| projectName / projectCode | String | 项目名 / 编号 |
| issuerName / region / amount | String | 招标人 / 地区 / 预算金额 |
| deadline | Long | 投标截止（epoch 毫秒，本模块既有约定） |
| state / stateName | String | 阶段 code（见 §4.1）+ 中文名（**下发中文名，前端优先用字典、回退用此列**） |
| ownerUserId / ownerName / ownerPost / ownerPhone | String | 负责人（四者可空，页面降级显示「—」） |
| intentionTime / registerTime / reviewTime / biddedTime / terminatedTime | Long | 各阶段时间戳（可空） |
| reviewResult / reviewReason | String | APPROVED / REJECTED + 原因 |
| documentName | String | 标书名（页面只读展示，不做下载入口） |
| remark | String | 备注 |

### 接口 2｜KPI 统计

| 项 | 内容 |
|---|---|
| 路径 | `GET /bidding/process-track/stats` |
| 权限 | `bidding:process-track:query` |
| 入参 | 无（租户视角自动限定本公司；可复用接口 1 的筛选条件，请后端定） |
| 出参 | `{ tenantCount, projectCount, ongoing, bidded, terminated, ownerCount, byState: {INTENTION: n, …} }` |

> `ongoing` 定义：意向投标 + 资质审核 + 待投标 三态之和（与页面 KPI 卡口径一致）。

### 接口 3｜本域候选（筛选项）

| 项 | 内容 |
|---|---|
| 路径 | `GET /bidding/process-track/options` |
| 权限 | `bidding:process-track:query` |
| 入参 | 无 |
| 出参 | `{ owners: [{value,label,extra}], tenants: [{value,label,extra}] }` |

- `owners.value = ownerUserId`（String），`label = 姓名`，`extra = 公司名`（**跨租户同名必须靠 extra 区分**）；
- `tenants` 仅超管需要（租户视角只会有一项，前端已隐藏该下拉）；
- 字段沿用 doc 24 的 `OptionItemRespVO` 形状，便于前端复用同一套组件。

### 接口 4｜详情（含事件史）

| 项 | 内容 |
|---|---|

| 权限 | `bidding:process-track:query` |

| 出参 | `ProcessTrackItemVO` + `events: [{ eventType, eventName, fromState, toState, operatorName, operationDesc, occurredAt }]` |

## 6. 权限与租户隔离（**硬要求，本节是本次改动的核心**）

### 6.1 权限码

| 权限码 | 归属 | 作用 |
|---|---|---|
| `bidding:process-track:query` | 租户 + 超管 | 本租户只读（菜单 6748 页面可见性） |
| `bidding:process-track:overview` | **仅超管** | 跨租户总览（决定 `tenantId` 参数是否生效、`tenants` 候选是否下发） |

### 6.2 服务端隔离（不可省略）

- 非超管：**必须**按 `TenantContextHolder` 强制过滤，`tenantId` 入参忽略——不允许「前端不传就返回全部」；
- 超管：跨租户查询走显式 `@TenantIgnore` / `TenantUtils.executeIgnore(...)`，并只出参 §5 字段（不夹带政务级字段，见规范 §4.4-5、§5 五）；
- 判定超管请用后端侧既有口径（角色码 `super_admin`），**不要**使用权限码含 `*:*:*` 的写法——本部署
  `AuthConvert` 下发的 `permissions` 是**菜单权限码去重**，不含通配符，`*:*:*` 恒不成立（前端已踩过这个坑）。

### 6.3 前端已实现的隔离（说明，非替代）

前端已按「超管（`userStore.userRoles` 含 `super_admin`）看全部 / 其余只看 `accessStore.tenantId` 对应公司」实现，
并在页头标注「平台视图 · 全租户 / 本公司视图」。**但前端过滤只是呈现层控制**——真实数据接入后跨租户可见性
必须由 §6.2 服务端强制，否则任何人构造请求即可越权。

### 6.4 菜单 SQL 需同步（2 处）

1. 菜单 **6748** 的 `permission` 需由 `bidding:notice-external:query` **改回** `bidding:process-track:query`
   （历史成因见 `sql/history/2026-09-09-process-track-perm-align.sql`：v1 页面唯一接口走 notice-follow，故临时借用；
   v2 页面已不再调用该接口，借用失去理由），并按 §6.1 增补 `bidding:process-track:overview`；
2. 按钮 **6749-6752**（`bidding:process-track:create/register/review/upload`）对应的写入口**已从页面全部移除**
   （见 §8），这 4 条菜单已无归属——建议**撤销**或明确保留为「状态机上线后再启用」，请后端与组员确认后同步 SQL。
