# 入参对等检查：一次**未通过验收**的工具尝试（2026-09-14）

- 缘起：出参侧已有第 13 道门禁（VO ↔ FE interface），但**入参/筛选字段**没有门禁。已证实这是真盲区——
  本轮前一次提交修的就是"后端 `beginTime/endTime` 支持、前端从不透传"（能力不可达）。
- 本轮目标：做 **入参对等** 检查（后端 `*ReqVO` ↔ 前端 `*Params/*Req`），并考虑立为第 17 道门禁。
- **结论：工具做出来了，但未达设门禁的标准，故不设门禁**，只把踩到的三个解析陷阱与核验结果记录下来。

## 1. 做法（配对口径）

按**接口 URL 确定性配对**，不靠注释点名（注释口径实测只覆盖 10/24 个入参类型，且会抓错相邻注释）：

1. 后端：`@RequestMapping(base)` + **方法级**归属 `@GetMapping/@PostMapping(...)` + 该方法的 `*ReqVO` 形参
   → 得到 75 个"URL → ReqVO"映射（实测 **0 个 URL 歧义**）；
2. 前端：`export function X(params: T)` + `requestClient.xxx('/url')`，并把 `T` **限定在同文件**解析；
3. 逐字段比对，输出 `[后端有·前端无]` 与 `[前端有·后端无]`。

首轮结果：可比对 41 组，报差异 9 组。**手核后发现多数是假阳性。**

## 2. 三个解析陷阱（全部实测踩到）

| 陷阱 | 症状 | 正解 |
|---|---|---|
| **嵌套类字段被当成顶层字段** | `CertLifecycleApplyReqVO.FieldChange` 的 fieldName/oldValue/newValue 被报成"后端有·前端无" | 解析字段时必须跳过嵌套 `class` / `static class` 体 |
| **FE 形参用命名空间类型** | `(data: PersonnelApi.SaveReq)` 里 `SaveReq` 命中**同文件另一个** `SaveReq`（员工档案），于是把证书保存报成"前端有·后端无 personNo/personName…" | 需解析 `Namespace.Type`，或在同文件多同名 interface 时报"无法配对"而非硬配 |
| **泛型里的空格** | `private Map<String, Object> payload;` 抓不到 → 误报"后端有·前端无 payload" | 字段正则须允许泛型内空格 |

## 3. 手核结果（**3/3 是假阳性**）

工具报的三条"前端有·后端无"，逐一读后端 VO 原文核对，**全部存在**：

| 工具报告 | 后端原文 | 判定 |
|---|---|---|
| `SubjectAuthPageReqVO` 缺 `authStatus` | 该 VO 有 `private String authStatus;`（"授权状态：ENABLED/DISABLED"） | ❌ 假阳性 |
| `SubjectUserPageReqVO` 缺 `enabled` | 该 VO 有 `private Boolean enabled;`（"启用状态"） | ❌ 假阳性 |
| `QualificationAlertPageReqVO` 缺 `entId/refType/alertLevel` | 该 VO 三者齐全 | ❌ 假阳性 |

假阳性来自"URL → ReqVO"映射被**同名 URL 覆盖**（`beEndpoints` 用 Map，后写覆盖先写；去重版本才正确）。
**在假阳性率如此高的情况下立门禁，只会训练出"看见红就绕"的习惯**——故本轮**不设门禁**。

## 4. 剩余 9 组差异的**逐条手核结果**（9/9 均非真缺陷）

| # | 探针报告 | 手核证据 | 判定 |
|---|---|---|---|
| 1 | `applyCertLifecycle` 缺 fieldName/oldValue/newValue | 后端是**嵌套类** `CertLifecycleApplyReqVO.FieldChange`；前端有 `changes?: FieldChange[]` 与之对应 | ❌ 假阳性（陷阱①） |
| 2 | `updatePersonnelCert` 多出 personNo/personName/idCard… | 前端 `personnel/index.ts` 内**同时存在** `PersonnelCertApi.SaveReq`（证书，函数真正用的是它）与 `PersonnelApi.SaveReq`（员工档案），探针抓到后者 | ❌ 假阳性（陷阱②） |
| 3 | `getQualificationApplyPage` 配到 `EnterpriseQualificationSaveReqVO` | 该 URL 后端确为 `QualificationApplyPageReqVO`（entId/qualId/applyType/status），与前端 `ApplyPageReq` **逐字段一致** | ❌ 假阳性（URL 映射被覆盖） |
| 4 | `fetchSubjectAuthPage` 缺 authStatus | 后端 `SubjectAuthPageReqVO` 有 `private String authStatus;` | ❌ 假阳性 |
| 5 | `fetchSubjectUserPage` 缺 enabled | 后端 `SubjectUserPageReqVO` 有 `private Boolean enabled;` | ❌ 假阳性 |
| 6 | `getQualificationAlertPage` 缺 entId/refType/alertLevel | 后端 `QualificationAlertPageReqVO` 三者齐全 | ❌ 假阳性 |
| 7 | `saveProject` / 8 `saveTenderProject` / 9 `saveBidSection` | 前端**直接拿出参类型当入参**：`saveProject(data: ProjectApi.Project)`，而 `Project` 注释写明是 `ProjectRespVO` | ⚠️ **口径盲区**：不是缺陷（能跑），但"入参对等"对这三个接口**永远比不出来**——要查它们必须另建"出参类型复用为入参"的清单 |

**净结果：9 组差异 → 假阳性 6 组、口径盲区 3 组、真缺陷 0 组。**
本轮次项调查的全部真实产出 = `taskType` 幽灵字段一处（已删）。

### 附带发现（值得单独立项，本轮未动）

前端把**出参类型**（`ProjectRespVO` 等）直接当 save 接口的入参用，共 3 处。这既让入参对等检查失效，
也让"保存时多带了后端不认的字段"这类问题无法被静态发现。建议后续为这三个接口补 `*SaveReq` 入参类型（前端可独立完成）。

## 5. 本轮唯一手核为真并已修的问题

`api/bidding/crawlExternal/index.ts` 的 `TaskPageParams.taskType` 是**幽灵字段**：
后端 `CrawlTaskPageReqVO` 字段为 jobId/sourceCode/status/channelCode/url/beginTime/endTime，
**无 taskType**（`externalfetch` 域全仓 `task_type` 0 处命中）；控制台里出现的 `taskType:'TEST'` 是**本地测试留档标记**
（代码注释已写明"非后端 crawl-task.taskType"），从不随请求发出。
声明一个不存在的入参，等于给后人埋一个"传了没效果"的坑 → **已删除**并写明依据。

## 6. 下次要立这道门禁，必须先做到的

1. `URL → ReqVO` 用**去重后**的映射，遇到一个 URL 多个 ReqVO 直接报错退出（不猜）；
2. 字段解析跳过嵌套类、允许泛型空格、忽略 `PageParam` 继承字段；
3. 前端形参解析支持 `Namespace.Type`；同文件同名 interface 视为不可配对；
4. **先跑出"假阳性=0"的样本集**（至少把这 9 组逐条手核通过）再谈门禁——本文件的 3 条反例就是验收集。
