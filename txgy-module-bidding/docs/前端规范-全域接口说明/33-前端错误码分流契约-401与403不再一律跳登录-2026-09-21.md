# 33 前端错误码分流契约：401 / 403 不再一律跳登录页（2026-09-21）

> 规范依据：《招投标模块开发规范》§4.5（统一响应体）；本文件由**后端**发出，前端按此改造守卫逻辑。
> 适用：**全部页面**（web-antd 全模块，不限招投标域）。
> 一句话结论：**HTTP 状态码在本框架里恒为 200，判成败/判登录态只能看 `body.code`；
> 且「未登录」与「无权限」是两个不同的 code（401 / 403），跳登录页只能由 401 触发。**

---

## 一、问题（前端现状）

前端目前把「请求失败」笼统当成「登录失效」，统一 `redirect` 到登录页。实际有两类完全不同的失败：

| 场景 | 用户真实处境 | 正确 UX | 现状（错） |
| --- | --- | --- | --- |
| 未登录 / 登录已过期 | 需要重新登录 | **跳登录页**（可带 redirect 回跳） | 跳登录页 ✅ |
| **已登录但无该权限** | 登录态是好的，只是没配权限码 | **原地提示**「无操作权限，请联系管理员开通」+ 留在当前页 | **也跳登录页** ❌ |

第二类跳登录页会让用户反复登录却永远进不去（因为权限不会因为重新登录而出现），
是**死循环式体验**：登录 → 跳回 → 再登录 → 再跳回。

---

## 二、后端真实响应（2026-09-21 活服务实测，非推断）

**所有情况 HTTP 状态码都是 200**，必须读 `body.code`：

```
GET /admin-api/bidding/certificate/page?pageNo=1&pageSize=1
```

| # | 场景 | 请求头 | HTTP | body.code | body.msg |
| --- | --- | --- | --- | --- | --- |
| ① | **未登录**（无 token） | 无 | **200** | **401** | `账号未登录` |
| ② | **无权限**（登录了，但角色没这个码） | 有效 token | **200** | **403** | `没有该操作权限` |
| ③ | 正常 | 有效 token | 200 | 0 | `` |
| ④ | **token 无效/伪造** | 垃圾 token | **200** | **401** | `账号未登录` |
| ⑤ | 无 token 且无租户头 | 无 | 200 | **401** | `账号未登录` |
| ⑥ | 个人用户访问企业端点 | 有效 token | 200 | **403** | `没有该操作权限` |
| ⑦ | 跨租户访问 | 有效 token | 200 | **403** | `没有该操作权限` |
| ⑧ | 租户不存在 | 有效 token | 200 | **1002015000** | `租户不存在` |
| ⑨ | 路径不存在 | 有效 token | 200 | **404** | `请求地址不存在:...` |

**注意 ④**：token 过期/失效也归 `401`，这正是"跳登录页"该触发的唯一条件。
**注意 ②⑥⑦ 合并**：无权限、跨租户、个人用户越权，后端**故意统一为 403**（不泄露资源是否存在）。

---

## 三、分流规则（前端按此实现）

```
拿到响应后：
  if (body.code === 0)         → 正常，走业务
  else if (body.code === 401)  → 【登录失效】清登录态 + 跳登录页（带 redirect=当前路径）
  else if (body.code === 403)  → 【无权限】**不跳登录页**，原地提示，登录态保持
  else if (body.code === 404)  → 【接口不存在】提示"功能未上线/联系管理员"，不要跳登录
  else                          → 业务错误，按 msg 提示（保持登录态）
```

### 3.1 各 code 的前端动作表

| body.code | 语义 | 清登录态 | 跳登录页 | 提示文案（建议） |
| --- | --- | --- | --- | --- |
| `0` | 成功 | 否 | 否 | — |
| `401` | 未登录/登录过期/token 失效 | **是** | **是**（带 redirect） | `登录已过期，请重新登录` |
| `403` | 已登录但无该权限 | **否** | **否** | `无操作权限，请联系管理员开通` |
| `404` | 接口不存在 | 否 | 否 | `功能暂未开放，请联系管理员` |
| `1002015000` | 租户不存在（保留租户 0 的特例） | 否 | 否 | `当前账号无企业租户上下文` |
| 其他非 0 | 业务错误 | 否 | 否 | 直接用 `msg` |

### 3.2 为什么 403 不能跳登录页（三条硬理由）

1. **权限不会因为重新登录而出现**——重新登录还是同一个账号、同一批角色，必然再 403，形成死循环。
2. **403 是终态而非会话问题**——它是"该账号在当前租户下没有这个权限码"，与登录态无关。
3. **用户会误判为系统故障**——反复被踢到登录页，用户会认为"系统坏了"，而不是"我需要申请权限"。

### 3.3 403 的推荐 UX（三种，按页面重要度选）

| 做法 | 适用 | 说明 |
| --- | --- | --- |
| **按钮级置灰 + tooltip** | 页面已知需要某权限码时（最推荐） | 前端提前用 `get-permission-info` 拿权限码集合，无码的按钮直接 disabled，`title="无权限：请联系管理员开通"`。**根本不让用户点出 403** |
| 原地 Error 提示条 | 用户点了才发现没权限 | `message.error('无操作权限，请联系管理员开通')`，**留在当前页** |
| 整页 403 占位 | 页面本身无权限（如菜单被误开） | 页面内渲染"无访问权限"空态 + 返回上一页，**不要整站跳登录** |

## 四、配套：登录态判定也不能看 HTTP 状态

同一框架事实（见 §32/33 已登记条目）：**鉴权失败不是 HTTP 401，是 HTTP 200 + `body.code=401`**。

因此下面这些写法**全都判不出问题**，必须改：

```ts
// ❌ 全部无效（HTTP 恒 200）
res.ok
res.status === 401
res.status === 403
error.response.status === 401

// ✅ 正确
const body = await res.json();
if (body.code === 401) { /* 跳登录 */ }
if (body.code === 403) { /* 原地提示，不跳 */ }
```

> 若前端用的是统一 `requestClient`（axios 封装），应把上述分流**收敛在拦截器里**一处实现，
> 避免每个页面各写一套。拦截器需要能拿到 `body.code` 而不是 `error.response.status`。

## 五、权限码集合从哪来（做按钮级置灰用）

**注意归属服务**：该端点在 **system 服务**（`/system/auth/get-permission-info`），
**不在 bidding 服务**——直连 bidding 端口（48110）会得到 `code=404 请求地址不存在`。
前端应走网关（`/admin-api/system/auth/get-permission-info`），登录时已在调用，可直接复用其中的 `permissions`。

**实测响应结构**（2026-09-21，system 服务）：

```jsonc
// 无角色账号（租户 1 的 bidding_robot）
{ "code": 0, "data": {
    "user":        { "id": 80932, "nickname": "招投标机器人", "username": "bidding_robot", ... },
    "roles":       [],
    "permissions": [],
    "menus":       []
}, "msg": "" }

// 超管（对照）
{ "code": 0, "data": {
    "roles":       ["common", "super_admin"],
    "permissions": ["", "mes:dv-mainten-record:query", ...],
    "menus":       [ ... ]
}, "msg": "" }
```

- 个人用户（保留租户 0）与无角色账号会返回 `roles:[] / permissions:[] / menus:[]`，
  **这是正常状态（code 仍为 0），不是错误**；
- 前端守卫务必容忍 `permissions` 为空数组：**空数组 = 无任何权限码**，不代表未登录。
- **未登录**的判据只有一个：`body.code === 401`（或本地无 token），**不是** `permissions.length === 0`。

### 5.1 招投标域的权限模型（影响你判哪些按钮该灰）

本域有**两种鉴权范式**，前端要区别对待：

| 范式 | 端点特征 | 判权方式 | 例子 |
| --- | --- | --- | --- |
| **仅登录** | `@PreAuthorize("isAuthenticated()")` | **不查权限码**，登录即可用 | `/bidding/notice-follow/**`（关注域 7 端点）、`/bidding/file/**`、`/bidding/attachment/**`、`/bidding/bid-review/portal/**`（标书审查门户 11 端点） |
| **权限码** | `@PreAuthorize("@ss.hasPermission('bidding:xxx')`)` | 查 `permissions` 集合 | 其余全部（证照/资质/项目/人员/投标流程…） |

**结论**：关注、附件、文件、标书审查门户这些**不要做按钮级判权**（它们不需要权限码，
按权限码置灰会误灰）；只有"权限码范式"的按钮才做置灰。

## 六、验收标准（前端自测清单）

以 `GET /admin-api/bidding/certificate/page` 为例：

- [ ] **不带 token** → 跳登录页，且 URL 带 `redirect`，登录后能回到原页面
- [ ] **带无效 token** → 跳登录页（同 401）
- [ ] **带无权限账号的 token**（如租户 1 的无角色账号）→ **留在当前页**，提示"无操作权限"，
      登录态**不被清除**（点其他有权限的页面仍正常）
- [ ] **登录态保持**：403 之后刷新页面，仍然处于登录状态（没有被登出）
- [ ] 无权限账号访问**关注域**（`/bidding/notice-follow/status`）→ **正常返回 code=0**，
      说明"仅登录"范式未被误判成无权限
- [ ] 无权限账号访问**标书审查门户**（`/bidding/bid-review/portal/my/page`）→ **code=0**

### 6.1 后端已实测的基线（前端可据此对照，2026-09-21 活服务）

| 探测 | HTTP | body.code | msg |
| --- | --- | --- | --- |
| 无 token 调 `certificate/page` | 200 | **401** | 账号未登录 |
| 无效 token 调 `certificate/page` | 200 | **401** | 账号未登录 |
| 无权限账号（租户1 无角色）调 `certificate/page` | 200 | **403** | 没有该操作权限 |
| 同一无权限账号调 `notice-follow/status`（仅登录范式） | 200 | **0** | — |
| 同一无权限账号调 `bid-review/portal/my/page`（仅登录范式） | 200 | **0** | — |
| 不存在的路径 | 200 | **404** | 请求地址不存在:... |
| `system/auth/get-permission-info`（无角色账号） | 200 | **0** | roles/permissions/menus 均为 `[]` |

**这张表的含义**：前两行必须跳登录页；第三行**必须不跳**（原地提示）；
第四、五行证明"仅登录"范式的端点不会被误判为无权限。

## 七、后端侧现状说明（哪些是设计，哪些是待改进）

| 项 | 现状 | 说明 |
| --- | --- | --- |
| HTTP 恒 200 | **框架设计，不会改** | 统一响应体 `{code,msg,data}` 是平台约定，前端必须适配 |
| 401 / 403 区分 | **已正确实现** | 实测确认，前端可直接依赖 |
| 403 文案 | `没有该操作权限`（**不含**缺哪个码） | 设计如此（不泄露权限模型）。前端如需精确提示，自行对照本地权限码判断 |
| `data.fieldErrors` | 参数校验失败时提供字段级错误 | 见 `code=400` 响应，格式 `[{field,message,rejectedValue}]` |
| 缺 `traceId` | 部分响应带 `traceId`（在 `data` 内），部分不带 | 已知不一致，排查问题时以服务端日志为准 |

## 八、给前端的落地建议（最小改动）

1. **改一处**：统一 `requestClient` 的响应/错误拦截器，把 `401 → 跳登录`、`403 → 原地提示` 分流收敛在此；
2. **清一处**：全仓搜 `res.ok` / `response.status` / `status === 401` 的鉴权判定，替换为 `body.code`（§33 已登记 6 处历史修复，如有新增同法处理）；
3. **加一处**（可选但推荐）：页面加载时取 `get-permission-info` 的 `permissions`，
   对"权限码范式"的按钮做置灰；**仅登录范式**的入口不要置灰；
4. **验一遍**：按 §六 清单自测，重点确认 **403 不跳登录、且登录态不被清除**。
