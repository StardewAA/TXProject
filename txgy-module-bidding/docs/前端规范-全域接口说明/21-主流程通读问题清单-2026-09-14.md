## 二·补（同日续查）：两个新发现

### 1. 更正：`/portal/bidding/publish` **不是死路由**，它有入口

上一提交的说明里我写它"全仓无任何界面入口"，**错了**：`views/portal/bidding/internalHall.vue:156`
有一张「发布公告 · 起草/四类公告/发布撤下」卡片，`goNav('/portal/bidding/publish')` 即跳该页（我当时用

因此"是否收回后台"这件事是**有用户可见影响**的，不能按死路由静默处理，仍需业务裁定。

### 2. 真越界（已修）：门户发布工作台暴露平台运维按钮

`NoticeWorkbench.vue` 是前后台共用的组件（`mode='admin'|'portal'`），表头三个"运维动作"
**未按模式区分**，门户页同样渲染：
· `POST /bidding/notice/reindex`（重建索引）、`POST /bidding/notice/reindex-all`（全量重建）、
  `POST /bidding/notice/exchange/gather-sync`（公开同步）；接口注释自称"**NoticeController 运维端点**"；
· 权限码均为 `bidding:notice:update` —— 而门户"**撤下**公告"用的也是这个码（见 api 注释 §1.8），
  ⇒ **门户用户点得动平台级索引重建与公开同步**（不是"看得见点不动"）。
· 修法：界面层收敛为 `v-if="!inPortal"`（管理端专属），并在代码注释写明"权限码相同 ≠ 职责相同"，
  建议后端后续把运维端点拆成独立权限码（如 `bidding:notice:ops`），届时界面约束即成为冗余双保险。

### 2·补 门户类型与 api 类型：同形重复 + 一处真漂移（已修）

门户 `views/portal/bidding/types.ts` 自建 13 个接口，与 `api/bidding` **并行**（这正是它能同时逃过
"类型对等"与"单位语义"两道门禁的原因，已在 README 记录）。本轮逐接口做了字段级比对：

| 门户类型 | 对应 api 类型 | 相似度 | 判定 |
|---|---|---|---|
| `FollowItem` | `processTrack.FollowItem` | **1.00**（字段全同） | 纯重复：仅 null 宽容度不同（门户 `null | string`，api `?: string`）。
  **依据后端 VO**：`FollowItemRespVO` 全部是包装类型（String/Integer/Boolean）且注释明写"维度行/无关联公告为 **null**" ⇒ **门户的写法才是准确的**，api 侧 `?: string` 是"可选但不可空"的类型谎（该类型目前无人消费，故未引爆）。建议后续以门户写法为准反向修正 api 侧 |
| `InternalNoticeItem` | `notice.Row` | **1.00** | 同形不同名（纯重复） |
| `InternalNoticeDetail` | `notice.Detail` | 0.83 | **真漂移：门户缺 `pdfSha256`** —— 后端 `NoticeDetailRespVO` 确有该字段（"版式文件（PDF）原文件哈希（SHA-256）"）⇒ **已补** |
| `NoticeExternalItem/Detail` | `ManageItem/ManageDetail` | 0.39 / 0.32 | **非重复**：公开端（大厅只读）与管理端（含审核/AI/抽取态）本就不同视图 ⇒ 保持分开 |
| `InternalNoticeParams` | `notice.PageParams` | 0.50 | 门户多 `publishTimeStart/End`（大厅时间窗）⇒ 合理扩展 |

结论：**结构上确实是两套并行类型，但目前只有 1 处真漂移（已修）**；未做"门户改为 import api 类型"的大改，
因为它会把 api 侧那处 null 类型谎一并继承（见上表第一行）。已记录方向供后续择机统一。
