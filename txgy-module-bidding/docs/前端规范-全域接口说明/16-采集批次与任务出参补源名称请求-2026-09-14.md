# 契约 16：采集批次/任务出参请补 `sourceName`（前端展示"信息源"名称）

> **现状封口（2026-09-18 复核）**：前端一律 `sourceName || sourceCode` 兜底展示（信息源卡墙/任务条/批次详情/频控提示），
> 缺失时回显 code 不白屏；出参补全由后端实施，前端不催不改。

- 提出方：前端（招投标前端 · 采集域）
- 日期：2026-09-14
- 影响面：采集控制台「采集批次」页（列表 + 详情抽屉）、任务链路详情
- 期望交付：后端（**前端不改后端**）

## 1. 现状（证据）

`CrawlJobRespVO`（`controller/admin/externalfetch/vo/`）字段：

```java
@Schema(description = "批次 ID")            private Long id;
@Schema(description = "源代码（空=全源）")   private String sourceCode;   // ← 只有 code
@Schema(description = "触发类型：SCHEDULE/MANUAL/REPAIR") private String triggerType;
…
```

`CrawlTaskRespVO` 同样只有 `private String sourceCode;`（"源代码"），**两者都没有 `sourceName`**。
而 `CrawlSourceRespVO` 是有 `sourceName` 的（源列表页正常显示中文名）。

**后果**：批次页与任务链路里，"信息源"这一业务对象只能显示成一串 code（如 `SH_GGZY`），
运营看批次健康度时必须自己记住 code 对应哪家交易中心；原筛选条件甚至是**手输 code 的输入框**。

## 2. 前端已做的兜底（不需后端也能用，但有代价）

前端改为：进入批次页时调 `GET /bidding/crawl-source/page`（pageSize=100）建 `code → sourceName` 映射，
列表/详情显示 `名称（code）`，映射未命中或加载失败时回落显示 code。

代价（这就是请求后端补字段的理由）：
1. **多一次请求**且与批次列表无事务一致性 —— 源被改名后，批次页显示的仍是本次加载时的名字；
2. **源数超过 100 时要分页拉全量**（当前 100 上限是前端写死的兜底值，不是可靠口径）；
3. 同一映射逻辑会在每个"带 sourceCode 的列表页"里重复实现（本页已是第 2 处，控制台另有 1 处）。

## 3. 请求（二选一，推荐 ①）

① **在 `CrawlJobRespVO` / `CrawlTaskRespVO` 增加 `@Schema(description = "信息源名称") private String sourceName;`**
   （分页查询 SQL 关联 `bidding_crawl_source.source_name`）。前端拿到后**删除本地映射与那次额外请求**，
   并把筛选下拉维持为源列表（筛选仍需全量源，但展示不再依赖它）。

② 若不便改 SQL：在 `/bidding/crawl-source/page` 之外补一个 `GET /bidding/crawl-source/simple-list`
   （返回 `sourceCode + sourceName` 全量、无分页、权限同 `bidding:crawl-source:query`），前端用它做映射。

## 4. 前端验收口径（后端交付后由前端执行）

- 批次列表"信息源"列显示 `名称（code）`；全源批次显示"全源"；
- 源改名后刷新批次页立即反映新名称（**不再需要额外请求**，即 ① 生效）；
- 前端删除 `job/index.vue` 的 `fetchCrawlSourcePage` 映射代码与 `job/data.ts` 里的回落注释；
- 类型对等门禁（第 13 道）会把新字段记为前端 interface 的缺失项 → 前端补 `sourceName` 后该项消失，
  这条链路正好验证"字段补齐 → 门禁自动放行"。
