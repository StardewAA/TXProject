# 文件「上传 / 下载 / 更新」接口口径对账与收敛建议 —— 2026-09-20

> 背景：用户 2026-09-20 反馈「文件的上传下载更新之间到底用的是什么接口，各个方面都有冲突」。
> 本文对该链路做**实码逐条对账**（前端 API/组件 + 后端 Controller/VO 注释 + 既有规范 11 号文），列出全部并行通道、冲突点与收敛建议。
> 结论先行：**上传 3 条通道、下载/预览 3 条通道、更新 4 套模型、鉴权 3 档、病毒口径 2 种**——冲突属实，需按 §三 收敛。

## 一、现状全景（实码取证）

### 1.1 上传：三条通道

| 通道 | 接口 | 返回 | 谁在用（证据） |
| --- | --- | --- | --- |
| A 业务包装（推荐） | POST /bidding/file/upload | {fileId, url, name, type, size, sha256} | 业务页统一走它：api/bidding/file#uploadBiddingFile；bidReview/TaskPanel:208、certificate/index:111、cert-files:129、lifecycle-apply:78 |
| B 平台原生 | POST /infra/file/upload | **只有 url，无 id** | api/infra/file/index.ts:84 upload()；components/upload/use-upload.ts:140 getUploadUrl()；getFilePresignedUrl |
| C 补登记 | POST /bidding/file/register-by-url | {fileId,...}（sha256=null） | 仅历史「只有 URL 没 fileId」数据修复通道（api/bidding/file:48） |

**根因（后端自己写明）**：controller/admin/file/BiddingFileController.java 类注释——
「平台既有 POST /infra/file/upload 只回 URL（无 id），业务表却以 file_id 关联，二者不匹配是本次缺陷的根因；
 在 bidding 侧补一个语义完整的上传接口，比修改 infra 公共接口（影响全平台调用方）风险更低」。

### 1.2 下载 / 预览：三条通道

| 通道 | 方式 | 用在哪（证据） |
| --- | --- | --- |
| ① 直接吃出参 url + 前端同源化 | downloadPlatformFile(url)（api/bidding/bidReview:334，取 /admin-api/ 起的同源路径） | 审查报告 Word：BidReviewReportDrawer:82、report/ReportPanel:132 |
| ② 按 id 换取 url | GET /infra/file/get?id=（**需 infra:file:query**） | views/bidding/vo/PdfPreview.vue:44（仅历史 fileId 数据的兜底分支） |
| ③ 后端签名地址 | FileApi 签名 downloadUrl | 外部公告附件：NoticeExternalDetailRespVO:101、NoticeExternalManageDetailRespVO:109；通用附件域注释「预览走 FileApi 签名下载」 |

**已知权限坑（两处自陈）**：
- BiddingFileRespVO 注释：「出参同时给 fileId 与 url……避免前端为预览再去调 /infra/file/get（该接口需 infra:file:query 权限，业务账号通常没有）」；
- PdfPreview.vue 注释同款：fileId 分支需 infra:file:query，「业务账号通常没有 ⇒ 历史数据可先 registerBiddingFileByUrl 补登记，或由后端在出参直接回传可访问 URL」。

### 1.3 更新 / 替换：四套模型

| 场景 | 机制 | 接口（证据） | 历史保留 |
| --- | --- | --- | --- |
| 证照文件 | **只追加版本** | CertificateController: /file/register(110)、/file/list(118)、/file/void(127)、/file/correct | ✅ 保留（软删留痕） |
| 通用附件 | **绑定 / 解绑** | AttachmentController: /save(43)、/delete(53)、/list(62) | ⚠️ 逻辑删除（可见性差） |
| CA 签章件 | **重新签章** | /bidding/ca/seal/document、/ca/seal/check、/ca/seal/verify | ⚠️ 新旧件并存但无关联 |
| 业务表内嵌 | 直接存 fileId 或 id 数组 | lifecycle evidenceFileIds（lifecycle/index:401、692 仅显示「文件编号：…」**无预览**）；certificate/index:116 import {fileId}；cert-files:135 fileId+fileHash | ❌ 覆盖即丢引用 |

### 1.4 鉴权与安全：三档权限 / 两种病毒口径

| 入口 | 鉴权 | 证据 |
| --- | --- | --- |
| /bidding/file/upload、/bidding/attachment/* | isAuthenticated()（登录即可） | BiddingFileController:41、AttachmentController:44 |
| /infra/file/get、/infra/file/upload | infra:file:query / infra:file:*（**业务账号通常没有**） | api/infra/file/index.ts:37 |
| /bidding/certificate/file/* | bidding:certificate:file / bidding:certificate:query | CertificateController:112/120 |

**病毒口径两种**：
- 通用附件域：行上带 virusStatus，**INFECTED 不下发下载 URL**（attachment/index.ts:9）；
- 证照域：契约 §3.2 要求「virusScanStatus !== CLEAN 禁止预览/下载」，但**后端不拦**——错误码 1_060_109_006 已定义却全仓无抛出（见《契约跟进-后端变更通知给前端总纲-落地核对清单-2026-09-28》§3.3 核对结论）。

## 二、冲突清单（现象 → 后果）

1. **上传双入口、身份模型不同**：A 回 fileId（业务关联键）、B 只回 url → 同一件事两套写法；业务页若误用平台组件，拿到 url 却落不了 file_id。
2. **dev 特例不同源**：api/bidding/file/index.ts 的 DEV_DIRECT_BASE 在 dev 下**直连 48110**（规避 Vite 代理对 POST body 的截断 bug），生产同源 —— dev/prod 行为分叉（CORS、鉴权头、cookie 策略不一致）。
3. **下载三通道并存**：同是「看/下文件」，有的用出参 url、有的按 id 换 url、有的用签名地址 → 权限要求不同、失败表现不同。
4. **权限倒挂**：真正需要「拿 url」的场景（历史数据只有 fileId）却要 infra 权限，业务账号没有 → 前端只能靠后端额外回传 url 兜底（两处注释都在抱怨这件事）。
5. **更新语义四分**：证照=版本追加、附件=解绑重绑、CA=重新签章、表单字段=覆盖 → 审计口径不统一，「这份文件是什么时候被谁换掉的」在四种模型里答案不同。
6. **附件三套数据模型**：①业务表单值 file_id 列；②业务表 id 数组（evidenceFileIds / attachmentFileIds）；③独立 bidding_attachment 表（bizType+bizCode 一对 N）→ 查询/权限/扫描/预览各自实现。
7. **「有编号无预览」**：lifecycle 佐证材料仅把 id 拼成文本展示（lifecycle/index:692「文件编号：x、y」），用户看得到编号、点不开文件。
8. **病毒口径双标**：附件域按 virusStatus 屏蔽下载 URL，证照域既不拦也不提示（码在路不在）。

## 三、收敛建议（推荐口径）

### 3.1 一句话口径

**上传只走 /bidding/file/upload；关联只认 fileId；预览优先用出参 url（同源化），需回查时走 bidding 自己的 file 读接口；更新按「版本 / 绑定 / 重新签章」三语义选型，不再新增第四种；病毒统一读 FileApi 的 virusStatus。**

### 3.2 需后端确认 / 新增（3 件）

| # | 事项 | 说明 | 优先级 |
| --- | --- | --- | --- |
| 1 | **新增 GET /bidding/file/get?id=**（isAuthenticated，返回 {fileId,url,name,type,size,sha256,virusStatus}） | 内部走 FileApi，把「fileId → 可访问 URL」的稳定映射收在业务侧，前端不再依赖 infra:file:query；PdfPreview 的历史兜底分支即可切换为它 | P0 |
| 2 | **明确 /infra/file/upload 的使用边界**（或提供返回 id 的平台版） | 建议规范写明：业务附件**必须**走 /bidding/file/upload；平台组件（components/upload/*）仅用于头像、知识库等非业务附件 | P1 |
| 3 | **统一病毒字段与拦截口径** | 二选一并写入规范：①各域统一读 virusStatus 且预览/下载一律拦截 INFECTED；②证照域明确「仅提示不拦截」并删除误导性契约表述 | P1 |

### 3.3 前端已做 / 待做

- 已做：业务页上传统一 uploadBiddingFile；PdfPreview 优先 url、infra 仅兜底并带明确报错文案；下载统一 downloadPlatformFile 同源化。
- 待做（依赖 3.2-1）：PdfPreview 的 fileId 兜底从 /infra/file/get 切到 /bidding/file/get；
- 待做（不依赖后端）：lifecycle 佐证材料由「文本编号」升级为附件行（走 /bidding/attachment/*，bizType 扩展 LIFECYCLE），使附件可点可预览。

### 3.4 迁移顺序（低风险优先）

1. 后端补 /bidding/file/get → 前端切换兜底分支（一次性、可回滚）；
2. 在 11 号文补一节「上传/下载/更新三段口径 + 平台上传禁用清单」；
3. 逐域把「业务表裸存 fileId 数组」迁移到通用附件域（迁移期双读：先读 attachment 行，回落到旧列）；
4. 病毒口径统一（依赖后端 3.2-3 决策）。
