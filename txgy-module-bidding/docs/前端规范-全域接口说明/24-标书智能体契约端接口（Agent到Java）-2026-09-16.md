## 1. 落点与职责

| 项 | 值 |
|---|---|
| 进程 | `txgy-module-bidding-server`（服务名 `bidding-server`，端口 **48110**，网关 `grayLb://bidding-server`） |
| 契约前缀 | `/admin-api/bidding/bid-agent/contract/**`（直连 48110 或经网关 48080） |

| 租户 | 请求**不带** `tenant-id` 头：控制器标 `@TenantIgnore`，租户由 `tenantId` 参数/请求体显式传入，服务层 `TenantUtils.execute` 再开启租户过滤 |
| 幂等 | 写方法带 `@Idempotent`（解析器＝方法名+参数 MD5，**1 秒**窗口），不需要调用方传任何请求头 |
| 表 | `bidding_bid_project` / `bidding_bid_agent_chunk` / `bidding_bid_chapter_draft` / `bidding_bid_enterprise_fact` / `bidding_bid_task_shadow` |

- 不做：长流程编排、直接调 LLM 写正文、docx 模板读写（这些在 Node 侧）。

## 3. 运行期配置（`txgy-module-bidding-server`）

配置以 `txgy-module-bidding-server/src/main/resources/application.yaml` 的 `bidding.bid-agent.*` 为准
（`txgy-server` 不依赖本模块，其 application.yaml 不承载该配置）。

```yaml
bidding:
  bid-agent:
    agent-key: ${TXGY_BID_AGENT_KEY:}        # 机对机密钥（仅用于入站契约端鉴权）；空=开发态不校验
    ai-enabled: ${BID_AGENT_AI_ENABLED:false} # 检索总开关；false 时 /retrieve 返回 hit=false 转人工、入库跳过并写台账原因
    embedding: # 阿里云百炼（OpenAI 兼容端点）
      base-url: ${DASHSCOPE_BASE_URL:https://dashscope.aliyuncs.com}
      api-key: ${DASHSCOPE_API_KEY:}         # 缺失时调用报「云端检索不可用」，不影响启动
      model: ${DASHSCOPE_EMBEDDING_MODEL:text-embedding-v3}
      dimensions: ${DASHSCOPE_EMBEDDING_DIMENSIONS:1024}
      batch-size: 10
    rerank: # 阿里云百炼 text-rerank
      enabled: ${DASHSCOPE_RERANK_ENABLED:true}
      base-url: ${DASHSCOPE_BASE_URL:https://dashscope.aliyuncs.com}
      model: ${DASHSCOPE_RERANK_MODEL:gte-rerank-v2}
    retrieve:  { top-k: 8, min-score: 0.35, candidate-factor: 4 }
spring:
  ai:
    vectorstore:
      qdrant: { host: 127.0.0.1, port: 6334, collection-name: bidding_bid_agent_chunk, initialize-schema: true }
```

> 2026-09-16 起**不再自建本地模型**：embedding/rerank 由 `framework/bidagent` 下的百炼 HTTP 客户端承担
> （`DashScopeEmbeddingModel implements EmbeddingModel` 供 Qdrant VectorStore 使用），因此
> `spring-ai-starter-model-openai` 与 `spring.ai.openai.api-key` 占位配置已删除——**不会再出现"少一个凭据就启动失败"**；
> 云端不可用时改为调用期显式报错（`1_060_111_070 云端检索不可用`）。
> `initialize-schema=true` 让首次启动自动建 Qdrant 集合（维度取 `embedding.dimensions`）。

## 5. 决策与待办

**决策**

- 鉴权：`@PermitAll` 免登 + `X-Agent-Key` 内部密钥过滤器（已实现，2026-09-16 实测无 key=401/错 key=401/对 key=200）。
- 租户：Agent 显式传 `tenantId`，Java 侧 `TenantUtils.execute` 兜租户过滤。
- `projectId` / `tenantId` 为 Long（平台主键约定），Node 侧需用真实数字主键。
- 幂等：契约端不接受 `idempotency-key` 请求头，改用「方法名+参数」MD5 的 1 秒窗口（与 A 侧后台接口的 `idempotency-key` 口径区分）。
- **检索栈上云（2026-09-16 定稿）**：embedding/rerank 统一走阿里云百炼，向量库复用 Qdrant 容器；不再自建 TEI。
- **两种检索口径**：契约端 `/contract/retrieve` 在检索栈不可用（无 key / 云端报错）时**降级为 `hit=false`**（Agent 转人工，编排不硬失败，原因落 WARN）；
  后台「召回验证 / 精准度测试」走严格口径，原样抛 `1_060_111_070`，避免专员把"云端没配好"误判成"资料没入库"。
- **智能体配置的"平台默认 + 租户覆盖"**：5 类智能体基线挂在 `tenant_id=0`（平台默认），读取时本租户优先、平台默认兜底；
  保存时本租户无覆盖则按平台默认复制一份到本租户再改（故新租户不会看到空列表，也不会污染平台默认行）。
- **标段隔离本期生效**：切片写入 `bid_section_code`（向量 metadata + 台账列），检索按标段过滤；`/contract/segment/index` 新增可选入参 `bidSectionCode`（向后兼容）。
- **A 侧不再透传底座**：材料入库/切片/召回/跑批改为直连 Java 检索实现（`BidIndexService` / `BidRetrievalService`），
  底座只剩编排与 LLM 生成；相应配置 `bidding.bid-agent.{enabled,base-url,index-path,retrieve-path,timeout-seconds}` 与
  错误码 `1_060_110_004/005` 已删除（底座原本并不提供 `/bid/segment/index` 等端点，属并入期遗留的错误指向）。

**待办（按优先级）**

1. ~~**BM25 / MySQL FULLTEXT(ngram)** 通道（当前仅向量 + rerank）~~ —— **2026-09-17 已落地**，见 §8。
2. 字段值规划 `FieldValuePlanner`（COPY_FACT/DERIVE/GENERATE/MANUAL）在 Java 侧落地（当前 Node 侧已做等价实现）。

踩坑记录（保留自旧 README，仍适用）：

- `-api` 模块不能使用 `@Schema`（api 模块不依赖 swagger 注解）——契约 DTO 保持纯 POJO。
- Spring AI 2.0.0 的 `FilterExpressionBuilder.build()` 与既有示例不一致，检索改为「向量检索 → 按 metadata 应用层二次过滤（租户/项目/文档类型）」。
- Lombok `@Builder`：`dal/dataobject` 下的 DO 不要用（生成的 `XxxDO$XxxDOBuilder` 会被 `DO_LAYER` 规约测试判为「非 XxxDO」）。
- MyBatis `@Resource` 注入：字段名会被当作 Bean 名优先匹配，跨域同名（如 `projectMapper`）必须写成与 Mapper 类一致的 Bean 名（`bidProjectMapper`），否则报 `could not be injected because it is a JDK dynamic proxy`。

| 方法 | 路径 | 说明 |

## 9. 关键词通道（BM25 · MySQL FULLTEXT ngram）落地与实测 — 2026-09-17

**链路**：`向量粗召回 → 关键词粗召回（MATCH…AGAINST）→ RRF 融合 → rerank + 阈值 → 必检`

| 项 | 取值 / 文件 |
|---|---|
| 索引 | `bidding_bid_agent_chunk.content` 上 `FULLTEXT ft_chunk_content WITH PARSER ngram`（实例 `ngram_token_size=2`） |
| 迁移 | `sql/history/2026-09-28-bid-agent-bm25.sql`（幂等：查 information_schema 后再 ALTER；晚于切片表建表脚本 09-27） |
| 开关 | `bidding.bid-agent.retrieve.bm25-enabled`（默认 true）/ `bm25-top-k`（默认 8）/ `rrf-k`（默认 60）；`bm25-enabled=false` 与"仅向量 + rerank"完全等价 |
| 检索模式 | NATURAL LANGUAGE MODE（用户 query 里的 `+ / - / *` 不做布尔解释，避免语义漂移） |
| 隔离口径 | 关键词 SQL 与向量侧 `filterByScope` 同一套：租户（租户拦截器自动拼）+ 项目 + 文档类型 + 标段 + 来源文档 |
| 命中方式 | `matchedBy` 取值收敛为 `rerank > hybrid > bm25 > vector`（rerank 开启时最终标记仍是 `rerank`） |
| 降级 | BM25 只在向量链路可用时作**补充**通道；`ai-enabled=false`、云端不可用、向量库异常一律维持 `hit=false` 转人工（不做"仅关键词兜底"，如需另加 `keyword-only-fallback` 开关） |

**实测（25 条精准度用例，来源：炼化公司2026年防腐保温项目施工招标技术文件.docx，11 条切片，tenant_id=1，标段 SEC-001）**

| 配置 | recall@8 | recall@3 |
|---|---|---|
| 候选放大×4 + BM25 关（改动前基线） | 1.00（25/25） | 1.00（25/25） |
| 候选放大×4 + BM25 开（生产配置） | 1.00（25/25） | 1.00（25/25） |
| 候选放大×1 + BM25 关（模拟大语料下向量候选受限） | 1.00（25/25） | **0.96（24/25）** |
| 候选放大×1 + BM25 开 | 1.00（25/25） | **1.00（25/25）** |

- 结论：当前语料只有 11 条切片，向量 + rerank 已接近全覆盖，故 recall@8 看不到差异；把向量候选收紧到
  top-8（候选放大×1）后差异显现——漏掉的「转包分包的违约责任」被关键词通道捞回，recall@3 由 0.96 → 1.00。
  即：**语料规模越大、候选截断越早，关键词通道的价值越大**（编号/术语/数字类查询尤其明显）。
- 复现方式：`/bidding/bid-agent/eval/run`（用例在 `bidding_bid_eval_case`，25 条 enabled），
  用 `--bidding.bid-agent.retrieve.bm25-enabled=false|true` 重启即可对照；
  本地重启与 A/B 脚本：`.tools/setup/start-bidding-local.ps1`（key 由调用方以环境变量注入，不落文件）。
- 已知观察：rerank 开启时 `matchedBy` 恒为 `rerank`，前端「命中方式」列看不出通道来源；
  若需要展示"谁是关键词捞回来的"，后续可给出参加一个 `channels` 字段（本期不动出参）。

## 10. 入库文本清洗（索引阶段）— 2026-09-21

**链路**：`Tika 抽取全文 → BidTextCleaner 清洗（编码统一 / 去噪 / 结构归一）→ 500 字切分 → 向量化 + 切片台账`

| 项 | 取值 / 文件 |
|---|---|
| 实现 | `service/bidagent/index/BidTextCleaner.java`（纯 JDK、无 Spring 依赖）；入口 `BidIndexServiceImpl#cleanContent` |
| 编码统一 | 换行统一 `\n`；去 BOM / 零宽 / 软连字符 / 私用区（Wingdings 类乱码）/ 替换符；控制字符只保留换行；NBSP 与全角空格折半角；逐码点 NFKC（全角字母数字、全角运算符、带圈序号、罗马数字折半角）。**中文标点不改写**（`，。；：！？（）《》—…""` 原样保留），避免把中文排版折成英文标点 |
| 去噪 | 删页码（`第 X 页`、`X / Y`、`- X -`、`Page X of Y`，以及"孤立出现 + 非递减"的裸数字序列）；删重复出现的短页眉页脚（≥3 次且占比 ≥8%）；删水印/扫描仪厂商行、纯符号装饰行、相邻重复段。条款行与「年 月 日 / 公章 / 签字」等填空占位行受保护，不参与页眉页脚删除 |
| 结构归一 | 分页符 `\f` 视为段落边界；合并 PDF 抽取造成的硬换行（上一行 ≥20 字、不以句末标点收尾，且下一行不是新条款/字段标签/表格行/裸数字）；行内连续空白压成单空格；目录点线折成 `……`；装饰符重复压成 1 个；段落一律以单个 `\n` 分隔 |
| 开关 | `bidding.bid-agent.index.clean-enabled`（默认 `true`）；`false` 时原文直入，用于回滚与 A/B 对比（与检索侧 `bm25-enabled` 同口径：只做开关，不做静默降级） |
| 可复算 | 每次入库打一行 INFO：`chars=输入->输出, paragraphs=…, 删页码=…, 删页眉页脚水印=…, 删空行=…, 删重复段=…, 合并折行=…, 编码归一字符=…`；DEBUG 另有被删行抽样（理由 + 原文前 40 字），用于复核"没有误删正文" |
| 检索侧配套 | 检索词同口径做编码归一（`BidTextCleaner.normalizeEncoding`，见 `BidRetrievalServiceImpl#doRetrieve`）。入库已把全角折半角，检索词若不归一会出现"资料里有、就是搜不到"的假未命中 |

**抽样实测（用知识库现有切片拼接近似原文，`clean-enabled=true`）**

| 样本 | chars | 删页码 | 删页眉页脚水印 | 删重复段 | 合并折行 | 编码归一字符 |
|---|---|---|---|---|---|---|
| 陕西液化天然气…杨凌LNG项目.docx（101 切片） | 45482 → 45148 | 13 | 8 | 8 | 232 | 79 |
| 炼化公司所属各单位2026年装置大修消缺.docx（40 切片） | 18201 → 18068 | 0 | 0 | 0 | 138 | 6 |
| 炼化公司2026年防腐保温项目施工招标技术文件.docx（11 切片） | 4589 → 4545 | 0 | 0 | 0 | 1 | 0 |

- 被删行抽样全部是页码与 `*` 之类纯装饰行，未出现正文行；口径由 `BidTextCleanerTest`（11 项单测）锁死：
  编码统一 3 项、去噪 3 项、结构归一 3 项、边界与可复算 2 项。
- **注意（重建索引的副作用）**：清洗改变切片边界，`sourceBlockIds`（`文档名#序号`）会随之变化。
  重建索引后需重跑 `/bidding/bid-agent/eval/run`；既有精准度用例若以块号为准（`expectBlockIds`），
  会出现"命中了但块号不符"的假失败，建议改按关键词判定或按新块号更新。
