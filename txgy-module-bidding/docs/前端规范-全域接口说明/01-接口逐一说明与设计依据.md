# bidding 模块：暴露给前端的接口逐一说明（功能 + 设计依据）

> 适用对象：招投标网站前端（门户大厅 + 企业后台 + 平台管理端）。
> 事实源：`/v3/api-docs`（OpenAPI）；本文为开发协作口径，与运行 OpenAPI 冲突时以 OpenAPI 为准。
> 代码侧依据注释均带「[依据]」标记；法规原文见 `docs/法规依据/00-索引与引用说明.md`。

## 0. 通用约定

| 项 | 约定 |
| --- | --- |
| 上下文前缀 | 所有接口走 `/admin-api`（容器/网关环境）；下表只写 controller 相对路径 |
| 返回体 | `CommonResult{code,msg,data}`，code=0 成功；分页 data=`PageResult{list,total}` |
| 分页参数 | `pageNo/pageSize`（PageParam 基类；maxPageSize 由框架控制） |
| 幂等 | 所有写操作标 `@Idempotent`（前端按钮 loading，防连点重复提交） |
| 租户 | 企业侧接口在租户上下文中执行（自动隔离）；标注「免租户」的公开接口 G 轨全局可读 |
| 时间序列化 | **实测（2026-09-07，48110 直连）**：LocalDateTime 出参统一序列化为 **epoch 毫秒数字**（如 `publishTime:1788668723000`），前端按需格式化；本表/示例中的 `yyyy-MM-dd HH:mm:ss` 仅作文义说明，非线格式 |
| 接口前缀 | 运行实例 HTTP 层生效前缀 **`/admin-api`**（`/v3/api-docs` 内 paths 均带此前缀；不带前缀的 `/bidding/...` 返回“请求地址不存在”）——直连与代理目标均需拼全 |
| 权限不足 | 框架统一返回错误码（前端统一走 code≠0 提示，勿硬编码） |
| 资格门 | 见 §7：公告/备案写操作受「招标人授权+完善」门约束；关注/订阅/浏览/管理仅需权限，不受档案完善度约束 |

## 7. 资格门（影响 1.5/1.6/1.7/4.1，其余接口不受影响）

- **投标资格门（预留）**：`assertBidderEligible(tenantId)` 供后续「本项目投标/报名递交」流程调用；本期未落地投标动作，不产生假接口。
- **招标人发布门（已生效）**：`/bidding/notice` 的 create/update/publish 与 `/bidding/filing` 的 submit 前置断言：
  - 未授权/已停用 → **1-060-106-031**（前端提示「企业尚未被平台授权为招标人，请联系平台管理端授权」）；
  - 已授权但档案未完善 → **1-060-106-034**（前端提示「主体信息未完善，请先完善后发布/备案」，可引导到 6.1.1/6.1.2）；
  - 无租户上下文（平台同步/初始化作业）不设门，不阻塞批处理。
- **豁免口径**：关注（3.x）、订阅、浏览（2.x/1.2/1.4）、档案维护（6.1）、授权管理（6.2）等**不需要信息完善**，只要登录+权限即可（需求 Task2 明文口径）。
- 前端投标入口建议：点击「投标/报名」前调 6.1.3（企业）或 6.2.4（平台）获取 `eligible/reasonCodes/missingRequiredNames`，不满足时展示原因并引导「完善信息」或「联系平台授权」。

## 附：编写说明（本文档尾部固定段）

### 编写原因
招投标网站业务需求（主体信息完善、平台授权、资格门）落地后，模块暴露给前端的接口集合扩大（新增主体域 10 个端点）且既有接口行为变化（公告/备案写操作受资格门约束）。为使前端团队有**单一、逐接口、带设计依据**的协作口径，编写本总览文档；此前分散在多个域文档中的接口说明在此对齐。

### 编写依据
- 业务需求：Task1（外部公告管理/关注/爬虫管理面）、Task2（完善投标人/招标人信息、管理端授权+管理用户、被授权仍须完善、未完善不能投标但可关注/订阅、信息不完整无法获得投标资格）；
- 法规/规范：《招标投标法》第8/12/16/24/25/26条，《实施条例》第15/19条，《电子招标投标办法》第9/13/14/17/19/24条，《招标公告和公示信息发布管理办法》第5/6/10/12/13条，GB 32100-2015，国家/陕西 V2.0 数据规范表89；全文见 `docs/法规依据/`；
- 代码事实源：本模块全部 controller（`controller/admin/**`）+ `/v3/api-docs`。

### 所满足的业务需求内容及其实现方式
- 需求「管理端显示已授权投标人并支持管理用户」→ 6.2.1~6.2.7（授权/启停/经办用户绑定与分页，G 轨 + 企业名称/档案完善度快照）；
- 需求「被授权投标人仍须完善信息；未完善不能在本项目投标，但可关注公告、参与其他项目」→ 6.1.1~6.1.3 完善度与资格接口 + §7 资格门（关注域 3.x 不设门）；
- 需求「信息不完整无法成功获取投标权限」→ 资格门=授权 ∧ 完善（`SubjectEligibilityServiceImpl`），投标入口经 6.1.3/6.2.4 前置校验；
- 需求「管理、关注、订阅等不需要信息完善，有权限即可」→ §7 豁免口径 + 各域权限注解；
- 招标人同构硬约束（授权+完善方可发布项目公告/备案）→ §7 招标人发布门（1.5/1.6/1.7/4.1 接线）。
