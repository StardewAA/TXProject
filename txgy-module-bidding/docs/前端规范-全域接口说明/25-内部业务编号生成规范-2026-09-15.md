# 25. 内部业务编号生成规范（bizNo 规则生成，非随机）——2026-09-15

## 1. 背景与决策

用户裁定：**内部管理项目、内部公告、备案回执等内部业务编号必须按规范规则生成，不能随机**（原实现为 `BN/FB + UUID12`，UUID 不可读、不可追溯、无法按年度/区划统计）。

规则依据：《电子招标投标系统技术规范 第1部分 交易平台》附录B.3.2 项目编号规则——编号总长 **17 位**，序列号段采用 **0-9、a-z 的 6 位组合序列号**（原 000001-999999 扩展为 36 进制，容量 36⁶ ≈ 21.7 亿）。

## 2. 编号结构（三类统一，17 位）

```text
┌────┬──────┬──────┬──────┐
│前缀│ 区划 │ 年度 │ 序列 │
│ 1  │  6   │  4   │  6   │
└────┴──────┴──────┴──────┘
```

| 段 | 位数 | 取值 | 说明 |
|---|---|---|---|
| 前缀 | 1 | B / F / I | 字母分类，隔离内部编号与外部数字开头编号 |
| 区划 | 6 | GB/T 2260 市级代码 | 缺省取 610000（陕西省级兜底） |
| 年度 | 4 | yyyy | 按年度分桶，序列每年重置 |
| 序列 | 6 | 0-9、a-z 36 进制，左补 0 | 原子递增，同桶连续不重号 |

### 类型表（BiddingBizNoTypeEnum）

| type | 前缀 | 业务 | 接入点 |
|---|---|---|---|
| NOTICE | B | 公告内部编号（notice_code） | NoticeServiceImpl.generateNoticeCode |
| FILING | F | 备案受理回执号（receipt_no） | FilingServiceImpl.generateReceiptNo |
| PROJECT | I | 内部管理项目编号（project_code） | ProjectServiceImpl.saveProject |

示例：`I6101002026000001` = 内部项目 + 西安市（610100）+ 2026 年 + 第 1 号；`B610000202600000a` = 公告 + 陕西省级 + 2026 年 + 第 10 号。

## 3. 原子递增实现（bidding_biz_sequence，G 轨全局）

表 `bidding_biz_sequence`（DDL：`sql/history/2026-09-15-bidding-biz-sequence.sql`，仅 CREATE，可重复执行）：

```sql
CREATE TABLE IF NOT EXISTS bidding_biz_sequence (
  biz_type varchar(16) NOT NULL COMMENT 'NOTICE/FILING/PROJECT',
  scope_key varchar(32) NOT NULL COMMENT '分桶键：年度_区划（如 2026_610000）',
  seq bigint NOT NULL DEFAULT 1 COMMENT '当前序号',
  create_time datetime DEFAULT CURRENT_TIMESTAMP,
  update_time datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (biz_type, scope_key)
) ENGINE=InnoDB COMMENT='内部业务编号序列（原子递增，G轨）';
```

取号单语句原子化（同一连接，无应用侧读-改-写窗口，多实例并发不重号）：

```sql
INSERT INTO bidding_biz_sequence (biz_type, scope_key, seq, create_time, update_time)
VALUES (?, ?, LAST_INSERT_ID(1), NOW(), NOW())
ON DUPLICATE KEY UPDATE seq = LAST_INSERT_ID(seq + 1), update_time = NOW();
-- 随后同一连接 SELECT LAST_INSERT_ID() 取走
```

设计要点：
- **G 轨全局**：不含 tenant_id、不做逻辑删除（内部编号全局唯一，不能按租户分桶撞号）；主键 = (biz_type, scope_key) 天然一桶一行。
- **分桶**：按 (年度, 区划) 分桶，序列号逐年重置、按区划独立计数。
- **越界**：36⁶ 容量内单桶实际不可能耗尽；防御性抛 `BIZ_NO_SEQ_EXCEEDED`。

## 4. 接入行为

### 4.1 内部项目（PROJECT，I 段）

- **新建（id 为空 + projectCode 为空）**：服务端按 `reqVO.regionCode`（缺省 610000）生成 I 段编号，回写入参后走原有幂等 upsert 流程。
- **编辑（id 非空 + projectCode 为空）**：**沿用库内原编号**（追溯以编号为键，每次编辑不重新编号、不耗序号）。
- **外部项目**：传外部 projectCode（如 E 开头平台编号）时不生成。
- VO 调整：`ProjectSaveReqVO.projectCode` 由 `@NotBlank 必填` 放宽为可选（外部项目必填、内部项目可空），`projectName` 保持必填。

### 4.2 公告 / 备案（NOTICE=B / FILING=F）

- `createNotice`：`noticeCode` 缺省时生成 B 段编号；显式传入（如外部同步）时沿用。
- `submitFiling`：`receiptNo` 由服务端生成 F 段编号，不提供入参覆盖（回执号是受理留痕，业务上应内定）。

## 6. 存量影响

- 存量 `BN+UUID / FB+UUID` 编号**不受影响、不迁移**（编号只增不改，新老格式并存可读）。
- 序列表自首笔新编号起记数；旧编号不占新序列。

## 7. 前端衔接（前端只读，仅告知口径）

1. **新建内部项目**：不带 projectCode 提交即可，返回后从详情取编号展示。
2. **编辑内部项目**：表单里显示原编号；提交若不带编号，后端沿用原号（不会跳号）。
3. **新建公告**：noticeCode 留空由后端生成（受招标人发布门约束的流程不变）。
4. 需要候选列表的场景继续走 `GET /bidding/meta/options`（见契约 24），本次不改动前端。

## 9. 层级式编号（2026-09-20 扩展：招标项目 / 标段，T08）

用户裁定：**招标项目编号 20 位 = 所属项目编号(17) + 3 位序列；标段编号 23 位 = 所属招标项目编号(20) + 3 位序列**（在父编号基础上追加序列号）。

```text
招标项目：┌─ 项目编号(17) ─┬ 序列(3) ┐   = 20 位
标    段：┌─ 招标项目编号(20) ─┬ 序列(3) ┐ = 23 位
```

| 段 | 位数 | 说明 |
|---|---|---|
| 父编号 | 17 / 20 | 项目编号 / 招标项目编号（含前缀+区划+年度，自带追溯链） |
| 序列 | 3 | 0-9、a-z 36 进制，左补 0；按 (biz_type, 父编号) 分桶，从 1 起 |

类型表补充：

| type | 前缀 | 模式 | 接入点 |
|---|---|---|---|
| TENDER_PROJECT | T | 层级式（20 位 = 父项目编号+3） | ProjectServiceImpl.saveTenderProject |
| BID_SECTION | S | 层级式（23 位 = 父招标项目编号+3） | ProjectServiceImpl.saveBidSection |

分桶：`scope_key = 父编号`（17/20 位 ≤ 列宽 32）；`biz_type` 列区分类型（TENDER_PROJECT 15 字符 ≤ 16）。

接入行为：

- **招标项目**：新建（id 空 + 编号空）→ 以 `reqVO.projectCode`（须已挂接项目，否则报参数错误）为父编号生成；编辑（id 非空 + 编号空）→ 沿用库内原编号。`TenderProjectSaveReqVO.tenderProjectCode` 放宽为可选。
- **标段**：新建 → 以 `reqVO.tenderProjectCode`（须已存在，保留 `BID_SECTION_TENDER_PROJECT_REQUIRED` 校验）为父编号生成；编辑沿用原编号。`BidSectionSaveReqVO.bidSectionCode` 放宽为可选。
- **投资项目统一代码（24 位）**：用户裁定为唯一需要用户输入的编号，`saveProject` 必填校验（`INVEST_PROJECT_CODE` 加入 missingRequired，主列同名字段回填 canonical）。
