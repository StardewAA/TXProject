# 字典/阈值元数据读取权限契约（bidding）——前端请求 + 验收口径（2026-09-14）

> 规范依据：《招投标模块开发规范》§4.4（映射方法必须带 `@PreAuthorize`）、§4.5；
> 用户硬约束：「状态码、枚举值、阈值必须支持动态配置，严禁硬编码」。
> 提出方：管理端前端（招投标页面）。**本文件只描述前端实测到的现象与期望契约，权限模型如何改由后端裁定与实施；
> 前端不改后端代码，也不代为决定权限设计。**
> 关联实现：`txgy-module-bidding/.../controller/admin/meta/MetaController.java`、
> 前端 `apps/web-antd/src/views/bidding/**` 的 `useCertMeta()`（`views/bidding/certificate/useCertMeta.ts`）。

---

## 一、现象（可复现）

`GET /bidding/meta/dicts` 与 `GET /bidding/meta/configs` 的 `@PreAuthorize` 只列了 **5 个电子证照/资质/人员域**权限：

```
bidding:certificate:query  bidding:qualification:query  bidding:personnel:profile:query
bidding:certificate:lifecycle:query  bidding:qualification:permit:query
```

而代码自述与实现不一致：

| 位置 | 原文 |
|---|---|
| `MetaController` 类注释 | 字典/配置是「所有电子证照页面共用的**前置元数据**」，绑死单个权限会让其他域页面拿不到枚举与阈值 |
| `RuleConfigController` 类注释 | 「读（`/bidding/meta/configs`）是业务页面刚需，**登录即可**」 |
| `MetaController#getDicts` 的 `@PreAuthorize` | 实际要求上述 5 个权限之一 |

**结论**：权限模型本身没错，问题是「**全域前置元数据的读取面偏窄**」——它服务于招投标全域页面，却只对电子证照/资质/人员域开放。
只持有其它招投标页面权限的角色调用这两个接口会 **403**。

---

## 二、影响面（前端实测清单，均为招投标页面）

| 页面（`apps/web-antd/src/views/bidding/…`） | 该页实际引用的权限码（实测） | 是否消费字典 | 403 时的表现 |
|---|---|---|---|
| `project/index.vue`（项目台账 + 全景追溯） | `bidding:project:create`、`bidding:project:update`、`bidding:filing:create`、`bidding:filing:update` | 是 | 招标方式/追溯状态列回落英文 code（有降级提示，不白屏） |
| `safety-risk/index.vue`（安许风险联动） | `bidding:project:query`、`bidding:project:update` | 是 | 风险等级/关键岗位回落英文 code |
| `personnel/index.vue`（人员与档案） | `bidding:personnel:alert-run` 等 | 是 | 若账号无 `personnel:profile:query` 则同样回落 |
| `noticeExternal/index.vue`（外部公告管理） | `bidding:notice-external:update` 等 | **是**（2026-09-14 起状态/审核/内容形态字典优先，映射表兜底） | **已受影响**：回落英文 code（有映射表兜底时不退化，但后台改字典文案对该页不生效） |
| `subjectAuth/index.vue`（主体授权） | `bidding:subject-auth:query` 等 | **是**（2026-09-14 起主体类型字典优先，`SUBJECT_TYPE_LABEL` 兜底） | **已受影响**：同上 |
| `crawlExternal/console/index.vue`（采集控制台） | — | 否（同上） | 同上 |

> 前端已实现的降级（不会白屏、不会自造中文）：字典取不到时 `dictLabel/dictTag` 回显原始 code，
> 页面顶部显示「字典/配置未加载，页面按 code 降级展示（功能不受影响）」+「重载字典/配置」按钮。
> **前端不会为了绕开 403 把枚举/阈值写死**——那正是硬约束禁止的做法。

---

## 三、期望契约（请后端二选一裁定）

### 方案 A（推荐，最小改动）：把「招投标全域页面查询权限」补进 `hasAnyPermissions`

即在现有 5 个权限之外，按 `system_menu` 实际码补入其它招投标页面的**查询**权限（以下为前端实测用到的码，供参考，
最终以菜单表为准）：`bidding:project:query`、`bidding:notice:query`、`bidding:notice-external:query`、
`bidding:subject:query`、`bidding:safety-permit:query`、`bidding:rule-config:query`、`bidding:crawl:query`、
`bidding:qualification:standard` 等。

- 不新增权限点，只扩大读取面；
- 风险面：字典/阈值是纯展示与判定参数，不含租户敏感数据（租户隔离仍由拦截器实施）。

### 方案 B（按注释本意）：这两个**读**接口改为「登录即可读」

与 `RuleConfigController` 注释一致；若后端担心面过宽，可仅对 `/bidding/meta/dicts` 放开（枚举对照表最无敏感性），
`/bidding/meta/configs` 维持域权限。

---

## 四、验收口径（后端改完后前端如何验证）

1. 造一个**只带 `bidding:project:query`** 的测试角色 → `GET /bidding/meta/dicts` 返回 200（当前为 403）；
2. 该账号打开项目台账：状态/类型列显示中文，页面顶部**无**「字典/配置未加载」提示；
3. `GET /bidding/meta/configs` 同样 200，且「即将到期」等阈值取自配置而非常量。

---

## 五、前端侧防回归（本轮随契约一并实施）

前端自检脚本新增一条检查：**凡消费字典的前端文件（调用 `useCertMeta()`），其引用的页面权限码必须与
「meta 可读权限集合」有交集**；集合以本契约的最终答复为准写入脚本常量（当前按实现写入 5 个权限）。
现状与「方案 A/B 之前」的既知缺口在脚本内逐条登记并注明"见本契约"，其它情况直接 FAIL ——
避免「新页面用了字典、能打开它的角色却读不到字典」再次静默发生。
