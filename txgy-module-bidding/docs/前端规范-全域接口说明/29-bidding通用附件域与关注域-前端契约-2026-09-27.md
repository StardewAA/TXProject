# bidding 通用附件域 & 关注域 & 草稿宽松 —— 前端契约（2026-09-27）

> 规范依据：《招投标模块开发规范》§4.7 段位表（101=公告与文件）、§5 三-5（文件经 FileApi，库内只记 file_id+sha256+size，URL 非一致性依据）、红线 8（附件三件套）；
> api/vo/AttachmentSetVO（附件集：ATTACHMENT_GUID/SET_CODE/NAME/TYPE/FILE_NAME/URL，URL=社交公开）+ AttachmentItemVO（35 类附件类型字典）；
> 用户裁定 2026-09-24：附件往往不止一个 → 针对主键的专门附件表（一对 N）；以 URL 方式承载、对象存储存储。
> 读者：前端同学。后端接口已实现（编译通过），live 库执行 DDL 后即可联调。

## 一、背景与设计裁定

### 1.1 现状（此前）
- 项目 / 招标项目 / 标段 / 自营公告 **均无附件能力**（仅外部采集公告有：bidding_notice_external_attachment）；
- 数据集规范层面要求附件：ProjectVO / BidSectionVO / TenderNoticeVO 均含 ATTACHMENT_CODE（附件编码）字段，
  且 170 个数据集 VO 普遍带 ATTACHMENT_CODE（报备/开标/评标报告等）；
- 自营公告仅支持版式 PDF（pdfFileId），无通用附件。

### 1.2 用户裁定（2026-09-24）
- **附件往往不只一个** → 针对主键的专门附件表（**一对 N**），按 biz_type + biz_code 关联业务实体；
- 文件以 **URL 方式承载**、以 **对象存储** 方式存储（复用平台 FileApi 对象存储）；
- 标段附件与公告附件**语义不同但机制统一**：公告附件=招标文件/澄清/结果文件；标段附件=技术文件/图纸/工程量清单；共用同一套附件表。

### 1.3 实现方式（对前端的关键点）
- **四实体后端零改动**：附件做成独立绑定式（bidding_attachment 表 + 独立接口），不侵入项目/招标项目/标段/公告的 DO/VO；
- 上传复用已有 `POST /bidding/file/upload`（响应带 fileId/url/sha256），业务落库**一律以 fileId 为准**；
- 附件类型字典 35 类（AttachmentItemVO 字段名照录），前端下拉可选常用项。

### 1.4 文件存储口径澄清（2026-09-18，回应「只存 ID/URL 是否够」）
- **附件行已含足量元数据**：`fileId`（一致性依据）+ `sha256`（防伪指纹/防篡改）+ `size`（字节）+ `fileName`（原始文件名，下载还原）+ `mimeType` + `url`（回显快照，**不作为一致性依据**）+ `virusStatus`；对齐规范「红线 8 / §5 三-5」口径（业务表只以 file_id+sha256+size 为一致性依据，url 可过期失效）；
- **存储是否改名（实测 infra_file 表）**：**不改名**——对象存储路径 = `{业务目录}/{原始文件名}`（例 `bidding/attachment/招标公告.pdf`），`name` 完整保留中文/空格；下载用 `presignGetUrl` 签名 URL + `fileName` 做 Content-Disposition 还原，前端无需拼物理路径；
- **加密密钥为何不存**：《电子招标投标办法》（发改委令第 20 号）第二十六条要求投标文件加密（未加密拒收），但**加解密是文件服务/投标文件组件层职责**（规范红线 8 同口径）；bidding 附件只关联 fileId，**密钥不得入库**——明文密钥反而是泄露面；
- **哈希算法**：现行为 SHA-256（bidding 侧对上传字节计算）；国密化登记为平台/文件服务层增强项（政务合规倾向）——**SM3（杂凑，替代 SHA-256 做防伪指纹）/ SM4（对称加密，投标文件等敏感文件加密）/ SM2（非对称签名，电子签名法第四十条存档）按用途选型，非新旧关系**；本表 `sha256` 列 char(64) 兼容 SM3 长度，跟随 FileApi 演进即可，**前端不感知**（详见待落地清单 §6.4 算法矩阵）。

## 二、接口契约

### 2.1 上传（复用已有，无新代码）

`POST /admin-api/bidding/file/upload`（multipart/form-data）

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| file | file | 是 | 上传文件 |
| directory | string | 否 | 归档目录，缺省 bidding/attachment |

**响应（成功）**：
```json
{
  "code": 0,
  "data": {
    "fileId": 1024,
    "url": "http://127.0.0.1:48080/admin-api/infra/file/4/get/bidding/attachment/xxx.pdf",
    "name": "招标文件.pdf",
    "type": "application/pdf",
    "size": 204800,
    "sha256": "9f2c…"
  },
  "msg": ""
}
```

### 2.2 绑定附件（新增）

`POST /admin-api/bidding/attachment/save`

**鉴权**：登录即可（isAuthenticated()，与上传口径一致）；写操作带 @Idempotent。

**入参**（JSON）：
```json
{
  "bizType": "PROJECT",          // 必填：PROJECT/TENDER_PROJECT/BID_SECTION/ANNOUNCEMENT
  "bizCode": "P20260927001",     // 必填：对应业务编号
  "fileId": 1024,                 // 必填：上传接口返回
  "attachmentType": "TENDER_FILE", // 可选：35 类字典
  "attachmentName": "招标文件",    // 可选：附件集名称
  "url": "http://…",              // 可选：预览用
  "fileName": "招标文件.pdf",      // 可选
  "sha256": "9f2c…",              // 可选
  "size": 204800,                  // 可选
  "remark": "标段一技术文件"        // 可选
}
```

**行为**：同一 (bizType, bizCode, fileId) 幂等——重复绑定返回原行，不重复建行。

**响应**：AttachmentRespVO（见 2.5）。

### 2.3 解绑附件（新增）

`DELETE /admin-api/bidding/attachment/delete?id={id}`

**行为**：逻辑删除；附件行不存在时也返回成功（幂等语义）。响应 `{ code: 0, data: true }`。

### 2.4 查附件列表（新增）

`GET /admin-api/bidding/attachment/list?bizType={PROJECT}&bizCode={P20260927001}`

**行为**：按业务实体一对 N 查询，按 seq 排序。

**响应**：`{ code: 0, data: [AttachmentRespVO…] }`

### 2.5 AttachmentRespVO（附件行）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | long | 附件行主键 |
| bizType | string | PROJECT/TENDER_PROJECT/BID_SECTION/ANNOUNCEMENT |
| bizCode | string | 业务编号 |
| attachmentType | string | 附件类型（35 类字典） |
| attachmentName | string | 附件集名称 |
| fileId | long | FileApi 文件主键（一致性依据） |
| url | string | 对象存储访问地址（SOCIAL 公开预览） |
| fileName | string | 文件名 |
| sha256 | string | 文件指纹 |
| size | long | 字节数 |
| mimeType | string | MIME 类型 |
| virusStatus | string | UNKNOWN/CLEAN/INFECTED（INFECTED 不下发下载 URL） |
| seq | int | 同实体内序号 |
| remark | string | 备注 |
| createTime | long | 创建时间（服务端 LocalDateTime 序列化，形态即 epoch 毫秒 number；对齐 01 号契约时间口径，勿手写 Long） |

### 2.6 附件类型字典（attachmentType 常用项）

35 类全集（照 AttachmentItemVO 字段名原样，含规范拼写瑕疵；attachmentType 传字段名，未知值前端兜底图标即可）：
- `PROJECT_APPROVAL_FILE` 项目审批文件、`TENDER_FILE` 招标文件、`TENDER_FILE_ATTACHS` 招标文件附件、`TENDER_NOTICE` 招标公告
- `OTHER_FILE` 其他文件、`FILE_EX_TDOC` 电子文档（扩展）、`INVITE_DOC` 邀请函、`PUBLICITY_DOC` 公示文件
- `WIN_BID_NOTICE` 中标通知、`CONTRACT_DOC` 合同、`QUALIFICATION_DOC` 资格文件、`PROJECT_SOURCE_PROOF` 项目来源证明
- `Contract_FILE` 合同文件（规范拼写原样）、`TENDER_CHANGE_NOTICE` 招标变更通知、`QUALIFICATION_NOTICE` 资格审查通知、`QUALIFICATION_CLARIFY_FILE` 资格审查澄清文件
- `QUALIFICATION_LIST` 资格审查名单、`BID_SIGN_LIST` 开标签到表、`QUALIFICATION_REPORT` 资格审查报告、`QUALIFICATION_RESULT_NOTICE` 资格审查结果公示
- `NET_QUESTION` 网上提问、`SURVEY_RECORD` 勘察记录、`CONTROL_FILE` 控制价文件、`WIN_NOTICE_FILE` 中标通知书文件
- `APPROACH_PROVE` 进场证明、`EXPERT_REVIEW_FILE` 专家评审文件、`COMMENTS_FILE` 评标意见文件、`QUANTITIES_CLEAR_REPORT` 工程量清单澄清报告
- `WIN_BID_TENDER_FILE` 中标人投标文件、`EVALUATION_REPORT` 评标报告、`CONTRACT_SING_FILE` 合同签订文件、`PERFORMANCE_FILE` 履约/业绩文件
- `INQUIRY_FILE` 质询文件、`OBJECTION_FILE` 异议函、`COMPLAIN_FILE` 投诉函

> **字典状态（2026-09-18）**：已注册 `bidding_dict_data.attachment_type`（35 条，id 段位 710000000000005001 起），执行脚本 `sql/history/2026-09-18-bidding-attachment-type-dict.sql`；

### 2.7 四实体 VO 接线预告（后端协作规范 + 前端预告，待项目域/公告域落地）

> 本附件域采用**独立绑定式**：前端可随时用 2.2 逐条绑定，无需等四实体接线。下列字段是四实体（Project/BidSection/TenderProject/Notice）Save/Resp VO **将来**会新增的
> 出/入参（登记于待落地清单 §1.3c，归属项目域/公告域），此处**预定义字段命名与语义**，保证各域接线后契约一致。

**RespVO 出参**（四个实体各加一个字段）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| attachments | AttachmentRespVO[] | 该实体的附件行（结构=2.5；按 seq 升序） |

**SaveReqVO 入参**（可选；不传 = 不改变附件关系）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| attachments | { fileId: long; attachmentType?: string; attachmentName?: string; remark?: string }[] | 保存时一并绑定的附件；幂等（同 fileId 不重复建行） |

- 前端两种用法二选一：① 实体保存时随 attachments 一并提交；② 实体先存、后用 2.2 逐条绑定（推荐，解耦）；
- 接线实现后本预告即转正；未接线前四实体接口**不返回** attachments 字段（前端勿假定存在）。

## 三、前端接入指引

### 3.1 表单页（项目/招标项目/标段/公告详情）附件区
1. 用户选文件 → 调 `POST /bidding/file/upload` 拿 fileId/url/sha256；
2. 调 `POST /bidding/attachment/save` 绑定（bizType + bizCode + fileId）；
3. 进入详情时调 `GET /bidding/attachment/list` 渲染附件列表（文件名/大小/类型角标）；
4. 删除调 `DELETE /bidding/attachment/delete?id=`（幂等，确认后调）。

### 3.2 下载/预览
- 优先用返回的 url（SOCIAL 公开预览地址）；INFECTED 行不下发 URL，按 fileId 走 FileApi 签名下载；
- 建议新增 api 模块 `src/api/bidding/attachment/index.ts`，封装 save/delete/list 三函数。

### 3.3 关注域 UX 建议（同轮通知）
> 关注域**接口契约**见《10-外部公告关注与我的关注页-前端交付》（targetType/targetKey 表 + status/follow/unfollow/item/page/timeline/read 全接口）与《04-全链路接口说明》C1-C5；本节仅登记 UX 建议。
- 公告详情页现在有「＋ 关注」（ANNOUNCEMENT）、「＋ 跟踪该项目」（PROJECT，BR-1）、「＋ 关注该标段」（SECTION）三个按钮，
  均调同一个 `POST /bidding/notice-follow/follow`（只是 targetType/targetKey 不同）；建议收敛为**单一主按钮**（默认 ANNOUNCEMENT），
  项目/标段关注折叠进「更多」；关注页按 followType 分组并明示组标题。

### 3.4 草稿宽松（提前知悉，后端待落地）
- 现状：项目/招标项目/标段 save 时强制校验名称/投资代码 → 草稿无法保存；
- 已裁定：**草稿阶段不做必填校验**（新建即落库空白草稿，仅系统生成编号），必填唯一强制点 = 状态流转事件（提交审批/发公告前）；
- 对前端：新建允许无名称保存；必填提示移到提交审批/发布时；INVEST_PROJECT_CODE 不再创建必填（审批通过后登记）。

## 五、验收清单（给前端）

- [ ] 上传文件 → 拿到 fileId 绑定成功（bizType+bizCode+fileId）；
- [ ] 同一文件重复绑定 → 返回原行（幂等，不重复）；
- [ ] 详情页 list 返回附件列表，字段齐全（含 virusStatus/seq）；
- [ ] 删除附件 → 列表消失；重复删除不报错；
- [ ] INFECTED 附件不下发 URL（无下载入口）。
