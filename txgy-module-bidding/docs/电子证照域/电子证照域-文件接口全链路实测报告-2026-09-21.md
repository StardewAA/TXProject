## 三、本次修复的 4 个问题

### 【严重】1. 所有 `*Name` 中文名字段**恒为 null**（影响全部读接口）

- **现象**：列表里 `certTypeName`/`certStatusName`/`certCategoryName`/`fileCategoryName` 全是 `null`。
- **根因**：`CertDictHelper` 调框架 `DictFrameworkUtils`，而它**只读 `system_dict_data`**；
  电子证照域字典实际注册在本模块 **`bidding_dict_data`**（实测：system 表 cert* **0 行**，bidding 表 **32 行**），
  两表之间没有同步桥 → 解析**必然 miss**。
- **为什么一直没发现**：`CertDictHelper` 的设计是"容错返回 null"，本意是"字典偶发不可用别让接口 500"，
  结果把这种**永久性错配**伪装成了"偶发故障"，看起来完全正常。
- **修复**：`CertDictHelper` 改为 Spring 组件，**直接读 `bidding_dict_data`**
  （平台租户 0 打底 + 当前租户覆盖，与 `MetaDictServiceImpl` 同口径）。
- **实测**：`营业执照` / `正常` / `身份类` / `原件` —— 中文名真正出来了。

### 【严重】2. CA 签章与 CA 共享组件**互斥**（一个开关管两件事）

- **现象**：`/bidding/ca/seal/document` 与 `/callback` 直接 **500**。
- **根因**：签章代码写「`bidding.ca.sdk.enabled=true` 就必须走官方 document 签发接口」，
  而 R3 签发调起参数**又必须**读到 enabled 携带的凭证 → 两者共用同一开关，
  **开启官方组件就把本地测试签章打死**（我上次为对接组件开 enabled 时踩的）。
- **修复**：拆出 `bidding.ca.sdk.seal-enabled` 专管"签章走哪条路"，`enabled` 只管"凭证/组件连通"。
  默认沿用原行为（false=本地测试签章），本地签章恢复可用。
- **实测**：`seal-enabled` 默认 false 时签章正常，且 `enabled=true` 的 R3 凭证不受影响。

### 3. `demo-seed`/`demo-tamper` 500（注释与代码自相矛盾）

- 方法注释写「PDFBox，**ASCII 文本避免字体依赖**」，但代码里混了一句中文；
  `PDType1Font.HELVETICA` 是 WinAnsiEncoding 内置字体、不含中文字形 →
  `IllegalArgumentException: U+62DB ('.notdef') is not available in the font Helvetica`。
- 已改回纯 ASCII 并留注释：中文需嵌入 TTF 字体，演示 PDF 不值得引依赖。

### 4. 个人解密人缺身份证哈希**未被拦**

- 契约写「`decryptionUserType=01`（个人）时 `idCardHash` 必填」，但**只写在注释与文档里，代码不校验**：
  实测传 01 不传 hash **照样生成二维码**，问题要到用户扫码那一步才暴露，且组件侧报错语焉不详。
- 已在入口校验：缺 hash 直接返回明确错误；传了 hash 正常；机构 02 无 hash 仍正常。

## 六、补充：自测中发现的自身疏漏（已修）

已补 `@NotNull`，现在缺参返回 400。记此一条以提醒：**文档标注 ≠ 校验**。
