## 一、结论：放在哪里

**不是**放到后台「知识库管理」里当 TEMPLATE 材料，而是放到 **Node 编排服务的内置模板目录**：

| 文件 | 目标位置 | 说明 |
| --- | --- | --- |
| `投标标书_合并.docx` | `services/bid-agent-service/templates/投标标书_主模板.docx` | 平台级内置模板 |
| `投标标书_变量字典_合并.md` | `services/bid-agent-service/templates/投标标书_变量字典.md` | 配套人读文档 |
| **（需新建，脚本生成）** | `services/bid-agent-service/templates/bookmark-dict.json` | **机器可读字典**，见改动 2 |

配置入口（`.env`，已验证 `.env.example` L79 已有 `BID_TEMPLATE_DOCX=`）：

```bash
# 指向新模板；留空则回退到默认的 投标文件模板.docx
BID_TEMPLATE_DOCX=templates/投标标书_主模板.docx
```

### 为什么是这里，而不是知识库管理

系统里有两套并存的模板概念，必须先分清：

| 概念 | 载体 | 作用域 | 代码位置 |
| --- | --- | --- | --- |
| 平台级内置模板 | Node 服务本地文件 | **全局唯一** | `config.docx.templatePath` |
| 租户级模板材料 | 知识库材料（`docType=TEMPLATE`） | 按租户 | 编排任务携带的 `templateId` |

本次需求是「后续所有标书统一用这一套版面」→ 属**平台级**，走前者。

若放进知识库当 TEMPLATE 材料，反而要每个租户各传一份；且 `BidDocxExporter` 优先读的是 `config.docx.templatePath`，会造成「传了但不生效」。

关键代码（当前工作区实测，行号以现行代码为准）：

```ts
// services/bid-agent-service/src/config.ts L226-229
docx: {
  pdfViaWord: bool('PDF_VIA_WORD', false),
  templatePath: str('BID_TEMPLATE_DOCX', '') || path.join(SERVICE_ROOT, 'templates', '投标文件模板.docx'),
},
```

```ts
// services/bid-agent-service/src/export/bidDocxExporter.ts L133-154（模板优先分支）
const templatePath = this.config.docx.templatePath;
```

## 三、好消息：新模板与现有回填引擎天然兼容（已验证）

字典文档第 14 行明确了模板的占位设计口径：

> 空白单元格内是**零长度书签**（`bookmarkStart` 与 `bookmarkEnd` 相邻），不含任何可见字符。

这正好命中 `bookmarkFill.ts` 已实现的**形态 2（空书签）**：

```ts
// services/bid-agent-service/src/lib/bookmarkFill.ts（fillRegion 内，形态 2）
if (runs.length === 0) {
  const rPr = extractParaRPr(seg);
  const run = `<w:r>${rPr}<w:t xml:space="preserve">${escapeXml(value)}</w:t></w:r>`;
  return { xml: xml.slice(0, endStart) + run + xml.slice(endStart), hit: true };
}
```

字典第 22 行的「按基础变量名统一回填（填 `bidder_name` 自动覆盖 `bidder_name_2`）」也已实现（`stripVariantSuffix`）。

**所以回填引擎本身不需要改。** 但四处必须动，否则结果达不到预期。

## 四、四处必须改动

### 改动 1：模板路径切换（0.5 人日）

改 `config.ts` 的默认值，或只用 `.env` 覆盖。

推荐**保留代码默认值不动**，通过 `.env` 指定，便于回滚与多环境切换。

### 改动 2：字典必须从「文档」变成「配置」——**脚本生成，1-2 人日**（v1 为 3-5 人日）

**现状**：映射关系硬编码在代码里，只覆盖约 50 条（`bookmarkFields.ts` 的 `BOOKMARK_STD_MAP`）。而新字典有 **1,334 个书签**。

**改进点（相对 v1 的核心压缩）**：合并字典 `.md` 本身已是结构化表格（变量名 / 含义 / 位置，2.0~2.21 共 22 个小节），**不需要手工编写 1334 条 JSON**。写一个解析脚本（Node/Python 均可）：

1. 按 `### 2.x` 小节边界切分章节，提取 `| \`变量名\` | 含义 |` 表格行；
2. 从「含义」列的「表格第 N 行第 M 列」文本正则提取 `table`/`row`/`col`；
3. 按前缀归类 `kind`（`scalar` / `table-cell`）与 `source`（`TENDER` / `FACT` / `PRICING` / `STAFF` / `DERIVE` / `MANUAL`）；
4. 生成 `bookmark-dict.json`，并输出「字典名 vs 模板实际书签」差集报告。

实测此路径已走通：从 `.md` 解析出 1336 个变量名，对模板 1334 个书签 **0 遗漏**。

建议 JSON 结构（同 v1，补充 `note` 字段）：

```json
{
  "version": "2026-09-22",
  "template": "投标标书_主模板.docx",
  "bookmarks": [
    { "name": "bid_no", "label": "招标编号", "chapter": "封面", "kind": "scalar", "source": "TENDER|FACT" },
    { "name": "bill_2_code", "label": "第1行 项目编号", "chapter": "表5", "kind": "table-cell",
      "table": "bill", "row": 3, "col": 2, "source": "PRICING",
      "note": "行号=Word表格行序号（表头第0行）" }
  ]
}
```

要点：

1. `kind` 区分 `scalar` 与 `table-cell`，后者带 `table`/`row`/`col`；
2. `source` 标注数据来源通道（见第五章），支撑自动路由；
3. `version` 用于启动时与模板书签做一致性校验（改动 4）；
4. `note` 保留模板细节防误填：表9 第 3/4 行预填固定文案（回填写回等值）、表4 第 6-15 行备用行、表1 与一/五共用书签等；
5. `bookmarkFields.ts` 从「硬编码常量」改为「读 `bookmark-dict.json`」（标量部分），表格部分由改动 3 的通道消费。

### 改动 3：补上「计价表数据通道」（6-10 人日，v1 为 5-8 人日）——决定能否达到预期

这是最实质的缺口。实测新模板 **约 92% 的书签是计价表数据**（约 1,229 个），而系统**完全没有这类数据的来源**。

现有字段来源通道：

| 通道 | 含义 | 是否经模型 |
| --- | --- | --- |
| 标准字段命中（企业事实/招标解析，中文名精确匹配） | 现 `bookmarkFields.buildBookmarkValues` | 否 |
| `DERIVE`（确定性换算，`valueRules.ts`：大写金额、日期拆分/推算） | 已实现 | 否 |
| `GENERATE`（检索 → 生成 → 校验） | 编排侧 | 是 |
| `MANUAL`（签字/盖章） | Agent 不碰 | 否 |

但 `analysis_*`（人工费/材料费/机械费/管理费/利润/风险）、`bill_*`（工程量清单综合单价）、`material_*`（材料价格）等，**是投标人自己编制报价的产物**，不可能从招标文件里抽取，也不属于企业事实库。

**必须新增一条导入通道**，v1 方案正确，改进版明确三步：

1. **先定标准 Excel 模板**（最关键的一步）：为 12 张计价表各定一张同列结构的 Excel（列名与字典「含义」一致，如 序号/项目编号/项目名称/计量单位/工程数量/综合单价/合价）。**不要直接啃计价软件原生格式**（GBQ 等多样且不稳定），先支持标准 Excel，原生格式后置；
2. Java 侧：后台「知识库管理 → 资料管理」新增材料角色 `PRICING`（报价数据），解析 Excel 写入结构化表；
3. Node 侧：编排新增 `COPY_PRICING` 通道，按 `bookmark-dict.json` 的 `table/row/col` 映射 Excel 行 → 书签名（`bill_2_*`…）回填。

```
TENDER    招标文件
FACT      企业资料
TEMPLATE  技术母本
PRICING   报价数据   ← 新增
```

### 改动 4（改进版新增）：「废标红线」一致性防线（0.5-1 人日）

`bid_total`（投标总价）在封面、投标函、表1、表5 等多处共用同名书签；`bidder_name`、`project_name`、`date_*` 同理（字典「共享变量说明」已列明）。回填时按名统一取值天然满足「单一数据源」，但**必须把校验自动化**，否则报价不一致直接废标：

1. 回填后抽取关键共享变量的**全部出现处**，做全等断言（`bid_total`、`bid_total_upper`、`bidder_name`、`project_name`、`date_year/month/day`、`duration_days`、`quality_standard`）；
2. 断言失败 → 交付前告警拦截；
3. 作为交付流水线（deliver 前）的固定校验步骤，脚本化成本半天（该检查逻辑已在模板审计中验证可行）。

> 注：v1 引用的 `fillTask.ts mergeFields` 已随该文件删除而不存在，一致性现由「按名统一取值」机制隐式保证；改动 4 把隐式保证升级为显式校验。

## 七、风险提示（改进版更新）

### 风险 1：回填性能 —— **降级为可选项（v1 为 P3 必做）**

v1 估计复杂度 O(书签数 × XML 长度) ≈ 10⁹ 字符操作。**实测全量回填 1.29 秒**，单次生成完全可接受。仅当出现高并发批量生成场景时再优化（单遍扫描建索引，半天工作量），不需要复杂方案。

### 风险 2：表格行数固定 —— **升级为程序化预扩展（v1 仅"截断告警"）**

模板中 `bill_2…bill_12`（11 行）、`analysis_3…analysis_22`（20 行）、`material_1…material_23`（23 行）、`staff_2…staff_15`（14 行）等均为**预排固定行数**。改进版策略：

1. 首选：**程序化预扩展模板**——用已验证的模板操作脚本克隆末行、重命名书签（`bill_13_*`、`bill_14_*` …），按业务需求生成「N 行版」模板（如 50 行/100 行版）；XML 层面克隆 `w:tr` + 书签改名技术已验证可行；
2. 次选：回填后按表格动态插入行（同样可行，略复杂）；
3. 兜底：超限截断并告警。

P2 启动时对两种方案做一次实测选型。

### 风险 3：跨字段一致性（废标红线）—— **由改动 4 的断言显式保障**

`bid_total` 等共享变量多处出现，回填按名统一取值（单一数据源），但必须**显式校验**：交付前对关键共享变量的全部出现处做全等断言，不一致即拦截告警。v1 引用 `fillTask.ts mergeFields` 已过时（文件已删除），现由改动 4 承接该职责。

### 风险 4：字典版本管理

字典「变更记录」已记录 2026-09-22 的三项修复（表8 书签去重 `daywork_material_*`、表8/表9 字号 36→24、仿宋字体替换）。`bookmark-dict.json` 带 `version` 字段，**服务启动时校验**「模板实际书签集合」与「字典声明书签集合」一致，不一致则告警。生成脚本输出的差集报告即为此校验的离线版。
