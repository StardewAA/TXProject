# 下载限速与合规频控设计（原文文件下载）（2026-09-10）

> 规范依据：《外部信息获取 v1.0》§六（消费端执行）、§11（增量回溯与频控）；
> 用户口径 2026-09-10：「下载器的时间间隔（Sleep/Delay）必须且只能作用于『下载公告原文文件』这一动作」
> 「每次下载原文文件之前，必须强制执行休眠等待，严禁无间隔高频请求」
> 「排队中的任务绝对不允许直接触发下载；必须确保任务按顺序流转，且每次下载前都经过合规的间隔控制」。

---

## 一、重构前的问题（逐条取证，不靠推测）

| 编号 | 问题 | 证据位置 | 后果 |
|---|---|---|---|
| P1 | **同步直抓路径无间隔连发下载**：列表条目循环里直接下载 GX 详情页 + 公告原文 PDF，只有 `entry-delay-ms: 1500` | `CrawlSourceRunner.ingestGxEntry`（原 `httpFetchClient.getText(detailUrl)` / `getBytes(pdfUrl)`） | 这就是"一有任务就直接发起下载请求"；`async-mode=false` 时必然高频请求目标站点 |
| P2 | **PDF 批量回填完全无间隔**：`for` 循环里逐份从目标站点下载 PDF | `NoticeExternalServiceImpl.backfillPdfDownloadUrls`（原 `httpFetchClient.getBytes(externalUrl)`） | 本模块最严重的频控缺口：管理端点一次即可对目标站点连发 N 次请求 |
| P3 | **限速位是进程内易失变量**：`volatile long lastConsumeAtMs` | `CrawlNoticeFetchMessageListener` | ① 进程重启即归零 → 重启后第一条消息立刻下载；② 多实例各自计时 → 聚合速率 ×N；③ 不落库、不可审计 |
| P4 | **限速作用在"任务调度"而非"下载动作"**：闸门在任务执行前判断 | 同上 `executeIfDue` | 纯本地处理任务（列表已带全文）也白扣间隔，而下载本身没有被约束到具体动作 |
| P5 | **消息"谁的消息谁执行"，可乱序** | 同上 `onMessage → executeIfDue(message.getTaskId())` | 新入队任务可越过队列先下载，与"排队中的任务不允许直接触发下载"冲突 |
| P6 | **同一任务可被并发执行**：`markRunning` 为无条件"读-改-写" | `CrawlTaskServiceImpl.markRunning` | 并发/多实例下同一任务被两个执行者下载 → 对目标站点重复请求 |
| P7 | `GenericHttpDownloadChannel.download` 下载前无限速（当前无运行时调用方，但属"下载原文文件"执行点） | `GenericHttpDownloadChannel` | 一旦接线即成为违规路径 |

> 说明：用户所述"任务生成后直接下载原文文件"在**异步模式**下并不成立（消费端原本就有一条 5 分钟节流闸）；
> 真正成立且更严重的是 P1/P2 两条**完全绕过闸门**的路径，以及 P3~P6 的闸门自身缺陷。本次一并修掉。

## 二、重构后的架构：一个闸门，落在下载动作之前

```
                         ┌──────────────────────────────────────────┐
  消息（唤醒信号） ──────► │ CrawlNoticeFetchMessageListener          │
  30s 兜底扫描 ─────────► │ consumeOldestDue()：按 id 升序取最老到期   │
                         │  PENDING → tryMarkRunning（条件抢占）      │
                         └───────────────┬──────────────────────────┘
                                         ▼
                         CrawlNoticeProcessor.execute(task)
                                         │
                     「本次是否要下载原文？」── 否（payload 带 contentHtml）→ 纯本地处理，不占闸
                                         │ 是
                                         ▼
                ┌────────────────────────────────────────────────┐
                │ CrawlDownloadGate.tryAcquire(...)   ← 唯一限速点 │
                │  条件 UPDATE 原子占位（表 bidding_crawl_download_gate）│
                │  未到间隔 → 抛 CrawlDownloadNotDueException      │
                └───────────────┬────────────────────────────────┘
                                ▼ 获准后才发起 HTTP
                 平台归档 rawFileUrl / 详情页 HTML / 详情页内 PDF 直链
```

### 2.1 限速闸（`CrawlDownloadGate`）

- **唯一真相**：表 `bidding_crawl_download_gate` 的 `last_download_at`（G 轨，无租户列）。
- **原子占位**：`UPDATE ... WHERE scope_key='GLOBAL' AND (last_download_at IS NULL OR last_download_at <= NOW() - INTERVAL ? SECOND)`；
  InnoDB 行锁保证并发下只有一条 UPDATE 命中（`affected=1`），**跨实例、跨重启**均有效，无需分布式锁组件。
- **生效间隔** = `max(bidding.crawl.runner.consumer-delay-ms, 源 fetch_interval_seconds × 1000)`，且**不低于 120 秒**（合规下限，防配置被改小而失效）。
- **失败关闭**：闸门表缺失/不可用 → 抛异常拒绝下载（提示执行 `sql/history/2026-09-10-crawl-download-gate.sql`），
  **不会退化成"无限速照跑"**。这是刻意的取舍：宁可停，不可违规。
- **一次占位 = 一份原文**：详情页与其 PDF 直链属同一份公告原文的取回过程，只占一次闸位（否则间隔被重复消耗）。

### 2.2 各下载路径的行为矩阵

| 路径 | 触发者 | 未到间隔时的行为 |
|---|---|---|
| 异步消费端（`CrawlNoticeProcessor`） | 消息唤醒 / 30s 扫描 | 抛 `CrawlDownloadNotDueException` → 任务回 PENDING，`next_retry_time`=可下载时刻，**不计**失败次数、不进死信 |
| 同步直抓（`CrawlSourceRunner.ingestGxEntry`） | 人工/调度 run（`async-mode=false`） | `acquireBlocking` 就地等待（每 60s 打进度日志），等待到位才下载 |
| PDF 批量回填（`backfillPdfDownloadUrls`） | 管理端点 | `tryAcquire` 失败即**跳过本条**并计入 `skipped`（不下载、不改数据），避免管理端请求被 N×interval 挂死；到点后重跑接口即可 |
| 通用下载通道（`GenericHttpDownloadChannel`） | 通道 SPI（当前未接线） | 抛 `CrawlDownloadNotDueException`（与消费端一致语义） |
| 列表/翻页/接口拉取 | 生产端 | **不限速对象**（不是"原文文件下载"），仍由 `page-delay-ms`（60s）控制 |
| 纯本地处理（列表自带全文） | 消费端 | **不占闸位**（没有下载动作）——间隔只花在真正的下载上 |

### 2.3 状态流转约束（排队中的任务不允许直接下载）

- 消息改为**纯唤醒信号**：`onMessage` 不再执行"消息里的那个 taskId"，而是与 30s 扫描共用
  `consumeOldestDue()`：`status=PENDING AND (next_retry_time IS NULL OR <= now)` 按 **id 升序**取一条 → 顺序流转。
- 执行权用条件更新抢占：`tryMarkRunning`（`UPDATE ... WHERE id=? AND status='PENDING'`），失败即放弃本次执行；
  同一任务不会被两个执行者重复下载（P6）。
- 未到间隔不是失败：`releaseToPending`（仅 `RUNNING → PENDING`）保留 `attempt` 不变，写入
  `message='WAIT_DOWNLOAD_INTERVAL …'` 便于审计"是在排队而不是在失败"。
- 单实例内的并发（扫描线程 vs 消息线程）由 `AtomicBoolean consuming` 互斥；跨实例由 DB 条件更新保证。

### 2.4 变更记录（2026-09-10 后续调整）

- **下载间隔 5 分钟 → 2 分钟**（`consumer-delay-ms: 120000`）；2 分钟即合规下限（`MIN_INTERVAL_SECONDS=120`）。
- **闸门取值修正**：原先 `interval = max(consumer-delay-ms, 源 fetch_interval_seconds)`，
  而源表值是 300s → 改配置也不生效（仍 5 分钟）。现改为**只认下载间隔配置**：
  `fetch_interval_seconds` 只控制调度器多久触发一轮采集，两个旋钮不再互相打架。
- 同轮补齐的爬虫缺陷（反爬三态异常/robots/单文件上限/完整性校验/下载审计/存储状态校验）见
  `docs/开发联调与运维/爬虫测试与监控指标-2026-09-10.md`。

## 三、运维须知

1. **必须先建表**：`sql/history/2026-09-10-crawl-download-gate.sql`（已并入 `sql/master-bidding-sync.sql` 第 ⑩ 节）。
   未建表时下载器**失败关闭**，日志会明确提示执行该脚本。
2. **配置**：`bidding.crawl.runner.consumer-delay-ms`（默认 300000=5 分钟）为最小间隔；
   源级 `bidding_fetch_source.fetch_interval_seconds` 更大时取更大值；两者都低于 120 秒时按 120 秒执行。
3. **观察限速是否生效**：
   ```sql
   SELECT scope_key, last_download_at, last_task_id, last_url FROM bidding_crawl_download_gate;
   -- 相邻两条原文下载的时间差应 >= 生效间隔；last_url 即最近一次下载地址（可审计）
   SELECT id, source_code, status, next_retry_time, message, started_at, finished_at
     FROM bidding_fetch_task ORDER BY id DESC LIMIT 20;
   -- 等待间隔中的任务：status=PENDING 且 message LIKE 'WAIT_DOWNLOAD_INTERVAL%'
   ```
4. **日志关键字**：`[download-gate] 放行下载`（放行）、`[download-gate] 等待合规下载间隔`（同步路径等待）、
   `[releaseToPending]`（任务回队）、`未到合规下载间隔`（消息/扫描期的拦截）。
5. **归零重爬**：`sql/tools/reset-crawl-to-zero.sql` 会把闸位 `last_download_at` 置空（首条下载不必等待历史时间戳）。
