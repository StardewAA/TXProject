## 一、本轮缺陷修复清单（缺陷 → 修复 → 位置）

| 编号 | 缺陷（修复前） | 修复 | 位置 |
|---|---|---|---|
| B1 | 抓取异常只有一根 `IOException`：404/403/429/超时一视同仁，重试策略无从下手，也无视 `Retry-After` | 三态异常 `FetchException.Transient/AntiCrawl/Permanent` + 尊重 `Retry-After` | `fetch/FetchException.java`、`fetch/HttpFetchClient.java` |
| B2 | 反爬识别缺失：拦截页（验证码/访问频繁）被当正文入库 | 状态码（403/429/503）+ 正文特征词双重识别 → 抛 `AntiCrawl`，不落库 | `HttpFetchClient`（ANTI_CRAWL_MARKERS） |
| B3 | robots.txt 从未真正检查（`robots_ok` 字段形同虚设） | `RobotsGuard`：按 host 缓存解析 `Disallow/Allow`（最长匹配），抓取前检查 | `fetch/RobotsGuard.java` |
| B4 | 无单文件上限：被灌大文件会撑爆内存/带宽 | 流式读取边读边计数，超 `max-download-bytes`（默认 50MB）立即中断 | `HttpFetchClient.readCapped` |
| B5 | 下载文件不做完整性校验：0 字节、截断 PDF、错误页都能落库 | `DownloadIntegrityValidator`：空/超限/格式（`%PDF-`+ `%%EOF`、图片魔数）/过短/错误页/乱码 六类判定 + sha256 | `validate/DownloadIntegrityValidator.java` |
| B6 | 无下载速度监控、无下载台账 | `CrawlDownloadAuditor` + 表 `bidding_crawl_download_audit`：量/速/摘要/结论/存储状态 | `audit/CrawlDownloadAuditor.java` |
| B7 | 存储状态不校验：`createFile` 返回 URL 就写死 `fileStatus=REGISTERED` | 归档后 `getMetadataByUrl` 回查 `file_id` 与字节数，回填**真实**状态与 `pdfFileId` | `CrawlNoticeProcessor.uploadPdfArchive`、`CrawlSourceRunner.uploadPdfArchive` |
| B8 | 摘要两处各算一次（易口径不一致） | 统一由校验器产出（落库 sha256 与审计 sha256 同源） | 同上 |
| B9 | 下载间隔 5 分钟过长 | 调整为 **2 分钟**（120000ms）；并把闸门取值改为**只认下载间隔**（原先与源 `fetch_interval_seconds=300` 取 max，导致改成 2 分钟也不生效） | `application.yaml`、`throttle/CrawlDownloadGate.java` |

> 说明：限速点位与排队次序（限速只作用于"下载原文文件"、消息=纯唤醒信号、按 id 升序消费、未到间隔回 PENDING 不计失败）
> 已在上一轮的《下载限速与合规频控设计-2026-09-10.md》完成，本轮只做上述缺陷补齐。

## 三、监控指标（严格口径）

### 3.1 下载速度监测

| 指标 | 定义 | 数据来源 | 告警阈值 |
|---|---|---|---|
| 单次下载速率 | `speed_bps = byte_size × 1000 / duration_ms` | `bidding_crawl_download_audit.speed_bps` | > `speed-warn-bps` 或 < `speed-slow-warn-bps` → `[download-monitor][速度偏高/偏低]` WARN |
| 单次下载量 | `byte_size` | 同上 | > `max-download-bytes` → 下载即中断（`FAIL_TOO_LARGE`） |
| 单位时间总下载量 | `SUM(byte_size)` 按小时聚合 | 审计表 | 用于带宽趋势（对比 2 分钟/条的预期上限） |
| 下载条数节奏 | 相邻两条放行的时间差 | `bidding_crawl_download_gate.last_download_at` | 必须 ≥ 120s（否则视为限速失效，最高优先级缺陷） |

### 3.2 文件完整性与状态监测

| 指标 | 定义 | 判据 |
|---|---|---|
| 完整性结论分布 | `integrity_verdict` 计数 | `PASS` 占比；任何 `FAIL_*` 都要能追到原因（`message`） |
| 摘要留痕率 | `sha256 IS NOT NULL` 占比 | 原文下载应 100%（红线 8） |
| 文件大小一致性 | `byte_size` vs `bidding_notice_external.pdf_size` | 差值为 0；不等即传输截断/二次加工 |
| 格式合规 | PDF：`%PDF-` 头 + `%%EOF` 尾；图片：魔数 | 不合格 → `FAIL_FORMAT`，不入库 |
| 存储状态 | `storage_status`/`file_id` | 归档后应为 `REGISTERED` 且 `file_id` 非空；`FAILED` 需人工排查（保留外站直链兜底） |
| 内容有效性 | 文本去标签后字符数 ≥120；错误页/乱码特征 | 不通过 → `FAIL_TEXT_TOO_SHORT`/`FAIL_ERROR_PAGE`/`FAIL_MOJIBAKE` |

### 3.3 链路健康

| 指标 | 查询 |
|---|---|
| 队列分布 | `SELECT status, COUNT(*) FROM bidding_fetch_task GROUP BY status` |
| 等待限速的任务 | `message LIKE 'WAIT_DOWNLOAD_INTERVAL%'`（正常现象，非失败） |
| 反爬拦截 | 任务 message 含「疑似反爬拦截」/审计 `FAIL_DOWNLOAD` + 日志 `AntiCrawl` |
| 死信 | `status='FAILED'`（attempt≥3）需人工复核 |

## 五、异常处置预案

| 现象 | 判定 | 处置 |
|---|---|---|
| 大量 `AntiCrawl` | 目标站点已识别爬虫 | 立即停源（`enabled=0`），把 `consumer-delay-ms` 调大并复核 UA/Referer 合规性，人工确认后再启 |
| `FAIL_EMPTY` 集中出现 | 站点收紧鉴权（如 GX 的 `openFileById` 需登录） | 补登录态（Cookie）或改免登接口；**不要**用空体占位入库 |
| `FAIL_FORMAT` 集中出现 | 站点改版/直链规则变化 | 用解析器测试接口取样本校准（`POST /bidding/crawl-parser/test`） |
| `storage_status='FAILED'` | 平台文件服务异常 | 检查 infra/file 服务；公告仍可经外站直链兜底展示，待服务恢复后可重跑归档 |
| 放行间隔 <120s | 限速失效（严重） | 检查闸表是否存在/被清空；闸门不可用时系统是**失败关闭**（拒绝下载），若出现放行则属缺陷，立即停源排查 |

## 八、专项复查结论（2026-09-11，用户指定 6 项）

### 8.1 robots 拦截该不该抛异常 —— **不该按"失败"抛，已改为 SKIPPED + 前置判定**

原实现两处缺陷（均已修）：
1. **判定太晚**：闸位在 `CrawlNoticeProcessor.execute()` 开头已占，robots 判定在其后的 `executeHtmlDetail()` 里 → 被 robots 禁止的页面照样消耗一个 2 分钟合规额度；
2. **语义错**：抛 `IllegalStateException` 被监听器当普通异常 → 重试 3 次（同一禁止页面必然次次失败）→ 进死信转人工审核，把"合规跳过"伪装成"站点故障"。

修复：
- 新增 `CrawlSkipException`（`service/externalfetch/CrawlSkipException.java`）：规则性跳过，不是失败；
- `CrawlNoticeProcessor.execute()`：**robots 预检前移到占闸之前**，命中即抛 skip；
- `CrawlNoticeFetchMessageListener`：新增 `catch (CrawlSkipException)` → `CrawlTaskService.markSkipped()` 置 `SKIPPED` 终态（INFO 日志，不计失败、不进退避、不进死信）；
- `CrawlSourceRunner` 同步路径：robots 判定移到 `acquireBlocking()` 之前，并把该类异常计 `skipped`（新增 `CategorySummary.skipped` / `CrawlRunStats.totalSkipped`），失败率不被"永远抓不到的页面"污染。

### 8.2 robots 有没有缓存 —— **有，且失败结果同样入缓存**

- `RobotsGuard.rulesOf(origin)`：`ConcurrentHashMap` 按 `scheme://host` 缓存，TTL = `bidding.crawl.http.robots-cache-minutes`（默认 **360 分钟**）；
- 关键点：`load()` 捕获异常后返回 `Rules.empty()`，**同样 `cache.put(...)`** → robots.txt 404/超时不会导致"每个任务都去取一次"；实测 `qyzb.shccmg.com/robots.txt` 为 404（fail-open 放行），该结果被缓存 6 小时；
- 处理器内层与 runner 的二次检查命中缓存，不产生额外请求；
- 可关闭：`bidding.crawl.http.robots-enabled=false`；非 http(s)（平台内部文件服务）直接放行。

### 8.3 会不会频繁抓取导致被封 —— **不会，请求预算如下**

| 请求类型 | 实际节奏 | 依据 |
|---|---|---|
| robots.txt | 每 host **6 小时最多 1 次**（含失败结果缓存） | `robots-cache-minutes=360` |
| 列表页/列表接口 | 每源 `fetch_interval_seconds`（300s）+ 翻页间隔 60s | runner 配置 |
| **详情页 HTML（原文）** | **全局每 120 秒最多 1 次** | 闸表 `bidding_crawl_download_gate` 单行原子占位 |
| 详情页内 PDF 直链 | 与详情页共用**同一次**占位（同一份原文只占一次） | 同上 |
| 平台归档/文件服务（内网 48080/48088） | 不占站点额度（不是目标站点流量） | 内部地址 |
| 在线预览的外站直链回退 | **修复前不过闸 = 合规旁路**；现改为 `tryAcquire`，未到点直接 404 | 本次修复（`NoticeExternalServiceImpl.pdfContent`） |
| 批量回填 PDF 直链 | `acquireBlocking` 阻塞等待到位 | 早前修复 |

结论：对目标站点的最大速率 ≈ 0.5 次/分钟（原文）+ 0.2 次/分钟（列表）+ robots 6h/次，实测 ≈0.008 req/s，
不存在触发封禁的请求压力；反爬拦截（403/429/`Retry-After`/验证码页）另有 **10 分钟冷却下限**（见 8.4）。

### 8.4 fetch 是否有超时与重试 —— **超时齐全；重试在任务级，并已尊重站点冷却**

- 超时（`bidding.crawl.http.*`）：`connect-timeout-seconds=10`、`read-timeout-seconds=20`、`download-timeout-seconds=60`；
  单请求 `.timeout()` = max(read, download) = 60s；单文件上限 `max-download-bytes=50MB`（流式读取超限即断，防灌爆内存/带宽）；
- 重试：**任务级**而非单请求级（避免在一个请求里连发）——`handleFailure` 指数退避 120s / 240s，累计 3 次 → FAILED 转人工审核；
  未到闸位抛 `CrawlDownloadNotDueException` → 回 PENDING 排队，**不计**失败次数；
- 本次修复：新增 `handleFailure(taskId, cause, retryAfterSeconds)` —— 实际等待 = max(指数退避, 站点 `Retry-After`)；
  反爬类（`FetchException.AntiCrawl`）冷却下限 **600 秒**（被警告后绝不在 2 分钟内又敲同一站点）；
- 线程中断：`InterruptedException` 恢复中断标记并抛出（不吞），避免线程池静默卡死。

### 8.5 parserCode 兜底是否用 hasText —— **修复前有两处没用，已全部改为 hasText 口径**

修复前（只判 `== null`，空串/纯空白会穿透兜底）：
- `execute()`：`task.getParserCode() == null ? task.getChannelCode() : task.getParserCode()` → 空串被原样写库；
- `executeHtmlDetail()`：`task.getParserCode() == null ? "HTML_GENERIC" : ...` → 空串 → `parserRegistry.get("")` 抛"未知解析器"（业务码 041）→ 任务被判失败。

修复后：`dto.setParserCode(StringUtils.hasText(task.getParserCode()) ? ... : task.getChannelCode())`、
`StringUtils.hasText(detailParser) ? detailParser : (StringUtils.hasText(task.getParserCode()) ? task.getParserCode() : "HTML_GENERIC")`；
路由判定同步收紧（GX 分支加 hasText；QYZB 分支用 `!"QYZB_JSON".equals(code)` 天然覆盖 null/空白）。
结论：`null` / `''` / `'   '` 三种取值现在走同一条兜底路径。

### 8.6 审计不存 HTML 是否影响后续 AI 回填 —— **不影响，但需知道原文存在哪**

审计表 `bidding_crawl_download_audit` 的职责是"量/速/摘要/结论/存储状态"，**不是原文存储**；原文另有三处落点：

| 形态 | 落点 | 实测 |
|---|---|---|
| HTML 正文 | `bidding_notice_external.content_html`（mediumtext） | 806 条中 **790 条有正文（98%）** |
| PDF | `pdf_file_id` / `pdf_download_url` / `pdf_sha256` / `pdf_size`（平台归档） | 归档链路待 GX 任务验证 |
| 原文文件本体 | infra 文件服务（`raw-html/...`、`pdf/...`），地址见任务 payload `rawFileUrl` | 网关起来后 HTTP 200 |

AI 回填素材优先级（`NoticeExternalAiExtractServiceImpl.pickText`）：`extraction_text`（PDF 抽取文本）→ 否则 `Jsoup.parse(content_html).text()`。
即：**只要 `content_html` 在，AI 回填就永远有素材**，与审计表存不存 HTML 无关；审计里的 `sha256` 反而是"原文是否被改动过"的校验凭据。

两点建议（未改，供决策）：① `content_hash` 当前覆盖率 127/806（历史数据，新链路逐条写 sha256）；② 若将来要用"原始 HTML 重跑解析/换模型重抽"，直接读 `content_html` 即可，无需改审计表。
