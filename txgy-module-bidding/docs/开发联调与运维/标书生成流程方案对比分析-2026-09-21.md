# 投标文件生成流程 · 方案对比分析

| 项目 | 内容 |
| --- | --- |
| 文档日期 | 2026-09-21 |
| 分析对象 | 现有「一键生成标书」流程 vs 拟建的「子模板 + 子 Agent + 评分门禁 + 拼接」方案 |
| 结论摘要 | 新方案方向正确，但**「拆成独立 docx 再拼接」是成本与风险的集中点**；建议采用折中方案（单文档交付 + 章节级子任务 + 确定性评分门禁 + 回填性能优化），约 3–5 周可控落地 |
| 关键前提 | 新方案的**前两步（书签模板制作、变量字典与回填引擎）项目内已完成**，不需从零建设 |

---

## 一、分析背景

拟建方案描述如下：

1. 自制带**隐藏占位书签**的投标标书模板；
2. 将模板按**大目录拆解**成多个子模板文件（如「封面模板.docx + 封面参数.json」）；
3. 标书制作时由**子 Agent** 分别实现每个子模板的数据生成（依据参数 json），并填充到模板；
4. 每个子 Agent 生成后**校验文件格式与模板一致性，评分达 80 分以上**才输出子文件；
5. 最终由**总 Agent 将所有子文件拼接**成完整投标文件。

本文基于对现有代码库的逐文件核查（含模板文件实测），输出：现有流程拆解、资产映射、逐维度对比、稳定性论证、开发成本估算与推荐路径。

## 二、现有流程拆解

### 2.1 主链路

```
上传招标文件 → 登记 TENDER 材料（同步入库：切片 + 向量）
   ↓
POST /bidding/bid-agent/task/generate  →  Node generateTask 串联四阶段
   ↓
PARSE     必检检索（不经模型）→ LLM 抽取 → 项目事实卡.md
OUTLINE   章节树（逐条承接评分点 / 废标条款）
DRAFT     逐章「写 → 引用校验 → 落库」，每章独立检查点
FILL      扫描模板字段 → 四通道取值 → 分批生成 → 回填
   ↓
导出 bidDocxExporter 三条路径
  ① deliver/filled-template.docx（FILL 阶段产物，最优先）
  ② config.docx.templatePath 回填（书签模板 或 标签+留白）
  ③ buildDocx 内置排版（兜底，deliveryMode=preview）
```

**字段取值的四通道设计（零幻觉核心）**：

| 通道 | 含义 | 是否经模型 |
| --- | --- | --- |
| `MANUAL` | 签字 / 盖章 / 法人代表，Agent 全程不碰 | 否 |
| `COPY_FACT` | 与企业事实同名精确命中，照抄原文 | 否 |
| `DERIVE` | 确定性换算（报价大写走央行规则、工期由开竣工日期推算） | 否 |
| `GENERATE` | 其余字段走「检索 → 生成 → 校验」闭环 | 是 |

### 2.2 三个决定性的实现事实

#### 事实 A：生产链路走的是「Word 原生书签」，Java 侧的 SDT 能力实际空转

Java 侧 `BidDocxServiceImpl` **只识别内容控件（SDT）**，完全不认书签、不认 `${}` 占位符：

```288:308:txgy-module-bidding/.../service/bidagent/docx/BidDocxServiceImpl.java
    private static void collectSdt(List<Object> content, List<Object> out) {
        for (Object element : content) {
            Object actual = element instanceof JAXBElement<?> je ? je.getValue() : element;
            if (actual instanceof SdtBlock || actual instanceof SdtRun) {
                out.add(actual);
            } else if (actual instanceof P p) {
                // 段落内可嵌行内内容控件（SdtRun，docx4j 以 JAXBElement<SdtRun> 包装）
                collectSdt(p.getContent(), out);
            } else if (actual instanceof Tbl tbl) {
                for (Object row : tbl.getContent()) {
                    if (row instanceof Tr tr) {
                        for (Object cell : tr.getContent()) {
                            if (cell instanceof Tc tc) {
                                collectSdt(tc.getContent(), out);
                            }
                        }
                    }
                }
            }
        }
    }
```

> 该方法只判定 `SdtBlock` / `SdtRun`，**全程无任何 bookmark / `${}` / 下划线留白的判定分支**。

而真实标书模板不含 SDT，因此 `fillTask` 在扫描为 0 字段时**跳过 Java 回填**，改由 Node 侧完成：

#### 事实 B：新方案的前两步已落地

项目内已存在书签模板与配套引擎：

| 资产 | 路径 | 状态 |

引擎已适配的 8 种书签区域形态（节选自 `bookmarkFill.ts` 文件头注释）：

| 形态 | 说明 |
| --- | --- |
| 1. 留白区 | 书签内为若干纯空白 run（下划线留白）→ 取值填入第一个空白 run |
| 2. 空书签 | 书签内无任何 run（表格数据格）→ 区域内插入带段落格式的取值 run |
| 3. 示例区 | 书签内为模板示例字（「无」「长期」「合格」、行号）→ 整区替换 |
| 4. 占位符区 | 示例为「ｘｘｘ」等占位字符 → 仅替换占位 run |
| 5. 括号区 | 「（  ）日历天」→ 仅替换括号对为（取值） |
| 6. 标签区 | 书签只包住「××：」标签 → 填同段内紧随其后的前导空白 |
| 7. 日期骨架 | 区域非空白文本只含「年/月/日」→ 填值后吃掉骨架 |
| 8. 标签链 | 「____（盖章）」单 run → 只填 run 内留白段 |

## 四、逐维度对比

| 维度 | 现有方案（单模板 + 单 Agent） | 新方案（子模板 + 子 Agent + 拼接） | 胜方 |
| --- | --- | --- | --- |
| 跨章一致性 | **天然强**：同名字段合并共用一处取值，报价在封面/投标函/报价表必然同值 | 弱：各子 Agent 独立生成，跨文件字段靠约定约束，报价不一致即废标风险 | 现有 |
| 单章写作质量 | 中：单次上下文含全大纲与多章，注意力分散 | 强：子 Agent 上下文聚焦单章，输出更小更准 | 新方案 |
| 失败隔离 | 中：章节级检查点已具备 | 强：子文件级隔离 | 平 |
| 回填性能 | **差**：对 1.1 MB XML 做 1344 次正则全量扫描 + 字符串重建 | 好：单子文件 XML 小（约 5 万字符），回填快且稳 | 新方案 |
| 交付件保真度 | **强**：单文档，样式/页眉/页码/目录域原样保留，只改 `document.xml` | 高风险：合并需处理 `sectPr`、`styles.xml`、`numbering.xml`、`media`+`rels`、书签 id/rId、`[Content_Types].xml` | 现有 |
| 表格类字段填充 | 依赖模板预排固定行数，行数不足无法扩展 | 同风险（继承同一问题） | 平 |
| 并行加速 | 串行四阶段 | 子 Agent 可并行（需调整并发上限与项目亲和锁） | 新方案 |
| 可解释 / 可审计 | 强：`字段取值规划.json`、`一致性快照.json`、每章溯源 | 需重建（粒度更细但入口更多） | 平 |
| 技术栈支持度 | 现有引擎直接可用 | **Java 侧无 merge 能力**（docx4j 11.4.11 未引 merge 模块）；Node 侧仅正则 + `zipStore` | 现有 |

## 五、稳定性分析

核心判断：**新方案把「稳定」分布错了位置**。需要拆成两层评估。

### 5.1 写作质量稳定性 → 新方案更优

子 Agent 上下文聚焦、单次输出更小、失败隔离、可单章重跑——这些是真实的稳定性收益，且**现有代码已证明该思路有效**：

- `draftTask` 的检查点 + 单章失败隔离
- `fillTask` 的**分批 15 字段**（避免单次 JSON 过大）：

```312:313:services/bid-agent-service/src/tasks/fillTask.ts
      // 分批生成：每批 15 个字段，降低单次 JSON 复杂度，避免模型输出非法 JSON（2026-09-19 实测 60 字段一次生成反复失败）
      const BATCH_SIZE = 15;
```

### 5.2 交付件正确性稳定性 → 现有方案更优，且差距很大

#### 风险 1（致命）：跨文件一致性失守

投标文件的废标红线是「报价 / 工期 / 资格信息全文一致」。现有 `mergeFields` 的设计初衷正是解决它：

```73:91:services/bid-agent-service/src/tasks/fillTask.ts
function mergeFields(fields: TemplateField[]): MergedField[] {
  const map = new Map<string, MergedField>();
  for (const field of fields) {
    const existing = map.get(field.name);
    if (existing) {
      if (field.blockId && !existing.locations.includes(field.blockId)) existing.locations.push(field.blockId);
      continue;
    }
    map.set(field.name, {
      name: field.name,
      label: field.label,
      type: field.type,
      fillBy: field.fill_by ?? 'ai',
      hint: field.hint,
      locations: field.blockId ? [field.blockId] : [],
    });
  }
  return [...map.values()];
}
```

对应的类型注释明确了设计意图——`MergedField.locations` 上方写着：

```30:31:services/bid-agent-service/src/tasks/fillTask.ts
  /** §4.2 决策 2：同名字段合并后共用一处取值，解决“同一内容填入多处” */
  locations: string[];
```

拆成子 Agent 后，封面 Agent 与报价表 Agent 各自算出的「投标报价」可能不同。只能靠「共享事实卡 + 强约束」兜底，但这比「单一数据源」弱一个量级。

#### 风险 2（高）：docx 合并是工程量黑洞

多个 docx 合并需要处理：

| 合并障碍 | 说明 |
| --- | --- |
| `sectPr` 节属性 | 各节的页面尺寸、页边距、页眉页脚引用、页码起始 |
| `styles.xml` 冲突 | styleId 重名但定义不同（如各子模板都定义了 `Heading1`） |
| `numbering.xml` 冲突 | 编号定义 numId / abstractNumId 重映射 |
| `media` 与 `rels` | 图片资源需重命名并重映射 `document.xml.rels` 的 rId |
| 书签 id 冲突 | 每个 docx 的书签 id 均从 0 开始 |
| `[Content_Types].xml` | 多部件的 ContentType 合并 |
| TOC 域 | 目录域跨文档失效，需重建 |

**现有技术栈不具备该能力**：Java 使用 `docx4j-JAXB-ReferenceImpl 11.4.11`（仅 server 模块声明，未引 merge 模块）；Node 侧仅 `zipStore`（store 模式）+ 正则替换。

用正则拼接 `document.xml` 来合并两个带样式的 docx，属于**必然踩坑**的路线；而合并失败的表现是「Word 提示文件损坏」，用户直接无法打开交付件。

#### 风险 3（中）：评分门禁容易做成「假安全」

若打分器只计算格式（书签覆盖率、段落数、样式清单），则**报价填错仍可拿满分**。而现有已有更强的内容校验：

| 现有校验 | 覆盖范围 | 位置 |
| --- | --- | --- |
| `verifyDraft` | claim 缺 `sourceBlockIds`、引用不存在 id、正文数字在证据中查无实据 | `src/tasks/draftTask.ts` |
| `checkAgainstFactsCard` | 模板取值与项目事实卡交叉比对，数字不一致即告警 | `src/tasks/fillTask.ts` |
| `resolveFieldValues` 的 `put()` | 过滤「未找到 / 未命中 / 待补充」占位值，防脏值入模板 | `src/lib/templateFields.ts` |

因此评分器应定位为**确定性规则集**，而非模糊打分。

## 七、推荐路径

建议**不按「拆 docx + 拼接」实施**，而是将新方案中三个真正有价值的内核嫁接到现有单文档链路上。

### 7.1 保留：单模板 + 单交付件

继续使用 `投标文件_书签模板.docx` 一次回填、一次导出。这保住了**跨字段一致性**与**格式保真**这两个不可退让的底线。

### 7.2 吸收 1：子 Agent → 章节级子任务（已有，强化即可）

把「按子模板拆分」改为**「按大纲大章拆分上下文」**：每章生成时只注入该章相关的评分点与证据，从而获得「子 Agent 上下文聚焦」的收益，而不产生独立 docx。

现有 `draftTask` 已具备：断点续跑、单章失败隔离、`status='review'` 标注。强化点在于**上下文裁剪**（按章节过滤检索证据与评分点）。

### 7.3 吸收 2：评分门禁 → 确定性校验套件

将「80 分」实现为可解释、可定位的规则集：

| 校验项 | 判定方式 | 权重建议 |
| --- | ---: | ---: |
| 书签覆盖率 | 已填书签 / 模板总书签（1,344） | 30% |
| 必填字段完整 | 报价、工期、投标人名称等红线字段非空 | 25% |
| 数值一致性 | 与事实卡 / 报价表交叉比对（复用 `checkAgainstFactsCard`） | 25% |
| 引用溯源完整 | 复用 `verifyDraft` 的 `sourceBlockIds` 校验 | 10% |
| 格式保真 | `styles.xml` / 段落数 / 表格行列数与模板 diff | 10% |

低于阈值时：章节标记 `review` 并**明确列出扣分项**，而非笼统给出一个分数。

### 7.4 吸收 3：解决真正的痛点——回填性能

这是 1.1 MB XML + 1,344 书签带来的实际风险。现有实现的复杂度为 **O(书签数 × XML 长度)**：

```256:279:services/bid-agent-service/src/lib/bookmarkFill.ts

    const value = values[name] ?? values[stripVariantSuffix(name)];
    // 同名书签可能多处出现：收集全部标签位置后倒序回填（前面的编辑不影响后面已收集的位置）

      const endRe = new RegExp('<w:bookmarkEnd\\b[^>]*?w:id="' + idMatch[1] + '"[^>]*?/?>');

      const result = fillRegion(xml, pos + tagLength(xml, pos), pos + 1 + end.index, value);
      if (result.hit) {
        xml = result.xml;
        anyHit = true;
      }

    else skipped.push(name);

```

性能要点在于：`nameRe.exec(xml)` 与 `xml.slice(pos + 1)` 都是**对整份大字符串的操作**，且外层按书签数循环，内层按同名出现处循环。

对 1.1 MB 字符串做 1,344 轮全量正则扫描，且每处位置都触发 `xml.slice()` 大字符串复制与整串重建，量级约 **10⁹ 字符操作**。

**优化方向**：

1. 书签配对**一次性建索引**（单遍扫描收集所有 start/end 位置），避免每个书签重复全量扫描；
2. 回填统一**从后往前**批量应用，避免每处修改都重建整个字符串；
3. 或改用**事件式 XML 流式改写**。

## 八、决策建议与后续动作

### 8.1 结论

新方案方向正确（聚焦、校验、隔离），但**「拆成独立 docx 再拼接」是成本与风险的集中点**，而其主要收益（写作质量）可以用「章节级上下文聚焦」以低成本获得。

### 8.2 建议

采用**折中方案**：单文档交付 + 章节级子任务 + 确定性评分门禁 + 回填性能优化，约 **3–5 周**可控落地。

若坚持多 docx 拼接路线，建议**先单独立项做合并引擎 PoC**：用两个含表格与页眉的样例 docx 验证合并可行性，再决定是否推进。

### 8.3 后续动作候选

| 优先级 | 动作 | 说明 |
| ---: | --- | --- |
| 1 | 实施回填性能优化 | 当前 1,344 书签在 1.1 MB XML 上的正则链路，是风险最实在的一项 |
| 2 | 落地确定性评分门禁 | 复用现有三处校验能力，补齐书签覆盖率与格式保真 |
| 3 | docx 合并 PoC（可选） | 若坚持多文件拼接路线，先验证合并可行性 |
