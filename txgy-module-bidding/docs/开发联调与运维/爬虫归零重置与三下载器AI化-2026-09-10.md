## 二、三下载器 AI 化：改了什么、为什么这么改

### 2.1 关键设计：列表解析器与详情解析器解耦

原实现只有「一个 parserCode」，既承担**执行路由**（GX 详情→PDF 直链、QYZB JSON 直采、HTML 详情抓取），
又承担**正文结构化**。若把它直接改成 `HTML_AI`，GX 的「详情→PDF」路由会失效
（`execute()` 依据 `parserCode.startsWith("GX")` 分派），出现「用 HTML_AI 解析 HTML 却拿到 PDF 任务」的错配。

因此新增**栏目级 `detailParser`**，并把两者分离：

| 位置 | 字段 | 取值 | 作用 |
|---|---|---|---|
| `bidding_fetch_task.parser_code` | 列表解析器 | QYZB → `QYZB_JSON`；GX → `GX_E_BIDDING`；EBIDDING → `EBIDDING` | 执行路由 + 去重语义（不变） |
| `bidding_fetch_task.payload_json.detailParser` | 详情/AI 解析器 | `HTML_AI` / `PDF_AI` | 正文结构化 + 防腐保温行业判定 |

- 载体选择原因：`detailParser` 随 payload 快照走（`ListEntry.detailParser` → `CrawlTaskDispatchServiceImpl.writePayloadIfPending`），
  **不需要改表结构**；旧任务 payload 无该字段时回退 `task.parser_code`，既有行为不变（向后兼容）。
- 落库策略码：`bidding_notice_external.parser_code` 写**实际参与解析的策略码**（AI 生效时为 `HTML_AI`/`PDF_AI`），可追溯「这条公告是谁解析的」。

### 2.2 三条执行路径都接上了 AI

| 路径 | 触发条件 | AI 接入点 |
|---|---|---|
| 全文直采（QYZB `rows.text`） | payload 带 contentHtml/rawFileUrl | `CrawlNoticeProcessor.applyAiEnrichIfConfigured`（异步）／`CrawlSourceRunner.applyAiEnrich`（同步） |
| HTML 详情抓取 | payload 只有详情 URL，列表解析器非 GX/QYZB_JSON | `executeHtmlDetail` 直接用 `detailParser`（`HTML_AI`）解析 |
| GX 详情→PDF | task.parser_code 以 GX 开头 | `executeGxDetail` 中 `PDF_AI`=PDFBox 抽文本→平台 AI；否则 `PDF_TEXT_GENERIC` |

产出的三个字段：`industryFlag`（BELONGS/NOT_BELONGS/UNCERTAIN）、`industryConfidence`（0~1）、`aiMetaJson`（AI 原始字段留痕）。

### 2.3 降级红线（为什么 AI 失败不阻断落库）

**宁可少字段，不可丢原文**：AI 未启用（`bidding.ai.enabled=false`）、AI 超时、返回不可解析时，
一律记 WARN 并保留本地规则/原文结果继续落库。公告是「不可再生」的采集产出，
行业判定只是增强字段，不能因为模型侧抖动让公告丢失或卡在队列。

前置条件（三者缺一即「AI 不生效但公告照常入库」）：
1. `bidding.ai.enabled=true`（application.yaml 已为 true）；
2. AI 链路可用：角色 20（公告AI解析）→ 模型 66（deepseek-chat）→ 测试 key 28 均为启用态；
3. 栏目 `detailParser` 已按 Step 3 配置（否则回退列表解析器 = 本地规则，无行业判定）。

## 三、归零重置操作手册（Docker 恢复后执行）

顺序不可颠倒（三者是同一份「已处理」记忆的三个副本，只清一个会出现「清了却爬不动」或「检索命中打不开」）：

```bash
# 0) 备份（强制）：容器内 dump + docker cp，避免 Windows 管道中文乱码
docker exec txgy-mysql sh -c "mysqldump -uroot -p123456 --default-character-set=utf8mb4 \
  --single-transaction --set-gtid-purged=OFF ruoyi-vue-pro \
  bidding_notice_external bidding_notice_external_attachment bidding_notice_external_meta \
  bidding_fetch_task bidding_fetch_job bidding_fetch_source > /tmp/reset-backup.sql"
docker cp txgy-mysql:/tmp/reset-backup.sql ./backups/2026-09-10-pre-reset-backup.sql

# 1) DB 归零（关源 → 清任务/批次/公告 → 三源切 AI + 启用 → 校验）
docker exec -i txgy-mysql mysql -uroot -p123456 --default-character-set=utf8mb4 ruoyi-vue-pro \
  < sql/tools/reset-crawl-to-zero.sql

# 2) Redis + ES 归零（预演→确认；CONFIRM=YES 才写入）
ES_PASSWORD='<ES密码>' bash sql/tools/reset-crawl-to-zero.sh              # 预演
ES_PASSWORD='<ES密码>' CONFIRM=YES bash sql/tools/reset-crawl-to-zero.sh  # 执行 + 触发全量
```

**全量为什么自动生效**：`CrawlRunServiceImpl.runNow` 以「该源是否存在 SUCCESS 批次」判定首次全量
（`bidding_fetch_job` 被清空 → `successCount=0` → `full=true`，按栏目 `fullLookbackDays` 回溯，默认 60 天）。

**预期节奏（正常，不是故障）**：`consumer-delay-ms=300000`，消费端**每 5 分钟一条**；`page-delay-ms=60000` 页间隔；
PENDING 堆积是设计结果而非卡死（用户口径：慢是要求，不是缺陷）。

## 四、解析器分类能力清单（哪些能分类、哪些不能）

「分类」= 产出防腐保温**行业判定**（`industryFlag` + `industryConfidence`）。
全库 9 个解析器中，**只有 2 个 AI 解析器能分类**：

| 策略码 | 实现类 | 载荷 | 阶段 | 结构化产出 | 行业判定 |
|---|---|---|---|---|---|
| `HTML_AI` | HtmlAiParser | HTML | 详情 | title / projectName / projectCode / tenderProjectCode / issuer / publishTime | ✅ BELONGS/NOT_BELONGS/UNCERTAIN + 置信度 + aiMeta |
| `PDF_AI` | PdfAiParser | PDF | 详情 | 同 HTML_AI（先 PDFBox 抽文字层，再送 AI） | ✅ 同上（**扫描件无文字层 → FAILED，需 OCR/多模态，当前不支持**） |
| `QYZB_JSON` | QyzJsonListParser | JSON | **仅列表** | 条目 title/url/date/category/contentHtml（不含正文结构化） | ❌ |
| `GX_E_BIDDING` | GxEbidNoticeParser | HTML | 列表 + 详情 | 列表条目；详情出 `meta.pdfDownloadUrl`（正文在 PDF 内） | ❌ |
| `QYZB_SHCCMG` | QyzNoticeParser | HTML | 详情 | 标题/发布时间/招标编号/招标人/正文区间（QYZB 站点规则 v1） | ❌ |
| `EBIDDING` | EbidNoticeParser | HTML/JSON | 详情 | v0 骨架：走通用抽取，站点规则待真实样本校准 | ❌ |
| `HTML_GENERIC` | HtmlNoticeParser | HTML | 详情 | h1/title、正文纯文本、发布日期启发、附件候选、发布单位启发 | ❌ |
| `JSON_GENERIC` | JsonNoticeParser | JSON | 详情 | 常见键名归一（中英/大小写/下划线） | ❌ |
| `PDF_TEXT_GENERIC` | PdfTextNoticeParser | PDF | 详情 | PDFBox 文字层文本（无文字层 → FAILED） | ❌ |

**结论**：
1. 想让某源「能分类」，必须把该源栏目的 `detailParser` 指向 `HTML_AI`/PDF 形态的 `PDF_AI`；
   仅靠列表解析器（`QYZB_JSON`/`GX_E_BIDDING`）永远不会有行业判定。
2. 列表解析器**不是分类能力缺失，而是职责不同**：它们只负责「栏目页 → 条目清单」，
   正文与判定必须由详情解析器完成（这正是本次解耦的目的）。
3. 真正的能力缺口是**扫描件 PDF**（无文字层）与**图片型公告**：当前全链路无 OCR，
   `PDF_AI`/`PDF_TEXT_GENERIC` 均返回 FAILED。如需覆盖，需引入 OCR/多模态通道（另行评估）。
4. `EBIDDING` 站点规则仍是 v0 骨架（通用抽取），虽然详情可挂 `HTML_AI`，但列表页规则未校准，
   该源当前 `entry_urls_json` 为空，**保持停用**（见 Step 3 注释）。

## 五、PDF 预览缺陷（0 字节）诊断与修复

**现象**：`GET /admin-api/bidding/notice-external/pdf?id=<id>` 返回 `200 application/pdf` 但 **0 字节**；
直连 `/admin-api/infra/file/4/get/...` 同样 0 字节 → 前端表现为「预览空白，且无报错」。

**根因（代码级）**：`NoticeExternalServiceImpl.pdfContent` 原判定为
`resp.statusCode()==200 && resp.body()!=null` → **空数组也是「成功」**，于是 0 字节被当成正常 PDF 返回 200，
真正的失败（归档文件为空/存储读不到）被静默吞掉，无法从接口层区分「没有原文」与「原文是空的」。

**修复**（已编译通过）：
1. 抽出 `fetchPdfBytes(url, id, channel)`：**按字节长度判定**，空体一律视为不可用，
   并打印 `HTTP 状态码 + 字节数 + url`（可区分「归档缺失」与「存储读空」）；
2. 双通道取原文：① 平台归档 `pdf_download_url` → ② 外站直链 `meta_json.pdfDownloadUrl`
   （外站直链必须过采集源白名单 = SSRF 防护，复用 `assertPdfDownloadAllowed`）；
3. 两通道皆不可用 → 返回 `null` → 接口 404（契约：无归档返回 404），不再返回空白 PDF。

**Docker 恢复后的验证清单**（逐条执行，把结果贴回）：
```bash
# 1) 归档文件是否真有内容（size 应 > 0；为 0/NULL 即存储侧问题）
SELECT id, content_type, pdf_size, pdf_download_url, meta_json->>'$.pdfDownloadUrl' AS external_url
FROM bidding_notice_external WHERE content_type='PDF' LIMIT 10;

# 2) 平台文件表里对应 blob 的字节数（与 pdf_size 对比；0 表示上传时就是空）
SELECT f.path, LENGTH(c.content) AS bytes
FROM infra_file f JOIN infra_file_content c ON c.file_id = f.id
WHERE f.path LIKE 'bidding/notice-external/%' ORDER BY f.id DESC LIMIT 10;

# 3) 归档地址直连（应返回 application/pdf 且字节数 > 0）
curl -sI "http://127.0.0.1:48080/admin-api/infra/file/4/get/<path>"

# 4) 预览端点（修好后：有原文=200+字节数>0；无原文=404，不再 200/0 字节）
curl -s -o /tmp/p.pdf -w '%{http_code} %{size_download}\n' \
  "http://127.0.0.1:48080/admin-api/bidding/notice-external/pdf?id=<公告id>"
```
若第 1/2 步显示存储本身是 0 字节，则属于**采集期归档失败**（历史上 GX 源因站点鉴权收紧，
`openFileById` 未登录返回 0 字节即被上传），需先解决站点登录态（Cookie）再重爬，而非接口问题；
本次修复保证这类情况**前端能看到明确的 404** 而不是空白页。
