# 标书模板与变量字典 · 落地方案

| 项目 | 内容 |
| --- | --- |
| 文档日期 | 2026-09-22 |
| 输入资产 | `投标标书_合并.docx`（占位变量模板）、`投标标书_变量字典_合并.md`（22 份字典合并版） |
| 目标 | 将上述两个文件接入现有系统，作为后续标书生成的统一模板与字典 |
| 核心结论 | **放置位置明确**（Node 编排服务内置模板目录）；但仅放置只能覆盖约 **11%** 的书签，**计价表数据通道是必做的关键改动** |

## 一、结论：放在哪里

**不是**放到后台「知识库管理」里当 TEMPLATE 材料，而是放到 **Node 编排服务的内置模板目录**：

| 文件 | 目标位置 | 说明 |
| --- | --- | --- |
| `投标标书_合并.docx` | `services/bid-agent-service/templates/投标标书_主模板.docx` | 平台级内置模板 |
| `投标标书_变量字典_合并.md` | `services/bid-agent-service/templates/投标标书_变量字典.md` | 配套人读文档 |
| **（需新建）** | `services/bid-agent-service/templates/bookmark-dict.json` | **机器可读字典**，见改动 2 |

配置入口（`.env`）：

```bash
# 指向新模板；留空则回退到默认的 投标文件模板.docx
BID_TEMPLATE_DOCX=templates/投标标书_主模板.docx
```

### 为什么是这里，而不是知识库管理

系统里有两套并存的模板概念，必须先分清：

| 概念 | 载体 | 作用域 | 代码位置 |
| --- | --- | --- | --- |
| 平台级内置模板 | Node 服务本地文件 | **全局唯一** | `config.docx.templatePath` |
| 租户级模板材料 | 知识库材料（`docType=TEMPLATE`） | 按租户 | `fillTask` 的 `payload.templateId` |

本次需求是「后续所有标书统一用这一套版面」→ 属**平台级**，走前者。

若放进知识库当 TEMPLATE 材料，反而要每个租户各传一份；且 `BidDocxExporter` 优先读的是 `config.docx.templatePath`，会造成「传了但不生效」。

## 四、三处必须改动

### 改动 1：模板路径切换（0.5 人日）

改 `config.ts` 的默认值，或只用 `.env` 覆盖。

推荐**保留代码默认值不动**，通过 `.env` 指定，便于回滚与多环境切换。

### 改动 2：字典必须从「文档」变成「配置」（3–5 人日）

**现状**：映射关系硬编码在代码里，只覆盖约 50 条：

```9:20:services/bid-agent-service/src/lib/bookmarkFields.ts
const BOOKMARK_STD_MAP: Record<string, string[]> = {
  // —— 封面 / 投标函 ——
  bid_no: ['招标编号'],
  section_no: ['标段号'],
  bidder_name: ['投标人名称'],
  legal_rep_or_agent: ['委托代理人姓名', '法定代表人'],
  tenderer: ['招标人'],
  project_name: ['工程名称'],
  bid_total_upper: ['投标报价大写'],
  bid_total: ['投标报价小写'],
  ...
```

而新字典有 **1,334 个书签**（前缀分布见附录 A）。

**要做的**：把字典结构化落成 `bookmark-dict.json`，并把 `bookmarkFields.ts` 从「硬编码常量」改为「读配置」。

建议 JSON 结构：

```json
{
  "version": "2026-09-22",
  "template": "投标标书_主模板.docx",
  "bookmarks": [
    { "name": "bid_no", "label": "招标编号", "chapter": "封面", "kind": "scalar", "source": "TENDER|FACT" },
    { "name": "bill_2_code", "label": "第1行 项目编号", "chapter": "表5", "kind": "table-cell",
      "table": "bill", "row": 3, "col": 2, "source": "PRICING" }
  ]
}
```

要点：

1. `kind` 区分 `scalar`（散字段）与 `table-cell`（表格单元格），后者带 `table`/`row`/`col` 便于结构化导入时按行列定位；
2. `source` 标注数据来源通道（见第五章），支撑「该字段该从哪里取」的自动路由；
3. `version` 用于启动时与模板书签做一致性校验。

### 改动 3：补上「计价表数据通道」（5–8 人日）——决定能否达到预期

这是最实质的缺口。实测新模板 **90% 的书签是计价表数据**（约 1,200 个），而系统**完全没有这类数据的来源**。

现有 `fillTask` 的字段来源只有两条：

| 通道 | 含义 | 是否经模型 |
| --- | --- | --- |
| `COPY_FACT` | 与企业事实同名精确命中 | 否 |
| `DERIVE` | 确定性换算（报价大写、工期推算） | 否 |
| `GENERATE` | 检索 → 生成 → 校验 | 是 |
| `MANUAL` | 签字/盖章，Agent 全程不碰 | 否 |

但 `analysis_*`（人工费/材料费/机械费/管理费/利润/风险）、`bill_*`（工程量清单综合单价）、`material_*`（材料价格）这些，**是投标人自己编制报价的产物**，不可能从招标文件里抽取，也不属于企业事实库。

**必须新增一条导入通道**：投标人上传造价软件导出的工程量清单（Excel / 计价文件）→ 解析为结构化 JSON → 按 `bill_*` / `analysis_*` / `material_*` 等书签名映射回填。

落点建议：在后台「知识库管理 → 资料管理」新增一种材料角色 `PRICING`（报价数据）：

```
TENDER    招标文件
FACT      企业资料
TEMPLATE  技术母本
PRICING   报价数据   ← 新增
```

由 Java 侧解析 Excel 后写入结构化表，Node 侧 `fillTask` 新增 `COPY_PRICING` 通道读取。

## 七、风险提示

### 风险 1：回填性能（继承自旧模板）

1,334 书签 × 1.1 MB XML 的正则回填链路，当前实现复杂度为 **O(书签数 × XML 长度)**：

```256:271:services/bid-agent-service/src/lib/bookmarkFill.ts
  for (const name of candidates) {
    const value = values[name] ?? values[stripVariantSuffix(name)];
    // 同名书签可能多处出现：收集全部标签位置后倒序回填（前面的编辑不影响后面已收集的位置）
    const positions: number[] = [];
    const nameRe = new RegExp('<w:bookmarkStart\\b[^>]*?w:name="' + escapeRegex(name) + '"[^>]*?/?>', 'g');
    let tag: RegExpExecArray | null;
    while ((tag = nameRe.exec(xml)) !== null) positions.push(tag.index);

    let anyHit = false;
    for (const pos of positions.reverse()) {
      const idMatch = /w:id="(\d+)"/.exec(xml.slice(pos, pos + 300));
      if (!idMatch) continue;
      const endRe = new RegExp('<w:bookmarkEnd\\b[^>]*?w:id="' + idMatch[1] + '"[^>]*?/?>');
      const end = endRe.exec(xml.slice(pos + 1));
```

`nameRe.exec(xml)` 与 `xml.slice(pos + 1)` 都是对整份大字符串的操作，量级约 **10⁹ 字符操作**。建议在 P3 一并优化（一次性建索引 + 从后往前批量应用）。

### 风险 2：表格行数固定

模板中 `bill_2…bill_12`（11 行）、`analysis_3…analysis_22`（20 行）、`staff_2…staff_15`（14 行）等均为**预排固定行数**。若实际数据行数超出，没有书签可用、无法扩展。

P2 设计中必须明确「超出行数的处理策略」（截断告警 / 模板预排更多行）。

### 风险 3：跨字段一致性（废标红线）

`bid_total`（投标总价）在封面、投标函、表1、表5 等**多处共用同名书签**。字典「共享变量说明」章节列明：

| 基础变量 | 出现章节 |
| --- | --- |
| `bidder_name` | 封面、一（含 _2/_3/_4）、二（含 _2/_3）、三（含 _2）、五、表1 |
| `project_name` | 封面、一（含 _2/_3）、三、五、表1~表12（全部计价表表头） |
| `date_year/month/day` | 封面、一（含 _2/_3）、二、三、五、表1 |
| `bid_total` / `bid_total_upper` | 一、五、表1 |
| `legal_rep_or_agent` | 封面、一（含 _2/_3）、五、表1 |

回填时必须**单一数据源**，否则报价不一致直接废标。现有 `mergeFields` 已解决此问题，务必保持：

```73:91:services/bid-agent-service/src/tasks/fillTask.ts
function mergeFields(fields: TemplateField[]): MergedField[] {
  const map = new Map<string, MergedField>();
  for (const field of fields) {
    const existing = map.get(field.name);
    if (existing) {
      if (field.blockId && !existing.locations.includes(field.blockId)) existing.locations.push(field.blockId);
      continue;
    }
    map.set(field.name, {
      name: field.name,
      label: field.label,
      type: field.type,
      fillBy: field.fill_by ?? 'ai',
      hint: field.hint,
      locations: field.blockId ? [field.blockId] : [],
    });
  }
  return [...map.values()];
}
```

### 风险 4：字典版本管理

字典「变更记录」已记录 2026-09-22 的三项修复：

| 日期 | 变更 |
| --- | --- |
| 2026-09-22 | 表8（计日工）书签 `material_*` 与表12（主要材料价格表）`material_N_*` 重名冲突，表8 统一改名为 `daywork_material_*`（含 `daywork_material_subtotal`）；表12 保持不变 |
| 2026-09-22 | 表8、表9 数据单元格段落标记 36 磅 → 24 磅（原模板生成缺陷，导致回填值偏大） |
| 2026-09-22 | 全文「仿宋_GB2312」→「仿宋」（旧字体名在多数机器未安装） |

这类修复必须与模板文件**同步版本化**。建议 `bookmark-dict.json` 带 `version` 字段，并在服务启动时校验「模板实际书签集合」与「字典声明书签集合」的一致性，不一致则告警。
