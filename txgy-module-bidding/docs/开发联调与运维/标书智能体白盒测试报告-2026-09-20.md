## 三、P0 阻断缺陷

### BUG-01 云端模型在企业租户下完全不可用

**严重级别**：P0 · 阻断
**影响模块**：智能体管理 → 云端模型；进而阻断智能体试跑与前台一键生成

#### 复现步骤

1. 以**企业租户**（`tenantId ≠ 0`）登录后台 → 智能体管理 → 云端模型
2. 列表可见「默认云端模型」，状态、端点均正常显示
3. 点击**编辑**，修改模型名后保存 → **报错「云端模型不存在」**
4. 点击**测试** → **报错「云端模型不存在」**
5. 进入智能体管理点击**试跑** → **报错「没有启用的云端模型配置」**
6. 前台标书工坊点击**一键生成** → **全流程失败**

### BUG-02 逻辑删除与唯一键冲突，重复保存必报 500

**严重级别**：P0 · 阻断
**影响模块**：智能体管理（技能绑定 / MCP 绑定 / 技能 CRUD / MCP CRUD）

#### 复现步骤

**场景 A（智能体挂载技能）**

1. 智能体管理 → 配置某智能体 → 勾选技能 A、B → 保存成功
2. 再次打开配置 → 取消勾选 B → 保存成功
3. 再次打开配置 → **重新勾选 B** → 保存 → **500 `DuplicateKeyException`**

**场景 B（技能删除后重建）**

1. 技能管理 → 新增技能，编码 `MY_SKILL` → 成功
2. 删除该技能 → 成功
3. 再次新增技能，编码仍为 `MY_SKILL` → **500 `DuplicateKeyException`**

#### 根因分析

**（1）删除是逻辑删除，物理行仍在**

```19:22:txgy-module-bidding/.../dal/mysql/bidagent/BidAgentProfileSkillMapper.java
default int deleteByProfileId(Long profileId) {
    return delete(new LambdaQueryWrapperX<BidAgentProfileSkillDO>()
            .eq(BidAgentProfileSkillDO::getProfileId, profileId));
}
```

`BidAgentProfileSkillDO extends TenantBaseDO` → `BaseDO` 的 `deleted` 字段带 `@TableLogic`，`delete(wrapper)` 实际执行 `UPDATE ... SET deleted = 1`，**不会物理删除行**。

**（2）唯一键未包含 `deleted`**

```83:93:txgy-module-bidding/sql/history/2026-09-16-bid-agent-agent-platform.sql
CREATE TABLE IF NOT EXISTS `bidding_bid_agent_profile_skill` (
    `id` bigint NOT NULL COMMENT '主键（雪花）',
    `profile_id` bigint NOT NULL COMMENT '智能体配置编号（bidding_bid_agent.id）',
    `skill_id` bigint NOT NULL COMMENT '技能编号（bidding_bid_agent_skill.id）',
    ...
    `deleted` bit(1) NOT NULL DEFAULT b'0',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_profile_skill` (`profile_id`, `skill_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='标书智能体-智能体与技能关联';
```

唯一键 `uk_profile_skill (profile_id, skill_id)` **不含 `deleted`** → 重新插入同一组合时撞上历史逻辑删除行 → 唯一键冲突。

**（3）同源缺陷的完整清单**

| 表名 | 唯一键（实际定义） | 含 deleted | SQL 位置 |
| --- | --- | :---: | --- |
| `bidding_bid_agent_profile_skill` | `(profile_id, skill_id)` | 否 | `2026-09-16-...sql:92` |
| `bidding_bid_agent_profile_mcp` | `(profile_id, mcp_server_id)` | 否 | `2026-09-16-...sql:131` |
| `bidding_bid_agent_skill` | `(tenant_id, code)` | 否 | `2026-09-16-...sql:80` |
| `bidding_bid_agent_mcp_server` | `(tenant_id, name)` | 否 | `2026-09-16-...sql:118` |
| `bidding_bid_agent_model` | `(tenant_id, name)` | 否 | `2026-09-16-...sql:56` |

**（4）技能侧还叠加了「校验放行」**

```73:83:txgy-module-bidding/.../service/bidagent/BidAgentSkillServiceImpl.java
@Override
@Transactional(rollbackFor = Exception.class)
public Long save(BidAgentSkillVO.SaveReqVO reqVO) {
    BidAgentSkillDO exist = skillMapper.selectByCode(reqVO.getCode());
    if (exist != null && !exist.getId().equals(reqVO.getId())) {
        throw exception(BID_AGENT_SKILL_CODE_DUPLICATE, reqVO.getCode());
    }
    BidAgentSkillDO item = reqVO.getId() == null ? new BidAgentSkillDO() : skillMapper.selectById(reqVO.getId());
```

`selectByCode` 受逻辑删除过滤，**查不到已删除的同编码行** → 唯一性校验通过 → 直接撞 DB 唯一键，报 500 而非业务错误码。

#### 规范符合性

《招投标模块开发规范》§六.1 明确要求：

> T 轨 `UNIQUE (业务编号, deleted, tenant_id)`（平台惯例：业务键在前、含 `deleted` 兼容逻辑删除、`tenant_id` 收尾）

上述 5 张表**全部违反本模块自身规范**。

#### 影响

- 核心配置能力丧失幂等性；用户最自然的「取消再勾选」操作即报 500
- 报错为数据库异常而非业务错误码，前端提示不友好且无引导

#### 修复建议

1. 将 5 个唯一键改造为含 `deleted` 或改用「删除时间戳」方案（如 `deleted` 存毫秒时间戳，未删除为 0），保证逻辑删除行之间不互斥。
2. 或对绑定类表采用**物理删除**（`BidAgentProfileSkillDO` / `BidAgentProfileMcpDO` 无审计价值时可去掉 `@TableLogic` 语义）。
3. 技能唯一性校验改为「查重时忽略逻辑删除」或捕获 `DuplicateKeyException` 转换为业务错误码。

#### BUG-10 事务内执行远程调用与向量写入（不可回滚）


被包裹的 `indexInternal` 下游链路为：`indexUrl` → `HttpUtil.downloadBytes`（外网下载）→ `TikaDocumentReader` 解析 → 逐 chunk 调 embedding → `vectorStore.add` 写 Qdrant。

同类问题存在于 `BidAgentSegmentServiceImpl` 的 `edit / split / merge / delete`（均在 `@Transactional` 内调 `reindexChunk` / `deleteChunks`），以及 `reindex()`。

**影响**：

1. **长事务**：DB 连接与行锁在「外网下载 + 向量化 + 向量写」全程被持有（100 页 PDF 可达数十秒至数分钟）。
2. **一致性缺口**：Qdrant 不是 DB 资源，**不参与事务回滚**。若 `updateById` 之后事务回滚，向量已写 → 台账与向量不一致。
3. **静默丢向量**：`reindexChunk` 采用「先删旧向量、再写入新向量」，若 `add` 失败，旧向量已删除而新向量未写入 → 该切片「内容改了但检索不到」。

```209:237:txgy-module-bidding/.../service/bidagent/index/BidIndexServiceImpl.java

                vectorStore.delete(List.of(chunk.getVectorId()));   // 先删

            ...
```

**修复建议**：

1. 事务边界只覆盖 DB 写入；远程调用（下载 / embedding / 向量写）移出事务。
2. 或采用「先写新向量 → 再更新台账 → 最后删旧向量」的顺序，并加失败补偿。
3. 引入本地消息表 / 重试队列，保证向量与台账最终一致。

## 六、本次已修复项

### BUG-09 技能管理页无法区分平台预置技能（上轮 UI 重构引入）

**问题描述**

后台「技能管理」页列表由 `BidAgentSkillServiceImpl.page()` 合并返回**平台预置技能（`tenant_id = 0`，8 条）**与租户自建技能。但：

- `BidAgentSkillVO.RespVO` **不含 `tenantId` 字段** → 前端无法区分来源；
- 后端 `get / save / delete` 均使用受租户过滤的 `selectById` → 租户操作平台技能必然抛 `BID_AGENT_SKILL_NOT_EXISTS`。

结果是页面上给平台预置技能也提供了「编辑」「删除」按钮，**用户点击必定报「技能不存在」**。

**修复内容**

| 文件 | 改动 |
| --- | --- |
| `.../controller/admin/bidagent/vo/BidAgentSkillVO.java` | `RespVO` 新增 `tenantId` 字段（0 = 平台预置） |
| `.../api/bidding/bidAgent/platform.ts` | `Skill` 接口新增 `tenantId` |
| `.../views/bidding/bidAgent/skill/index.vue` | 新增 `isPlatformSkill()` 判定；平台技能展示「平台预置」标签；编辑/删除按钮置灰，点击给出「复制为租户技能（改用不同编码新增）」的引导 |

**验证**：Java 与前端均通过 lint 检查（0 错误）。

**遗留建议**：后端 `get/save/delete` 对平台技能当前返回「技能不存在」，措辞具有误导性，建议改为明确的「平台预置技能不可修改」业务错误码。
