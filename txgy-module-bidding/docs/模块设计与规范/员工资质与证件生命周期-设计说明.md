## 二、关键设计决策

### 2.1 为什么新建人员域，而不复用 cert_person_bindings
v3.3 表 10 `cert_person_bindings` 的定位是"**一证一绑定**"，以证为主体；而本期需求是"**以人为主体**"
（一人多证 + 培训 + 社保 + 合同 + 身份证有效期），两者主体相反。强行复用会让"人的属性"被迫挂在证上，
社保/合同履历无处安放。因此新建 `bidding_personnel_*` 人员域，并让 `personnel_certificate.binded_cert_id`
/ `file_id` 复用既有证照影像与验真能力，保持"**证照事实归 certificate_info、业务要素归资质域**"的既有边界。

### 2.2 为什么四类生命周期归并为一张 cert_lifecycle_record
v3.3 把生命周期拆成 `cert_review_record`（表 3）/ `cert_renewal_record`（表 5）/ `cert_change_record`（表 6）/
`cert_revoke_record`（表 7）。四表约八成字段同构（业务对象 + 申请人/时间 + 状态 + 结论 + 新文件 + 备注），
且本期要同时服务"通用证照"与"员工证书"两个域对象——按四表 × 两域展开即 8 张近乎同构的表与 8 套 Mapper/Service。

**决策**：归并为一张表，用 `biz_domain` 区分对象、`lifecycle_type` 区分流程；字段已按四类分组排列，
若评审要求拆表可按 `lifecycle_type` 无损拆分。这与既有 `cert_alert_records` 用 `ref_type/ref_id` 泛化承载
QUAL_EXPIRY 的范式一致（先例：`sql/history/2026-09-10-qual-expiry-alert.sql`）。

### 2.3 与 cert_change_logs 的边界（避免机制重复）
| 机制 | 定位 | 触发方式 |
| --- | --- | --- |
| `cert_change_logs`（既有） | **审计日志**：任何主档更新后记录的哈希链流水 | 服务层写操作自动产生 |
| `cert_lifecycle_record`（本期） | **业务流程**：申请 → 审核 → 生效，含新旧值对照与审批人 | 人工发起 + 审批 |

二者互补：日志回答"改过什么"，流程回答"为什么改、谁批的、批的是哪次申请"。生效回写主档时，审计日志照旧由
主档更新路径产生，不重复记录。

### 2.4 状态可用性统一口径
- 人员：仅 `ACTIVE` 参与投标/申报；
- 员工证书：仅 `VALID` / `EXPIRING_SOON` 可用；`EXPIRING_SOON` **只能由预警扫描置位**（人工设置被拒，
  防止绕过预警口径）；`SUSPENDED`（暂扣，年检不通过）为可恢复失效，与 `REVOKED`/`CANCELLED` 终态区分；
- 生命周期流程：`PENDING → REVIEWING → APPROVED → EFFECTIVE`，`REJECTED`/`EFFECTIVE` 为终态；
  **"待办 → 直接生效"被拒绝**，"已生效 → 再次生效"也被拒绝（防止台账被回写两轮）。

### 2.5 版本管理
- 企业证照：沿用既有 `cert_file_versions`（换证产生新文件版本）；
- 员工证书：`personnel_certificate` 自带版本链（`is_current` / 生效时由续期流程刷新有效期与新证号），
  生命周期记录保留 `old_valid_to / new_valid_to / new_cert_no` 便于复算。

## 三、到期预警（M11 核心能力）

**三源扫描**（`PersonnelAlertService#scanPersonnelExpiries`）：

| 来源 | 表字段 | alert_type | ref_type | 幂等键 |
| --- | --- | --- | --- | --- |
| 员工证书有效期 | `personnel_certificate.valid_to` | EXPIRY | PERSON_CERT | PERSON_CERT:{id}:EXPIRY:yyyyMMdd |
| 证书复审/年审 | `personnel_certificate.next_review_date` | REVIEW | PERSON_CERT_REVIEW | PERSON_CERT_REVIEW:{id}:REVIEW:yyyyMMdd |
| 身份证有效期 | `bidding_personnel_profile.id_card_valid_to` | EXPIRY | PERSON_ID_CARD | PERSON_ID_CARD:{id}:EXPIRY:yyyyMMdd |

- **复用既有域**：记录写 `cert_alert_records`，通知写 `cert_notify_outbox`（可靠送达），不新建预警表；
- **幂等**：幂等键含触发日期，定时任务重跑/手动补跑均安全；
- **状态联动**：≤30 天的证书由 `VALID` 置为 `EXPIRING_SOON`（CAS 更新，失败抛错不吞并发）；
- **法定下限优先**（06 文档 §二-5）：配置阈值只能更早不能更晚——进入法定窗口至少 WARNING，
  进入 30 天内 CRITICAL。下限表见 `GET /bidding/personnel-alert-run/legal-floor-days`
  （建造师 90、安许证 90、特种设备生产许可 180、司炉复审 60、排污许可 60、身份证 90）。
- **复审独立维度**（06 文档 §二-4）：只看到期日会漏判"到期之前就已失效"（司炉证逾期复审、ISO 年审逾期），
  故 `next_review_date` 单独成源、单独预警。

## 四、企业材料完备性自查（身份 / 资质 / 实力）

`EnterpriseMaterialTypeEnum` 固化"材料类别 → 校验来源"映射（改口径只改一处）：

| 大类 | 材料 | 判定来源 |
| --- | --- | --- |
| 身份类 | 营业执照 / 法定代表人身份证明 / 法人授权委托书 | certificate_info（按 cert_type） |
| 资质类 | 建筑业企业资质证书 | enterprise_qualification |
| 资质类 | 安全生产许可证 | qualification_safety_permit |
| 实力类 | 财务审计报告 / 社保证明 | certificate_info（按 cert_type） |
| 实力类 | 工程业绩证明 | qualification_performance（存在即具备） |

结论三档对齐 v3.3 表 15-6：**必备缺失或已过期 → FAIL；仅临近到期（≤60 天）→ RISK；其余 → PASS**。
接口：`GET /bidding/enterprise-material/completeness?entId=&asOf=`（asOf 支持以投标截止日为基准回填）。

## 五、数据分级与脱敏（开发规范 §4.8）

- 身份证号属 **L4**：`idCard` 明文只在建档/更新**入参**出现一次；落库只有 `idCardBlindIndex`
  （HMAC-SHA256，盐由 `bidding.personnel.id-card-secret` 注入）+ 密文占位；出参只回 `idCardMasked`（前 6 后 4）；
- 手机/姓名属 **L3**：列表出参默认掩码（`PersonnelSensitiveUtils.maskMobile/maskName`，复姓保留两字）；
- 一人一档判重靠**盲索引**而非明文比对：同证号必同索引、索引不可逆（拖库拿不到明文，裸哈希会被彩虹表反查）；
- 工具类为**纯 JDK 实现**（`javax.crypto` + `HexFormat`），不为一个工具类引入第三方依赖。
