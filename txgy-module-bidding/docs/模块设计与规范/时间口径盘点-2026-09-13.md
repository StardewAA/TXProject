# 时间口径盘点与统一（2026-09-13）

> 起因：用户提问「爬虫区域出现的所有关于时间的都是什么，全域时间的数据类型统一吗，都有按规范走吗」。
> 结论：**不统一**——全模块同一件事有四种时间表达，且规范里那一条与三种实现都不一致。本文是取证 + 已统一项 + 待拍板项。

## 一、四种口径并存（取证）

| # | 口径 | 用在哪 | 证据 |
| --- | --- | --- | --- |
| 1 | `LocalDateTime`（平台序列化为 `yyyy-MM-dd HH:mm:ss`） | **多数出参 VO**（48 处时间字段） | `grep "private LocalDateTime" controller/**/vo` |
| 2 | `Long` epoch 毫秒 | **项目/追溯/关注域出参**（8 个字段：3 个 `createTime`、`ProjectTraceRespVO` 内的 `publishTime`/`submitTime`/`latestDynamicTime`） | `ProjectServiceImpl.epoch(...)` 11 处调用点 |
| 3 | epoch 毫秒（ES 存储） | 索引 `bidding-notice` 的 `publishTime`（注释写明「存毫秒时间戳便于排序」，并按该字段 `sort`） | `NoticeServiceImpl.indexDoc` → `NoticeSearchDoc.publishTime(Long)` |
| 4 | ISO 字符串 `yyyy-MM-dd'T'HH:mm:ss` | 索引 `bidding-notice-external` 的 `publishTime` | `EsExternalNoticeIndexNotifier.ES_TIME`（现已收敛到工具类） |

**同一字段名（`publishTime`）在两个索引里是两种类型** ✗ ——按 `bidding-notice` 的排序写法去查 `bidding-notice-external` 会直接报类型错误，反之亦然。

## 二、与规范的对账（《招投标模块开发规范》）

| 规范条款 | 现实现状 | 判定 |
| --- | --- | --- |
| §三-267 / §四-344：自建 VO 用 `LocalDateTime`、时间出入参用 `LocalDateTime` | 多数 VO 是 `LocalDateTime` ✓；但项目/追溯/关注域出参是 epoch 毫秒 ✗ | **不符**（口径 2 违规） |
| §六-460：时间字段以 `datetime` 存储，**输出及上报时转换为规范的 `yyyyMMddHHmmss` 字符串** | 库列确实是 `datetime` ✓；但出参既不是 `yyyyMMddHHmmss`（是 `yyyy-MM-dd HH:mm:ss` 或 epoch 毫秒），ES 用 ISO ✗ | **不符**（三种输出都不等于规范格式；需澄清该条是否只约束「上报/交换层」） |
| §六-485：到期预警、截止时间等按需对时间列建索引 | 到期扫描 `valid_to` 走索引 ✓（本次还统一了到期窗口定义） | 符合 |

## 三、本次已统一（不改对外契约，纯内部收敛）

1. 新增 `BiddingTimeUtils`（`framework/util`）作为**时间转换唯一入口**：`toEpochMilli` / `fromEpochMilli` / `toEsDateTime` / `fromEsDateTime`，统一时区（`ZoneId.systemDefault()`，与既有行为一致，只收敛实现）、统一 null 兜底；
2. `ProjectServiceImpl.epoch(...)` 改为薄委托（11 处调用点不动）；
3. `NoticeServiceImpl` 里手写的 `atZone(...).toEpochMilli()` 改调工具（原为同一转换的第二份实现）；
4. `EsExternalNoticeIndexNotifier` 的本地 `ES_TIME` 常量删除，改调工具（ES 日期格式从此一处定义）；
5. 回归测试 `BiddingTimeUtilsTest`（null 兜底 / 往返一致 / ES 格式与外部公告索引现行口径一致）。

## 四、已按规范改正（2026-09-13 落地，前端零影响）

原先我判"要拍板才能动"，是**读窄了规范**——规范本身自洽：

| 规范条款 | 适用范围 | 本次落实 |
| --- | --- | --- |
| §三-3.1 自建 VO 用常规类型（含 `LocalDateTime`）；§四-4.4-3 时间出入参用 `LocalDateTime`、与上报格式互转放 Service | **admin 自建 VO（页面/内部接口）** | 项目/追溯/关注域 8 个 **手写 `Long` epoch 出参全部改为 `LocalDateTime`**（3 个 `createTime` + `NoticeItem.publishTime`/`ExternalNoticeItem.publishTime`/`FilingItem.submitTime`/`FollowItem.latestDynamicTime`/`Stats.latestDynamicTime`）；`ProjectServiceImpl.epoch(...)` 删除 |
| §三-3.2、§六-6 的 `yyyyMMddHHmmss` | **上报/交换层（全量 VO、国家/陕西 V2.0 数据规范）** | 不动；交换层转换仍收敛在 Service 公共方法 |
| §六-6 「输出及上报时转换」 | 措辞含"输出"，易被读成也管 admin 出参 | 建议条文加限定词「**上报/交换输出**」；本次先把实现统一到 admin=`LocalDateTime` |

**为什么前端零影响（实测，不是推断）**：平台的 Jackson 把 `LocalDateTime` 序列化成 **epoch 毫秒数字**——
`GET /admin-api/bidding/notice-external/manage/page` 实测返回 `publishTime=1789056000000 (number)`、`createTime=1789322311000`。
即：`Long`(手写毫秒) 与 `LocalDateTime`(平台序列化毫秒) 对前端是**同一个 JSON 数字**，
契约文档那句「时间字段为 epoch 毫秒数字（前端 `dayjs(Number(v))`）」依然成立、无需前端排期。
差别只在服务端：手写 `Long` 属规范不允许的出参类型，且各处重复实现换算（"改一处漏一处"）。

**ES 侧**：两索引同一字段名两种类型的问题已消——`bidding-notice.publishTime` 由 epoch 毫秒改为 ISO 字符串，
与 `bidding-notice-external` 一致，并显式声明 `{"type":"date","format":"yyyy-MM-dd'T'HH:mm:ss"}`（可正确按时间排序）；
索引已重建（实测 `creation_date` = 部署时刻、映射为 date）。

## 四之二、本轮顺带修掉的真缺陷（不是我这轮改出来的）
`EsNoticeSearchEngine`（内部公告检索）**完全没有 ES 认证代码**，而外部公告索引器有——
本地 ES 开安全认证时它每次调用都 **401**，而 `ensureIndex` 把异常吞成 debug 日志，
现场表现是"`bidding-notice` 索引从未建成、内部公告全文检索静默失效、reindex 只报 total/ok/failed 全 0"。
现已补上 Basic 认证（与外部公告索引器同口径）+ 索引创建失败改为 WARN 上报。

## 五、新增字段的强制口径（即日起生效，建议同步进规范时间章节）

1. **时刻**：Java 一律 `LocalDateTime`、库列一律 `datetime`、出参一律**不做手工格式化**（交给平台序列化）；命名统一 `xxxAt`（`startedAt`/`finishedAt`/`auditAt`/`aiReviewAt` …）；**例外（平台既有约定，不得改名）**：`createTime` / `updateTime`（框架 `BaseDO` 提供）。
2. **时长/间隔**：字段名与配置键必须带单位后缀——`xxxSeconds`（业务窗口、调度节奏）、`xxxMs`（HTTP/线程/执行耗时）、`xxxDays`（回溯窗口）；单位换算**只允许在转换点做一次**（如 `CrawlDownloadGate` 读源表的「秒」、yml 的「毫秒」只在兜底处换算）。
3. **时区**：部署必须以 `-Duser.timezone=Asia/Shanghai` 固定（容器默认 UTC 会让同一时刻在不同实例换算出不同毫秒/字符串）；代码统一走 `BiddingTimeUtils.ZONE`，禁止各写 `ZoneId.of(...)`。
4. **禁止**：手写 `atZone(...).toEpochMilli()`、各自 `DateTimeFormatter.ofPattern("yyyy-MM-dd'T'HH:mm:ss")`、在 VO 里放 `String` 时间。
