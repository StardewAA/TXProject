### 1.2 该不该做
- **应该做**。ATTACHMENT_CODE 是数据集 VO 的通用字段（报备/开标/评标报告均有），规范层面要求；招标文件/图纸/澄清文件是招标实务刚需。
- **机制统一**：项目/招标项目/标段/自营公告复用**同一套附件基础设施**（上传 → file_id + sha256 + 病毒扫描 + 附件清单），按实体维度关联，参照 bidding_notice_external_attachment 的三件套实现。
- 标段附件 ≠ 公告附件（语义不同：公告附件=招标文件/澄清/结果文件；标段附件=技术文件/图纸/工程量清单），但数据结构用同一套机制。

### 1.3 设计方案（用户裁定 2026-09-24：一对 N 附件表 + URL/对象存储）

（基础设施已就绪：`POST /bidding/file/upload` 已返回 `{ fileId, url, name, type, size, sha256 }`，底层为 infra 对象存储，URL 形如
`/admin-api/infra/file/{id}/get/bidding/attachment/xxx.pdf`——见契约 11；新增设计直接复用，无需再造上传通道。）

**① 附件表（一对 N，按主键关联）**：
```sql
CREATE TABLE IF NOT EXISTS `bidding_attachment` (
  `id`            bigint      NOT NULL AUTO_INCREMENT COMMENT '主键',
  `biz_type`      varchar(32) NOT NULL COMMENT '归属实体：PROJECT / TENDER_PROJECT / BID_SECTION / ANNOUNCEMENT',
  `biz_code`      varchar(64) NOT NULL COMMENT '归属实体业务编号（project_code / tender_project_code / bid_section_code / notice_code）',
  `file_id`       bigint      NOT NULL COMMENT '文件服务主键（infra file 表；一致性依据）',
  `url`           varchar(512) DEFAULT NULL COMMENT '对象存储访问地址（即时预览用；非一致性依据，规范 §5 三-5）',
  `name`          varchar(255) DEFAULT NULL COMMENT '文件名（展示）',
  `sha256`        varchar(64)  DEFAULT NULL COMMENT '文件指纹（红线 8 三件套）',
  `size`          bigint      DEFAULT NULL COMMENT '字节数',
  `type`          varchar(64)  DEFAULT NULL COMMENT 'MIME 类型',
  `virus_status`  varchar(16)  DEFAULT NULL COMMENT '病毒扫描状态（CLEAN/INFECTED/UNKNOWN，对齐外部公告）',
  `seq`           int         NOT NULL DEFAULT 0 COMMENT '同实体内的附件序号（展示顺序）',
  `remark`        varchar(255) DEFAULT NULL COMMENT '备注（如：招标文件/图纸/澄清）',
  `deleted`       bit(1)      NOT NULL DEFAULT b'0',
  `tenant_id`     bigint      NOT NULL DEFAULT 0,
  `creator`/`create_time`/`updater`/`update_time` 审计列,
  PRIMARY KEY (`id`),
  KEY `idx_biz` (`biz_type`, `biz_code`, `deleted`)
) ENGINE=InnoDB COMMENT='bidding 通用附件（项目/招标项目/标段/公告一对 N）';
```

**② 上传链路（复用现成）**：前端 multipart 上传 → `POST /bidding/file/upload`（返回 fileId+url+sha256）→ 后端存 `bidding_attachment`（file_id 为一致性键，url 仅预览）；
公开展示/下载时按 file_id 出签名 URL（对齐外部公告安全套件，INFECTED 不下发）。

**③ 各实体接入**：
- 四实体 DO 增加 `attachment_ids_json`（或直接按 biz_type+biz_code 反查，推荐后者，避免冗余）；
- VO 出参增加 `attachments: [{ fileId, url, name, size, virusStatus, seq, remark }]`；Save 入参接受 `[{ fileId, remark }]` 数组；
- 公告侧：payload 的 `ATTACHMENT_CODE`（附件编码，四类公告必填集均含）与附件表打通——`ATTACHMENT_CODE` = 附件表记录的规范编码，发布时校验非空。

**④ 归属**：项目域（表 + 项目/招标项目/标段接入）+ 公告域（公告接入 + ATTACHMENT_CODE 打通）。

## 二、必填校验阶段化重设计（本次用户质询引出，2026-09-24）

### 2.1 现状问题（2026-09-24 复核工作树：编号问题已解决，剩余校验仍挡草稿）
- **编号已不再是问题**：工作树项目域已实现编号自动生成——项目 projectCode（I 段 17 位）、招标项目 tenderProjectCode（所属项目 17 位 + 3 位序列 = 20 位）、标段 bidSectionCode（20 + 3 = 23 位），前端不输入不显示。
- **仍挡草稿的是名称/投资代码校验**：save 时 checkRequired 仍强制——项目 PROJECT_NAME + **INVEST_PROJECT_CODE**（24 位投资项目统一代码）；招标项目 TENDER_PROJECT_NAME；标段 BID_SECTION_NAME。
- **与同事已实现的业务流程冲突**：点击新建 → **直接创建空白草稿并落库，除系统自动生成的编号外全部字段为空（含名称）**——当前 save 必填校验会拦截空白草稿落库。
- 与状态机"新建默认 DRAFT"语义矛盾：草稿阶段必然字段不全，保存即被拦，无法"先存半个项目"。
- 24 位投资项目统一代码（INVEST_PROJECT_CODE）在**立项审批前必然为空**（政府未批，审批通过后才登记），当前却在创建时强制必填。

### 2.2 用户裁定方向（"用业务做规范，不是用数据库做规范"）
- **表不用重设计**：字段本就是 VARCHAR NULL，数据库层无 NOT NULL 硬约束（除主键/系统 code）。问题在**校验时机绑定错误**，不在表结构。
- **校验按状态机事件分级**（对齐规范 26 §5：状态变更必须走动作方法，动作方法内做校验→变更→联动）：
  | 阶段 | 事件 | 必填口径 |
  | --- | --- | --- |
  | 草稿保存 | save | **完全宽松：除系统生成编号外全空可落库**（同事"新建即落库空白草稿"流程即既定业务） |
  | 提交立项审批 | SUBMIT_APPROVAL | 立项必需字段；**24 位政府代码仍可空** |
  | 审批通过 → 立项 | APPROVE_PASS | 审批环节登记 24 位投资项目统一代码（ACTIVE 后才有的代码） |
  | 发布招标公告 | PUBLISH_TENDER_NOTICE | 公告数据集必填（招标文件完整字段） |
  | 数据同步上报 | 同步任务 | 按数据集"必填=是"全集校验 |
- 落地：把 checkRequired 从 save **移除/放宽**，必填校验全部移到状态流转事件钩子（SUBMIT_APPROVAL / PUBLISH_TENDER_NOTICE 前校验对应实体）；
  save 阶段只保留"系统生成编号 + 所属关系"的系统性校验（如标段必须有所属招标项目）；删除 save 时的 INVEST_PROJECT_CODE 必填（挪到 APPROVE_PASS 后登记）。

### 2.3 遗留问题确认（用户 2026-09-24 裁定：作为遗留问题记录）
- **草稿阶段不做必填校验**：除后端自动生成的编号外，名称/投资代码/数据集字段在 DRAFT 阶段均可为空、可落库。
- 同事的"点击新建 → 空白草稿直接落库（仅系统自动生成编号）"流程是**既定业务前提**，校验不得拦截它。
- 必填的**唯一强制点 = 状态流转事件**（提交立项审批 SUBMIT_APPROVAL / 发布招标公告 PUBLISH_TENDER_NOTICE 等），进入下一状态前一次性校验该阶段必需字段；**草稿永远不校验**。

### 2.4 归属：招标全流程代理（flow 状态机侧，加校验钩子）+ 项目域（ProjectServiceImpl 侧，放宽 save 校验）

### 6.4 文件存储合规增强项登记（2026-09-18，回应「只存 ID/URL 是否够」，均为平台/文件服务层，非附件表）

## 九、CA 互认与国密链路后端遗留契约（2026-09-28，前端联调登记）

> 本节只登记后端/部署侧遗留，不在前端伪造实现；前端 CA H5、签名快捷入口、SM3 接口调用及既有场景回归已完成。后端完成后须按验收条件回填结果并通知前端复测。

### 9.1 文件上传必须提供 SM3 文件指纹（归属：文件服务/附件域）
- **现状**：POST /bidding/file/upload 返回 fileId、url、name、type、size、sha256，未返回文件级 SM3；CA 签名和第十四条防篡改追溯要求使用 documentHash/document_hash（SM3，GB/T 32905，64 位小写 hex）。
- **契约要求**：上传成功响应增加 sm3；bidding_attachment 查询/保存响应同步提供该值。原 sha256 保留兼容，不得将 SHA-256 冒充 SM3。
- **验收**：重复上传、空文件、中文文件名和二进制文件均得到稳定且严格 64 位小写 hex 摘要。

### 9.2 签章结果必须业务落库（归属：CA 互认/交易业务域）
- **契约要求**：以 bizType + bizCode + fileId 幂等落库 documentHash、documentHashAlgo=SM3、documentSignature（SM2 Base64）、caCertNo、publicKeyAlgorithm、签章时间及 CA 机构信息。
- **验收**：签章后刷新仍可查询；文件替换或摘要变化时旧签名失效并要求重新签名；重复回调不产生重复记录。

### 9.3 第三十条投标文件加密/解密闭环（归属：交易平台/投标文件域）
- **契约要求**：递交前使用 SM4 加密，SM4 密钥使用 CA/SM2 信封封装；截止前平台不得取得明文；开标通过 decrypt/qrcode → status → user-info → envelope → data 完成授权解密。
- **接口口径**：POST /bidding/ca/decrypt 请求体为纯 Base64 字符串，不额外包 JSON 引号；caCertNo 等元数据走查询参数。
