## 1. 待决策（6 条，按"不决策的后果"排序）

### ① 法定下限口径 A/B/C —— **唯一"业务会出事"级别** ⚠️

**问题**：资质到期预警的"法定下限"（`cert.alert.legal.floor.days`）与**特种设备**类证照的**法定 180 天**存在冲突。
不决策的后果：**特种设备证照会在法定到期前就被判"预警已处理"或漏预警** → 合规风险（不是显示问题）。

**为什么我不能自己定**：这是**法律口径**，属企业合规责任，不是技术选择——三种方案对应三种责任边界。

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 按**证照类别**分别配下限（特种设备 180、排污 60…） | 要维护一份"类别→法定下限"表，且需法务确认取值 |
| B | 扫描时**强制不低于法定下限**（扫描口径兜底，配置只能更严） | 配置看起来能调、实际被兜底，容易被误解为"改了没反应" |
| C | **只修种子数据**（把 180 写进特种设备类别） | 最小改动，但依赖人记得以后新增类别时同步维护 |

**我的推荐**：A + B（A 保证取值正确，B 保证不会被误配绕过），但**必须先由懂资质的人确认 180/90/60 这些数字的出处**。

**2026-09-13 追加的硬证据（读契约 + 查代码后确证，问题比原先判断的更严重）**：

| # | 事实 | 位置 |
| --- | --- | --- |
| 1 | 写入期校验 `validateAlertThresholds`（唯一读 `cert.alert.legal.floor.days` 的地方）**零调用方**——生产代码、测试代码都没有 ⇒ **这个配置键在运行期毫无作用** | `RuleConfigServiceImpl`（校验方法） / 全仓 grep 仅接口声明+实现 |
| 2 | 该方法的词表是 `SEWAGE_PERMIT / SAFETY_PERMIT / BOILER_REVIEW`；而运行期真正生效的 `PersonnelAlertServiceImpl#legalFloorDays()` 是**硬编码 Map**，词表为 `POLLUTION_PERMIT / SAFETY_ASSESS_CERT / SKILL_CERT` ⇒ 两套名字指同一件事 | `RuleConfigServiceImpl` vs `PersonnelAlertServiceImpl` |
| 3 | 词表对不上时该方法**直接 `return`（静默放过）**，而不是报错 ⇒ 即使将来接线，这三类也会**悄悄跳过法定下限校验** | 同上，`floor == null → return` |
| 4 | 对外的 `GET /bidding/personnel-alert-run/legal-floor-days` 返回的是**硬编码 Map**（词表 2），而契约 §8.4 的 Mock 写的是词表 1 ⇒ 前端按契约做"即时对比"时，**安许/排污/司炉三类永远查不到、静默不告警** | §8.4 契约 vs 控制器+服务实现 |

**2026-09-13 第三条硬证据（根因）**：不是"忘了接线"，而是**接不上**——`cert.alert.thresholds` 是**全局数组** `[90,60,30,7]`，
而下限是**按类别**的 map；`validateAlertThresholds(certCategory, …)` 的签名要的是"按类别档位"，现实中不存在这种数据。
且承载该表的 `CertAlertConfigDO` **只有 DO + Mapper，没有 Service、没有 Controller** ⇒ 按类别档位连写入口都没有。
故第 3 步的正确形态是**口径决定（3-A 按类别改造 / 3-B 下限改全局 / 3-C 保留现状并更正契约表述 / 3-D 删除）**，详见补丁方案。

⇒ 结论：这不是"口径未定"，而是**这条合规防线目前整体是空的**（配置无人读、运行期认硬编码、对外暴露的词表与契约不符）。
无论最终选 A/B/C，都**必须先决定一件事：法定下限的"权威词表"是哪一套**（真实 `cert_type` 还是配置键那套）。
建议处置顺序：① 定词表 → ② 让运行期与对外接口共用同一份来源（并把硬编码 Map 收进配置）→ ③ 给校验方法接上调用点（或删除），
并在死方法门禁里登记 `RuleConfigService#validateAlertThresholds`（本轮已备好登记文案，因构建被他人改动中断未能验证，见 §4.7）。

**2026-09-13 又一条硬证据**：错误码 `LEGAL_FLOOR_VIOLATED`（1_060_108_009，"预警天数不得低于法定下限 {} 天（依据：{}）"）
**只有那个零调用方法在抛** ⇒ 契约 §1.2 承诺的"**后端才是最终裁判**：低于下限保存会被拒绝并返回法规出处"
**目前没有任何可达路径**（码定义了、没人抛）。已把该方法登记进死方法门禁（含 P0 说明），见 §4.7。

**➡️ 详细落地方案见《法定下限落地补丁方案.md》**（含：法定值 vs 代码值的逐条原文证据、
三套词表的对应关系、三步补丁的确切改动点与回归测试点、以及必须由人拍板的那一处）。
其中一条新增的重要事实：**代码里的数字是"缓冲值"而非"法定值"**（排污 60 = 法定 60 ✅；
建造师法定 30、代码取 90 ⚠️）⇒ 前端按契约提示"不得低于 N 天（依据：法规）"会把**政策缓冲说成法律义务**，
建议拆分"法定下限"与"建议预警值"两个概念。
**动了哪些文件**：`sql/history/2026-09-16-rule-config-center.sql`（种子）、`RuleConfigServiceImpl#validateBound`、契约 §规则键表。

## 3. 并发边界（为什么"能并行的"和"不能并行的"要分开）

- **可以并发**：只读分析（字段对账、键账目、SQL 一致性）——本轮已开 3 个只读子代理并行扫，结果见 §6。
- **不能并发**：任何**写**共享文件的操作（尤其 `sql/` 生成器与一键包）。并发写 = 互相覆盖，且**覆盖发生时不会报错**，
  只会在事后表现为"某人的改动凭空消失"。所以写操作在我这边一律串行、路径限定、提交可追溯。
- **也无法靠并发解决**：§1 的 6 条**不是任务而是决策**——并行只能让"做错的决定"更快落地。它们缺的是**权威口径**（法务/产品/流程），不是算力。

**§3.2 的缺陷（根因：该端点直接返回 DO，没有 RespVO）**
1. **字段名对不上**：契约文档化 `sha256`，接口实际返回 `fileHash`（`CertFileVersionDO.fileHash`）
   ⇒ 前端按契约取 `sha256` 得到 `undefined`，而"文件指纹核验"（§4.2）正依赖该字段；
2. **DO 直出**：`GET /bidding/certificate/file/list` 返回 `List<CertFileVersionDO>`，除契约 13 个字段外还吐出
   `tenantId`/`deleted`/`creator`/`updater`/`copyCreationTime`/`copyCreator`/`copyCause`/`remark` 等**未文档化字段**
   ⇒ 契约与实现之间没有稳定边界，改表就可能悄悄改接口。

**处置（已定）**：补 `CertFileVersionRespVO`，**字段名保持 `fileHash` 不变**——不采用"改名为 sha256"的方案，
因为**给已发布契约字段改名只会让前端返工、收益为零**；契约那处按"实现为准"更正（更正内容见给前端的通知文件）。
