# 接口相似实现归并结论 + 待接线清单（2026-09-13）

> 起因：用户口径「A. 真·相似实现（一个功能多个入口，建议后端评估合并）／B. 设计使然（文档写明口径）／C. 前端有包装、视图层没人调」。
> 本文是**后端评估结论**：哪些已合并、哪些按设计保留、哪些是前端接线问题。前端只读，后端不改对外契约、不删端点。

## 一、A 组逐条结论

| # | 组 | 现状取证 | 结论 | 本次动作 |
| --- | --- | --- | --- | --- |
| 1 | 全景追溯 ×3：`/project/trace`、`/tender-project/trace`、`/bid-section/trace` | 三者**早已共用一个实现**：`ProjectTraceServiceImpl` 三个入口只差"起点锚"（项目编号／招标项目编号／标段编号），随后全部汇入同一个 `aggregate(queryCode, queryType, projectCode, tenders)` | **不是重复，无需合并** | 文档写明：三入口=同一聚合的三个锚点；`/tender-project/trace` 前端未接线（见 C 组） |
| 2 | 取详情两种键 ×3：`/get` + `/get-by-code`（项目／招标项目／标段） | **端点层**：每对方法都共用同一个转换器（`toProjectResp`/`toTenderResp`/`toSectionResp`），唯一差异是查询键（`selectById` vs `selectXxxByCode`）；语义差异是有意的：`get` 缺失抛业务码（106_xxx），`get-by-code` 缺失返回 `null`（追溯联动要容忍未登记）。<br>**实现层是真重复** ✗：同一个"按编号取主档"谓词（`eq(编号)+LIMIT 1`）在 `ProjectServiceImpl` 与 `ProjectTraceServiceImpl` **各写了一份**，连空值兜底都不完全一致（追溯侧忘了判空就查询） | 端点**保留**（两种键都是真实用法）；实现层**已合并** | 收敛为三个 Mapper 的 `selectByCode`（唯一定义：编号空值直接返回 null + `LIMIT 1`），两个服务层改作薄委托；`getBidSectionByCode` 前端未接线（见 C 组） |
| 3 | 主体资格 ×2：`/subject-auth/eligibility`（平台侧，带 tenantId）与 `/subject/profile/eligibility`（本企业） | 出参同类型 `SubjectEligibilityRespVO`，但**作用域与权限码不同**（`subject-auth:query` vs `subject:query`），两个都在被前端调用 | **设计使然（B 类）**，不是重复 | 文档写明作用域/权限码差异 |
| 4 | 到期清单口径重叠：`/personnel-certificate/list-expiring` 与 `/page`（已支持到期窗口筛选） | **真重复且口径打架** ✗：三条路径三种实现——预警扫描 `selectExpiringCandidates` 用开区间 `(today, …]` 且**不过滤 `is_current`**；分页 `expiringDays` 用闭区间 `[today, …]` 且过滤 `is_current=true`；到期清单复用扫描方法又在 Java 内存里过滤 `entId` | **已合并（本次改动）** | 抽出唯一定义 `PersonnelCertificateMapper.applyExpiringWindow`：可用状态 + `is_current=1` + `valid_to ∈ [today, today+days]`；扫描／清单／分页三处全部改调它；`entId` 下推 SQL（不再内存过滤） |

### 第 4 条为什么必须合并（现场症状）
- 页面上筛"30 天内到期"显示 3 张，预警扫描却报 5 条 → 因为一个过滤 `is_current`、另一个不过滤；
- "今天到期"的证书在清单里看不到 → 旧扫描/清单用开区间 `>`，把最后一天漏掉；
- 到期清单的 `entId` 在 Java 内存过滤 → 多查一轮数据，且"清单口径"与"扫描口径"再次分叉。

统一后语义（**今天到期必须出现**）：`cert_status ∈ {VALID, EXPIRING_SOON}` + `is_current = 1` + `valid_to ∈ [today, today+days]`。
回归测试：`PersonnelCertExpiryWindowTest`（把口径钉死，谁改谁先红）。

### 第 2 条为什么也要动（实现层重复，不是端点重复）
- 同一个"按编号取主档"的谓词写了两遍：`ProjectServiceImpl.selectProjectByCode/selectTenderProjectByCode/selectBidSectionByCode`
  与 `ProjectTraceServiceImpl.selectProject/selectTender`（外加追溯里一段内联的标段查询）；
- 两处实现细节已经漂移：追溯侧没有判空就直接查询（空编号会打出无谓 SQL）；
- 后果是"改一处漏一处"——例如将来要给编号查询加索引提示/规范化（去空格、大小写），很容易只改一半。
- 现统一为 `ProjectMapper/TenderProjectMapper/BidSectionMapper.selectByCode`（编号空值直接返回 null + `LIMIT 1`），
  两个服务层只作薄委托。**端点、路径、权限码、出入参一律不变**。

## 二、B 组（设计使然，只写口径）

1. 公开端 vs 管理端字段集不同：见 `README.md` §7.6（公开端裁剪审核/AI/审计字段、`contentHtml` 恒 null 只下发 `contentHtmlSafe`；管理端全字段）。
2. 主体资格两入口：平台侧（带 tenantId，权限 `subject-auth:query`）用于"看别人/平台核查"；本企业（`subject:query`）用于"自查本企业"。同一出参、不同作用域，**保留**。
3. 取详情 `get` / `get-by-code`：**缺失语义不同**是有意设计——`get` 抛业务码（详情页要求必须存在）、`get-by-code` 返 null（追溯/联动场景允许"还没登记"）。

## 三、C 组（能力未接线，前端侧待办）

## 四、边界与回滚

- 本次改动**只动后端内部实现**：端点、路径、权限码、出入参一律不变，前端零改动。
- 唯一的行为变化在"到期窗口"：原先被 `is_current` 漏掉的历史证不再告警（更准）、"今天到期"的证书会出现在清单与预警里（更全）。
- 回滚点：`PersonnelCertificateMapper.applyExpiringWindow` 的区间/过滤条件（一处定义，改一处即全量生效）。
