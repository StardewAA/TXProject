## 议题一 · 审批工作台 → 爬虫任务工作台式查询

### 1.1 现状（代码实测，2026-10-01）

「审批工作台」= 菜单 60005604，组件 `bidding/flow/index.vue`（招标全流程目录下，2026-09-28 从「投标流程跟踪」拆出）。
当前交互是**单选实体 → 一次性全量拉详情**：

1. **实体选择**：实体类型下拉（项目 / 招标项目 / 标段）+ 实体编号下拉（show-search）。
   - 下拉候选 = `getProjectPage / getTenderProjectPage / getBidSectionPage` **pageNo=1 & pageSize=100 一次性拉取**（`loadEntityOptions`），show-search 只是**客户端**过滤这已加载的 100 条；
   - 没有服务端分页、没有关键字/状态筛选、没有"下一页"→ **实体一多（项目/招标项目/标段逐年累积）下拉即卡、也没法按状态管理**。
2. **选中即全量并行**：`onEntityPick` → 一次并发 5 组请求（next-actions + timers + logs + 实体完整主档 getXxxByCode + 附件），每次切换实体全部重发 → 高频切换明显卡顿。
3. 页面其余 5 个面板（当前状态+可执行动作 / 审批对象全景+附件 / 时间驱动调度 / 流转留痕 / 政府审批 stub）都是**好的资产**，问题只在「实体选择」这一段。

**爬虫任务工作台（对照目标）**：`crawlExternal/job|source/index.vue` 用 `useVbenVxeGrid`：
`formOptions.schema`（查询表单，字段少、可折叠）+ `toolbarConfig.search/reset/refresh` + `proxyConfig.ajax.query`（**服务端分页** pageNo/pageSize + 表单参数）+ 行「详情」按需打开。这就是"按分页查、不卡、好管理"的形态。

### 1.2 目标形态（照爬虫工作台改，后端零改动）

```
+-- 查询表单（schema 驱动，折叠时只露一行）----------------------+
|  实体类型 [v]  关键字[名称/编号]____  状态 [v]  [查询] [重置]    |
+-- 实体列表（vxe-grid，服务端分页）----------------------------+
|  项目/招标项目/标段 列表行（名称·编号·状态）  [打开]  分页器      |
+-- 选中行 → 下方/抽屉：现有 5 面板原样复用 ----------------------+
|  当前状态+可执行动作 / 对象全景+附件 / 调度 / 留痕 / 政府审批    |
+-------------------------------------------------------------+
```

- 实体选择从「100 条下拉」换成「查询表单 + 分页表格」，行「打开」时才加载 5 面板；
- 后端复用：`ProjectApi.PageParams` 已支持 projectCode/projectName/state 等筛选 + 分页（项目台账页在用同一接口）；TENDER_PROJECT / BID_SECTION 同类 page 接口同理——**纯前端改造**；
- 5 个面板与流转/政府审批弹窗代码**零改动**，只把"选中"从下拉改为行选、把"切换即 5 连发"改为"打开时加载 + 去抖/禁用连点"。

### 1.3 成本与风险

| 项 | 说明 | 人日 |
| --- | --- | --- |
| 查询表单 schema（类型/关键字/状态 + 查询/重置） | vxe formOptions，参考 crawlExternal 现成写法 | 0.5 |
| 实体列表 vxe-grid + 服务端分页 + 行打开联动 | 替换下拉，行选回调复用现有 loadFlow/loadEntityDetail | 0.5~1 |
| 加载策略（打开才取详情、切换去抖、loading/空态） | 防连点卡顿 | 0.5 |
| 回归（5 面板、流转弹窗、政府审批 stub、三种实体类型） | e2e 截图取证 | 0.5~1 |
| **合计** | | **1.5~3** |

风险：
- R1（低）：TENDER_PROJECT / BID_SECTION 的 page 接口关键字/状态参数名需逐个核对（若缺则补前端参数或小契约），影响 0.5 人日以内。
- R2（需你拍板）：原设计裁定「不允许手填编号、一律下拉带出」——改列表查询后该裁定自然放宽为「列表可查可点」，语义等价但**形式上推翻了原裁定**，需要你确认。
- R3（低）：行选后仍是 5 个并行接口，需按「打开时才发 + 切换期间禁点」处理，避免回到"切一下卡一下"。

## 议题二 · 门户公告大厅：进入详情返回后筛选重置

### 2.1 根因（代码实测，非猜测）

`views/portal/bidding/index.vue`（大厅）的全部筛选与结果状态都是**组件内局部状态**：

- `state = reactive({ keyword, code, codeDim, noticeType, sourceCode, contentType, industry, quick, customOn })` + `pageNo / rows / total / totalTruncated` 等 **15+ 项**，没有任何持久化；
- 门户布局 `layouts/portal.vue` 是普通 `<RouterView>`（**无 KeepAlive**）；大厅（/portal/bidding）与公告详情（/portal/bidding/detail/:id、/internal-detail/:id）是两个路由组件；
- 点公告 → 路由切到详情 = **大厅组件被销毁**；浏览器返回 → **重新挂载** = 状态全部归零 → 必须重筛。

### 2.2 修复方案对比与风险

| 方案 | 做法 | 成本 | 风险 |
| --- | --- | --- | --- |
| **1 sessionStorage 持久化（推荐）** | 筛选/页码在变更时写入 sessionStorage（键=路由名）；组件挂载时若有存档 → 恢复筛选并自动重查；清空筛选/点重置时清除存档 | 0.5~1 人日 | **低**。不动共享布局；刷新页面同样保留；注意恢复后走同一条「fetchHallPage → 合并本站 → 分页切片」加载路径 |
| 2 keep-alive 缓存大厅组件 | 门户布局 RouterView 加 KeepAlive include=[PortalBidding] + onActivated 刷新 | 0.5~1 人日 | 中低。改动共享布局（影响所有门户页，需 include 精确隔离）；重进要 onActivated 主动刷新否则脏数据；滚动位置另记 |
| 3 URL 查询参数回显 | 筛选变更即 push query（keyword/type/source/quick…），返回由 URL 还原 | 1~1.5 人日 | 中。10+ 字段序列化/反序列化易漏、pageNo 与 quick 联动要处理；好处是可分享"带筛选的链接" |

### 2.3 结论

- **推荐方案 1**：成本 0.5~1 人日、风险低、不动布局、刷新不丢；若将来要"分享带筛选的链接"再叠加方案 3（可后置，不冲突）。
- 共通风险（如实）：恢复后若期间有新公告爬取入库，结果与离开时不同——属**预期行为**（重新查询的结果），不是缺陷；大厅异步合并窗口逻辑需保证恢复后仍按同一路径执行，回归时用现有 e2e 覆盖。
