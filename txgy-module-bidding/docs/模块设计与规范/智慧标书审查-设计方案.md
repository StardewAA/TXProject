## 〇、先划边界（避免过度设计）

### 已锁定口径（2026-09-16）

| # | 决策项 | 取值 |
|---|---|---|
| 1 | AI 供应商 | **DeepSeek 官方 API**（`https://api.deepseek.com/v1`，默认模型 `deepseek-chat`），**单通道、不接第二家** |
| 2 | 调用方式 | 模块内直连 `POST /chat/completions`，**不经 AI 模块**，不复用平台/CRM 的 Key |
| 3 | 密钥 | 本模块专属 `BIDDING_REVIEW_AI_API_KEY`；环境变量注入，不入库、不进日志、不回前端 |
| 4 | 扫描件 | DeepSeek 无视觉模型 → **不做图片转写**，直接提示用户上传文字版 PDF/Word；OCR 留 P2 |
| 5 | 「一键生成」 | = 生成**审查报告**（问题清单 + 整改建议 + 评分预估），不含"整改后的标书成稿" |
| 6 | 招标文件 | 可选上传：传了按本项目要求逐条比对；没传则只按平台规则库自查，报告注明「未使用招标文件要求」 |
| 7 | 报告效力 | 内部参考件：报告页标注「AI 生成，需人工复核」，不设签章位 |

**本期做**：

1. 个人端（门户）：**上传投标文件（标书）→ 点「一键生成」→ 等待进度 → 查看/下载审查报告**。个人端没有规则编辑、没有复核、没有评分调整。
2. 管理端（后台）：审查**规则库**维护（平台级模板）、**审查任务**看板（列表/进度/重试）、**审查结果复核**（确认/忽略/补充意见）、**报告**查看与导出、**统计**（通过率、高频问题）。
3. 审查内容：**响应性/形式合规检查（废标项逐条核对）+ 招标文件要求命中检查（资格、业绩、人员、格式） + 评分办法自评估分**。
4. 审查依据双来源：**平台规则库**（管理端维护，跨项目复用）+ **招标文件 AI 解析出的项目级规则**（上传招标文件时抽取）。

**本期不做（明确登记，见 §12）**：远程/云端 OCR 服务、标书自动改写与整改后成稿、专家评审流程、与财评/电子签章联动、跨租户对标。

## 一、角色与场景

| 角色 | 入口 | 能做的事 | 不能做的事 |
|---|---|---|---|
| 个人端用户（投标经办人） | 门户 `/portal/bidding/bidReview` | 上传标书、一键生成、看进度、看/下载报告、删除自己的记录 | 改规则、改评分、看别人的任务、发布报告 |
| 管理端用户（招投标管理员） | 后台「招投标 → 智慧标书审查」 | 维护规则库、建/派任务、复核问题项、重跑、导出报告、看统计 | — |
| 系统（AI/调度） | 本模块定时任务 + **直连 DeepSeek（专属 Key）** | 解析文件、抽规则、逐项比对、汇总出报告 | — |

> 口径提醒：本方案把「一键生成」理解为**一键生成审查结果与审查报告**（含问题清单 + 整改建议 + 评分预估）。若业务要的是「一键生成整改后的标书成稿」，属于文档生成能力，见 §12 第 1 条预留。

## 二、关键设计决策（含取舍理由）

### 2.1 以「审查任务」为核心聚合，一次上传 = 一个任务

标书审查是**长耗时、多步骤、可失败重试**的过程，不能同步返回。因此：

- 任务表 `bidding_bid_review_task` 承载状态机、进度、结论；文件、规则集、问题项、报告都以 `task_id` 挂载。
- 个人端「一键生成」= 创建任务 + 立即触发流水线；前端只轮询进度接口（1.5s 间隔，后端返回 `step/progress/status`）。

### 2.2 规则来源双轨：平台规则库 + 招标文件解析

| 轨道 | 谁维护 | 存哪 | 适用 |
|---|---|---|---|
| 平台规则库 | 管理端 | `bidding_bid_review_rule_set` / `_item`（`source=PLATFORM`） | 通用废标项、格式要求（投标函、法定代表人授权书、保证金凭证、盖章签字等），跨项目复用 |
| 项目级规则 | 系统（AI 从招标文件抽取）+ 管理端可校正 | 同两张表（`source=TENDER_DOC`，带 `tender_file_id`） | 本项目特有的资格条件、业绩门槛、评分办法分值 |

理由：只靠 AI 抽规则不稳定，只靠固定规则库又覆盖不了项目个性化要求；双轨后「一键生成」在**没传招标文件**时也能跑（退化为平台规则库 + 纯合规自查），传了招标文件则自动升级为**按本项目要求逐条比对**。

### 2.3 正文与文件：文件只存 `file_id`，正文按内容表版本化

- 上传统一走既有 `POST /admin-api/bidding/file/upload`（`BiddingFileService`），业务表只落 `file_id / file_name / sha256 / size`，不落 BLOB、不把 URL 当一致性依据（规范 §5.3 第 5 款、红线 8）。
- 解析出的标书正文/结构化章节/AI 原始返回属「内容型文本」，按规范 §5.3 第 2 款落 `bidding_bid_review_content`（追加式版本，`UNIQUE(biz_id, content_type, version, deleted)`）。这样重复生成不覆盖历史，复核时有据可查。

### 2.4 AI 由本模块直连大模型，且使用本模块专属 API Key（不经 AI 模块）

两条硬口径：**① 不调 AI 模块（ai-server）；② 用审查模块自己的 Key，不复用 CRM / 平台的 `DASHSCOPE_API_KEY`。**

仓库里已有同构先例可照搬：CRM 的 `framework/ai/core/CrmAiIntentClient` 就是模块直连千问兼容接口（`{baseUrl}/chat/completions` + `response_format=json_object`，配置项 `txgy.crm.ai.*`，密钥环境变量注入）。本模块照此实现，但**配置前缀、密钥变量、客户端类都独立**：

| 项 | 本模块取值 | 说明 |
|---|---|---|
| 配置前缀 | `bidding.review.ai.*` | 与公告域 `bidding.ai.*`、CRM `txgy.crm.ai.*` 并列、互不干扰 |
| 密钥变量 | `BIDDING_REVIEW_AI_API_KEY` | **专用密钥**，不出现在任何共用变量里 |
| base-url | `${BIDDING_REVIEW_AI_BASE_URL:https://api.deepseek.com/v1}` | DeepSeek 的 OpenAI 兼容端点（`/v1` 只是兼容别名，与模型版本无关） |
| model | `${BIDDING_REVIEW_AI_MODEL:deepseek-chat}` | 支持 JSON 输出，作为默认；`deepseek-reasoner` 需走 `json-mode: false`（见下方约束 ②），不作默认 |
| json-mode | `${BIDDING_REVIEW_AI_JSON_MODE:true}` | 是否带 `response_format={"type":"json_object"}`；换 reasoner 类模型时置 false |
| 客户端 | `service/bidreview/ai/BidReviewAiClient` + Impl | `java.net.http.HttpClient` + Jackson，**零新增依赖**；只需 `chatJson(system,user)` 一个方法（无视觉，不做图片入参） |

**为什么坚持独立 Key**：审查是高频长文调用，成本与失败率都高；独立 Key 后可单独计量、单独限流、单独吊销，**出问题不会连累 CRM AI 助手与公告域 AI 抽取**，也不会被别人的配额挤占。反面代价是失去了平台统一管控（见 §12 第 7 条），实施时用「调用流水 + 失败率告警」补上。

**DeepSeek 的三条硬约束（不写进实现一定踩坑）**：

1. **JSON 模式有前置条件**：除 `response_format={"type":"json_object"}`，提示词里必须出现 "json" 字样，否则接口直接报错；官方还建议给一个输出示例，避免返回空 `content`（空内容按失败处理，**不当作"无问题"**）。
2. **`deepseek-reasoner` 与 `deepseek-chat` 参数不同**：reasoner 不支持 `response_format`、`temperature`、`top_p`、penalty 类参数，响应里多一个 `reasoning_content`——解析时**只取 `content`，忽略 `reasoning_content`**。本期默认 `deepseek-chat`。
3. **DeepSeek 开放 API 目前没有视觉/多模态模型**：扫描件标书不能"页码转图片喂模型"。本期策略：解析不出文字 → 直接 `FAILED(PARSE_EMPTY)` 并提示上传文字版；本地 OCR 列 P2（§11 第 2 条）。

> 以上以 DeepSeek 官方文档为准；实施第一步就用 `POST /bidding/bid-review/config/ai-probe` 实测端点、模型名、JSON 模式三条都通。

密钥落位（三处，均不进仓库）：

1. `txgy-module-bidding-server/src/main/resources/application.yaml`：`bidding.review.ai.api-key: ${BIDDING_REVIEW_AI_API_KEY:}`。
2. `deploy/.env`（真实值）+ `deploy/.env.example`（占位 `BIDDING_REVIEW_AI_API_KEY=`）。
3. `deploy/local/docker-compose.server-bidding.yml` 的 bidding 服务环境变量：`BIDDING_REVIEW_AI_API_KEY: ${BIDDING_REVIEW_AI_API_KEY:-}`。

其余实现要点：

- 协议：OpenAI 兼容 `POST {base-url}/chat/completions`（DeepSeek 即 `https://api.deepseek.com/v1/chat/completions`），提示词含 "json" 字样 + `response_format={"type":"json_object"}`；取 `choices[0].message.content` → 剥 markdown fence → JSON 解析；`reasoning_content` 忽略。
- 文件解析：文本走既有 `service/noticeexternal/pdf/PdfContentExtractor`（PDFBox，文本 + 表格），DOCX 走 POI；**扫描件（无文字层）本期直接判 `FAILED(PARSE_EMPTY)`**，提示"请上传文字版 PDF/Word"——图片转写这条路暂时不通。
- 与公告域 AI 的关系：**两条链路互不依赖**。公告域 `AiHttpSupport`（走 AI 模块）保持原样，本域不引用、不改动、不共用 Key。

### 2.5 异步执行：任务表 + 有界线程池（P0），调度兜底（P1）

- P0：`@Async("bidReviewExecutor")`（core 2 / max 4 / queue 50）+ 任务表状态机；拒绝策略为「入队失败即标 `QUEUED` 等待调度扫描」，不做无界队列。
- P1：加 `BidReviewJob`（风格对齐 `job/SafetyRiskJob`），每 1 分钟扫描：`QUEUED` 超 1 分钟未启动 → 重新投递；`RUNNING` 超 30 分钟无心跳 → 标 `FAILED(TIMEOUT)`。**不引入 MQ**，与外部采集域保持同一实现风格。

### 2.6 个人端端点独立命名空间 + `.self` 权限码，防越权

现状：门户页面调用的是 `/bidding-api/bidding/**`（dev 代理）→ 落到 admin 控制器，且**门户目前没有任何自助写接口**（见契约 22）。本方案新增个人端端点，规则：

- 路径统一 `POST/GET /bidding/bid-review/portal/**`，**入参不收 `userId`**，一律用 `getLoginUserId()`（`SecurityFrameworkUtils`）定位本人，查询一律带 `owner_user_id = 当前用户`，管理端无权复用这些端点。
- 权限码独立成段：`bidding:bid-review:self:create|query|delete`，由角色授权；前端用门户既有 `usePortalCan()` 控制按钮（未下发时放行，最终由后端裁决）。
- 个人端**不做**规则/评分修改，报告只读（`bidding:bid-review:self:query`）。

## 三、领域模型与表清单

### 3.1 表清单（域前缀 `bidding_bid_review_`，新域先登记；错误码段见 §11）

| # | 表 | 轨 | 说明 |
|---|---|---|---|

```sql
  `deleted`         bit(1)       DEFAULT b'0',
  PRIMARY KEY (`id`),
  KEY `idx_task` (`task_id`, `severity`),
  KEY `idx_task_status` (`task_id`, `status`)
) COMMENT='智慧标书审查问题项';
```

## 四、端到端流程与状态机

### 4.1 个人端（最简路径，只有两步操作）

```
① 上传标书（可选再传招标文件）
     POST /admin-api/bidding/file/upload  →  { fileId, name, sha256, size }
② 点「一键生成」
     POST /admin-api/bidding/bid-review/portal/create-and-generate
     →  返回 { taskId, taskNo, status: QUEUED }
③ 进度条（前端 1.5s 轮询）
     GET  /admin-api/bidding/bid-review/portal/progress?id=xx
     →  { status, currentStep, progress, errorMsg }
④ 出结果：问题清单（按严重级别分色）+ 结论 + 自评得分
     GET  /admin-api/bidding/bid-review/portal/get?id=xx
⑤ 下载报告
     GET  /admin-api/bidding/bid-review/portal/report?id=xx   → pdf/word 预览地址
```

### 4.2 后端流水线（一个任务四步）

| 步骤 | step | 做什么 | 失败处理 |
|---|---|---|---|
| 1 | `PARSE` | `bid_file_id` 取文件 → PDF/DOCX 抽文本+表格（PDFBox / POI）；写 `_content(BID_TEXT/BID_STRUCT)` | 空文本（扫描件）→ **不调模型**，直接 `FAILED(PARSE_EMPTY)`，提示「扫描件请上传文字版 PDF 或 Word」 |
| 2 | `RULE` | 有 `tender_file_id` → AI 抽规则集（`_rule_set/_item`，管理端可校正）；无 → 取平台默认规则集 | AI 超时 → 重试 1 次 → 仍失败则**降级**为平台规则库（状态仍 SUCCESS，报告标注「未使用招标文件要求」） |
| 3 | `GENERATE` | 按规则分组批量比对：规则类走确定性匹配（关键词/正则/字段存在性），语义类走 AI；逐条产出 `_issue`（含原文片段定位） | 单条失败跳过并记 `_ai_log`，不整体失败 |
| 4 | `REPORT` | 汇总分项得分、结论（PASS/RISK/FAIL）、高频问题摘要 → `_report` + `_content(REPORT_MD)`；渲染 PDF/Word 存 `file_id` | 报告渲染失败标 `FAILED(REPORT_RENDER)`，问题清单仍可看 |

### 4.3 状态机

```
QUEUED ──启动──▶ RUNNING ──成功──▶ SUCCESS
   ▲               │  │
   │               │  └──异常/超时──▶ FAILED ──retry──▶ QUEUED
   └──取消─────────────────── CANCELED
```

- 结论与状态解耦：`SUCCESS` 只是「跑完了」，结论看 `verdict`（`FAIL` = 命中高危废标项，`RISK` = 有中低风险，`PASS` = 无问题）。
- 同一 `(tenant_id, owner_user_id, bid_file_sha256, tender_file_id)` 在 24 小时内命中历史成功任务时，直接复用解析与问题清单（`_ai_log` 标注 `REUSE`），节省 token——个人端会反复传同一份标书试。

## 六、AI 审查设计（决定「智慧」是否靠谱的地方）

### 6.1 提示词分三层，输出强约束

1. **系统提示（固定）**：角色 = 招投标评审专家；输出**只能是 JSON**（不得回传全文、不得 markdown 包裹）；每条问题必须给出 `hitLocation`（页码/章节）与 `evidenceText`（原文片段，≤200 字）；无法定位时必须返回 `evidenceLack=true` 而不是编造。
2. **规则提示（动态）**：把当前批次的规则项（`rule_code/category/requirement/check_mode/score_max`）作为 JSON 传入，要求逐条给 `ruleCode + result(PASS/RISK/FAIL/NOT_FOUND) + reason`。
3. **正文提示（分块）**：按章节/页码切块（单次内联长度取 `bidding.review.ai.chunk-size`，默认 **3 万字符**——DeepSeek 的上下文与最大输出预算比千问系紧，取保守值），块内先做「章节-规则相关性」筛选，只把相关块喂给模型，控制成本与精度。

### 6.2 两阶段 + 一次汇总

```
阶段 A（有招标文件时）：招标文件正文 → 规则集 JSON（含条款定位）
阶段 B：规则 × 标书相关章节 → 命中结果 JSON（逐条）
阶段 C（可选，管理端复核用）：AI 二次评分校准 + 整改建议润色
```

阶段 A 的产出**必须落库并可人工校正**（管理端规则集页），后续任务可复用；阶段 B 是耗时的主循环，按「10 条规则一批」并发调用（线程池 max 4）。

### 6.3 输出校验与兜底（不许"看起来成功"）

| 情况 | 处理 |
|---|---|
| JSON 解析失败 | 重试 1 次（重试提示词强制"仅输出 JSON"并确保出现 json 关键字——DeepSeek JSON 模式的前置要求），仍失败 → 该批次标 `AI_PARSE_FAILED`，降级为规则关键词匹配 |
| 缺 `evidenceText` | 问题项标 `证据不足`，`ai_confidence ≤ 0.5`，默认不计入高危 |
| 模型编造的 ruleCode | 丢弃该条并记 `_ai_log`（用规则集白名单过滤，防幻觉） |
| 超时 | 单次 `bidding.review.ai.timeout-seconds`（默认 60s），失败按 `retry-times` 指数退避；任务级 30 分钟封顶 |
| 扫描件 | 阶段 1 文本为空 → **不产生任何模型调用**，直接 `FAILED(PARSE_EMPTY)` 并提示用户换文字版（DeepSeek 无视觉模型；OCR 属 P2） |
| Key 无效/过期 | 模型返回 401/403 → 不重试，落 `_ai_log`，任务标 `AUTH_FAILED`，错误码 `BID_REVIEW_AI_KEY_INVALID`，同时在管理端配置页高亮提示"密钥失效" |

### 6.4 直连客户端的工程要求（自己调模型、自己持 Key，就得自己兜住）

| 关注点 | 做法 |
|---|---|
| 密钥隔离 | 只读 `BIDDING_REVIEW_AI_API_KEY`：不落库、不进日志、不回前端（配置接口只回掩码 `sk-****abcd`）；**任何代码都不得回退读取 `DASHSCOPE_API_KEY`**，避免和 CRM/公告域串用 |
| 可用性判定 | `isAvailable()` 三重判定（enabled + base-url + api-key）；缺失时**不在启动期 fail-fast**（服务能起来），只在调用点报 `BID_REVIEW_AI_DISABLED`（CRM 同款处理） |
| 重试 | 连接异常 / 5xx / 429 → 指数退避重试 `retry-times`（默认 2）；401/403/400 不重试，直接降级 |
| 限流 | 客户端级信号量 `concurrency`（默认 4）+ 单任务批次串行，防止一键生成打满该 Key 的配额 |
| 审计与计量 | 每次调用落 `bidding_bid_review_ai_log`：`model / step / prompt_digest / request_chars / response_chars / cost_ms / status`；prompt 只留摘要哈希（标书含敏感内容）；按 `tenant_id + model` 可单独统计本模块 token/费用 |
| 自检与告警 | 提供 `config/ai-probe` 主动自检；统计近 1 小时失败率 > 50% 或出现 401 时，管理端配置页给出显式告警（密钥轮换有据可依） |
| 供应商绑定 | 默认 DeepSeek（`deepseek-chat`）；`base-url`/`model`/`json-mode` 全走配置，切内网私有化（vLLM/Ollama）或其它兼容端点都不改代码；切 reasoner 类模型需同时关 JSON 模式 |
| 可替换 | 客户端是接口：将来若改回统一走平台 AI 模块，只换实现类与配置，流水线不动 |
| 成本控制 | 阶段 A 结果按 `tender_file_sha256` 复用；同 `(bid_file_sha256, rule_set_id)` 24h 内命中历史成功任务直接复用问题清单，不重复烧 token |

## 九、验证方式

1. 编译：`mvn -o -pl txgy-module-bidding-server -am test-compile`。
2. 单测（无 DB/无 AI，Mockito）：状态机迁移与非法迁移拒绝；AI JSON 解析（含 fence、脏字段、缺 evidence）；规则白名单过滤（防幻觉）；`(tenant, owner)` 越权读取他人任务必须失败；幂等键重复提交只产生一个任务。
3. 端到端（本地 48110 直连，脚本落 `script/bid-review-demo/`）：
   - 剧本 1（个人端）：登录 → 上传标书 PDF → `portal/create-and-generate` → 轮询至 SUCCESS → 拉问题清单 → 下载报告；断言：问题项均带 `evidence_text`，无 `ruleCode` 越界。
   - 剧本 2（管理端）：建规则集 → 传招标文件解析规则 → 建任务指定标书 → 生成 → 复核两条问题（确认/忽略）→ 报告导出；断言：复核状态与报告一致。
   - 剧本 3（降级）：把 `bidding.review.ai.enabled=false`（或清空 `BIDDING_REVIEW_AI_API_KEY`）→ 一键生成仍返回 SUCCESS（仅规则匹配），报告标注「AI 未启用」；**密钥缺失时服务必须能正常启动**，只在调用点报 `BID_REVIEW_AI_DISABLED`。
   - 剧本 4（换模型/换端点）：① 把 `model` 换成 `deepseek-reasoner` 且 `json-mode=false`，跑通一条规则比对；② 把 `base-url` 指向本地 Ollama / vLLM 兼容端点 —— 验证"换模型只改配置、不改代码"。
   - 剧本 5（Key 隔离）：只配 `BIDDING_REVIEW_AI_API_KEY`、**清空** `DASHSCOPE_API_KEY`，审查任务仍能成功 → 证明没有复用 CRM/平台的密钥；再把 `BIDDING_REVIEW_AI_API_KEY` 换成无效值，断言任务标 `AUTH_FAILED`、错误码 `BID_REVIEW_AI_KEY_INVALID` 且不重试。
   - 剧本 6（扫描件）：上传图片型（无文字层）PDF → 任务在 `PARSE` 步失败并给出"请上传文字版"文案，且 `_ai_log` 里**没有任何模型调用记录**（不浪费 token、不误报通过）。

## 十二、风险与待确认口径（实施前请业务拍板）

1. **「一键生成」的确切含义**：生成**审查报告**（本方案默认）还是生成**整改后的标书**？后者会显著扩大范围（见 §11 第 1 条）。
2. **招标文件是否必传**：本方案设计为「可传可不传」（不传则仅按平台规则库自查）。若业务要求"必须按本项目招标文件比对"，则个人端要多一步上传招标文件，且报告结论口径更严格。
3. **报告对外效力**：审查报告是内部参考件还是可对外提交的正式件？影响是否需要固定模板、编号、签章位。
4. **评分办法分值的来源**：AI 从招标文件推断的满分/权重是否可作为自评依据？若不可信，`score_total` 应只作参考并在报告上明示「AI 预估」。
5. **数据密级**：标书可能含商业敏感信息（报价、业绩），需按规范 §4.8 确认 L2/L3 密级、日志脱敏，以及**是否允许把标书正文发给 DeepSeek 公有云**——直连模式下数据从本服务直接出网，不受平台 AI 模块的渠道管控；若不允许，把 `base-url` 改指内网私有化端点即可（代码不用改）。
6. **本地联调前置**：目前本机栈缺 28 张表（含 `bidding_dict_data`/`bidding_rule_config`）；改造后 AI 只需**模型端点可达 + 一个专用 API Key**（`BIDDING_REVIEW_AI_API_KEY`），**不再依赖网关 48080 与 ai-server**。补齐建表 + 配好密钥即可端到端验证。
7. **密钥归属与轮换**：模块自持专属 Key 等于绕开平台统一管控，需明确谁申请、谁轮换、失效如何告警。建议在 DeepSeek 开放平台按子业务单独建 Key（便于独立计量与吊销），并落地 §6.4 的失败率/401 告警与 `ai-probe` 自检。

### 编写原因

用户提出「前台智慧标书审查」需求，要求分管理端与个人端、且**个人端只做上传文件和一键生成**。需要一份能直接指导实施的方案：说清表结构、接口、AI 审查链路、前端落点与分期边界，避免"AI 一句话出报告"这种不可复核的实现，也避免个人端被做成第二个管理端。

### 编写依据

《招投标模块开发规范》（§4.2 分层 / §4.4 接口与数据约定 / §4.5 幂等 / §4.7 错误码 / §4.8 密级 / §5 建表与租户轨）；
`docs/前端规范-全域接口说明/11-文件上传与file_id契约-2026-09-10.md`、`22-门户个人自助录入接口请求-2026-09-14.md`、`12-字典元数据读取权限契约`；
DeepSeek 开放平台接口约定（OpenAI 兼容端点 `POST /chat/completions`、JSON 模式要求提示词含 "json"、`deepseek-chat` 与 `deepseek-reasoner` 的参数差异、无视觉模型）；
代码事实源：`txgy-module-crm/.../framework/ai/{config/CrmAiProperties,core/CrmAiIntentClient}.java`（**模块直连大模型的既有先例**：HttpClient + `/chat/completions` + `response_format=json_object` + 专属配置前缀 + 密钥环境变量注入、缺失不 fail-fast）、`service/noticeexternal/ai/*`（公告域走 AI 模块的对照实现，本方案不再复用）、`service/noticeexternal/pdf/*`（PDF 抽取 SPI）、`service/file/BiddingFileService`（file_id 契约）、`framework/ruleconfig/*`（可配置项）、`job/SafetyRiskJob`（调度范式）、前端 `views/portal/bidding/*` 与 `router/routes/core.ts`（门户路由硬编码）、《员工资质与证件生命周期-设计说明》的文档体例。

| 需求 | 实现方式 |
