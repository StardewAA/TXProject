## 四、本轮机械扫描结果：10 个"无生产调用者"的服务方法（已逐个核实证据）

扫描口径：本模块 `service/**` 接口方法 → 在 main 源码里找调用（排除方法自身声明行）。
**已验证检测器有效**：把 `QualificationController` 排除后，`markAlertHandled` 立即被判死 —— 即本门禁**在本轮修复前就能抓到缺陷 4**。

| 方法 | 分类 | 影响 | 建议 |
| --- | --- | --- | --- |
| `CertFileVersionService#markScanResult` | DEBT | 病毒扫描结果写不回去：`INFECTED` 无法置隔离；反之文件永远停在 `PENDING`，CLEAN 也到不了 → 预览/下载链路断。**并且全仓 grep `CLEAN` 无任何校验点**：注释与方案写的"CLEAN 才可预览/下载"在代码里不存在（见 §六.3） | 接扫描组件（Job 或回调端点）；"CLEAN 才可下载"的拦截点需明确归属（本模块无下载端点） |

## 五、门禁：`DeadServiceMethodGateTest`

- **口径**：`service/**` 接口方法必须在本模块 main 里有调用者；无调用者必须登记到 `UNCALLED_REGISTRY`（写明 DEBT/OTHER/CROSS 与理由）。
- **双向棘轮**：新出现无出口方法 → 失败；登记项恢复调用者 → 也失败（要求移除登记，防白名单腐烂）。
- **自检**：合成本例钉住"声明 ≠ 调用"（本门禁第一版探索脚本正是把声明当调用，导致**永远判不出死方法**，实测漏掉 `markAlertHandled`）。
- **局限（如实登记）**：① 只扫本模块 `service/**`（`api/**` 是跨模块契约，调用方在别处）；② 按方法名判定，不区分重载；③ 看不到反射/SpEL/跨模块调用 —— 故 CROSS 项必须人工确认，门禁不能替代评审。

## 六、本轮新增发现（两处，均需你决策）

### 6.1 已修：边界校验可以"由请求方关掉"（RuleConfigServiceImpl#validateBound）

保存路径原来只信任**请求里传来的** `legalFloor`：`validateBound` 见空即 `return` → 请求不带这个字段，边界校验整段跳过。
而种子行**都带**权威边界（如 `cert.expiring.window.days = {"min":1,"max":365}`）——即服务端本来就有真值，却没用它。
这是"守卫由被守卫者提供"：任何人直接调 API、不传 legalFloor，就能把"到期预警窗口"写成 999 天。

**已改为**：先按**存量行**的 `legal_floor` 校验，再叠加请求里带的（请求只能更严、不能更松）。新增 3 个用例钉住
（存量边界在请求省略时仍生效 / 更严的请求边界生效 / 边界内可保存）。
残留：请求仍可写入更宽的 `legal_floor`（运维显式调边界，需填变更原因并进审计历史链），
故放宽边界是"先改边界、再改值"两步且两步留痕；如需更强约束（边界只能收窄），请给口径。

### 6.2 未修（需口径）：**出厂默认配置与自身声明的法定下限冲突**

`cert.alert.legal.floor.days` 的种子值（描述原文："各证照类别的法定预警下限（**保存预警天数时不得低于此值**）"）：

| 证照类别 | 法定下限 | 说明 |
| --- | --- | --- |
| SPECIAL_EQUIPMENT（特种设备） | **180 天** | ← 与默认阈值冲突 |
| SAFETY_PERMIT / REG_PRACTICE_CERT / ID_CARD | 90 天 | |
| SEWAGE_PERMIT / BOILER_REVIEW | 60 天 | |

而多级预警阈值默认是 `[90,60,30,7]`（最大 90 天）。于是：

1. **若按文本执行**：出厂默认配置**自身违规**——特种设备只提前 90 天预警，低于法定 180 天；
2. **若把校验接进"全局阈值键"的保存路径**：用最严下限（180）判 → **连默认配置都存不进去**（我实测推演过，故没有接线）；
   用单类别下限判 → 全局键根本没有类别字段，无从判起。

**根因**：法定下限是"按证照类别"的，而阈值键是"全局一个数组"——两个口径不匹配，
所以"保存时校验"这件事在当前数据结构下**无法成立**。三条出路，需你选：
- **A**：改为按类别的阈值（每类别一个键或一张配置表），保存时按该类别下限校验（最贴合现状文本，改动中等）；
- **B**：保留全局阈值，但把下限变成**扫描期的兜底**——扫描时对每一张证照取 `max(配置阈值, 该类别法定下限)`，
  即"配置短了系统也保证法定提前量"（改动小，且不依赖人配得对；但预警量会变多，需业务认可）；
- **C**：确认特种设备 180 天下限写错了（如实际应为 90），改种子值即可。
（无论哪条，都建议顺带核对：这条下限的**规范出处**是否真要求 180 天——种子里带了《排污许可管理条例》等出处，特种设备那条需复核。）

### 6.3 未修（需归属）：「CLEAN 才可预览/下载」在代码里不存在

`CertificateVirusScanStatusEnum` 与 `CertFileVersionServiceImpl` 的注释都写"CLEAN 才可预览/下载、INFECTED 自动置 is_current=false"，
但 **main 源码里 grep `CLEAN` 没有任何判断点**（只出现在类名与一个无关 VO 的字段注释里），
且证照控制器只有 page/get/create/file.register/file.list/change-status **六个端点、没有下载或预览端点**。

即：这条"高安全底线"要么应由**平台文件服务/URL 签发处**拦截（不在本模块，需与平台侧确认），
要么应由前端按 `virusScanStatus` 控制（但前端可控 = 可绕过）。建议：明确拦截点归属后再实现，
本模块至少可以做到"未 CLEAN 的文件不下发可用 URL"（若 `file/list` 会返回地址，这里是本模块能守的那道门）。

### 6.4 已修（本轮追加）：预警阈值是"看得见的旋钮没接线"

契约把"预警设置页多档输入"的编辑对象登记为规则键 `cert.alert.thresholds`（有审计、版本、灰度、回滚），
但 `CertificateAlertServiceImpl#effectiveConfig()` 原来只读 `cert_alert_config` 表——**而全仓没有任何端点能写那张表**
（控制器层搜不到"预警设置"相关端点）。两者叠加的后果：

> 用户在设置页改阈值 → **对预警毫无影响**；真实生效的一直是本类的硬编码常量 `DEFAULT_THRESHOLDS = List.of(7,30,60,90)`。
> 即：**看得见的旋钮没接线，真实的旋钮没人能拧**（"假配置"的完整形态，比 §一.2 更严重——那个只是没人读，这个是"读了另一个地方"）。

**已改为**：阈值经 `RuleConfigService#resolveWithAudit(cert.alert.thresholds, "CERT_ALERT_SCAN")` 解析（新增审计场景
`CERT_ALERT_SCAN`，回答"这条预警按哪次、哪版配置判出来"），表行只留"启用开关 + 通知渠道"（运营参数，非业务口径）。
**今天行为不变**（规则键的代码兜底同为 `[90,60,30,7]`，与硬编码常量同值），故本次是"接通旋钮"而非改口径；
两个用例钉住：设置页把阈值改成 `[180,90,30,7]` 后候选窗口随之变成 180、档位仍按新档判定；以及审计场景名。

### 6.5 已修（本轮追加）：验真留痕"只进不出"

§4.1/§4.2 两个验真接口每次都返回"验真历史主键"，但**全仓没有读接口**（控制器层 grep 无涉及
`CertVerifyHistory` 的 `@GetMapping`）——留痕只进不出，主键等于一个再也打不开的句柄；
事后追溯"谁在什么时候验了哪张证、结论是什么"只能查库。**已补** `GET /bidding/certificate-verify/history/page`：

- 复用读权限 `bidding:certificate:query`（不新增权限码——历史属台账读取面，动作码仍是 `certificate:verify`）；
- 等值过滤（证照/渠道/结论）+ `verifiedAt` 倒序；
- 证照名**一次 in 查询**批量回填（不 N+1），行数再多也只有两次 SQL；
- **L3 报文原文不下发**（含证照编号等可识别信息），只回 `snapshotAvailable` 布尔位——留痕的用途是举证与审计，
  不是界面展示；两个用例钉住（批量回填只查一次 + 空结果不回查）。

契约已补 §4.3（含字段表、异常契约、Mock 示例）。

### 6.6 本轮核实为"无缺陷"的两项（如实记录，不硬凑结论）

- **材料完备性自查**：`GET /bidding/enterprise-material/completeness` 存在且带权限码；"不落表"是**有意设计**

### 6.7 已修（本轮追加）：硬编码 30 天 → 可配键（**默认值不变**）

门禁欠账表里登记着 `CertificateAlertServiceImpl::EXPIRING_SOON_DAYS = 30`（"扫描 ≤30 天置 EXPIRING_SOON"），
理由是"**与 `cert.expiring.window.days`(60)/`cert.alert.thresholds` 的语义对应未定，擅自接线会改变全租户状态流转口径**"。

本轮第一次动手时我正是准备把它接到 `cert.expiring.window.days`(60) —— **差点又犯"把两个不同口径并成一个"的错**。
停下来读登记理由后发现两件事：① 60 是**展示口径**（列表角标/筛选），且契约 §3.11 明确**由前端传窗口天数、后端有意不读**；
② 30 是**状态流转口径**（51 号文 ZZZT），改宽会动全租户证照状态。

正解是**新开一个键**：`cert.expiring.status.days`（默认 **30** = 原硬编码值 → **行为完全不变**，只是从写死变可配），
种子行 `700000000000000014`，走 `resolveWithAudit(..., CERT_ALERT_SCAN)` 解析（循环外解析一次，避免每张证照一条审计行）。
欠账表相应划掉，并登记新键。用例：把窗口配成 45 天 → 40 天后到期的 ACTIVE 证照也置 EXPIRING_SOON（旧实现下必红）。

**推广这条经验**：遇到"硬编码该不该接配置"时，先确认**这是不是同一个口径**——接错键比不接更危险（不接只是不能配，接错是悄悄改了业务行为）。
本项目的判据：**决策值**（业务结论）走规则配置中心；**运营参数**（cron/开关/批量）走部署配置；**前端口径**（前端自己传给接口的）后端不读。

### 6.8 已修（本轮追加）：材料完备性窗口 60 天 → 可配键（同样**默认值不变**）

门禁欠账登记：`EnterpriseMaterialServiceImpl::EXPIRING_WINDOW_DAYS`，理由"**与 cert.expiring.window.days(60)
数值相同但语义不同（材料完备性 vs 列表角标），需先定语义再接线**"。

处理方式与 §6.7 一致：**新开键** `qual.material.expiring.window.days`（默认 **60** = 原硬编码值 → 行为不变），
种子行 `700000000000000015`，走 `resolveWithAudit(..., MATERIAL_COMPLETENESS)`（新增场景）解析，
**在 checkCompleteness 里解析一次后沿 checkOne → fillBy*/applyValidTo 逐层传参**（不是每项材料解析一次——那会产生重复审计行）。
用例：窗口配成 90 天 → 80 天后到期的材料判 RISK（旧实现硬编码 60 → 必红）。类注释里"阈值取 60 天"的表述同步改为"取规则键（默认 60）"。

**两处接线合起来看**：`EXPIRING_WINDOW_DAYS`(材料) 与 `EXPIRING_SOON_DAYS`(证照状态) 都是"数值相同/相近但语义不同"的典型——
门禁欠账表把它们标为 BUSINESS_DEBT 而不是直接接线是对的：**接错键比不接更危险**（不接只是不能配，接错是悄悄改了业务行为）。
