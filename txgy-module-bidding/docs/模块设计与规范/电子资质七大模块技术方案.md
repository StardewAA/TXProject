> 归属：txgy-module-bidding（电子资质子模块）

## 〇、总览与设计前提

### 0.1 与既有体系的边界（先声明，避免重复造物）

| 既有能力 | 已有实现 | 本方案的态度 |
| --- | --- | --- |
| 到期预警（多档阈值 + 档位 + 幂等 + 发件箱） | `cert_alert_config` + `cert_alert_records` + `cert_notify_outbox` | **复用**，模块 3 只加"下限拦截"，不新建预警表 |
| 证照台账与文件版本 | `certificate_info` + `cert_file_versions`（含 GB/T 36903 §5.4 加注件 4 元数据） | **复用**，模块 5 的加注件建独立表但引用其文件版本 |
| 变更审计日志 | `cert_change_logs`（哈希链） | **复用**，本方案所有新增审计统一挂哈希链范式 |
| 人员与证书 | `bidding_personnel_profile` + `personnel_certificate`（含 `cert_sub_type`、`next_review_date`） | **扩展**（加 risk 列），不建重复表 |
| 资质达标核查 | `qualification_standard` + `qualification_compliance_review` | 复用其"只追加结论"范式 |
| 安许证 | `qualification_safety_permit` | **加列** `risk_flag` 等 |

### 0.2 依赖顺序（实现必须先做 8.1）

```
8.1 规则配置中心  ──┬─→ 1 安许 risk_flag 联动
                   ├─→ 2 周检 Job
                   ├─→ 3 下限拦截
                   ├─→ 4 设备台账
                   ├─→ 5 加注件
                   ├─→ 6 标书引用拦截
                   └─→ 7 身份证 L4/KMS
8.2 审计与追溯     ── 与 8.1 同期，被全部模块依赖
```

### 0.3 状态与命名约定（与既有代码一致）

- 审计列由 `BaseDO` 提供（`creator/create_time/updater/update_time/deleted`），**不另建改名**；
- 业务租户隔离表继承 `TenantBaseDO`（`tenant_id` 由拦截器自动维护）；
- 乐观锁统一 `version int` + `@Version`；
- 幂等键统一 `{业务域}:{主键}:{类型}:{yyyyMMdd}` 形态，配 UNIQUE KEY 兜底；
- 错误码新增段 **108（预警下限/设备/加注件/标书拦截/加密）**，先登记规范 §4.7 再占用。

## 一、安许 A/B/C 联动与 risk_flag

### 1.1 数据模型与字段

**(a) 扩展 `qualification_safety_permit`（企业级风险）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `risk_flag` | varchar(16) | 企业级风险档：NORMAL/YELLOW/RED/INVALID/ABNORMAL/FREQUENT |
| `risk_level` | varchar(16) | 档位映射：LOW/MEDIUM/HIGH/MAJOR（供周检 Job 直接用） |
| `risk_evaluated_at` | datetime | 最近评估时刻 |
| `grace_expire_at` | datetime | 宽限截止（NULL=无宽限） |
| `grace_reason` | varchar(256) | 宽限原因（如"法定代表人变更"） |
| `grace_source_ref` | varchar(128) | 宽限依据（变更单号/决定书号） |
| `frequent_alert_count` | int | 滑动窗口内预警次数 |
| `frequent_window_start` | datetime | 滑动窗口起点 |
| `rule_version` | varchar(32) | 本次评估所用规则版本 |

**(b) 扩展 `bidding_personnel_profile`（人员级风险，与 (a) 分离）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `person_risk_flag` | varchar(16) | 人员级标签：NORMAL/ABNORMAL/FREQUENT |
| `job_change_count_12m` | int | 12 个月内更换受聘企业次数 |
| `job_change_window_start` | date | 统计窗口起点 |
| `person_risk_evaluated_at` | datetime | 最近评估时刻 |

> **为什么企业级/人员级必须分离**：企业级回答"这家企业能不能投标"，人员级回答"这名人员能不能上岗"。
> 混在一列会导致两种处置互相覆盖（企业进宽限期时人员异常被掩盖，反之亦然），也无法分别授权查看。

**(c) 新表 `safety_permit_risk_snapshot`（风险快照，只追加）**

`permit_id`、`ent_id`、`risk_flag`/`prev_risk_flag`、`risk_level`、
`a_count/b_count/c_count`、`min_required_json`(json)、`grace_applied`(bit)、
`hit_rules_json`(json，命中的规则键与取值，可复算)、`rule_version`、`batch_no`、
`evaluated_at`、`record_hash`/`prev_hash`（哈希链）+ 标准列。

**(d) 新表 `personnel_job_change_log`**：`person_id`、`from_ent_id`、`to_ent_id`、
`change_type`（TRANSFER/RESIGN/REHIRE）、`effective_date`、`source_ref`、`remark` + 标准列。

**(e) 新表 `project_key_post_assignment`**：`project_id`、`tender_project_code`、
`post_code`（项目经理/技术负责人/安全员…）、`person_id`、`start_at`、`end_at`、
`change_seq`、`change_reason` + 标准列；UK `(tenant_id, project_id, post_code, change_seq, deleted)`。

**(f) 新表 `personnel_multi_post_check`**（多岗合规结论，只追加）：`person_id`、`primary_post`、
`secondary_post`、`required_cert_type`、`required_cert_sub_type`、`matched_cert_id`、
`check_result`（PASS/FAIL）、`fail_reason`、`checked_at`、`rule_version` + 标准列。

### 1.2 核心规则与参数配置

**判定顺序（采纳 06 文档 §四-1：风险与非日期型失效必须排在日期判断之前）**

```
1  主证件已作废(CANCELLED)                     → INVALID
2  三类人员全为 0                               → INVALID
3  任一 required 类为 0（豁免类型除外）          → RED
4  任一类低于配备要求                           → YELLOW
5  处于宽限期且未到期                           → 降一档（RED→YELLOW，YELLOW→NORMAL）
6  窗口内预警次数 ≥ 频繁阈值                     → FREQUENT
7  人员维度异常（变更次数 ≥ 阈值）               → 打 person_risk_flag，不改 ent_risk_flag
8  安许证本身过期                               → 按既有 cert_status 口径处理
```

**配置项（键 → 默认值，全部落 `bidding_rule_config`）**

| 规则键 | 默认值 | 含义 |
| --- | --- | --- |
| `safety.abc.required` | `{"A":1,"B":1,"C":1}` | 三类人员最低配备 |
| `safety.abc.roles` | `["A","B","C"]` | 参与判定的角色集合 |
| `safety.abc.exempt.ent.types` | `{"LABOR_SUBCONTRACT":["B"]}` | 豁免矩阵：劳务分包 B 证为 0 不触发红 |
| `safety.abc.grace.legal.person.change.days` | `180` | 法定代表人变更致人数不足的宽限天数 |
| `safety.abc.grace.reason.whitelist` | `["LEGAL_PERSON_CHANGE"]` | 允许触发宽限的原因（防滥用） |
| `safety.abc.frequent.alert.threshold` | `4` | 频繁预警次数阈值 |
| `safety.abc.frequent.window.days` | `365` | 频繁统计滑动窗口 |
| `safety.abc.invalid.grace.days` | `90` | 3 个月不整改列失效 |
| `safety.abc.block.flags` | `["INVALID","RED"]` | 哪些档位阻断业务 |
| `personnel.job.change.threshold` | `4` | 人员更换受聘企业次数阈值 |
| `personnel.job.change.window.days` | `365` | 人员变更统计窗口（12 个月） |
| `project.key.post.change.threshold` | `2` | 同一项目同一关键岗位变更次数阈值 |
| `project.key.post.change.window.days` | `90` | 关键岗位变更统计窗口 |
| `personnel.multi.post.require.cert` | `true` | 兼任 ≥2 岗是否必须持另一岗位证书 |
| `risk.level.mapping` | `{"NORMAL":"LOW","YELLOW":"MEDIUM","RED":"HIGH","INVALID":"MAJOR"}` | risk_flag → risk_level |

### 1.3 Job/接口设计

**Job `safetyPermitRiskJob`**（每日 02:10，cron 可配）
- 入参：`tenantId`（空=全租户）、`asOf`（空=今天）、`dryRun`；
- 处理：① 取全部安许证 → ② 按 `personnel_certificate`（certType=SAFETY_ASSESS_CERT，状态可用）按
  `cert_sub_type` 分 A/B/C 计数 → ③ 对照配置判档（含宽限/豁免/频繁） → ④ 与 `prev_risk_flag`
  比对，**仅在变化时**写快照 + 发通知 → ⑤ 回写主表 risk 列；
- 出参：`{evaluated, changed, byFlag, elapsedMs}`；
- 幂等：同 `(permit_id, asOf, rule_version)` 已评估则跳过；`dryRun` 不落库。

**Job `personnelRiskJob`**（每周一 03:00）：统计 12 个月变更次数 → 人员级标签。
**Job `projectKeyPostChangeJob`**（每日 03:30）：关键岗位变更超阈值 → 挂靠嫌疑待办。

| 方法 | 路径 | 入参 | 出参 | 说明 |
| --- | --- | --- | --- | --- |
| GET | /bidding/safety-permit/risk | `entId`、`asOf?` | `{riskFlag,riskLevel,aCount,bCount,cCount,graceExpireAt,hitRules}` | 招投标/施工许可/现场监督**统一读此接口** |
| POST | /bidding/safety-permit/risk/recheck | `entId`、`dryRun?` | 同上 | 人工重算 |
| GET | /bidding/safety-permit/risk/history | `permitId` + 分页 | 快照分页 | 追溯 |
| GET | /bidding/personnel/{id}/risk | — | `{personRiskFlag,jobChangeCount12m}` | 人员级 |
| POST | /bidding/safety-permit/grace | `entId,reason,sourceRef,days?` | `{graceExpireAt}` | 登记宽限（原因须在白名单） |
| POST | /bidding/personnel/multi-post-check | `personId,primaryPost,secondaryPost` | `{pass,failReason,requiredCert}` | 多岗合规校验 |
| GET | /bidding/project/{id}/key-post-changes | `windowDays?` | 变更次数与明细 | 频繁变更监控 |

### 1.4 拦截点逻辑

| 拦截点 | 触发时机 | 策略 |
| --- | --- | --- |
| 投标登记/资格预审提交 | 提交前校验 | 命中 `safety.abc.block.flags` → **阻断**；`FREQUENT`/`YELLOW` → 放行 + 风险提示 |
| 施工许可申报 | 申报前 | 命中阻断档 → 阻断 |
| 现场监督检查读取 | 只读 | 不阻断，返回统一 risk 状态 + 整改倒计时 |
| 人员上岗/配证 | 绑定时 | 人员 `person_risk_flag=ABNORMAL` → 阻断；多岗无证 → 阻断 |
| 关键岗位变更登记 | 登记时 | 超阈值不阻断，产出合规待办并升级风险等级 |

### 1.5 数据迁移路径（含回滚）

1. **DDL**：`ALTER TABLE ... ADD COLUMN`（幂等）+ 建 4 张新表；
2. **初始化**：写入 `safety.*` 默认配置行（幂等 upsert）；
3. **存量评估**：先 `dryRun=true` 核对分布 → 关掉 dryRun 正式评估一轮，全部落快照
   （**此前 `risk_flag` 为 NULL 表示"未评估"，与"正常"区分**）；
4. **回填**：`personnel_job_change_log` 无历史时以人员档案入职/变更时间回填一次；
5. **回滚**：① 立即止血 = `risk_flag` 置回 NULL + 停 Job（业务侧把 NULL 视为"未评估=不阻断"，
   回到改造前行为）；② 表不删（快照只增不改，删除破坏哈希链）；③ 规则回滚到上一 `version_no` 后重跑。

## 二、周检 Job 自动生成

### 2.1 数据模型与字段

**新表 `inspection_task`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `task_no` | varchar(48) | 任务编号（UK 含 tenant） |
| `project_id` / `project_code` | bigint/varchar | 关联项目 |
| `risk_level` | varchar(16) | LOW/MEDIUM/HIGH/MAJOR |
| `phase` | varchar(24) | PREPARE/FOUNDATION/MAIN/INSTALL/TEST/COMPLETE |
| `cycle_days` / `lead_days` | int | 本任务所用周期/提前量（配置快照，可复算） |
| `plan_date` / `due_date` | date | 计划/截止日期 |
| `priority` | int | 优先级（MAJOR 最高） |
| `status` | varchar(16) | PENDING/ASSIGNED/IN_PROGRESS/DONE/CANCELLED/MERGED |
| `merged_into_id` | bigint | 被合并到哪条（防消息轰炸） |
| `generate_reason` | varchar(32) | CYCLE/ESCALATE/ACCIDENT/HIDDEN_DANGER/MANUAL |
| `trigger_rule_json` | json | 触发快照 |
| `last_inspection_result` | varchar(16) | PASS/RISK/FAIL（入参） |
| `clean_streak` | int | 连续无异常次数（供动态降级） |
| `assignee` / `assigned_at` | bigint/datetime | 派单人 |
| `idempotent_key` | varchar(96) | UK：`{projectId}:{phase}:{planDate}:{riskLevel}` |
| `rule_version` | varchar(32) | 规则版本 |

**新表 `inspection_task_merge_log`**：`merged_task_id`、`target_task_id`、`merge_reason`、`merged_at` + 标准列。

### 2.2 核心规则与参数配置

**生成公式**：`plan_date = anchor_date + lead_days(risk_level, phase)`；
`anchor_date` 默认取"上次检查完成日"，无历史则取项目当前阶段起始日。

| 规则键 | 默认值 |
| --- | --- |
| `inspection.lead.days.LOW` | `14` |
| `inspection.lead.days.MEDIUM` | `7` |
| `inspection.lead.days.HIGH` | `3` |
| `inspection.lead.days.MAJOR` | `0`（立即生成并推送） |
| `inspection.cycle.days.LOW/MEDIUM/HIGH/MAJOR` | `90/30/14/7` |
| `inspection.phase.overrides` | `{"MAIN":{"LOW":30},"INSTALL":{"HIGH":7}}` |
| `inspection.escalate.clean.streak` | `3`（连续 N 次无异常→降级） |
| `inspection.escalate.on.accident` | `true` |
| `inspection.escalate.on.hidden.danger` | `true` |
| `inspection.escalate.degrade.max.level` | `"LOW"` |
| `inspection.merge.window.minutes` | `120` |
| `inspection.dedup.window.hours` | `24` |
| `inspection.major.immediate.notify` | `true` |
| `inspection.block.on.overdue.major` | `false` |

### 2.3 Job/接口设计

**Job `inspectionTaskGenerateJob`**（每日 06:00）
- 入参：`tenantId?`、`asOf?`、`dryRun?`、`projectIds?`；
- 逻辑：① 遍历在施项目 → ② 解析 `risk_level`（取模块 1）与 `phase` → ③ 算 `plan_date` →
  ④ **去重**（同 `idempotent_key` 已有未完成任务则跳过）+ **合并**（落在合并窗口内同项目同阶段 →
  合并并写 `merge_log`） → ⑤ `MAJOR` 立即推送；
- 出参：`{generated, merged, skipped, escalated, elapsedMs}`。

**Job `inspectionEscalateJob`**（每日 06:30）：连续无异常达阈值→降级拉长周期；事故/整改不力→升级并立即生成高优任务。

| 方法 | 路径 | 入参 | 出参 |
| --- | --- | --- | --- |
| POST | /bidding/inspection-task/generate | `projectIds?,dryRun?` | 生成统计 |
| GET | /bidding/inspection-task/page | `projectId,riskLevel,phase,status,dateRange` + 分页 | 任务分页 |
| POST | /bidding/inspection-task/{id}/finish | `result,remark,hiddenDanger?` | 完成并触发升降级 |
| POST | /bidding/inspection-task/{id}/cancel | `reason` | 取消 |
| GET | /bidding/inspection-task/plan-preview | `projectId,riskLevel,phase` | `{planDate,leadDays,cycleDays}`（只读配置预演） |

### 2.4 拦截点逻辑

| 拦截点 | 策略 |
| --- | --- |
| 生成前 | 同键去重 + 窗口合并 → **不产生新任务、不推消息**（防轰炸） |
| 事故/隐患升级 | 立即生成 `priority=MAJOR` 并发通知；已有任务被升级覆盖而非并行堆积 |
| 任务完成 | 写 `clean_streak`、触发升降级；**不阻断**任何业务 |
| 招投标登记 | 存在逾期未完成 MAJOR 任务 → 风险提示（是否阻断走 `inspection.block.on.overdue.major`，默认 false） |

### 2.5 数据迁移路径（含回滚）

1. 建表 + 写 `inspection.*` 默认配置；
2. 首轮用 `dryRun=true` 观察条数（防一次生成上万条）→ 正式跑；
3. `anchor_date` 缺省回落：无历史检查记录的项目以 `asOf` 为锚，避免一次性全部逾期；
4. **回滚**：`UPDATE inspection_task SET status='CANCELLED'` + 停 Job；配置回滚上一版本。

## 三、预警天数保存时法定下限拦截

### 3.1 数据模型与字段

**新表 `bidding_legal_floor`（法定下限码表）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `cert_category` | varchar(32) | 证照类别 code |
| `floor_days` | int | 法定下限天数 |
| `regulation_ref` | varchar(256) | 法规出处 |
| `regulation_excerpt` | varchar(1024) | 原文摘要（返给前端） |
| `regulation_url` | varchar(512) | 原文链接 |
| `effective_from` / `effective_to` | date | 生效区间（法规换版可并存） |
| `enabled` | bit(1) | 开关 |

默认行（依据 06 文档 §二-5）：排污许可 60、司炉复审 60、特种设备生产许可 180、安许证 90、一级建造师 90、身份证 90。

**新表 `alert_threshold_override_request`（特批通道）**：`cert_category`、`cert_type`、
`current_thresholds`(json)、`requested_thresholds`(json)、`legal_floor_days`、`apply_reason`、
`status`（PENDING/APPROVED/REJECTED/REVOKED/EXPIRED）、`approver`、`approved_at`、
`effective_until`、`evidence_file_ids`(json)、`apply_no`、`version` + 标准列。

### 3.2 核心规则与参数配置

- **校验规则**：保存 `cert_alert_config.thresholds` 时，`max(thresholds) >= legalFloor(cert_category)`
  （最大档即最长提前量，小于法定下限就会错过法定窗口）；
- **特批豁免**：存在 `APPROVED` 且在 `effective_until` 内的特批 → 放行，但**强制**写审计日志。

| 规则键 | 默认值 | 含义 |
| --- | --- | --- |
| `alert.floor.enforce` | `true` | 是否启用下限拦截（应急可关） |
| `alert.floor.override.enabled` | `true` | 是否允许特批通道 |
| `alert.floor.override.max.days` | `90` | 特批有效期上限 |
| `alert.floor.override.require.evidence` | `true` | 特批是否必须附证明材料 |
| `alert.floor.override.approver.roles` | `["QUALITY_DIRECTOR","COMPLIANCE"]` | 审批角色白名单 |
| `alert.floor.return.regulation.ref` | `true` | 拒绝时是否返回法规出处 |

### 3.3 Job/接口设计

无新增 Job（拦截发生在保存时）。接口：

| 方法 | 路径 | 入参 | 出参 |
| --- | --- | --- | --- |
| GET | /bidding/alert-floor/list | 分页 | 下限码表 |
| POST | /bidding/alert-floor/save | `certCategory,floorDays,regulationRef,regulationExcerpt,regulationUrl` | id（仅平台管理员） |
| POST | /bidding/alert-threshold/save | `certType,thresholds,notifyChannels` | 成功 / **拒绝并返 `regulationRef`** |
| POST | /bidding/alert-threshold/override/apply | `certCategory,certType,requestedThresholds,applyReason,evidenceFileIds` | 申请单号 |
| POST | /bidding/alert-threshold/override/audit | `id,approve,remark,effectiveUntil?` | 审批结果 |
| GET | /bidding/alert-threshold/override/page | 分页 | 特批台账 |

`evidence_json`、`status`（OPEN/INVESTIGATING/CLOSED）、`handled_by`、`handled_at` + 哈希链列。

### 6.2 核心规则与参数配置

**两类比对必须物理区分**

| 类型 | 范围 | 处置 |
| --- | --- | --- |
| **自引查重 SELF** | 仅"同一投标人"本次标书 vs 其**企业历史标书白名单** | 相似 → 提示"自引重复"，**不报警**（依法持有自身文件） |
| **串标检测 CROSS** | 不同投标人之间 | **严禁自动两两比对**；仅监管角色在合规事件流程内发起，且发起即生成合规事件 |

> **为什么严禁自动互比**：不同投标人互比会把"引用同一招标文件模板/同一标准图集"这类正常现象判成串标，
> 产生大量假阳性；且未经授权的互比本身可能构成对第三方商业秘密的接触。故设计为
> **白名单内自动、跨主体走合规事件 + 人工介入**。

| 规则键 | 默认值 | 含义 |
| --- | --- | --- |
| `biddoc.similarity.threshold.default` | `0.70` | 语义相似度阈值（>70% 高风险） |
| `biddoc.similarity.threshold.by.project.type` | `{"ENGINEERING":0.70,"GOODS":0.80,"SERVICE":0.75}` | 按项目类型覆盖 |
| `biddoc.similarity.model` | `"SENTENCE_EMBEDDING"` | 句向量模型标识（可替换） |
| `biddoc.similarity.min.segment.length` | `50` | 参与比对的最小句段长度（防短句噪声） |
| `biddoc.hardware.match.fields` | `["mac_list","cpu_serial","disk_serial_list","dongle_no","storage_serial"]` | 硬件比对字段 |
| `biddoc.hardware.risk.mapping` | `{"dongle_no":"MAJOR","mac_list":"HIGH"}` | 字段→风险权重 |
| `biddoc.image.phash.hamming.threshold` | `6` | 感知哈希汉明距离阈值（≤ 判雷同） |
| `biddoc.trace.revision.window.days` | `7` | 修订/批注时间过于集中的判定窗口 |
| `biddoc.self.whitelist.enabled` | `true` | 自引白名单开关 |
| `biddoc.cross.require.role` | `["COMPLIANCE","SUPERVISION"]` | 允许发起跨主体比对的角色 |
| `biddoc.auto.cross.compare` | `false` | **默认关闭**跨主体自动比对 |
| `biddoc.block.on.hardware.collision` | `false` | 硬件碰撞是否阻断提交 |

### 6.3 Job/接口设计

- **`bidDocFingerprintJob`**（上传后异步队列消费）：提取硬件指纹 + 文档属性 + 痕迹 → 落库；

| 方法 | 路径 | 入参 | 出参 |

### 6.4 拦截点逻辑

| 时机 | 策略 |
| --- | --- |
| 标书上传/提交 | 指纹提取**异步**，不阻断提交（避免拖慢投标）；但**引用失效证照** → 阻断 |
| 自引相似 > 阈值 | **不阻断**，标"自引重复"提示（白名单内属正常） |
| 跨主体比对请求 | 非授权角色 → **阻断**；授权角色 → 放行但**强制**生成合规事件 |
| 硬件指纹跨投标人碰撞（同项目内） | 生成合规事件 + 提交时**强提示**；是否阻断走 `biddoc.block.on.hardware.collision`（默认 false，交评标委员会认定） |
| 修订/批注异常一致 | 仅标记，不阻断 |
| 不同投标人标书被互相比对 | **直接升级为合规事件**（用户明确要求），并记录发起人 |

### 6.5 数据迁移路径（含回滚）

3. 白名单初始化：按"企业依法持有的历史标书"导入，**缺 `legal_basis` 的不导入**（合规优先）；
4. 灰度：先对 1~2 个项目开启自引比对，核对误报率后再全量；
5. **回滚**：`biddoc.*` 规则一键关闭比对 → 提交流程回到改造前；合规事件与指纹数据保留（审计需要）；
   指纹为异步依赖，表不影响主流程。

## 七、身份证 L4 密文加密与 KMS 接入

### 7.1 数据模型与字段

**改造 `bidding_personnel_profile.id_card_enc`**：从"密文占位"升级为真实信封加密密文，格式：

```
v1.{alg}.{keyVersion}.{iv_b64}.{ciphertext_b64}.{tag_b64}
```

- `v1` 格式版本（未来换算法用 `v2`）；
- `alg`：`SM4-GCM`（优先）或 `AES-256-GCM`（备选）；
- `keyVersion`：加密时所用 DEK 版本（**密文头带密钥版本**，解密按版本取键）；
- `tag`：GCM 认证标签（防篡改）。

**盲索引 `id_card_blind_index` 保持不变**（`HMAC-SHA256(索引密钥, 归一化证号)`），
**索引密钥与加密密钥分离**。

**新表 `crypto_key_meta`（密钥元数据）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `key_version` | varchar(32) | 密钥版本号（UK） |
| `key_type` | varchar(8) | KEK / DEK |
| `algorithm` | varchar(24) | SM4-GCM / AES-256-GCM |
| `kms_key_id` | varchar(256) | KMS 侧密钥标识（KEK） |
| `wrapped_dek` | varchar(512) | 被 KEK 包裹的 DEK（DEK 行专用） |
| `status` | varchar(16) | PENDING/ACTIVE/ROTATING/RETIRING/RETIRED/DESTROYED |
| `activated_at` / `retire_at` / `destroyed_at` | datetime | 生命周期时刻 |
| `rotated_from` | varchar(32) | 由哪个版本轮换而来 |

> **G 轨（无 `tenant_id`）**：密钥平台级共享，避免每租户一套密钥导致轮换复杂度爆炸。

**新表 `crypto_audit_log`（密钥操作审计，哈希链）**：`operation`
（GENERATE/WRAP/UNWRAP/ROTATE/RETIRE/DESTROY/DECRYPT_FALLBACK）、`key_version`、`operator`、
`result`、`detail`、`occurred_at`、`record_hash`、`prev_hash`。

**新表 `crypto_perf_metric`（性能监控）**：`metric_type`（ENCRYPT/DECRYPT）、`biz_table`、
`count`、`avg_ms`、`p95_ms`、`max_ms`、`slow_count`、`stat_window`（小时桶）、`recorded_at`。

### 7.3 KMS/加密流程（含密钥轮换与迁移）

**写入（信封加密）**

```
1 取当前 ACTIVE 的 DEK（dek.per.record=true 时该记录新生成）
   └─ 无 ACTIVE DEK → 调 KMS GenerateDataKey（KEK 在 KMS 内不出域）
2 明文 idCard → SM4-GCM(DEK, iv=随机12B) → ciphertext + tag
3 组密密文头 v1.SM4-GCM.{keyVersion}.{iv}.{ct}.{tag}
4 落库 id_card_enc；同时落 id_card_blind_index（HMAC，独立索引密钥）
5 审计：写 crypto_audit_log(ENCRYPT)；性能：累计 crypto_perf_metric
6 明文立即从内存丢弃（不落日志、不进异常栈）
```

**读取（解密）**

```
1 解析密文头 → keyVersion
2 keyVersion 为当前 ACTIVE → 直接取键
3 否则（双密钥并存期）→ 查 crypto_key_meta 状态 ∈ {ACTIVE, ROTATING, RETIRING}
   └─ 命中 → 取键解密，审计记 DECRYPT_FALLBACK
   └─ 未命中（已 RETIRED/DESTROYED）→ 报错并告警（需人工介入）
4 解密成功后按 PublicLevel 掩码输出（L4 只回前 6 后 4）
```

**轮换流程（90 天）**

```
T+0        生成新 DEK v(n+1) → ACTIVE；旧 DEK v(n) → ROTATING（仍可解密）
T+0        新写入一律用 v(n+1)
T+0~T+180  双密钥并存期：旧数据仍是 v(n)，读取按密文头版本回退解密
T+180      旧 DEK v(n) → RETIRING（只读解密，不再用于新写入）
T+210      （retire.grace.days=30）确认无 v(n) 引用 → RETIRED
T+?        确认全量重加密完成 → DESTROYED（KMS 销毁，审计留痕）
```

> **双密钥并存期的解密策略是本模块核心**：解密**永远以密文头 keyVersion 为准**，而不是"用当前活跃密钥试"。
> 后者会导致轮换瞬间全部旧数据解不开——这是最常见的生产事故。

**存量重加密**：后台批处理按主键游标扫描 → 解密（旧键）→ 加密（新键）→ 写回 → 校验 → 记账；可断点续跑。

### 7.4 框架与监控

- **透明加解密**：自定义 MyBatis `Interceptor`（`Executor.update` / `ResultSetHandler` 两个切点），
  对标注 `@EncryptedField` 的 DO 字段自动加解密；业务代码**零侵入**，
  禁止在 Service 手工调加解密（除审计/迁移场景）；
- **性能监控**：切点内计时 → 累计 `crypto_perf_metric`（小时桶）；P95 > `crypto.perf.alert.p95.ms` 告警；
- **优化**：热点数据走 `crypto.cache`（短 TTL）；大批量导出走**异步解密**（避免拖垮在线查询）；
- **慢查询统计**：超 `crypto.slow.query.ms` 记录 SQL 指纹（不含明文）。

### 7.5 数据迁移路径（含回滚预案）

**三阶段迁移（`crypto.mode` 驱动）**

| 阶段 | 模式 | 行为 |
| --- | --- | --- |
| P0 现状 | `PLACEHOLDER` | `id_card_enc` 为占位；查询走盲索引 + 掩码 |
| P1 双写 | `DUAL_WRITE` | 新数据**同时**写占位与真实密文；读仍走旧逻辑 |
| P2 切换 | `ENCRYPTED` | 读走密文解密；写只写密文；占位分支保留一版以防回滚 |
| P3 清理 | `ENCRYPTED` | 校验通过后移除占位读写分支（下一版本） |

**存量批处理**：按 `crypto.batch.size` 分批 → 每批事务提交 → 校验（抽样解密回比原文哈希）→
进度表记账 → 支持断点续跑。

**回滚预案（三级）**

1. **一键切回占位**：`crypto.mode=PLACEHOLDER`（配置中心灰度，秒级生效）→ 读走盲索引 + 掩码，
   写回占位；**真实密文列不删**（保留以便再次切换）；
2. **恢复旧密文**：P2 期间写坏部分数据 → 按 `keyVersion` 回取上一版密文（双密钥并存期内旧键仍可用），
   或按审计日志定位批次重放；
3. **密钥不可用兜底**：KMS 短时不可用 → 走本地加密缓存（加密后的 DEK 副本，仅内存）；
   长时间不可用 → **禁止写入（失败关闭），绝不退化为明文落库**。

## 八、全局架构：规则配置中心、审计与优先级排期

### 8.1 规则配置中心（所有模块的前置依赖）

**(a) 新表 `bidding_rule_config`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `rule_key` | varchar(96) | 规则键（如 `safety.abc.required`） |
| `rule_group` | varchar(32) | SAFETY/INSPECTION/ALERT/EQUIPMENT/ANNOTATION/BIDDOC/CRYPTO |
| `value_type` | varchar(16) | INT/DECIMAL/BOOL/STRING/JSON |
| `config_value` | json | 配置值（**一切数值在此，代码不硬编码**） |
| `legal_floor` | json | 该键的允许边界（如天数 ∈ [0,365]） |
| `description` / `regulation_ref` | varchar | 说明与法规出处 |
| `version_no` | int | 版本号（每次发布 +1） |
| `status` | varchar(16) | DRAFT/PUBLISHED/GRAY/ROLLED_BACK |
| `gray_scope` | json | `{"tenantIds":[...]}` 或 `{"percent":10}` |
| `effective_from` / `effective_to` | datetime | 生效区间 |
| `version` | int | 乐观锁 |

`tenant_id=0` = 平台默认行；UK `(tenant_id, rule_key, version_no, deleted)`。

**新表 `bidding_rule_config_history`**（只追加 + 哈希链）：`rule_key`、`from_version`、
`to_version`、`from_value`、`to_value`、`changed_by`、`changed_at`、
`change_reason`、`record_hash`、`prev_hash`。

**(b) 解析优先级（三级回落，与既有 `cert_alert_config` 同范式）**

```
租户级 PUBLISHED（且在生效期）
  → 灰度命中（GRAY 且 scope 命中当前租户/百分比）
  → 平台默认（tenant_id=0）
  → 代码兜底常量（仅生存兜底，不得作为业务默认值）
```

> **"代码兜底常量"必须与 DB seed 一致**：加一条测试断言"SQL seed 默认值与代码兜底常量逐键相等"，
> 避免两处默认值漂移（配置中心最常见的腐坏方式）。

**(c) 缓存与生效**：一级缓存 Caffeine（进程内，短 TTL）；发布后经 Redis pub/sub 广播失效；
全局 `ruleConfigVersion` 自增，业务表记 `rule_version` 保证评估结果可复算。

**(d) 接口**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /bidding/rule-config/get | `ruleKey` → 生效值（含来源：租户/灰度/平台） |
| GET | /bidding/rule-config/list | 按 `ruleGroup` 列出生效值（配置页） |
| POST | /bidding/rule-config/save-draft | 存草稿（不生效） |
| POST | /bidding/rule-config/publish | 发布（校验边界 + 必填） |
| POST | /bidding/rule-config/gray | 灰度发布 |
| POST | /bidding/rule-config/rollback | 回滚到指定 `version_no` |
| GET | /bidding/rule-config/history | 版本历史与审计链 |

**(e) 发布拦截点**：① 值类型匹配 `value_type`；② 不越 `legal_floor` 边界（天数为负、相似度 >1）；
③ 跨键一致性（如 `inspection.lead.days.LOW >= MEDIUM >= HIGH >= MAJOR`）；④ 变更必填 `change_reason`。
