# 智慧标书审查 · 设计方案（当前实现版）

> 版本：2026-09-22
> 编写口径：**以本仓库实际代码、库表、菜单权限为准**（不是目标态设想）。凡标注「已实现」的，都能在代码/库里找到对应物；「未实现」的单独列在第 11 章。
> 模块位置：后端 `txgy-module-bidding`（独立服务，端口 48110）；前端 `txgy-ui-admin-vben/apps/web-antd`（管理端 + 门户个人端）。

## 1. 系统定位与边界

### 1.1 一句话定位

面向**投标人**的标书合规自查工具：上传投标文件（标书）+ 招标文件 → **一键 AI 审查** → 输出「是否废标 + 废标原因 + 分级问题清单 + 评分 + Word 审查报告」。

### 1.2 做什么

| 能力 | 说明 |
|---|---|
| 文件审查 | PDF / DOCX 解析出正文，逐条比对审查规则（AI 判定 + 确定性规则） |
| 风险分级 | 高危 / 中危 / 低危；命中高危即判定「废标」 |
| 结论输出 | 是否废标、废标原因、自评得分、问题清单（含标书原文证据、整改建议） |
| 报告交付 | 网页报告 + 一键下载 **Word 审查报告** |
| 角色覆盖 | 企业端（后台管控 + 台账）与个人端（上传 + 一键生成） |

### 1.3 不做什么（边界）

- 不做招标公告抓取、投标流程跟踪、开标评标——那些是同模块的其它域，**与标书审查互不调用**。
- **不经过 AI 模块**：标书审查直连大模型（DeepSeek），用本模块专属 API Key。
- 不做扫描件 OCR：DeepSeek 无视觉能力，解析不出文字时**明确报错并提示上传文字版**，不做假成功（见 §5.5）。

### 1.4 依赖的外部能力

| 依赖 | 用途 | 隔离口径 |
|---|---|---|
| system 模块 | 登录态、用户/角色/租户、菜单权限 | 只读调用（RPC/本地 Bean） |
| infra 模块 | 文件上传/下载/归档 | 文件地址以相对路径存储，服务端解析成容器内地址（§10） |
| DeepSeek API | 规则级 AI 审查 | 专属 Key（`BIDDING_REVIEW_AI_API_KEY`），与 CRM 的 `DASHSCOPE_API_KEY`、公告域的 `bidding.ai.*` 完全隔离 |

## 2. 角色与两端划分

| 端 | 使用者 | 入口 | 职责 |
|---|---|---|---|
| **企业管理端** | 企业管理岗 / 平台运营岗 | `/bidding/bid-review/*`（后台侧边栏「招投标 → 智慧标书审查」） | 看本企业审查台账、复核问题、维护规则库、下载报告、维护 AI 配置 |
| **个人端（门户）** | 投标经办人（自然人账号） | `/portal/bidding/bidReview/*`（门户「合规审查」入口） | **只做**上传文件 + 一键生成 + 看结论/历史 |

### 2.1 数据可见性口径（重要）

1. **租户隔离**：审查任务、问题项、报告都带 `tenant_id`，企业端只能看到本租户数据。
2. **个人端 → 企业端可见**：个人账号（通常属平台默认租户 tenant 0）提交时，会把记录**写进企业租户**，让企业端看得到。
3. **归属企业怎么定（2026-09-22 口径）**：个人端**不展示、也不让用户选**企业，系统静默默认：
   - 首选 **延河热力集团有限公司（tenant_id=2019）**；
   - 该账号没被授权延河热力时，回落到「唯一/第一家被授权企业」；
   - 一家都没有时按个人记录提交（落个人租户，企业端看不到）。
4. **授权来源**：`bidding_subject_user`（企业把该用户加为**经办人**）。后端建单前校验，未授权则报错「你尚未被该企业授权为经办人，无法以该企业名义提交」。
5. **个人端读自己记录跨租户**：按 `owner_user_id` 校验归属（个人账号能看到自己提交到企业租户的任务/问题/报告），不跟随登录租户过滤。

## 3. 功能模块总览

```
智慧标书审查
├── 管理端（企业侧边栏）
│   ├── 审查任务        ← 台账、建单、一键生成/重跑、取消、统计看板
│   ├── 问题复核        ← 问题清单筛选/统计、逐条复核（确认/误报/已整改）
│   ├── 审查规则库      ← 规则集 + 规则项维护（分类/级别/检查方式/分值/要求/证据提示）
│   └── 报告与统计      ← 报告台账、报告详情、报告下载（Word）、AI 配置维护与连通性探测
└── 个人端（门户）
    ├── 标书审查        ← 上传标书/招标文件 + 一键审查 + 进度 + 完整报告抽屉
    ├── 审查结论        ← 是否废标 + 废标原因 + 分级问题 + 报告下载
    └── 审查历史        ← 我的记录列表、查看、重试、删除、分页
```

后端支撑模块（不是页面，但决定了能力边界）：**解析服务 / 规则服务 / AI 审查服务 / 报告服务 / 报告文档服务 / 配置服务 / 任务编排（异步流水线）**。

## 4. 管理端模块明细

### 4.1 审查任务（`/bidding/bid-review/task`，页面 `bidding/bidReview/task/TaskPanel`）

权限码：`bidding:bid-review:query`（查看）、`:create`（建单）、`:generate`（一键生成/重跑）、`:update`（取消/重试）

| 功能 | 说明 |
|---|---|
| 分页台账 | 按任务名/编号、提交人、来源场景、状态、结论、时间区间筛选 |
| 统计看板 | 总数、运行中、成功、失败；结论分布（通过/存在风险/不通过）；问题级别分布；**高频问题 TOP10**（按规则**名称**展示，不显示规则编码） |
| 建单 | 管理端替本人/他人建单，可指定规则集、标书、招标文件；`generate=true` 立即排队执行 |
| 一键生成 / 重跑 | 重新触发整条流水线（管理端不校验归属） |
| 取消 | 非终态任务可取消 |
| 提交人回填 | `owner_name` 为空时按 `owner_user_id` 批量解析昵称（一次调用，不是 N+1） |

### 4.2 问题复核（`/bidding/bid-review/issue`，页面 `bidding/bidReview/issue/IssuePanel`）

权限码：`bidding:bid-review:query`（查看/统计）、`:audit`（复核）

| 功能 | 说明 |
|---|---|
| 问题分页 | 按规则、级别、状态、来源（AI / 确定性规则）筛选 |
| 统计 | 各严重级别数量、命中 TOP 规则 |
| 逐条复核 | 状态流转：`OPEN`（待处理）→ `CONFIRMED`（确认） / `IGNORED`（误报，**不计入结论**） / `FIXED`（已整改）；记录复核人、时间、备注 |
| 结论联动 | 复核为误报后，自动重算任务结论（`refreshTaskVerdict`） |

### 4.3 审查规则库（`/bidding/bid-review/rule-set`、`/rule-item`，页面 `bidding/bidReview/rule/RulePanel`）

权限码：`bidding:bid-review:rule:query`（查看）、`:rule:update`（维护）

| 功能 | 说明 |
|---|---|
| 规则集管理 | 新建/编辑/启停/删除；字段含 `rule_set_code`、`rule_set_name`、来源（平台默认 / 招标文件抽取）、`default_flag`、`rule_cnt`、解析状态 |
| 规则项管理 | 分类、规则名称、检查方式（`AI` 模型判定 / `RULE` 确定性关键词匹配）、严重级别、满分、审查要求、证据提示、来源引用、排序、启停 |
| 招标文件抽取 | 规则集可绑定招标文件（`tender_file_id` + SHA256），从招标文件解析出的要求形成项目专属规则 |
| 现状数据 | 3 套「平台默认审查规则集」（tenant 1 / 0 / 2019 各 1 套），每套 12 条；全部规则分类分布：资格 12、格式 9、技术 6、响应 3、报价 3、商务 3 |

### 4.4 报告与统计（`/bidding/bid-review/report`、`/config`，页面 `bidding/bidReview/report/ReportPanel`）

权限码：`bidding:bid-review:query`（报告）、`:config:update`（AI 配置）

| 功能 | 说明 |
|---|---|
| 报告台账 | 报告编号、所属任务、结论、得分、是否已生成 Word、生成时间 |
| 报告详情 | 网页版报告（结论 + 评分 + 问题汇总） |
| 报告下载 | `GET /report/doc` 生成/复用 **Word（.docx）**；同一任务只生成一次，复用已生成文件 |
| AI 配置 | 查看/维护模型、base-url、超时、重试、并发、分片大小等（密钥只从环境变量注入，**不落库**） |
| AI 连通性探测 | `POST /config/ai-probe` 一键测试 Key/模型可用性 |

## 5. 个人端模块明细

入口：门户「合规审查」→ 工作台 `/portal/bidding/bidReview/review`（左侧两个页签 + 结论页）。

### 5.1 标书审查（`index.vue`）

| 功能 | 说明 |
|---|---|
| 上传标书 | 拖拽/点击上传，支持 .pdf/.docx，单文件 ≤ 30MB；上传后展示文件名与大小，可重传 |
| 上传招标文件（可选） | 传了则按本项目要求逐条比对；不传则按平台规则库自查 |
| 任务名称 | 必填，默认取文件名前 20 字 |
| 所属企业 | **不展示、不可选**（2026-09-22 口径），系统静默按 §2.1 归属 |
| 一键审查 | 建单 + 立即执行；**幂等**：同人 + 同标书 + 同招标文件复用已有任务，不重复消耗 token |
| 进度展示 | 轮询（1.5s）：排队 / 审查中 / 已完成 / 已失败 / 已取消 + 当前步骤 + 百分比 |
| 中途操作 | 运行中可取消；失败可重试（限次） |
| 结果速览 | 结论（通过 / 存在风险 / 不通过）、规则条数、问题条数（含高危数）、自评得分、按级别折叠的问题清单（含证据与建议） |
| 完整报告抽屉 | 抽屉内渲染报告 HTML + 「下载报告文档（Word）」（直接触发下载，不跳转文件页） |
| 页签保活 | 审查未完成时切到「审查历史」再切回，**不重建页面**（进度、任务、表单都保留）；审查完成才跳结论页 |

### 5.2 审查结论（`result.vue`，路由 `/portal/bidding/bidReview/result?taskId=`）

| 功能 | 说明 |
|---|---|
| 是否废标 | 大字号结论：废标 / 不废标 |
| 废标原因 | 命中高危（且未被判为误报）的规则**名称**列表；无原文证据时证据文案统一为「标书没有对应内容」 |
| 问题分组 | 高危 / 中危 / 低危三段展示，每条含说明、证据（定位）、建议 |
| 报告下载 | 一键下载 Word 审查报告 |

### 5.3 审查历史（`history.vue`）

| 功能 | 说明 |
|---|---|
| 我的记录列表 | 分页；列含任务名、状态、结论、时间（时间走统一格式化，不显示 epoch 数字） |
| 状态轮询 | 排队/审查中的记录自动刷新 |
| 查看 | 已完成 → 跳结论页 |
| 重试 | 失败记录一键重提 |
| 删除 | 逻辑删除本人记录（带二次确认） |
| 刷新联动 | 新提交审查后由父级通知刷新列表 |

## 6. 核心流程

### 6.1 一键审查流水线（异步，四步）

| 步骤 | 进度 | 做什么 | 失败处理 |
|---|---|---|---|
| `PARSE` | 25% | 下载文件（相对地址→容器内绝对地址）→ PDF/DOCX 抽正文 | 抽不出文字 → `BID_REVIEW_PARSE_EMPTY`，提示上传文字版；**不调模型** |
| `RULE` | 50% | 取规则集（未指定则用默认集） | 无可用规则 → 明确报错「请先维护规则库」 |
| `GENERATE` | 80% | 逐条规则判定：`check_mode=RULE` 走确定性关键词匹配（**不耗 token**）；其余走 AI 比对；写问题项 | 单条失败不中断整单 |
| `REPORT` | 100% | 汇总结论、评分、问题摘要，生成报告（网页 + 可按需导出 Word） | — |

任务状态机：`QUEUED → RUNNING → SUCCESS / FAILED / CANCELED`；记录 `cost_ms`、`ai_called`、`retry_count`、`error_code/error_msg`。

### 6.2 幂等与省 token

- 建单幂等键：`owner_user_id + bid_file_id + tender_file_id`（`idempotent_key` 唯一索引），重复提交直接返回已有任务。
- 规则类（`RULE`）判定不调用模型；正文按 `chunk-size`（默认 30000 字符）内联，避免超长上下文。

### 6.3 报告生成

- 报告行落库：`report_no`、`verdict`、`score_total`、`score_json`、`issue_summary_json`、`conclusion`、`html_content`。
- Word 文档**手写最小 OOXML**（零新增依赖），文件名 = 任务名 + 报告号；存储名加时间戳避免重名覆盖；同一任务只生成一次（`docx_file_id/docx_file_url` 复用）。
- 历史报告去重兼容：老数据 `conclusion` 里若带「## 问题清单」，文档渲染时截断，避免同一清单出现两遍。

## 7. 关键业务规则

| 规则 | 口径 |
|---|---|
| 风险级别 | `HIGH` 高危 / `MEDIUM` 中危 / `LOW` 低危 |
| 审查结论 | `PASS` 通过（无问题）/ `RISK` 存在风险（仅中低危）/ `FAIL` 不通过（命中高危） |
| 是否废标 | `FAIL` 即视为存在废标风险（`rejected=true`），原因是命中的高危规则名称 |
| 证据不足 | AI 判高危但给不出标书原文证据时，**仍按高危计**，证据文案统一「标书没有对应内容」（2026-09-20 按用户口径调整，取代原来的"自动降级为 MEDIUM"） |
| 误报复核 | 问题被复核为 `IGNORED` 后不计入结论，并触发任务结论重算 |
| 来源标记 | 问题带 `source`（AI / RULE）与 `ai_confidence`，便于区分模型判定与确定性规则 |

## 11. AI 接入与成本控制

配置段：`bidding.review.ai.*`（`application.yaml`，可用环境变量覆盖）

| 配置 | 默认值 | 说明 |
|---|---|---|
| `enabled` | true | 关闭后一键生成会明确报「未配置」 |
| `base-url` | `https://api.deepseek.com/v1` | OpenAI 兼容 |
| `api-key` | 空 | **只从环境变量注入**（`deploy/.env`），不落库、不进仓库 |
| `model` | `deepseek-chat` | 切 `deepseek-reasoner` 时须置 `json-mode=false`（它不支持 `response_format/temperature`） |
| `json-mode` | true | JSON 模式要求提示词含 "json"，客户端已兜底补写 |
| `temperature` | 0.2 | 判定场景取低随机性 |
| `timeout-seconds` / `retry-times` | 60 / 2 | 仅对连接异常、5xx、429 重试 |
| `concurrency` | 4 | 并发闸门，防止一键生成打满 Key 配额 |
| `chunk-size` | 30000 | 单次内联正文上限（字符） |
| `bidding.review.file.base-url` | `http://server:48080` | 容器内文件服务地址（服务端下载用） |

## 12. 文件与部署形态

- **文件地址口径**：infra 返回相对路径（`/admin-api/infra/file/4/get/...`）。前端浏览器按同源代理访问；**服务端下载时由 `resolveDownloadUrl` 补成容器内绝对地址**（`{file.base-url} + path`），宿主机地址（127.0.0.1/localhost）也一并替换。
- **本地联调拓扑**：MySQL(3307)、Redis(6379)、`txgy-server`(48080，单体只跑 system+infra)、`txgy-bidding`(48110)、前端 dev server(5667)。
  > 本地单体刻意**不启用** bpm/crm/hrm/mes/wms 等模块：它们与标书审查无关，且会额外引入 Flowable 建表与依赖。
- **端口**：前端 dev 5667（正式静态部署曾用 5666，本地已停用）。
