## 〇、结论摘要（先看这一页）

**一句话诊断**：管理端现在不是"功能少"，而是**同一件事被做了两遍，同时有三处后端能力没有前端出口**。

| 现象 | 硬证据 |
|---|---|
| **任务列表 + 概览统计 + 报告抽屉，被完整实现了两遍** | `task/TaskPanel.vue` 与 `report/ReportPanel.vue` 各自调用 `getReviewOverview()` + `getReviewTaskPage()`，各自有一个"审查报告"抽屉（`br-` 与 `brp-` 两套重复样式） |
| **管理端"建单"能力从未被使用** | 后端 `POST /task/create` 存在（权限码 `bidding:bid-review:create`），前端 `api/bidding/bidReview/index.ts` **没有对应封装**；库里 9 个任务的 `source_scene` **全部是 `PORTAL_SELF`**，`ADMIN_TASK` 0 条 |
| **复核功能从未被使用** | 库里 42 条问题项 **全部是 `OPEN`**（高危 11 / 中危 21 / 低危 10），`CONFIRMED/IGNORED/FIXED` 各 0 条 —— 因为复核只藏在"某任务的抽屉里"，没有跨任务工作台 |
| **10 类字典齐全，页面全部硬编码** | `bidding_dict_data` 已有 `bid_review_status/verdict/severity/step/scene/issue_status/issue_source/rule_category/rule_type/check_mode` 共 10 类；三个面板仍各自硬编码 `statusTag`/`severityTag`/`verdictLabel` 与 6 组 `options` |

**目标**：把管理端从"3 个互相重叠的页面"收敛为 **5 个职责单一的页面 + 3 个可复用组件**，并让后端已有能力全部有前端出口。

```
标书审查（目录 60007000）
├── 1 审查任务          任务台账 + 建单 + 详情（结论/问题清单/报告）
├── 2 问题复核    ★新增  跨任务「待复核问题」工作台
├── 3 审查规则库        规则集 + 规则项
├── 4 报告与统计        概览 / 分布 / 高频问题 / 报告台账与导出
└── 5 AI 与运行配置 ★新增 AI 配置 + 连通性自检（从"审查任务"页抽出）
```

## 二、问题清单（逐条带证据）

### P1 任务列表 + 概览统计 + 报告抽屉，被实现了两遍

- **证据**：`TaskPanel.vue` 与 `ReportPanel.vue` 都调用 `getReviewOverview()`（全项目 4 处引用 = 2 个页面 × 声明+调用）与 `getReviewTaskPage()`；两页各有一个 `reportOpen` 抽屉，样式类分别是 `.br-report__*` 与 `.brp-report__*`（同一份 DOM 复制两份）。
- **影响**：改一处漏一处；两个页面的"审查报告"长一样但用户不知道该点哪个；代码量虚高。
- **处置**：抽 `BidReviewReportDrawer.vue` 组件；任务表只保留在「审查任务」页；「报告与统计」改为**报告台账**（只列已出报告的任务）。

### P2 概览统计被两个页面各查一次

- **证据**：两页 `onMounted` 都 `Promise.all([loadOverview(), loadTasks()])`；`/task/overview` 是**全表聚合**查询。
- **影响**：同一批数字在两页出现，且刷新时机不同 → 用户看到"两边数字不一样"。
- **处置**：概览只在「报告与统计」呈现；「审查任务」页去掉 6 个统计卡（保留 1 行极简指标或直接不要）。

### P3 同一结论两套文案

- **证据**：`TaskPanel` 的 `verdictLabel.FAIL = '不通过'`；`ReportPanel` 的 `verdictLabel.FAIL = '不通过（废标）'`；字典 `bid_review_verdict.FAIL` 的 label 是 `'不通过'`。
- **影响**：同一状态三种说法；口径漂移。
- **处置**：一律走字典 `bid_review_verdict`；需要强调"废标"时用 **独立字段 `rejected`**（布尔）另列一列，不靠改 label 表达。

### P4 管理端"建单"能力没有前端出口

- **证据**：后端 `POST /task/create`（`BidReviewTaskCreateReqVO`：taskName/ownerUserId/ruleSetId/招标文件三件套/投标文件三件套/projectId/tenderProjectId/remark/generate）存在；`api/bidding/bidReview/index.ts` **无 create 封装**；库里 `ADMIN_TASK` 0 条；权限点 `60007104 建单`（`bidding:bid-review:create`）已入库但页面上无任何按钮。
- **影响**：管理员"替经办人补建一次审查"只能让对方自己去门户传；权限点空转。
- **处置**：「审查任务」页增加「新建审查任务」按钮 + 表单，接 `POST /task/create`。

### P5 报告导出能力没有前端出口

- **证据**：后端 `GET /report/export`（返回报告正文 HTML，供打印/另存）存在；前端只封装并使用了 `/report/get` 与 `/report/doc`。
- **影响**：管理端只能下载 Word，不能"打印/另存 HTML"。
- **处置**：「报告与统计」的报告台账增加「导出 HTML」动作（新 URL 打开 or 下载）。

### P6 AI 配置挂错地方、权限点也挂错

- **证据**：`TaskPanel.vue` 里有一个 `aiConfigOpen` 抽屉（模型/JSON 模式/温度/并发/内联上限 + 自检）；而权限点 `60007302 AI 配置维护`（`bidding:bid-review:config:update`）的 `parent_id = 60007300`（报告与统计）。
- **影响**：① 在"审查任务"页做运维配置，语义不搭；② 授权界面里"AI 配置维护"挂在"报告与统计"下，管理员找不到；③ `openAiConfig()` 失败时只弹 warning，用户不知道为什么。
- **处置**：抽出独立的「AI 与运行配置」页面 `60007460`，把 `60007302` 迁到它下面。

### P7 字典齐全但页面全硬编码（三份重复）

- **证据**：`bid_review_*` 10 类字典已入库；`TaskPanel` 里有 `statusTag`(5) + `severityTag`(3) + `verdictLabel`(3) + 2 组 options；`RulePanel` 里有 6 组 options（category/ruleType/severity/checkMode/source）；`ReportPanel` 里又有一份 `verdictLabel` + 1 组 options。API 文件头注释明写"标签一律走字典（`bid_review_*`）显示，别在页面硬编码中文"，**但没有任何页面执行**。
- **影响**：改字典不生效；枚举加一个值要改 3 个文件；与规范 §4.4 冲突。
- **处置**：新增 `useBiddingDict()`（封装 `GET /bidding/meta/dicts`，带内存缓存），三个面板 + 新增页面统一从字典取 label 与色值（字典里已带 `color_type`）。

### P8 没有跨任务的「待复核问题」工作台

- **证据**：复核入口只在 `TaskPanel` 的"问题清单"抽屉里（必须先知道是哪个任务、再点进详情）；库里 42 条问题 100% `OPEN`。
- **影响**：复核人（法务/造价/技术）无法"今天把待复核的清一遍"；复核这个动作事实上没发生。
- **处置**：新增「问题复核」页 `60007450`，默认筛 `status=OPEN`，跨任务列出待复核问题，支持按级别/类别/来源/任务编号筛选。后端 `GET /issue/page` 已支持，**无需改后端**。

### P9 问题清单抽屉固定 50 条、无筛选

- **证据**：`loadIssues()` 写死 `{ pageNo: 1, pageSize: 50, taskId }`；后端 `BidReviewIssuePageReqVO` 支持 `severity/category/status/source` 四个附加筛选，前端一个都没用。
- **影响**：问题多的任务看不全（当前单任务最多 11 条，但 42 条总量说明量级会上来）；无法"只看高危"。
- **处置**：抽 `BidReviewIssueTable.vue`，带分页 + 级别/状态/类别/来源筛选，任务详情与复核页共用。

### P10 "证据不足"标记没有展示（与既有口径矛盾）

- **证据**：`bidding_bid_review_issue.evidence_lack` 字段存在；`TaskPanel` 的证据列只在 `evidenceText` 为空时兜底显示"标书没有对应内容"，**不读 `evidence_lack`**。
- **背景**：用户此前明确口径——「AI 判成高危但给不出标书原文证据时，**直接保持高危**，原文证据写『标书没有对应内容』」，即 `evidence_lack=true` 是一等公民信息。
- **影响**：复核人无法区分"有原文证据"和"证据不足但按高危处理"，复核判断依据缺失。
- **处置**：证据列显示 `evidence_lack` 徽标；复核页把"证据不足"作为可筛选维度（前端按 `evidenceText` 空 + 标记双条件，或后端加 `evidenceLack` 入参——见第五章）。

### P11 任务列表与详情信息缺口

- **证据**：现有表列 = 任务编号/任务名称/来源/状态/结论/问题(高危)/耗时/操作。缺 **创建时间、提交人、是否废标、废标原因**；抽屉只展示 4 个字段（编号/规则集/规则条数/自评得分），缺 `parse_mode`（文本层/无文字层）、`ai_called`、`retry_count`、`started_time/finished_time`、`error_code`。
- **影响**：用户此前专门问过"审查历史的时间为什么不是审查时的时间"，说明时间字段很关键；管理端却连创建时间都没显示。失败任务只看得到 `error_msg`，看不到错误码（无法对照 §4.7 的 `1-060-113-xxx`）。
- **处置**：列表补 提交人 / 创建时间 / 是否废标；详情补 解析方式 / AI 是否调用 / 重试次数 / 开始完成时间 / 错误码+错误信息 + **废标原因列表**（`rejectReasons`）。

### P12 三个统计口径问题

- **证据**：① `aiCallsLast24h` 后端返回但两个页面都**没用**；② `aiFailureRate` 为 `null` 时页面渲染 `0.0%`（看起来"AI 一切正常"）；③ "完成率"用 `successCount / totalCount`，分母含 `QUEUED/RUNNING` → 任务一多，完成率天然偏低。
- **处置**：① 展示"AI 调用(24h)"；② `null` 显示 `—`；③ 改名"成功占比"或改分母为终态任务数（`SUCCESS + FAILED + CANCELED`），二选一（决策点 D4）。

## 三、设计原则

| # | 原则 | 落地判据 |
|---|---|---|
| 1 | **一页一事** | 每页只有一个主对象：任务 / 问题项 / 规则 / 报告 / 配置 |
| 2 | **一次查询** | 同一数据源在一屏内只查一次；跨页不重复渲染同一列表 |
| 3 | **字典是唯一真源** | 所有枚举 label 与色值来自 `bid_review_*` 字典，页面不出现枚举中文字面量 |
| 4 | **后端有能力，前端必须有出口** | 每个管理端端点都要有对应 UI 入口（否则登记为"刻意不暴露"并写明原因） |
| 5 | **复核是一等公民** | 复核人不应该先找任务才能干活；提供跨任务待办视图 |
| 6 | **信息分层** | 列表给"能不能快速判断"，详情给"为什么"，报告给"对外交付" |
| 7 | **组件复用** | 标签、问题表、报告抽屉三类抽成组件，禁止第 4 份复制 |
| 8 | **管理端与门户边界清晰** | 管理端=全量台账+规则+复核+配置；门户=上传+一键生成+看自己的报告 |

### 4.3 各页面详细设计

#### 4.3.1 审查任务（60007100）

**布局**：单卡片（**去掉顶部 6 个统计卡**，仅保留一行文字摘要，如"共 9 个任务，2 个执行中"）。

**筛选行**：任务编号 `taskNo` | 任务名称 `taskName` | 来源 `sourceScene` | 状态 `status` | 结论 `verdict` | 创建时间 `beginTime~endTime` | 查询 / 重置

- 「是否废标」筛选**不新增后端入参**：按既定口径 `rejected=true ⟺ verdict=FAIL`，用 `verdict=FAIL` 表达即可。
- 「提交人」第一版只做**列展示**；按姓名模糊筛选需后端补 `ownerName`（见第五章）。

**表格列（10 列内）**：任务编号 / 任务名称 / 来源 / 提交人 / 状态（含进度百分比） / 是否废标 / 结论 / 问题（高危/总） / 创建时间 / 操作

**行操作**：详情 · 报告（`reportReady` 时） · 重跑（`FAILED/SUCCESS`） · 取消（`QUEUED/RUNNING`）

**右上动作**：「新建审查任务」（`can('bidding:bid-review:create')`）

**任务详情抽屉（宽 1100）**，分四区：

1. **基本信息**（`a-descriptions` 12 字段）：任务编号 / 来源 / 提交人 / 任务名称 / 规则集 / **解析方式**（`TEXT` 文本层 / `EMPTY` 无文字层） / **AI 是否调用** / **重试次数** / 创建时间 / 开始时间 / 完成时间 / 耗时 / 备注
2. **结论卡**：是否废标（布尔，取 `rejected`）+ **废标原因列表**（`rejectReasons`，无则显示"未命中废标项"）+ 结论 + 自评得分 + 分项得分（`scoreItems`）+ 失败信息（`errorCode` + `errorMsg`）
3. **问题清单**：复用 `BidReviewIssueTable`（筛选 级别/状态/类别/来源 + 分页 + 复核操作）
4. **底部动作**：查看报告 / 下载 Word（复用 `BidReviewReportDrawer`）

> 详情数据一律走 `GET /task/get`（顺带用掉 P13 的死封装 `getReviewTask()`），而不是直接拿列表行对象——列表行不含 `scoreItems`/`parseMode` 等字段。

**新建任务表单（Modal 720）**：

| 字段 | 必填 | 说明 |
|---|---|---|
| 任务名称 | ✅ | 默认取标书文件名 |
| 归属人 `ownerUserId` | ✅ | 默认当前管理员；替经办人建单时改选 |
| 规则集 `ruleSetId` | 否 | 默认取 `defaultFlag=true` 的平台规则集 |
| 投标文件（标书） | ✅ | 走 `/bidding/file/upload` 取 `file_id`（与门户同一 file_id 契约） |
| 招标文件 | 否 | 传了则按本项目逐条比对 |
| 关联项目 / 招标项目 | 否 | `projectId` / `tenderProjectId` |
| 备注 | 否 | — |
| 保存并立即执行 `generate` | — | 默认开 |

幂等：一次点击生成一个 `idempotent_key`（表已有该列，规范 §4.5）。

#### 4.3.2 问题复核（60007450）★新增

**存在理由**：复核人不需要先知道"是哪个任务"。当前 42 条问题 100% `OPEN`，正是因为入口藏在任务抽屉里。

**布局**：

1. **顶部 4 个小指标**：待复核 / 已确认 / 已忽略 / 已整改（第一版用 4 次 `GET /issue/page?status=X&pageSize=1` 取 `total`；后端加聚合接口后替换，见第五章）
2. **筛选行**：任务编号 `taskId`（下拉或输入任务号解析）/ 严重级别 `severity` / 类别 `category` / 复核状态 `status` / 来源 `source` / 证据是否不足 / 查询 / 重置
3. **默认筛选**：`status = OPEN`（打开页面即"我的待办"）
4. **表格列**：任务编号 / 级别 / 类别 / 问题标题 / 证据（`evidenceText` + **证据不足徽标** `evidenceLack`） / 建议 / 来源 / AI 置信度 / 复核状态 / 复核人 / 复核时间 / 操作
5. **复核弹窗**：状态（确认 / 忽略 / 已整改）+ 复核意见 `reviewRemark`（选"忽略"时必填理由，留痕）

**不做批量复核**：后端 `PUT /issue/review` 只有单条接口；批量列入第五章可选增强，避免前端假批量。

#### 4.3.3 审查规则库（60007200）

结构保留（规则集列表 → 规则项抽屉），改动集中在四处：

| 改动 | 说明 |
|---|---|
| 枚举走字典 | `category` / `ruleType` / `checkMode` / `severity` / `source` 全部改从 `bid_review_*` 字典取 label |
| 规则项改分页 | 现在是 `pageSize: 100` + `pagination: false` 硬拉；改为后端分页（`/rule-item/page` 已支持） |
| 规则项补列 | 增加 **启用状态**、**满分 `scoreMax`**、**出处 `sourceRef`**（字段已有，页面没展示） |
| 规则集补列 | 增加 **更新时间**（判断"规则昨天有没有被改"） |

保留既有交互：删除二次确认；"被任务引用过的规则集不允许删除"由后端错误码返回（现有弹窗文案已声明）。

#### 4.3.4 报告与统计（60007300）

**去掉**重复的全量任务表与第二份概览逻辑，改为三段：

1. **指标区（6 项）**：任务总数 / 执行中 / 已完成 / 失败 / **成功占比** / **AI 调用（24h）**
   - 修正 P12：`aiFailureRate` 为 `null` 显示 `—`（不再渲染 `0.0%`）；把后端已返回却未用的 `aiCallsLast24h` 展示出来；"完成率"改名"成功占比"（分母含排队中任务，叫"完成率"名不副实）。
2. **分布区（3 卡，保留现状）**：结论分布（通过 / 存在风险 / **不通过=废标**）· 问题级别分布（高危=废标项 / 中危 / 低危）· 高频问题 TOP10（按 `rule_code` 聚合）
3. **报告台账**：列 = 报告编号 / 任务编号 / 任务名称 / 结论 / 是否废标 / 自评得分 / 是否 AI 生成 / 报告生成时间 / 操作（查看 · 下载 Word · **导出 HTML**）
   - 数据源见决策点 D3（`task/page` 加 `reportReady` 入参，或新增 `GET /report/page`）
   - 「导出 HTML」接上后端已有但前端未接的 `GET /report/export`

**报告抽屉**：只保留一份实现（`BidReviewReportDrawer.vue`），任务页与报告页共用。

#### 4.3.5 AI 与运行配置（60007460）★新增

把 `TaskPanel` 里的 `aiConfigOpen` 抽屉整段抽出成独立页面，并补齐语义：

| 变更原因 `changeReason` | **改为必填输入**（后端 ReqVO 已有该字段，现在前端写死"管理端配置页调整"，等于没有留痕） |
| 连通性自检 | 保留「测试连接」，展示模型名 / 耗时 / 错误信息 |
| AI 调用流水（可选） | `bidding_bid_review_ai_log` 已有 8 条数据但无查询接口 → 见第五章，需后端补分页接口后本轮或下轮接入 |

**权限**：进入页面看配置需要 `bidding:bid-review:query`；保存与自检需要 `bidding:bid-review:config:update`——无该码的账号进入页面时**配置区只读 + 顶部提示缺哪个权限**（不再只弹一个 warning 就完事）。

```sql
SELECT id,name,type,sort,path,component FROM system_menu
 WHERE parent_id=60007000 AND deleted=b'0' ORDER BY sort;

-- ② 两个共用动作的归属正确（60007103 挂 60007000；60007302 挂 60007460）

 WHERE id IN (60007103,60007302,60007450,60007460) ORDER BY id;

-- ③ 60007100 下不应再挂着 60007103
SELECT id,name FROM system_menu WHERE parent_id=60007100 AND deleted=b'0' ORDER BY sort;
-- 期望：60007101 / 60007102 / 60007104
```

## 七、风险与回滚

| 风险 | 触发条件 | 处置 |
|---|---|---|
| **权限回归** | 移动 `60007103` / `60007302` 的 `parent_id` | id 不变 → `system_role_menu` 的 `(role_id, menu_id)` 语义不变，**不回收任何授权**；执行前备份两张表 |

### 编写原因

用户提出「标书审查模块管理端重新设计」。核查发现当前管理端的核心问题不是缺能力，而是**三件事叠加**：① `TaskPanel` 与 `ReportPanel` 把"任务列表 + 概览统计 + 报告抽屉"各实现了一遍（含两套重复样式）；② 后端已有能力没有前端出口——管理端建单 `POST /task/create` 无封装（库里 9 个任务 100% 来自个人端自助）、报告导出 `GET /report/export` 无封装、`GET /task/get` 封装了却 0 处调用；③ 复核入口只藏在"某任务的抽屉"里，导致 42 条问题项 100% 停在 `OPEN`，复核这个动作事实上没有发生。此外 `bid_review_*` 10 类字典虽已入库，三个面板仍各自硬编码枚举中文，与《招投标模块开发规范》§4.4 和 API 层注释口径相悖。需要一份能直接照着改的设计，把这五个页面职责划清、把组件抽出来、把后端已有能力接到 UI 上。

### 编写依据

《招投标模块开发规范》（§4.2 分层 / §4.4 菜单与权限码同步 / §4.5 幂等 / §4.7 错误码）；

### 所满足的业务需求内容及其实现方式

| 需求 | 实现方式 |
|---|---|
| 管理端不再"三个页面互相重叠" | 任务台账只在「审查任务」；报告只在「报告与统计」；抽屉与问题表抽成组件，消灭第 2、3 份复制 |
| 管理端能真正"干活"，不只是看 | 补建单（`POST /task/create`）与跨任务复核工作台，让 `source_scene=ADMIN_TASK` 与问题复核从"0 条"变成常规动作 |
| 复核有地方做、有痕迹 | 「问题复核」页默认筛 `OPEN`，支持级别/类别/来源/证据不足筛选；复核写 `reviewer_id/review_time/review_remark` |

| 后端能力无沉没 | 建单、报告 HTML 导出、任务详情三个"有接口无入口"的能力全部接上；`ai-log` 与 issue 聚合作为已知缺口显式登记 |
