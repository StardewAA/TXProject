# 外部公告采集与展示设计方案 v0.6（仓库内实现版）

> 状态：设计草案（仅文档）。v0.1（仓库内自研/死枚举）与 v0.2（独立 Python 微服务）思路均**作废**。
> v0.3 结论：**在 txgy-module-bidding 仓库内实现**（Java + 平台既有能力），不另起 Python、不做独立微服务；
> 结构化交给 AI（大模型出站调用），**AI 侧的冗余/重试由 AI 服务方承担**，本地只保留"消息级有限重试（≤3）→ 转人工审核"，主压力不在本模块。
> v0.4 追加：对同一 项目/招标项目/标段 的**跟踪**，登录投标人可**关注**（公告/项目/标段），新公告发布触发**提醒**（见 §十二）。
> v0.5 决策与追加：①本组全部表走 **G 轨**（平台级聚合；需要租户/用户隔离的表显式带 tenant_id/user_id 列，服务层校验）；②关注沉淀为**“投标人·关注项目列表”**（位置待定，先设计数据库），可见项目**当前进展阶段 + 基础信息**，点入看该项目**公告列表与动态**，有动态才提醒；③下载器之外增加**下载策略器**（当前仅 AI 策略），④PDF-only 场景预留**PDF 解析回调接口**（本版直接回传原文件）；⑤跨模块通知等先留 API 占位。
> **v0.6 修订（以 §十五 为准，覆盖上述冲突表述）**：用户级 4 表回归 **T 轨**（拦截器隔离）；错误码登记 **106** 段；external/feed 接入 **ES 事件链**；PDF 用**本地 OpenDataLoader** 抽取文本+表格，**扫描件抽空直接判失败**；用户身份 v1 默认 system AdminUser。
> 引用：《招投标模块开发规范》（唯一权威、冻结）、01/05/04；法规见 §九（沿用）。

## 一、结论性定位

| 项 | 决定 |
|---|---|
| 实现位置 | 本仓库 txgy-module-bidding 内新增"外部公告"功能组（新表/调度/消费/AI 客户端/展示接口） |
| 是否微服务/Python | 否。复用平台能力：starter-job（调度）、starter-mq（Redis Stream，消息+重试）、starter-redis、starter-web（下载/回调 HTTP） |
| 解析器 | 不手写解析器；**AI 结构化**（固定 Schema 输出）+ 行业分类 |
| 重试冗余 | 消息级最多 3 次 → 失败交 AI 兜底/人工审核；AI 服务端自身的重试由 AI 方负责，本地不做深队列 |
| 下载器 | 通用 HTTP 下载器 + **源/通道配置**（不同平台差异配置化），另支持"AI 摘要"兜底（无法原样时只取关键信息） |
| 身份认证 | 采集由本系统内调度与管理员配置发起（既有 admin 鉴权）；保留"服务账号+HMAC"备用于未来外部试解析/第三方回调 |

## 二、模块内流程（全在本仓库）

```
[starter-job 调度] ──► 下载器(HTTP，多通道配置，增量=url+last_fetch_time)
       │  落原文：HTML 原样 / 接口数据 / PDF 原件（对象存储/本地），投递 MQ
       ▼
   MQ(crawl.downloaded → crawl.process)  Redis Stream（starter-mq）
       │  消费编排：重试 ≤3（指数退避）
       ├─ 成功 ─► 调 AI(固定Schema结构化 + 防腐保温行业三态分类)
       │           └─ 校验器：只查类型/长度/格式（失败→打回重做，计入3次）
       │           └─ 通过 ─► 落库 bidding_notice_external*（去重/生效期/审核状态）─► 对外只读展示
       └─ 3 次失败 ─► 审核队列(记录 url/原文引用/parserCode/原因) ─► 人工审核
```

- 全链路 taskId/urlHash 贯穿，每步写审计日志（阶段/尝试次数/错误码/时间）。
- 打回类型：下载失败→重下；AI 输出不合规（校验不过）→ 重抽；均计入该消息 3 次上限。

## 三、消息与重试（复用 starter-mq：Redis Stream）

- 主题：`crawl.downloaded`（原文就绪）、`crawl.process`（处理/AI）、`crawl.retry`、`crawl.audit`。
- 消息体：`{taskId,url,urlHash,channelCode,parserCode,contentType:HTML|API|PDF,fetchedAt,retryCount,contentRef,extra}`。
- 重试：消费异常/校验失败 → `retryCount+1` 回 `crawl.retry`（指数退避），>3 进审核；**AI 服务端自身的超时/重试由 AI 网关策略处理，本地不展开深重试**。
- 用 Redis Stream 天然支持消息确认/重投；重复消费靠 `urlHash+fetchedAt` 幂等去重。

## 四、下载器（多通道，配置化不写死）

1. 配置表 `bidding_crawl_source`（本模块）：`channelCode/入口URL/抓取间隔/robots 开关/UA/是否启用/所属行业判定策略(默认AI)/备注`——不同平台的 URL 编排差异在配置与可插拔 Adapter Bean 上收敛（`ChannelAdapter` 接口：通用实现 + 平台专属实现，均在本仓库 Java 内）。
2. 增量：读取该 urlHash 最近一次抓取时间，只抓更新。
3. 原文一律先落（对象存储 FileApi 或本地存储按部署），供 AI/审核/复检与展示回源使用。

## 五、AI 结构化 + 行业分类（解析不再手写）

1. **固定 Schema**：AI 按模板（模板 code ↔ prompt/JSON Schema 版本）输出：主列（标题/发布时间/类型原文/发布单位/正文或内容引用/附件/项目编号等）+ `meta_json` 原字段快照。
2. **校验器只做**：字段是否存在、类型、长度、格式（时间/金额/URL http(s)）；不合格返回错误码打回。
3. **防腐保温行业判定**：AI 输出 `BELONGS/NOT_BELONGS/UNCERTAIN + 置信度`；`BELONGS` 进重点展示，`NOT_BELONGS` 留档不推，`UNCERTAIN` 转人工。
4. `parserCode`：URL 审批通过后绑定；决定 AI 模板/通道/校验规则；可换 code 重处理（§六）。

## 六、URL 白名单与审批（管理员/授权人）

- 仅**超级管理员或授权人**可配置/试解析 URL：提交 → 下载+AI 试跑 → 返回数据+原文预览 → 审批通过（绑定 parserCode/规则）→ 该 URL 此后按此 code 自动处理；可多次试跑/改配/再审批，全程留痕。
- 试解析/预览接口用既有 admin 鉴权（如 `bidding:ext-source:try-parse`、`bidding:ext-source:approve`）。
- 未在白名单的 URL 默认不抓。

## 七、数据模型与展示（沿用 v0.1 表草案，域命名待确认）

- `bidding_notice_external` 主档：`title / source_code/source_name / orig_url / orig_url_hash(唯一) / content_hash / content_type(HTML|PDF|ATTACHMENT|IMAGE|OTHER) / content_html(原样) / pdf_file_id+sha256+size(FileApi，红线8) / attachment_ids_json / notice_type_raw / notice_type_code(可空) / legal_flag(Y/N/NULL) / industry_flag(BELONGS/NOT_BELONGS/UNCERTAIN+confidence) / project_code / issuer_name / publish_time / effective_from / effective_to / status(NEW→ACTIVE→INACTIVE→ARCHIVED) / audit_status / public_scope(默认SOCIAL) / fetch_count / last_fetch_time / 审计列`。
- `bidding_notice_external_meta`（动态字段兜底）、`bidding_notice_external_attachment`（附件下载：FileApi 签名 URL + 病毒扫描）、`bidding_crawl_source`（源配置）、`bidding_crawl_task`/`bidding_crawl_job`（任务与批次、失败原因审计）。
- **字段不固定**用"主列稳定 + meta_json 兜底"；种类不写枚举，写源配置与 parserCode；`legal_flag` 处理非依法项目（未知=null，不误标）。
- 展示三形态（对外只读详情，都带**原网址**）：
  - HTML → 原文原样返回（安全：消毒/沙箱，见 §九）；
  - PDF → `pdfFileId/pdfDownloadUrl + origUrl`，前端 JS 预览；
  - 附件 → 逐条下载地址。
- 列表只返回主列（标题/时间/类型/来源/生效期/行业标签），详情才带原文。

## 八、身份认证（按 v0.3 内部实现口径）

1. **本系统内调用**：采集由调度与管理员配置发起 → 全程既有登录态/权限码与内部 MQ，无需外部身份。
2. **对外留口**（文档保留，不实现）：若未来"AI 网关/第三方试解析"需要反向回调，使用 **服务账号 + HMAC-SHA256 签名**（`X-Access-Key/X-Timestamp/X-Nonce/Authorization`，验签+时间窗+nonce 防重放+审计）或固定内网 API-Key——到那时再接，本版不引入。
3. 我方展示/预览接口仅经授权管理员访问；公开列表只出 SOCIAL 内容（01 规则兜底）。

## 九、安全与合规（沿用并精简）

| 项 | 做法/依据 |
|---|---|
| 公开信息范围 | 仅白名单公开源；尊重 robots/ToS，冲突转人工（《网络安全法》《数据安全法》） |
| 展示授权 | HTML 原样/PDF 缓存需源站授权或摘要+原链接+署名；可应诉下架（《著作权法》） |
| 个人信息 | 不收录/展示专家、联系人等敏感字段，脱敏处理（《个保法》） |
| 分级存储 | 采集内容 L1/L2；涉密不采 |
| XSS/SSRF/开放重定向 | HTML 消毒或 sandbox；下载目标 http(s)+IP 校验；外链协议白名单 |
| 附件/PDF 安全 | FileApi 病毒扫描+类型白名单+sha256 |
| AI 调用 | 出站调 AI 网关（HTTPS、密钥走配置中心），AI 端重试由 AI 方负责 |
| 行业标签声明 | 页面注明"以原站/原公告为准"，行业分类仅供聚合推荐 |

## 十、开放问题（推进前确认）

1. 表前缀/归属：默认 `bidding_notice_external_*` + G 轨（平台级聚合）——接受？或需在冻结规范登记新域（需你授权）。
2. 版权展示形态：A 原文全文（需源站授权/白名单） vs B 摘要+原链接（推荐 v1 默认）。HTML 原样只在授权源开。
3. 错误码段：新接口错误码暂挂 199 通用并注释（同备案先例）还是你授权登记新段。

5. 首批白名单源清单；消息队列主题命名是否沿用 `crawl.*`（Redis Stream）。
6. 下载器是否需要反爬增强（IP 池/代理）——默认 v1 不做，靠源配置频控。

## 十一、分期（仓库内 Java 实现）

## 十二、跟踪、关注与提醒（v0.4 追加需求）

> 需求：同一项目/招标项目/标段要被持续**跟踪**（新公告能串成时间线）；登录后的投标人可**关注**某个公告、项目或标段；当有**新公告**发布时**提醒**投标人。

### 12.1 关联与跟踪维度（公告 → 项目/招标项目/标段）

- 归一关联键：公告主档/`meta_json` 中解析出 `project_code`（项目）、`tender_project_code`（招标项目）、`bid_section_code(s)`（标段，招标公告数据集必填 `BID_SECTION_CODES`）。
- 跟踪视图＝按关联键聚合：同一 `bid_section_code / tender_project_code / project_code` 下的所有公告（招标→变更/澄清→候选人→结果）按 `publish_time` 串成时间线；键缺失的公告单独成条（无跟踪维度）。
- 该聚合只读，用于“关注流/项目详情”与触发提醒的匹配。

### 12.2 关注模型（登录投标人）

| 表 | 说明 |
|---|---|
| `bidding_notice_subscription`（G 轨，显式 tenant_id+user_id 列） | `id / tenant_id / user_id / target_type(ANNOUNCEMENT|PROJECT|TENDER_PROJECT|SECTION) / target_key(公告 id 或维度 code) / follow_status(FOLLOWING|UNFOLLOWED) / follow_time / unfollow_time / 审计列`；唯一键 `(tenant_id, user_id, target_type, target_key, deleted)`；同维度重复关注幂等（已关注返回原记录） |
| `bidding_notice_subscription_event` | 提醒事件留痕：`event_key(唯一：user_id+target_key+notice_id) / notice_id / matched_type / channel(IN_APP[,EMAIL]) / channel_status(PENDING|SENT|FAILED) / sent_time / 审计列` |

- 关注权限：登录用户本人（`getLoginUserId()`），仅可管理自己的关注（租户隔离由拦截器保证）。
- 数据范围：投标人只能关注/收到其**可见范围**内的公告——内部公告（internal）仅本租户、公开公告取 SOCIAL+ACTIVE+生效期内的内容；规则沿 01/红线 2。

### 12.3 提醒触发链路（异步解耦，规范 4.6 风格）

```
公告 publish 事务提交后(afterCommit)
   └─► MQ 事件(crawl/notice-published: noticeId)
        └─► 消费者：读该公告的 project/tender/section 维度键
             ├─► 查 bidding_notice_subscription 命中（target_type/target_key 任一匹配且 FOLLOWING）
             │    ├─ 每个命中用户：幂等 event_key（user+target_key+noticeId）防重复
             │    └─ 站内信必发；EMAIL 按用户订阅设置（渠道可扩展）
             └─► 写 subscription_event 状态留痕；失败重试走事件队列（≤3 次→人工）
```

- **同一用户对同一新公告只收一条提醒**（合并多关注命中，事件注明命中的维度）；不打扰已退订用户。
- 关注“公告本身”的用户，在该公告正文发布新版本/状态变更（如发布、变更、撤下后再发）时按需提醒（v1 只提醒“新公告/新版本发布”，撤下不提醒，避免噪音）。

### 12.4 接口（后台/企业用户，登录态）

| 接口 | 说明 |
|---|---|
| `POST /bidding/notice-subscription/follow` | 关注：入参 `targetType + targetKey`；重复关注幂等返回原记录 |
| `POST /bidding/notice-subscription/unfollow` | 取消关注 |
| `GET /bidding/notice-subscription/page` | 我的关注列表（可带 targetType 过滤） |
| `GET /bidding/notice-subscription/feed` | 关注流：命中公告时间线分页（只 SOCIAL+ACTIVE） |
| `GET /bidding/notice/.../timeline`（项目/标段详情内） | 单个 project/tender/section 的全部公告时间线 |

- 权限码建议 `bidding:notice:subscribe`（读/写一体，登录用户即可）；写接口按 4.5 标 `@Idempotent`。

### 12.5 与采集域的关系

- 内部公告（`bidding_notice`）与外站公告（`bidding_notice_external`）都可进入关注流：内部公告 publish 走 12.3 链路；外站公告在“审核通过转 ACTIVE”时同样触发提醒（同一实现，事件源标记来源）。
- 关注/订阅是本仓库内实现（同 v0.3 结论），不另起服务。

## 十三、关注项目列表与阶段视图（数据库设计，v0.5）

> 界面位置待定；此处只设计数据库。核心：投标人“关注的项目列表”→ 每行=一个被关注维度（项目/招标项目/标段）的**当前进展与动态摘要** → 点入后该项目**公告列表 + 动态**。

### 13.1 关注主档 `bidding_follow_item`（=界面上的“关注的项目列表”行）

- 字段：`id / tenant_id(显式) / user_id(显式) / follow_type(PROJECT|TENDER_PROJECT|SECTION) / follow_key(维度代码：project_code/tender_project_code/bid_section_code) / display_name(项目/标段名快照，最新公告解析回填) / issuer_name / stage_code / stage_name(进展阶段快照，见 13.4) / base_json(基础信息快照：建设单位、监管、招标方式、地点等关键几项) / latest_dynamic_time(最近动态时间) / unread_count(未读动态数，读后清零) / follow_time / unfollow_time / follow_status / 审计列`
- 唯一键 `uk(tenant_id, user_id, follow_type, follow_key, deleted)`；重复关注幂等。

### 13.2 动态/事件 `bidding_follow_item_event`（列表的“动态信息”来源 + 未读/提醒依据）

- 字段：`id / tenant_id / user_id / item_id(所属关注行) / source(INTERNAL|EXTERNAL) / event_type(NOTICE_PUBLISHED|NOTICE_UPDATED|EXTERNAL_ACTIVE|STAGE_CHANGE) / notice_id(可空) / event_key(唯一：user+item+source+notice_id/版本) / title_snapshot / orig_url / occurred_at / read_flag(未读=提醒) / 审计列`。
- “有动态信息才通知”判定：关注行新增事件且用户未读 → 触发通知（§12.3 链路；同一用户同一事件只提醒一次）。

### 13.3 公告→关注项的归属（时间线数据来源）

- 公告（内部 `bidding_notice` 或外部 `bidding_notice_external`）落库后，按解析出的 `project_code/tender_project_code/bid_section_code(s)` 关联到关注行：同一维度键的多条公告串成该项目公告列表/时间线；归属在事件写库时顺带回写关注行的 `latest_dynamic_time/unread_count/stage`。

### 13.4 进展阶段推导（stage）

- 阶段 code 建议：`PENDING(未见招标) / TENDER(招标/资审) / OPEN_BID(投标/开标进行) / EVAL(评审) / RESULT(候选人/结果公示) / CONTRACT(合同/定标后) / DONE(结束) / UNKNOWN`。
- 推导规则（v1 简单映射，文档级）：内部公告按 notice_type（招标公告→TENDER；变更→同前阶段刷新时间；开标/评标→EVAL；中标候选人→RESULT；结果→RESULT；合同→CONTRACT）；外部公告按 `notice_type_raw` 关键词映射（解析不到→UNKNOWN 不猜）；阶段变化写 `STAGE_CHANGE` 事件并刷新关注行。

### 13.5 接口（对应界面，登录态）

| 接口 | 说明 |
|---|---|
| `GET /bidding/follow-item/page` | 我的关注项目列表（阶段、基础信息、最新动态时间、未读数） |
| `GET /bidding/follow-item/{itemId}/timeline` | 该项目公告列表+动态（分页） |
| `POST /bidding/follow-item/{itemId}/read` | 标记已读（清未读） |
| `POST /bidding/follow-item/follow` / `unfollow` | 关注/取消（§12.4 关注原语可落到本表） |

## 十四、下载策略器与 PDF 解析（v0.6）

### 14.1 下载策略器（Strategy）

- 概念：下载器产出原文后，由**策略器**决定“怎么把原文变成结构化信息”。当前策略枚举：`AI_STRATEGY`（默认：AI 分类+信息提取，模板 code 驱动）；预留 `RULE_STRATEGY`（不用 AI 时的规则/人工审核兜底）——实现为可插拔 Bean（`NoticeParseStrategy` 接口 + 按策略码路由），后续加策略不改主流程。
- 消息里的 `parserCode` 即“策略码+模板版本”；URL 审批通过时绑定（§六）。

### 14.2 PDF-only 场景与解析（v0.6 改为本地 OpenDataLoader）

- 场景：爬虫只拿到 PDF（无 HTML/文本）→ 需先抽取文本/表格才能分类/提取。
- 设计（v0.6）：下载器把 PDF 落 FileApi（pdf_file_id+sha256）→ **本地 Java 库 OpenDataLoader（本地模式）抽取：只抽文本 + 表格**（不 OCR、不排版重建）→ 结果落 external 主档 `extraction_status=SUCCESS / extraction_text / extraction_tables_json / extraction_at` → 文本/表格就绪后再走 AI 分类+提取（或规则策略）。
- **扫描件规则：OpenDataLoader 未抽到任何文本/表格（返回空）→ 直接置 `extraction_status=FAIL_EMPTY` 并报错失败**（错误码 106 段，进入重试计数；不静默通过，不强行依赖 OCR）。
- 无论成败，PDF 原件 + origUrl + 下载地址始终保留、可回源展示。
- 取消 v0.5“外部解析器回调/直返原文件占位”方案（除非未来 OpenDataLoader 换远程模式再走回调）。

### 14.3 跨模块/通知渠道 API 预留

- 通知（站内信/邮件）真实下发属平台其它模块能力：本组先定义**接口占位**（如 `bidding` api 侧 `BiddingNotifyApi#push(...)` 接口 + server 内空实现/降级为写站内事件表），待平台通知域就绪后替换实现；不阻塞关注/事件建模。
