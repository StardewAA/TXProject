## 〇、结论摘要（先看这一页）

**一句话诊断**：管理端的乱不是"缺设计"，而是**同一批功能被三代历史口径各做了一遍，下线/改名/迁移之后又没有清尾**——老顶级菜单 `tender`、新顶级菜单 `/bidding`、独立顶级菜单 `certificate` 三套并存，中间夹着软删除残留、号段预约未落地、孤儿页面。

| # | 病灶 | 一句话证据 | 目标态 |
|---|---|---|---|
| 1 | **三个顶级入口名字近义** | `51000 招投标管理`(tender, sort 95)、`6735 招投标`(/bidding, sort 301)、`60005000 资质与证书管理`(certificate, sort 1100) 同时存在 | 招投标业务域**只留 `6735`**；`51000`（tender 旧域）**已于 2026-09-20 整体删除**；`60005000` 作为资质域保留但补授权 |
| 2 | **排序断档、顺序反直觉** | `6735` 下 sort = 1 / 2 / 3 / 30 / 40 / **1000** / **1001**，公告被排到审查、报表之后 | 统一 10/20/30…，按**业务链路**排：采集 → 公告 → 项目 → 投标 → 审查 → 主体 |
| 3 | **目录里塞着"页面"** | `6736 外部公告审核管理`、`6748 投标流程跟踪` 是 `type=2` 页面，却直接挂在 `6735` 下与目录同级 | 各自归入对应二级目录；`6735` 下**只放目录** |
| 4 | **软删除残留** | `6739/6740/6744/6745` 的 `deleted=1`，而 `6747 批次查询`(`deleted=0`) 仍挂在本已删除的 `6740` 下；`system_role_menu` 里还留着 `6740` 的授权行 | 恢复 `6739/6740/6744`，保持 `6745` 删除，清理指向已删父级的孤儿按钮 |
| 5 | **页面权限码与语义错配** | `6736`（外部公告审核页）挂 `bidding:notice-external:update`；`6748`（投标流程跟踪页）挂 `bidding:notice-external:query` | 页面统一挂本域 `:query`，写动作下沉为按钮权限点 |
| 6 | **权限码后端根本不存在** | `6749~6752` 用 `bidding:process-track:create/register/review/upload`，而全量扫描后端 `@PreAuthorize` → **无任何 `bidding:process-track:*`** | 按已预约号段补注册权限点，后端状态机另立需求 |
| 7 | **个人端权限点混进管理端目录** | `60007400~402`（`bidding:bid-review:self:*`）挂在管理端目录 `60007000 智慧标书审查` 下 | 迁到独立目录 `门户个人端`，与管理端权限面分离 |
| 8 | **授权口径两套** | `6735` 子树只授给 2~6 个角色，`60007000` 子树授给 **478** 个角色；`60005000`、`51000` 为 **0** | 见第六章：默认不改现状 + 补资质域授权 + 提供可选收窄脚本 |
| 9 | **菜单与页面脱节** | `views/bidding/crawlExternal/source/index.vue` 有页面无菜单；`views/bidding/review-center/index.vue` + `api/bidding/review-task` 有页面无菜单，且 `qualification/index.vue:1167` 已跳 `/certificate/review-center`（点了 404） | 采集源管理补菜单；平台审查中心二选一（入库 / 删除） |
| 10 | **空转权限点** | `bidding:bid-review:self:*` 三个码在 `BidReviewPortalController` 中**未被校验**（全部 `isAuthenticated()` + 按登录人隔离），授权界面勾了不产生任何效果 | 保留为登记性权限点，并在文档中写明效力边界 |

## 二、问题清单与处置（逐条对应）

### P1 三套顶级入口并存

- **证据**：`51000 招投标管理` / `6735 招投标` / `60005000 资质与证书管理` 三个顶级项；前两者名字只差"管理"两字。
- **影响**：超管侧边栏出现三个近义顶层；`51000` 里还有一个 `51004 标书评审`，与 `60007000 智慧标书审查`、`60005600 平台审查中心` 形成 **三处"评审/审查"语义打架**。
- **处置**：`51000` 整棵子树 `status=1` 停用（保留数据、不删行，便于回滚）；`60005000` 保留为资质域顶级（见 §4.1）。

### P2 排序断档、业务顺序反直觉

- **证据**：sort = `1,2,3,30,40,1000,1001`；`项目与标段(30)` 夹在 `投标流程跟踪(3)` 与 `智慧标书审查(40)` 之间；`公告/公示管理(1000)`、`主体与授权(1001)` 排到最后。
- **影响**：新同事看不懂业务链路；新增菜单无处安放（只能往 1002、1003 加）。
- **处置**：按 10/20/30… 重排，每次留 10 的插空。

### P3 目录与页面同级

- **证据**：`6735` 的直接子节点里混着 `type=1` 目录（6737/6753/6759/6770/60007000）与 `type=2` 页面（6736/6748）。
- **影响**：侧边栏同一层级出现"可展开的"和"点一下进页面的"两种行为，认知负担高。
- **处置**：`6735` 下只放目录；`6736` 移入公告目录、`6748` 移入新建的投标目录。

### P4 软删除残留 + 孤儿按钮

- **证据**：`deleted=1` 的是 `6739/6740/6744/6745`；而 `6747 批次查询` `deleted=0` 且 `parent_id=6740`（父级已删）。
- **影响**：`采集批次` 页无入口但页面文件仍在；`bidding:crawl-task:query` / `bidding:crawl-task:update` / `bidding:crawl-job:query` 三个权限码在**角色授权界面已不可再勾选**，新角色拿不到 → 工作台「任务」页签与批次相关接口对非超管可能 403。
- **处置**：恢复 `6739/6740/6744`（`deleted=0` 并归位），`6745` 保持删除（与 `6739` 同码重复），`6747` 随 `6740` 恢复自动归位。

### P5 页面权限码与写动作错配

- **证据**：`6736` 是页面却挂 `:update`；`6748` 是页面却挂 `bidding:notice-external:query`（别人的域）。
- **影响**：授权界面里"这个页面该授什么"无法自解释；按码排查永远找不到投标流程跟踪。
- **处置**：页面统一挂本域 `:query`；`6736` 改用后端已有的 `bidding:notice-external:query`（`NoticeFollowController` 在用）。

### P6 权限码后端不存在（"功能存在但授权不出来"）

- **证据**：全量扫描后端 `@PreAuthorize` → 无 `bidding:process-track:*`；而 `6749~6752` 正是用这四个码。前端 `processTrack/index.vue` 头部注释亦自认"后端状态机尚未实现，按钮为占位、v1 存 localStorage"。
- **影响**：这四个权限点在授权界面与外键上都是"悬空"的；用户点按钮只会看到"该能力待上线"。
- **处置**：**分两步**——① 菜单侧按 §8.3 预约号段正式登记 `bidding:process-track:*`，使授权界面可见；② 后端状态机另立需求（第十章登记），不做假实现。

### P7 个人端权限点挂在管理端目录下

- **证据**：`60007400~402` 的 `parent_id = 60007000`（管理端「智慧标书审查」目录）。
- **影响**：管理端目录被"污染"；授权时分不清哪些是后台菜单权限、哪些是门户动作权限。
- **处置**：新建 `6778 门户个人端` 目录（sort 90），三码迁入；该目录仅含 `type=3` 子节点 → 不生成路由、不进侧边栏。

### P8 授权口径两套

- **证据**：`6735` 子树 2~6 角色；`60007000` 子树 478 角色（来自 2026-09-16/17 的"给所有角色授权"）；`60005000`、`51000` 为 0。
- **处置**：见第六章。默认**不改现状**（避免把用户已开通的入口关掉），只补 `60005000` 资质域授权；收窄脚本作为可选附录。

### P9 菜单与页面脱节

- **证据**：`crawlExternal/source`、`review-center` 两个孤儿页；`qualification/index.vue:1167` 硬跳 `/certificate/review-center` 必然 404。
- **处置**：采集源管理补菜单 `6777`；平台审查中心二选一（第九章 D2）。

### P10 空转权限点

- **证据**：`BidReviewPortalController` 全部端点 `@PreAuthorize("isAuthenticated()")`，类注释明写"不再校验 `bidding:bid-review:self:*`"。
- **处置**：保留为**登记性权限点**（未来做动作级控制时的锚点），在第五章写清效力边界，避免后人误以为勾了就能控。

## 三、设计目标与原则

| # | 原则 | 落地判据 |
|---|---|---|
| 1 | **一域一顶级** | 招投标业务只在 `6735` 下；资质域只在 `60005000` 下；两者不互相挂靠 |
| 2 | **一功能一入口** | 同一能力在侧边栏只出现一次（外部公告审核不再既做顶级页又做公告子项） |
| 3 | **按业务链路排序** | 采集 → 公告 → 项目 → 投标 → 审查 → 主体；sort 从 10 起、步长 10 |
| 4 | **目录是名词域，页面是台账/工作台** | `6735` 下只放 `type=1`；页面不叫「…管理」造成层级歧义 |
| 5 | **三级封顶** | 顶级 → 目录 → 页面 → 按钮；不再加深 |
| 6 | **权限点归属角色面** | 管理端权限点只在管理端目录；门户权限点只在门户目录 |
| 7 | **菜单/路径/组件/权限码四者可对账** | `path` 是二级段、`component` 指向真实文件、`permission` 在后端 `@PreAuthorize` 可 grep 到 |
| 8 | **下线要清尾** | 停用菜单必须同步处理子节点、孤儿按钮与 `system_role_menu`，不留"半下线"状态 |

## 五、个人端权限点归属方案

个人端（门户）页面走**静态路由**（`router/routes/core.ts:255~357`），不经菜单表；但为了能在「角色授权」里勾选，动作权限点仍须在 `system_menu` 中存在。

**方案**：新建目录 `6778 门户个人端`（`parent_id=6735`，`sort=90`，`path`/`component` 为空，只含 `type=3` 子节点）。

- 只含 `type=3` 的目录会在路由生成阶段被整体过滤 → **不会出现在侧边栏**；
- 在「系统管理 → 角色 → 分配菜单」中会作为一个分组出现，管理员一眼可辨"这是门户权限，不是后台菜单"。

**效力边界（必须写进文档，避免误用）**：

| 权限码 | 登记位置 | 后端是否校验 | 说明 |
|---|---|---|---|
| `bidding:bid-review:self:create` | 6778 / 60007400 | 否 | 门户 `POST /bidding/bid-review/portal/create-and-generate` 用 `isAuthenticated()`，数据按登录人隔离 |
| `bidding:bid-review:self:query` | 6778 / 60007401 | 否 | 同上（列表 / 详情 / 报告） |
| `bidding:bid-review:self:delete` | 6778 / 60007402 | 否 | 同上（删除） |

> 三个码当前是**登记性权限点**：勾了不影响功能（门户默认放行，越权由 SQL 层的 `user_id` 隔离兜住）。
> 将来若要按角色收紧门户动作，改动点单一：把 `BidReviewPortalController` 的 `@PreAuthorize` 从 `isAuthenticated()` 换成对应码即可——因此**保留、不删**。

4. 只有 `6745`（重复权限点）需要 `DELETE FROM system_role_menu WHERE menu_id=6745`；`6739/6740/6744` 恢复时**不要**新增授权行，历史行仍在，会自动生效。

 WHERE type=2 AND deleted=b'0' AND permission<>'' AND permission NOT LIKE '%:query'
   AND (id BETWEEN 6735 AND 6799 OR id BETWEEN 60007000 AND 60007499);

-- ④ 权限点与后端一致性（门禁脚本）

### 编写原因

用户在使用管理端时反馈「管理端模块有点混乱」。核查后发现根因不是功能缺失，而是**三代历史口径叠加**：老顶级域 `tender`(51000)、新顶级域 `/bidding`(6735)、独立资质域 `certificate`(60005000) 并存；`6735` 子树内排序断档（1/2/3/30/40/1000/1001）、目录与页面同级混放、软删除残留（`6739/6740/6744/6745`）与孤儿按钮（`6747`）、页面权限码错借他域（`6748` 用 `bidding:notice-external:query`）、权限点指向后端不存在的码（`bidding:process-track:*`）、个人端权限点塞在管理端目录下（`60007400~402`）、已预约号段未落地（`60004000` 段、`60005600` 段）、孤儿前端页（`crawlExternal/source`、`review-center`）。需要一份能直接指导实施的方案，把信息架构一次收敛，并给出可回滚的幂等 SQL 与验证清单。
