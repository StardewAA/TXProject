# 电子文件 CA 真实性验证工具 —— 硬性条件清单

> 依据文件：《电子招标投标办法》（国家发展改革委等 8 部委令第 20 号，2013-05-01 施行）及其附件《电子招标投标系统技术规范 第 1 部分：交易平台技术规范（2013）》、《中华人民共和国电子签名法》（2004 通过，2015/2019 两次修正）。
>
> 状态：初稿。本清单只回答一个问题——**要做出一把"能站得住脚"的电子文件 CA 真实性验证工具，法律、规范、技术上分别必须满足哪些条件**。
>
> 约定：本文中"应"= 规范原文用"应"或法律强制性要求，属于硬性条件，缺一不可；"宜"= 规范建议项，尽量满足；"决策项"= 规范未强制、但工程上必须先拍板。

---

## 0. 本工具的定位与验证边界

依据《电子招标投标办法》第二条第 2 款、第四十条和《技术规范》8.2.1(c)、8.2.2(b)，电子招标投标中以下数据电文**必须**按《电子签名法》进行电子签名（身份鉴别行为 + 签名文件清单），本工具即针对这些文件做 CA 真实性验证：

- 办法第四十条清单：资格预审公告/招标公告/投标邀请书、资格预审文件、招标文件及其澄清补充修改、资格预审申请文件、投标文件及其澄清说明、资格审查报告、评标报告、资格预审结果通知书、中标通知书、合同，以及国家规定的其他文件；
- 技术规范 8.2.1(c) 身份鉴别行为：递交资格预审申请文件、递交投标文件、递交投标保证金、撤回投标文件、确认开标记录、递交回执、发出中标通知书、签订合同（协议书）等需要主体承担法律责任的电子招标投标行为；
- 技术规范 8.2.2(b) 电子签名文件：招标公告（资格预审公告）、投标邀请书、资格预审文件（澄清修改）、资格预审申请文件（澄清修改）、资格审查报告、招标文件（澄清修改）、投标文件（补充、修改、撤回、澄清）、开标记录、评标报告、中标通知书、合同（协议书）及相关文件签收回执等具有法律约束力的文件。

**验证边界（本工具回答的问题）**：

1. 该电子文件的签名在密码学上是否有效（内容、签名、时间戳均未被篡改）；
2. 签名证书链是否可追溯到**合法电子认证服务机构**颁发的受信任根证书，且签名时刻证书有效、未被吊销；
3. 据此给出"电子签名真实有效 / 签名人身份可识别"的判定与可留痕报告。

**不做的事**（明确划界，避免工具责任外溢）：投标文件加密后的解密（属开标解密职责，见办法第二十六、三十条）、注册信息与实体的比对核验（属平台 5.1 注册验证职责）、对签章图片真伪的美术鉴定（只验证其与数字签名的绑定关系）。

关键术语（规范定义，工具文档与代码注释必须沿用）：

- **电子文件**（3.1）：按特定用途和规定内容格式要求编辑生成的数据电文；
- **电子签名**（3.15）：运用电子密码技术在数据电文中以电子形式所含、用于识别签名人身份并表明签名人认可其中内容的数据；
- **电子印章**（3.16）：模拟在纸质文件上加盖传统实物印章的外观和方式进行电子签名的形式；
- **版式文件**（3.28）：不同阅读环境显示内容、版面格式固定一致、**防止篡改**的数据电文——"电子招标投标中的大多数电子文件需要采用版式文件"；
- **CA 证书**（3.29）：经**有关部门认可的电子认证服务机构**基于 PKI 签发、认证和管理，具备身份识别、电子签名、加密解密功能，内容含服务机构名称、持有人名称及签名验证数据、序列号、有效期、服务机构签名；
- **时间戳**（3.32）：应用电子签名技术，对电子文件提供日期和时间信息的安全保护和证明。

## 2. 输入文件硬性条件（格式与承载）

| 编号 | 硬性条件 | 依据 |
|---|---|---|
| F1 | 被验证文件必须是数据电文/电子文件，且为可随时调取查用、内容稳定的**版式文件**（推荐 PDF、OFD 等），或交易平台约定的其他标准化文件封装 | 电子签名法第 4/5 条；规范 3.1、3.28 |
| F2 | 文件内必须能解析出完整签名数据：签名值、签名人证书（链）、摘要算法/签名算法标识、可选的签名时间与时间戳 | 规范 3.29、8.2.2 |
| F3 | 若采用电子印章：印章数据必须与数字签名**绑定**（符合安全电子签章密码技术规范的数据结构），验证时须校验"印章 ↔ 证书 ↔ 签名"三者一致，防"移花接木"假章 | 规范 3.16；GB/T 38540-2020 |
| F4 | 带签名的文件在验证过程中**不得被再保存/再转换**（PDF 等以增量字节范围签名，任何重写都会破坏签名）；工具必须只读解析 | 电子签名法第 13 条(三)(四)；规范 8.2.2(a) |
| F5 | 结构化交换数据若同时存在（XML 附件等），其与签名内容的对应关系需一并校验，验证"数据电文不被篡改、不遗漏" | 办法第 14 条；规范 8.1.3(a) |
| F6 | 加密（数字信封）文件不属本工具验证范围，工具须能识别并明确提示"需先按开标流程解密后再验证" | 办法第 26 条；规范 8.2.3 |

## 3. 密码学验证硬性条件（核心功能）

### 3.1 摘要与签名算法

| 编号 | 硬性条件 | 依据 |
|---|---|---|
| C1 | 支持按标准重算原文摘要并与签名内摘要比对：内容完整性（电子签名法第 13 条(四)：签署后对数据电文内容和形式的任何改动能够被发现） | 电子签名法 13 条；规范 8.2.2(a)、5.5.1(g) |
| C2 | 摘要算法须支持国密 SM3（GB/T 32905）与 SHA-256（按平台实际 CA 算法配置） | 商用密码合规（L16）；算法下限决策项 §9 |
| C3 | 签名算法须支持 SM2（GB/T 32918）及/或 RSA 等平台实际使用算法；**必须校验算法标识与密钥长度下限**（弱算法直接判不满足，不得"验签成功但结论可用"） | 商密条例；RFC 5280 |
| C4 | 签名结构与数据须按统一语法解析：GB/T 35275《SM2 密码算法加密签名消息语法规范》（国际对应 RFC 5652 CMS）；不得使用私有容错解析 | 实现正确性硬条件 |
| C5 | 每个签名分别独立验证并分别出结论（一份文件可含多签：如投标文件 + 开标记录多主体签署） | 规范 5.6.2(f)(g) 多主体电子签名 |

### 3.2 证书验证

| 编号 | 硬性条件 | 依据 |
|---|---|---|
| C6 | 证书格式须符合 X.509 v3 / GB/T 20518《数字证书格式》，能提取：版本、序列号、签发者、主体、有效期、公钥、签名算法、扩展项 | 规范 3.29 |
| C7 | 证书内容要素必须齐全：电子认证服务提供者名称、证书持有人名称、证书序列号、有效期、持有人电子签名验证数据、服务机构电子签名等 | 电子签名法第 21 条 |
| C8 | 证书链校验：自签名证书 → 逐级验证至**受信任根证书**；任何一环签名无效/算法不符/扩展不符即判链无效 | RFC 5280；规范 8.2.2(a) |
| C9 | **信任根必须限定为依法设立的合法电子认证服务机构**（工信部许可 + 国家密码管理机构同意使用密码的证明），工具须内置可配置的"信任根池/CA 白名单"并支持按地区/平台实际 CA 增补 | 电子签名法第 17、18 条；办法第 44 条(四)；规范 8.2.1(c)、3.29 |
| C10 | 有效期校验分两层：当前验证时刻有效；**签名时刻证书有效**（以签名时间/时间戳时间为准，处理"签署时有效、现在过期"的历史文件） | 电子签名法第 21 条(四)、22 条 |
| C11 | 证书密钥用法校验（KeyUsage / 扩展密钥用法必须含签名用途）；CA 证书与终端证书角色不得错位 | RFC 5280；GB/T 20518 |

### 3.3 证书撤销状态（吊销检查）

| 编号 | 硬性条件 | 依据 |
|---|---|---|
| C12 | 必须提供证书撤销状态检查：CRL（下载并校验其签发与有效期）或 OCSP（RFC 6960 在线查询） | 电子签名法第 22、24 条（证书在有效期内完整准确、信息可查）；《电子认证服务管理办法》 |
| C13 | CRL/OCSP 的响应本身必须验签并核对（响应者证书、新鲜度、本证书序列号命中） | 防重放/防伪造 |
| C14 | 撤销检查失败（网络不可达、无响应）时**不得默认放行**：结论必须标记"撤销状态未决"，由调用方按策略处理（如人工复核） | 可靠性要求（对应规范 8.4.2 容错） |
| C15 | 平台应按规范保留认证信息（证书失效后至少五年），工具的吊销检查与证据留存期应与之匹配 | 电子签名法第 24 条；办法第 49 条 |

### 3.4 时间与时间戳

| 编号 | 硬性条件 | 依据 |
|---|---|---|
| C16 | 工具运行环境时钟必须与国家授时中心标准时间同步（投标截止/开标时间亦以此为准） | 规范 5.5.1(l)(m)、8.6.3.1(c) |
| C17 | 平台对需签名数据电文生成的时间戳（按国家授时中心标准时间源）必须可验证：TSA 证书链、时间戳签名、时间值合法（时间戳本身不可被伪造/篡改） | 规范 8.2.2(c)、3.32 |
| C18 | 时间戳时间须落在签名人证书有效期内，且与签名内容的哈希一致（时间戳作用于签名摘要而非随便一段数据） | 时间戳语义（RFC 3161 / GM/T 0033） |
| C19 | 归档长期有效性（可选增强）：支持对时间戳再签章（长期验证 LTV）以便多年后仍可复核 | 办法第 49 条电子归档；决策项 §9 |

### 3.5 电子签章绑定

| 编号 | 硬性条件 | 依据 |
|---|---|---|
| C20 | 若文件带可视化电子印章：校验印章数据结构合法（符合 GB/T 38540 / GM/T 0031 类规范）、印章证书与签名证书一致、印章外观指向的机构与证书主体一致 | 规范 3.16；防假章 |

### 3.6 《电子签名法》第十三条四条件的工具化映射（验收主线）

| 可靠电子签名条件 | 工具如何证明 |
|---|---|
| (一) 签名制作数据属于签名人专有 | 间接证明：证书由合法 CA 依法定程序查验身份后签发（电子签名法第 20 条）+ 链上证书主体唯一持有该公钥；工具不直接掌握私钥，此项结论以"证书链 + CA 白名单"为代理证据并在报告中明示该代理关系 |
| (二) 签署时制作数据仅由签名人控制 | 同上，由 CA 签发机制与签名密码学有效性代理证明 |
| (三) 签署后对电子签名的任何改动能被发现 | 重算摘要比对失败即检出；签名数据字节被改则验签失败（C1、C5） |
| (四) 签署后对数据电文内容和形式任何改动能被发现 | 内容摘要比对（C1） |

## 4. 结论判定与报告硬性条件

| 编号 | 硬性条件 | 依据 |
|---|---|---|
| R1 | 结论必须分级（如：通过 / 不通过 / 无法判定），不得出现"验签通过但证书不可信"式的矛盾结论 | 逻辑完备性 |
| R2 | 报告必须逐项列示：文件指纹（哈希）、每个签名的算法、证书链各环节（DN/序列号/有效期/吊销状态）、时间戳结果、各检查项通过/失败 | 电子签名法第 8 条真实性审查四因素；规范 8.2.10 审计要素（日期、时间、发起者、类型、描述、结果） |
| R3 | **密码学结论与业务主体结论必须分栏**：工具只能证明"某证书持有人在某时间点对文件签名且证书链可信"；"持有人 = 某投标人/招标人"需平台主体信息库/CA 注册信息佐证，报告不得越界断言 | 规范 5.1（主体注册与 CA 绑定属平台职责）；边界见 §0 |
| R4 | 验证过程必须留痕并支持追溯（验证人、验证时间、输入文件哈希、工具版本、规则版本、吊销检查凭证），验证记录保存期不低于证书失效后五年 | 办法第 49 条；电子签名法第 24 条 |
| R5 | 验证操作本身不得修改被验证文件（只读），且应记录审计日志（登录、验证动作、异常） | 规范 8.2.10；R4 |

## 6. 工具自身合规硬性条件

| 编号 | 硬性条件 | 依据 |
|---|---|---|
| S1 | 密码算法实现须为国密合规实现（SM2/SM3 按国标实现；不得使用自研算法）；涉及商用密码产品时须符合商用密码检测认证要求 | 《密码法》《商用密码管理条例》（L16） |
| S2 | 工具/库的密码实现若来自第三方，须选择通过商密检测认证的厂商产品并保留合规证明 | L16 |
| S3 | 工具不得存在故意放行的后门/弱化路径（如"忽略证书错误继续"的静默开关）；所有放宽项必须显式告警 | 规范 8.2.9 安全缺陷防范 |

## 7. 测试与验收硬性条件（必须有样本集，缺一不可验收）

正样本（全部应通过并给出"真实有效"结论）：

- T1 合法 CA（平台实际对接的 CA，如陕西 CA 等）签发的、未篡改的版式文件，含时间戳；
- T2 上述正样本的历史文件（签名时刻有效、当前已过证书有效期）——应给出"签署时有效"结论；
- T3 多主体多签名文件（如开标记录多单位确认）——逐个签名全部通过。

负样本（必须分别给出"不通过/无法判定"且原因可定位到检查项）：

- T4 正文改动 1 字节（应命中内容完整性失败，13 条(四)）；
- T5 签名数据被改动（应命中签名验证失败，13 条(三)）；
- T6 证书已吊销（应命中吊销状态失败）；
- T7 自签名/不受信任 CA 签发（应命中信任根失败）；
- T8 证书当前已过期且签名时刻也在有效期外；
- T9 时间戳无效 / 时间戳时间超出证书有效期 / TSA 不可信；
- T10 算法低于下限或算法标识被替换（算法混淆攻击）；
- T11 密钥用法不符（签名证书被用于加密场景等）；
- T12 无签名的普通文件（应输出"无签名，真实性无法证明"，不得误报通过）；
- T13 加密文件（应提示先解密）；
- T14 损坏/空/超大文件（容错与性能，规范 8.3.1、8.4.2）。

验收条件：

- A1 样本须由对接 CA / 交易平台方提供真实生产证书与测试 CRL/OCSP 服务，而非仅用工具自签的测试证书（否则信任根与吊销两条链路未真实打通）；
- A2 负样本防回归：全部样本入库作为回归用例，规则（信任根、算法策略、CRL 配置）变更后全量回归；
- A3 出具验证报告模板样例，字段满足 R2/R3。

## 8. 待拍板的决策项（非国家规范硬性，但工程前置，拍板后进入设计）

1. **工具形态**：命令行（.jar/脚本）、可执行验证库被 bidding-server 内嵌调用、独立验证微服务、或桌面端批量验证器——影响 §5 部署条件是否全部适用；
2. **算法策略**：仅国密（SM2/SM3/SM4 + GM/T 时间戳）或国密+国际算法双轨（对接 CA 实际证书算法决定）；
3. **信任根/CA 白名单范围**：陕西公共资源交易平台及拟对接平台实际使用的 CA 清单（需对接方提供根证书与机构信息，含测试 CA 与生产 CA 分离管理）；
4. **吊销检查策略**：CRL/OCSP 优先级、超时与离线时的默认行为（拒绝 / 标记未决人工复核）；
5. **时间戳策略**：验证平台内嵌时间戳即可，还是要求第三方可信时间戳（联合信任类 TSA）并存；
6. **归档复核要求**：是否要求长期有效签名（LTV/时间戳链）支持多年后复核（办法第 49 条电子归档的现实需要）；
7. **报告载体**：普通验证单 vs 带防伪的电子报告（再次签名）——直接决定 R4 的存证强度。

## 附录 A：关键条款摘录

**《电子签名法》第十三条**（可靠的电子签名，同时符合下列条件）：
（一）电子签名制作数据用于电子签名时，属于电子签名人专有；
（二）签署时电子签名制作数据仅由电子签名人控制；

**《技术规范》8.2.1(c)**：应使用有关部门认可的合法电子认证服务机构提供的 CA 数字证书对交易主体身份标识与鉴别（行为清单见 §0）。
