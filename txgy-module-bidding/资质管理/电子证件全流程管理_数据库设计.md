# 电子资质全流程管理 · 数据库表结构设计（招投标系统子模块）

> 定位：招投标系统中的「电子资质管理」子模块，企业可用、覆盖证件全生命周期：**资格录入建档 → 文件材料管理 → 资质审查（含 AI 自查）→ 续期 → 变更 → 吊销/注销 → 到期预警**。招投标本体（项目/标段/评标）不在此设计内；投标需求仅在 AI 自查时作为输入快照。
> 无签发功能（不做发证机关签发流）；证书表只存证照事实，审查结论放审查/自查记录表（一次审查一条，可多次）。
> 「自查标记」列：**1 = 该字段参与 AI 自查（自查时从库里抽取交给 AI 的输入字段）**，仅是功能标注，不是系统核心；其余字段为管理/展示/审计字段。

> **全局约定（v3 高可用 · 高安全基线补齐）**
> - **公共列**（各表默认含，下文不再逐一重复）：`tenant_id bigint NOT NULL DEFAULT 0`（平台 `TenantBaseDO` 提供 `Long tenantId`）；审计列按平台 `BaseDO` 命名 `creator varchar(64) DEFAULT ''` / `create_time datetime DEFAULT CURRENT_TIMESTAMP` / `updater varchar(64) DEFAULT ''` / `update_time datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` / `deleted bit(1) DEFAULT b'0'`（@TableLogic）。正文旧写法 `created_by/created_at/updated_by/updated_at/is_deleted` 及自建 `deleted_at/deleted_by` 一律按此口径落库（v3.3 起，见 §17.9）。写入类表带 `idempotent_key`（UNIQUE 幂等）；状态可更新表带 `version`（乐观锁 CAS）；日志/大表带 `archive_status`（0 热 / 1 冷 / 2 已归档）。
> - **字段安全分级** L1 公开 / L2 内部 / L3 敏感（脱敏展示）/ L4 高敏（加密存储），未注明默认 L2；L4 用 AES-256-GCM + KMS（90 天轮换），并配盲索引做等值查询/唯一约束。
> - **分区与保留**：`cert_usage_logs/cert_change_logs` 按月 RANGE 分区，`cert_self_check_records` 与资质达标核查按季度；变更日志保留 ≥3 年（等保2.0 三级）、自查/核查记录 ≥3 年（投标追溯）、已处理预警满 6 个月归档；归档以 `DROP PARTITION` 秒级完成。
> - **日志防篡改**：`record_hash=SHA-256(记录字段拼接)` + `prev_hash` 哈希链，根哈希定期固化到独立审计库；DB 账号对日志表仅授 INSERT。

## 十三、AI 自查流程（标记=1 字段的用途）

    1 发起自查（选证照 + 填/导入投标需求）
    2 抽取三块快照
        ① requirement_snapshot  投标需求（资格要求）
        ② enterprise_snapshot   企业基本资格（enterprise_basic 标记字段）
        ③ certs_snapshot        所选证照的自查标记=1 字段（PERSON 证加人员扩展 9 字段，文件取 is_current=TRUE 存在性）
    3 组装 JSON → 调 AI → 返回 符合(1)/不符合(0) + 风险项
    4 落库 cert_self_check_records 一行；需要走审查流程的同步生成 cert_review_record（review_mode=AI 辅助）
    5 可反复自查（每次一行），证书表只读不动

### 17.9 平台多租户实现核对与 v3.3 对齐（2026-09-03）

> 依要求核对大项目（txgycloud，yudao-cloud 系，包 `cn.iocoder.txgy`）中租户 id 的真实写法，本文档按实测口径修正。

**平台实际机制（源码核对）**：

1. 基类：`txgy-framework/txgy-spring-boot-starter-biz-tenant` —— `TenantBaseDO extends BaseDO`，仅新增 `Long tenantId`；`BaseDO` 提供 `createTime/updateTime/creator(String)/updater(String)/deleted(@TableLogic)`。
2. DDL 惯例（平台 hrm/fms 等新模块建表）：
   - `creator varchar(64) NULL DEFAULT ''`（创建者，用户 ID 字符串）
   - `create_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP`
   - `updater varchar(64) NULL DEFAULT ''`
   - `update_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
   - `deleted bit(1) NOT NULL DEFAULT b'0'`
   - `tenant_id bigint NOT NULL DEFAULT 0 COMMENT '租户编号'` ← **类型 BIGINT、默认 0**（旧设计 VARCHAR(32) 作废）
3. 过滤判定（`TenantDatabaseInterceptor`，MyBatis-Plus `TenantLineHandler`）：实体继承 `TenantBaseDO` → 自动拼 `AND tenant_id=?`；配置忽略表（`txgy.tenant.ignore-tables`）、DO 标 `@TenantIgnore`、或非 `TenantBaseDO` 实体 → 一律跳过。**是否拼条件看 DO 基类，不看"表有没有列"**。
4. 配置前缀 `txgy.tenant.*`（enable 默认 true / ignore-urls / ignore-visit-urls / ignore-tables / ignore-caches），不是 `yudao.tenant`；bidding-server `application.yaml` 已配 `tenant: enable: true`。
5. 跨租户/无租户执行：`TenantUtils.execute(tenantId, …)` 指定租户、`TenantUtils.executeIgnore(…)` 忽略租户；方法级注解 `@TenantIgnore`（Controller 类上加会并入 ignore-urls）。
6. 存量对照：crm/erp/mall/wms/hrm 等存量模块 DO 仍直接继承 `BaseDO`（部分表含 `tenant_id` 默认 0 但拦截器不拼条件，属单租户部署/迁移形态）；system（AdminUser/Role/Dept/OAuth2）与 pay 新表用 `TenantBaseDO`。本设计按框架与 system 目标形态实施（T 轨继承 TenantBaseDO），评审时勿以存量模块写法为准。

**本版已对齐（v3.3）**：

- ① 各表 `tenant_id` 列型由 VARCHAR(32) 统一为 `bigint`（默认 0）；
- ② 审计列名统一平台命名 `creator/create_time/updater/update_time/deleted`，移除行内自建 `deleted_at/deleted_by`（删痕走 `cert_change_logs` 表 13）；
- ③ 唯一约束建议含 `deleted`（平台惯例如 `fms_account_set` `UNIQUE(company_code, deleted, tenant_id)`），同步修订于《招投标模块开发规范》第五章；
- ④ G 轨（纯 BaseDO、无 tenant_id 列）由拦截器自动免租户，不再需要"登记以防报错"，但建议显式登记 `txgy.tenant.ignore-tables` 或 DO `@TenantIgnore` 固化意图。

**遗留**：v3 数据字典 xlsx 中相关列型/列名随 v3.3 同步（见 17.8 待办）；若有历史存量库需兼容旧列名，在建表评审时一并确认。
## 十八、v3.4 表设计对齐（certificate 分支 · 2026-09-04）

> 依据：《资质管理规范文件》目录（GB/T 36902/36903/36904/36906/36905）＋《招投标模块开发规范》（§2.2/§4.5/§4.8/§5）＋《资质管理/05-规范VO表设计.md》。
> 实施真源：`sql/2026-09-04-certificate.sql`（M1 首批 3 表 DDL，随代码同仓入库）；本节点明相对 v3.3 的差异与出处，逐表 DDL 注释已标出处，不再在此复述全部列。

### 18.1 certificate_info（表 1）修订

1. **文件列口径重构**（依据开发规范 §5「三、文本与文件存储」第 5 款与红线 8：文件经 FileApi 上传，业务表只记 file_id/sha256/size，URL 仅签名回显不作一致性依据）：删除 v3.3 主表的 `original_file_url`、`e_cert_file_url`、`original_file_hash`、`file_format`、`file_size`、`file_version` 冗余列——文件实体统一落 `cert_file_versions`（按类别、版本、is_current）；主表仅保留 `e_cert_ident varchar(96)`（GB/T 36904 电子证照标识，≤74 位含版本，建办市 51 号 DZZZBZ）。
2. **自查语义调整**：v3.3 自查字段 `original_file_url/e_cert_file_url`（“有原件/有电子证照”）改由自查快照组装时判定 `cert_file_versions` 中 `file_category=ORIGINAL/E_CERT` 且 `is_current=TRUE` 是否存在，快照范式（v3.3 十三）不变，主表不再冗余文件指针。
3. **GB/T 元数据对齐**：字段列名保持 v3.3 业务驼峰（如 cert_no），语义/取值逐列对齐 GB/T 36903 §5.2 英文名/短名并写进列注释；新增 `issuing_authority_code varchar(32)`（ZZBFJGDM，统一社会信用代码）。
4. **并发/幂等列**：新增 `version int NOT NULL DEFAULT 0`（乐观锁，开发规范 §4.5 乐观锁款）；创建幂等靠 `cert_no` UK（租户内唯一）＋接口级幂等（§4.5）。
5. **代码型列**：`cert_type/cert_status/holder_type/verification_status/source_channel` 均存 code（§5 三-7），状态语义对齐建办市 51 号 `ZZZT`（v3.3 已定口径，本节不变）。

### 18.2 cert_file_versions（表 2）修订

1. `file_url` → `file_id bigint`＋`file_hash varchar(64)`（SHA-256）＋`file_size bigint`（§5 三-5）；`file_name/file_format` 保留作展示；`file_format=OFD` 表示 GB/T 36905 版式电子证照。
2. `upload_by/upload_at` 移除——审计列由 BaseDO 提供（§5 四-1，不得另建改名），上传人=creator、时间=create_time。
3. 新增 GB/T 36903 §5.4 加注件元数据 4 列（`copy_creation_time/copy_creator/copy_cause/copy_expiring_time`），仅加注件（COPY/E_CERT 行）填写；`virus_scan_status` 保留（上传须 CLEAN 才可预览/下载）。
4. 唯一约束：UK(`cert_id,file_hash,deleted,tenant_id`) 防同证同哈希重复上传（替代 v3.3 idempotent_key 列，§4.5 由框架幂等＋DB UK 双保险）；UK(`cert_id,file_category,version,deleted,tenant_id`) 保证类别内版本只追加。

### 18.3 cert_change_logs（表 13）修订

1. 哈希链（record_hash/prev_hash，根=ROOT）与只追加语义保留（等保 2.0 三级，v3.3 §13）；防重由 UK(`cert_id,prev_hash,deleted,tenant_id`) 链式保证（前驱唯一→并发重复追加被拒），服务端写日志与主表更新同事务。
2. **分区登记（差异与出处）**：v3.3 与开发规范 §5 六-3 均要求日志只追加表按月分区；本表 DO 继承 TenantBaseDO、主键为平台 `id`（不含 create_time），MySQL RANGE 分区要求所有唯一键（含主键）包含分区列，与 MP 按 id 主键操作冲突，故 M1 不采用 MySQL 分区，改由定时归档任务按月转储/清理冷数据、保留期 ≥3 年（任务随 M 里程碑落地，登记于建表评审第 9 项差异说明）。
