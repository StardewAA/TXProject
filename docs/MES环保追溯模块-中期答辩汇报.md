## 一、选题背景：MES 有质量管控，但没有环保管控

平台现行 MES 主流程已经跑通完整闭环：

```
基础数据建档 → 工艺准备 → 物料备料 → IQC 来料检验 → 采购入库
→ 生产工单与排产 → 生产执行 → IPQC / 工序流转 → OQC → 产品入库 → 销售出库
```

这条链路对**质量**的管控是完整的，但**环保**维度是空白，具体有三个缺口：

1. **入厂材料不判定环保属性**。一批原料 IQC 质量合格就正常入库，至于它是否含重金属、是否属于危化品、该存放在什么环境，系统一无所知，只能靠人记。
2. **生产过程废弃物去向无人管**。边角料、废漆渣、废机油、更换下来的废活性炭，产出之后去哪了、回用了还是外排了，没有任何系统记录。
3. **成品把"质量"和"环保"混为一谈**。一个质量达标但存在污染残留的成品，会被当作正常品直接出库；一个不达标的成品，也没有区分"有害"与"无害"再分别处置。

从合规角度看，危废管理本身要求**去向可追溯**——来料怎么进的、在哪个库位暂存、最终怎么处置的，都要能拿得出台账。这正是本期要解决的问题。

**模块目标**：在不动现有质量流程的前提下，在 **采购入库、生产领用、中间废弃物、成品** 四个环节插入环保判定，以 **AI 初筛 + 人工复核** 双阶段给出污染分类，并把判定结果**落地到批次、拦截到出入库、留痕到台账**。

## 二、总体设计

### 2.1 六条贯穿规则

设计上先立规则，全场一致，避免四个环节各写一套：

| 编号 | 规则 |
| --- | --- |
| R1 | AI 初筛只输出**三值预分类**：无污染 / 有污染 / 不确定，并给出依据、置信度、推荐存储方法 |
| R2 | **终态一律以人工复核二值为准**（无污染 / 有污染）。AI 判"不确定"也必须由人工收口，**系统不允许"不确定"作为终态留存** |
| R3 | **环保判定独立于质量判定**：污染状态只影响"存储 / 去向 / 出库"，不触发采购退货、不改变质量合格口径 |
| R4 | 判为"有污染"的物料，一律按确认后的**存储方法**存入受控环境并登记台账 |
| R5 | 判定以 `环节 + 关联单号 + 批次 + 物料` 为唯一约束，一条记录贯穿"AI 初筛 → 人工复核 → 处置去向" |
| R6 | 所有排出 / 处置都登记**去向**，全程可反查 |

其中 **R3 是最重要的一条边界**：环保判定绝不能污染现有业务。举个例子——一批原料 IQC 判合格、环保判"有污染"，结论是"**不退货，但要按危化品受控存储**"，而不是拒收。退货口径仍然只由 IQC 决定。

### 2.2 四环节判定矩阵

| 环节 | 触发时机 | 判无污染 | 判有污染 |
| --- | --- | --- | --- |
| 采购入库 | IQC 合格、执行入库前 | 入普通原料仓 | 按存储方法入污染管控环境 + 台账 |
| 生产领用 | 原料投线前 | 允许领用 | 拒绝领用，转隔离处理 |
| 中间废弃物 | 工序报工标记废弃物 | 回用 / 排放（记去向） | 保存处理，入危废暂存区 + 台账 |
| 成品 | 成品入库前 | 入成品合格仓 | 隔离存储 + 打标记，禁止按正常品出库 |

### 2.3 双阶段判定的核心思想

```
   业务数据（物料名/规格/环节）
        │
        ▼
   AI 初筛  ──→  CLEAN / POLLUTED / UNCERTAIN  + 置信度 + 依据 + 存储建议
        │                                        （只是"建议"）
        ▼
   人工复核 ──→  CLEAN / POLLUTED              （二值收口，是"终态"）
        │
        ▼
   落地：批次环保戳 + 台账登记 + 出入库门禁
```

**AI 是建议，人工是终态。** 这个分工既拿到了大模型的效率，又把合规责任锚在人工签字上，同时天然规避了"大模型幻觉导致误判流转"的风险。

## 三、数据模型与状态机

### 3.1 表结构

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `mes_set_pollution_check` | 判定记录（核心） | 唯一键 `环节 + 关联单号 + 批次 + 物料` |
| `mes_pollution_check_log` | 判定履历（AI 结果、复核结果、人、时间） | 只增不改 |
| `mes_pollution_ledger` | 污染 / 危废暂存台账 | 唯一键 `source_check_id`（与判定一对一） |
| `mes_pollution_ledger_log` | 台账流转履历 | 只增不改 |
| `mes_wm_batch`（扩展 4 列） | 批次环保戳 | `pollution_status / pollution_location / pollution_marked / pollution_src_record` |

判定记录与台账是**严格一对一**：一条判定至多产生一条台账行，靠唯一键 `source_check_id` 保证，杜绝重复登记。

### 3.2 状态机

判定记录：

```
AI 初筛完成(待复核) ──复核──→ 无污染 / 有污染(终态)
```

台账：

```
复核"有污染" ──自动登记──→ 暂存 STORED
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
          处置中             已回用           已处置/已排放
        PROCESSING      REUSED/DISCHARGED   DISPOSED   ← 人工闭环
                              │
                    批次后续复核"无污染" → 已解除 CLEARED  ← 系统自动纠错
```

**不变量**：终态不存在"不确定"；同一批次同一环节不允许出现两条不同终态的判定。

## 四、五个关键实现

### 4.1 架构决策：台账是唯一权威，批次戳只是投影缓存 ★

这是本模块最核心的一个设计判断。

判定结果为"有污染"时，需要影响两件事：**一是批次能不能被领用/出库，二是这批货在哪暂存**。最直觉的做法是把污染状态写在批次表上。但这样会有一个致命问题：**批次的反悔和多次判定没法收敛**。

举个真实场景：某批次先被复核为"有污染"存进危废暂存间；后来查明是误判，重新复核为"无污染"。如果污染状态直接写在批次上，那么"撤销"这个动作就要人去手工改批次表的字段——一旦有一次漏改，这批货就被永久锁死，而且没有任何记录能解释为什么。

所以实现上做了一个**主从分离**：

- **台账行（`mes_pollution_ledger`）= 该批次污染管控的唯一权威**。批次是否受控，取决于"它**还有没有未闭环的台账行**"。
- **批次环保戳（`mes_wm_batch` 的 4 列）= 投影缓存**，只回答"该批当前是否仍有未闭环台账行"，由台账重算（`refreshBatchStamp`），**不作为判定依据的存储**。

带来两个好处：

1. **可反悔且可收敛**。复核改为"无污染"时，系统自动把该批所有**未闭环**的台账行置为 `CLEARED`（并写入解除人、时间、原因），然后按剩余开放行重新投影戳。判错了能纠、纠了有痕。
2. **历史处置记录不可逆**。已经人工处置到终态（已回用/已排放/已处置）的台账行**保留不动**——处置这个动作客观发生过，不能因为后来改判就抹掉。

### 4.2 四件事串成一条链：A1–A4

| 编号 | 动作 | 实现位置 |
| --- | --- | --- |
| A1 | 批次环保戳投影 / 清戳 | `refreshBatchStamp` |
| A2 | 台账登记（仅"有污染"）+ 流转留痕 | `applyReviewEffect` |
| A3 | 出入库门禁拦截 | `assertIssueAllowed` / `assertOutboundAllowed` |
| A4 | 单据作废/删除时清理待复核判定 | `purgePendingByBizNo` |

### 4.3 门禁拦截：在动库存之前拦下

光有记录不够，**管控必须能拦住动作**。在 4 个仓储单据的实现类里植入门禁：

| 集成点 | 拦截时机 | 拦截条件 |
| --- | --- | --- |
| 生产领料 `MesWmProductIssueServiceImpl` | 领料出库前，**遍历明细批次逐个校验** | 批次有污染 → 拒绝领用 |
| 销售出库 `MesWmProductSalesServiceImpl` | 成品出库前 | 批次有污染 **或** 被打标记 → 禁止出库 |
| 采购入库 `MesWmItemReceiptServiceImpl` | 单据删除/作废时 | 清理仍"待复核"的判定 |
| 成品入库 `MesWmProductReceiptServiceImpl` | 单据删除/作废时 | 清理仍"待复核"的判定 |

**关键点是拦截位置**：校验放在"动库存之前"。领料单如果先扣了库存再校验污染，失败时就要回滚库存，风险大得多。现在的顺序是**先拦后扣**，校验不过直接抛业务异常，库存不会被碰。

错误码：

| 错误码 | 含义 |
| --- | --- |
| `1040818005` | 有污染判定必须关联真实批次号（中间废弃物除外） |
| `1040818006` | 有污染判定必须填写去向/库位 |
| `1040818007` | 批次不存在，无法落地管控 |
| `1040819000` | 批次存在有污染判定，**禁止领用** |
| `1040819001` | 批次存在有污染/标记判定，**禁止出库** |

### 4.4 AI 初筛：真实大模型 + 降级兜底，永不阻断业务

初筛接的是 **DeepSeek 大模型**（`deepseek-chat`，`temperature=0.2`，强制 JSON 输出，25 秒超时）。工程上做了三层容错：

1. **未配置 api-key** → 降级为本地"污染特征词典"规则（安全白名单优先，避免"无铅"被"铅"误命中）。
2. **大模型调用失败 / 超时 / 返回非预期内容** → 同样降级词典，并打告警日志。
3. **返回字段逐个清洗兜底**：非法枚举值归为 `UNCERTAIN`，置信度裁剪到 0–100，缺失的依据/建议填默认文案。

**设计原则是"AI 挂了业务不能挂"**：初筛只是建议，降级后人工照样能复核收口，整条链路不会因为第三方接口抖动而不可用。

### 4.5 复核是一个事务

人工复核时校验不通过，**整体回滚**——包括已经写进 `location` 的字段。这意味着不会出现"去向填了一半、台账没登记"的中间态。批次不存在、去向未填这类错误码，都是在同一个事务里抛出的。

## 五、前端实现

页面挂在「MES 系统 → 安全环保检测」下（污染判定 `34301`、污染暂存台账 `34302`）。

| 页面 / 组件 | 职责 |
| --- | --- |
| `pollutionCheck/index.vue` | 判定列表、多维筛选（环节/单号/物料/批次/AI 结果/判定状态） |
| `pollutionCheck/modules/form.vue` | 新建 / 修改判定 |
| `pollutionCheck/modules/review.vue` | 人工复核（二值收口 + 补批次号 + 去向） |
| `pollutionCheck/modules/history-drawer.vue` | 判定履历抽屉 |
| `pollutionLedger/index.vue` + `status-modal.vue` | 台账列表与状态流转 |
| `wm/_pollution/judge-modal.vue` | **嵌入仓储单据**的判定弹窗（在入库/领料单上直接判定） |

前端做了一件容易被忽略但很实用的事：**把人工录入尽量变成选择**。

- **选择物料/产品按环节对应仓库取**（`StockItemSelect`）：每个环节只列**该环节对应仓库里实际在库**的物料——采购入库 → 原料仓+危化品库，生产领用 → 再加隔离区，成品 → 成品仓，中间废弃物 → 危废暂存间+一般固废暂存区。仓库映射走**仓库编码**（`WH-RAW`/`WH-FIN`/`WH-CHEM`/`WH-ISOLATE`/`WH-HAZWASTE`/`WH-GENSW`）而非 id，因为各租户仓库 id 不同、编码跨租户一致。未选环节时该字段禁用并提示"请先选择环节"。
- **关联单号按环节联动 + 按物料过滤**（`BizNoSelect`）：先按环节锁定单据类型，再按已选物料**只保留行明细里含该物料的单据**（具体物料在某环节确实没有单据时显示"暂无数据"，而不是给出一堆对不上的单）。选中单据后自动带出该物料对应的批次。
- **选中单据自动带出批次号**：从单据行明细取批次回填，**且优先匹配已选物料那一行**——一张单有多行（如"喷涂工位领料"含环氧粉末+PE 料两行）时不会带错。
- **去向/库位改下拉**（`WmLocationPathSelect`）：数据来自仓库-库区-库位三级体系，值形如 `危化品库·稀释剂防爆柜区`，杜绝自由文本写错。
- **批次号改下拉**（`WmBatchCodeSelect`）：只列真实存在的批次，并按所选物料过滤；复核表单也支持补填批次号，用于救活"建单时漏填批次"的记录。

这一系列改动的直接收益，是**把校验从后端报错前移到用户看不见的地方**——以前不填批次号复核才被拒（`1040818005`），现在表单上根本选不出不存在的批次。

### 6.2 AI 初筛质量实测

用词典**命中不了**的物料验证是真实大模型在判（词典降级会返回"命中污染特征词"）：

| 输入物料 | AI 判定 | 置信度 | 判定依据（AI 生成） |
| --- | --- | --- | --- |
| 废旧锂电池 | **POLLUTED** | 95% | 含镍钴锰等重金属及电解液有机溶剂，属危险废物，具腐蚀性和反应性 |
| 防腐钢管 | **UNCERTAIN** | 60% | 仅表明基材为钢，涂层可能含铬酸盐、环氧或溶剂残留，信息不足 |
| 少量包装纸箱 | **CLEAN** | 95% | 属常见纸品，无重金属、溶剂、酸碱等污染残留 |

判定结果是**有梯度、会承认信息不足**的，说明是模型在语义判断，而不是关键词匹配。

### 6.3 建议现场演示顺序（约 2 分钟）

1. 用演示账号登录（建议 `huahan` / `admin123`，租户 2010）→ 进「污染判定」，展示记录列表的完整字段（AI 结论 + 置信度 + 依据 + 人工复核 + 去向）。

3. 对该记录点「复核」→ 选"有污染" → 去向选 `危化品库·稀释剂防爆柜区` → 确定。
4. 切到「污染暂存台账」→ 同一条已**自动登记**（证明复核联动台账）。
5. 回「生产领料」对**同批次**发起领用 → **被门禁拦下**（`1040819000`）→ 这是最直观的管控效果。

## 七、难点与解决

| 难点 | 现象 | 解决方式 |
| --- | --- | --- |
| **单体模式下配置被覆盖** | 把配置写进 mes 模块的 `application.yaml` 后不生效，AI 一直走降级 | 单体只加载 `txgy-server` 的 `application.yaml`，同名的模块配置被覆盖；新配置一律放 server 模块 |
| **模块胖 jar 导致扫不到类** | 启动报 `No MyBatis mapper was found` | 模块 pom 的 `repackage` 不带 classifier，产物是可执行胖 jar；改为依赖装普通 jar、仅 server 打胖 jar |
| **多租户唯一键是全局的** | 两个租户写同样编号报 `1062` 主键冲突 | 唯一键不分租户，种子数据按租户加前缀 / 分段 id |
| **AI 不可控** | 大模型可能超时、返回非法枚举、甚至幻觉 | 三层降级 + 字段清洗 + **终态永远在人工**（R2） |
| **中间废弃物没有批次主数据** | 废弃物是过程产物，批次表里查不到，会卡校验 | 中间废弃物环节**特例放行**：允许空批次，只登记台账，不投影批次戳 |
| **超管绕过菜单绑定** | 想让某账号看不到台账菜单，怎么配都看得到 | `super_admin` 角色直接返回全部菜单，忽略绑定；改为**建专用角色**（`MES环保专员（无台账）`）演示 |
| **判错了要能纠** | 误判"有污染"会把批次锁死 | 台账主、批次戳从的投影设计 + `CLEARED` 自动解除（见 4.1） |

## 九、总结

本期完成的是一个**从"没有环保管"到"判定可控、去向可查、动作可拦"的闭环**。三个设计取舍值得强调：

1. **AI 只做建议，终态在人工** —— 既拿到大模型效率，又守住合规责任与幻觉风险。
2. **台账为权威、批次戳为投影** —— 让"误判可纠正、纠正有留痕、历史处置不可逆"三件事同时成立。
3. **判定独立于质量** —— 环保判定不侵入现有 IQC/OQC/退货逻辑，是在既有流程上的**增量插桩**，而不是改造。

## 预设问答（评委可能追问）

**Q：AI 判错了怎么办？**
A：两层兜底。第一，终态必须由人工复核收口，AI 结果只是建议，不直接驱动流转；第二，即使人工也判错，台账可被后续复核纠正为 `CLEARED` 自动解除，且解除人、时间、原因全部留痕，历史处置记录不可逆。

**Q：为什么要用大模型，规则引擎不够吗？**
A：规则引擎做的是关键词匹配，遇到"废旧锂电池"这种名称里没有污染特征词的物料就失效了（会落进 `UNCERTAIN`）。大模型能做语义推断——它知道锂电池意味着电解液和重金属。同时保留了词典作为降级路径，所以不依赖大模型的可用性。

**Q：环保判定会不会影响现有业务？**
A：设计上明确独立（R3）。污染状态只影响存储、去向和出入库，不触发退货、不改质量合格口径。实现上是增量插桩，只在 4 个仓储单据里加了门禁校验，质量流程代码未作修改。

**Q：门禁会不会误伤正常业务？**
A：门禁只看批次上有没有**未闭环**的台账行。一旦该批处置闭环，或复核纠正为无污染，戳自动清除，批次立即恢复正常流转。所以是"受控"而不是"永久封禁"。

**Q：为什么台账和批次表要存两份状态？**
A：台账是权威、批次戳是投影缓存。如果只存批次表，误判纠正时就得人工去改批次字段，一旦漏改批次被永久锁死且无从解释；投影设计让纠正动作自动化、可收敛、有留痕。详见 4.1。
