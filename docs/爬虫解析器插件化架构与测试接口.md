# 爬虫解析器插件化：架构与解析器测试接口

> 背景：采集管线按“下载器(channel 插件) → 解析器(parser 插件) → ingest 落库”分层。下载器（GENERIC 占位）与真实站点抓取后置，**解析器插件与本测试接口先行**：拿到真实站点 HTML/JSON 样本后即可在管理端逐条校准解析规则，规则稳定后再接下载器。

## 1. 架构与设计
- 对称设计：下载侧已有 `DownloadChannelAdapter/ChannelRegistry`（按 channel_code 路由，GENERIC 通用占位）；本次补齐解析侧 `NoticeParser/ParserRegistry`（按 parser_code 路由，多策略可插拔）。
- 解析器 SPI（`service/crawlexternal/parser/NoticeParser`）：code/名称/说明/supportedPayloadTypes/parse(ParseInput) → NoticeParseResult。
- 注册表（ParserRegistry）：构造注入自动收集全部 NoticeParser Bean；重复 code 启动即失败；未知 code 明确报错（防静默走错策略）。
- 源配置绑定：bidding_crawl_source.parser_code_default 保存时校验解析器已注册（未注册拒绝保存，防脏配置）；下载器阶段将按 源/URL 审批 → parser_code 路由。
- 结果模型（NoticeParseResult）：公告规范化字段与 ingest/主档列对齐（title/origUrl/contentType/正文/跟踪键/时间/附件候选）+ 测试观测信息（status/meta/warnings）。

- `POST /admin-api/bidding/crawl-parser/test`（权限 bidding:crawl-source:update；@Idempotent；**multipart/form-data**）

## 5. 校准工作流（拿到真实数据后）
1. 从目标站点获取详情页原文：浏览器“查看源代码”全选复制（HTML 文本），或另存 .html 文件（FILE），或 F12-Network 抓取页面数据接口响应（JSON）；
2. 先用 HTML_GENERIC / JSON_GENERIC 测试：看 status/warnings 与抽取字段是否符合预期；
3. JSON 键名没命中：看返回 meta 的 `unmatched.*`（期望键提示），把该站点真实键名贴给后端 → 添加别名或建站点专用解析器固化规则；
4. 规则固化位置：通用别名 → JsonNoticeExtractor.FIELD_ALIASES；站点定向（列表/详情/接口三态）→ 新增站点专用 NoticeParser（如 EBIDDING），按 input.url/特征分派；
5. 下载器阶段：channel 插件按 task 下载原文落存储 → 按 parser_code_default 路由解析器 → 产出直接对接 ingest（ExternalNoticeIngestDTO）落库。

## 11. 增量回溯（时间窗口翻页，2026-09-08 落地，P2-2 收敛）

> 背景：v1 每栏目每轮仅取第一页（最新 10 条），轮询间隔（≥120s/通常 180~300s）内发布量超过一页即漏采。
> 本节的“增量回溯”把每轮从“只看最新一页”升级为“**按发布时间窗口把窗口内公告补齐**”，保证定时轮询不漏。

### 11.1 业务口径
- 窗口：\`lookbackDays\`（栏目级配置，默认不启用=保持 v1 单页行为）。启用后本轮覆盖 \`publishDate >= now-lookbackDays\` 的全部公告；早于窗口的一律视为已被历史轮次覆盖，**不再采集**（不以源站接口 hasNext 为准，以“日期越界即停”为准）。
- 停页条件（任一满足即停止本栏目本轮）：
  1. 已翻页数 ≥ 有效页上限（显式 \`maxPages\`；启用 lookbackDays 且未配时默认 10 页/栏目/轮，防单轮失控）；
  2. 响应无条目（空页 / hasNext=false 且无数据）；
  3. **页内出现早于窗口起点的条目**（列表按时间倒序，其后页必然更老 → 直接停，该页窗口外条目不采集）。
- 不依赖源站分页总页数接口：停页由“日期越界”驱动，天然适配秦源 JSON 与国信 HTML 两种列表。
- 幂等安全：翻页回扫窗口内已入库公告时走 ingest \`origUrlHash\` 幂等（ACTIVE/NEW+未变 → 直接返回，不重复进审核；内容变化才覆盖重投）→ 增量回溯不会骚扰审核队列。
- 防封：翻页请求沿用源内条目间隔（页间 sleep 1.5s）；单轮页上限兜底；**轮询间隔（源级 ≥120s）语义不变**——回溯只是单轮内多翻几页，不增加访问频率。

### 11.2 配置字段（entry_urls_json 栏目对象，均可选）
| 字段 | 缺省 | 含义 |
| --- | --- | --- |
| \`lookbackDays\` | 不启用 | >0 时开启该栏目增量回溯窗口（天）；缺省保持 v1“每轮仅最新一页” |
| \`maxPages\` | 1（未启用回溯）/ 10（启用回溯未配） | 本栏目本轮最大翻页数（防封上限） |
| \`pageSize\`（已有） | 10 | 每页条数 |

### 11.3 落库口径
- 窗口外条目不采集（不 ingest、不建任务）；无日期条目保守视为窗口内（宁多采、靠幂等去重，不丢数据）。
- 栏目摘要 fetched = 窗口内实际尝试条数；ingested/failed 语义不变。
- 两站日期来源：秦源 rows.publishDate（取前 10 位 yyyy-MM-dd）；国信列表条目 date（/sdny_bulletin/{date}/ 已解析）。

### 11.4 验收（建议冒烟）
1. 单栏目配置 lookbackDays=1 连跑两轮（间隔 ≥ 源间隔）：两轮之间发布的公告第二轮能抓到，且第一轮已入库的不重复进审核（幂等返回）；
2. 窗口内发布 >10 条时单轮 fetched >10（证明翻页补漏生效）；
3. 观察日志/摘要：停页发生在“日期越界页”，不会无限翻页；单轮时长 ≤ 页数×(1.5s×条目数) 可预期。

## 附：编写说明（本文档尾部固定段）

### 编写原因
采集研发顺序调整为“先解析后下载”：从两个目标网址直接取回真实 HTML/JSON 样本先行校准解析规则，需要插件化多策略架构 + 管理端解析器测试接口；本文档固化架构、接口契约与校准工作流。

### 编写依据
- 业务需求：爬虫插件式多策略（解析器可插拔）、管理界面测试功能（选择解析器 + 输入 HTML/JSON 文本或上传文件）；
- 代码事实源：service/crawlexternal/parser/**（NoticeParser/ParserRegistry/Html|Json|Ebid 解析器）、CrawlParseTestService/Impl、CrawlParserController、CrawlSourceServiceImpl（parser_code_default 校验）；
- 既有设计：下载通道 DownloadChannelAdapter/ChannelRegistry（对称参考）；ExternalNoticeIngestDTO（解析结果对齐）。

### 所满足的业务需求内容及其实现方式
- “插件式多策略爬虫” → NoticeParser SPI + ParserRegistry 自动收集（新增策略=新增类，不改主流程），下载侧 channel 插件对称并存；
- “管理界面测试功能（选解析器 + 文件/HTML/JSON 输入）” → GET /bidding/crawl-parser/list + POST /bidding/crawl-parser/test（multipart，三态输入），出参含公告字段/附件候选/meta/warnings 供逐条校准；
- “先测试解析器、再写下载器” → §5 校准工作流：样本 → 通用解析器 → 键名校准（unmatched.*）→ 站点专用规则 → 下载器按 parser_code 路由并直连 ingest。
