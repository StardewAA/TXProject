## 1. 边界一：私有图片缓存的账号 / 租户隔离

### 问题

`sheep/helper/private-image.js` 的缓存**只按图片 URL 作键**，没有账号、租户、会话维度。
于是「账号 A 下载私有图 → 缓存未释放 → 切到账号 B → B 读到同一地址」会**直接命中 A 的 blob**，
B 未经任何鉴权就看到了 A 的图片。

### 修复

| 机制 | 实现 |
|------|------|
| **会话作用域键** | 缓存键 = `${scope}\u0000${url}`，`scope` 取自 `captureTenantRequest()` 的 `sessionEpoch / epoch / browseTenantId / accountTenantId / userId` + token 指纹（不存明文 token） |
| **变化即整体作废** | `loadPrivateImage` 每次先算 scope，与上次不同就**先作废全量缓存**再取图（`invalidateCache`） |
| **事件驱动失效** | 监听 `mall:session-changed`（tenant-runtime 在 token 被替换 / 清除 / 跨标签页换号 / 会员资料与会话不一致时都会发）→ 清空 scope + 作废缓存 |
| **页面图片也要清** | 新增 `subscribePrivateImageSession(listener)`；`upload-image.vue` 订阅后**清掉已渲染的本地路径并重新取图**（否则缓存清了、DOM 上仍挂着上一个账号的图） |
| **异步竞态** | 组件内新增 `renderRevision`：会话切换即自增，旧一轮下载回来的结果按代数丢弃；模块内 `scopeRevision` 同理，切换后到达的响应会被 `revokeObjectURL` 丢弃 |
| **释放仍按引用计数** | `releasePrivateImage(url)` 只在当前作用域内按 URL 递减引用，归零后回收 blob |

### 证据

- **服务端不变量**（HTTP，回归 `P1 / P1b`）：同一私有地址，账号 A → **200**；切换到同租户账号 B → **403**。
  ⇒ 服务端本来就要求按账号重新鉴权，**任何跨账号复用客户端缓存都是越权**，本修复消除了这条路径。
- **浏览器内实测**（真实 Chromium，`localhost:3000` 页面上下文，走 H5 自己的 `/app-api` 代理）：

  | 请求 | 结果 |
  |------|------|
  | 同一地址 + 账号 A token | **200**，成功 `URL.createObjectURL` → `blob:http:..., size=67` |
  | **同一地址 + 账号 B token** | **403** |

- **线上产物核对**：H5 容器内 `/usr/share/nginx/html/assets/s-uploader.DVslGAxA.js` 含
  `私有图片缓存失效回调失败`（本模块的失效回调），`mall:session-changed` 命中 66 个产物 →
  会话隔离与失效订阅确实在线上包内。

## 2. 边界二：历史无归属文件禁止普通业务"声明式认领"

### 问题

上一轮把「文件无完整上传者信息」的处理写成了 *「请求显式声明了上传者就允许补录并绑定」*。
但头像、商品图、评价图这些入口**都会声明"当前用户就是上传者"**，于是"声明是我" 等价于 "确实属于我"：
同租户任何人只要知道地址，就能把一条历史无归属的私有文件**认领成自己的**（公开类型还会被抬成匿名可读）。

### 修复

`bindFiles` 的归属核验改为**不接受声明式认领**：

```
3.3 上传者核验（放行前拒绝）
    a) 文件**已有完整归属** → (ownerUserType, ownerUserId) 必须完全一致，否则 FILE_BIND_OWNER_MISMATCH
    b) 文件**缺少完整归属** → 一律拒绝，抛 **FILE_BIND_OWNER_UNKNOWN(1001003015)**
       （不再有"请求声明归属即可补录"的分支）
3.4 公开绑定二次确认 → 只有归属核验一致的请求才能抬为公开
```

新增错误码：`FILE_BIND_OWNER_UNKNOWN = 1_001_003_015`（"文件缺少可信上传者归属，需先完成归属补录或核验"）。

同时删除已经不可达的「按请求补录 owner」写入分支——**绑定只授予读取权，任何情况下都不改写 owner**；
归属变更只能走**可信迁移**（`009-file-public-recompute.sql` 按 `creator` + 用户类型唯一可判来回填）或人工核验。

### 证据（回归 `P2 / P2b / P2c`）

| 用例 | 场景 | 结果 |
|------|------|------|
| `P2` | 把 `owner` 为空的私有文件设为**自己的头像**（声明"是我"） | **1001003015** 拒绝 |
| `P2b` | 被拒文件状态复核 | owner 仍为空、`access_type=2`、`bind_status=0`（**未被认领、未被公开**） |
| `P2c` | **同租户另一个账号**同样尝试认领 | 同样 **1001003015**（跨租户会先命中租户边界，故用同租户验证） |

> 影响面说明：这是**有意的收紧**。若某条历史文件需要参与业务，必须先做归属补录（可信迁移或人工核验），
> 否则它既不能被绑定、也不会被抬公开——这正是复评要求的"默认拒绝"。
