# 招投标模块开发规范

本文件是 `txgy-module-bidding` 唯一的开发规范，讲清四件事：全量 VO 怎么用、模块自建 VO 怎么建、前后端怎么配合、哪些是红线。新约定直接补进对应章节，不再另开文件。

- 规范源头在 `VO数据规范/`：《公共资源交易平台系统数据规范（V2.0）》、陕西省 V2.0 规范及变更记录是权威文件，只读、不改；《VO数据对象规范（国家V2.0模版·陕西适配全量版）.md》是整理好的速查版，可以更新。
- 工程上的分层与命名参考 yudao（ruoyi-vue-pro）和已有模块（fms 等），全项目统一。

## 一、三条底线

1. 全量 VO 是字段字典，不是页面 DTO：只在上报、对接第三方、跨系统交换时用，字段须与规范逐字一致；页面和内部接口另建 VO，不要把上百字段的大对象直接丢给前端。
2. 全量 VO 与代码集常量按规范整理，字段名照录规范原文（含拼写瑕疵）；要增删字段，先回规范核对、说清理由，再动手。
3. 规范就这一份，从写代码到上线的约定都在这里，没有例外。

## 二、全量 VO：一份"命名和字段"的字典

### 2.1 定位

`txgy-module-bidding-api` 的 `api/vo/` 下放 170 个类（`ProjectVO`、`TenderProjectVO`……），类名对应规范里的数据集名，字段名是规范"英文名称"列的照录。用途单一：标明每个数据集有哪些字段、英文名叫什么、哪些社会公开、哪些政务公开，供上报与对接查表。

所以：

- 列表、表单、详情等页面接口，用自建 VO（第三章），不要拿这些类当出入参；
- 与第三方对接、向监管上报时，字段名必须和这些类（即规范）逐字一致，连拼写瑕疵都不能"顺手修"；
- 规范没写公开范围的字段不标 `@PublicLevel`，`PublicLevelFilter` 默认按内部字段处理，不外泄给外部。

### 2.2 命名规则

1. 字段名照录规范英文名称。`QULIFICATION_CHECK_MODE`、`BID_ECTION_NUM`、`BUIDING_AREA` 这些看着别扭的拼写都是原文如此，改了上报就对不上号。
2. 交换层字段类型统一用 `String`。规范里的 C/N/日期/二进制先用字符串承载，真正的格式和单位以"数据类型及格式""值域/备注"为准（金额默认元，时间 `yyyyMMddHHmmss`）。
3. 只有规范表里写了公开范围（社会公开/政务公开）的字段才标 `@PublicLevel`。
4. 少数字段名含 Java 不认的字符，做了最小改写，仅此三处：

| 规范原文 | 生成出来的字段名 | 为什么 |
| --- | --- | --- |
| `OTHER_OWNED_FUND _ RATIO` | `OTHER_OWNED_FUND_RATIO` | 原文中间多了个空格，去掉 |
| `BIDDER'S_IP_ADDRESS` | `BIDDER_S_IP_ADDRESS` | 单引号换成下划线（BidOpenDetailVO、PurchaseBidOpenDetailVO 两处） |
| `IS_ALLOWING_HIGHEST/LOWEST_PRICE_BIDDING` | `IS_ALLOWING_HIGHEST_LOWEST_PRICE_BIDDING` | 斜杠换成下划线（PropertyBiddingRuleVO） |

5. 同一张表里英文名重复的（规范原文确实有，例如 WinCandidateVO 里两个 `FROM_TRADE_PLAT_CODE`），从第二个起追加 `_序号` 区分；落地时按业务需要去重。

## 三、模块自建 VO：供页面与内部接口使用

### 3.1 放置与命名

| 用途 | 类名 | 位置 |
| --- | --- | --- |
| 列表/分页出参 | `<业务>RespVO`（如 `ProjectPageRespVO`） | server 的 `controller/admin/<domain>/vo/` |
| 新增/修改入参 | `<业务>SaveReqVO` | 同上 |
| 分页查询入参 | `<业务>PageReqVO extends PageParam` | 同上 |
| 详情出参 | `<业务>DetailRespVO`（字段少就并进 RespVO） | 同上 |
| 跨模块 RPC 出入参 | `<业务>Api` + 对应的 DTO | api 的 `api/<domain>/dto/`，**别放全量 VO 目录里** |

约定：

1. 自建 VO 用 Java 驼峰、常规类型（Long/Integer/String/BigDecimal/LocalDateTime/Boolean/List），不沿用全大写交换层风格。
2. 只放当前页面/接口真正需要的字段；能对上规范字段时，在 `@Schema` 里注明规范字段名（如 `对应规范字段 PROJECT_CODE`），便于回溯。
3. 字典值注明字典类型（`DictTypeConstants`），枚举注明枚举类（如 `NationalTenderModeEnum`）。
4. 不要把全量 VO 直接当 `@RequestBody`/`@ResponseBody`：字段多、混政务字段、类型也不合前端。

### 3.2 与全量 VO 的切换

- 转换只放在 Service 层，用 `cn.iocoder.txgy.framework.common.util.object.BeanUtils`；Controller 不写转换代码。
- 上报/交换时：Service 组装数据 → 映射为全量 VO → 用 `PublicLevelFilter` 按调用方的公开级别裁剪。
- 时间、金额的转换收敛在 Service 的公共方法：内部 `LocalDateTime` ↔ 上报 `yyyyMMddHHmmss` 字符串；内部 `BigDecimal` ↔ 上报字符串，单位统一元。

## 四、前后端分离的开发框架

### 4.1 整体结构

```text
txgy-ui-admin-vben (apps/web-antd)         txgy-module-bidding-server              txgy-module-bidding-api
┌────────────────────────────┐   REST/JSON  ┌──────────────────────────────┐  RPC(Feign)  ┌───────────────────────┐
│ src/views/bidding/<菜单>/*.vue │ ──────────▶ │ controller/admin/<domain>    │             │ api/<domain>/          │
│ src/api/bidding/<domain>/... │ ◀────────── │ service/<domain>             │ ◀──────────▶ │   dto/、Api 接口        │
│ (requestClient 封装)          │             │ dal/(dataobject|mysql)       │             │ enums/ApiConstants      │
└────────────────────────────┘             └──────────────────────────────┘             └───────────────────────┘
```

- 前端不碰数据库，后端只返回 JSON；跨模块（system/infra/bpm 等）一律走 api 契约 + RPC。
- 单体/微服务同构：打进 `txgy-server` 时 Feign 走本地 Bean；`bidding-server` 独立部署时走 RPC（服务名 `bidding-server`，前缀 `/rpc-api/bidding`）。

### 4.2 后端分层（对齐 fms）

| 层 | 包 | 类命名 | 要点 |
| --- | --- | --- | --- |
| 接口契约 | `api/<domain>`、`api/vo`、`api/enums` | `XxxApi`、全量 VO、代码集常量类 | 只依赖 txgy-common，不依赖 server |
| Controller | `controller/admin/<domain>` | `XxxController` | 只做参数校验、权限注解、Swagger，不写业务 |
| Service | `service/<domain>` | `XxxService` / `XxxServiceImpl` | 业务规则、事务、自建 VO ↔ 全量 VO 转换都在这 |
| DO | `dal/dataobject/<domain>` | `XxxDO extends BaseDO` | 和表一一对应，驼峰字段，`@TableName` |
| Mapper | `dal/mysql/<domain>` | `XxxMapper extends BaseMapperX` | 分页条件用 `LambdaQueryWrapperX` 的 eqIfPresent/likeIfPresent 那套 |
| 枚举/错误码 | `enums` | `ErrorCodeConstants`、`DictTypeConstants` | 错误码段 1-060-xxx-xxx；字典 key 前缀 `bidding_` |

### 4.3 前端目录约定（txgy-ui-admin-vben / apps/web-antd）

| 目录 | 约定 |
| --- | --- |
| `src/api/bidding/<domain>/index.ts` | 一个业务域一个文件。顶部 `export namespace BiddingXxxApi { ... }` 定义类型，下面 `export function getXxxPage(...)` 走 `requestClient.get<PageResult<...>>` |
| `src/api/bidding/<domain>/...` | 子域再开子目录（如 `project/section/index.ts`） |
| `src/views/bidding/<菜单>/*.vue` | 页面组件，`<script setup lang="ts">`；请求一律走上面的 api 封装，页面里别出现裸 axios |

字段类型与第三章 VO 一一对应（`PageResult<T>`、`CommonResult` 框架已有）；枚举值在类型定义处旁注。前后端以 `/v3/api-docs`（knife4j）为联调事实源，两侧路径保持一致（`/bidding/...`）。

### 4.4 接口与数据的统一约定

1. 返回统一用 `CommonResult`，分页用 `PageResult`，参数校验用 `jakarta.validation` + `@Validated`。
2. 每个写接口都加 `@PreAuthorize("@ss.hasPermission('bidding:xxx:update')")`，权限码同步到 sql/ 菜单脚本。
3. 时间出入参用 `LocalDateTime`，与上报格式的互转放 Service。
4. 字典值存 code，展示名交给前端翻译（`@DictFormat` 只用于 Excel 导出）。
5. 租户隔离交给 `txgy-spring-boot-starter-biz-tenant`，业务代码不再自行过滤。

## 五、数据层落地（建表约定）

> 本章规定业务数据落库（建表）的命名、长度、冗余列与文本存储规则；字段与全量 VO 的对应关系以第二、三章为据，DDL 一律置于 `sql/` 目录。

### 一、表结构分轨

1. 业务表命名 `bidding_<域>_<实体>`（示例：`bidding_project`、`bidding_bid_section`），列名与 DO 字段一一对应，采用驼峰转下划线（如 `holderName` → `holder_name`）。
2. 交换镜像表命名 `bidding_std_<数据集>`，用于向监管上报、第三方对接及数据归集；列名照录全量 VO 字段（如 `TENDER_PROJECT_CODE`），字段统一按字符串存储并可适当加宽。镜像表仅由写入方程序维护，业务代码不得将其作为常规读写存储。
3. 用途无法立即确定的，先仅建业务表；镜像表待上报需求明确后另行建立。

### 二、字段长度

VARCHAR 的声明长度仅为容量上限，不预分配存储空间，行内按实际内容占用。据此，编号类字段应一次性预留余量，避免后续频繁变更表结构；宽度无法确定时向上取一档。

| 内容类型 | 示例 | 列定义 |
| --- | --- | --- |
| 短码（≤10 位） | 字典 code、证书编号 | `varchar(16)` |
| 中长码（11~21 位） | 统一社会信用代码（18）、证照类型代码（21） | `varchar(32)` |
| 组合编号（20~40 位） | 项目编号、招标项目编号 | `varchar(64)` |
| 长标识（41~74 位） | 电子证照标识（74） | `varchar(96)` |
| 名称（≤100 字） | 项目名称、单位名称 | `varchar(128)` |
| 说明性内容（无固定上限） | 备注、意见、正文 | 按第三节文本规则处理 |

### 三、文本与文件存储

1. 文本按内容性质分两类管理：
   - 随表文本：单值说明性内容（备注、意见等），长度在数百字以内，随主表存储——短文本使用 `varchar`，较长内容使用 `text`；不得为自由文本指定超出必要的 varchar 宽度。其变更历史由所在业务的变更审计记录（记录字段旧值/新值）留痕。
   - 内容型文本：正文类大段内容（公告正文、澄清修改内容、处理决定、意见书等），一律版本化管理，不得随主表覆盖式更新。
2. 内容型文本的版本化约定：
   - 通过独立内容表实现，命名 `bidding_<域>_content`（示例：`bidding_doc_content`），建议结构如下：

   | 字段 | 说明 |
   | --- | --- |
   | `content_id` | 主键（雪花 ID） |
   | `biz_id` | 业务记录 ID，与主表关联 |
   | `content_type` | 内容类型编码，区分同一业务下的多类正文 |
   | `content` | `mediumtext`，正文全文 |
   | `sha256` | 内容哈希，防篡改与去重 |
   | `version` | 版本号，自增、只追加 |
   | 公共审计列 | `tenant_id` 及审计四件套，继承框架基类 |

   - 内容每次变更追加一个新版本（`version` 递增），旧版本只读保留，不更新、不删除；
   - 内容表与主表同事务写入；主表不冗余正文全文，详情读取时按最新版本关联；
   - 版本保留期不低于对应业务的存档要求（招投标档案按既有保存期规定执行）。
3. 大文本关键字检索经 ES 实现，不得依赖数据库 LIKE 或全文索引；检索针对当前生效版本。
4. 多选及结构化数据使用 JSON 列；需按 JSON 内部值过滤时，应优先拆分子表，避免大量 JSON_EXTRACT 查询。作为证据性快照的 JSON（自查/核查快照等）如需留痕，参照第 2 款方式版本化。
5. 文件（扫描件、电子证照等）不入库，统一存放对象存储，表内仅记录 `url`、`sha256`、`size`；禁止 BLOB 存储。
6. 时间字段以 `datetime` 存储，输出及上报时转换为规范的 `yyyyMMddHHmmss` 字符串；仅镜像表允许直接存储字符串。
7. 代码型字段存储规范 code（字典 key 前缀 `bidding_`），名称经字典查询获取；发证机关等历史名称按第四节快照列处理。

### 四、冗余列约定

1. `tenant_id` 与审计列（`creator/create_time/updater/update_time/deleted`）由框架基类提供，业务表直接继承，不得另行自建。
2. 允许冗余的情形：
   - 子表冗余父表主键与租户列（如 `cert_id`、`tenant_id`），用于隔离与查询；
   - 名称快照列（如持证主体名称），用于列表展示免联表；其语义为登记/签发时点快照，源数据变更时不回改，不作为数据一致性校验的唯一依据。
3. 禁止以名称列替代外键，或使可变名称成为主数据的唯一事实来源。

### 五、索引与表维护

1. 主键采用框架雪花 ID；业务唯一性优先通过 `UNIQUE (tenant_id, 业务编号)` 约束保证。
2. 长文本列不建普通索引；到期预警、截止时间等场景按需对时间列建索引；索引以必要为限。
3. 日志、流水等只追加表按月分区，并按保留期归档。

### 六、建表评审

新表 DDL 提交 `sql/` 前，应确认下列事项通过后再实施：
1. 字段对应全量 VO 已存在（缺失时先补全字典）；
2. 表名、列名符合命名约定且与 DO 一致；
3. 长度档位符合第二节规定；
4. 文本字段已确定归属：内容型文本按第三节第 2 款建带版本的 `bidding_<域>_content` 表，随表短文本明确变更留痕方式；文件、时间、代码字段按第三、四节约定落地；
5. 冗余列符合第四节适用情形；
6. 唯一键与索引定义明确。

## 六、容易踩的坑（红线，别碰）

| # | 坑 | 怎么躲 |
| --- | --- | --- |
| 1 | 把规范字段名/值域"修"好看点 → 上报、联调对不上 | 全量 VO 的字段名一律照录；要改先回规范核对并说明理由，禁止随手改 |
| 2 | 政务公开字段流到公共服务大厅/ES → 数据泄露 | 出参一律过 `PublicLevelFilter`；没标 `@PublicLevel` 的字段默认不外发 |
| 3 | 时间/金额各写各的转换 → 上报数据乱 | 时间统一 `yyyyMMddHHmmss`、金额统一元；转换只放 Service 公共方法 |
| 4 | 字典/枚举直接写魔法值 → 码值漂移 | 只用 `api/enums` 常量类和 `DictTypeConstants`；码值要变先改规范 |
| 5 | 删字段/删码值立刻下线 → 存量接口炸 | 按规范节奏来：出参先移除，入参兼容一个版本周期再关 |
| 6 | 跨模块直连人家的库、复制表 → 数据不一致 | 走 api 契约 + RPC（FileApi/AdminUserApi/DeptApi 已配好），禁止跨库 SQL |
| 7 | 直接改已上线的表 → 迁移风险 | 学 yudao 的做法：优先扩展表（`xxx_ext`）+ 字典 + 配置，动主表结构先评审 |
| 8 | 附件、密文往库里塞 → 泄露 | 附件走 FileApi，库里只存附件关联标识号，加解密是文件服务的事 |
| 9 | 敏感信息（联系方式、证件号、政务字段）打进日志 | 日志脱敏；访问日志/操作日志够用了，业务代码别自己打印敏感值 |
| 10 | 页面直接吐全量 VO → 接口又胖又漏 | 页面一律走自建 VO（第三章），Service 裁好了再返回 |

### 常规习惯

1. 提交信息用中文写清楚"改了什么、为什么"；提交前自查 `git status`，别碰到 `VO数据规范/` 里的权威文件。
2. 代码风格跟着仓库走：lombok 链式 setter、import 不用 `.*`、类上 Javadoc 必须有。
3. 核心规则（时限、金额、状态流转、公开级别裁剪）要写单元测试，参考 yudao-bidding 的 TDD 先例；Controller 留 `*.http` 文件方便调试。
4. DDL/菜单/字典脚本进 `sql/`；表名用 `bidding_` 前缀（业务域另有约定按约定），字段长度按"数据层落地"的冗余约定来。
5. 改了接口、字典、全量 VO，顺手把本文件对应章节也更新掉，别让文档落后半年。

### 新功能上线前的自查清单

1. □ 先查字段语义有没有对应的全量 VO（有就引用字段名，没有先到 2.3 补上再动手）；
2. □ 自建 VO 按第三章命名、放对位置，`@Schema` 注明规范字段；
3. □ Controller 权限码/Swagger/校验齐全，Service 事务和转换正确；
4. □ 把第六章红线条条过一遍；
5. □ 字典/菜单/DDL 脚本入库，文档同步；
6. □ 编译 + 相关测试跑绿再提交。
