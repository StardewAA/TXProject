# 招投标模块开发规范

本文件是 `txgy-module-bidding` 唯一的开发规范，讲清四件事：全量 VO 怎么用、模块自建 VO 怎么建、前后端怎么配合、哪些是红线。新约定直接补进对应章节，不再另开文件。

- 规范源头在 `VO数据规范/`：《公共资源交易平台系统数据规范（V2.0）》、陕西省 V2.0 规范及变更记录是权威文件，只读、不改；《VO数据对象规范（国家V2.0模版·陕西适配全量版）.md》是整理好的速查版，可以更新。
- 工程上的分层与命名参考 yudao（ruoyi-vue-pro）和已有模块（fms 等），全项目统一。
- 服务对象主要有货物类、工程类和服务类以及甲方企业，编写业务代码时需要囊括企业需求。

## 一、三条底线

1. 全量 VO 是字段字典，不是页面 DTO：只在上报、对接第三方、跨系统交换时用，字段须与规范逐字一致；页面和内部接口另建 VO，不要把上百字段的大对象直接丢给前端。
2. 全量 VO 与代码集常量按规范整理，字段名照录规范原文（含拼写瑕疵）；要增删字段，先回规范核对、说清理由，再动手。
3. 规范就这一份，从写代码到上线的约定都在这里，没有例外。

## 二、全量 VO：一份"命名和字段"的字典

### 2.1 定位

`txgy-module-bidding-api` 的 `api/vo/` 下放 170 个类（`ProjectVO`、`TenderProjectVO`……），类名对应规范里的数据集名，字段名是规范"英文名称"列的照录。用途单一：标明每个数据集有哪些字段、英文名叫什么、哪些社会公开、哪些政务公开，供上报与对接查表。

所以：

- 列表、表单、详情等页面接口，用自建 VO（第三章），不要拿这些类当出入参；
- 与第三方对接、向监管上报时，字段名必须和这些类（即规范）逐字一致，连拼写瑕疵都不能"顺手修"；
- 规范没写公开范围的字段不标 `@PublicLevel`，`PublicLevelFilter` 默认按内部字段处理，不外泄给外部。

### 2.2 命名规则

1. 字段名照录规范英文名称。`QULIFICATION_CHECK_MODE`、`BID_ECTION_NUM`、`BUIDING_AREA` 这些看着别扭的拼写都是原文如此，改了上报就对不上号。
2. 交换层字段类型统一用 `String`。规范里的 C/N/日期/二进制先用字符串承载，真正的格式和单位以"数据类型及格式""值域/备注"为准（金额默认元，时间 `yyyyMMddHHmmss`）。
3. 只有规范表里写了公开范围（社会公开/政务公开）的字段才标 `@PublicLevel`。
4. 少数字段名含 Java 不认的字符，做了最小改写，仅此三处：

| 规范原文 | 生成出来的字段名 | 为什么 |
| --- | --- | --- |
| `OTHER_OWNED_FUND _ RATIO` | `OTHER_OWNED_FUND_RATIO` | 原文中间多了个空格，去掉 |
| `BIDDER'S_IP_ADDRESS` | `BIDDER_S_IP_ADDRESS` | 单引号换成下划线（BidOpenDetailVO、PurchaseBidOpenDetailVO 两处） |
| `IS_ALLOWING_HIGHEST/LOWEST_PRICE_BIDDING` | `IS_ALLOWING_HIGHEST_LOWEST_PRICE_BIDDING` | 斜杠换成下划线（PropertyBiddingRuleVO） |

5. 同一张表里英文名重复的（规范原文确实有，例如 WinCandidateVO 里两个 `FROM_TRADE_PLAT_CODE`），从第二个起追加 `_序号` 区分；落地时按业务需要去重。

## 三、模块自建 VO：供页面与内部接口使用

### 3.1 放置与命名

| 用途 | 类名 | 位置 |
| --- | --- | --- |
| 列表/分页出参 | `<业务>RespVO`（如 `ProjectPageRespVO`） | server 的 `controller/admin/<domain>/vo/` |
| 新增/修改入参 | `<业务>SaveReqVO` | 同上 |
| 分页查询入参 | `<业务>PageReqVO extends PageParam` | 同上 |
| 详情出参 | `<业务>DetailRespVO`（字段少就并进 RespVO） | 同上 |
| 跨模块 RPC 出入参 | `<业务>Api` + 对应的 DTO | api 的 `api/<domain>/dto/`，**别放全量 VO 目录里** |

约定：

1. 自建 VO 用 Java 驼峰、常规类型（Long/Integer/String/BigDecimal/LocalDateTime/Boolean/List），不沿用全大写交换层风格。
2. 只放当前页面/接口真正需要的字段；能对上规范字段时，在 `@Schema` 里注明规范字段名（如 `对应规范字段 PROJECT_CODE`），便于回溯。
3. 字典值注明字典类型（`DictTypeConstants`），枚举注明枚举类（如 `NationalTenderModeEnum`）。
4. 不要把全量 VO 直接当 `@RequestBody`/`@ResponseBody`：字段多、混政务字段、类型也不合前端。

### 3.2 与全量 VO 的切换

- 转换只放在 Service 层，用 `cn.iocoder.txgy.framework.common.util.object.BeanUtils`；Controller 不写转换代码。
- 上报/交换时：Service 组装数据 → 映射为全量 VO → 用 `PublicLevelFilter` 按调用方的公开级别裁剪。
- 时间、金额的转换收敛在 Service 的公共方法：内部 `LocalDateTime` ↔ 上报 `yyyyMMddHHmmss` 字符串；内部 `BigDecimal` ↔ 上报字符串，单位统一元。

## 四、前后端分离的开发框架

### 4.1 整体结构

```text
txgy-ui-admin-vben (apps/web-antd)         txgy-module-bidding-server              txgy-module-bidding-api
┌────────────────────────────┐   REST/JSON  ┌──────────────────────────────┐  RPC(Feign)  ┌───────────────────────┐
│ src/views/bidding/<菜单>/*.vue │ ──────────▶ │ controller/admin/<domain>    │             │ api/<domain>/          │
│ src/api/bidding/<domain>/... │ ◀────────── │ service/<domain>             │ ◀──────────▶ │   dto/、Api 接口        │
│ (requestClient 封装)          │             │ dal/(dataobject|mysql)       │             │ enums/ApiConstants      │
└────────────────────────────┘             └──────────────────────────────┘             └───────────────────────┘
```

- 前端不碰数据库，后端只返回 JSON；跨模块（system/infra/bpm 等）一律走 api 契约 + RPC。
- 单体/微服务同构：打进 `txgy-server` 时 Feign 走本地 Bean；`bidding-server` 独立部署时走 RPC（服务名 `bidding-server`，前缀 `/rpc-api/bidding`）。

### 4.4 接口与数据的统一约定

1. 返回统一用 `CommonResult`，分页用 `PageResult`，参数校验用 `jakarta.validation` + `@Validated`。
2. 每个写接口都加 `@PreAuthorize("@ss.hasPermission('bidding:xxx:update')")`，权限码同步到 sql/ 菜单脚本。
3. 时间出入参用 `LocalDateTime`，与上报格式的互转放 Service。
4. 字典值存 code，展示名交给前端翻译（`@DictFormat` 只用于 Excel 导出）。
5. 租户隔离交给 `txgy-spring-boot-starter-biz-tenant`（MyBatis-Plus 多租户拦截器按 DO 基类自动实施：DO 继承 `TenantBaseDO` 的表，读写 SQL 自动带租户条件），业务代码不再自行过滤；需要跨租户读取的公开接口，显式使用框架租户忽略机制（`TenantUtils.executeIgnore(...)` / 方法级 `@TenantIgnore`），并配合公开级别字段白名单（标注见 2.1/2.2，出参裁剪见 3.2 的 `PublicLevelFilter`）。

### 4.5 写接口并发与幂等

- 幂等：所有写接口（create/update/delete、状态跃迁、上报）标 `@Idempotent`（`cn.iocoder.txgy.framework.idempotent`，protection starter）。默认按「登录用户 + 接口 + 参数摘要」生成幂等 key，命中窗口内重复提交直接返回首次结果、不二次落库；需按业务键判重的，用 SpEL 指定（`ExpressionIdempotentKeyResolver`，如 `#reqVO.bidSectionCode`）。写接口超时后由前端带同一 key 重试，禁止"再点一次"绕过。
- 互斥：确需"同一时刻只允许一个实例执行"的临界区（定标、发中标通知书、保证金退还、同标段开标/评标推进）用分布式锁 `@Lock4j`（lock4j-redisson，框架已装配 `TxgyLock4jConfiguration`），锁 key 规范 `bidding:lock:<实体>:<业务键>`，必设 `expire`（秒级、覆盖最长临界区）并配 `DefaultLockFailureStrategy`（抢不到即抛 `bidding` 段错误码），禁止无超时的锁。能用「幂等 + 乐观锁」解决的，优先不上锁。
- 乐观锁：并发覆盖热点列（`version`、状态、金额）在 DO 上加 MyBatis-Plus `@Version`，更新走 `WHERE id=? AND version=?`，影响行 0 视为冲突，抛「数据已被他人修改，请刷新」。框架**未**默认注册 `OptimisticLockerInnerInterceptor`，本模块须在自己的 MyBatis-Plus 配置里补注册后才生效，勿假设开箱可用；业务表 DDL 加 `version int NOT NULL DEFAULT 0`。
- 择用：防重复提交→幂等；防并发覆盖→乐观锁；防串行互斥→分布式锁。关键写路径按需叠加，写操作与流转/审计日志同事务。

> 平台实现核对（2026-09-03，源 txgy-framework）：`@Idempotent` 与 `IdempotentAspect`、`Default/ExpressionIdempotentKeyResolver` 在 `txgy-spring-boot-starter-protection`；`@Lock4j` 由 `TxgyLock4jConfiguration`（`@ConditionalOnClass com.baomidou.lock.annotation.Lock4j`）+ `DefaultLockFailureStrategy` 装配，底层 Redisson（依赖 `lock4j-redisson-spring-boot-starter`）；MyBatis-Plus `OptimisticLockerInnerInterceptor` 在框架内未检索到注册点，需业务侧补。

### 4.6 检索、缓存与慢查询

- 大文本检索走 ES，与落库解耦：业务表事务提交后发一条 MQ 事件（`txgy-spring-boot-starter-mq`，Redis Stream——`AbstractRedisStreamMessage` 定义消息、`AbstractRedisStreamMessageListener` 消费并写/删 ES 文档），采用「本地写库 + 消息驱动建索引」的最终一致，不做同步双写；消息未消费由框架 `RedisPendingMessageResendJob`（XPENDING/XCLAIM）补偿重投，消费端按业务键幂等 upsert。检索只查 ES 取 id+摘要，详情回主表/内容表取当前生效版本；DB 侧禁用 LIKE/全文索引（见第五章第三节第 3 款）。
- 缓存：低频变更的字典（代码集、行政区划、交易目录）走 Redis + `@Cacheable`，key 前缀 `bidding:`，TTL 小时级，字典变更靠短 TTL 自然过期或失效广播；详情读热点按 id 缓存、写路径主动 `@CacheEvict`。带租户的列表/分页默认不缓存（租户×多条件命中率低且易脏）；G 轨共享字典可全局缓存，T 轨业务数据缓存 key 必含 `tenant_id`。
- 慢查询：单查询 P95 > 500ms、导出/报表 > 3s 视为待优化。判定用 MySQL 慢日志（团队既定阈值，默认 `long_query_time=1s`）+ `EXPLAIN`。硬性约定：禁 `select *`；分页 `pageSize ≤ 100`、深分页走游标（`WHERE id > #{lastId}`）；截止/预警等时间列按需建索引、列表过滤列命中索引前缀（与第五章第六节"索引以必要为限"一致）；跨模块取数走 RPC，禁止本库 join 他模块表（第六章红线 6）。

> 平台实现核对：`txgy-spring-boot-starter-mq` 为 Redis Stream 实现，含 `RedisPendingMessageResendJob`（待确认消息重投）与 `RedisStreamMessageCleanupJob`；ES 客户端框架未内置，由 `bidding` 侧检索组件按需引入（对齐 `docs/招投标系统模块化设计/04-公开文档与ES搜索引擎设计.md`）。

### 4.7 错误码分配与接口版本

- 错误码格式 `1-060-YYY-ZZZ`：`1`=业务/用户侧错误码前缀（框架约定），`060`=招投标模块，`YYY`=子功能段，`ZZZ`=段内序号（001 起、只增不复用）。常量集中在 server 的 `enums/ErrorCodeConstants`。子功能段先在本表登记再占用，避免撞段；系统级错误用框架 `GLOBAL_*`，不占 `060`；段位登记集合与 `ErrorCodeConstants.java` 现状一致，由规约测试自动断言（见第六章「规约自动化校验」）。

  | YYY 段 | 子模块 | 示例 |
  | --- | --- | --- |
  | 100 | 项目/招标项目/标段 | `1_060_100_001` |
  | 101 | 公告与文件 | `1_060_101_001` |
  | 102 | 开标/评标 | `1_060_102_001` |
  | 103 | 中标与合同 | `1_060_103_001` |
  | 104 | 主体/专家 | `1_060_104_001` |
  | 105 | 监管/信用 | `1_060_105_001` |
  | 106 | 外部公告/采集/关注提醒（ext-notice：大厅展示、审核、下载通道、关注扇出等） | `1_060_106_001` |
  | 107~198 | 预留（先在本表登记、再登记进规约测试的段位集合，才可占用） | — |
  | 199 | 通用（交换层校验、公开级别裁剪等） | `1_060_199_001` |

- 接口版本与下线：读接口保持向后兼容（只加字段、不改语义、不改类型）。破坏性变更走 v2 并行——路径 `/admin-api/bidding/v2/<...>`（或网关按 header 分流），v1 与 v2 并存一个版本周期；v1 方法标 `@Deprecated` 且在 Swagger 置 `@Operation(deprecated = true)`；出参字段先在文档标弃用并通知前端、再移除；入参新增必填须兼容旧调用。节奏与第六章红线 5 一致：出参先移除，入参兼容一个版本周期后再关。

### 4.8 数据密级与日志脱敏

公开范围（`@PublicLevel` 社会公开/政务公开）管"能不能对外"；下面的密级管"存哪、怎么存、日志里怎么露"。二者正交：一个字段可以既是"政务公开"又是"高敏"（如证件号），也可"社会公开"且低敏（如项目名称）。

- 密级分级（自建 VO/DO 字段注释或 `@Schema` 上标 L 级，入库按级处理）：
  - L1 公开：可对社会公开、日志可直打（项目名称、公告正文）。
  - L2 内部：仅业务/监管内部流转（价格明细、评审过程、统一社会信用代码），日志宜脱敏。
  - L3 敏感：证件/资质证书编号、联系方式（电话/邮箱/地址）、联系人、保证金子账号、专家身份与打分——日志必脱敏、列表默认掩码、按需授权解密。
  - L4 高敏：投标报价（开标前）、身份证号、密钥类、个人隐私——存储加密、检索走盲索引、任何日志只留掩码。
- 存储加密：L4 列在 DO 上做字段级加解密（MyBatis TypeHandler 或框架加密组件，无则在 bidding 侧引入），密钥走配置中心/密钥服务、不落代码；检索需等值匹配的另存 `xxx_hash`（盲索引）列，明文不出库。镜像表按上报口径需明文时，只在 `bidding_std_*` 出参层解密，业务表仍存密文。
- 日志脱敏：用 `txgy-spring-boot-starter-web` 的 `desensitize` 注解（`@IdCardDesensitize`/`@MobileDesensitize`/`@FixedPhoneDesensitize`/`@EmailDesensitize`/`@BankCardDesensitize`/`@ChineseNameDesensitize`），访问日志由 `ApiAccessLogFilter` 统一脱敏。以下字段在出入参 DTO、`toString`、日志里一律挂脱敏注解：

  | 类别 | 涉及字段（全量 VO 英文名/常见业务列） | 注解 |
  | --- | --- | --- |
  | 证件/证书号 | `ID_CARD`、`EXPERT_IDCARD`、`*_ID_CARD`、`QUAL_CERT_NO` | `@IdCardDesensitize` |
  | 手机 | `*_MOBILE`、`EXPERT_MOBILE`、`LIANXIMOBILE`、`QUESTIONER_MOBILE` | `@MobileDesensitize` |
  | 固话/联系方式 | `CONTACT_INFORMATION`、`*_TEL`、`PHONE`、`CONTACT_TEL` | `@FixedPhoneDesensitize` |
  | 邮箱 | `*_EMAIL`、`COMPLAINANT_EMAIL`、`DISSENTOR_MAIL` | `@EmailDesensitize` |
  | 银行/账号 | `IACCT_NO`、`BANK_NAME` | `@BankCardDesensitize` |
  | 人名 | 评委/专家/联系人姓名（对外展示时） | `@ChineseNameDesensitize` |

  与第六章红线 9 一致：业务代码不自行打印敏感值，统一走注解与访问/操作日志脱敏。

## 五、数据层落地（建表约定）

> 本章规定业务数据落库（建表）的命名、长度、冗余列与文本存储规则；字段与全量 VO 的对应关系以第二、三章为据，DDL 一律置于 `sql/` 目录。
> 编号约定：本章小节用中文序号（一~七），正文里"第X节"即指对应中文序号小节——一=表结构分轨、二=字段长度、三=文本与文件存储、四=冗余列约定、五=表级租户策略、六=索引与表维护、七=建表评审；小节内条目用 1./2./3.，被引用时称"第X款"（如"第三节第 2 款"=「三、文本与文件存储」的第 2 条）。

### 一、表结构分轨

1. 业务表命名 `bidding_<域>_<实体>`（示例：`bidding_project`、`bidding_bid_section`），列名与 DO 字段一一对应，采用驼峰转下划线（如 `holderName` → `holder_name`）。
2. 交换镜像表命名 `bidding_std_<数据集>`，用于向监管上报、第三方对接及数据归集；列名照录全量 VO 字段（如 `TENDER_PROJECT_CODE`），字段统一按字符串存储并可适当加宽。镜像表仅由写入方程序维护，业务代码不得将其作为常规读写存储；写入语义为按数据集业务键幂等 upsert（同键重报覆盖旧值），每次上报落批次标识供核对与回滚（批次先例见资质域导入批次设计）。
3. 用途无法立即确定的，先仅建业务表；镜像表待上报需求明确后另行建立。
4. `<域>` 取值与 4.7 错误码子功能段对齐，先登记再用：主体、项目、标段、公告、投标、开标、评标、定标、合同、归档、监管等；已登记例外——资质域（证照台账）沿用 `cert_`/`qualification_` 前缀表名（如 `certificate_info`、`cert_change_logs`、`qualification_apply_record`），不套 `bidding_` 前缀（设计见 `资质管理/电子证件全流程管理_数据库设计.md`），新域/新前缀先在本款登记。

### 二、字段长度

VARCHAR 的声明长度仅为容量上限，不预分配存储空间，行内按实际内容占用。据此，编号类字段应一次性预留余量，避免后续频繁变更表结构；宽度无法确定时向上取一档。

| 内容类型 | 示例 | 列定义 |
| --- | --- | --- |
| 短码（≤10 位） | 字典 code、状态/类型短码 | `varchar(16)` |
| 中长码（11~21 位） | 统一社会信用代码（18）、证照类型代码（21） | `varchar(32)` |
| 组合编号（20~40 位） | 项目编号、招标项目编号 | `varchar(64)` |
| 长标识（41~74 位） | 电子证照标识（74） | `varchar(96)` |
| 名称（≤100 字） | 项目名称、单位名称 | `varchar(128)` |
| 说明性内容（无固定上限） | 备注、意见、正文 | 按第三节文本规则处理 |

> 证书编号等随证型/码制浮动的编号不套短码档：按业务实测最长核定，无法确定时向上取一档（先例：资质域证照编号按 `varchar(128)` 落，见 `资质管理/电子证件全流程管理_数据库设计.md`）。

### 三、文本与文件存储

1. 文本按内容性质分两类管理：
   - 随表文本：单值说明性内容（备注、意见等），长度在数百字以内，随主表存储——短文本使用 `varchar`，较长内容使用 `text`；不得为自由文本指定超出必要的 varchar 宽度。其变更历史由所在业务的变更审计记录（记录字段旧值/新值）留痕。
   - 内容型文本：正文类大段内容（公告正文、澄清修改内容、处理决定、意见书等），一律版本化管理，不得随主表覆盖式更新。
2. 内容型文本的版本化约定：
   - 通过独立内容表实现，命名 `bidding_<域>_content`（示例：`bidding_doc_content`），建议结构如下：

   | 字段 | 说明 |
   | --- | --- |
   | `content_id` | 主键（雪花 ID） |
   | `biz_id` | 业务记录 ID，与主表关联 |
   | `content_type` | 内容类型编码，区分同一业务下的多类正文 |
   | `content` | `mediumtext`，正文全文 |
   | `sha256` | 内容哈希，防篡改与去重 |
   | `version` | 版本号，自增、只追加 |
   | 审计列 | BaseDO 五列：`creator/create_time/updater/update_time/deleted`；归口随主表（T 轨含 `tenant_id bigint`，见第五节） |

   - 内容每次变更追加一个新版本（`version` 递增），旧版本只读保留，不更新、不删除；同一业务内容的版本追加受唯一约束 `UNIQUE (biz_id, content_type, version, deleted)` 保护（防并发重复追加），追加写接口按 4.5 幂等约定处理；
   - 内容表与主表同事务写入；主表不冗余正文全文，详情读取时按最新版本关联；
   - 版本保留期不低于对应业务的存档要求（招投标档案按既有保存期规定执行）。
3. 大文本关键字检索经 ES 实现，不得依赖数据库 LIKE 或全文索引；检索针对当前生效版本。
4. 多选及结构化数据使用 JSON 列；需按 JSON 内部值过滤时，应优先拆分子表，避免大量 JSON_EXTRACT 查询。作为证据性快照的 JSON（自查/核查快照等）如需留痕，参照第 2 款方式版本化。
5. 文件（扫描件、电子证照等）不入库，经 FileApi（infra 文件服务）上传，业务表只记录 `file_id`、`sha256`、`size`：`file_id` 为文件服务对象主键，`url` 为签名下发/回显快照，不作为一致性依据（红线 8 同口径）；上传须过病毒扫描与类型白名单（先例：资质域 `virus_scan_status`）；禁止 BLOB 存储。
6. 时间字段以 `datetime` 存储，输出及上报时转换为规范的 `yyyyMMddHHmmss` 字符串；仅镜像表允许直接存储字符串。
7. 代码型字段存储规范 code（字典 key 前缀 `bidding_`），名称经字典查询获取；发证机关等历史名称按第四节快照列处理。

### 四、冗余列约定

1. 审计列由框架 `BaseDO` 提供（不得另行自建或改名）：`creator varchar(64) DEFAULT ''`、`create_time datetime DEFAULT CURRENT_TIMESTAMP`、`updater varchar(64) DEFAULT ''`、`update_time datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`、`deleted bit(1) DEFAULT b'0'`（逻辑删除 @TableLogic）。T 轨表继承 `TenantBaseDO`（由基类得 `tenant_id bigint NOT NULL DEFAULT 0`），G 轨表继承 `BaseDO`（不建 `tenant_id` 列），归口判定见本章第五节。
2. 允许冗余的情形：
   - 子表冗余父表主键与租户列（如 `cert_id`、`tenant_id`），用于隔离与查询；
   - 名称快照列（如持证主体名称），用于列表展示免联表；其语义为登记/签发时点快照，源数据变更时不回改，不作为数据一致性校验的唯一依据。
3. 禁止以名称列替代外键，或使可变名称成为主数据的唯一事实来源。

### 五、表级租户策略（T/G 分轨）

1. 租户隔离是**表级策略**，由 `txgy-spring-boot-starter-biz-tenant` 的 `TenantDatabaseInterceptor`（实现 MyBatis-Plus `TenantLineHandler`）自动实施：**凡 DO 继承 `TenantBaseDO` 的表**，读写 SQL 自动追加 `AND tenant_id = ?`；业务代码不得自行手写租户过滤。判定依据是实体是否继承 `TenantBaseDO`，不是"看表里有没有列"。
2. **T 轨（租户数据）**：交易中心/企业后台业务表（项目登记、标段、投标递交、开标评标、合同、归档及其内容表等）必须继承 `TenantBaseDO`，由基类获得 `Long tenantId`（列 `tenant_id bigint NOT NULL DEFAULT 0`，注释"租户编号"），并带 BaseDO 审计列；后台管理读写自动按租户隔离。
3. **公告/公示（含内容表）**：归 T 轨，管理侧（发布、撤回、审核）由拦截器自动按租户隔离；面向公众的公开读取接口使用框架租户忽略机制（`TenantUtils.executeIgnore` 或 Service 方法级 `@TenantIgnore`）跨租户读取，且只外发标为"社会公开"的字段（公开级别定义与标注见第二章 2.1/2.2，出参裁剪见 3.2 的 `PublicLevelFilter`，配合第六章红线 2）。跨租户读取等于返回全部租户并集，公开接口的字段白名单与发布侧的公开级别校验必须两头把关，漏一头即泄露。
4. **G 轨（无租户语义）**：`bidding_std_*` 标准镜像表、交易目录与代码集等共享字典、监管归集等平台级表继承 `BaseDO`（纯 BaseDO，不含 `tenantId`），不建 `tenant_id` 列；唯一性以全局业务编号/code 保证。本平台拦截器按实体基类判定（非 `TenantBaseDO` 实体一律跳过），G 轨**不会被拼租户条件、不会因此 SQL 报错**；仍建议在配置 `txgy.tenant.ignore-tables`（注意前缀是 `txgy`，不是 `yudao`）显式登记表名，或在 DO 上加 `@TenantIgnore`，把"无租户"意图固化，防止后来者误把 DO 改成继承 `TenantBaseDO` 后整表报错（无列拼条件）。
5. 判定顺序：新表先判定有无租户归属语义——无（全局共享/公开只读/平台级）归 G 轨；有则归 T 轨，其中对外提供公开读的（公告/公示类）按第 3 款处理；拿不准默认 T 轨。内容表、子表归口随主表。

> 平台实现核对（2026-09-03，源：txgycloud `txgy-framework/txgy-spring-boot-starter-biz-tenant`）：`TenantBaseDO extends BaseDO`（新增 `Long tenantId`）；`BaseDO` 审计字段为 `creator(String)/createTime/updateTime/updater(String)/deleted(@TableLogic)`，DDL 惯例 `creator varchar(64) DEFAULT ''`、`create_time datetime DEFAULT CURRENT_TIMESTAMP`、`updater varchar(64) DEFAULT ''`、`update_time datetime ... ON UPDATE CURRENT_TIMESTAMP`、`deleted bit(1) DEFAULT b'0'`；`TenantDatabaseInterceptor`（MP TenantLineHandler）按"实体是否继承 TenantBaseDO"决定是否拼 `tenant_id = ?`，配置忽略表、`@TenantIgnore`、非 TenantBaseDO 实体均跳过；配置前缀 `txgy.tenant.*`（enable/ignore-urls/ignore-visit-urls/ignore-tables/ignore-caches）；工具 `TenantUtils.execute/executeIgnore`、注解 `@TenantIgnore`。
> 存量对照：system 主数据（AdminUser/Role/Dept/OAuth2）与 pay 新表用 `TenantBaseDO`；crm/erp/mall/wms/hrm 等存量模块 DO 仍直接继承 `BaseDO`（部分表虽含 `tenant_id`（默认 0）但拦截器不拼条件，属单租户部署/迁移形态）。本模块按框架目标形态（T 轨继承 `TenantBaseDO`）实施，评审对照时勿以存量模块写法为准。

### 六、索引与表维护

1. 主键采用框架雪花 ID；业务唯一性优先通过唯一约束保证：T 轨 `UNIQUE (业务编号, deleted, tenant_id)`（平台惯例：业务键在前、含 `deleted` 兼容逻辑删除、`tenant_id` 收尾；列序亦可 tenant_id 在前，但必须含 `deleted`），G 轨 `UNIQUE (全局业务编号/code, deleted)`。
2. 长文本列不建普通索引；到期预警、截止时间等场景按需对时间列建索引；索引以必要为限。
3. 日志、流水等只追加表按月分区，并按保留期归档。分区键默认取 `create_time`（业务发生时间与落库时间差异大的取业务时间列，建表评审注明）；归档由定时任务执行、冷分区 `DROP PARTITION` 秒级下线，任务与保留期登记在建表评审中，保留期按对应业务档案/监管要求定到表级（先例：资质域变更日志 ≥3 年、自查记录 ≥3 年、预警满 6 个月归档，见 `资质管理/电子证件全流程管理_数据库设计.md`）。
4. 索引命名 `uk_<语义>`/`idx_<语义>`，与列序语义一致（参照平台 fms `uk_business` 风格）；唯一约束与普通索引各自命名，避免同名混淆。

### 七、建表评审

新表 DDL 提交 `sql/` 前，应确认下列事项通过后再实施：
1. 字段对应全量 VO 已存在（缺失时先补全字典）；
2. 表名、列名符合命名约定且与 DO 一致；
3. 长度档位符合第二节规定；
4. 文本字段已确定归属：内容型文本按第三节第 2 款建带版本的 `bidding_<域>_content` 表，随表短文本明确变更留痕方式；文件、时间、代码字段按第三、四节约定落地；
5. 冗余列符合第四节适用情形；
6. 唯一键与索引定义明确；
7. 表级租户归口（T/G）已按本章第五节判定：T 轨 DO 继承 `TenantBaseDO`（`tenant_id bigint NOT NULL DEFAULT 0` + BaseDO 审计列）；G 轨 DO 纯继承 `BaseDO`、不建 `tenant_id`，且已显式登记 `txgy.tenant.ignore-tables`（或 DO 标 `@TenantIgnore`）。
8. 并发/幂等与密级列已按第四章落地：写路径需要的 `version`（乐观锁）与 `idempotent_key`（幂等）按 4.5 落列；L1~L4 密级标注、L4 加密列与盲索引列、脱敏注解挂载按 4.8 确认；
9. 分区/保留/归档已按本章第六节第 3 款明确（分区键、保留期、归档任务）；
10. 镜像表（`bidding_std_*`）如建：写入语义与唯一键已按本章第一节第 2 款确定。

## 六、容易踩的坑（红线，别碰）

| # | 坑 | 怎么躲 |
| --- | --- | --- |
| 1 | 把规范字段名/值域"修"好看点 → 上报、联调对不上 | 全量 VO 的字段名一律照录；要改先回规范核对并说明理由，禁止随手改 |
| 2 | 政务公开字段流到公共服务大厅/ES → 数据泄露 | 出参一律过 `PublicLevelFilter`；没标 `@PublicLevel` 的字段默认不外发 |
| 3 | 时间/金额各写各的转换 → 上报数据乱 | 时间统一 `yyyyMMddHHmmss`、金额统一元；转换只放 Service 公共方法 |
| 4 | 字典/枚举直接写魔法值 → 码值漂移 | 只用 `api/enums` 常量类和 `DictTypeConstants`；码值要变先改规范 |
| 5 | 删字段/删码值立刻下线 → 存量接口炸 | 按规范节奏来：出参先移除，入参兼容一个版本周期再关 |
| 6 | 跨模块直连人家的库、复制表 → 数据不一致 | 走 api 契约 + RPC（FileApi/AdminUserApi/DeptApi 已配好），禁止跨库 SQL |
| 7 | 直接改已上线的表 → 迁移风险 | 学 yudao 的做法：优先扩展表（`xxx_ext`）+ 字典 + 配置，动主表结构先评审 |
| 8 | 附件、密文往库里塞 → 泄露 | 附件经 FileApi（infra 文件服务）上传，业务表只存 `file_id` + `sha256`（+`size`），不存裸 url 与明文内容；加解密是文件服务的事。存储口径与病毒扫描见第五章第三节第 5 款 |
| 9 | 敏感信息（联系方式、证件号、政务字段）打进日志 | 日志脱敏；访问日志/操作日志够用了，业务代码别自己打印敏感值 |
| 10 | 页面直接吐全量 VO → 接口又胖又漏 | 页面一律走自建 VO（第三章），Service 裁好了再返回 |
| 11 | 绕过租户拦截器：原生 SQL、手写租户条件、把 T 轨表当 G 轨查 | 查询一律走 Mapper 与 `TenantBaseDO` 实体，让拦截器拼租户条件；确需跨租户的公开场景用 `TenantUtils.executeIgnore`/`@TenantIgnore` 并过白名单（第五章第五节） |
| 12 | L3/L4 字段明文进报表导出、Excel、下载包 | 导出走统一导出组件并挂脱敏注解；L4 需授权解密，镜像表明文只出现在上报链路（4.8 口径） |
| 13 | 对已发布公告/处理决定的正文做覆盖式更新 | 正文一律走 `bidding_<域>_content` 版本化（第五章第三节第 2 款），发布后只追加新版本，不 UPDATE 旧版本 |
| 14 | 把 `bidding_std_*` 镜像表当业务读写表 | 镜像表只由写入方程序维护；业务读写走业务表（第五章第一节第 2 款） |

### 常规习惯

1. 提交信息用中文写清楚"改了什么、为什么"；提交前自查 `git status`，别碰到 `VO数据规范/` 里的权威文件。
2. 代码风格跟着仓库走：lombok 链式 setter、import 不用 `.*`、类上 Javadoc 必须有。
3. 核心规则（时限、金额、状态流转、公开级别裁剪）要写单元测试，先写失败用例再实现（仓库内暂无同类模块测试可抄时按此来）；Controller 留 `*.http` 文件方便调试。
4. DDL/菜单/字典脚本进 `sql/`；表名用 `bidding_` 前缀（业务域另有约定按约定），字段长度按"数据层落地"的冗余约定来。
5. 改了接口、字典、全量 VO，顺手把本文件对应章节也更新掉，别让文档落后半年。
6. 新功能默认走 TDD：先写失败用例（核心规则、状态流转、字段规约先行）→ 跑红 → 实现 → 跑绿，测试随功能同批提交；红绿都过不了，不许说"做完了"。
7. 业务 SQL（建表/菜单/字典/初始化脚本）一律放本模块 `sql/` 目录，文件按 `sql/yyyy-MM-dd-<主题>.sql` 命名，随功能同批提交；建表 DDL 按第五章约定过建表评审，不得散落到平台库脚本或其他目录。
