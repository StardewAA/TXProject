## 二、启动冒烟发现的失败链（按出现顺序）

冒烟命令（临时参数覆盖，未改任何配置文件）：
```
java -jar txgy-server.jar \
  --txgy.bid.agent-key=smoke-key \
  --spring.datasource.dynamic.lazy=true \
  --spring.autoconfigure.exclude=org.redisson.spring.starter.RedissonAutoConfigurationV4
```

1. **装配层：`ApiErrorLogCommonApi` no qualifying bean**
   - 根因（已实证）：`txgy-module-{system,infra,bid}-server` 的 jar 均被各自 `spring-boot-maven-plugin` **repackage 成 executable jar（内容为 `BOOT-INF/classes/...`）**。作为依赖方（txgy-server）引用的 jar 内类不可被组件扫描/ClassLoader 命中 → infra 提供的 `ApiErrorLogApiImpl(@RestController implements ApiErrorLogCommonApi)` 永远注册不上。
   - 临时验证：把三模块打成普通 jar 覆盖 .m2 后，该 bean 及其依赖链（直到 Mapper/数据源）**全部正常装配** ⇒ 确认根因 = 构建产物形态，非业务代码问题。
2. **数据库层：`dynamic-datasource create datasource [master] error` → `Access denied for user 'root'@'localhost'`**
   - 本机 MySQL(3306) 可达但 `root/123456` 凭据不符（application-local.yaml 默认账号）。
   - 用 `--spring.datasource.dynamic.lazy=true` 绕过启动期建连后推进成功（dynamic-datasource 显示 add master/slave success）。
3. **缓存层：RedissonAutoConfigurationV4 启动即连 6379 失败（本机无 Redis）**
   - `OAuth2AccessTokenRedisDAO → stringRedisTemplate → RedissonClient` bean 创建期强连 `127.0.0.1:6379` 失败。
   - 按预案排除 Redisson 自动配置后，Boot 的 Lettuce 未接管 `StringRedisTemplate`（此 fork 的 Redis 模板实际由 Redisson starter 提供），仍缺 bean ⇒ **无 Redis 无法到 Web 就绪**（属环境硬前置，停止进一步 hack）。

## 三、解锁清单（按顺序）

| # | 解锁项 | 说明 | 动作 |
|---|---|---|---|
| 1 | **构建基线修复（mono 装配前提）** | 被依赖的 module-server 应产出「普通 jar」供装配，另留可执行 jar（如有单跑需要）。当前 jar 是 executable 布局，作为依赖永远装配不上 | 三模块 `spring-boot-maven-plugin` repackage 加 `<classifier>exec</classifier>`（主 jar 普通 + `-exec` 可执行），或 mono 场景对 module-server 构建 `spring-boot.repackage.skip=true`；需产品侧确认 cloud 独立部署 jar 命名影响 |
| 2 | **MySQL 可用账号/库** | 提供能连 `127.0.0.1:3306` 的账号（或改默认 root/123456 为本机真实凭据），并导入全量 schema：`sql/00-sql文件/sql/mysql/ruoyi-vue-pro.sql` + `deploy/mysql/init/0070-*`、`0071-*`（bid 表） | 导入后启动即不再 Access denied |
| 3 | **Redis 服务** | 本机 6379 起 Redis（docker `deploy/docker-compose.yml` 的 redis 服务 / Memurai / WSL），或改 `spring.data.redis` 指向可用实例 | 起后无 Redisson 连不上问题 |
| 4 | （可选）冒烟专用轻量方式 | 若只想在无 MySQL/Redis 环境验证 bid 路由，需做更多参数排除与 bean 补齐 | 不建议，解锁 1–3 后正常启动最有价值 |

## 四、对「Java 25 + Spring AI 2.0」P0 spike 的判定

- 整包编译（含 Spring AI 2.0.0 starter、docx4j、Tika）✅；
- Spring 装配推进到安全/权限/oauth2 链之前**零版本性报错**（web 前缀、swagger、mybatis、dynamic-datasource、bid controller/service 均可创建）；
- 三个失败点均与 Java25/SpringAI 无关，属构建产物形态 + 外部依赖缺失；
- ⇒ 架构文档风险登记「Spring AI 2.0 + Java 25 太新（高）」在运行期方向得到缓解，剩余为「环境就绪 + 构建基线」问题。

## 五、建议下一步

1. 先由产品/运维拍板 **module-server 构建形态**（普通 jar vs `-exec` 双 jar）并落 pom（最小改动点：system/infra/bid 三模块的 repackage 配置）；
2. 部署 MySQL（导入全量 + bid schema）与 Redis；
3. 复跑本冒烟（java -jar），预期到 Web 就绪 → 验证 `/actuator/health/liveness` 与 `/admin-api/bid/segment/index`（401/400/业务错误链路）；
4. 之后进入真实联调：起 TEI×2/vLLM/Qdrant → 入库真实招标文件 → `/agent/retrieve` → Node Agent 对接。

> 复现备注：本次为验证装配，临时把三模块 server 打普通 jar 覆盖本地 .m2（已恢复为原始 executable jar 并清理备份）。重复冒烟前需按「解锁项 1」重新用普通 jar 装配，或直接修 pom 后重新 install。
