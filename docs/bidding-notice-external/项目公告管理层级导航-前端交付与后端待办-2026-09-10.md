## 一、业务层级与创建入口（已实现）

| 级别 | 页面 | 路由 | 创建入口 |
| --- | --- | --- | --- |
| 第一级 | 项目列表（工作台） | `/portal/bidding/projects` | **创建项目** |
| 第二级 | 某项目下的招标项目 | `/portal/bidding/projects/:projectCode/tender-projects` | **创建招标项目**（自动带 PROJECT_CODE） |
| 第三级 | 某招标项目下的标段（包） | `/portal/bidding/projects/:projectCode/tender-projects/:tenderProjectCode/sections` | **创建标段**（自动带 TENDER_PROJECT_CODE） |
| 第四级 | 某标段下的公告/公示 | `/portal/bidding/sections/:bidSectionCode/notices` | **创建公告**（仅在此级） |

- 导航逻辑：点击行内编号/「进入下级」逐级下钻；每页有面包屑可回上级。
- 创建公告：**先选公告类型（4 选 1）**，再按类型**动态加载**对应的表前端文件（`defineAsyncComponent` 分包懒加载，选哪个加载哪个）：
  - 招标公告 → `views/bidding/notice/tables/TenderNoticeTable.vue`
  - 变更公告 → `ChangeNoticeTable.vue`
  - 中标候选人公示 → `CandidatePublicityTable.vue`
  - 中标结果公示 → `ResultPublicityTable.vue`
  自动写入 `TENDER_PROJECT_CODE` / `BID_SECTION_CODES` / `NOTICE_BID_NUM`（用户不手抄编号），并按类型挂对应附件采集项。
- **发布公告的前置状态限制本期不处理**（按要求忽略）：只创建草稿 + 查看，不做发布门校验。
- 附件：项目、招标项目、标段、公告**各级都可挂多个附件**（`AttachmentsPanel`，按 AttachmentItemVO 采集项分组，多文件、必传项缺失提示、`ATTACHMENT_CODE` 半角分号拼接）。各级列表页均有「附件」入口查看。

## 二、接口对接（均为既有后端接口，未新增契约）

| 用途 | 接口 | 权限 |
| --- | --- | --- |
| 项目分页/详情/编号查/保存/删除/追溯 | `/bidding/project/{page,get,get-by-code,save,delete,trace}` | `bidding:project:*` |
| 招标项目同上 | `/bidding/tender-project/{page,get,get-by-code,save,delete,trace}` | 复用 `bidding:project:*` |
| 标段分页/详情/编号查/保存/追溯 | `/bidding/bid-section/{page,get,get-by-code,save,trace}` | `bidding:bid-section:*` |
| 标段下公告列表 | `/bidding/bid-section/trace?bidSectionCode=` → `notices`（一次聚合，免多次请求） | `bidding:bid-section:query` |
| 公告创建/详情/类型元数据 | `/bidding/notice/{create,get,meta/types}` | `bidding:notice:*` |

写入口径（与后端实现一致）：`payload` = 数据集字段全集（key = VO 规范英文名，服务端按 record `canonicalize` 补 null、丢多余键）+ 主列 camelCase（列表/追溯展示）。必填以后端实况为准（仅校验 编号 + 名称）。

## 三、必须由后端补的能力（前端已就绪，等接口）

1. **项目域附件持久化（阻塞"逐级挂附件"闭环）**
   现状：`Project/TenderProject/BidSection` 的 Controller、DO、`fields_json` 均无附件结构；`ProjectPayloadUtils.canonicalize` 会**丢弃未知键**，因此附件明细（ATTACHMENT_GUID/名称/类型/URL）**无法随实体落库**，只有 `ATTACHMENT_CODE`（GUID 串）能存进 `fields_json`。
   前端当前兜底：GUID 照规范写入 `payload.ATTACHMENT_CODE`；附件明细按「实体+编号」存本地供页面回显（`attachmentStore.ts`，明确标注为临时）。
   请后端二选一：① 提供实体附件集读写接口（`AttachmentSetVO` 列表，按 entity + code 存取）；② 在 `fields_json` 中保留附件集结构（如新增 `ATTACHMENT_SET` 键，不被 canonicalize 丢弃）。
2. **标段删除接口缺失**：`ProjectController`/`TenderProjectController` 有 `/delete`，`BidSectionController` 没有。前端已改为"不删除 + 明确提示"，避免误删上级数据。请补 `POST /bidding/bid-section/delete?id=`（并做"存在公告时拒绝"的追溯链保护）。
3. **公告 PDF 预览取不到 URL（前端因此暂时无法预览 PDF）**
   现状：`NoticeDetailRespVO` 只有 `pdfFileId`（无 URL）；前端唯一取 URL 的途径是 `GET /infra/file/get?id=`，该接口需 `infra:file:query` 权限。
   前端已建 `PdfPreview.vue`：优先用附件 URL（上传接口返回的 URL）直接内嵌浏览器原生 PDF 查看器预览，**该路径现在即可用**；公告版式文件（pdfFileId）则依赖上面的 URL 获取。
   请后端：① 在公告出参直接回传可访问的 `pdfUrl`（推荐，或提供 `/bidding/notice/{id}/pdf-url`）；② 确认文件服务 URL 是否需要鉴权头（若需要，`<iframe>` 无法带 header，必须由后端提供免鉴权/带签名的直链，否则前端须改用 pdf.js + 请求流渲染）。
4. **前台账号权限点**：前台页面走 `bidding:project:*`、`bidding:bid-section:*`、`bidding:notice:*`。权限点已由 `txgy-module-bidding/sql/history/2026-09-10-project-domain.sql` 插入，但需给企业/租户角色默认分配（否则前台 403，页面打不开）。
5. **上传返回缺 `file_id`**：`/infra/file/upload` 只回 URL；而公告发布强制 `pdfFileId` 非空。前端已实现 presigned-url + `/infra/file/create` 兜底取 file_id，请确认该链路对前台账号可用（配置 `configId` 是否存在）。
6. **口径确认（不影响本期前端）**：
   - 项目域 save 只校验 编号+名称，VO 规范"必填=是"字段更多 —— 是否需要后端按规范强校验？
   - 主列 `approvalDeptName/approvalDeptCode/approvalDocNo` 与规范字段 `APPROVAL_AUTHORITY/APPROVAL_NUMBER/APPROVAL_NAME` 命名不一致（前端已按语义对齐：AUTHORITY→approvalDeptName、NUMBER→approvalDocNo）。
   - `NoticeServiceImpl.createNotice` 无条件 `canonicalize` + `checkRequired`，与文档"站内公告可不填 payload"口径冲突。
