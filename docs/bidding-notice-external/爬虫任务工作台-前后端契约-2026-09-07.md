## 0. 术语与总模型

- **任务（run）= 一次爬取动作的完整实例**（一次点击“爬取”、一次定时轮询、一次手动录入各产生一条任务条）。
- **任务类型 taskType**：
  - `TEST`：手动录入（贴 HTML/JSON 原文、传 PDF/HTML/JSON 文件）或对指定源“立即爬取一次（测试口径）”；
  - `SCHEDULE`：源启用后由调度器按轮询间隔产生的周期执行。
- 一个**采集源**（bidding_crawl_source）可产生多条 SCHEDULE run；手动录入不依赖源。
- 后端沿用现有雪花主键（BigInt → JSON 序列化为字符串，前端全按 string 处理，已兼容）。
- 轮询间隔下限 120s 已由后端校验（1-060-106-046）；前端对“立即爬取”按钮做 ≥120s 距上次触发节流提示。

## 1. 后端待实现契约（按实现优先级）

### 1.1 任务条回执与过程留痕

在 `bidding_crawl_task`（雪花主键）之上**新增任务实例语义**，建议落地方式二选一（A 优先，改动最小）：

- **方案 A（推荐）**：`bidding_crawl_task` 增列 `task_type VARCHAR(16)`（TEST/SCHEDULE，源定时任务建任务时=TEST 由手动触发写 TEST）；
  每行即一条任务条。现有 id/状态/attempt/url 等保留；**过程信息放新表 `bidding_crawl_task_run_detail`（run_id 同主键雪花，1:1）**：

  | 列 | 说明 |
  | --- | --- |
  | run_id | 雪花主键，= crawl_task.id |
  | task_type | TEST/SCHEDULE |
  | channel_code | 使用的下载器适配器（GENERIC/站点专属） |
  | parser_code | 使用的解析器 |
  | source_code | 来源（手动录入可空/填 MANUAL） |
  | input_type | HTML/JSON/PDF/URL（手动录入的口径） |
  | input_file_id / input_text_head | 手动录入原文出处（文件 fileId 或文本前 512 字） |
  | raw_content | 源代码/原文（HTML/JSON 原文，可 64KB 截断；PDF 存文件引用 raw_file_id） |
  | extract_json | 提取内容（公告字段 JSON：title/projectKey/tenderProjectKey/bidSectionCodes/issuerName/publishTime/contentType/… + parser meta matched/unmatched） |
  | render_html | 渲染后的内容（结构化 HTML：heading/paragraph/table/list，前端以公文样式展示；后端生成或前端按 extract 兜底） |
  | steps_json | 过程步骤数组（见下） |
  | logs | 过程日志（换行文本，可空） |
  | error | 失败原因/死信原因 |
  | status | 与 crawl_task.status 对齐（PENDING/RUNNING/SUCCESS/FAILED/SKIPPED） |

  `steps_json` 数组元素：`{ step: DOWNLOAD|PARSE|EXTRACT|RENDER, channelCode?, parserCode?, status: OK|FAIL, durationMs, artifact: { kind: SOURCE_RAW|PDF|EXTRACT_TEXT|RENDER_HTML, fileUrl?, size? } }`。
  中间文件（原文、PDF、抽取文本）落 infra file 后回填 fileUrl；未接 file 能力时 fileUrl 可空、内容入列如 raw_content 截断。

- 方案 B（不新增 run_detail 表）：在 crawl_task 上直接冗余上述字段（task_type/raw_content/extract_json/render_html/steps_json/logs），1 行=1 任务条，过程不落子表。缺点：过程与任务生命周期耦合；建议 A。

### 1.3 手动录入 multipart 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| inputType | 是 | `HTML`（粘贴 HTML 源代码）/ `JSON`（粘贴 JSON 原文）/ `FILE`（上传 .html/.htm/.json/.pdf） |
| content | HTML/JSON 必填 | 源代码/原文文本 |
| file / fileName | FILE 必填 | 上传文件；fileName 用于扩展名/解析器路由 |
| sourceCode | 否 | 期望归属的采集源 code（可空=MANUAL 直测） |
| parserCode | 否 | 缺省按 inputType/文件名自动路由（HTML_GENERIC/JSON_GENERIC/PDF_TEXT_GENERIC/站点专用） |
| url | 否 | 来源页 URL（附件相对链接绝对化、站点上下文提示） |

## 2. 前端行为约定（后端验收用）

1. **点击“爬取”**（对某源）→ 调 `run-async` → 得 runId → 页面顶部插入任务条（PENDING），轮询 `run/{runId}`（2s 间隔）直至终态；卡片头部常驻：类型 Tag（测试/定时）、状态 Tag、源、触发时间。
2. **任务条三段展示**：源（原文 HTML 净化 / PDF fileUrl 下载·预览占位）、提取（公告字段键值 + matched/unmatched/warnings）、渲染（render.html 或前端兜底公文化渲染）。
3. **过程抽屉**：steps 时间线、channelCode/parserCode、中间文件（artifact.fileUrl）、logs、error、审查记录（run_id 关联）。
4. **类型筛选**：测试任务 / 定时任务 / 全部（crawl-task/page taskType）。
5. **120s 节流**：同一源“立即爬取”后 120s 内再点 → 前端拦截并提示剩余秒数；后端保存/调度同样以 120s 为下限兜底。
6. 状态语义沿用 crawl_task（PENDING/RUNNING/SUCCESS/FAILED/SKIPPED），FAILED 可“重试”。

## 3. 验收 checklist（后端自查）

1. 手动录入 PDF → 返回 runId → run/{runId} 终态 SUCCESS：extract.title 等齐、render.html 非空（或 builtBy=FRONTEND_FALLBACK）；
2. 手动录入 HTML 源码（开头含空格段落）→ 渲染不出现空白占位，正文正常输出；
3. 源 run-async → SCHEDULE 任务条；120s 内重复触发被拒绝或前端已拦截；
4. crawl-task/page 按 taskType=TEST/SCHEDULE 过滤正确；
5. approve（人工）→ audit_record operator_type=USER、operator 正确；AUTO 场景同理；
6. 返回的雪花 ID 均为字符串，前端按 string 处理不报错。
