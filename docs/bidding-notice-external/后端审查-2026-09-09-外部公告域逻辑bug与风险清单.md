## 一、爬虫采集链路

### A1【高】"5 分钟/条"频控只在异步消费者里存在，而异步模式默认关闭——用户口径实际未生效
- 证据：`service/externalfetch/CrawlSourceRunner.java:74-76`（`async-mode` 默认 false=同步直抓）；`application.yaml:131-133`（entry-delay-ms=1500、page-delay-ms=60000，无 async-mode、无 consumer-delay-ms 配置）；`service/externalfetch/mq/CrawlNoticeFetchMessageListener.java:41-42`（consumer-delay-ms 兜底 300000=5 分钟，**仅消费者路径使用**）；`CrawlRunServiceImpl.java:222-224`（30s tick 调度）。
- 问题：同步直抓模式下真实节流=1.5 秒/条 + 60 秒/页，"下载器 5 分钟/条"（yaml:133 自述口径）从未生效。一轮增量=每栏目 1 页，秒级~十几秒完成——**这就是"说了 5 分钟、干到两秒"的结构性根因**。另 yaml:129 注释写"用户口径 5s=5000"，实际配 60000，注释与值互相矛盾。
- 建议：明确唯一频控口径：要么 async-mode=true 走消费者 5 分钟/条（job 收尾依赖 tryFinalizeJob，链路见 §A3 修复前提），要么把 consumer-delay 语义并入同步路径；入口 `/run` 同步长跑还需配 HTTP 超时与 @Idempotent 的兼容评估。

### A2【高】源级 `api_config_json` 保存即校验、执行链路从不读取——fetchType=API 的源必然空跑
- 证据：`service/externalfetch/CrawlSourceServiceImpl.java:172-185`（API 源强制要求 apiConfigJson，校验通过即保存）；`CrawlSourceDO.java:31`（字段注释"API 源配置 JSON"）；`CrawlSourceRunner.java:103,122,488-489`（执行只读 `entry_urls_json` 每栏目内的 `apiConfig`，源级 apiConfigJson **全链路无消费方**，已 grep 证实）。
- 问题：管理员把 API 配置填在源级字段（FE 表单也收集它）→ runner 走 HTML/QYZB 分支找不到 listUrl/categoryId → 每轮 0 类目、0 抓取 → `doRunNow` 收尾 SUCCESS（`CrawlRunServiceImpl.java:203-206` 空跑也 SUCCESS）→ **秒回"成功落库 0 条"，无任何告警**。
- 建议：runner 读源级 apiConfigJson 作为栏目缺省（或保存校验强制 API 源把 apiConfig 写进 entryUrlsJson）；空跑（0 类目/0 抓取）时批次记 PARTIAL 并打 error 汇总，前端弹窗不得显示"成功"。

### A3【高】重试链路断裂：失败一次的任务永久卡 PENDING，整个源被 RUNNING 守卫停摆
- 证据：`CrawlTaskServiceImpl.java:240-246`（handleFailure 未耗尽→PENDING+nextRetryTime）；`CrawlNoticeFetchMessageListener.java:83`（异常不向上抛、消息被 ACK，**无任何机制重发信号**；无扫描 PENDING+nextRetryTime 到期的调度）；`CrawlTaskServiceImpl.java:141-144`（人工 retryTask 仅接受 FAILED，PENDING 卡死连人工入口都没有）；`CrawlRunServiceImpl.java:170-179`（同源有 RUNNING 批次即跳过）+ `tryFinalizeJob` 279-291（PENDING task 永不终态 → job 永远 RUNNING）。
- 问题：一条 task 消费失败 → 重试只改了 DB 状态、信号丢失 → task 永久 PENDING → job 永久 RUNNING → **该源此后每轮 runNow/调度都被 RUNNING 守卫跳过，直到重启**；重启自愈（`CrawlRunServiceImpl.java:120-148`）也只补发 RUNNING→PENDING 的信号，补发后再失败则再次卡死。
- 建议：增加"到期 PENDING 重投"扫描（复用 @Scheduled tick：`status=PENDING AND next_retry_time<=now` → 重发轻信号）；retryTask 放开 PENDING（清 nextRetryTime 重发）；或 handleFailure 未耗尽时同步重发 MQ 消息。

### A4【高】消费者在 onMessage 里 sleep 5 分钟：持未 ACK 消息长睡，pending 重投必然造成重复执行
- 证据：`CrawlNoticeFetchMessageListener.java:95`（`sleep(consumerDelayMs)` 在 onMessage 内、ACK 之前，兜底 300000ms）；`:44-45,67-68`（consumeLock 串行）；类注释:22 自述框架 pending 5 分钟超时重投。
- 问题：单条消息占用消费线程 ≥5 分钟且未 ACK → Redis Stream pending 堆积、ResendJob 重投 → 重投消息回查 task 非终态即重跑（`:62-70` 不检查 nextRetryTime）→ **同一 URL 双重下载/落库竞态**；串行锁使吞吐=1 条/5 分钟，一批 10 条 50 分钟起步，job 长时间 RUNNING。
- 建议：节流移出 onMessage（消费后置 delay 用调度实现，或独立拉取线程控速）；重投路径消费前校验 nextRetryTime。

### A5【中】runner 预填 publishTime=now，把 ingest 的 BR-5 原文日期回填打穿
- 证据：`CrawlSourceRunner.java:203,290`（`dto.setPublishTime(publish == null ? LocalDateTime.now() : publish)`）；`service/noticeexternal/ingest/ExternalNoticeIngestServiceImpl.java:347-353`（resolvePublishTime 仅在 null 或 year<2000 时才 resolveFromText）。
- 问题：列表日期解析失败的公告，runner 已填"抓取时间"→ ingest 判非空直接采信 → 原文里明明有的发布日期（标题/正文锚点）永远不解析 → 列表时间倒序失真。
- 建议：runner 解析失败时传 null，把回填决策权完整交给 ingest（BR-5 本来就是 ingest 的职责）。

### A6【中】覆盖重投不清 bodyBlocks：内容已换，前台优先渲染的还是旧结构化块
- 证据：`ExternalNoticeIngestServiceImpl.java:158-191`（overwriteNotice 仅重置 extractionStatus=NONE，`bodyBlocksStatus/bodyBlocksJson/bodyParserCode` 未动；Portal 渲染优先级=bodyBlocksStatus=SUCCESS 且 JSON 非空→按块渲染，见前端 `views/portal/bidding/api.ts` 头注）。
- 问题：源站内容更新→打回 NEW→审核通过→**前台展示旧正文**（新 contentHtml 被旧 bodyBlocksJson 遮蔽），直到有人手动重跑正文结构化。
- 建议：overwriteNotice 同步置 bodyBlocksStatus=NONE 并清 bodyBlocksJson/bodyParserCode（与 §C2 一并修）。

### A7【中】解析器与接口域名硬编码，源配置形同虚设
- 证据：`CrawlSourceRunner.java:45`（`QYZB_API = "https://qyzb.shccmg.com/..."` 常量，:237 使用）；`:312`（runHtmlCategory 固定 `parserRegistry.get("GX_E_BIDDING")`）；`:238`（QYZB 分支固定 `get("QYZB_JSON")`）。`config.getParser()` 只决定走哪个分支，不决定用哪个解析器。
- 问题：`crawl_source.base_url/parser_code_default` 配了也不生效；新增同型第二家源必然抓错域名/用错解析器，且错误表现为"解析 0 条"静默空跑。
- 建议：列表/详情 URL 一律从源 baseUrl+栏目配置拼装；parserCode 缺省取源 parserCodeDefault。

### A8【中】GX iframe 分页失效被注释"自认"，60 天回溯静默丢数据
- 证据：`CrawlSourceRunner.java:351-353`（bumpPageParam 注释自述"page 参数不影响内容，仅站点壳 UI"）。
- 问题：全量回溯窗口内条目数超过列表单页容量时，窗口外条目**静默丢失**（停页逻辑判定"窗口内"永远成立，翻页无效），无告警无补偿。
- 建议：GX 源改按 dates= 窗口分段请求（注释里已点明该参数），或对"翻页内容指纹不变"的情况记 PARTIAL 告警。

### A9【低】空跑静默 SUCCESS + 前端弹窗语义错位
- 证据：`CrawlSourceRunner.java:469-499`（entry_urls_json 解析失败仅 log.warn 返回空表）；`CrawlRunServiceImpl.java:203-206`（0/0 收尾 SUCCESS）；FE `views/bidding/crawlExternal/source/index.vue`（弹窗"成功落库 N 条"）。
- 问题：asyncMode=true 时 N 实为"入队数"非"落库数"（`RunSummary.async` 注释自认），弹窗文案在异步模式下说谎；空配置与真无数据不可区分。
- 建议：RespVO 增补 async 标志与"空跑原因"，FE 按 async 切换文案。

### A10【低】两处启发式实现不一致 + escapeJson 不转义控制字符
- 证据：`CrawlSourceRunner.java:544`（正则 `"(招标人|采购人)\s*[:：]..."`——Java 15 起 `"\s"` 是**字面空格**转义，意图的 `\s` 应写 `"\\s"`；`CrawlNoticeProcessor.java:256` 同功能代码写的是 `"\\s"`，两处口径不一）；`CrawlSourceRunner.java:603-605` 与 `CrawlNoticeProcessor.java:167-171`（escapeJson 仅转 `\` 和 `"`，控制字符可造出非法 metaJson → ingest 校验拒绝 → 任务白跑）。
- 建议：extractIssuer 收敛为一处共用；metaJson 改 ObjectMapper 序列化，废弃手拼。

### B1【高】SSRF：下载链路无任何 host/内网校验，PDF 直链来自源站页面内容
- 证据：`service/externalfetch/fetch/HttpFetchClient.java`（全文无 URL 校验；`:47` follow-redirects=NORMAL）；`application.yaml:124`（follow-redirects: true）；`CrawlSourceRunner.java:371-377`（detailUrl/pdfUrl 来自解析源站 HTML，直接 getBytes）；`CrawlNoticeProcessor.java:102-109` 同。`crawl_source.allowed_hosts` 字段存在但采集执行从不校验（全模块 grep 证实）。
- 问题：源站页面被插花/解析器被骗 → 服务器向 `http://127.0.0.1:48110/admin-api/...`、内网/云元数据地址发起 GET 并跟随重定向。
- 建议：下载前统一守卫：协议 http/https + 解析 IP 拒环回/私网/链路本地 + host ∈ allowedHosts∪baseUrl 域 + 关闭跨 host 重定向。

### B2【高】robotsOk 承诺未落地：字段存在，无任何 robots.txt 逻辑
- 证据：`dal/dataobject/externalfetch/CrawlSourceDO.java:34`（"是否允许按 robots 抓取"）；全模块 grep `robots` 仅 VO/DO 三处出现，无抓取/判定/执行代码。
- 问题：对外合规承诺与实现脱节；若被源站主张即构成真实法律/商誉风险。
- 建议：首轮采集前抓取并解析 robots.txt（按 UA 缓存），robotsOk=false 的源拒绝调度；或该字段降级为"人工承诺标记"并写入文档口径。

### B3【中】下载无大小上限：大文件全量入内存
- 证据：`HttpFetchClient.java:61-130`（getText/ofByteArray 全量缓冲，无 Content-Length 校验与上限）；`infra/file/PdfBoxOpenDataLoader.java:63`（PDDocument.load 全量内存，仅 512 页上限无字节上限）。
- 问题：恶意/异常大响应直接 OOM；并发采集叠加放大。
- 建议：响应体超上限（如 32MB）即中断；PDF 抽取限并发。

### B4【中】死信"转人工审核"是 LogOnly 占位，失败任务无出口
- 证据：`service/externalfetch/sink/LogOnlyCrawlDeadLetterSink.java:18-22`（仅 log.info，crawl.audit 主题预留）；`CrawlTaskServiceImpl.java:226-238`（3 次失败→FAILED+"转人工审核"）。
- 问题：重试耗尽的任务除日志外无任何人工处理入口（采集任务管理页前端也未建），失败=永久黑洞。
- 建议：短期先建 task 管理页 + retryTask（API 已就绪）；中期接 MQ 投 crawl.audit。

### B5【低】跨 job 复用未终态任务时 jobId 归属错乱
- 证据：`CrawlTaskServiceImpl.java:64-74`（同 urlHash 未终态任务跨 job 直接复用返回旧行）；`CrawlTaskDispatchServiceImpl.java:115-122`（信号带的是**新** jobId，task.jobId 仍是旧 job）。
- 问题：新批次收尾统计（tryFinalizeJob 按 task.jobId 计数）漏掉该 URL，批次 summary 失真；旧 job 可能已收尾，事件挂在已结束批次上。
- 建议：复用时把 task.jobId 改挂当前 job，或信号/统计统一以 task.jobId 为准。

### B6【低】writePayloadIfPending 读-改-写无乐观锁
- 证据：`CrawlTaskDispatchServiceImpl.java:59-88`（selectById→判空→updateById）。
- 问题：同任务并发投递时 payload 互相覆盖（窗口小，影响低）。
- 建议：带 `payload_json IS NULL` 条件的 update 即可闭环。

### B7【低】API 源"结构性缺全文"逐条记 FAILED，污染失败率与退避口径
- 证据：`CrawlSourceRunner.java:190-193`（列表行无 contentHtml→每条记 FAILED+recordTask）。
- 问题：配置缺陷被计成业务失败，连续失败触发调度退避（`CrawlRunServiceImpl.java:238-241`），坏的是配置、罚的是频率。
- 建议：该场景记 SKIPPED+明确 message，并在栏目级汇总 error。

## 二、关注域 noticefollow（子代理细读，关键条目已抽检）

### F1【高】markRead 与扇出并发：unreadCount 丢失更新 + 整行覆盖写回（已抽检属实）
- 证据：`service/noticefollow/FollowServiceImpl.java:338-350`（markRead：selectById→setUnreadCount(0)→`updateById(item)` 整行写回）；`:573-583`（扇出 unreadCount+1 同为读-改-写）；`:505-515`（事件 insert 与留痕分步）。
- 问题：用户点已读与新事件扇出并发时：+1 被 0 覆盖、事件批量置 readFlag 先于事件 insert 执行造成"角标 0 但库里有未读"、markRead 旧快照覆盖扇出刚写的 latestDynamicTime/displayName。
- 建议：未读数改原子 SQL（`SET unread_count=unread_count+1` / 置 0 前按 readFlag=FALSE 重算），写回只传变更列。

### F2【高】外部公告扇出循环无单订阅隔离：一个订阅者异常中断其后所有订阅者（已抽检属实）
- 证据：`FollowServiceImpl.java:424-428`（for 循环内 TenantUtils.execute 无 per-subscription try/catch）；`:554-570`（去重 select-then-insert 未捕获 DuplicateKeyException，对比 seed 路径 :693-697 有捕获）。
- 问题：并发重放 approveExternal 撞 event_key 唯一键等任意异常直接冲出循环 → 排后面的订阅者永久漏提醒；调用方仅整体记日志（补偿扫描未实现）。
- 建议：循环内逐订阅 try/catch；去重 insert 捕获 DuplicateKeyException 视为幂等成功。

### F3【中】follow/unfollow 无事务 + 状态分叉后无自愈（已抽检：三方法均无 @Transactional）
- 证据：`FollowServiceImpl.java:87,147,338`（follow/unfollow/markRead 均无事务注解）；`:96-104`（subscription=FOLLOWING 即幂等早退，不校验 item 行）；`:148-154`（unfollow 同理）。
- 问题：两张表半写成功后：① 重 follow 永远早退，"我的关注"缺行、事件写进看不见的行；② 幽灵行挂列表且无法再取消。
- 建议：加 @Transactional；幂等早退前校验另一张表状态一致，不一致修复。

### F4【中】退订再关注时快照刷新未落库
- 证据：`FollowServiceImpl.java:138-142`（restoreItem 已 updateById，snapshotAnnouncement 只改内存）；`:782-788`（seed 已存在时直接 return 不再写）。
- 问题：与 :140 注释"重关应看到新标题"不符；getFollowStatus 仅 displayName 为空或等于 targetKey 时补名（:372-373），旧标题持续展示。
- 建议：snapshot+restore 后统一一次 updateById。

### F5【中】内部公告扇出只匹配公告级/项目级，TENDER_PROJECT/SECTION 关注者是静默黑洞
- 证据：`FollowServiceImpl.java:446-455`（仅两类 targetType 查询）；follow() 接受四类且不校验目标存在性（:88-89 白名单只查拼写）。
- 问题：对标段/招标项目关注的用户关注成功、建行成功、永不产生动态。
- 建议：follow() 对内部公告拒绝后两类，或补 NoticeDO 维度归属字段扩展匹配。

### F6【中】关注域 6 个接口全部借用 `bidding:notice-external:*` 权限
- 证据：`controller/admin/noticefollow/NoticeFollowController.java:45,54,62,69,77,86`（写=update、读=query）。
- 问题：投标人要能关注就必须授外部公告 update 权限——update 同时意味着可操作审核接口，横向权限错配。
- 建议：增设 `bidding:notice-follow:query/create` 权限点并同步菜单 SQL。

### F7【中】内部扇出在发布事务内同步执行 + 单订阅内 event/reminder 非原子
- 证据：`service/notice/NoticeServiceImpl.java:155-170`（@Transactional 内调扇出）；`FollowServiceImpl.java:504-523`。
- 问题：发布 RT 被扇出规模放大、行锁持有到提交；reminder 失败被吞成"有未读无提醒"半截状态。
- 建议：扇出改 afterCommit/异步；单订阅 event+reminder 同一子事务。

### F8【中·待确认】stageCode 恒 UNKNOWN、STAGE_CHANGE 事件从未产生
- 证据：`FollowServiceImpl.java:125,603`（仅有的两处 setStageCode 均为 "UNKNOWN"）；全模块无 setStageName/setBaseJson 写入点。

## 三、公告展示与安全面（子代理细读，关键条目已抽检）

### S1【中】公开响应直接下发未经校验的外站 URL，/go 中转存在后门
- 证据：`ingest/ExternalNoticeIngestServiceImpl.java:380-398`（validatePayload 仅 origUrl 做协议校验，pdfDownloadUrl/附件 origDownloadUrl 不校验）；`NoticeExternalServiceImpl.java:445,479`（原样下发）；`url/ExternalRedirectService.java:24-25`（类注释明确"不应被前端直接外链"）。
- 问题：采集侧投递 `javascript:`/`data:` 形态 URL 原样流入 @PermitAll detail；前端直连 origUrl 即绕过 /go 白名单。
- 建议：入库对全部 URL 字段做协议+域名白名单；公开 VO 只下发 `/go?url=` 封装链接。

### S2【中】ES 检索异常静默 fail-open（已抽检属实，注意是"有意但口径不一致"）
- 证据：`search/EsExternalNoticeSearchEngine.java:72-76`（catch→log→`return List.of()`）；`NoticeExternalServiceImpl.java:159-162`（空命中集→empty）；对比 ES 未启用引擎抛 `EXTERNAL_NOTICE_SEARCH_UNAVAILABLE`。
- 问题：ES 宕机=全站关键词搜索无报错返回"无结果"；同是"检索不可用"，一个报错一个静默，排障只能翻日志。
- 建议：区分"成功无命中"与"查询异常"，后者上抛 1-060-106-015 让前端提示"检索暂不可用"。

### S3【中】覆盖重投 updateById 忽略 null：内容形态切换（PDF↔HTML）旧字段残留并流入公开端与 ES（已抽检属实）
- 证据：`ingest/ExternalNoticeIngestServiceImpl.java:166-170,190`（MyBatis-Plus 默认 NOT_NULL 策略，null 字段不进 SET）；`indexer/EsExternalNoticeIndexNotifier.java:132-143`（contentText 优先取残留 extractionText/contentHtml）。
- 问题：HTML→PDF 重投后 contentHtml 残留 → ES 索引旧正文；PDF→HTML 重投后旧 PDF 链接与新 HTML 同时公开。与 §A6 同根（重投不清场），字段面不同。
- 建议：重投用 UpdateWrapper 显式 `.set(col, null)` 清理旧形态字段，与 §A6/§C2 一并修。

### S4【低】approve 请求线程内同步调 ES（10s 超时）——已知债务，注释自认；建议改异步旁路。
- 证据：`NoticeExternalServiceImpl.java:101-105`；`EsExternalNoticeIndexNotifier.java:74`。

### S5【低】净化白名单实际放行 `ftp:`（jsoup relaxed 自带，addProtocols 是追加非替换；已对 jsoup 1.22.2 反编译核实）
- 证据：`sanitize/HtmlSanitizer.java:34`。建议 `removeProtocols("a","href","ftp")`。

### S6【低】外站 `<img src>` 直出：访客 IP/时序对源站可见（追踪像素）
- 证据：`HtmlSanitizer.java:35`。建议代理化 img 或懒加载+no-referrer。

### S7【低·待确认】附件病毒门控只拦 INFECTED，PENDING（未扫描）照常下发
- 证据：`NoticeExternalServiceImpl.java:380-382`；入库即 PENDING（`ExternalNoticeIngestServiceImpl.java:370`）。需确认扫描闭环时序是否保证先于 approve；建议仅 CLEAN 放行。

### S8【低·待确认】allowedHosts 通配符 `*.gov.cn` 被解析成字面 host
- 证据：`url/ExternalRedirectService.java:118-128`。fail 方向安全但运维写法必错，建议启动时校验拒绝或显式支持 `*.` 前缀。

### S9【低】backfillPdfDownloadUrls 服务端直接 GET meta_json 任意 URL（管理权限门内，SSRF 面同 §B1）
- 证据：`NoticeExternalServiceImpl.java:503`。

### S10【低】ingest（机器高频写）与 approve/reject/take-down（人工审核）共用 `bidding:notice-external:update`
- 证据：`controller/admin/noticeexternal/NoticeExternalController.java:115,124,133,157`。采集凭据泄露=可自行 ingest+approve 发布。建议拆分权限点。

> 正面结论（不占条数）：/go 的开放重定向防护扎实（URI 严格解析、userinfo/IP 直连/协议相对路径均拒、no-store+no-referrer 真实设置）；ES keyword 无注入面；分页有 @Max 上限；公开 detail 严格校验 SOCIAL+ACTIVE；净化统一在读取侧且公开/管理口径一致；NoticeExternalDO @TenantIgnore 无租户拦截问题。

## 四、AI 抽取与正文结构化（子代理细读，关键条目已抽检）

### C1【高】60 秒 AI 长调用后整实体 updateById：并发下静默回滚审核结果（已抽检属实）
- 证据：`ai/NoticeExternalAiExtractServiceImpl.java:53`（selectById）→ AI 调用（yaml timeout-seconds=60）→ `:95`（`updateById(notice)` 整行写回）；`body/NoticeBodyStructureServiceImpl.java:55,92` 同模式。
- 问题：调用期间审核员 approve/reject（条件 patch 更新成功）→ AI 回写用旧快照把 status/auditStatus 整体盖回 → **审批被静默回滚，但关注扇出已发生**。
- 建议：改 LambdaUpdateWrapper 只更新 AI 相关列，或 version 条件更新。

### C2【高】源站内容更新未重置 AI 与正文产物，新旧内容错配（与 §A6/§S3 同根，一起修）
- 证据：`ingest/ExternalNoticeIngestServiceImpl.java:189`（仅置 extractionStatus）；`:173`（industryFlag 被置 null 但 MP 不清列，industryConfidence 残留旧值——flag/confidence 配对撕裂）。
- 建议：overwrite 统一清场：aiExtractionStatus/aiMetaJson/bodyBlocksStatus/bodyParserCode/bodyBlocksJson/industryFlag/industryConfidence。

### C3【中】扫描件 AI 转写在 60s 超时下基本不可用，且同步占死请求线程
- 证据：`ai/AiHttpSupport.java:128`；`ai/AiChatNoticeExtractor.java:105-107`（提示词要求转写全文）；`controller/admin/noticeexternal/NoticeExternalController.java:172-194`（同步执行）。
- 建议：AI 任务异步化或附件场景独立放大超时；错误码区分超时/输出非法。

### C4【中】admin-token 默认 `test1` 进配置兜底
- 证据：`application.yaml:158`（`${BIDDING_AI_ADMIN_TOKEN:test1}`）；`AiHttpSupport.java:134-136`。生产漏配环境变量=持弱凭据调管理面。建议默认空+enabled 时强校验。

### C5【中】tenant-id=1 兜底：无租户上下文的触发点会把 AI 会话/计费落租户 1
- 证据：`AiHttpSupport.java:49,77-80`。当前唯一触发点有上下文尚安全，但该类声明"供各类场景复用"。建议无上下文直接拒绝。

### C6【中】industryFlag 回写无来源标记、无区间校验
- 证据：`ai/NoticeExternalAiExtractServiceImpl.java:120-135`（无条件覆盖、confidence 不校验 0~1、解析失败时 flag/confidence 撕裂）。建议"人工已定不覆盖"+区间校验。

### C7【中】HtmlBodyBlocksParser 嵌套表格行重复/单元格错位
- 证据：`body/HtmlBodyBlocksParser.java:100,102`（后代选择器把内表行收进外表）。建议 `> tbody > tr` 直接子选择器。

### C8【中】发布时间解析取"窗口内第一个日期"，截止日/历史日误判
- 证据：`NoticePublishTimeResolver.java:72-79`（upper=now+1 天、无锚点词、无过去窗口下限）。与 §A5 叠加后 publishTime 失真面更大。建议锚定"发布/公告日期"词+收紧窗口。

### C9【中】PDF 三要素红线未在入库侧强校验
- 证据：`ingest/ExternalNoticeIngestServiceImpl.java:243-249`（注释宣称"缺 sha256 不入"，实际无条件入库）；validatePayload 未校验。建议 contentType=PDF 时强校验 sha256/size 非空。

### C10【低】bodyBlocksJson/extractionText 无长度上限（`NoticeBodyStructureServiceImpl.java:90`、`AiExtractServiceImpl.java:86`）——待确认 DDL 列类型，text 列有截断损坏 SUCCESS 状态风险。
### C11【低】PDFBox 全量内存无字节上限（`PdfBoxOpenDataLoader.java:63,69`）——与 §B3 一并加限。
### C12【低】项目名提取句读不含逗号、更正公告取旧编号（`NoticeProjectFieldExtractor.java:58,96-121`）。
### C13【低】Markdown 表格"全单元格非空"过滤静默丢行（`MarkdownBodyBlocksParser.java:111`）。
### C14【低】AI 解析失败不留原始应答（`AiChatNoticeExtractor.java:138-142`），重试无法定位漂移。
### C15【低】sendMessage 拼接 conversationId 未加引号（`AiHttpSupport.java:99,114`），非数字 id 造非法 JSON。

> 正面结论：状态机只有 NONE/SUCCESS/FAILED 三态且失败路径全部可重试，无卡 PENDING 死路；枚举无拼写错。
