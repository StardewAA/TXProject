# 投标流程与招标流程串联方案（2026-10-02）

> 背景：用户提出「投标流程和招标流程感觉没串起来」，并给出三个业务问题需要回答：
> ① 公告关联多个标段，投标人是**针对标段**投标的——他关注一个招标项目后，是不是每个标段都算一个投标？
> ② 给招标方发文件，是不是不应该只发一个文件？
> ③ 资格预审、上传标书，是不是不只上传一个文件？
> 本文档先实锤现状（表结构/接口/前端），再给出把业务串起来的方案与落地路线。

---

## 一、业务主线（一句话）

**招标侧**：项目 → 招标项目 → 标段（三级编号），公告挂在招标项目下、用 `BID_SECTION_CODES`（半角分号）关联多个标段；
**投标侧**：投标人以**标段（包）为投标单元**——关注招标项目，按标段逐个意向 → 报名 → 资格预审 → 审查 → 递交投标文件 → 开标/保证金/异议/合同，**一个标段一个投标档案、一个标段一个回写**；每步文件支持**多文件**（不只一个）。

## 二、现状实锤（表结构 + 数据 + 前端）

### 2.1 已有「按标段」的骨架（无需重建）

| 表 | 标段维度字段 | 说明 |
|---|---|---|
| `bidding_process_track`（投标流程跟踪） | `bid_section_code` ✓ | 每个标段一条：意向→报名→资质审核→待投标→已投标→终态，各阶段时间戳 + 状态机 |
| `bidding_prequal_apply`（资格预审申请） | `bid_section_code` ✓ | 按标段申请 + 审核结论 |
| `bidding_tender_doc_download`（招标文件下载回执） | `bid_section_code` ✓ | 下载回执记到标段 |
| `bidding_follow_item`（关注） | 三级键 `follow_type+follow_key` | PROJECT / TENDER_PROJECT / SECTION 三种跟踪键，关注=一条 |
| `bidding_attachment`（通用附件） | `biz_type + biz_code + attachment_type + seq` | **一对 N 多文件挂载机制已存在**（病毒扫描/顺序/分类） |

实测数据（2026-10-02）：`process_track` 3 条均为同一标段（`I6106002026000001001001`，招标项目 `I6106002026000001001`），状态 `BIDDED/PENDING_BID` —— 现在的数据形态**就是按标段一条**。

### 2.2 缺口（多文件化）

| 位置 | 现状 | 问题 |
|---|---|---|
| `process_track.document_file_id / document_name / document_hash…` | **单文件**字段（CA 签章件） | 投标人给招标方发文件不只一个（资质/技术/商务/报价…） |
| `prequal_apply.file_id` | **单文件** | 资格预审材料不只一份 |
| `bid_review_task.bid_file_id` | 单文件（审查=招标文件 vs 投标文件一对一） | 投多份文件时审查对象需扩展 |

> 即：**按标段回写的骨架已有，多文件是主要缺口**；bidding_attachment 的通用挂载能力可以直接复用，不必新建多文件表。

### 2.3 前端现状

- 门户 `portal/bidding/process.vue`（投标流程管理）：关注列表 + 按标段投标流程 + CA 签章 + 每步信息卡 + 公告详情入口（全部真实接口）。
- `portal/bidding/bidDocument.vue`（标书制作）、`portal/bidding/bidReview/*`（标书审查工作台）已存在。
- 关注**不自动建档**：用户显式点「意向投标」才建按标段的 `process_track`（口径：关注 ≠ 投标意向）。

## 三、业务怎么串（结论）

```
公告发布（挂招标项目，BID_SECTION_CODES=001;002;…）
        │
        ▼
投标人（门户/前台）按招标项目关注（follow_item 一条，跟踪键=TENDER_PROJECT）
        │ 点「意向投标」
        ▼
按标段展开：每个标段一条 process_track（bid_section_code=001 / 002 / …）
        │
        ├─ 报名投标（register）→ 资格预审（prequal_apply.bid_section_code，多文件附件）
        ├─ 资质审核（review，结论回写该标段）
        ├─ 待投标（pending_bid）→ 递交投标文件（**多文件** + 主件 CA 签章）
        ├─ 已投标（bidded）→ 开标（bid_opening/bid_section_code）→ 保证金/异议/合同（bid_section_code）
        └─ 每个状态变化 → bidding_process_event（标段留痕）+ follow_item_event（关注动态通知）
```

要点：
1. **投标单元 = 标段**：一个招标项目下 N 个标段 = N 条投标档案，各自走状态机、各自回写（数据模型现状一致）。
2. **关注一行、投标 N 行**：关注按招标项目（一条 follow_item），投标按标段（N 条 process_track）——「关注了招标项目，底下每个标段都想投」= 每个标段各建一条，互不干扰。
3. **公告 → 标段的桥**：公告 `fields_json.BID_SECTION_CODES`（001;002）是公告大厅「投哪个标段」与标段侧「哪些公告关联我」（契约 B 部分）的唯一定位键。
4. **多文件递交**：资格预审 / 投标文件 / 审查参考文件全部挂 `bidding_attachment`（biz_type + biz_code + attachment_type + seq），主表保留主件 file_id 字段作「CA 签章主件」兼容既有链路。

## 四、改造清单

### 4.1 后端（契约请求，前端不代改）
1. **投标文件多文件化**：`process_track` 保留 `document_file_id` 主件（CA 签章/哈希），另以 `bidding_attachment(biz_type='BID_TRACK_FILE', biz_code=track.id)` 挂全部文件；`attachment_type` 字典扩展：资质文件 / 技术标 / 商务标 / 报价单 / 其他。
2. **资格预审多文件化**：`prequal_apply.file_id` 保留主件，`bidding_attachment(biz_type='PREQUAL_APPLY_FILE', biz_code=apply.id)` 挂材料集；上传接口放开一次多文件（复用 `/bidding/file/upload` + 批量绑定）。
3. **审查多文件化**：`bid_review_task` 增加 `bid_files_json`（或走 attachment），审查引擎按文件集逐份解析合并结论（现有 `bid_review_content/issue` 已可按任务关联）。
4. **按标段回写确认**：`process_track / prequal_apply / bid_opening / bid_deposit / objection / contract` 全部已有 `bid_section_code`，契约核对一遍即有结论（现状已达标）。

### 4.2 前端
1. 门户 `process.vue`：按标段列表已具备；补充「该标段的资格预审/投标文件**多文件清单**」展示与上传（attachment 挂载），主件显示 CA 签章摘要。
2. `bidDocument.vue`（标书制作）：多文件分段上传（技术标/商务标/报价单），递交时逐文件 CA 签章（bidding_ca_seal 已 per-file）。
3. 公告大厅/详情：标段编号显示短序号（001/002，一个编号一行，本轮已改）；点「投这个标段」直达该标段的投标档案。

## 五、落地顺序

1. 契约文档：`txgy-module-bidding/docs/电子证照前前端契约/` 新增「投标文件与资格预审多文件化」请求（file_id 主件 + attachment 多文件清单，后端补批量绑定接口）。
2. 前端：先做展示层（标段投标档案页展示多文件清单），再补上传交互。
3. 验证：构造一条公告关联 2 个标段 → 关注招标项目 → 两个标段各建投标档案 → 每个档案传 3 份文件 → 状态机走通 → 后台/门户双向可见。

## 六、验证口径

- `GET /bidding/process-track/my` 返回按标段多行，每行可携带多文件清单；
- 关联多标段的公告在两个标段的投标档案里都能看到（契约 B 部分落地后精确匹配）；
- 资格预审/投标文件上传多份后，管理端审查任务能看到全部文件并按文件集审查；
- 文件病毒扫描/CA 签章按文件逐份生效（既有机制，不回归）。
