## 2. 缺口①~③修复方案（内部公告订阅闭环）

### 2.1 触发点与事件语义
- 入口：FollowService.handleInternalNoticeChanged(action, noticeId, title, publisherName, projectName, projectCode, version)，由公告服务在事务内调用（失败仅记日志，不阻断发布）。
- 匹配：**公告级**订阅（ANNOUNCEMENT，targetKey=公告 id）＋ **项目级**订阅（PROJECT，targetKey=projectCode）；同一用户多订阅只提醒一次（按订阅去重）。
- 事件键：`user-item-INTERNAL-noticeId-{NOTICE_PUBLISHED|NOTICE_UPDATED}-version`——**版本号进事件键**：
  - 同版本重放/重发：幂等跳过（不重复提醒、未读不叠加）；
  - 内容更新出新版本 v2/v3…：产生新动态，订阅者 timeline 有新提醒；
  - 撤回重发同版本：不重复提醒（见核查点⑥）。
- 触发：
  - publishNotice（DRAFT→PUBLISHED，含撤回后重发）：扇出 PUBLISHED，版本=当前最新正文版本；
  - updateNotice：仅当**原状态=PUBLISHED** 且正文实质变化（追加了版本）→ 扇出 UPDATED（版本=新版本号）；
  - createNotice（DRAFT）、unpublishNotice、deleteNotice、未发布状态的编辑：**不扇出**。

### 2.2 正文版本与“实质变化”口径
- 追加版本条件沿用 NoticeContentUtils.shouldAppendVersion：去除首尾空白后比较，内容不同才追加（避免“存了个带空格的正文”产生无意义新版本）。
- 版本语义：v1=首次保存（create/首次编辑都走版本演进）；发布扇出用的是**发布时刻的最新版本**；后续每产生一次实质变更版本号+1。
- 业务防骚扰结论：订阅者只收到“发布”与“已发布内容实质更新”两类提醒；中间草稿过程与无实质变化的保存一律不打扰。

### 2.3 订阅者视角的初始反馈（与外部公告对称）
- 关注一个**已发布（PUBLISHED）**的内部公告：立即种一条**已读** NOTICE_PUBLISHED 初始动态（seedKey：`user-item-INTERNAL-noticeId-seed`），timeline 非空、未读角标不增加；幂等（重复关注/并发双写只落一条）。
- 关注未发布（DRAFT/UNPUBLISHED）内部公告：不种初始动态，等发布扇出再提醒（与外部 NEW 关注等 approve 扇出口径一致）。

### 2.4 读路径双源（公告级关注行/单点状态）
- “我的关注”列表与单点关注状态查询，公告级行按 id 先查外部（G 轨），未命中再查内部（T 轨**同租户**）：
  - 名称快照补全：displayName/issuerName（内部=标题/发布单位）；
  - 展示状态与可达性：`noticeStatus` + `available`（EXTERNAL=ACTIVE、INTERNAL=PUBLISHED 才可跳平台详情；否则前端隐藏详情跳转按源站原文兜底）。
- 时间线事件同规则：INTERNAL 事件反查本租户内部公告状态。

### 2.5 改动文件
- service/notice/NoticeServiceImpl.java：appendContent 返回新版本号；publishNotice/updateNotice 按上述触发点扇出（try/catch，失败不影响公告本身）。
- service/noticefollow/FollowService(Impl).java：新增 handleInternalNoticeChanged（建/恢复关注行 → 版本幂等 → 刷 latestDynamicTime/unread+1 → IN_APP PENDING 留痕）；双源行映射/补名/状态；内部公告 seed 初始反馈。
- 测试：FollowServiceImplTest +6、NoticeServiceImplTest +8（发布扇出版本语义、UPDATED 扇出、草稿不扇出、版本幂等重放、双源行状态、内部 seed、部分更新语义 ×3），全量 **272 用例全绿**（2026-09-08 增量回溯 +3 → 274）。

### 2.6 部分更新语义修复（E2E 实测发现，同批修复）
- 现象：E2E 只提交正文+标题保存时，updateNotice 先把 internalFlag 翻回 false（企业内部公告若走此路径会变公开可见）、并把 projectCode/projectName/publisherName/pdfFileId 在内存中置空——updateById 因 null 不写库，但关注扇出的 projectCode 为空 → 项目级（PROJECT）订阅收不到 UPDATED 提醒；pub 路径若复用同对象还会误伤。
- 修复：applyBase 拆分为 applyBaseCreate（新建全量+缺省，行为不变）与 applyBaseUpdate（部分更新：仅覆盖显式提交字段；internalFlag/publicLevel 等只在 VO 显式传值时才改动）。
- 口径：更新=提交什么改什么；未提交=保留。显式传 internalFlag=false/publicLevel=值 仍可生效（企业内部→公开的转换操作不受影响）。前端回填全量表单的既有行为无感知变化。

## 4. 建议的验收口径（给测试/前端）

1. 招标人发布一条内部公告 → 关注该公告/关注其 projectCode 的用户在 1 次轮询内收到动态：公告级=NOTICE_PUBLISHED 未读+1；项目级=同事件（行快照显示项目名）。
2. 已发布公告改正文保存 → 关注者收到 NOTICE_UPDATED（新版本）且**未读只加一次**（同版本重复保存/重放不叠加）。
3. 草稿状态多次编辑 → 全程无动态；撤回（UNPUBLISHED）后再发布且正文未变 → 无新动态（不打扰）；正文变了 → 有新动态。
4. 新用户关注已发布内部公告 → 立即有 1 条**已读**初始动态（timeline 非空、未读角标 0）。
5. 内部公告 UNPUBLISHED/ARCHIVED 后：关注行的 noticeStatus 变化、available=false（前端隐藏“查看详情”）。
6. 时间字段一律 dayjs(Number(epochMs))，不要 new Date(Number) 以外的处理。
