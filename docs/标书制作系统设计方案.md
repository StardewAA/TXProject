## 1. 概述

### 1.1 背景与定位

标书制作是招投标平台的核心业务能力：用户在门户上传招标文件后，系统自动完成「解析招标要点 → 生成章节大纲 → 撰写正文 → 回填投标文件模板」，产出可直接交付的 .docx 标书。本设计覆盖这条链路的全部三个落点：

- **门户层**：标书制作页 / 标书工坊（BidStudio），位于 `txgy-ui-admin-vben/apps/web-antd/src/views/portal/bidding/`；
- **服务层**：Java 招投标模块 `txgy-module-bidding`（端口 48110，容器内 48080），承担台账、检索、契约、权限与租户；
- **执行层**：Node 标书智能体 `services/bid-agent-service`（端口 8199），承担任务编排、LLM 调用、模板回填与交付导出。

### 1.2 设计目标

1. **零幻觉**：标书正文与字段取值必须可溯源，杜绝编造（检索未命中即转人工，确定性字段不经模型）。
2. **全文一致**：报价、工期、资格信息在封面/投标函/报价表/正文之间强制同值（废标红线）。
3. **可审计**：每个章节、每个字段都能追溯到来源块（sourceBlockIds）与取值通道。
4. **可重入**：任务可中断、可回退、可单章重跑，进程重启后状态可对账恢复。
5. **租户隔离**：门户个人租户、企业租户、平台租户三轨分治，任务与材料互不可见。
6. **前后台解耦**：前台只调 app-api，不感知执行底座与模型密钥；底座可独立替换。

### 1.3 范围界定

本方案覆盖：材料入库（知识库）、一键生成（PARSE→OUTLINE→DRAFT→FILL）、模板回填与导出、任务状态管理与人工确认、智能体配置（模型/技能/MCP）。

不覆盖（相邻域，各有独立方案）：外部公告采集与检索（ES）、投标流程跟踪（前端本地状态机）、合规审查、企业主体/人员/资质台账。

### 1.4 术语

| 术语 | 含义 |
| --- | --- |
| TENDER / FACT / TEMPLATE | 材料三类：招标文件（必绑标段）/ 企业资料（跨标段复用）/ 技术母本 |
| PARSE / OUTLINE / DRAFT / FILL | 生成四阶段：解析招标要点 / 章节大纲 / 逐章撰写 / 字段回填 |
| HIL | Human-in-the-Loop，人工确认闸门（ask-user 工具 + /confirm 应答） |
| 契约端（contract） | Java 侧供 Node 机对机调用的接口面，`/admin-api/bidding/bid-agent/contract/**` |
| 台账 | Java MySQL 中的任务/材料/切片/草稿记录；与 Node 文件态互为影子 |
| 事实卡 | 项目事实卡（`项目事实卡.md` / `bidding_bid_project.facts_json`），全文一致性的单一数据源 |

### 2.2 分层职责

| 层 | 负责 | 明确不负责 |
| --- | --- | --- |
| 门户层 | 上传与登记、发起生成、进度展示、HIL 应答、产物下载 | 直接调 LLM；直连 8199；感知模型密钥 |
| Java 服务层 | 台账 CRUD、材料/切片、检索（向量+BM25+rerank）、契约端回调落库、权限/租户、产物回收入 infra 文件服务 | 长流程编排、直接调 LLM 写正文（契约文档 §1 明确「不做」） |
| Node 执行层 | 任务状态机、LLM 编排与工具循环、HIL、检查点、四通道取值、模板回填、docx 导出 | 台账持久化（回调 Java）；文档解析/向量化（交给 Java） |

### 2.3 设计原则

1. **可靠性放底座，业务零侵入**：Java 只做 CRUD/台账/检索基础设施，全部 Agent 编排逻辑（状态机/HIL/检查点/重试/可观测）在 Node 层。
2. **检索是写作的前提**：正文 claim 必须携带 `sourceBlockIds` 且存在于检索证据中；检索 `hit=false` 时硬性转人工，不得继续生成（写入接口契约的硬约定）。
3. **确定性优先于生成**：能确定算出来的值绝不交给模型（见 §5.2 四通道取值）。
4. **单一数据源**：同名字段合并共用一处取值（`mergeFields`），事实卡为全文一致性锚点。
5. **双保险状态同步**：Node 主动推影子状态（可关）+ Java 查询时拉取式懒同步（无定时轮询任务）。
6. **幂等无处不在**：台账写接口、契约端写接口、章节回写、任务影子、running 唯一键，五层幂等防线。

## 4. 核心业务流程

### 4.1 材料入库链路（知识库）

```
前端上传（BidStudio，招标文件必填 + 补充文件）
  → POST /bidding/file/upload               返回全局唯一 fileId（落库权威键，url 仅供预览/取内容）
  → POST /bidding/bid-agent/material/save   登记台账 bidding_bid_material
      · 招标文件 docType=TENDER，必绑 bidSectionCode（标段隔离口径）
      · 补充文件 docType=FACT（企业资料，跨标段复用）
  → 入库（Java 内闭环，不经 Node）：
      BidIndexServiceImpl：下载文件（fileDownloadHost 重写支持容器内回拉）
        → Tika 解析 PDF/docx → 切分（块级 sourceBlockIds 溯源 id）
        → DashScope text-embedding-v3（1024 维，batch 10）→ 写入 Qdrant
        → 切片台账 bidding_bid_agent_chunk（与向量库一致，供前端透传展示）
  → index_status：0 待入库 / 1 已入库 / 2 失败（失败写明原因，可 /material/reindex 重建）
```

边界：扫描件无 OCR 能力；`bidding.bid-agent.ai-enabled=false` 时入库跳过并写明原因。

### 4.2 一键生成主链路（PARSE → OUTLINE → DRAFT → FILL）

```
POST /app-api/bidding/bid-agent/task/generate   body: projectId? / bidSectionCode? / tenderMaterialId?
     / templateMaterialId? / docCategory(technical|business) / remark?
  → Java BidAgentTaskServiceImpl：校验前置条件（标段已有入库 TENDER 材料，否则 1_060_121_094；
    底座在线，否则 1_060_121_086）→ 判重（uk_running 唯一键兜底并发）→ 写台账
  → BidAgentOrchestratorClient.createTask(taskType=generate) → Node POST /agent/tasks
  → Node 队列：并发上限 MAX_CONCURRENT_TASKS=2 + 项目亲和锁（同 tenant+project 串行，
    避免并发覆盖共享事实卡/大纲）→ 拉取 Java /contract/agent-runtime（模型/提示词/技能/工具白名单/MCP）
  → generateTask 串联四阶段（进度映射 0.05→1）：
     ① PARSE    必检检索（不经模型）→ LLM 抽取废标条款/关键约束/全局事实
                 → 项目事实卡.md + 招标文件解析.md + tenderParse.json → /contract/project/facts 回写
     ② OUTLINE  LLM 规划章节树（逐条承接评分点/废标条款）→ outline.json → /contract/outline 回写
     ③ DRAFT    每节点 SELECT→RETRIEVE→WRITE→VERIFY→COMMIT（§5.5）；正文回写 /contract/draft/chapter
     ④ FILL     模板字段扫描 → 同名字段合并 → 四通道取值（§5.2）→ 分批生成（每批 15 字段）
                 → 事实卡交叉比对 → 回填（真实模板无 SDT 时跳过 Java 回填，由导出阶段完成，§5.3）
  → 导出 bidDocxExporter 三路径（§5.4）→ Java pullArtifact 拉 docx 入 infra 文件服务
  → 前台 GET /task/artifact 拿 artifactUrl 下载
```

任务状态：`PENDING / RUNNING / SUCCEEDED / FAILED / CANCELED`，带 `currentStep`（PARSE/OUTLINE/DRAFT/FILL）、`progress`（0~100）、`openQuestionsJson`（待确认清单）、`errorMessage`。

### 4.3 状态同步（双保险）

1. **影子推送**：Node 每次 patch 状态后 POST `/contract/task-status` 落 `bidding_bid_task_shadow`（`uk_task_id` 幂等，progress 为 0~1 小数）。
2. **拉取式懒同步**：Java 查询任务台账时向 Node `GET /agent/tasks/{id}` 拉最新状态落 MySQL（含 pendingQuestions / result.openQuestions / usage.totalTokens），无定时轮询任务。

### 4.4 前端交互

- **轮询而非 SSE**：BidStudio 以 3s 起、指数退避至 30s 轮询 `GET /task/page`；有 HIL 待确认问题时放慢到 15s；无 RUNNING/PENDING 任务即停表。轮询请求带 `X-Silent-Error` 头静默（错误由全局拦截器统一处理）。
- **HIL 人工确认**：任务进入 `awaiting_human` 后 `openQuestionsJson` 非空 → 前台弹确认框 → `POST /task/confirm` 回填答案续跑。**注意**：当前「一键生成」在 Node 侧自动答复（确认/保留/跳过），该旁路是开放决策点（§10.1）。
- **产物消费**：SUCCEEDED 后「下载标书」（artifact）+「查看章节」（outline：章节树+正文）；FAILED 显示 errorMessage + 重试；CANCELED 可重试。

## 5. 关键设计

### 5.1 检索体系（向量 + BM25 双通道）

**入库侧**（§4.1）已把切片写入「Qdrant 向量 + MySQL 切片台账」双份；向量 metadata 携带完整溯源：`tenantId / projectId / docType / bidSectionCode / sourceDocName / chapterPath / pageNo / sourceBlockIds`。

**检索侧**（`BidRetrievalServiceImpl`，Java 内闭环）显式编排：

```
查询 → 双通道粗召回：向量（Qdrant） + 关键词（BM25 = MySQL FULLTEXT ngram）
     → RRF 融合（k=60，候选数 = topK × candidateFactor=4）
     → DashScope rerank（gte-rerank-v2）
     → 阈值闸门（min-score 0.35）
     → 必检通道（mandatory 词条，如「安全生产许可证」必须命中）
     → 溯源标注（matchedBy = vector / bm25 / hybrid / rerank）
```

- 云端（百炼）故障时**自动降级纯 BM25**，彻底失败才 `hit=false` 转人工（编排不硬失败，原因落 WARN）。
- 后台「召回验证 / 精准度测试」走严格口径（原样抛 `1_060_121_070` 云端检索不可用），避免专员把「云端没配好」误判成「资料没入库」。
- 精准度测试（golden set）：`bidding_bid_eval_case` 用例 + `/eval/run` 跑批，按 `expectBlockIds`（溯源块号）或 `expectKeywords` 判定命中，`missReason` 区分「资料没入库」与「切片/口径不对」。
- 检索开关：`bidding.bid-agent.retrieve.bm25-enabled`（默认 true）可回到「仅向量 + rerank」。

### 5.2 零幻觉保障（四通道取值 + claim 校验）

**字段取值四通道**（`resolveFieldValues` / `fillTask`，零幻觉核心）：

| 通道 | 含义 | 是否经模型 | 示例 |
| --- | --- | --- | --- |
| `MANUAL` | 签字/盖章/法人代表，Agent 全程不碰 | 否 | 签字栏 |
| `COPY_FACT` | 与企业事实同名精确命中，照抄原文 | 否 | 企业名称、资质编号 |
| `DERIVE` | 确定性换算：报价大写走央行规则（万元→元 ×10000）、工期由开竣工日期推算 | 否 | 投标报价（大写） |
| `GENERATE` | 其余字段走「检索 → 生成 → 校验」闭环 | 是 | 技术方案描述 |

「未找到/未命中/待补充」占位值被过滤，禁止入模板（防脏值）。生成字段回填前与项目事实卡交叉比对（`checkAgainstFactsCard`），数字不一致即告警。

**正文 claim 校验**（`draftTask.verifyDraft`）：

1. 每个 claim 必须携带 `sourceBlockIds` 且存在于本轮检索证据中；
2. 正文中所有事实性数字必须在「检索证据 ∪ 事实卡」集合中查得到（集合级比对），否则触发修复轮（最多 3 次）；
3. 2-gram 重合度 < 0.35 提示人工复核；
4. 二次不通过挂 HIL 转人工。

**提示词层反幻觉硬约束**（`orchestrator/prompts.ts`）：6 条硬约束注入 system prompt；检索证据以 `<<<EVIDENCE id=...>>>...<<<EVIDENCE_END>>>` 包裹注入；疑似指令注入文本（检索内容里的「忽略以上要求」等）被正则标注警告、不执行。结构化输出经自研 JSON Schema 校验器守门（`lib/jsonSchema.ts`），失败进修复轮。

### 5.3 模板回填引擎

真实投标模板不含 Word 内容控件（SDT），Java 侧 docx4j 的 SDT 扫描实际空转；**真正生效的是 Node 侧回填引擎**，在导出阶段执行（`fillTemplate`）。

**两种模板形态自动识别**（`hasFillBookmarks` 检测非 `_` 开头书签）：

| 形态 | 模板 | 机制 |
| --- | --- | --- |
| 书签占位（变量字典方案） | `templates/投标文件_书签模板.docx`（1,344 书签 / 1.1 MB XML） | `BOOKMARK_STD_MAP` 把 60+ 标准字段映射到书签名（bid_no→招标编号、bidder_name、bid_total_upper、quote_*、staff_*、unit_cost_* 等）；基础变量名自动覆盖 `_N`/`_appendix` 变体；日期拆 year/month/day + full_date |
| 标签+留白锚点（默认） | `templates/投标文件模板.docx` | `TEMPLATE_FIELDS` 24 个标准字段按锚点文字定位（before/after/occurrence，如「RMB￥」第 1 次）；完整日期回填后自动吃掉「____年____月____日」骨架（`consumeDateSkeleton`） |

**书签引擎适配 8 种区域形态**（`bookmarkFill.ts` `fillRegion`）：

1. 留白区（书签内纯空白 run → 填入第一个空白 run）
2. 空书签（表格数据格 → 插入带段落格式的取值 run）
3. 示例区（「无」「长期」「合格」等示例字 → 整区替换）
4. 占位符区（「ｘｘｘ」→ 仅替换占位 run）
5. 括号区（「（  ）日历天」→ 括号对换为取值）
6. 标签区（书签只包住「××：」→ 填同段前导空白）
7. 日期骨架（非空白文本只含年/月/日 → 填值后吃骨架）
8. 标签链（「____（盖章）」单 run 混排 → 只填 run 内留白段）

**版式保护**：回填只编辑 `word/document.xml`，封面/目录/页眉/页脚/表格/样式原样保留；实测回填前后 PDF 页数不变（35 页）。计价表分表模板（1–12 号）已实测全量回填零跳过。

**坑位沉淀**（设计约束）：封面与目录书签复用 id 1–13（配对=每个 start 向后找第一个同 id end）；`<w:rPr/>` 自闭合不被 run 正则匹配需单独处理；表头标签格（姓名/年龄）书签误包标签需跳过。

### 5.4 导出三条递降路径（`bidDocxExporter`）

1. **FILL 阶段已回填件**（`deliver/filled-template.docx` 存在则直接交付，最优先）；
2. **模板回填**（`deliveryMode: template`，正式交付）：书签模板或锚点模板回填 + 章节正文插入（定位「六、施工组织设计」段落后插入 markdown 转换的 body XML）；交付件剔除「溯源引用/待复核提示」内部小节但保留待复核标注；
3. **内置排版兜底**（`deliveryMode: preview`）：零依赖 markdown→OOXML 排版引擎（封面/TOC 域/PAGE 域/updateFields），仅供内部审阅。

PDF：默认关闭；`PDF_VIA_WORD=true` 时 PowerShell 调本机 Word COM 转换。

### 5.5 章节级子任务与检查点（draftTask）

- 每个大纲节点独立执行 `SELECT → RETRIEVE → WRITE → VERIFY → COMMIT` 五个子步骤；
- **断点续跑**：检查点落盘（`sessions/{taskId}/checkpoints.json`），重启/回退后跳过已 COMMIT 章节（`committedNodeIds`）；
- **单章失败隔离**：整章检索未命中不中止全流程——写占位正文 + `status='review'` 标注 + 继续后续章节；
- **回退重跑**：`rollback {toPhase, keepSession, nodeId}` 截断检查点后重新入队；generation 代号防止旧协程改写新状态。

### 5.6 多租户与鉴权（三轨分治）

**三个接口面的鉴权口径**：

| 接口面 | 前缀 | 鉴权 | 租户口径 |
| --- | --- | --- | --- |
| 前台/门户 app-api | `/app-api/bidding/bid-agent/task/**` | 登录态 `isAuthenticated()`（细分权限码可选） | 从登录态取租户，跨租户任务按「不存在」处理 |
| 后台 admin-api | `/admin-api/bidding/bid-agent/**` | 权限码 `bidding:bid-agent:*`（角色界面勾选，super_admin 自动可见） | 当前租户 |
| 契约端 contract | `/admin-api/bidding/bid-agent/contract/**` | `@PermitAll` 免登 + `BidAgentKeyFilter` 校验 `X-Agent-Key`（order=-200 先于 Spring Security） | 请求不带 tenant-id 头：控制器 `@TenantIgnore`，租户由参数/请求体显式传入，服务层 `TenantUtils.execute` 再开启过滤；tenantId 缺失即拒绝（不静默落 0） |

**平台默认 + 租户覆盖**（智能体配置）：5 类智能体基线挂在 `tenant_id=0`（平台默认）；读取时本租户优先、平台默认兜底；保存时本租户无覆盖则先复制平台默认一份再改（新租户不会看到空列表，也不污染平台默认行）。

**Portal 租户拦截器**（`BidAgentPortalTenantInterceptor`）：个人/平台租户（tenant=0）在门户用标书工坊时，preHandle 把执行上下文切换到 `bidding.bid-agent.portal-enterprise-tenant-id` 配置的企业租户，afterCompletion 恢复；拦截 `/bidding/bid-agent/**` 但排除 `/contract/**`。

**底座侧租户隔离**（Node）：`AGENT_API_KEYS=key:租户A|租户B` 可把 key 绑定租户；跨租户任务按 404 掩盖（不暴露存在性）。

### 5.7 智能体平台化（配置管理）

- **智能体配置**（`bidding_bid_agent`，`uk_tenant_task_type`）：PARSE/OUTLINE/DRAFT/FILL/REVIEW 五类任务各自的 systemPrompt/model/temperature/knowledgeRoleList/工具白名单；`editable=0` 为 Agent 侧内置只读。
- **云端模型**（`bidding_bid_agent_model`）：全局一套 + 每智能体覆盖模型名/温度/max-tokens；运行期经 `/contract/agent-runtime` 下发覆盖底座 `.env`。
- **技能**（提示词增强包）：新智能体按任务类型自动挂载；技能片段注入 system prompt。
- **MCP 服务**：外部 server 登记 + 连通性自检（tools/list + tools/call）+ 单次试调；运行期注入工具清单。
- **试跑**（`/agent/preview`）：`taskType + input + withRetrieve` → `promptSource(BID_AGENT/BUILT_IN) + output`，脱离平台 AI 模块、直接走本模块自持云端模型。

## 9. 已知风险

| 风险 | 等级 | 说明与缓解 |
| --- | --- | --- |
| 回填性能 | 高 | 1,344 书签 × 1.1 MB XML 的正则全量扫描 ≈ 10⁹ 字符操作，量级 O(书签数 × XML 长度)。缓解方向：书签配对单遍建索引、回填统一倒序批量应用、或事件式流式改写 |
| HIL 旁路 | 中 | 一键生成自动确认导致「待复核」章节未经人工直接入交付件（§10.1 二选一） |
| 多副本部署 | 中 | HIL 为进程内 Promise、SSE 为内存事件、检查点在本地文件——当前单实例设计；多副本需共享应答通道 + 集中任务存储 |
| 任务元数据在文件不在 MySQL | 中 | 底座任务事实源是 task.json，Java 台账靠懒同步补偿；底座丢盘即任务状态失真（生产要求挂持久卷） |
| 扫描件无 OCR | 中 | 图片型招标文件无法解析入库 |
| 云端配额与模型授权 | 中 | 生成 key 仅授权 qwen3.5-flash；embedding/rerank 独立 key。云端不可用时检索降级 BM25、生成侧需人工兜底 |
| 工作区重构进行中 | 低 | 独立 fill 任务已从 registry 下线（fillTask.ts/bidDocx.ts 删除），回填收敛到导出阶段；注意 generateTask 对旧模块的引用需同步清理后编译 |

## 10. 开放决策与演进路线

### 10.1 开放决策

1. **HIL 闸门口径**（BUG-04）：方案 A——一键生成在关键闸门（至少 DRAFT→FILL 之间）恢复人工确认，前台按 `awaiting_human` 正确显示确认入口；方案 B——明确「一键生成不设人工确认」为产品口径，则移除前台确认按钮与 HIL 弹窗，并在交付件中对「待复核」章节做显著标注。当前代码状态：Node 自动答复 + 前台确认 UI 并存，需产品二选一收口。
2. **切片在线编辑**：本期只有「查看 + 重建索引」；在线编辑需与向量库同步改写（删向量→重嵌入），接口预留为下一迭代。
3. **按标段过滤检索**：`bidSectionCode` 已在台账与用例维度生效；检索侧按 projectId/projectCode 过滤，编号映射待补齐。

### 10.2 演进路线（据《标书生成流程方案对比分析-2026-09-21》结论）

拟建的「子模板 + 子 Agent + 评分门禁 + 拼接」方案方向正确，但「拆成独立 docx 再拼接」是成本与风险的集中点（docx 合并引擎 10–20 人日，且现有技术栈无 merge 能力）。**推荐折中方案，约 3–5 周可控落地**：

1. **保留**：单模板 + 单交付件（保住跨字段一致性与格式保真两个不可退让的底线）；
2. **吸收 1**：子 Agent → 章节级子任务（已有：检查点、单章失败隔离、review 标注；强化点=按章节过滤检索证据与评分点的上下文裁剪）；
3. **吸收 2**：评分门禁 → 确定性校验套件（书签覆盖率 30% / 必填红线字段 25% / 数值一致性 25% / 引用溯源 10% / 格式保真 10%；低于阈值时列明扣分项，不做模糊打分）；
4. **吸收 3**：回填性能优化（最实在的风险项）；
5. 若坚持多 docx 拼接路线，先单独立项做合并引擎 PoC（两个含表格与页眉的样例 docx 验证可行性）。
