## 1. Problem Statement（不含任何解决方案）

### 1.1 现状

污染判定记录（`mes_set_pollution_check`）当前是**脱离库存独立手工新建**的自由文本行。前端 `safetyEnv/pollutionCheck/data.ts:84-175` 的新建表单里，`itemName`（必填）、`itemCode`、`itemSpec`、`weight`、`bizNo`、`batchNo` **全部是可打字的 Input**，`batchNo` 没有选择器。

同一份数据在 wm 侧已经是权威的：入库单行 `mes_wm_item_receipt_line` 带 `item_id` / `batch_id` / `batch_code` / `lot_number`，库存 `mes_wm_material_stock` 带 `item_id` / `batch_id` / `batch_code` / `quantity` / `area_id` / `receipt_time`。

**于是产生了一份权威数据的自由文本副本**，两者靠字符串碰。

### 1.2 实测证据

全库 69 条在用判定记录（`deleted=0`）的关联率：

| 关联目标 | 能对上 | 比例 |
|---|---|---|
| `mes_wm_batch.code`（批次） | 37 / 69 | **54%** |
| `mes_md_item.code`（物料） | 28 / 69 | 41% |
| `mes_wm_item_receipt.code` / `product_issue.code`（单号） | 10 / 69 | **14%** |
| `ai_result = UNCERTAIN` | 37 / 69 | 54% |

分租户看，**32 条回不到批次**的构成：

| 租户 | 判定总数 | 批次能对上 | 无批次号 |
|---|---|---|---|
| 1（西安鸥鹏） | 25 | 13 | 12 |
| 2010（华瀚节能） | 44 | 24 | 20 |

租户 2010 的样本里 `item_name` 直接是 `E2E冻结用例料`、`e2e无签物料`、`e2e附件用例物料`，`batch_no` 出现 `PC`（id=1220）这种无意义值 —— 是端到端用例残留。

索引侧：`mes_set_pollution_check` **只有 `PRIMARY(id)` 和 `uk_record_no(record_no)`**，`batch_no` / `biz_no` 上无索引，按批次反查是全表扫。

### 1.3 谁在疼

| 角色 | 疼在哪 |
|---|---|
| 环保管理员 | 判完了不知道判的是库里哪一桶；想出库放行时对不上号 |
| 仓库 | 在库列表（`wm/materialstock`）**没有任何污染字段**，看不出哪批被管控 |
| 合规审计 | 46% 的判定无法证明对应某个真实批次，台账链断 |
| 管理 | 无法回答"全库有多少批次该检没检" |

### 1.4 目标（可测）

把"环保检测"从**一张独立表单**变成**库存属性的一层视图**：任何一条判定都能回答"它判的是哪一批在库/入库物品"，且能反向从任何一批在库物品回答"它检过没有、检成什么、现在被怎么处置"。

## 2. 需求层次（MoSCoW）

| 级别 | 需求 |
|---|---|
| **Must** | 判定记录锚定 `batch_id`；在库/入库物品上有发起环保检测的入口；在库视图能看出某批次的污染与检测状态；四项操作可在该视图上执行 |
| **Must** | 存量记录区分「已关联 / 未关联」，未关联的显式可见且可筛 |
| **Should** | 全库体检：按判据算出待检清单，支持批量发起；合规看板（覆盖率 / 超期未检 / 异常率） |
| **Should** | 批次全链档案：采购入库 → 生产领用 → 中间废弃物 → 成品去向，每节点带判定 |
| **Could** | 定时自动体检（受 §3 定时任务约束限制，见 §5.7） |
| **Could** | 危化品相容组禁配校验（原受 §3 档案对不上物料限制，见 §5.6）——**2026-09-11 已实现**，见 §4.3.1 |
| **Won't（本期）** | 包装破损检测；改造 wm 既有表结构；改判据为每物料一套周期 |

## 5. 设计

### 5.1 根因与核心决定

**根因**：判定记录没有指向批次的外键，只能复制 `batch_no` 字符串，所以判定与库存是两份互不约束的数据。

**核心决定：判定行锚定 `batch_id`，`batch_no` 降级为显示快照。**

这与本模块既有约定一致 —— `mes_set_pollution_check.location` 已是 `location_id` 的名称快照（见其列注释「`location` 为其名称快照」）。照抄这个模式，不发明新约定。

**附带收益**：join 从字符串等值变为整数主键等值，**顺带消灭 F15 的排序规则分裂问题**（不再需要 `COLLATE`），也消灭 F14 所说"字符串碰不上"的一整类故障。

### 5.2 数据模型变更（全案唯一一处 schema 变更）

```sql
ALTER TABLE `mes_set_pollution_check`
  ADD COLUMN `batch_id` BIGINT NULL COMMENT '批次编号（mes_wm_batch.id；空=历史未关联记录）' AFTER `biz_no`,
  ADD INDEX `idx_batch_id` (`batch_id`);
```

规则：

- **可空**。存量 32 条未关联记录保持 `NULL`，不臆测回填（依 Q4 决策「保留 + 标未关联」）
- 新记录**必须**带 `batch_id`（由入口保证，见 §5.3）
- `batch_no` 保留为显示快照，不删
- `idx_batch_id` 是必需的：当前只有 `PRIMARY` 和 `uk_record_no`，新视图按批次 join 会全表扫

### 5.3 三个检测入口

判定逻辑、复核、台账、追溯**一律复用**，只换锚点来源。

| # | 入口 | 锚点来源 | 改动 |
|---|---|---|---|
| E1 | 库存台账列表 `wm/materialstock` 加行操作「环保判定」 | 该行 `batchId` | 复用 `judge-modal`，payload 由 batch 构造 |
| E2 | 在库环保视图（新页）行操作 + 批量 | 选中行 `batchId` | 新页，见 §5.4 |
| E3 | 既有单据行入口（itemreceipt / productreceipt / productissue） | 单据行 | **不动**。但 `judge-modal` 内部补 `batchId` 传递 |

`judge-modal.vue` 的改造（最小）：

- `JudgePayload.lines[]` 增可选 `batchId`
- `handleJudge(line)` 调 `createPollutionCheck` 时带上 `batchId`（当前只传 `stage/bizNo/batchNo/itemCode/itemName/itemSpec`，`:102-123`）
- `joinKey` 由 `itemCode|batchNo` 改为 `batchId ?? itemCode|batchNo`（`:83-85`），保持向后兼容

`pollutionCheck` 新建表单（`safetyEnv/pollutionCheck/data.ts:84-175`）的处置：**保留但降级**。`batchNo` 从可打字 Input 改为 `WmBatchSelect` 选择器（组件已存在），选中后 `batch_id` / `itemCode` / `itemName` / `itemSpec` / `weight` 自动带出。这样即使有人从旧入口新建，也不会再造出对不上的记录。

**5.3.1 环节枚举补 `IN_STOCK`（开发中发现的设计遗漏）**

`stage` 是 `@NotEmpty` 且服务端 `validateStage` 白名单只有四个业务环节（采购入库/生产领用/中间废弃物/成品）。在库检测**不属于其中任何一个**——它没有发生业务动作，只是对存量批次做体检。若硬套一个既有环节，判定记录的"环节"字段就是错的，`defaultDisposition(stage, result)` 也会按错误的语境取默认处置。

因此新增第五个环节 `IN_STOCK`：

| 位置 | 改动 |
|---|---|
| `MesSetPollutionCheckServiceImpl` | 新增 `STAGE_IN_STOCK` 常量 + 加进 `STAGES` 白名单 |
| `MesSetPollutionCheckAiService` | `STAGE_CONTEXT` 增 `IN_STOCK → 在库复查（对已入库的存量批次做环保体检，非新到货验收）`；不加的话 AI 提示词里会直接塞英文枚举值 |
| `MesSetPollutionCheckSaveReqVO` | `@Schema` 描述补该值 |
| `safetyEnv/pollutionCheck/data.ts` | `STAGE_OPTIONS` 增「在库」 |

`defaultDisposition` 无需改：非领用/非废弃物的分支已兜底为"有污染→受控存储、无污染→正常入库"，对在库语境恰好正确。

**5.3.2 同一批次允许重复检测（复检）**

`batch_id` 上只有普通索引 `idx_batch_id`（非唯一），所以一个批次可以有多条判定。这是**有意的**：体检是周期性的，半年前的 CLEAN 不能当"永远合格"。列表按 `id DESC` 取首条为当前有效判定（`judge-modal` 的 `recordMap` 已是此语义）。因此 `judge-modal` 在已有判定的行上提供「重新检测」，不再只给已复核的静默只读态。

### 5.4 在库环保视图（新页）

**落点**：`views/mes/safetyEnv/inventoryEnv/`（新目录），菜单挂在「安全环保检测」下。

**为什么是新页而不是改 `wm/materialstock`**：改既有页要动 `MesWmMaterialStockApi` 的 VO 与 wm 模块，会波及所有用该接口的地方；新页只读、零侵入。

**数据源**（服务端 join，一次分页）：

```
mes_wm_material_stock s
  LEFT JOIN mes_wm_batch b            ON b.id = s.batch_id          -- 污染投影
  LEFT JOIN mes_md_item i             ON i.id = s.item_id
  LEFT JOIN mes_set_pollution_check p ON p.batch_id = s.batch_id    -- 最近判定
                                     AND p.deleted = 0
```

**列**：

| 列 | 来源 |
|---|---|
| 批次号 / 物料编码 / 物料名称 / 规格 | `s.batch_code` / `s.item_code` / `s.item_name` / `s.specification` |
| 在库数量 / 单位 | `s.quantity` / `s.unit_measure_name` |
| 仓库 / 库区 / 库位 | `s.warehouse_id` / `s.location_id` / `s.area_id` 及名称快照 |
| 入库时间 / **在库天数** | `s.receipt_time`，天数由入库时间算 |
| 冻结 | `s.frozen` |
| **污染投影** | `b.pollution_status` + `b.pollution_marked` + `b.pollution_src_record` |
| **最近判定** | `p.review_result` / `p.ai_result` / `p.review_time` / `p.disposition` |
| **检测覆盖** | 由判据算出（§5.5） |
| **关联状态** | `p.id IS NULL` → 未检测；`p.batch_id IS NULL` 的历史记录 → 未关联（Q4） |

**筛选**：检测状态（已检 / 未检 / 超期未检 / 积压）、污染投影、仓库、物料分类、在库天数 > N、批次号 / 物料模糊。

**行操作**：环保判定（E2）、冻结/解冻、受控库位调整、标记终审、查看批次档案。

**批量操作**：勾选多行 → 批量发起检测（走待检清单，§5.7）。

### 5.5 体检判据

四项判据**全部可由现有字段算出，无需 schema 变更**（F8、F9）：

| 判据 | 算法 | 依赖 |
|---|---|---|
| **未检测** | `p.id IS NULL` | 新 join |
| **超期未检** | `receipt_time + 周期 < now()` 且无有效判定 | `s.receipt_time`；周期见下 |
| **积压** | `DATEDIFF(now(), receipt_time) > 阈值` | `s.receipt_time` |
| **混放** | 同一 `area_id` 下同时存在 `pollution_status='POLLUTED'` 与非 POLLUTED 的批次 | `s.area_id` + `b.pollution_status` |

> **ponytail：** V1 的「周期」与「积压阈值」用**全局配置**（默认 90 天 / 180 天），不做每物料分类一套。天花板：物料周转差异大时误报。升级路径：A1 验证后改为按 `item_type_id` 配表，判据函数签名不变。

> **注意 F16**：`pollution_status` 为 NULL 覆盖「未判定」和「已判无污染」两种含义（列注释与实现矛盾）。因此**混放判据只认 `= 'POLLUTED'` 作为"需管控"信号**，不把 NULL 当"干净"也不当"污染"——NULL 一律归入"未知，需检测"，由「未检测」判据接住。这同时修正了 F16 的歧义而不必改 wm 列注释。

**「包装破损」不在 V1**（A5，无数据源）。这是体检清单已知的不完整处，须在页面上显式标注，不能让使用者以为清单是全的。

### 4.3.1 危化品相容组禁配 / 储存专区校验（2026-09-11 实现）

§4.3 给的重启条件是「危化品档案与物料建立关联（补 `item_id` 或加映射）」。按此实现：

| 变更 | 内容 |
|---|---|
| 新列 | `mes_set_chemical_profile.item_id`（→ `mes_md_item.id`，可空）。**为空 = 未绑定 = 在库侧不判**——与「未锚定的禁配组合不猜」同一口径 |
| 新列 | `mes_wm_warehouse_area.storage_zone`（`GENERAL`/`EXPLOSION_PROOF`/`ISOLATION`）。与 `pollution_control` **相互独立**：一个库位可以既是被污染管控的危废暂存间、又是防爆区，合成一列会出现"既是又不是"的死结 |
| 规则 | 抽到纯静态类 `service/set/chemical/ChemicalCompatRules`，档案侧 `checkStorage` 与在库侧共用同一份矩阵（规则分两份是这类合规校验最典型的腐化方式） |
| 拦截点 | `MesPollutionControlServiceImpl.assertChemicalStorageAllowed`，挂在**两个**入口：① `applyReviewEffect`（复核）② `changeControlLocation`（受控库位调整）。只在②拦的话，改库位被拒的人会绕开调整、回头用①把货放进去——门就形同虚设 |
| 新错误码 | `1040830010` 物料重复绑定 / `1040830011` 专区不符 / `1040830012` 同库位禁配 |

两个实现要点（都是"写错了不会报错、只会静默失效"的那种）：

- **禁配比对集取"该库位此刻在库的物料"**，即 `mes_wm_material_stock.area_id` → `mes_wm_warehouse_area.id`（库位）。注意**不是** `location_id`——后者指 `mes_wm_warehouse_location`（库区），是上一级。两列名字只差一个词、都没注释，写错了比对集恒为空集，禁配就成了永不放行的摆设。
- **批次锚点两处口径必须一致**：判定行的 `batch_id` 是**请求方传的**（`MesSetPollutionCheckServiceImpl.applyBatchAnchor` 不按 batchNo 反查），而 `applyReviewEffect` 的批次戳投影认 `batchNo`。所以只传 `batchNo` 的判定行也要能反查出物料，否则那是一条绕过这道门的后门。

验证：`e2e/run_e2e_compat.py` 18 用例（未绑定放行 / 专区正反例 / 禁配正反例 / 只传 batchNo 的后门回归 / 两个入口各测一遍 / 拦截不落库 / 夹具还原）。

> **前提说明（重要）**：本机制靠 `item_id` 绑定驱动，而**当前库内没有任何危化品物料**——`mes_md_item` 里搜不到酸/醇/酯/醚/异氰/胺/溶剂等任何一条，租户 2010 只有钢筋/螺丝刀/小包装盒/ABC 四件。所以本功能**现在是休眠的**：要把危化品建成物料、并在「危化品档案」上绑定 `item_id` 之后，拦截才会真正生效。绑定入口已做在档案表单的「关联物料」字段上。

### 5.7 全库体检（待检清单 + 派工复检）

**做法**：一个只读扫描把 §5.5 四项判据跑成待检清单，落为一条体检批次，条目可逐条或批量发起检测。

**关于定时（F12 的硬约束）**：

- `infra_job` 里**没有** `mesSetBatchExpireFreezeJob` 的注册记录，且现有任务 `status` 全为 `2`（暂停运行）
- 因此 **V1 必须支持手动触发**（页面上一个「立即体检」按钮），这是主路径
- 新增 `MesInventoryEnvInspectJob` 类，注册到 `infra_job` 属加分项；但**不得让功能依赖它**——否则在 F12 未解决前整个功能不可用

> **ponytail：** V1 的体检是**全量扫描**（69 行库存量级，一次全表 join 毫秒级）。天花板：库存到十万行级时全表扫会变慢。升级路径：加 `receipt_time` 索引 + 增量扫描（只扫上次体检后有变动的批次）。

## 8. 风险与未知

| 风险 | 影响 | 应对 |

```bash
# 判定记录关联率
mysql -uroot -proot ruoyi-vue-pro -e "
SELECT COUNT(*) 总, SUM(EXISTS(SELECT 1 FROM mes_wm_batch b
  WHERE b.code COLLATE utf8mb4_general_ci=p.batch_no COLLATE utf8mb4_general_ci)) 批次对上
FROM mes_set_pollution_check p WHERE p.deleted=0;"

# 混放预演
mysql -uroot -proot ruoyi-vue-pro -e "
SELECT s.area_id, COUNT(DISTINCT s.batch_id), SUM(b.pollution_status='POLLUTED')
FROM mes_wm_material_stock s JOIN mes_wm_batch b ON b.id=s.batch_id
WHERE s.deleted=0 AND s.area_id IS NOT NULL GROUP BY s.area_id
HAVING SUM(b.pollution_status='POLLUTED')>0
   AND SUM(COALESCE(b.pollution_status,'')<>'POLLUTED')>0;"
```
