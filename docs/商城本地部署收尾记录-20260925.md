### 本轮发现并修复

- 后台冻结安装失败：锁文件与已有 Sass/Vite 版本声明不一致。仅同步锁文件，没有自行升级清单；Docker 继续 `--frozen-lockfile`。
- 1024 MB 安装堆仍会触发构建进程自身 OOM，改为安装 2048 MB、构建 4096 MB；不是容器总内存上限。已按获准停机安排释放资源，不能据此宣称可与原微服务并行构建。
- 后台跳转按钮缺少实际编译地址：Turbo 严格环境透传显式纳入 `VITE_*` 与 `NODE_OPTIONS`，兼顾地址配置、内存参数及缓存输入。
- 演示单位错误：353 条 WMS 物料单位与 SKU 计量单位不符，例如桶错误写成 CAN、个错误写成 EA、kg/m³ 未正确归一。修正 002，并让 `export_fixture.py` 通过 `fixture_units.py` 读取 Java 单位字典，未知单位直接失败；903 个 SKU 已逐项比较通过，没有绕过结算保护。
- 订单详情返回“商城已禁用”：实际缺少 `trade_erp_inventory_request`，原导出器误把全部 trade_erp 表排除。补回只读审计空表，仍排除 ERP mock 表、仍不依赖 ERP 服务，也不导出旧订单。011 最终门槛加入该表检查。

### 后台构建未通过与资源事件

- 2026-09-25 04:00（北京时间），后台 Docker 构建处于 `pnpm install` 阶段时，Docker/WSL 主机出现 `global_oom`。内核日志明确显示 `Out of memory: Killed process ... (mysqld)`；并非只有构建任务自身失败。
- `deploy-mysql-1` 自动重启一次，完成 crash recovery，04:01 重新就绪并恢复 healthy。没有人工执行 stop/restart 或数据库写入。`docker inspect` 的 `OOMKilled=false` 不能排除主机级 OOM，本次根因以 WSL 内核日志为证据。
- 取消构建后只读复查：现有 PC（15175）和 H5（3000）的商品目录接口均返回 `code=0,total=841`；这是原运行库的恢复检查，不能与新演示库 898 个 SPU 混作同一数据集。
- 发现后已主动取消后台构建，没有生成本轮后台验收镜像；不会将本轮后台源码构建标记为通过。
- 安装阶段原来没有 Node 堆限制，现将 1024 MB 堆限制放到依赖安装前，后续 Vite 保留 2048 MB。**堆限制不等于容器总内存限制，修改后未再次重型构建**，不能据此保证同机并行安全。
- 继续后台源码构建/全栈验收前，应使用独立资源充足的环境，或取得用户授权后暂停明确的现有服务释放资源。不能擅自停止业务、调整 Docker/WSL 全局配置或继续挤占当前内存。
