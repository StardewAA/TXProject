## 3. 当前开发主线：MES 环保污染监控

### 3.1 需求

- 需求文档：`docs/MES环保污染监控需求文档.md`（v0.1，2026-09-03，**状态：待评审**）。
- 业务流程图：仓库上级目录 `环保模块业务流程图.html`（2026-09-07）。
- 定位：在 MES 主流程上以 **AI 初筛 + 人工复核** 双阶段，对生产线物品去向做污染监控与合规管控；**环保判定独立于质量判定**（不触发退货、不改质量口径）。

四个插桩环节（贯穿全链，一条记录可追溯）：

| 环节 | 常量 | 关键规则 |
| --- | --- | --- |
| 采购入库 | `PURCHASE_INBOUND` | IQC 合格后入库前初筛；判有污染≠退货，入受控存储 |
| 生产领用 | `MATERIAL_ISSUE` | 领出前复核，有污染 → 拒绝领用（源头隔离） |
| 中间废弃物 | `WASTE_INTERMEDIATE` | 无污染 → 回用/排放；有污染 → 隔离暂存 |
| 成品 | `FINISHED_PRODUCT` | 达标有污染 → 隔离+标记不出库；不达标 → 整批锁定 |

核心规则：AI 只给三值预分类（无污染/有污染/不确定）；**终态一律人工复核二值收口（CLEAN/POLLUTED）**，不允许"不确定"留存。

### 3.2 已实现功能（后端 `txgy-module-mes-server`）

**污染判定记录** `service/set/pollutioncheck/` + `controller/admin/set/pollutioncheck/`：
- `MesSetPollutionCheckController`：create / update / delete / review / prescreen / get / page / log-list。
- `MesSetPollutionCheckServiceImpl`：
  - 四环节 + 二值复核校验，记录编号 `PC-yyyyMMddHHmmssNNN`；
  - 创建/改单时自动回填 AI 初筛（改单触发 AI 重筛）；
  - 复核时按"环节 × 复核结果"给出默认处置（`NORMAL_INBOUND` / `ISSUE_ALLOWED` / `REJECT_ISSUE` / `REUSE` / `ISOLATE_STORAGE` / `CONTROLLED_STORAGE`）与默认存储方法（无污染→普通仓储；有污染→沿用 AI 推荐，否则受控隔离）；
  - 复核后同事务**写透**（`MesPollutionControlService.applyReviewEffect`）→ 批次污染戳 + 自动登记台账。

**AI 初筛** `MesSetPollutionCheckAiService`：
- **已接真实 DeepSeek 大模型**（`chat/completions`、`response_format=json_object`、temperature 0.2、25s 超时），输出四字段 JSON（aiResult / confidence / reason / suggestedStorage），逐字段清洗兜底；
- 未配置 api-key 或调用失败时**自动降级为污染特征词典**（安全词优先匹配"无铅"先于"铅"，命中污染词如铅镉铬汞苯甲醛等 → POLLUTED；均未命中 → UNCERTAIN，置信度 55–76 随机）；
- 配置项（api-key 仅本地配置，勿提交仓库）：`txgy.pollution-ai.deepseek.api-key / base-url / model`。
- 说明：需求原计划 P1 词典 mock、P2 真实 AI，实际已提前完成 P2 接入（带降级兜底）。

**污染管控写透** `service/pollution/MesPollutionControlServiceImpl`：
- 台账行 = 批次污染管控的权威；批次戳只是"该批是否有未闭环台账行"的投影缓存；
- 复核=有污染 → 校验库位/真实批次（中间废弃物允许空批次）→ 按 `source_check_id` 幂等登记台账（STORED）→ 批次戳投影 `POLLUTED`；
- 复核=无污染 → 解除该批历史未闭环台账行（CLEARED，留痕）→ 清批次戳；
- 台账处置终态（已回用/已排放/已处置）→ 按剩余开放行重投影；
- 门禁：`assertIssueAllowed`（领用拦截）、`assertOutboundAllowed`（出库拦截，POLLUTED 或 marked 即拦）；
- `purgePendingByBizNo(Item)`：单据创建/更新时清理未复核的悬挂判定。

**污染台账** `set/pollutionledger/`：
- 状态机 `STORED(暂存) → PROCESSING(处置中) → {REUSED/DISCHARGED/DISPOSED}`，外加 `CLEARED(自动解除)`；
- 每次流转写台账历史留痕。

**审计履历**（`pollution-audit-20260903.sql`）：
- `mes_pollution_check_log`：CREATE（含 AI 初筛快照）/ UPDATE（重筛快照）/ REVIEW（人工终态快照）各一行，不可改；
- `mes_pollution_ledger_log`：登记/处置中/终态/自动解除每步留痕。

## 11. 2026-09-10 第三轮：成品不达标三分支 + 判定表导出与筛选补全（需求文档 §11 用例5）

承接 §10。本轮处理需求文档里最后两处「写了、代码没有 / 半成品」——**§11 验收用例5「不达标成品整批锁定不出库」**与**判定表只能翻页不能导出/筛不全**。原则不变：与既有二值不变量正交、复用既有载体、不新造表。

### 11.1 建模口径（为什么不是「把 review_result 改成三分支」）

最容易走偏的一步是直接把 `review_result` 从二值扩成三分支。那样会打破 §9 已经立起来的 R2 不变量——**复核终态二值收口（无污染/有污染），不存在 UNCERTAIN 之类的中间态**，而且「有污染」是驱动台账登记/批次污染戳的唯一判据，混进「返工」会让台账链路失去语义。

所以拆成两个**正交**字段：

| 字段 | 语义 | 取值 | 谁填 |
| --- | --- | --- | --- |
| `review_result` | **污染态**——放行不放行 | `CLEAN` / `POLLUTED`，终态二值 | 四个环节都填 |
| `finished_result` | **达标分支**——成品行不行 | `QUALIFIED` / `REWORK` / `SCRAPPED` | **只有** `FINISHED_PRODUCT` 填 |

- `QUALIFIED` 达标 → 正常入库出厂；
- `REWORK` 局部缺陷 → 返工（补口/重新发泡），**不锁批**；
- `SCRAPPED` 整体报废 → **整批锁定不出库**；有害走受控存储 + 台账，无害直接存储 + 标记。

DDL `sql/00-sql文件/finished-result-20260910-ddl.sql`：`mes_set_pollution_check` 加 `finished_result varchar(32) NULL`（在 `review_result` 之后），存量 12 条成品判定回填 `QUALIFIED`（不改污染态）。实测回填后 `FINISHED_PRODUCT/NULL` 归零，其余环节全 `NULL`。

### 11.2 整批锁定的载体：复用批次污染戳，不新建列

「锁定」需要一个所有出库路径都认的地方。既有 `mes_wm_batch.pollution_marked` 已经被两个门禁读（`MesWmProductIssueServiceImpl:180` 领用、`MesWmProductSalesServiceImpl:220` 出库），直接把报废锁语义并进它——**零新列、零新门禁**。

`MesPollutionControlServiceImpl.refreshBatchStamp` 是批次戳的唯一投影点，改动只有一处：

```java
// 该批存在"整体报废"判定即锁死。与台账无关——无害报废没有污染台账行，
// 也必须挡住出库/领用，且不因后续无污染复核被解除。
boolean scrapLocked = pollutionCheckMapper.selectCount(new LambdaQueryWrapperX<MesSetPollutionCheckDO>()
        .eq(MesSetPollutionCheckDO::getBatchNo, batchNo)
        .eq(MesSetPollutionCheckDO::getFinishedResult, FINISHED_SCRAPPED)) > 0;
```

再把 `scrapLocked` 或进两个分支的 `marked`（`open.isEmpty()` 的清戳分支也要带上，否则无害报废的锁会被清掉）。领用门禁 `assertIssueAllowed` 同时放宽到与出库同口径——`POLLUTED 或 marked` 都拒，原先只看 `POLLUTED`。

**为什么锁定不能挂在台账上**：无害报废不产生污染台账行（`review_result = CLEAN` 时不登记），台账里根本没有东西可挂；而「整体报废」是成品自己独立的结论，与污染态无关。

### 13.2 入库待检冻结：一个投影，五个入口

`mes_wm_material_stock.frozen` 是**推导结果**，不是人工开关。唯一判据 `isBatchFrozen(batch)` 三条取或：

1. 批次污染戳为 `POLLUTED`，或 `pollution_marked`（含 §11 成品整体报废的整批锁定）；
2. 该批**仍有待复核判定行** → 待检期冻结。判 CLEAN 后该行不再是"待复核"，自然解冻；
3. 批次**已过期**。

第 3 条与污染**解耦**，是最容易写错的一处：把过期当成污染的子集，就会"判了无污染"把过期货一起放行。e2e 用 F3c（未过期判 CLEAN → 解冻）与 F5b（已过期判 CLEAN → 仍冻结）成对夹住这个维度。

`syncStockFrozenByBatch(batchNo)` 幂等重算，被 5 处调用：判定行 **create / update / delete**、复核 `applyReviewEffect`、定时任务。其中：

- 复核路径里它**必须排在 `refreshBatchStamp` 之后**——它读的批次污染戳是上一步刚重刷的，顺序反了就会拿旧戳推导，"判 CLEAN 才解冻"会慢一拍解不开；
- 两条 purge 路径（`purgePendingByBizNo` / `...Item`）**删前先记下涉及哪些批次**，删完逐个重算。漏掉这步就是"单据删了、库存永远冻着"——冻结态必须有对应的理由行存在才成立。

## 14. 2026-09-10 第六轮：排污许可合规（二期「按证排污」主线首刀）

设计文档以 **团队终版**为准（17:42 定稿、自述"合并定稿/单一事实源"；最终版 17:02 为"送评审"稿）。其 §六给出的口径是：**排污许可证 = 全厂环保数据的基准源**——限值取自证、监测对着证、总量卡在证。本轮把这句落成代码。

### 14.1 两条规则，一个权威

`MesSetPermitComplianceService`（`service/set/permitcompliance/`）：

1. **限值比对**：监测行入库时按该排放口的 `permit_limits` 匹配污染物，回填 `limit_value` 并按 `浓度 > 限值 → FAIL` 定 `result`。人工传的 `limitValue`/`result` **不作数**——证是唯一权威（e2e L1 故意传 `limitValue=999`/`result=FAIL`，必须被证上的 30/重算结果覆盖）。浓度**等于**限值算达标（限值是上限，取到边界不算超）。
2. **年总量红线**：自然年 Σ 排放量 ÷ 许可年总量，**≥80% WARN 黄警 / ≥100% RED 红线**，次年 1/1 由自然年边界天然归零。

两个关键取舍：

- **「没配限值」≠「达标」**。`judgeByOutletLimit` 在无排放口/无该污染物限值时返回 `null`，调用方保持原值不动，**不得**编一个 PASS 出来（e2e L4：未配限值的口传 `result=FAIL`，必须原样保留 FAIL，且 `limit_value` 不得凭空生成）。
- **配置期失败快**。`permit_limits`/`annual_limits` 的格式校验放在排放口、许可证的保存口上，而不是等监测入库时才炸——那时整段时间的监测数据都没在比对，**静默失效比报错危险得多**。校验也收紧了：既有 `validateLimitJson` 只检查"是不是一个 JSON 数组"，一串合法但无意义的 JSON 能过检然后在红线判定里静默失效；现改为每条必须 `pollutantCode` 非空且限值 > 0（e2e V2/V3）。

`emission_amount` 与 `annualLimitT` 的**单位**：前者按 kg 记、后者按 t 记，换算系数 `KG_PER_TON` 单独提取成常量并注明——现场口径若是 g/t，改一处即可，判定与红线同源。

### 14.2 演示数据补基准源

### 14.3 本轮踩的两个坑（都会静默失败，值得记）

1. **MySQL 的 `||` 是逻辑或，不是字符串拼接**（除非开 `PIPES_AS_CONCAT`）。`'a' || 'b'` 被当数值运算，直接报 `Truncated incorrect DOUBLE value`。JSON 字面量别拼，整条写。
2. **本接口的 `LocalDateTime` 走 epoch 毫秒，不是 `"yyyy-MM-dd HH:mm:ss"` 字符串**。传字符串**不报错**，被静默当 0 → 落库成 `1970-01-01`。后果极具迷惑性：年累计恒为 0、红线永远 NORMAL、接口一切正常。本轮 e2e 的 Q1–Q3 就是这么全挂的，根因不在合规逻辑而在夹具。已加断言 Q0a 专门盯"监测行时间确实落在 2026 自然年"。

第 2 条属于**跨模块的接口约定**，前端按毫秒传所以线上无恙，但任何脚本/联调方按肉眼日期串传都会中招。

## 15. 2026-09-10 第七轮：执行报告自动取数汇总 + 证载有效期预警（二期收口前半）

### 15.1 统计期 ≠ 自然年，这是本轮最容易埋的雷

设计文档里这两句话隔了两行，口径完全不同，混起来就会错：

- 行 199/237：执行报告**按许可证载频次**建季报/年报，取数范围是**统计期**。
- 行 236：年累计达 80% 黄警 / 100% 红线，口径是**自然年 Σ**，"次年 1/1 重置"。

所以 `env_report.data_summary` 的汇总里同时存在两种口径，实现上必须分开算、分开标：

| 段 | 口径 | 来源 |
|---|---|---|
| `exhaustGas` / `wastewater` | 统计期 `[periodStart 00:00, periodEnd+1 00:00)` | 直接查监测表 |
| `quota` | 自然年（`periodEnd` 所在年） | 复用 §14 的 `checkAnnualQuota` |

`e2e/run_e2e_report.py` 的夹具就是冲着这条缝设计的：故意放一行**统计期外但同一年**（2026-04-01，777 kg）和一行**跨自然年**（2027-01-05，555 kg）。
断言 A4 要求它不进统计期排放量（500 而非 1277），断言 A8 要求它**进**年累计（1.277 t 而非 0.5）。两边同时成立才算口径没串。

另：统计期取**闭区间**——`periodEnd` 当天 23:00 的行必须计入（夹具 R4），落到 SQL 是 `end.plusDays(1).atStartOfDay()`。

### 15.2 取数内容与"没配就别编"的一贯口径

`data_summary` 结构（`MesSetEnvReportServiceImpl.buildSummary`）：

```
{ periodStart, periodEnd, generatedAt,
  exhaustGas: { records, exceedCount, emissionAmount,
                pollutants:[{pollutantCode,records,exceedCount,emissionAmount}],
                exceeds:[{recordNo,outletId,outletCode,pollutantCode,concentration,limitValue,monitorTime}] },
  wastewater: { 同上 },
  quota:[{outletId,outletCode,pollutantCode,annualLimit,used,ratio,level}] }
```

- `quota` 段对统计期内**出现过的每个 (排放口,污染物)** 都出一条，但**没配年总量时不编水位**：`annualLimit`/`ratio` 为 `null`、`level` 仍 `NORMAL`，只如实报累计量。与 §14.1「没配限值不得凭空造 PASS」同一口径。（断言 A10）
- `exceeds` 里的 `outletCode` 是从排放口表一次性取的映射——原始监测行只存 `outletId`，报告给人看得能认出是哪个口。
- `generatedAt` 与 `monitorTime` 用 `yyyy-MM-dd HH:mm:ss` **字符串**而非 epoch 毫秒。注意这与**接口 DTO** 的约定相反（见记忆 `txgy-mes-api-conventions`）：DTO 走毫秒是框架行为，这里是写给人看的报告快照，故手工格式化。别照抄错边。

### 15.3 建单静默降级、显式调用才报错（有意为之）

`POST /mes/safety-env/env-report/create` 时若统计期已填且调用方没给 `dataSummary`，自动取数写入。但**统计期没填时不报错**——报告本身得能建出来（草稿阶段统计期常常后补）。摘要是空的。

### 15.4 证载有效期：基准日可传，所以能一次跑完

`MesSetPermitComplianceService.checkPermitValidity(permitId, onDate)`：距有效期止 ≤60 天 `EXPIRING`、已过 `OVERDUE`，`onDate` 缺省取今天。
**到期当天算有效**（`daysLeft==0` → `EXPIRING`，不是 `OVERDUE`）；有效期为空按 `OVERDUE` 处理——证载期限是按证排污的前提，登漏了不能算安全。

接口：`GET /mes/safety-env/pollution-permit/validity?id=&onDate=`。

## 16. 2026-09-10 第八轮：接入 infra 文件服务依赖（解开拍照/签名/MSDS/标签的共同前置）

### 17.2 门卫为什么必须是"硬"的

设计文档 §194 的原话是：**「门卫扫车牌/联单码硬校验：联单号存在+已生效+四方签字齐，缺一不放行」**。四条校验逐条落地，每一条给一个独立错误码，而不是笼统的"校验失败"：

| 校验 | 错误码 | 语意 |
|---|---|---|
| 联单号存在 | `1040829007` | 拿不出联单，后面三条免谈 |
| 联单已生效 | `1040829008` | 已申报 且 运输方、接收方均已确认 |
| 车牌一致 | `1040829009` | 签字齐不能替车牌；两边任一为空则跳过核对 |
| 三方签字齐 | `1040829010` | 移交环保员 / 押运司机 / 接收经手人 |

`gate-check` 是纯校验（给门卫看"为什么不让走"），`gate-release` 才放行。**关键点是拦截必须拦在写库之前**：e2e 里每条拦截都额外查了一次库，确认联单状态还停在「已生效」——只返回 `passed:false` 而库里已经放出去了，那才叫真的没拦住。

放行成功四件事在一个事务里：补签门卫（四方会签的第 4 方由放行动作补上）→ 联单转「已出厂」→ 写 `transferTime`/`gateReleaseTime`/`gateGuard` → 同单号台账推到「转移」。**复扫已出厂的单是回放不是重放**：仍返回放行信息，但放行时间一个字不改（e2e C9 前后对拍）。

### 17.3 生效判据对齐国家系统的"三方确认"

联单按 `草稿 → 已申报 → 已生效 → 已出厂 → 已归档` 走。生效的判据不是"申报了就算"，而是 **产生方已申报 且 运输方、接收方都已确认**，三条齐了才在 `confirmParty` 里自动翻状态。

顺序也是硬的：e2e B1 先确认运输方、再申报，确认那次被记下但不生效；B3 只差接收方一方，仍停在「已申报」；B4 补上接收方当场转「已生效」。**申报不是"点一下"，它是生效的前置条件**，顺序反了就真的反了。

### 17.4 只进不退：两条单调性

`STAGES = 产生→贮存→转移→处置`，`MANIFEST_STATUSES = 草稿→已申报→已生效→已出厂→已归档`。两条线都做单调性校验，回退和原地重复推进都拒（`1040829004` / `1040829006`）。

理由写在代码注释里：**危废台账是负法律责任的流水，退一格就是改历史**。配套两条：
- `updateHazardousWaste` 显式把 `stage` 置空——改单不许改环节（e2e A7 传 `stage=GENERATED` 进改单接口，库里仍是「处置」）；
- 已出厂 / 已归档的联单，前端整块字段转只读（出厂信息是追溯证据）。

### 17.5 危险特性：没配就别编（第三次应用同一口径）

`HW_HAZARD_TRAITS` 只收设计文档锚定过的四个码（HW06/08/12/49），**没收录的一律留空，不猜**。这跟 §15.2 取数、§12 判据是同一条纪律。

标签上写错一个危险特性，比留空危险得多——留空会被看见，写错会被当成真的。UI 侧配了一句提示，让人按现行《国家危险废物名录》人工补录。e2e 双断言：HW49 带出「毒性」，HW99 必须是 `null`。

### 17.7 本轮抓到的一个真 bug

`closeManifest`（回执归档）原来只做 `目标序号 > 当前序号`，于是 **「已申报」能一步跳到「已归档」**——跳过整个出厂环节，凭空生出一份没有出厂记录的回执。但它的错误提示写的是"只能按 草稿→已申报→已生效→已出厂→已归档 逐级推进"，**代码和自己的提示语对着干**。

是 e2e C12 逼出来的。修法很窄：归档只认 `TRANSFERRED`。顺带一个级联——C12 修好前 M2 被误关成 CLOSED，导致 E0（倒排提醒）查不到它而假失败；修完两处一起绿。

**台账侧的 `to > from` 保留不动**：小厂漏记「贮存」直接记「转移」是真实存在的，前进跳格是录入便利，回退才是改史。这两处的松紧不一样是有意的。

## 18. 2026-09-10 第十轮：危化品链（档案 + 分级储存禁配 + 储量上限 + 五双双人签字）

对应任务 #26 的另一半。第九轮（§17）做的是危废，本轮做危化品——两者同属设计文档《MES环保模块质优化设计-最终版-2026-09-09》的"危险品全生命周期"主线，但**管控对象完全不同**：危废管的是"出厂之后去哪了"，危化品管的是"进场之后放在哪、放多少、谁能动"。

### 18.1 缺口在哪

设计文档 §313 把危化品链排在 `chemical_safety` 这张空壳表上。**但那张表的语义不是档案**——它已经是"一次巡检的快照"（`label_ok` / `msds_ok` / `storage_ok` / `separation_ok` / `result` / `inspector` / `inspect_time`），是"某天某人去查了一次，结论合格不合格"。

而本轮要的是**物料本身的常量属性**：这个料属于哪个相容组、该进哪个专区、储量上限多少、同库位能不能和它放一起。这是"一物一行、很少变"，跟"一天一行、天天变"不是一回事。硬塞进巡检表，就会出现"改一次档案=伪造一次巡检记录"。

所以新建 `mes_set_chemical_profile`，与巡检表用 `chemicalCode` 关联。理由写在 DDL 抬头和 DO 的 javadoc 里，免得后来人以为漏了。

字段：`profile_no / chemical_code / chemical_name / cas_no / compat_group / hazard_class / storage_zone / storage_location / storage_limit / storage_unit / stock_quantity / incompatible_groups / explosion_proof / msds_url / msds_expire_date / expire_manage / shelf_life_days / emergency_measure / status`。

**建表就只给普通索引**：`profile_no` / `chemical_code` / `storage_location` / `compat_group` 四个 `KEY`，没有 UNIQUE。这是沿用 §13.4 定下的口径——业务编号唯一键和逻辑删除天然冲突（建→删→再建就撞 500），查重交给 Service 层返业务错误码（`1040830001`）。

### 18.2 四道校验的顺序不是随便排的

`checkStorage` 按 **① MSDS 挂载 → ② 专区要求 → ③ 同库位禁配 → ④ 储量上限** 出结论，`stockIn` 按同一顺序逐条抛具体错误码：

| 序 | 判据 | 不过的错误码 |
|---|---|---|
| ① | 已挂载 MSDS | `1040830003` |
| ② | 须防爆的料在防爆区 | `1040830004` |
| ③ | 同库位无禁配物料 | `1040830005` |
| ④ | 现有 + 本次 ≤ 上限 | `1040830006` |

顺序的含义是**"连进来的资格都没有"排在"进来多少"前面**：没有 MSDS 的危化品根本不该出现在厂里（设计文档原话：无 MSDS 的危化品不下采购单），这比"你这个库位放不下"更靠前。库管看到的第一条原因，应该是最该先去解决的那条。

**④ 只在给了本次入库量时才判**：`quantity` 为空时 `quotaOk` 返回 `null`，而不是 `true`。"没给量"和"给了量、量没超"是两件事，混成同一个 `true` 会让前端把"没校验"显示成"校验通过"。e2e 的 B6 专门钉这一条。

### 18.3 五双必须按**账号**判重，所以加了一列

设计文档 §5.3 要求"双账号各签一次"，§295 又写"账号即签名"。但 `mes_set_sign_record` 当时只存了 `sign_user`——**一个给人看的昵称**。

拿昵称判重是错的：两个人重名、或者同一个人改了昵称，都会判错。判错的后果是两个方向都严重——要么放行了一个人签两次的假双人，要么拦住两个真的不同人。

加 `sign_user_id`（`ALTER TABLE mes_set_sign_record ADD COLUMN sign_user_id bigint`），`doubleSign` 按它判重，撞了抛 `1040830007`。历史行为 NULL（那时没有双人判重需求），判重时只认非空值。三个写入点（`signManifest` / `releaseGate` / `doubleSign`）都补了赋值。

五双的五个动作（`RECEIVE` / `KEEP` / `LOCK` / `ISSUE` / `TRANSPORT`）**各签各的**，互不干扰——e2e D5 钉的是"收发货签齐了，领料还能重新从一开始签"。

### 18.4 禁配只对**同库位**判，不搞全场一刀切

禁配矩阵只收设计文档 §5.2 / §130 点名的组合：

```java
{"ISOCYANATE","POLYOL"},  // 黑料与白料剧烈反应 → 分间、双锁分开
{"ISOCYANATE","WATER"},   // 异氰酸酯遇水放热剧反应
{"ISOCYANATE","ALCOHOL"},
{"ISOCYANATE","AMINE"},
```

判定时只比**同一 `storage_location` 上已启用的其他档案**（`selectEnabledByLocation`），不是全库扫描。理由：禁配讲的是"放在一起才反应"，黑料在 A 间、水在 B 间是安全的，全场一刀切会拦掉本可以并存的两批货。e2e B3 专门放了一桶单独库位的水，它必须通过。

矩阵之外还有 `incompatible_groups` 人工追加列（逗号分隔），给"文档没写但厂里知道"的组合留了口子——**默认空，不猜**。

### 18.5 没配就别编（与 §17.5 同一口径）

`GROUP_NAMES` 只收 7 个文档点名的物料族（黑料/白料/稀释剂/环氧粉末/水/醇/胺），没收录的**按原值回显**，不猜中文名。前端的下拉也只给这 7 个。

`EXPLOSION_PROOF_GROUPS` 只有 `THINNER`——文档写了"稀释剂：易燃液体专柜"，别的易燃品文档没点名，就不替它做主。真需要时走 `explosion_proof` 布尔字段手工勾。

`getAlerts` 只出三类：**超量 / MSDS 缺失 / MSDS 将到期**。**刻意没做批次效期预警**——那已经是 wm 侧冻结投影的判据③（§13），再做一份就是两处判同一件事，早晚对不上。

### 18.6 复用而不是新建

| 想做的事 | 实际做法 |
|---|---|
| 五双签字存哪 | 复用 `mes_set_sign_record`（`bizType = CHEMICAL_DOUBLE`），不新开表 |
| 查某单某动作的签字 | 复用 `signRecordService.getSignRecordPage`，没加 Mapper 方法 |

## 19. 二期：治污设施运行管控（台账 / 换炭→HW49 / 停运申报审批 / 同开同停）

设计文档 §6.3。菜单 34463~34468（`治污设施`，父 34000）。权限键 `mes:set-facility:query|create|update|delete|operate`。
`operate` 一个键管换炭/停运申报/停运审批/复运四个动作——它们都是"对设施动手"，拆开只是多配四个键。

### 19.1 表名：`mes_set_treatment_facility`，不是设计稿的 `mes_dg_facility`

沿用 §17.1 的结论：设计文档里的 `mes_dg_*` 前缀在仓库里**不存在**，全部是 `mes_set_*`。建表脚本抬头写明了这处偏离。

### 19.2 三条管控都是"绕不过去"，不是"提醒一下"

这一节的全部价值在于：**每条约束都堵死在结构上**，而不是前端弹个提示。

**① 换了炭不能不记危废。**
`replaceConsumable` 是 `@Transactional`：登记废活性炭 HW49 与顺延下次更换日期在**同一个事务**里。换下的活性炭**就是** HW49，写不写危废不是操作员的选择。
- 危废行是**复用 `MesSetHazwasteService.createHazardousWaste`** 建的，不是自己拼 DO 插进去——编号查重、默认环节/状态全走危废链那套口径。
- 量 ≤ 0 直接拒（`1040831006`）。**不放行 0**：放行等于给危废台账留一条空行，"记了"和"没记"就分不清了。

**② 申报 ≠ 停运。**
`declareShutdown` 只把 `shutdown_status` 置 `PENDING`，**设施仍是 `RUNNING`**。只有 `approveShutdown(approved=true)` 才置 `STOPPED`；**驳回时 `run_status` 回到/保持 `RUNNING`**——驳回的设施还在转，这是两回事。
审批动作写一条 `mes_set_sign_record`（`biz_type='FACILITY_SHUTDOWN'`），复用签字表白拿一份审批历史，不另建审批表。

**③ 改档案绕不过停运审批。**
`updateFacility` 显式把 `runStatus` / `shutdownStatus` / `shutdownDeclaredAt` / `shutdownApprover` / `shutdownApprovedAt` **置 null** 再更新。
理由写在了代码注释里：运行状态与停运申报不是"档案属性"。否则改一次档案就等于绕过了审批，停运审批也就白设了。e2e 的 F 组专门打这一条——用 update 接口塞 `runStatus=RUNNING, shutdownStatus=APPROVED`，库里纹丝不动。

**④ 复运顺手归档。**
`resumeFacility` 回到 `RUNNING` 并把 `shutdown_status` 清回 `NONE`。不清的话，下次要停运时 `declareShutdown` 的 `PENDING` 判定会拿着上一轮的历史挡路。

### 19.3 同开同停：产线运行信号**由调用方给**，系统不编

设计文档 §6 想的是"设施未运行 → 工单禁止开工"。查过了：**`mes_pro_work_order` 表没有产线 / 设施 / 排放口列**，自动取不到这个信号。

选择是把 `productionRunning` 做成**入参**，并在 VO 上写清楚为什么——**没配就别编**。编一个假的产线状态挂上去，比不挂更危险：它会让"同开同停"变成一个显示绿色但对不上现实的灯。

校验是**只读**的，违规时返回两条分开的原因：
- `同开同停：产线「X」运行中，配套治污设施 Y(Z) 处于停运，产能不能开`
- `未批先停：该设施停运申报状态为 NONE（须已批准）`

两种违规性质不同，分开说。产线也停了则不算违规（停机检修是正常的，不能一刀切）。
`stopped-without-approval` 是一个**独立清单接口**：已停运但申报不是 `APPROVED` 的设施，供巡检直接捞。

### 19.4 "没周期就不算到期"

`calcNextReplace(base, cycleDays)` 在 `base` 或 `cycleDays` 缺失时返回 **null**，不拿建档日凑。
`next_replace_date` 是派生值（上次更换 + 周期），所以**不放进表单**——手填只会填出一个跟换炭日志对不上的日期。表单里连字段都没有。

## 20. 2026-09-10 事故与修复：生成器无参数重跑冲掉第一批 6 个模块的手写代码

### 20.1 发生了什么

为了给第二批 10 张空壳表生成模块，跑了 `python gen_shell_modules.py`——**没带表名**。
而 `main()` 里是这句：

```python
picked = [t for t in TABLES if not args or t["table"] in args]   # 没参数 = 全选
```

`TABLES` 当时已有 16 张表，于是**第一批 6 张（env-report / emission-outlet / exhaust-gas / wastewater /
carbon-emission / chemical-safety）被原样重写**。生成器只会写 CRUD，§14~§16 长在这几个文件里的业务逻辑
被整体抹平。

关键教训有两条，都不是"要小心"这种废话：

1. **冲掉的代码编译期不一定报错，运行期不一定抛异常。** 这一轮实际被冲掉 5 处，症状各不相同：

   | 被冲掉的东西 | 症状 |
   |---|---|
   | 两个监测 Mapper 的 `sumEmissionAmount` / `selectByMonitorRange` | **编译不过**（`PermitComplianceServiceImpl` 调不到）——唯一一个当场暴露的 |
   | 监测 Service 的 `applyOutletLimit` | 编译过、接口正常，只是 `limit_value`/`result` 不再按证重算——**静默失效** |
   | 报告 Service 的 `autoSummary` / `archiveSummary` | 编译不过（Controller 在调） |
   | 排放口 Service 的 `validateOutletLimits` 调用 | 编译过、接口正常，非法限值 JSON 照收——**静默失效** |
   | 排放口 Controller 的 `GET /annual-quota` | 接口 404，但没有任何编译期线索 |

   **所以"能编译过"完全不能作为"没被冲掉"的证据。** 这次是靠 e2e 才发现的。

2. **`.m2` 里的 fat jar 不是可靠的恢复源。** 我一度用它当基线做 `diff_jar_vs_src.py`，但它只在
   "最后一次成功 `install`" 时更新——重跑一次构建就被覆盖成新的（含冲掉之后的）内容。本轮就是这么
   丢掉基线的，最后是靠 **e2e 断言 + 文档 §14~§16 的改动清单**把行为规格还原出来的。
   临时副本**没有 `.git`**，写下来的文档就是唯一的历史。这条以后每次都要记住。

### 20.2 怎么修的

按"文档写了什么 + e2e 断言要什么"反推，逐处补回（不凭记忆编）：

- `MesSetExhaustGasMapper` / `MesSetWastewaterMapper`：`selectByMonitorRange(start, end)`（闭起开止）
  与 `sumEmissionAmount(outletId, pollutantCode, start, end)`。
- `MesSetExhaustGasServiceImpl` / `MesSetWastewaterServiceImpl`：`applyOutletLimit`，在 create/update
  里调 `permitComplianceService.judgeByOutletLimit`；**返回 null 就原样保留人工值**
  （e2e L4a：未配限值的人工 `FAIL` 不得被改成 `PASS`——「没配」不等于「达标」）。
- `MesSetEnvReportService(Impl)` + `Controller`：`autoSummary` / `archiveSummary` 与
  `buildSummary/buildSummaryQuietly/section/quotaSection/concat` + 内部 `record Mon`，
  外加 `POST /auto-summary`、`POST /archive`（两个都复用 `mes:set-env-report:update` 权限——
  从 jar 的注解常量池里核过，不是新编的）。
- `MesSetEmissionOutletController`：`GET /annual-quota`。
- `MesSetEmissionOutletServiceImpl`：`validateBase` 里补回 `permitComplianceService.validateOutletLimits`。

统计期/自然年两种口径、闭区间边界、`dataSummary` 字段形状全部按 §15.1/§15.2 与
`run_e2e_report.py` 的 A/B/C/E 段断言还原，没有一处是"看着差不多"写的。

### 20.3 顺带清掉的假故障

修完第一次回归，permit 的 V1/V2 与 report、shell 的收尾断言红了。查下来**不是代码问题**：
在"校验被冲掉"的那段时间里跑过 e2e，V 组那两个**本该被拒**的排放口
（`DA-E2E-BADJSON` / `DA-E2E-BADITEM`）真的落库了；而 V 组的设计前提是"必然被拒，所以无需清理"，
清理逻辑自然不会删它们。它们又恰好是 shell 套件取模板时的"最新一行"（`page?pageSize=1`），
于是把坏 JSON 当模板复制，连累了一个跟排放口无关的套件。

物理删掉这两行残留后 8 套全绿。**教训：e2e 的"必然失败"型夹具一旦真的成功，会留下没人负责清理的脏行**，
而这类脏行会顺着"取最新一行当模板"这种写法污染别的套件。

### 20.4 堵住根因（这是本轮真正的产出）

改了两处，让同一件事**不可能再发生**，而不是靠"记得带参数"：

1. **不给表名就拒绝执行**（`gen_shell_modules.py:main`）。全量重写要显式写 `--all`，
   且建议先 `--dry` 看会碰哪些文件。

2. **`write()` 只覆盖"还是生成器上次写的样子"的文件**。生成器落盘的内容用 sha1 记在
   `codegen/.gen_manifest.json`；要覆盖时先比对当前内容——**对不上就说明有人手改过，拒绝并提示**。
   首次遇到"已存在但没有记录"的文件同样拒绝（宁可不写，也不猜它是不是手写的）。
   `--force` 才强行覆盖。

   实测：`python gen_shell_modules.py mes_set_env_report` 现在会逐文件打印
   `[skip] ... 与生成器上次写的对不上（有人手改过），拒绝覆盖`，源码一字未动。

   > ponytail: 用 sha1 全量比对而不是行级 diff，够用且最短；将来若需要"只重生成某几个方法"，
   > 再说那是另一个工具的事。
