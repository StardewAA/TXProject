# 外部公告采集与展示设计方案 v0.3（仓库内实现版）

> 状态：设计草案（仅文档）。v0.1（仓库内自研/死枚举）与 v0.2（独立 Python 微服务）思路均**作废**。
> v0.3 结论：**在 txgy-module-bidding 仓库内实现**（Java + 平台既有能力），不另起 Python、不做独立微服务；
> 结构化交给 AI（大模型出站调用），**AI 侧的冗余/重试由 AI 服务方承担**，本地只保留"消息级有限重试（≤3）→ 转人工审核"，主压力不在本模块。
> 引用：《招投标模块开发规范》（唯一权威、冻结）、01/05/04；法规见 §九（沿用）。

---

## 一、结论性定位

| 项 | 决定 |
|---|---|
| 实现位置 | 本仓库 txgy-module-bidding 内新增"外部公告"功能组（新表/调度/消费/AI 客户端/展示接口） |
| 是否微服务/Python | 否。复用平台能力：starter-job（调度）、starter-mq（Redis Stream，消息+重试）、starter-redis、starter-web（下载/回调 HTTP） |
| 解析器 | 不手写解析器；**AI 结构化**（固定 Schema 输出）+ 行业分类 |
| 重试冗余 | 消息级最多 3 次 → 失败交 AI 兜底/人工审核；AI 服务端自身的重试由 AI 方负责，本地不做深队列 |
| 下载器 | 通用 HTTP 下载器 + **源/通道配置**（不同平台差异配置化），另支持"AI 摘要"兜底（无法原样时只取关键信息） |
| 身份认证 | 采集由本系统内调度与管理员配置发起（既有 admin 鉴权）；保留"服务账号+HMAC"备用于未来外部试解析/第三方回调 |

## 二、模块内流程（全在本仓库）

```
[starter-job 调度] ──► 下载器(HTTP，多通道配置，增量=url+last_fetch_time)
       │  落原文：HTML 原样 / 接口数据 / PDF 原件（对象存储/本地），投递 MQ
       ▼
   MQ(crawl.downloaded → crawl.process)  Redis Stream（starter-mq）
       │  消费编排：重试 ≤3（指数退避）
       ├─ 成功 ─► 调 AI(固定Schema结构化 + 防腐保温行业三态分类)
       │           └─ 校验器：只查类型/长度/格式（失败→打回重做，计入3次）
       │           └─ 通过 ─► 落库 bidding_notice_external*（去重/生效期/审核状态）─► 对外只读展示
       └─ 3 次失败 ─► 审核队列(记录 url/原文引用/parserCode/原因) ─► 人工审核
```

- 全链路 taskId/urlHash 贯穿，每步写审计日志（阶段/尝试次数/错误码/时间）。
- 打回类型：下载失败→重下；AI 输出不合规（校验不过）→ 重抽；均计入该消息 3 次上限。

## 三、消息与重试（复用 starter-mq：Redis Stream）

- 主题：`crawl.downloaded`（原文就绪）、`crawl.process`（处理/AI）、`crawl.retry`、`crawl.audit`。
- 消息体：`{taskId,url,urlHash,channelCode,parserCode,contentType:HTML|API|PDF,fetchedAt,retryCount,contentRef,extra}`。
- 重试：消费异常/校验失败 → `retryCount+1` 回 `crawl.retry`（指数退避），>3 进审核；**AI 服务端自身的超时/重试由 AI 网关策略处理，本地不展开深重试**。
- 用 Redis Stream 天然支持消息确认/重投；重复消费靠 `urlHash+fetchedAt` 幂等去重。

## 四、下载器（多通道，配置化不写死）

1. 配置表 `bidding_crawl_source`（本模块）：`channelCode/入口URL/抓取间隔/robots 开关/UA/是否启用/所属行业判定策略(默认AI)/备注`——不同平台的 URL 编排差异在配置与可插拔 Adapter Bean 上收敛（`ChannelAdapter` 接口：通用实现 + 平台专属实现，均在本仓库 Java 内）。
2. 增量：读取该 urlHash 最近一次抓取时间，只抓更新。
3. 原文一律先落（对象存储 FileApi 或本地存储按部署），供 AI/审核/复检与展示回源使用。

## 五、AI 结构化 + 行业分类（解析不再手写）

1. **固定 Schema**：AI 按模板（模板 code ↔ prompt/JSON Schema 版本）输出：主列（标题/发布时间/类型原文/发布单位/正文或内容引用/附件/项目编号等）+ `meta_json` 原字段快照。
2. **校验器只做**：字段是否存在、类型、长度、格式（时间/金额/URL http(s)）；不合格返回错误码打回。
3. **防腐保温行业判定**：AI 输出 `BELONGS/NOT_BELONGS/UNCERTAIN + 置信度`；`BELONGS` 进重点展示，`NOT_BELONGS` 留档不推，`UNCERTAIN` 转人工。
4. `parserCode`：URL 审批通过后绑定；决定 AI 模板/通道/校验规则；可换 code 重处理（§六）。

## 六、URL 白名单与审批（管理员/授权人）

- 仅**超级管理员或授权人**可配置/试解析 URL：提交 → 下载+AI 试跑 → 返回数据+原文预览 → 审批通过（绑定 parserCode/规则）→ 该 URL 此后按此 code 自动处理；可多次试跑/改配/再审批，全程留痕。
- 试解析/预览接口用既有 admin 鉴权（如 `bidding:ext-source:try-parse`、`bidding:ext-source:approve`）。
- 未在白名单的 URL 默认不抓。

## 七、数据模型与展示（沿用 v0.1 表草案，域命名待确认）

- `bidding_notice_external` 主档：`title / source_code/source_name / orig_url / orig_url_hash(唯一) / content_hash / content_type(HTML|PDF|ATTACHMENT|IMAGE|OTHER) / content_html(原样) / pdf_file_id+sha256+size(FileApi，红线8) / attachment_ids_json / notice_type_raw / notice_type_code(可空) / legal_flag(Y/N/NULL) / industry_flag(BELONGS/NOT_BELONGS/UNCERTAIN+confidence) / project_code / issuer_name / publish_time / effective_from / effective_to / status(NEW→ACTIVE→INACTIVE→ARCHIVED) / audit_status / public_scope(默认SOCIAL) / fetch_count / last_fetch_time / 审计列`。
- `bidding_notice_external_meta`（动态字段兜底）、`bidding_notice_external_attachment`（附件下载：FileApi 签名 URL + 病毒扫描）、`bidding_crawl_source`（源配置）、`bidding_crawl_task`/`bidding_crawl_job`（任务与批次、失败原因审计）。
- **字段不固定**用"主列稳定 + meta_json 兜底"；种类不写枚举，写源配置与 parserCode；`legal_flag` 处理非依法项目（未知=null，不误标）。
- 展示三形态（对外只读详情，都带**原网址**）：
  - HTML → 原文原样返回（安全：消毒/沙箱，见 §九）；
  - PDF → `pdfFileId/pdfDownloadUrl + origUrl`，前端 JS 预览；
  - 附件 → 逐条下载地址。
- 列表只返回主列（标题/时间/类型/来源/生效期/行业标签），详情才带原文。

## 八、身份认证（按 v0.3 内部实现口径）

1. **本系统内调用**：采集由调度与管理员配置发起 → 全程既有登录态/权限码与内部 MQ，无需外部身份。
2. **对外留口**（文档保留，不实现）：若未来"AI 网关/第三方试解析"需要反向回调，使用 **服务账号 + HMAC-SHA256 签名**（`X-Access-Key/X-Timestamp/X-Nonce/Authorization`，验签+时间窗+nonce 防重放+审计）或固定内网 API-Key——到那时再接，本版不引入。
3. 我方展示/预览接口仅经授权管理员访问；公开列表只出 SOCIAL 内容（01 规则兜底）。

## 九、安全与合规（沿用并精简）

| 项 | 做法/依据 |
|---|---|
| 公开信息范围 | 仅白名单公开源；尊重 robots/ToS，冲突转人工（《网络安全法》《数据安全法》） |
| 展示授权 | HTML 原样/PDF 缓存需源站授权或摘要+原链接+署名；可应诉下架（《著作权法》） |
| 个人信息 | 不收录/展示专家、联系人等敏感字段，脱敏处理（《个保法》） |
| 分级存储 | 采集内容 L1/L2；涉密不采 |
| XSS/SSRF/开放重定向 | HTML 消毒或 sandbox；下载目标 http(s)+IP 校验；外链协议白名单 |
| 附件/PDF 安全 | FileApi 病毒扫描+类型白名单+sha256 |
| AI 调用 | 出站调 AI 网关（HTTPS、密钥走配置中心），AI 端重试由 AI 方负责 |
| 行业标签声明 | 页面注明"以原站/原公告为准"，行业分类仅供聚合推荐 |

## 十、开放问题（推进前确认）

1. 表前缀/归属：默认 `bidding_notice_external_*` + G 轨（平台级聚合）——接受？或需在冻结规范登记新域（需你授权）。
2. 版权展示形态：A 原文全文（需源站授权/白名单） vs B 摘要+原链接（推荐 v1 默认）。HTML 原样只在授权源开。
3. 错误码段：新接口错误码暂挂 199 通用并注释（同备案先例）还是你授权登记新段。
4. AI 网关/模型与模板 code↔Schema 版本管理；行业判定的 few-shot 样例集。
5. 首批白名单源清单；消息队列主题命名是否沿用 `crawl.*`（Redis Stream）。
6. 下载器是否需要反爬增强（IP 池/代理）——默认 v1 不做，靠源配置频控。

## 十一、分期（仓库内 Java 实现）

- P0：本模块"外部公告"表 + 展示/审核接口（HTML/PDF/附件三形态、去重、生效期）——按 §十 决策后开工；
- P1：源配置 + 调度（starter-job）+ 通用下载器 + MQ 3 次重试 + 回调落库（无 AI）；
- P2：AI 结构化/行业分类 + 校验器 + 审核队列 + URL 白名单审批（绑定 parserCode）；
- P3：多通道适配、增量策略、批量试解析工具、监控。
- 全程 TDD/规约测试/真库 IT；代码注释按规范标注出处；遵循冻结规范六章流程。
