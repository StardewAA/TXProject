# 外部网站公告 · 采集与展示设计方案（草案 v0.1）

> 状态：设计草案，未落地。范围：**只做方案文档**，不改《招投标模块开发规范》（唯一权威、冻结），不改既有表/接口。
> 需求来源：①外部网站公告种类繁多、字段不固定、枚举难定；②展示形态三选：HTML 原样+原网址、附件下载、PDF（JS 展示+原网址/下载）；③只记录最关键字段（排序/生效期/标题等，重要字段不能丢）；④外站公告每次经接口返回需在系统内留档（独立新表）；⑤含非依法招标项目，需能管理；⑥外站爬虫需**分布式**管理。
> 依赖权威文件：《招投标模块开发规范》§4.6（检索）、五章（建表/文件/JSON/审计/索引）、红线 2/8；01/05（公开级别边界、幂等）；04（公开文档形态）；平台 starter（mq/job/redis/lock，见 07）。

---

## 一、定位与边界

| 项 | 说明 |
|---|---|
| 是什么 | 把"外部网站/其它交易平台"已公开的公告聚合进来：**采集 → 去重 → 留档 → 对外只读展示**，与自有业务公告（bidding_notice，须按权威数据集上报）完全隔离 |
| 不是什么 | 不替代 bidding_notice 上报域；不做对第三方系统的写回；不把外站内容当"权威可上报数据集" |
| 谁在用 | 公共服务大厅（匿名只读）+ 后台运营（采集源/任务/审核/下线） |
| 合规前提 | 只采集**公开**信息；遵守目标站 robots/服务条款、保留来源署名、支持应诉下架；展示版权形态为开放问题（见 §八-2） |

## 二、数据模型（草案，均不进 sql/ 目录执行）

### 2.1 命名与归属（关键决策点，见 §八-1）

- 为避免动冻结规范，表前缀建议挂"公告域"扩展：`bidding_notice_external_*`（注释注明属外部聚合，非 bidding_std 上报、非 bidding_notice 业务公告）。
- 归属：外部公告是**平台级公共聚合数据**，建议 **G 轨（BaseDO、无 tenant_id）**——多个租户不应各自重复存同一外站公告；租户个性化（订阅/收藏）另建关系表。若业务要求租户各自管理采集范围，再切 T 轨（文档留两案，默认 G 轨）。

### 2.2 主档表 `bidding_notice_external`（记录"最关键的字段"，重要字段不丢）

| 字段 | 类型/说明 | 为什么留 |
|---|---|---|
| `id` | 雪花 PK | 主键 |
| `source_code` | varchar(32)：来源站配置 code（§5） | 溯源 |
| `source_name` | varchar(128)：来源站名快照 | 展示/归口 |
| `title` | varchar(512)：标题 | 列表/检索核心 |
| `orig_url` | varchar(1024)：原网址 | 必须附赠"原网址" |
| `orig_url_hash` | char(64)（SHA-256，**唯一键**） | **去重指纹**（URL 级） |
| `content_hash` | char(64)：正文/文件指纹（用于内容级去重与更新识别） | 去重/变更识别 |
| `content_type` | varchar(16)：HTML / PDF / ATTACHMENT / IMAGE / OTHER | 决定展示形态（§三） |
| `content_html` | mediumtext（HTML 原样保存，不转义不裁剪） | HTML 原样展示 |
| `pdf_file_id` / `pdf_sha256` / `pdf_size` | FileApi 三件套（红线 8 口径） | PDF 形态 |
| `attachment_ids_json` | JSON（附件记录 id 列表，见 2.4） | 附件下载 |
| `notice_type_raw` | varchar(128)：外站自述类型原文（如"招标公告/更正/结果"） | 类型不定，原文必留 |
| `notice_type_code` | varchar(64)：可空，能映射权威码则填（否则 NULL） | 尽力对齐，不强求 |
| `legal_flag` | varchar(8)：Y=依法必招 / N=非依法（外站自述）/ NULL=未知 | **非依法项目管理** |
| `project_code` / `project_name` | 可空 | 关键关联（若页面含） |
| `issuer_name` | 发布单位（快照） | 排序/归口 |
| `publish_time` | datetime：外站公告时间（解析失败取抓取时间） | **排序核心** |
| `effective_from` / `effective_to` | datetime：生效期（投标截止/澄清截止等解析到就记） | **生效期判断** |
| `status` | varchar(16)：NEW→ACTIVE→INACTIVE→ARCHIVED（状态机见 §六） | 生效管理 |
| `audit_status` | varchar(16)：UNREVIEWED / APPROVED / REJECTED / TAKEN_DOWN | 运营审核 |
| `public_scope` | varchar(16)：默认 SOCIAL（仅社会公开可展示；政务/涉密不进） | 01 公开边界 |
| `fetch_count` / `last_fetch_time` | 采集统计 | 治理 |
| 审计列 | BaseDO/G 轨（无 tenant_id） | 平台惯例 |

**排序/生效期相关绝不丢**：`title / publish_time / status / effective_to / source_code / content_type / public_scope`；**原文溯源绝不丢**：`orig_url / orig_url_hash / content_hash / issuer_name`。

### 2.3 动态字段（种类不定 → 防丢兜底）`bidding_notice_external_meta`

- `notice_id`、`meta_json`（JSON，**原页面全部结构化字段原样存放**：key 保留原文，含外站私有字段）、`extra_raw`（TEXT，整页正文快照，可追溯）。
- 查询不依赖动态字段；需要过滤的少数稳定维度一律提升到 2.2 主列。**列不固定问题用"主列稳定 + meta_json 兜底"解决，不用枚举去框定种类。**

### 2.4 附件 `bidding_notice_external_attachment`

`id / notice_id / file_id / sha256 / size / name / ext / orig_download_url / download_url(FileApi 签名) / virus_status` —— 附件必须提供**下载地址**（FileApi 签名 URL；不做第三方裸链直传，见 §七安全）。

### 2.5 采集任务/源配置（分布式爬虫，§五）

- `bidding_crawl_source`：`source_code / name / base_url / entry_urls / parse_type / fetch_interval / robots_ok / enabled / ip_group / extra` —— 每个外站一条配置，**种类不写在枚举里，写在配置里**（驱动式）。
- `bidding_crawl_task`：`task_id / source_code / url / url_hash / priority / status(PENDING→RUNNING→SUCCESS/FAILED/SKIPPED) / attempt / next_retry_time / worker_id / grabbed_at / message`。
- `bidding_crawl_job`（批次）：`job_id / trigger / scope / status / summary_json`（跑批汇总）。

## 三、展示形态（接口返回设计）

统一对外只读：`GET /bidding/notice-external/{id}`（或分页列表）返回：

```json
{
  "title": "…", "publishTime": "…", "status": "ACTIVE", "effectiveTo": "…",
  "sourceName": "…", "origUrl": "https://…",          // 必带：原网址
  "contentType": "HTML|PDF|ATTACHMENT|OTHER",
  "contentHtml": "<原文原样>",                          // HTML 形态：原样给前端渲染（安全见§七）
  "pdfFileId": 123, "pdfSha256": "…",                  // PDF 形态：前端用 JS 预览组件展示，
  "pdfDownloadUrl": "/file-api/…签名",                 //        并给 origUrl + 下载地址
  "attachments": [{ "name": "…", "downloadUrl": "…" }] // 附件形态：下载地址列表
}
```

- HTML：**原样返回原文** + 原网址；前端展示时可加"来源：xx（原链接）"署名。
- PDF：只给 `pdfFileId/pdfDownloadUrl + origUrl`，前端 JS（如 pdf.js）渲染，不落正文 HTML。
- 附件：提供逐条下载地址。
- 列表页只返回主列（title/publish_time/type/source/status），详情才回原文，避免大字段。

## 四、入库留档链路（用户要求：接口返回即内部记录）

1. 外部入口/展示前**必经采集入库**（不允许"只转不发"）：任务/手动入库 → 查 `orig_url_hash` 去重：
   - 命中：比对 `content_hash`；内容变则**更新主档+追加 meta 快照**（记录变更），URL 不变不发重复行；
   - 未命中：新建主档（status=NEW→ACTIVE，若生效期解析成功）。
2. 入库后走运营审核（可选自动放行公开源白名单），再对外分页/详情。
3. 与 bidding_notice（自有公告）**完全两张表**，不做合并写；大厅聚合列表如需同源展示，另行读两表 union（文档方案，暂不实现）。

## 五、分布式爬虫管理方案（先用现有能力，不引重型框架）

**职责拆分**：调度中心（定时/job）→ 任务队列（Redis/MQ 分片）→ 分布式 Worker（多节点抢占）→ 解析入库 → 失败重试。

1. **源配置驱动**：`bidding_crawl_source` 决定抓哪些站、多快、是否遵守 robots（不进代码枚举）。
2. **任务入队与去重**：`bidding_crawl_task.url_hash` 唯一；调度按 source 的频率生成 PENDING 任务，Redis set/stream 做待抓集合，天然去重。
3. **分布式执行**：Worker 节点用 `txgy-spring-boot-starter-mq`（Redis Stream 消费者组：消息即 URL，天然分片/负载均衡）或 starter-redis 幂等抢占 + starter-job 定时补扫；同 URL 只允许一个 worker（消费组/锁双保险）。`worker_id` 记录谁在抓，断点续抓靠 task 状态机与 `next_retry_time`。
4. **限速与反爬友好**：每 source 配 `fetch_interval`（令牌桶/间隔等待），遵守 robots、UA 声明来源用途；失败重试指数退避（3 次后转人工，对齐 05 补偿口径）；IP 池/代理为可插拔（设计预留，不进 v1）。
5. **解析**：`parse_type` 驱动解析器（HTML 提取标题/正文/附件/时间/类型原文）；解析失败保存整页快照进 `extra_raw` 转人工。
6. **监控**：任务状态统计 + 失败告警日志；页面提供"采集源/任务/最新批次"后台查询（只读管理接口）。

## 六、状态机与生效期

- `NEW → ACTIVE`（审核通过且已发布）；`ACTIVE → INACTIVE`（超过 `effective_to` 或源站下架/变更失效，由定时 job 扫描）；`INACTIVE → ARCHIVED`（只读留痕）。列表默认只出 `ACTIVE`（大厅），排序 `publish_time DESC`。
- 生效期判定规则（文档约定）：有 `effective_to` 且 `now > effective_to` → INACTIVE；无法解析生效期的按 `publish_time + 源站源类型默认窗口`（源配置可配）或保持 ACTIVE 直至人工/源站标记失效——规则进 source 配置，不进死代码。

## 七、安全与合规（外站内容风险高，必须前置设计）

| 风险 | 措施 |
|---|---|
| XSS（HTML 原样展示） | 回显层做 HTML 消毒（白名单标签/属性）或 iframe `sandbox` 隔离；链接强制 http(s) 并校验跳转；**绝不 eval 外站脚本** |
| SSRF（爬虫） | 抓取目标只允许 http(s)；URL/IP 校验（禁内网/环回/云元数据）；域名走 source 配置白名单 |
| 开放重定向/钓鱼外链 | 外链展示前 URL 协议白名单 + 落库审核；可配置只展示不下跳 |
| 附件/PDF 恶意文件 | 下载只经 FileApi（病毒扫描 status 先例：资质域 virus_scan_status），扩展名/类型白名单，sha256 留存 |
| 越权/涉密 | 只收"社会公开"内容；页面含疑似政务/个人隐私字段由 `public_scope` 与审核拦截，01 规则在出口兜底 |
| 版权/聚合授权 | 展示形态开放问题（§八-2）——原样全文 vs 摘要+原链接，需业务定夺 |

## 八、开放问题（需要你拍板后再细化/落地）

1. **归属与命名**：默认 G 轨 + `bidding_notice_external_*`（不动规范）。是否接受？还是想新增"外部域"（涉及在冻结规范登记新域，需你授权改规范或按"公告域扩展"处理）。
2. **版权展示形态**：A=原样全文（需评估授权/robots/删除响应）；B=标题+摘要+原链接跳转（合规最稳）。建议 v1 用 B、HTML 原样仅在授权源白名单开。
3. **错误码段**：外站域新接口错误码需要新段位，冻结规范表暂无；建议暂挂 199 通用子段并注释（同备案先例），或你授权登记。
4. **采集范围**：首批外站清单（域名/URL/频率）由你给，我落到 `bidding_crawl_source` 设计示例。
5. **是否与大厅自有公告合并展示**：默认两张表分开、各自出接口；要合并展示再加 union 只读接口。

## 九、落地分期（本文件只做文档，先不动手）

- **P1 存储+展示**：三张表 + 对外只读接口（HTML/PDF/附件形态、去重、生效期、审核）——本期做这块需你确认 §八-1/2/3。
- **P2 采集框架（分布式）**：源配置 + 任务队列/Worker（用现有 mq/job/redis）+ 限速重试监控。
- **P3 解析与治理**：解析器、附件/PDF 抓取、IP/代理、告警看板。
- P1~P3 均按 TDD + 规约测试 + 真库 IT 交付，遵循《招投标模块开发规范》六章流程约定。

## 十、与本仓库既有内容的关系

- 不与 `bidding_notice`（权威上报）混用；字段映射沿用"主列稳定 + meta_json 兜底"思路，避免无效枚举；
