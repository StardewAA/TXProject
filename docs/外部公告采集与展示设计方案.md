# 外部公告采集系统设计方案 v0.2（独立采集微服务版）

> 状态：设计草案。**本方案对应的实现由"另一个独立微服务（Python）"承担，不属于 txgy-module-bidding 的开发任务**；本仓库只做方案、接口契约与接收侧（留档/展示/审批）设计。
> 更新说明：v0.1 的"仓库内实现"思路作废；v0.2 改为——独立 Python 服务内再拆【下载器 / 消息队列(重试) / AI 结构化 / 校验器 / 回调落库 / 审核】；解析器不再手写，由 AI 按固定 Schema 输出，我们只做**类型/长度/格式校验**，不合格打回重做。
> 权威/引用：《招投标模块开发规范》（仓库侧唯一权威）、01 系统间接口与数据交换约定、05 接口设计文档、04 公开文档/ES；法规见 §九。

## 一、总览（微服务分工）

```
[定时调度/增量] ─► 下载器 Downloader（多通道 Adapter）
                      │  读存储中的 URL + last_fetch_time，增量抓最新
                      ▼
                原文落对象存储/本地缓存（HTML 原文 / 接口数据 / PDF 原件）
                      │  放入消息队列（消息带 contentType + parserCode）
                      ▼
              ┌─► 处理编排（Retry ≤3）
              │     ├─ 成功：AI 结构化 + 行业分类 → 校验器
              │     └─ 失败重试，3 次仍失败 ─► AI(固定格式) ─► 审核队列 ─► 人工审核
              ▼
           校验器（类型/长度/格式/必填，失败→打回重下/重解析并记录原因）
              ▼
           回调我方接收接口（身份签名）→ 我方 bidding_notice_external 留档/展示/审批
```

原则：**下载器与解析/处理完全解耦**（各自可独立部署扩容）；任务从"网页下载→MQ→AI→校验→落库→再校验打回"全链路可追踪（任务 id 贯穿）。

## 二、消息队列与重试机制（必须项）

- 独立消息中间件（微服务自带，选型见 §十）：队列主题：
  - `crawl.downloaded`：下载器产出（原文已存对象存储，消息只带元数据+内容引用）；
  - `crawl.process`：AI 结构化/分类消费；
  - `crawl.retry` / `crawl.dead`：重试/死信；
  - `crawl.audit`：进人工审核；
  - `crawl.result`：校验通过待回调入库。
- 消息示例（JSON）：

```json
{
  "taskId": "…全局追踪", "url": "https://…", "urlHash": "sha256",
  "channelCode": "source_adapter_code",       // 下载器通道（平台适配，见 §六）
  "parserCode": "AI_TMPL_001",                 // 解析/处理代码：URL 关联的审批通过的 code
  "contentType": "HTML|API|PDF",
  "fetchedAt": "2026-09-03T10:00:00",
  "retryCount": 0,
  "contentRef": "oss://bucket/…html",          // 原文引用（HTML 原文/PDF 原件/接口报文）
  "extra": {}
}
```

- 重试语义：处理/AI/校验失败 → `retryCount+1` 回 `crawl.retry`（指数退避），**单个消息最多重试 3 次**；第 4 次（3 次失败后）进 `crawl.dead` → 转 AI 兜底（若此前不是 AI 路径）→ 最终进 `crawl.audit` 人工。全程记录 url、原文引用、parserCode、各次原因。

## 三、下载器（与解析器分开）

1. **职责**：按 `urlHash` 查库得到 `last_fetch_time` → 只抓增量（站内新发/变更页）；抓三类：**HTML 原文、接口/API 返回数据、PDF 下载原件**；抓完写对象存储并投递 `crawl.downloaded`。
2. **通道适配（解决"不同平台 URL 编排不同"）**：`channelCode` 驱动"通道适配器"：
   - 每个白名单源配 `channelCode`（对应特定平台的下载实现/路由规则/UA/反爬策略）；
   - 通用通道兜底：HTTP GET + robots 尊重 + UA 声明 + 编码探测；
   - 优先智能方式：**基于 URL/站点的适配器**（白名单源级别），不在运行时猜；候选增强：站点列表页入口 + 增量游标/分页策略（配置化），供后续迭代。
3. **原文留痕**：无论后续成败，HTML/PDF/接口报文都先落地（对象存储/本地缓存），供 AI、审核、复检使用。

## 四、处理：AI 结构化 + 行业分类（解析器不手写）

1. **AI 结构化**：按固定 JSON Schema（我方给定：标题/发布时间/类型原文/发布单位/正文或附件引用/项目编号等主列 + 原始字段快照）输出；AI 只做字段抽取，**原文不去重改写**。
2. **固定格式输出** → 校验器：
   - 只做**数据类型、长度、格式**（时间 yyyyMMddHHmmss / datetime、金额、URL http(s)、必填主列非空）；
   - 不合格 → 打回：记录原因回到处理重试（计入 3 次上限），或直接回下载/解析（按失败类型分层打回：下载失败→重下；AI 输出不合规→重抽）。
3. **项目分类（防腐保温行业筛选）**：AI 三态 `BELONGS / NOT_BELONGS / UNCERTAIN` + 置信度；`BELONGS` 才进后续推荐/展示重点，`NOT_BELONGS` 仅留档不推，`UNCERTAIN` 转人工。**分类只是筛选标签，不代替"以原站为准"**。
4. parserCode 语义：URL 一经"审批通过"绑定某个 code；该 code 决定用哪套 AI 模板/通道/校验规则（可写很多 code，有的适用有的不适用）；更换/再审批即可换 code 重新处理历史（见 §五）。

## 五、URL 白名单与"审批通过即长期生效"

1. **白名单管理**：平台超级管理员或其授权的人，才能**配置 URL/源并试解析**（后台接口 + 审批流，权限点如 `bidding:ext-source:*`）。
2. **试解析流程**：
   - 提交 URL → 下载+AI 试跑 → 返回"成功的数据 + 原文"预览；
   - 管理员点**审批通过**（可带 parserCode/校验规则/分类策略）→ 该 URL 绑定该 code，**以后该 URL（及同源规则）都按此 code 处理**；
   - 支持多次试跑/改配/再审批（审批记录留痕，可回溯换 code 后重处理）。
3. URL 归属：白名单之外默认不抓（防滥用/越权采集）；白名单+code 一并入 `bidding_crawl_source/bidding_notice_external`（仓库侧仅存配置镜像与结果）。

## 六、全链路"打回重做"与状态

`PENDING → DOWNLOADING → DOWNLOADED → PROCESSING → VALIDATING → (PASS → CALLBACK → 我方入库/ACTIVE) | (FAIL → RETRY/回源打回 → …≤3 → AI → AUDIT → 人工 APPROVED/REJECTED)`
- 每一跳记录 `taskId / urlHash / stage / attempt / error_code / error_msg / created_at`（审计表），失败原因随消息走。
- 我方接收后仍有**格式/长度复检**：不合格返回明确错误码 → 采集侧按错误类型打回重做（不静默丢弃）。

## 七、独立服务调我方接口的**身份认证**（重点）

采集服务→我方只开放"接收结果/查询配置/审批回调"等少量接口，身份验证方案（建议 A）：

**方案 A（推荐）— 服务账号 + HMAC 签名**
1. 我方管理员在后台创建"外部服务账号"：生成 `accessKeyId + accessKeySecret`（secret 只显示一次，支持轮换/禁用）；
2. 采集服务每次回调请求带：
   - Header `X-Access-Key: {accessKeyId}`
   - Header `X-Timestamp: {epochMs}`、`X-Nonce: {uuid}`（防重放）
   - Header `Authorization: HMAC-SHA256(secret, "{method}\n{path}\n{timestamp}\n{nonce}\n{bodySha256}")`
3. 我方校验：查服务账号 → 验签 → 时间窗（±5min）→ nonce 幂等缓存 → 通过后按账号权限放行；全部调用记审计日志。
4. 叠加可选：IP 白名单（部署环境固定时）；传输 TLS；禁止内网裸奔，统一走我方外部接入网关（API 网关/网关层做签名终结与限流）。
5. 管理员对 Python 服务的后台操作（白名单/审批）走我方既有 admin 鉴权（`@PreAuthorize` 权限码），与服务账号体系分开。

**方案 B（兜底）**：固定 API-Key（简单，但轮换/审计弱，仅内网/试验期）。
（此认证方案同适用于"白名单授权人试解析"时调用 AI/我方预览接口。）

## 八、仓库侧（txgy-module-bidding）配套（接收与展示，v0.2 范围外仅接口契约）

- 接收接口：`POST 采集回调（外部服务账号签名）`：入参=主列+原文引用+meta_json+校验结果；我方 `url_hash` 去重 upsert 到 `bidding_notice_external*`（沿用 v0.1 表草案：HTML 原样/PDF file_id+sha/附件/原网址/生效期/行业分类三态/审核状态）；
- 展示接口沿用 v0.1 §三 三形态（HTML 原样+原网址、PDF 用 JS 预览+原网址+下载、附件下载列表）；
- 审核/打回结果回调给采集侧（明确错误码，支持重做）。

## 九、法律与合规要点（相应法律法规）

| 事项 | 依据/做法 |
|---|---|
| 只采集公开信息 | 《网络安全法》《数据安全法》：不得绕过技术措施抓取非公开内容；仅白名单公开源 |
| 著作权/展示授权 | 《著作权法》：HTML 原样展示/PDF 原件缓存需**授权或仅摘要+原链接**（建议 v1 白名单源做摘要+署名+原网址，全文展示需源站授权）；应权利人要求下架 |
| robots/服务条款 | 尊重 robots（是否允许）；与 ToS 冲突的 URL 转人工评估，不默认强抓 |
| 个人信息 | 《个人信息保护法》：页内含专家/联系人等个人信息不收录敏感字段、展示脱敏；只处理公开招投标业务信息 |
| 数据分类分级 | 采集内容按 L 分级存储（L1/L2 存储、涉密不采）；AI 仅处理授权范围内的公开文本 |
| 接口身份/安全 | 服务账号+HMAC+审计（§七）；回调只经网关；全链路 TLS |
| 行业筛选 | "防腐保温行业"仅为聚合/推荐标签，页面声明"以原站/原公告为准"，不构成法律意见 |
| 爬虫频控 | 限速+UA 声明+失败退避；不做恶意并发冲击目标站（反不正当竞争风险规避） |

## 十、开放问题（推进前需确认）

1. 消息中间件选型：RabbitMQ / Kafka / Redis Stream（独立服务自带；建议 RabbitMQ 便于 TTL/DLQ 重试语义）。
2. 微服务部署形态与仓库归属：独立仓库/目录？是否也纳入 txgycloud 编排？
3. 我方"接收/审批"对外接口的路径与网关（`/open-api/…`）与签名密钥发放流程。
4. 首批白名单源 & 是否要求"原文全文展示授权"。
5. AI 供应商/模型与固定 Schema 版本管理（模板 code ↔ prompt/schema 版本）。
6. 防腐保温行业判定细则样例集（供 AI few-shot 与验收）。
